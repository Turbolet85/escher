## Design Philosophy

- **Radically modular, embeddable engine** — the engine is a set of separately usable crates around a headless DOM that external code drives and any renderer can paint.
  - The root manifest describes its crate as "Top level crate for Blitz" with keywords dom, ui, gui, react, wasm (Cargo.toml:252-254); a captured GitHub profile fixture shows the repository description "A radically modular HTML/CSS rendering engine" (examples/assets/github_profile_reduced2.html:93-95)
  - The blitz crate describes Blitz as "a modular, embeddable web engine with a native Rust API" that powers the dioxus-native UI framework (packages/blitz/src/lib.rs:3-5); it "does not bring any unique functionality" and re-exports the relevant crates as modules, each also usable stand-alone (packages/blitz/src/lib.rs:7-9; packages/blitz/src/lib.rs:24-42)
  - blitz-dom is a flexible headless DOM (`BaseDocument`) designed to be embedded in and "driven" by external code, with most users expected to use a wrapper (`HtmlDocument` from blitz-html, `DioxusDocument` from dioxus-native) (packages/blitz-dom/src/lib.rs:3-10); it holds the DOM tree, CSS parsing and resolution, layout and event handling, while html parsing (blitz-html), networking (blitz-net), rendering (blitz-paint) and windowing (blitz-shell) live in separate crates (packages/blitz-dom/src/lib.rs:12-14); its native Rust API is designed for higher-level abstractions, so any implementor can interact with the DOM and render it with any renderer (packages/blitz-dom/src/lib.rs:18-21)
  - blitz-traits holds types and traits enabling interoperability between the other Blitz crates "without circular or unnecessary dependencies" (packages/blitz-traits/src/lib.rs:1-2)
  - blitz-paint pushes anyrender drawing commands into an impl PaintScene, and the PaintScene implementation decides whether to rasterize, emit SVG/PDF, or serialize the commands (packages/blitz-paint/src/lib.rs:1-2; packages/blitz-paint/src/lib.rs:34-42); painting assumes styles and layout are already resolved (packages/blitz-paint/src/lib.rs:37-38; packages/blitz-paint/src/render.rs:170-174)
  - `dioxus-native-dom` is the "Core headless native renderer for Dioxus based on blitz" (packages/dioxus-native-dom/Cargo.toml:6; packages/dioxus-native-dom/src/lib.rs:3) and `dioxus-native` the "Native renderer for Dioxus based on blitz" (packages/dioxus-native/Cargo.toml:6; packages/dioxus-native/src/lib.rs:3); `stylo_taffy` is an implementation detail of `blitz-dom` that can also be used standalone as a reference for integrating stylo with taffy (packages/stylo_taffy/src/lib.rs:1-4; packages/stylo_taffy/Cargo.toml:4)
  - `accesskit_xplat` is a cross-platform AccessKit adapter similar to accesskit_winit but without depending on Winit (packages/accesskit_xplat/src/lib.rs:5-7); `wasm_hello` is a minimal WASM proof driving `BlitzApplication` on `wasm32-unknown-unknown` (examples/wasm_hello/src/lib.rs:1-4)
  - First-party inline SVG (`svg-native`) is parsed into Blitz's DOM rather than painted as an opaque image, so ordinary CSS including `:hover` applies inside it (examples/svg_native.rs:1-3); custom WGPU content can be rendered beneath layers of HTML and above layers blended with content underneath (examples/custom_widget.rs:42; examples/custom_widget.rs:48); transparency requires a transparent winit window, an alpha-aware compositing renderer with transparent base color, and CSS painting no opaque background (examples/transparent/src/main.rs:4-13)
  - The root `[package]` is a "virtual package" not meant to be published, existing so `cargo run --example XYZ` works (Cargo.toml:245-256); CI states Blitz only guarantees "latest stable", keeps an MSRV check to advertise its MSRV, and makes an effort not to increase MSRV in patch versions (.github/workflows/ci.yml:28-30)
- **Embedder services are injected, with no-op defaults** — networking, navigation, shell and parsing reach the DOM only through provider traits the embedder supplies.
  - `DocumentConfig` carries trait-object providers `NetProvider`, `NavigationProvider`, `ShellProvider`, `HtmlParserProvider` (packages/blitz-dom/src/config.rs:40-47); when one is not supplied, `BaseDocument::new` falls back to `DummyNetProvider`, `DummyNavigationProvider`, `DummyShellProvider` and `DummyHtmlParserProvider` (packages/blitz-dom/src/document.rs:432-443; packages/blitz-traits/src/net.rs:19-30; packages/blitz-traits/src/net.rs:165-173; packages/blitz-traits/src/navigation.rs:10-20; packages/blitz-traits/src/shell.rs:11-66)
  - blitz-net provides networking (HTTP, filesystem, Data URIs) as an implementation of the `blitz_traits::net::NetProvider` trait (packages/blitz-net/src/lib.rs:1-3)
  - blitz-vibey-script wraps a `BaseDocument`, executes `<script>` JavaScript with Boa and exposes DOM APIs backed by blitz-dom (packages/blitz-vibey-script/src/lib.rs:1-6); boa_runtime's fetch and AbortController are deliberately not registered because "fetch should go through the embedder's net provider, not an internal HTTP client" (packages/blitz-vibey-script/src/runtime.rs:1311-1316); uncaught JS errors are captured and the embedder drains them and decides how to surface them (packages/blitz-vibey-script/src/document.rs:251-261)
  - `DioxusDocument` integrates `BaseDocument` with `VirtualDom`; UI events are pushed with `handle_ui_event` and changes flushed with `poll` (packages/dioxus-native-dom/src/dioxus_document.rs:41; packages/dioxus-native-dom/src/dioxus_document.rs:67-68)
- **Behave like a browser, and cite the spec** — web semantics are written against named specifications and named browser engines.
  - Spec-cited behaviour: WHATWG form-owner reset, form submission and form data set construction (packages/blitz-dom/src/form.rs:36; packages/blitz-dom/src/form.rs:70; packages/blitz-dom/src/form.rs:183), WAI-ARIA tree exclusion (packages/blitz-dom/src/accessibility.rs:96), HTML-AAM role mapping (packages/blitz-dom/src/accessibility.rs:192), CSS Transforms current transformation matrix (packages/blitz-dom/src/stylo_to_kurbo.rs:11-24), HTML dimension-value parsing (packages/blitz-dom/src/stylo.rs:917-923), Pointer Events `touch-action` intersection (packages/blitz-dom/src/events/pointer.rs:158-166), HTML implicit form submission (packages/blitz-dom/src/events/keyboard.rs:139), CSS Fonts feature precedence (packages/blitz-dom/src/stylo_to_parley.rs:264-273), css-images default object size, css-tables-3 abspos, CSS 2.1 Appendix E paint order, CSS2 §10.3.2, CSS Sizing 4 (packages/blitz-dom/src/layout/mod.rs:37-38; packages/blitz-dom/src/layout/mod.rs:371-374; packages/blitz-dom/src/layout/paint_tree.rs:293-297; packages/blitz-dom/src/layout/replaced.rs:149-158; packages/blitz-dom/src/layout/replaced.rs:132-141)
  - CSSOM mutation errors mirror the `DOMException` names JavaScript APIs throw (packages/blitz-dom/src/cssom.rs:38-69); interaction-state teardown on node removal matches WebKit/Blink semantics (packages/blitz-dom/src/document.rs:888-907; tests/blitz-tests/tests/interaction_state_teardown.rs:1-14)
  - Paint mirrors named engines: Chrome contrast ratio, WebKit/Blink darken and lighten, Chrome inset/outset shading, Chrome dashed-border ratios, Blink dash-gap selection, Chrome line-through position, Firefox per-box decoration, Chromium scrollbar contrast ratios (packages/blitz-paint/src/color.rs:27-28; packages/blitz-paint/src/render/border.rs:17-19; packages/blitz-paint/src/render/border.rs:44-53; packages/blitz-paint/src/render/border.rs:92-98; packages/blitz-paint/src/text.rs:97-99; packages/blitz-paint/src/text.rs:529-532; packages/blitz-paint/src/text.rs:583-586; packages/blitz-paint/src/render.rs:768-770); text is painted from its container element's resolved styles, described as matching how HTML works (packages/blitz-paint/src/render.rs:278-286); text decoration geometry is built explicitly so it renders consistently across renderers (packages/blitz-paint/src/text.rs:274-278)
  - Networking matches browsers: per-host concurrency cap of 6 (packages/blitz-net/src/lib.rs:23-24) and a single-user (private) HTTP cache "like a real browser", since the shared-cache default forces revalidation on `Set-Cookie` and gets the client rate limited (packages/blitz-net/src/lib.rs:100-112)
  - Overlay scrollbar fade timings and thumb dimensions are Chromium's overlay values (packages/blitz-dom/src/node/scrollbar.rs:12-16; packages/blitz-dom/src/node/scrollbar.rs:122-126); style-attribute mutation is copy-on-write mirroring Gecko's `nsDOMCSSDeclaration::EnsureBlockMutable` (packages/blitz-dom/src/node/element.rs:718-740)
  - A reference page lists the browser DOM APIs used by core Preact, React (react-dom) and the WPT harness (examples/preact/core_dom_apis.html:62-69), naming `createElementNS`-only creation and the `element[prop] = value` reflected-property fallback as the two easiest things to overlook when bootstrapping an engine (examples/preact/core_dom_apis.html:443-445); the flex example notes "Servo doesn't have: space-evenly? gap" (examples/flex.rs:1-5)
- **One incremental pipeline, safe identities** — style, damage, box construction, layout and paint topology are invalidated incrementally through a single code path, over versioned node ids.
  - Incremental and non-incremental layout run the same style → damage → box construction → layout pipeline; non-incremental marks every node damaged each resolve (packages/blitz-dom/src/document.rs:2000-2017; packages/blitz-dom/src/resolve.rs:85-91), so the two must produce identical layouts after any sequence of mutations (tests/blitz-tests/tests/incremental_oracle.rs:1-7)
  - Blitz runs a style pass then a separate layout pass (unlike Servo, which interleaves them), accepting it is slower because it is fast enough (packages/blitz-dom/src/layout/mod.rs:1-5); inline (Parley) layout construction is deferred to a dedicated phase so text shaping can be multithreaded (packages/blitz-dom/src/layout/construct.rs:619-624; packages/blitz-dom/src/layout/construct.rs:929-931)
  - The paint tree holds topology only, built once per frame after layout for damaged subtrees; geometry is derived at use time from `final_layout()` and memoised per geometry generation so a cached list cannot paint a box where layout no longer puts it (packages/blitz-dom/src/layout/paint_tree.rs:1-9; tests/blitz-tests/tests/paint_tree_incremental.rs:1-4)
  - Style changes are classified into damage bits and only nodes whose subtree needs relayout have their layout caches cleared (packages/blitz-dom/src/layout/damage.rs:45-53; packages/blitz-dom/src/layout/damage.rs:118-125); state changes (hover/focus/active/disabled) set no restyle hint and invalidation is driven by element snapshots (packages/blitz-dom/src/node/node.rs:687-697)
  - Device changes (resize, zoom, color-scheme, media type) are coalesced so the stylist device is rebuilt at most once per resolve (packages/blitz-dom/src/stylo_device.rs:1-5; packages/blitz-dom/src/stylo_device.rs:22-42; tests/blitz-tests/tests/device_coalescing.rs:1-3); a viewport resize invalidates only origins whose media query results changed and elements using viewport units (tests/blitz-tests/tests/resize_restyle.rs:1-3; tests/blitz-tests/tests/resize_restyle.rs:77-94)
  - Text decoration styles are kept out of Parley so they can change without rebuilding the Parley layout, read lazily at render time (packages/blitz-dom/src/stylo_to_parley.rs:506-521); user-initiated and programmatic scrolls share one scrolling primitive, differing only in the `ScrollRequest` (packages/blitz-dom/src/scrolling.rs:126-130)
  - Node storage is a versioned slotmap so a dropped node's id stops resolving instead of aliasing a reused slot (packages/blitz-dom/src/tree.rs:27-35); the slotmap key is used only at the storage boundary and all public APIs use `NodeId` (packages/blitz-dom/src/tree.rs:11-15); persistent interaction state references DOM nodes only, never layout-generated nodes, so it survives box-tree reconstruction (tests/blitz-tests/tests/interaction_state_canonicalization.rs:1-10)
  - `Node` carries only tree-structure information, other fields living on element data (packages/blitz-dom/src/node/element.rs:84-87); Taffy layout output is lazily boxed because inline-level elements are positioned by parley (packages/blitz-dom/src/node/element.rs:120-124; packages/blitz-dom/src/node/element.rs:152-154); cloning an element resets runtime style/layout state (packages/blitz-dom/src/node/element.rs:287-323); overlay scrollbar geometry is shared between painting and hit-testing "so the two cannot drift" (packages/blitz-dom/src/node/scrollbar.rs:1-3); `StyloData` encapsulates an `UnsafeCell` relying on Stylo's exclusive-access traversal model (packages/blitz-dom/src/node/stylo_data.rs:9-19); Blitz does not track browsing history, so all links are unvisited (packages/blitz-dom/src/node/element.rs:486-499)
- **Headless, measurable, testable** — the engine is exercised without a window through a headless harness, a WPT runner and phase-split benchmarks; the reference browser keeps its own state best-effort.
  - The test harness runs headless: no window, GPU or compositor is required, and synthesized input routes through the real event-dispatch pipeline (packages/blitz-test-harness/src/lib.rs:1-16); integration tests live in the `tests/` directory of the blitz-tests crate (tests/blitz-tests/lib.rs:1)
  - The WPT runner wraps `.any.js`/`.window.js` tests in a synthesized HTML page mirroring wptserve's handlers (wpt/runner/src/test_runners/js_wrapper.rs:1-4), runs testharness.js tests through `blitz-vibey-script` with a custom `testharnessreport.js` (wpt/runner/src/test_runners/harness_test.rs:1-3), keeps a fast no-JS path for `checkLayout()`-only attr tests (wpt/runner/src/test_runners/attr_test.rs:30-36; wpt/runner/src/test_runners/attr_test.rs:71-74), passes a crashtest if it parses, runs scripts, resolves and renders without panicking (wpt/runner/src/test_runners/crash_test.rs:17-19), runs JS timers on virtual time with a real-time backstop (wpt/runner/src/test_runners/mod.rs:121-128; wpt/runner/src/test_runners/mod.rs:133-163), mirrors wptrunner's `test-wait.js` reftest readiness (wpt/runner/src/test_runners/ref_test.rs:252-279), and follows the upstream WPT manifest filtering rules (wpt/runner/src/main.rs:184-214; wpt/runner/src/main.rs:222-226)
  - The paint benchmark separates a paint phase (blitz-paint `paint_scene` to renderer command encoding) from a rasterization phase (examples/paint_bench.rs:1-2)
  - The browser is "A web browser with UI powered by Dioxus Native and content rendering powered by Blitz" (apps/browser/src/main.rs:5); its persistence writes are best-effort and may silently no-op, history being UX state not load-bearing on the browser (apps/browser/persistence/src/lib.rs:5-19); persistence methods are synchronous and runtime-agnostic, callers keeping disk work off latency-sensitive threads (apps/browser/persistence/src/lib.rs:21-25); `HistoryService` is the single entry point for visit/favicon writes (apps/browser/src/browser_history.rs:104-111); only consecutive visits to the same URL fold into the head entry (apps/browser/src/browser_history.rs:51-72); the favicon cache stores only positive results (apps/browser/src/favicon.rs:9-15); chrome writes for a loaded document run as one straight-line block so a render cannot sample a half-applied state (apps/browser/src/tab.rs:126-148)
