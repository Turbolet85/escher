## Constraints
- A command must not be hangable by a load. security-plan §API Security («Settle and loads in flight» row) requires that the absent request timeout (same section, «Request timeout» row) cannot hang a settle or a driver command. It also requires the settle pass loop to stay bounded (64 passes). Today the row meets that by never waiting. The chunk must meet it with a fixed bound that ends every wait. The row's «never waits on one» / «no driver command waits on a load» wording is a recorded decision this chunk moves, and the wrap restates it (per security-plan §API Security).
- The stated bound must sit strictly below every transport bound that reads a call's answer, or a waiting call surfaces as a transport failure. The bounds are the client's 30 s read of a call's answer (`wire::ANSWER_BOUND`), read as `SessionError::Timeout`, and the host's one connection at a time with its 2 s read and write bounds (per security-plan §API Security, «Local session socket» row). Whether the host's 2 s bounds span the run of a call or only the request and reply lines is research's question.
- The bound must also sit below the cold-agent replay's 30 s per-reply bound (`REPLY_BOUND`) on `escher-session mcp` children (per security-plan §Input Validation, «Cold-agent check» row). Today the MCP server checks the idle expiry when a request arrives, with no timer or thread, so a waiting `tools/call` blocks the stdio loop for the length of the wait (per security-plan §Input Validation, «MCP server» row).
- No new input on the validated surface. `validate` checks a closed `'static` table of eleven verbs with six argument kinds, each bounded, and reads no clock. A wait bound passed as a call argument, or a new result field of a wait, would widen that surface (per security-plan §Input Validation, «Driver command schema» row). The «Settle and loads in flight» row also says no instance verb has an argument or a result field of a wait (per security-plan §API Security). The bound is a constant. Its value lives only in fixed `'static` help and `describe()` text on the ratified carriers.
- The «Driver command schema» row records that escher-driver's executor, session, schema, validation and JSON writer read no clock. It names the clocks that do exist: the host's accept loop for the idle expiry, and the MCP server's on request arrival (per security-plan §Input Validation, «Driver command schema» row). A wall-clock read for the wait changes that recorded fact, wherever P4 places it. The read must move no virtual time: `advance` stays the one mover of the session's clock (per security-plan §API Security, «Settle and loads in flight» row).
- A load still in flight when the bound passes is reported as a result, `settled: false` with the closed busy class `loads`, not as a refusal. It names a class only: no URL, request, node, id, name or value (per security-plan §API Security, «Settle and loads in flight» row). The refusal causes stay closed at eight (per security-plan §Error Handling).
- The fixture's delayed answerer opens no socket, port or listener and reads no env var. The escher-driver library and the `escher-session` binary read no env var beyond `RUST_LOG` (per security-plan §Secret Management, «Environment values read»). No served network API exists, so a new listener is a registration (per security-plan §API Security). The fixture stays offline and routes no URL through blitz-net, which has no request timeout or response-size cap (per security-plan §API Security, «Request timeout» and «Request size limit» rows).

## Patterns to follow
- A typed outcome naming a closed class only. `NotSettled { busy: Loads }`, written as `settled: false`, `busy: "loads"`, already says a load is in flight without a page value (per security-plan §API Security, «Settle and loads in flight» row).
- Fixed `'static` table text on the ratified carriers. The schema's help and `describe()` ride stdout and MCP as the program's own text, so the stated bound can be stated there with no new crossing (per security-plan §Input Validation, «MCP server» row and «CLI arguments (escher-session)» row).
- A transport bound pinned by a test at its edge. `client::imp::tests::an_answer_read_past_its_bound_is_a_timeout` holds `wire::ANSWER_BOUND`. A stated wait bound can be pinned against it the same way (per security-plan §Input Validation, «Driver session socket» row).
- A test-only stand-in served by no binary and reached by no caller is no crossing (per security-plan §Secret Management, the `TMPDIR` entry). An in-process delayed answerer follows that shape and stays in test code.

## Anti-patterns to avoid
- An unbounded wait on a load: one tied to the absent request timeout, or to a load the outside world may never answer (per security-plan §API Security, «Request timeout» row and «Settle and loads in flight» row).
- A new `command` span field, such as the time waited, a «waited» flag or a request count, added without a ruling. The span keeps its eight fields of fixed words, bools and counts, and logs no `Outcome` or `Call` content (per security-plan §Input Validation, «Driver command schema» row).
- A wait bound read from the call, an env var or a file. That is a new input on the validated surface (per security-plan §Input Validation, «Driver command schema» row) or a new env read (per security-plan §Secret Management).

- security ↔ arch: the stated bound and the move of «no driver command waits on a load» bind arch §Standard Contracts (Driver session; Harness settle) and the security plan's «Settle and loads in flight» row together (per security-plan §API Security).

Whether any kept check holds such a step is research's question (per security-plan §Input Validation, «Recorded check» row).
