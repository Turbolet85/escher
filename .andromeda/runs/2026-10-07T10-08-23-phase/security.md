# security extract

## Relevance
partial — settle is an in-process call on the held instance, so the chunk's security content is what it must NOT change (the two-verb wire, the env reads, the log fields, the dependency gate) plus one positive requirement: the wait has to end on its own bound, whatever the content or the net provider does.

## Constraints
- security-plan §Input Validation (row "Driver session socket (escher-driver)") requires the wire to stay a closed grammar of `hello v1` and `stop v1`, with a reply that carries a pid, the session's label and a count only. Settle adds no verb, no reply field and no settle outcome on that socket; a quiescence answer that travels over it is a new crossing, to be amended in the plan before it is built.
- security-plan §Threat Model Summary (attack-surface vector "local IPC — the driver session's socket") requires that no element id, accessible name, control value, snapshot text or diff crosses the socket. A typed "which source was still busy" outcome stays in process; whether the outcome type as designed can hold any of those five content classes is research's question.
- security-plan §API Security (rows "Request timeout" and "Request size limit") records that the net provider gives a request no timeout and a response no size cap. A pending load therefore cannot be relied on to end: settle's own bound has to end the wait, in a typed not-settled outcome — never a hang, never a return as if settled.
- security-plan §Threat Model Summary (attack-surface vectors "remote web content" and "script execution") treats document content and scripts as untrusted. A periodic timer, a running animation or a load that re-queues must not be able to hold a settle call open: the bound holds for any content, not only for the stand's. The plan's application-level threat model itself is marked not measured and is not cited here.
- security-plan §Secret Management ("Environment values read") requires that the escher-driver library and the `escher-session` binary read no env var beyond `RUST_LOG`. A settle bound or iteration limit is a constant or a call parameter, never an env read; whether the chunk's design needs it configurable at all is the plan's question.
- security-plan §Input Validation (row "CLI arguments (escher-session)") requires a closed argv of exactly two arguments, nothing on stdout on any path, and a fixed error message holding no path, label, id or value. If the host is touched (the `TimerTicks` handle it keeps), its argv, its stdout silence and its error text stay as that row states.
- security-plan §Dependency Security ("Audit tool", "Pinning") requires any dependency the chunk adds to be inherited through the workspace, locked in the committed `Cargo.lock`, built with `--locked` and passed by the cargo-deny audit leg; whether the settle loop needs a crate the workspace does not already resolve is research's question.

## Patterns to follow
- A failed load is dropped and its waiters are released rather than left pending — per security-plan §Error Handling ("Internal logging", the failed-resource-load bullet). The loads leg needs every pending set settle reads to be released on failure as well as on success; the plan states it for image waiters only, so whether the other pending sets clear on a failed or discarded answer is research's question.
- Stale ids resolve to nothing and missing state returns early instead of panicking — per security-plan §Error Handling ("Graceful degradation"). A settle loop that reads nodes or pending sets across polls uses the non-panicking readers.
- Typed errors with fixed, content-free text at a boundary — per security-plan §Input Validation (rows "Driver session state directory" and "CLI arguments (escher-session)"). The not-settled outcome follows the same shape: a closed set of source names, no free text taken from the document.
- Cancellation through the document's `AbortSignal` — per security-plan §API Security (row "Cancellation"). It is the recorded way to end in-flight fetches tied to a document; whether the loads fixture or a bounded settle should use it is the plan's choice.

## Anti-patterns to avoid
- Carrying settle state, a busy-source name or anything of the screen over `session.sock`, or adding a third verb to it — barred by security-plan §Input Validation (row "Driver session socket (escher-driver)").
- Logging what settle waited on with a content-bearing field (a pending load's URL, an element id, an accessible name, a control value), or printing unconditionally — security-plan §Logging & Monitoring ("Log format and backends") requires engine call sites behind the crate's `tracing` feature and names the fields escher's sink prints or redacts; a field outside those sets is a plan amendment first.
- Routing the loads fixture through `blitz-net` or any real fetch — security-plan §Input Validation (row "`file:` URLs (net provider)") records no path restriction on that provider; the fixture answers its own requests in process.
- security-plan §Security Anti-Patterns holds no recorded intent; nothing is extracted from it, and the three bans above come from the sections they cite.

## Contract bindings
- security ↔ obs: any field settle logs falls under the scrub sets security-plan §Logging & Monitoring names (the engine safe-field list and the `escher_*` redacted list), which the obs plan's scrubbing contract shares; the span over the settle wait belongs to the later "Driver command spans" entry, not to this chunk.
- security ↔ tests: the two-verb wire is proven by the session checks and the host-log check named in security-plan §Input Validation (row "Driver session socket (escher-driver)") and §Logging & Monitoring ("Log format and backends"); a settle change to `Session` or to the host must leave those checks green, and the loads fixture must use no real network and no real user data.
- security ↔ architecture: a new listener, port, env var or workspace crate is a resource registration before it is code; security-plan §API Security states one listener and no served network API, and the chunk's scope commits to adding none.
- Anchor note for the planner: the scope names "security-plan §Surfaces", which is a heading of `.claude/rules/security.md`, not of the security plan. In the plan the same content sits under §Threat Model Summary (the local-IPC vector), §Input Validation (the driver-session rows) and §API Security (row "Local session socket (escher-driver)"); an amendment, if one is needed, targets those.

## Acceptance criteria contributions
- The session socket still answers `hello v1` and `stop v1` only, any other request line is still refused, and no reply gains a field: the existing session lifecycle checks pass unchanged against the chunk's build (per security-plan §Input Validation, row "Driver session socket (escher-driver)").
- A settle call on a fixture whose load is never answered returns the typed not-settled outcome inside its bound, with no sleep, no wall-clock read, no panic and no hang, in both layout modes (per security-plan §API Security, row "Request timeout"; §Error Handling, "Graceful degradation").
- An env-read census over the files the chunk touches in escher-driver, the harness and the `escher-session` host finds no read beyond `RUST_LOG` (per security-plan §Secret Management, "Environment values read").
- If the chunk adds a log call site or a dependency: the host-log check still finds no stable id and no accessible name on `escher-session`'s stderr at any `RUST_LOG` level with stdout empty (per security-plan §Logging & Monitoring, "Log format and backends"), and `bash .github/scripts/ci-leg.sh audit` passes on the committed lockfile (per security-plan §Dependency Security, "Audit tool").
