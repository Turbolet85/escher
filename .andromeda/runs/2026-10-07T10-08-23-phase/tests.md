# tests extract

## Relevance
relevant — the chunk changes the headless `Harness` drive surface and the stand checks that test-plan §3 records (test tier `0`, per test-plan §1 Test tier); the plan itself holds no settle or quiescence mandate, so every item below is a recorded contract the chunk must keep or amend, not a settle spec.

## Constraints
- test-plan §3 Pump semantics requires that `pump` polls with no waker context and resolves at the harness time, and that `dispatch` / `dispatch_recorded` do not pump; test-plan §3 Input helpers requires each input helper to pump after its dispatch. A settle call is new surface beside these: existing callers' semantics must hold, or the plan's wording is amended at wrap. Whether the one pump an input helper already runs leaves the instance settled is research's question.
- test-plan §3 Construction requires stand checks to boot through `seven_guis::stand::boot` / `boot_timer` with `stand::options(incremental)` — the settle proof uses that drive surface, not a boot of its own.
- test-plan §8 Time (seven_guis timer) requires `TimerTicks` to be the timer's one stand-in: a delivered tick is applied on the next pump, an undelivered source holds elapsed at 0.0 s. The settle proof drives the timer only through that handle; "applied on the next pump" is the sentence the chunk's timers decision changes or keeps.
- test-plan §5 Session ↔ held instance records that on a held session timer time moves only by delivered ticks (`stand_session_state`). A settle that advanced ticks on its own would contradict that recorded claim — the timers decision must either keep it or name the amendment.
- test-plan §2 Font-dependent tests requires headless-stand checks to assert unconditionally under the bundled font with no skip path; test-plan §7 Builders and options requires the layout mode to come from `HarnessOptions.incremental` through `stand::options(incremental)` — the proof runs once per mode.
- test-plan §3 `run {selection}` requires `run stand` to select one `--test` per `tests/blitz-tests/tests/stand_*.rs` and to read libtest's pretty lines as events: a new `stand_*.rs` file is selected by its prefix with no script change, a shared module directory is not, and an empty run is never a pass.
- test-plan §3 session-wire (Session lifecycle key) requires the socket to carry `hello` and `stop` only; test-plan §3 session-start requires a check to read the held instance through `harness()` / `harness_mut()`. Settle on a session is an in-process call; whether `Session` needs a new method or the existing accessors suffice is research's question. test-plan §3 session-checks applies only if the chunk adds a check that starts a host process (bounded waits, kill-and-reap guard, `cfg(unix)`).

## Patterns to follow
- One integration-test file per behaviour under `tests/blitz-tests/tests/`, a stand check declaring `mod common;` and reading the shared tables and helpers (`boot`, `by_id`, `node`) rather than restating them (per test-plan §3 blitz-tests (stand checks)); a session-held check reads `hold(task, incremental)` and `change(task, session, ticks)` from `session_common` (per test-plan §3 blitz-tests (session checks)).
- The loads leg's stand-in is the hand-written `ManualNetProvider` — it holds requests and the test delivers the response when it chooses (per test-plan §8 Network); it reaches the harness through `HarnessOptions.net_provider`, which `stand::options` sets to `None`, so the fixture overrides that one field (per test-plan §7 Builders and options). A fixture "booted with the stand's options" in the check's own file is the recorded shape for a case the lean tasks lack (per test-plan §1 tests/blitz-tests).
- Unit tests sit in `#[cfg(test)] mod tests` inside the source file (per test-plan §4 Test file location); a blitz-dom unit test builds `BaseDocument` from `DocumentConfig` and the DOM through `DocumentMutator`, since blitz-html would be a circular dev-dependency, and pins a load path by driving `load_resource` with a fabricated `ResourceLoadResponse` (per test-plan §2 blitz-dom pipeline tests; test-plan §5 DOM ↔ resource loading).
- Timers outside the stand already have virtual-time seams — blitz-vibey-script's virtual time and `without_timer_thread` for embedders that drive timers by hand (per test-plan §3 blitz-vibey-script), used by the WPT runner (per test-plan §8 Time (WPT)). They are the recorded precedent for the "pending but not due" decision; whether the harness can reach them is research's question.
- Idle behaviour is already pinned: a pump with nothing pending reads an empty diff and a false `has_changes` on every lean task (per test-plan §1 tests/blitz-tests, `stand_diff`), and an idle `resolve` marks nothing in either layout mode (per test-plan §1 blitz-dom covered behaviours). A settle on an idle instance must leave both readings as they are.

## Anti-patterns to avoid
- The plan's own anti-pattern section records none, and the plan states no no-sleep rule anywhere: scope.md attributes one to test-plan §3, but its source is `.claude/rules/testing.md` §Determinism as scope's Boundaries cite it (not read here). The one real-time sleep the plan records is an observation of the blitz-vibey-script timer tests (per test-plan §2 Script tests), not a sanctioned pattern — do not read it as precedent for a settle check.
- No `dispatch_recorded` in a settle check over the Dioxus stand: it drives the underlying `BaseDocument` and bypasses the VirtualDom forwarding the delayed update travels through (per test-plan §5 Harness ↔ event pipeline).
- No image injected straight into `background_images` with `Status::Ok` as the loads proof: that seed skips the request, so nothing is ever pending (per test-plan §7 Seed strategies, Image loads).

## Contract bindings
- tests ↔ architecture — the `Harness` surface test-plan §3 Core and §3 Pump semantics record, and the session API the Session lifecycle key defers to architecture §Standard Contracts → Driver session: a settle call on either is one amendment in both plans.
- tests ↔ obs — test-plan §3 Stand log format binds the `escher-session` host's stderr to obs-plan §3 / §8 (no stable id and no accessible name at any level, pinned by seven_guis `host_log`): anything settle logs on the host path stays inside that reading. The agent-run events are harness metadata, not a telemetry sink (per test-plan §3 Events).
- tests ↔ security — test-plan §3 session-wire carries nothing of the screen; a settle outcome that crossed the socket would be a new crossing under security-plan §Surfaces.
- tests ↔ a11y — none: the a11y leg's three files are unchanged by this chunk (per test-plan §9 Legs).
