# a11y extract

## Relevance
partial — the chunk adds no UI surface, role, name, focus order or painted colour (scope §Surfaces reads "a11y-plan — none expected", marked inferred), but it works in the three places the a11y plan's tree-refresh and focus contracts sit: the engine's changed set and `Document::poll` / `resolve`, the headless harness pump the stand's focus checks run through, and the driver session's feature set.

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary): the chunk's a11y obligation is to leave keyboard operability, focus order and painted colours as they are, not to add assertions of a new criterion.
- a11y-plan §2 (Accessibility tree lifecycle) requires the platform tree to be refreshed on change through one path: the shell's `View::poll` takes the changed set on a poll that reported work and rebuilds the tree when the set it took was non-empty. The chunk's scope names `has_changes` / `take_changed_nodes` and `Document::poll` among its code surfaces — a settle loop must not change what `Document::poll` reports to the shell, nor move a drain of the changed set into a path the shell's poll shares. Whether the settle design reads or drains the changed set at all is research's question.
- a11y-plan §2 (Accessibility tree lifecycle) requires the changed set to keep its marking rule — a mutation of an in-document node, a focus or checked change and a text control's input mark it; node creation, hover, active, scroll and layout do not. A settle signal built on `has_changes` inherits that rule: a layout-only or hover-only pass does not read as change. Whether the settle design leans on that flag as a quiescence source is research's question.
- a11y-plan §2 (Accessibility tree lifecycle) records the windowed witness of the refresh as still owed on the working route's "Stand a11y assertions". This chunk is headless and its scope leaves the windowed path unchanged — it neither discharges that witness nor may claim it.
- a11y-plan §5 (Focus order per layout) records two engine paths that move focus with no input: the `autofocus` feature focuses the latest mounted `autofocus="true"` node on flush, and removing the focused node resets focus to the body (per a11y-plan §5 Focus restoration). A settle loop repeats polls and flushes; the focus reading after a settle must equal the reading one hand pump gives today. Whether a repeated poll and resolve can re-fire either path is research's question.
- a11y-plan §1 (A11y Scope Summary, Dioxus crates) records that `escher-driver` names no feature of `dioxus-native-dom`, so the `escher-session` host builds no accessibility code, and that the entry that first reads the snapshot through a session decides the feature then. If settle on the held `Session` reads a snapshot, this chunk is that entry and the decision is a stated one in the plan; if it reads none, the manifest's feature set stays as it is.
- a11y-plan §7 (Accessibility tree output) requires the stand's 15 interactive controls to carry an HTML-AAM role and a non-empty accessible name in both layout modes with the Tab order unchanged. The chunk's proof runs on the Timer task and its scope lists `tasks/timer.rs` and `stand.rs` among its surfaces — an edit there keeps every control's `id`, role, name and Tab position.

## Patterns to follow
- A11y assertions are Rust tests in blitz-tests over the AccessKit tree, built after `resolve` (per a11y-plan §3 A11y testing tool pick) — a settle check that reads a11y state reads it after settle returns, through the same tree, in the same crate.
- Keyboard focus is driven through the harness's `press` / `press_with` and read back from the snapshot and the tree's focus (per a11y-plan §3 Keyboard test harness; a11y-plan §5 Test harness pattern) — the no-sleep stand flow uses the harness's own input helpers, not a second input path.
- The snapshot, its text form and its diff are readers of the accessibility tree's role, name and focus with no second mapping (per a11y-plan §7 Accessibility tree output) — a post-settle state assertion reads through them rather than deriving role, name or focus again.
- Expected roles, input names and rendered ids are stated once, in the stand checks' shared tables `controls`, `INPUT_NAMES` and `rendered` (per a11y-plan §7 Accessibility tree output) — a new stand check for the Timer flow reads those tables.
- Stand a11y readings are proven in both layout modes (per a11y-plan §7 Accessibility tree output; a11y-plan §5 Test harness pattern) — the same `for incremental in [false, true]` shape the scope already sets.

## Anti-patterns to avoid
- a11y-plan §11 (A11y Anti-Patterns) reads `NO RECORDED INTENT` — no ban is extracted from it. The two items below are the inverse of measured sections, not recorded bans.
- Draining the changed set inside a call the windowed shell also makes, so the shell's poll takes an empty set and the platform tree stops refreshing — the state the plan records as the pre-fix defect (per a11y-plan §2 Accessibility tree lifecycle).
- Turning on `dioxus-native-dom`'s `accessibility` feature for `escher-driver` as a side effect of a settle helper, with no stated decision (per a11y-plan §1 A11y Scope Summary, Dioxus crates).

## Contract bindings
- a11y ↔ architecture: the tree refresh is "one item" with the engine's changed-set contract (a11y-plan §2 Accessibility tree lifecycle) — it binds to architecture §Cross-cutting Patterns (Invalidation and state integrity), which the scope names as touched. A change to the changed set's marking or drain is an amendment to both.
- a11y ↔ tests: the stand's focus and role checks run on the headless harness's pump (a11y-plan §3 Focus management test harness; a11y-plan §5 Test harness pattern) — it binds to test-plan §3 (the harness contract), where the scope places the pump change. A changed pump is the same pump under those checks.
- a11y ↔ tests (CI): the `a11y` leg runs in ci.yml's slow tier behind the fast jobs (a11y-plan §9 CI Integration) — it binds to the test plan's CI section; the tests extract owns that anchor.
- a11y ↔ obs: none for this chunk — the violation schema against the obs log format sits under a `NOT YET MEASURED` mark in a11y-plan §3 and is not extracted.
- The plan's one keyed contract (`Bootstrap phases`, labels `contrast-verification-harness-setup` · `a11y-ci-gate-wire`) is not turned on by this chunk and was not read.
