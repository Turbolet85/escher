# security extract

## Relevance
relevant — the chunk decides how a password input's text is kept out of the snapshot and which `disabled` reader the snapshot trusts, both on a reader security-plan §Input Validation already registers; it must do so without opening a crossing or a log path (security-plan carries no masking rule yet — that row is the wrap's amendment).

## Constraints
- **No new crossing.** security-plan §Input Validation (row `Markup attributes · id (stable element id)`) registers `DioxusDocument::snapshot` as an in-process reader with no wire form and no log, event, socket or file carrying it, the platform accessibility adapter being the only exit. Every state reading this chunk adds or changes must leave that row true: no serialization, no file, no env read (security-plan §Secret Management → Environment values read lists the only permitted reads), no listener (security-plan §API Security: no served API surface).
- **A password's text has more than one path, and one of them already leaves the process.** security-plan §Input Validation (row `Markup attributes · aria-label · <label for> (accessible names)`) registers that names reach the platform accessibility adapter like any text run, and that the snapshot resolves the same names into `SnapshotNode.name`. So masking `value` alone is not sufficient if the accessibility tree derives a name, label or value from a password input's typed text — and a mask applied only in the snapshot would not cover the adapter exit. Whether the tree carries a typed password's text on any node property is research's question; security-plan itself states no masking requirement (security-plan §Authentication & Authorization records `<input type="password">` only as a role mapping, not as a credential surface), so the masked form and its reach are a P4 decision, recorded at wrap.
- **A value and a name are user content: no log path.** security-plan §Logging & Monitoring → Log format and backends requires escher's sink to redact content-named fields (`value`, `text` among them) at any target and print only the allowlisted fields for engine targets; it also records that the upstream apps' subscribers and the WPT runner's logger are unscrubbed and that the chained panic hook prints the raw panic message. The chunk adds no log field, `println!` or panic/`expect` message that carries a node's value or name in `snapshot.rs` or `mutation_writer.rs` — a masked value must not reach a sink unmasked through a diagnostic.
- **Resolve, never index; no panic.** security-plan §Input Validation (`id` row) requires the snapshot to resolve each tree id through `BaseDocument::get_node`, never by index, and to omit a node that does not resolve; security-plan §Error Handling → Graceful degradation requires stale ids to resolve to `None`. Every new state reader (enabled, checked, value for `range` / `select`, focused) keeps that shape; whether the current readers already do so on each control is research's question.
- **`enabled` follows one registered `disabled` reader.** security-plan §Input Validation (row `Markup attributes · disabled`) registers two readings — a parsed boolean for focusability, and presence alone (a literal `"false"` included) for the DISABLED state and for pointer/click default actions. The snapshot's `enabled` is what a later driver will trust before acting, so its choice must be stated against that row and must not read a control as enabled that the engine refuses to act on (or the reverse) for content that parsed HTML can carry; where the two readers disagree is research's question, and the row is re-stated at wrap.
- **Values that are not on-screen text.** security-plan §Data Protection → Local user data handled registers that a chosen file's full filesystem path is stored in a file input's `value` attribute, and security-plan §Input Validation (row `Paint values · Hidden inputs`) that a `type=hidden` input is not painted. A value reader that falls through to the `value` attribute could carry a host path, or a value the screen never shows, into the snapshot. Whether the snapshot's value reader reaches a file or hidden input (and whether the accessibility tree keeps such a node at all) is research's question; if it does, P4 treats it alongside the password mask rather than leaving it implicit.
- **No new dependency, no real credential in a fixture.** security-plan §Dependency Security → Pinning requires `--locked` builds and workspace-inherited versions, and its Audit tool / CI integration paragraphs require any new crate to pass the cargo-deny audit leg; the chunk is expected to add none. security-plan §Secret Management → Never in code requires that source and fixtures hold no secret: the password fixture's typed string is an obviously synthetic literal.

## Patterns to follow
- The registered in-process reader shape — takes no argument, copies from the accessibility tree and the document, resolves through `get_node`, omits what does not resolve, logs nothing (security-plan §Input Validation, `id` row; `snapshot` and `unkeyed_actionable` are both registered this way).
- Name resolution kept in-process and cycle-guarded, adding no input class (security-plan §Input Validation, accessible-names row) — the path the password-name check must follow.
- Attribute reads that fail closed: `attr_parsed` yields `None` on a parse failure rather than panicking (security-plan §Input Validation, row `Markup attributes · attr_parsed`).
- If the falsy-boolean fix lands in the bridge: unsupported `AttributeValue` types are ignored, not coerced (security-plan §Input Validation, row `Dioxus mutations · Attribute value types`) — widen the clear list in that style, since the bridge serves every Dioxus document.
- Engine telemetry only behind the crate's `tracing` feature, read through the allowlist scrub (security-plan §Logging & Monitoring → Log format and backends).

## Anti-patterns to avoid
(security-plan §Security Anti-Patterns reads NO RECORDED INTENT — nothing is extracted from it; the bans below come from the sections cited.)
- Indexing the node slab with a tree id, or `unwrap`/`expect` on a node lookup, in a state reader (security-plan §Input Validation, `id` row; security-plan §Error Handling → Panic paths lists the existing ones — add none).
- Putting a control's value or name into a log field, a `println!`/`eprintln!` in library code, or a panic message (security-plan §Logging & Monitoring → Log format and backends).
- Giving the snapshot a serialized or wire form, or any exit other than the registered adapter, in this chunk (security-plan §Input Validation, `id` and accessible-names rows).

## Contract bindings
- **obs ↔ security:** the scrub set that redacts `value` / `text` (security-plan §Logging & Monitoring) binds to obs-plan's scrubbing contract — the chunk adds no content-named field, so neither plan's set should need widening.
- **a11y ↔ security:** the accessibility tree is both the snapshot's source and the one process exit (security-plan §Input Validation, `id` and accessible-names rows); what the tree carries for a typed password input is shared ground with a11y-plan, and a mask decided in one reader must be reconciled with the other.
- **tests ↔ security:** the fixture's password string is synthetic (security-plan §Secret Management → Never in code); the agent-run `run.log` and `target/ci-logs/` hold raw libtest output unscrubbed (security-plan §Logging & Monitoring, agent-run paragraph), so a failing assertion prints whatever it formats.
- **arch ↔ security:** `NodeState`'s shape and the "no new crate, port, env var or listener" rule are arch §Standard Contracts / §Occupied Resources; the security-plan rows above are amended at wrap alongside them (a password's masked value; the `disabled` reader the snapshot follows).

## Acceptance criteria contributions
- (security) With a known string typed into a password input on the fixture, that string occurs in no field of any snapshot node — `value`, `name`, or any other — for `incremental in [false, true]`; the test asserts absence across the whole tree, not only on the password node (per security-plan §Input Validation, rows `Markup attributes · id (stable element id)` and `aria-label · <label for> (accessible names)`).
- (security) The chunk's diff adds no call site in `packages/dioxus-native-dom/src/snapshot.rs` or `mutation_writer.rs` that logs, prints or panics with a node's value or name; grep of the diff for `tracing::`, `log::`, `println!`, `eprintln!`, `panic!`, `expect(` verifies (per security-plan §Logging & Monitoring → Log format and backends).
- (security) The snapshot gains no wire form and the workspace no crossing: the diff adds no serialization derive on `SnapshotNode` / `NodeState`, no file, socket or env read, and `Cargo.lock` gains no crate — or `bash .github/scripts/ci-leg.sh audit` passes if one is added (per security-plan §Input Validation, `id` row; security-plan §Dependency Security → Audit tool).
- (security) Every state reader added or changed resolves nodes through `get_node` with no index and no `unwrap` on the lookup, and a snapshot taken after a control is removed returns without panic (per security-plan §Input Validation, `id` row; security-plan §Error Handling → Graceful degradation).
