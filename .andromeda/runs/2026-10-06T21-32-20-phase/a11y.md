# a11y extract

## Relevance
partial — the chunk adds no painted surface of its own, but it proves `focused` and `enabled` (focus order and focusability are a11y surface at tier 0, per a11y-plan §1 A11y tier), reads every state through the accessibility tree's consumer (per a11y-plan §7 Accessibility tree output), and adds a minimal fixture with new controls (checkbox, radio, password) that fall under the role, name and key requirements.

## Constraints
- Tier and target: a11y tier 0 with SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y tier). Of these the chunk touches SC 2.1.1 and SC 2.4.3 through the `focused` and `enabled` readings; SC 1.4.3 is touched only if the fixture or a state change alters painted colours.
- The snapshot is a consumer of the accessibility tree: a11y-plan §7 Accessibility tree output requires role, name and the focused node to come from the tree `accessibility_tree` returns, with no second role or name mapping. A state reader this chunk adds or changes must keep that shape for role, name and focus; whether the `enabled` / `checked` / `value` readers the code holds today already sit beside it without a second mapping is research's question.
- Focus is reported once: a11y-plan §7 Accessibility tree output requires the focused DOM node to be the tree's focus, and requires that on the stand nothing reads focused at boot and exactly one node does after a focus move, in both layout modes. The chunk's pointer-focus and keyboard-focus proofs extend that requirement; they must not introduce a second source of truth for focus.
- Disabled-ness has two engine readers that disagree on some inputs (per a11y-plan §5 Focus order per layout (engine)): the element state and click target follow the attribute's presence, focusability follows its parsed value. The snapshot's `enabled` must name which reader it follows, and where the two disagree a control that reads disabled while still focusable (or the reverse) is an SC 2.1.1 / 2.4.3 fidelity question, not only a data one. Where they disagree on the stand and on the fixture is research's question.
- Focus side effects of real input are part of the reading (per a11y-plan §5 Focus restoration): a checkbox or radio click moves focus to the control, and a click on a non-interactive area clears focus. The `checked` proof through real input therefore changes `focused` in the same snapshot, and the "nothing focused" case has a specified way to be reached.
- Fixture controls carry the same accessible-tree obligations as stand controls (per a11y-plan §7 Accessibility tree output; roles per a11y-plan §4 Per-component pattern catalog (engine mapping), Form input row): each interactive control reads its HTML-AAM role and a non-empty accessible name, and every element an agent can act on reads an author key (the actionable-key rule, a11y-plan §7). Whether the fixture is reachable by `DioxusDocument::unkeyed_actionable` as the stand tasks are is research's question.
- Hidden exclusion and the Dioxus falsy-boolean write (per a11y-plan §4 Per-component pattern catalog, Hidden content row; a11y-plan §5 Script and framework exposure): the plan requires `hidden` to exclude a node from the tree and records the `hidden: false` drop as recorded, not established. The chunk's measurement of that hypothesis is the a11y plan's open item; a confirmed drop means a visible control is missing from the tree assistive technology reads, not only from the snapshot.

## Patterns to follow
- A11y assertions are Rust tests in blitz-tests over the AccessKit tree, with `blitz-dom` and `dioxus-native-dom` built under the `accessibility` feature (per a11y-plan §3 A11y testing tool pick; a11y-plan §1 A11y scope, blitz-tests row). The chunk's state proofs follow that form rather than a new tool.
- The stand snapshot check's standing shape: every snapshot node's role and name compared against its accessibility node, focus asserted at boot and after one move, for both layout modes (per a11y-plan §7 Accessibility tree output; a11y-plan §8 Error recovery).
- Focus sequence asserted through the engine's own focus-move entry points and the harness's focused-node query (per a11y-plan §5 Focus order per layout (engine); a11y-plan §3 Focus management test harness). A keyboard-event (Tab key) navigation test is recorded as observed absent (per a11y-plan §5 Test harness pattern); whether the chunk's keyboard-focus proof goes through a synthesized Tab key or through the focus-move call is research's and the plan's to settle, and it should say which.
- State cues asserted without colour: the flight booker's invalid-date check asserts the class and the `disabled` attribute, not the painted red (per a11y-plan §8 Error recovery). The `enabled` proof on Book and the return-date input follows that pattern.
- Names for inputs come from `<label for>` or `aria-label`, bound after the tree is built (per a11y-plan §7 Accessibility tree output). The fixture's checkbox, radio and password inputs take their names the same way.

## Anti-patterns to avoid
- a11y-plan §11 A11y Anti-Patterns records no bans (it reads NO RECORDED INTENT), so none is extracted from it; the items below are the inverse of requirements other sections state.
- A second role, name or focus derivation inside the snapshot, bypassing the tree (contrary to a11y-plan §7 Accessibility tree output).
- Keying or naming a fixture control by adding `tabindex`, a `role` override or any change to focusability or Tab order — the plan's keying is by `id` alone (per a11y-plan §7 Accessibility tree output, actionable-key rule); and masking a password by blanking or altering its accessible name rather than its value.
- Proving a state only by its painted cue (colour, opacity) instead of the attribute or tree state behind it (per a11y-plan §8 Error recovery; a11y-plan §6 State color (not-color-alone)).

## Contract bindings
- a11y ↔ architecture: the two `disabled` readers (a11y-plan §5 Focus order per layout (engine)) are the same decision the scope cites at arch §Established Decisions → DOM semantics; the Dioxus falsy-boolean write (a11y-plan §5 Script and framework exposure) is arch §Standard Contracts → Dioxus DOM bridge; the `NodeState` shape is arch §Standard Contracts. One decision, three records — the wrap amends them together.
- a11y ↔ tests: the proof files are stand checks (`stand_` prefix) under test-plan §3; the CI `a11y` leg runs three named accessibility test files and carries no stand assertion (per a11y-plan §9 CI Integration), so the chunk's a11y proofs ride the workspace test leg unless the plan deliberately adds one to the `a11y` leg — a CI-invariant change if so.
- a11y ↔ security: password masking is security-plan §Input Validation's to own; the a11y side of it is only that the masked control keeps its role and accessible name (a11y-plan §7 Accessibility tree output). What the tree itself carries for a typed password input is research's question.
- a11y ↔ layouts: focus order per surface binds to layout-templates' focus sequence for the four lean tasks; the chunk must leave that sequence unchanged (per a11y-plan §7 Accessibility tree output, Tab order requirement).
- a11y ↔ obs: none recorded — the violation schema in a11y-plan §3 is marked not measured, so nothing is bound here.

## Acceptance criteria contributions
- (a11y) After a pointer click on a stand control and, separately, after a keyboard focus move, exactly one snapshot node reads `focused` and it is the node the accessibility tree reports as focus; with focus cleared, none does — for `incremental in [false, true]` (per a11y-plan §7 Accessibility tree output; a11y-plan §5 Focus restoration)
- (a11y) Each disabled stand control (the flight booker's return-date input and Book button, CRUD's Update and Delete) reads disabled in the snapshot by the reader the chunk names, the reading flips when the app enables it, and each lean task's forward focus sequence is unchanged by the chunk (per a11y-plan §5 Focus order per layout (engine); a11y-plan §8 Error recovery)
- (a11y) Every interactive control on the minimal fixture reads its HTML-AAM role (checkbox, radio, password input), a non-empty accessible name equal to its accessibility node's name, and an author key — the actionable-key check returns nothing for the fixture (per a11y-plan §4 Per-component pattern catalog (engine mapping); a11y-plan §7 Accessibility tree output)
- (a11y) A control rendered with a Dioxus falsy `hidden` is present in the accessibility tree and in the snapshot, or its absence is recorded as a measured defect with its owner named; a truly hidden control stays excluded (per a11y-plan §4 Per-component pattern catalog, Hidden content row; a11y-plan §5 Script and framework exposure)
