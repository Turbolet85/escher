# layouts extract

## Relevance
partial — the chunk builds no surface and moves no component; it reads state off the seven_guis TaskShell stand that layout-templates §Surface: desktop-native → Primary screens describes, and it may add one minimal fixture screen the plan has no row for.

## Constraints
- The proof surface is the headless stand, not Home: layout-templates §Surface: desktop-native → Primary screens requires the stand to skip Home and mount one lean task (Counter, FlightBooker, Timer, Crud) in TaskShell through `task_in_shell`, with the header-over-body hierarchy that bullet names. Every state reading the chunk proves on "the stand" is a reading of a node inside that task body.
- The viewport is pinned: the same bullet requires the stand's fixed size, scale, colour scheme and bundled font, and layout-templates §Surface: desktop-native → IA notes requires the harness default to match it. The chunk's stand checks must not introduce a second viewport; a fixture that boots beside the stand inherits the same pin unless P4 records a reason.
- Controls are addressed by the author ids the plan lists: layout-templates §Surface: desktop-native → Primary screens requires each lean task's controls and value displays to carry an author `id` that is its stable element id, and CRUD's rows the `crud-person-{person.id}` form. The chunk's per-control state checks (disabled return date and Book, disabled Update and Delete, typed name / surname / filter, the timer's duration control) address nodes by those ids. Whether every control the scope names has an id in that list — the flight booker's `select` in particular, since the plan lists `flight-one-way` and `flight-return` without saying what element each sits on — is research's question.
- Ids and names are structure-neutral: the same bullet requires that ids add no class, style, wrapper or order, that no task CSS selects by them, and that the six task inputs are named by attributes alone, adding no element, class, style or order. Any attribute the chunk adds to a lean task to make a state readable falls under the same rule.
- A fixture mounts into the fixed skeleton: layout-templates §Surface: desktop-native → IA notes requires each document to start from the fixed `html / head / body / main#main` skeleton with the app mounted into `main`, and records that arbitrary `index.html` templates are not supported. The minimal fixture for checkbox, radio and password therefore boots as a Dioxus component under `main#main`, not from an HTML template.
- The plan has no row for a fixture screen: §Primary screens lists the stand's four lean tasks and no "minimal fixture beside the stand". Where the fixture lives and whether it sits inside TaskShell is P3/P4's; a new screen is a layout-templates amendment at wrap, never this phase's.
- The plan carries no focus-order section for any surface, so it sets no Tab position for any stand control. The chunk's keyboard-focus check cannot cite a layout-declared order; the order the engine actually walks is research's to measure and a11y-plan's to own.

## Patterns to follow
- Boot through the stand's existing entry and hierarchy (layout-templates §Surface: desktop-native → Primary screens: `task_in_shell`, TaskShell header above the task body) rather than a bespoke mount, so the snapshot's tree shape and bounds stay those the earlier stand checks pin.
- Reach a control by its listed author id, and a CRUD row by its `crud-person-{id}` key, as the plan's id list fixes them (same bullet); a row's id follows its person under filter, Create and Delete, so a state check after one of those actions re-reads by the same id.
- Name or mark a control with attributes only (the `for` / `aria-label` precedent on the six task inputs, same bullet) when a reading needs something the markup lacks.
- Keep stand proofs selectable as stand checks: layout-templates §Surface: cli → Primary screens lists `agent-run.sh`'s run selections as `stand · all · <blitz-tests file name>` and points the grammar at test-plan §3; a new check file is named so the `stand` selection picks it up.

## Anti-patterns to avoid
- Adding a checkbox, radio or password input to one of the four lean tasks to get a case to prove: it changes the control set layout-templates §Surface: desktop-native → Primary screens lists for that task. The scope's ruling puts those cases on a fixture beside the stand.
- Adding a wrapper, class, style or reordering to a lean task or to TaskShell for the sake of a state reading — the plan's "no class, style, wrapper or order" rule (same bullet) covers every id-bearing control.
- Booting a state check through Home and navigating in, or at a viewport other than the pinned one (same bullet; §IA notes) — it changes the tree and bounds every stand check is pinned against.

## Contract bindings
- layouts ↔ a11y: keyboard focus on stand controls binds to a11y-plan's focus-order criterion (SC 2.4.3). layout-templates declares no focus order, so the binding is one-sided — a11y-plan is the only authority for which control Tab reaches next.
- layouts ↔ tests: the stand's boot shape and pinned viewport (layout-templates §Surface: desktop-native → Primary screens) are what the `stand_*` checks assert against, and the `stand` run selection (layout-templates §Surface: cli → Primary screens) binds to test-plan §3's agent-run contract.
- layouts ↔ architecture: the author-id list in §Primary screens is the layout-side statement of the stable element ids the snapshot's `id` field carries (arch §Standard Contracts); a fixture's controls need author ids too if they are to pass the actionable-key rule.
- layouts ↔ design: none — no token, colour or spacing is touched.

## Acceptance criteria contributions
- Every stand state check boots one lean task in TaskShell at the pinned viewport, never through Home (per layout-templates §Surface: desktop-native → Primary screens).
- Each proven control is read by the author id the plan lists for it, and each CRUD row by `crud-person-{id}`; a control the scope names that has no listed id is surfaced, not addressed by path (per layout-templates §Surface: desktop-native → Primary screens).
- After the chunk, the four lean tasks and TaskShell carry no added element, wrapper, class, style or reordering — only attributes, if any (per layout-templates §Surface: desktop-native → Primary screens).
- The minimal fixture mounts as a component under `main#main` of the fixed document skeleton, with no HTML template (per layout-templates §Surface: desktop-native → IA notes).
