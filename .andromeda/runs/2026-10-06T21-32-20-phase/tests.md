# tests extract

## Relevance
relevant — the chunk's deliverable is a proof per control (state readings of `DioxusDocument::snapshot` on the stand and on a minimal fixture), which lands in the harness-driven stand checks and the snapshot builder's unit tests that test-plan §1–§3 describe.

## Constraints
- Test tier is `0` (per test-plan §1 Test Scope Summary); breadth is the plan's existing levels — inline unit tests beside the code and one integration file per behaviour (per test-plan §2 Test directory + naming conventions · §5 tests/blitz-tests crate). No threshold is drawn from §10: it is marked not measured.
- The proof for the stand lands as `tests/blitz-tests/tests/stand_*.rs`; the `stand_` prefix is what puts a file under the agent-run `stand` selection, with no script change (per test-plan §3 Agent-run contract → `run {selection}` · Proof). A fixture-only check that should not count as a stand check needs a deliberate name — which file each new check lives in is the plan's (P4) decision.
- Stand checks boot each lean task through `seven_guis::stand::boot` / `boot_timer` with `stand::options(incremental)` — pinned viewport, bundled font, no net provider — and assert unconditionally: the stand has no font-skip path (per test-plan §3 blitz-test-harness → Construction · §7 Builders and options · §2 Font-dependent tests · §8 Real dependencies kept). The minimal fixture for checkbox / radio / password must run under the same pinned options to measure the same on any runner (per test-plan §9 Fonts); whether `stand::options` is reusable for a non-`LeanTask` component is research's question.
- Every state reading is proven for both layout modes — the stand checks' standing shape in test-plan §1 (tests/blitz-tests row: "in both layout modes") — selected through `HarnessOptions.incremental` (per test-plan §7 Builders and options · §2 Differential oracle).
- "Typed value reads back", "toggling changes checked" and "focus moves" must go through the harness input helpers (`click`, `press` / `press_with`, `type_text`), each of which pumps after dispatch; `dispatch` and `dispatch_recorded` do not pump, and `dispatch_recorded` bypasses Dioxus VirtualDom forwarding (per test-plan §3 Input helpers · Pump semantics · §5 Harness ↔ event pipeline). The synthesized key event carries `Code::Unidentified` and fills text only for pressed character keys (per test-plan §3 Input helpers) — whether a synthesized Tab moves focus on the stand, and whether `type_text` reaches a Dioxus-controlled input's value, a `range` input or a `select`, is research's question.
- Snapshot-builder unit tests stay in `snapshot.rs`'s own `#[cfg(test)]` module, compiled only under the crate's default `accessibility` feature, and build the document the way the existing ones do — `DocumentConfig::default()`, `initial_build`, then `resolve(0.0)` through `inner_mut()` before the snapshot is read (per test-plan §3 Crate-local test helpers → dioxus-native-dom · §1 dioxus-native-dom · §4 Conventions).
- The plan records engine tests that pin `disabled` as read by presence — the `DISABLED`/`ENABLED` element-state tests (including the `"false"` value case) and the mutator's disabled toggling (per test-plan §4 blitz-dom (node) · blitz-dom (net, mutator)) — and the Dioxus falsy-`disabled` integration file (per test-plan §1 tests/blitz-tests). The chunk's "pick one reader" decision must leave those green or re-pin them explicitly; whether the reader the snapshot picks disagrees with what they pin is research's question.

## Patterns to follow
- One file per behaviour with the standing stand shape: `for incremental in [false, true]`, boot, drive one real interaction, read the snapshot, assert the reading; the existing `stand_snapshot.rs` already pins "state as the engine reads it" and the snapshot following a re-render (per test-plan §1 tests/blitz-tests · §5 tests/blitz-tests crate) — whether its existing pins already hold any reading this chunk changes (and so need re-pinning rather than adding) is research's question.
- A fixture for a case the tasks lack is an inline Dioxus component built through `Harness::from_component` / `Harness::from_vdom(vdom, options)` — the plan's seed strategy is inline literals, with no fixture loader or fixture file tree (per test-plan §3 blitz-test-harness → Construction · §7 Seed strategies · §7 Observed absent).
- State is read through the harness inspection helpers (`query`, `node`, `focused`, `attr`, `text_content`) and mutations applied by `pump()`, never by reaching around the harness (per test-plan §3 Inspection helpers · Pump semantics).
- If the falsy-boolean fix lands in the bridge, its regression test follows the existing precedent: a dedicated integration file named for the behaviour it guards, documenting the bug (per test-plan §2 Test function naming · §1 tests/blitz-tests, the `dioxus_falsy_disabled` file).
- No mocking library and no new stand-in: the timer's `range` reading is taken under the `TimerTicks` source every stand boot provides, which holds elapsed fixed until ticks are delivered (per test-plan §8 Hand-written fakes and stubs → Time (seven_guis timer) · §8 Observed absent).

## Anti-patterns to avoid
- test-plan §11 holds no recorded ban (it is marked, so nothing is cited from it); the three below are drawn from §2–§5.
- No runtime skip in a stand or fixture check: a state reading that passes by skipping (font unavailable, control absent) is outside the stand's contract (per test-plan §2 Font-dependent tests).
- No assertion placed only inside an `if` on a measured condition — the plan records that shape as tests that pass without asserting (per test-plan §4 Conditional assertions); a masked-password or disabled reading must fail when the control or field is missing.
- No `dispatch_recorded` (or a programmatic value set) as the proof of a typed value, a toggle or a focus move on a `DioxusDocument` (per test-plan §5 Harness ↔ event pipeline · §3 Pump semantics).

## Contract bindings
- tests ↔ obs: agent-run events are harness metadata, not an escher-telemetry sink, and nothing between a `failures:` line and the next `test result:` reaches an event — so a failing check's assertion text (which could quote a fixture's typed or password value) stays in `run.log` only (per test-plan §3 Agent-run contract → Events · `logs`; binds obs-plan §3). The chunk adds no log field, so the stand log format binding (per test-plan §3 Stand log format) is untouched.
- tests ↔ a11y: the `a11y` CI leg runs three named files (accessibility_hidden, accessibility_roles, focusability_updates), not the `stand_` files (per test-plan §9 Legs). A change to how `hidden` or focusability is read must keep that leg green; the new focused-reading checks run in the `test` leg, alongside the existing Tab-order pin in `stand_accessibility_ids` (per test-plan §1 tests/blitz-tests) — whether the a11y plan wants the focused reading in its own leg is the a11y extract's.
- tests ↔ security: the password-masking check is the test evidence a security-plan amendment would cite at wrap; test-plan carries no rule for sensitive fixture literals, so the fixture's password is a synthetic literal by the security rules, not by this plan.
- tests ↔ arch: `NodeState` is a registered public contract and the snapshot sits under the `accessibility` feature, so its unit tests exist only in the default-feature build (per test-plan §1 dioxus-native-dom).
- Bootstrap phases: none applies — the one keyed contract (`coverage-tooling-install`) reads discharged (per test-plan §3 Bootstrap phases (derive for route / setup-project)).
