## Patterns to follow
- The command span's closed-span line takes its close fields (`message`, `time.busy`, `time.idle`) from `tracing-subscriber` itself, and the plan records the lock's `tracing` version beside the workspace requirement. If upstream's `cargo update` moves the `tracing` / `tracing-subscriber` / `tracing-log` versions in the lock, the line's shape is re-read from a real capture, not assumed (per obs-plan §6 Log Coverage → Log format (escher's sink) and obs-plan §2 Telemetry Strategy → Telemetry mechanism).
- Service identity is read from the binary's own `CARGO_PKG_NAME` / `CARGO_PKG_VERSION`. The plan's recorded capture reads `service.name=blitz-tests`, so a change to which package or binary holds our checks, or an upstream version bump, moves those two values; a check reads them from the build, never from a literal (per obs-plan §3 Observability Harness Contract → Service identity and line format (escher's sink)).
- Under a workspace build the sink-installing child of `stand_act_spans` also receives blitz-dom's focus event beside a driver `type`. Upstream #1085 (a bare `autofocus` treated as enabled) can move how many such engine lines a capture holds; whether that check asserts an exact line count is research's question, and a moved count is re-measured and recorded (per obs-plan §2 Telemetry Strategy → Feature wiring and obs-plan §6 Log Coverage → Logged events (current truth)).
- The package install's output stays in the job's step log and enters no `target/ci-logs/` file. Whichever of upstream's install changes (#1114, #1129, #1140) are taken, the fork's install steps keep calling `.github/scripts/apt-install.sh`, so its one-line-per-failed-attempt diagnostic stays the reading the folded WATCH depends on (per obs-plan §9 CI Integration).

## Anti-patterns to avoid
- Never fix a merged engine log site by editing its fields or its message: the scrub is the formatter's, and an edit of an upstream call site is a non-additive change the chunk would have to name (per obs-plan §8 PII Scrubbing & Compliance → Scrubbing).
- Never let a check that installs escher's sink share a process with checks that must run with none. One global subscriber in a combined test binary would make every in-process headless boot log, and would make `stand_session_quiet`'s zero say something other than what it says (per obs-plan §3 Observability Harness Contract → Logging stack).
- Never print a captured sink line or a child's stderr from a failing check while repairing a post-merge failure: a failure reports a kind and a count only (per obs-plan §3 Observability Harness Contract → Logging stack).

The scope's proof by count that every one of our test files ran is read through that field, so the test-build decision fixes what `file` can attribute: one binary per file keeps a name per file, a combined binary gives one name for all. - obs ↔ tests: the engine-features-by-runner reading is shared with test-plan §9 → Engine features by runner (per obs-plan §2 Telemetry Strategy → Feature wiring); if the merged feature graph moves it, both plans move together at the wrap.
