# security extract

## Relevance
relevant — the merge rewrites the dependency graph (`Cargo.lock`, the coupled pins), resolves a conflict in `deny.toml` and in `.github/workflows/ci.yml`, and touches the three upstream-only workflows that hold the secret-bearing jobs; it adds no surface of ours, so the plan's surface sections apply as "must not move", not as new work.

## Constraints
- The `deny.toml` resolution must keep the audit configuration the plan records: the six-platform `[graph]` with `all-features = true`, and `[advisories]` as per-ID ignores only, each with a written reason, no blanket allow, `unmaintained` and `unsound` at their defaults (per security-plan §Dependency Security, Audit tool). Whether upstream's #1089 edits to `deny.toml` leave those keys intact after resolution is research's question.
- The audit leg (`cargo deny --locked check advisories`) must read the merged lock: an advisory it fires on is fixed by a semver-compatible update or ignored by ID with a reason, and the standing ignore (the ttf-parser advisory behind the coupled winit pin) is kept only while it is still reached — whether upstream's `cargo update` and pin set still reach it, and whether the merged lock keeps the rustls fix the plan records, is research's question (per security-plan §Dependency Security, Audit tool).
- Git dependencies stay pinned by commit `rev` (the bumped Taffy rev included), `Cargo.lock` stays committed, and every ci.yml cargo leg but `examples/wasm_hello` keeps `--locked`; a merged lock that does not resolve under `--locked` is re-resolved as upstream's set, never loosened (per security-plan §Dependency Security, Pinning; §Supply chain integrity, Lockfile verification).
- The reconciled `ci.yml` must keep every `uses:` pinned to a 40-hex commit SHA with its ref as a trailing comment, and the pinned tool installs (`cargo-deny`, `cargo-llvm-cov`, `cross` by git rev) — an upstream job change taken into `ci.yml` (#1114, #1128, #1129, #1140) arrives pinned or is not taken; whether upstream's new steps reference an action at a mutable ref is research's question (per security-plan §Dependency Security, Pinning).
- The reconciled `ci.yml` must keep its workflow-level `permissions: contents: read` with no job-level grant, and the `audit` job must stay in it, run through `ci-leg.sh audit` on every pull request and push (per security-plan §Authentication & Authorization, RBAC rows; §Dependency Security, CI integration).
- The three upstream-only workflows are overlap files: the merge must keep the `github.repository == 'DioxusLabs/blitz'` guard on the publish and post-results jobs, the "Signed Builds" environment limit, and the pairing of each signing-material write with its `always()` removal — no fork ref may reach a secret (per security-plan §Authentication & Authorization, RBAC rows; §Secret Management, Storage). Whether upstream's delta to those three files touches a guard is research's question.
- Package installs in `ci.yml` stay calls of `.github/scripts/apt-install.sh` with package names and no option, the script's argument form and its exit-2-before-`sudo` rule unchanged; and whichever way the test files are built after the merge, an `agent-run.sh` selection must still reach cargo only as a validated name of an existing test file (per security-plan §Input Validation, rows "CLI arguments (apt-install.sh)" and "CLI arguments (agent-run.sh)").

## Patterns to follow
- New crates, versions and git revs that enter with upstream's set are reviewed by hand as well as by the audit: the plan records that the audit's reach is cargo-deny's resolved graph, which misses advisories in pruned optional chains (per security-plan §Dependency Security, Audit tool).
- Upstream's 61 commits are read for the surfaces the plan records as absent or closed, as a census rather than an assumption: no served listener or port (per security-plan §API Security), no secret read in source and no env read outside the recorded list (per security-plan §Secret Management, Never in code / Environment values read). Whether upstream's delta adds either is research's question; one that does is a plan amendment at the wrap, never a silent add.
- The merged engine sources keep logging through `tracing` behind each crate's `tracing` feature, and escher's sink keeps its target allowlist and scrub sets untouched; upstream's new call sites then fall under the sink's existing rule, and the sink's readings (no element id, no accessible name on a sink-installing binary's stderr) are re-proven by the standing checks, which must be among the test files the chunk counts as ran (per security-plan §Logging & Monitoring, Log format and backends).
- The merged `packages/blitz-shell/src/window.rs` and the accesskit bumps keep the platform accessibility adapter as the only exit escher's code gives a stable id or an accessible name — the poll-time refresh carries the same content classes through the same crossing, and `author_id` is set on element nodes only (per security-plan §Input Validation, row "Markup attributes — `id` (stable element id)").
- Plan rows measured against upstream-owned code that this delta changes are re-read at the wrap, not edited mid-merge: the `file:` URL read (upstream moves it to `Url::to_file_path`), the font-source rows (a hintless `@font-face` source), the boolean-attribute rows (`autofocus`, #1085), and every cited line range in the merged files (per security-plan §Input Validation; §Error Handling, Panic paths). `apps/browser/Cargo.toml` is an overlap file: JavaScript execution stays behind the non-default `javascript` feature (per security-plan §Threat Model Summary, Attack surface — script execution; the section's application-level threat model is marked NOT YET MEASURED and nothing is drawn from that part).

## Anti-patterns to avoid
- Clearing a red audit with a blanket allow, with `unmaintained` or `unsound` set to none, or with a lone bump of one side of a coupled pin (per security-plan §Dependency Security, Audit tool). (§Security Anti-Patterns itself reads NO RECORDED INTENT; the bans here come from the sections that state them.)
- Taking upstream's workflow text as it stands where it carries an action at a mutable ref, a job-level permission grant, or an `if:` that selects by ref without the repository guard (per security-plan §Dependency Security, Pinning; §Authentication & Authorization, RBAC rows).
- Adding a user-content log field, an unconditional print, or a widened sink allowlist to make a merged check pass (per security-plan §Logging & Monitoring, Log format and backends).

## Contract bindings
- tests ↔ security: the security gate is a job of the workflow being reconciled — `ci.yml`'s `audit` job and the invariants `.github/scripts/test_ci_workflows.py` asserts (SHA pins, permissions, the install script's bad-call test) bind to the test plan's CI contract; a job renamed or dropped in the resolution moves both (security-plan §Dependency Security, CI integration ↔ test-plan §3).
- tests ↔ security: the test-build decision (one binary per file, upstream's `all.rs`, or a binary of ours) binds to `agent-run.sh`'s selection validation, which admits a name only where `tests/blitz-tests/tests/{name}.rs` exists (security-plan §Input Validation ↔ test-plan §3).
- obs ↔ security: upstream's new engine log call sites meet the sink's allowlist and scrub sets (security-plan §Logging & Monitoring ↔ obs-plan §3).
- a11y ↔ security: the accesskit bumps move the API that carries `author_id` to the platform adapter, the one registered exit of ids and names (security-plan §Input Validation, `id` row ↔ a11y-plan §3).
- arch ↔ security: "no new crate, port, env var or listener" is the arch §Occupied Resources reading the census above checks for upstream's side.
- No coverage, stated so the plan does not read one in: license compliance is marked NOT YET MEASURED (security-plan §Supply chain integrity), so the security plan mandates nothing on whether upstream's license check (#1089) runs in our audit leg — that fork is decided on other grounds.
