# tests extract

## Relevance
relevant — the chunk's whole proof is the test surface: upstream's single-binary restructure of `tests/blitz-tests` and its CI job changes meet the target layout, the agent-run contract, the leg script and the workflow invariants the plan records.

## Constraints
- Target layout: test-plan §1 (Coverage scope → tests/blitz-tests) and §2 (Test directory + naming conventions → Directory pattern) state blitz-tests as one test-target file per behaviour under `tests/`, with `tests/common/mod.rs` and `tests/session_common/mod.rs` as shared modules that are no target, each read through a `mod …;` line in the check file. Upstream's `autotests = false` + `tests/all.rs` replaces that layout; whichever build shape the operator picks, the plan's statement of the layout must stay true or be amended with it. How `mod common;` / `mod session_common;` resolve when a check file is compiled as a module of another binary is research's question.
- Agent-run selections are target-shaped: test-plan §3 (Agent-run contract → `run {selection}`) requires `stand` to pass one `--test {stem}` per `tests/blitz-tests/tests/stand_*.rs`, `{name}` to name one such file, and each `test` event's `file` to be the target binary's stem; test-plan §3 (Agent-run contract → `boot`) requires `cargo test -p blitz-tests --locked --no-run` to build every test binary. A layout with no per-file target breaks all three; whether the merged manifest still yields one target per stand file is research's question.
- Re-run children depend on binary identity and test path: test-plan §2 (Test levels observed → Process-lifecycle checks) requires a process check to re-run its own test binary on one `#[ignore]` child by `--ignored --exact {child} --nocapture`, and warns that a bare `--ignored` run blocks on the two host children. Folding these files into a shared binary changes the child's exact path and puts serve-until-stopped children beside every other ignored test; test-plan §3 Session lifecycle (`session-checks`, `session-proof`) names the files and child counts that must still run.
- Process-global checks need their own process: test-plan §1 (Coverage scope → escher-telemetry) states the sink's process-global behaviours are proven by the five `telemetry_*` integration files, and test-plan §3 (Stand log format) binds the format and the drop to them. Whether those five stay sound when compiled into one binary with other tests (one subscriber, one panic hook, one stdout) is research's question; the plan gives no single-binary form for them.
- CI shape is pinned by tests, not by the workflow alone: test-plan §4 (What unit tests cover → CI workflows and leg script) requires `CiWorkflowTest`, `UpstreamGuardTest`, `LegScriptTest` and `InstallScriptTest` to hold — the fast four with no `needs`, every linux job through `ci-leg.sh` with its leg in the script's list, the matrix platforms, every `uses:` on a 40-hex SHA, no `secrets.`, the `DioxusLabs/blitz` guard on the three upstream-only workflows, and every package install bounded with the calling jobs exactly `INSTALL_JOBS`. Each upstream job change taken (the dropped default-features test job, the removed counter job, the changed package installs) moves an invariant and must move its test with it; none may be loosened to pass.
- Leg set and platform reach: test-plan §9 (Pipeline facts → Legs) states twelve linux legs — `counter`, `audit` as `cargo deny check advisories`, and `a11y` as three named `--test` files among them — and test-plan §1 (Surfaces under test → Native platforms) requires windows and macos to run the tests and ios and android to build. Test-plan §5 (Boundaries covered → Session host ↔ lifecycle socket) states the non-unix arms are compiled and run by the windows leg only, and test-plan §3 (blitz-test-harness → Input helpers) that `apple_keybinding` has its one standing check on the macos leg — so neither leg may be lost to a runner the fork lacks.
- Two builds, two verdicts: test-plan §9 (Pipeline facts → Engine features by runner) states `cargo test --workspace --locked` and `cargo test -p blitz-tests --locked` build blitz-dom with different features, so a green per-package run is not the workspace leg's green and a sink capture is counted by target. The merge is proven under both; whether upstream's delta adds engine `tracing` records beside a driver call is research's question.

## Patterns to follow
- Re-count at a sync, attributed: test-plan §9 (Pipeline facts → Local baseline) carries a re-count entry per chunk — result lines · passed · failed · ignored, each delta attributed to a named file or upstream commit — including the first real upstream merge. This sync adds its own entry the same way; result lines will move if the target layout does, and the entry says why.
- Stand selection grows by prefix, counted in `run.end`: test-plan §3 (Agent-run contract → Proof) re-counts `run stand` per chunk by its `run.end` tallies and the number of files the selection lists. The post-merge reading is taken the same way, and an unchanged file count is the by-count proof the scope asks for on the stand side.
- Pinned measurements are stated tables with asserted row counts: test-plan §1 (Coverage scope → tests/blitz-tests) records the stand's measured readings (snapshot byte sizes under in-file ceilings and `SNAPSHOT_TEXT_BUDGET`, the accepted/refused split of driver clicks, control bounds at boot) as stated expectation. A number Parley 0.12 or the Taffy bumps move is re-measured and restated with its row count, never widened into a tolerance.
- No skip path on the stand: test-plan §2 (Test levels observed → Font-dependent tests) and test-plan §8 (Real dependencies kept) require the stand checks to assert unconditionally under the bundled DejaVu Sans with system fonts off — the same on any runner. A post-merge metric shift is answered inside that pinning.
- Both layout modes, and the oracle: test-plan §2 (Test levels observed → Differential oracle) requires the incremental and non-incremental documents to agree after every step, and test-plan §5 (Boundaries covered → Session ↔ held instance) requires the driver's diffs equal across the two modes — the standing proof against upstream's move of the Taffy tree impls.

## Anti-patterns to avoid
- An empty or thinned run read as green: test-plan §3 (Agent-run contract → `run {selection}`) states an empty run is never a pass. The workspace leg has no such guard — a manifest that compiles none of our files still exits 0 — so the merge is never accepted on exit code alone, only on counts.
- A per-file or per-package green offered as the gate: test-plan §9 (Pipeline facts → Engine features by runner) rules it out; the gate is the workspace leg, with the per-package run beside it.
- A process check that waits for exit before reading, or lets a child's libtest lines reach the parent: test-plan §2 (Test levels observed → Process-lifecycle checks) bans both — the second is how `agent-run.sh` would miscount tests after a layout change.

## Contract bindings
- tests ↔ obs: test-plan §3 (Stand log format) binds the two record classes and the target allowlist to obs-plan §3, §6 → Log format and §8; the `telemetry_*` files, `stand_act_spans` and seven_guis' `host_log` are that binding's checks and must all still run after the merge.
- tests ↔ a11y: test-plan §9 (Pipeline facts → Legs) names the `a11y` leg's three test files by target name (a11y-plan §3); the accesskit bumps land on the `author_id` checks recorded in test-plan §1 (Coverage scope → tests/blitz-tests). A layout that removes those target names breaks the leg's command line.
- tests ↔ security: test-plan §9 (Pipeline facts → Legs) states the `audit` leg as the advisories check (security rules §Dependencies; `deny.toml`). Taking upstream's license check into that leg changes the leg's statement and `LegScriptTest`'s reading of it — a plan decision, flagged to the security extract.
- tests ↔ arch: test-plan §3 Session lifecycle (`session-state`, `session-checks`) ties the process checks to architecture §Standard Contracts → Driver session — the state directory under `CARGO_TARGET_TMPDIR`, the `0700`/`0600` modes, `cfg(unix)` gating.
- tests ↔ project docs: the per-file command `cargo test -p blitz-tests --test {name}` (CLAUDE.md, `.claude/docs/commands.md`) and test-plan §9 (Pipeline facts → Benchmarks) `--test paint_tree_bench -- --ignored` both name a target; they move with the layout decision or stay true by it.
