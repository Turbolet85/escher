# a11y extract

## Relevance
partial — the chunk adds no UI surface, but the merge crosses a11y surface the plan covers: the accesskit dependency family, the `accessibility` feature wiring in five overlapped manifests, the engine files that hold the changed set and the shell's tree refresh, focus-at-boot behaviour (upstream #1085), and the `a11y` CI leg's three test targets (upstream #1123).

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` and the `accessibility` feature reach is part of the scope: a11y-plan §1 requires the feature to stay a default of the engine and Dioxus crates, blitz-tests to build `blitz-dom` and `dioxus-native-dom` with it and take `accesskit` as a dev-dependency, the feature to reach seven_guis through the `escher-driver` edge, and no platform adapter (`accesskit_xplat`, `accesskit_winit`) to enter either stand binary's graph. The merge resolves `Cargo.toml`, `tests/blitz-tests/Cargo.toml`, `packages/dioxus-native/Cargo.toml`, `packages/dioxus-native-dom/Cargo.toml` and `apps/browser/Cargo.toml`, and takes upstream's accesskit_unix and accesskit_android bumps into `accesskit_xplat`; whether the merged manifests and lock still give that reach, and whether the workspace `accesskit` version moves with the bumps, is research's question (per a11y-plan §1 A11y Scope Summary).
- The platform tree is refreshed on change: a11y-plan §2 requires the shell's poll to drain the document's changed set outside the `accessibility` cfg and, under it, to rebuild the platform tree when the drained set was non-empty, both paths through the `Document::accessibility_tree` trait method so a wrapper's override reaches the platform tree; and it requires a focus move, a checked change and a rewritten accessible name each to mark the set while a pointer move alone does not. `packages/blitz-shell/src/window.rs` and `packages/blitz-dom/src/{document,mutator,node/node}.rs` are overlap files; whether the textually clean merge keeps those paths and marks is research's question. The refresh's windowed witness stays owed on the route's "Stand a11y assertions" and is not this chunk's (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- Role derivation must not move with the merge: a11y-plan §4 requires the HTML-AAM element mapping, an `<a>` to be a Link only with `href` and a generic container without, and hidden content to be excluded or marked as the section records. Upstream #1134 restyles an `a` without `href`; whether it touches the role mapping or only the stylesheet is research's question (per a11y-plan §4 ARIA Patterns & Roles).
- Focus order (SC 2.4.3) and keyboard operability (SC 2.1.1): a11y-plan §5 requires the focusability rule, Tab and Shift+Tab moving focus to the next and previous focusable node, and focusability recomputed when `tabindex`, `href` or `disabled` is set or removed (the recompute lives in `mutator.rs`, an overlap file). §5 also records autofocus as acting on `autofocus="true"` under the `autofocus` feature, with the script reflection writing that value and the Dioxus bridge removing a falsy `autofocus`; upstream #1085 treats a bare `autofocus` as enabled, so that record moves with the merge. Whether any stand task, fixture or test carries an `autofocus` attribute, and whether a build of ours enables the `autofocus` feature, is research's question; the section's line is re-measured at the wrap, never left reading the old value (per a11y-plan §5 Keyboard Navigation, Focus order).
- Painted colour (SC 1.4.3): a11y-plan §6 requires the paint-side contrast helper and the contrast stroke on default scrollbar thumbs, and records the default stylesheet's focus outline on inputs; the merge brings upstream's style and paint changes under them. Whether upstream's delta touches `packages/blitz-dom/assets/default.css` focus rules or the scrollbar paint is research's question. Design-token contrast pairs are marked not yet measured in that section and add no requirement here (per a11y-plan §6 Visual Design Verification).
- Accessibility-tree identity and the snapshot's readings: a11y-plan §7 requires every element node of a Dioxus document to carry its stable element id as AccessKit `author_id` (no text-run, document-root or window node carrying one), the stand's interactive controls to carry an HTML-AAM role and a non-empty accessible name in both layout modes, the snapshot to take role, name and focus from the tree with no second mapping, and element nodes to carry their HTML tag name. The scope's hypothesis that the accesskit bumps move the API `author_id` is carried through, and whether upstream's custom-widget tag override (#1081) changes the tag the tree carries, are research's questions (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- The a11y CI gate: a11y-plan §9 requires ci.yml's `a11y` job to run `bash .github/scripts/ci-leg.sh a11y` over three named test targets — `accessibility_hidden`, `accessibility_roles`, `focusability_updates` — with the test counts the section records, in the slow tier behind the fast jobs. Upstream #1123 (`autotests = false`, one `tests/all.rs` binary) can leave those three names resolving to no target; whether they are upstream files that become modules of that binary, and what the leg's command must then name, is research's question, and the chunk's test-layout decision must cover this leg (per a11y-plan §9 CI Integration).

## Patterns to follow
- Accessibility assertions are Rust tests in blitz-tests over the AccessKit tree — built after `resolve`, matched on role and hidden state, with the role helper mapping an element's node id to its AccessKit id; the merge is re-proven by these standing checks, with no new tooling (per a11y-plan §3 A11y Assertion Harness Contract, A11y testing tool pick).
- The stand's key-press focus check runs through the test harness in both layout modes: Tab and Shift+Tab between named controls, the first Tab on a fresh boot, nothing focused at boot, and the focused snapshot node equal to the tree's focus (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- Expected roles, input names and rendered ids are stated once, in the stand checks' shared tables; a value the merge legitimately moves is re-measured and restated there, never patched per test (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- A check that reads the engine's change flag as "this step changed something" drains the changed set first, because a freshly booted harness document reads non-empty and a harness settle neither reads nor drains it (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- The a11y leg is run as its own CI leg through the leg script, restoring the test job's cache and saving none; the conflict resolution of `ci.yml` keeps that shape (per a11y-plan §9 CI Integration).

## Anti-patterns to avoid
- a11y-plan §11 A11y Anti-Patterns reads `NO RECORDED INTENT` and nothing is extracted from it; the two bans below come from the sections they cite.
- No second role or name mapping: a snapshot, its text, its diff, the actionable-key check or a test table that derives a role or a name anywhere but from the tree `accessibility_tree` returns — including as a quick repair of a check the merge breaks (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- No ARIA `role` override taken as a fix for a native element's mapping: the section records that override path as a known deviation from WAI-ARIA 1.2, so a merge repair must not lean on it (per a11y-plan §2 A11y Strategy, Role derivation).

## Contract bindings
- a11y ↔ tests (CI gate and test targets): the `a11y` leg's three `--test` names and its recorded counts bind to the chunk's test-layout decision, to test-plan §9's baseline counted in result lines, and to `scripts/agent-run.sh run {name}`; the keyed contract `a11y-ci-gate-wire` reads discharged and points at this section (per a11y-plan §9 CI Integration; a11y-plan §3 Bootstrap phases).
- a11y ↔ tests (harness build): the test harness and blitz-tests build the engine with the `accessibility` feature; the resolution of `tests/blitz-tests/Cargo.toml` keeps those feature names and the `accesskit` dev-dependency (per a11y-plan §1 A11y Scope Summary; a11y-plan §3 A11y Assertion Harness Contract).
- a11y ↔ architecture (changed-set contract, coupled pins): the tree refresh rests on the engine's changed-set contract (arch §Cross-cutting Patterns, Invalidation and state integrity), and the accesskit family is taken as one set under the coupled-pins rule (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- a11y ↔ driver / security: the driver's `disabled` refusal is stated on the snapshot's `enabled` reading, which follows the presence of `disabled`; an upstream change to disabled-ness or to the snapshot's sources moves a refusal cause (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- a11y ↔ obs (violation schema) and a11y ↔ design (contrast token pairs): none — both read not yet measured in the plan (a11y-plan §3, §6).
