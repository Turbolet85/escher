# a11y extract

## Relevance
partial — the chunk is pipe tooling (`scripts/cold-agent.sh`, its contract tests, one live run). It builds no UI and binds no key. It touches a11y in three places: the cold agent reads the stand only through the snapshot, which is built from the accessibility tree; its completion oracle reads that same model; and item 8 (`task-header-spacer` refused `covered`) could be closed by a stand markup edit, which would move the stand's a11y tables.

## Constraints
- The a11y target stays tier 0, SC 2.1.1 · 1.4.3 · 2.4.3. The stand binary builds no platform adapter, kept so on the founder's F1. Swapping the pipe to the `escher-session mcp` role must therefore add neither `accesskit_xplat` nor `accesskit_winit` to the seven_guis graph (per a11y-plan §1 A11y Scope Summary).
- An MCP tool result is one more reader of the snapshot model, with no second role or name mapping. A `snapshot` result is `to_text`'s output itself, and an acting call's result is its JSON line with the diff. A completion oracle built on the tool's answers must read role, name and state from that model alone. It must never re-derive them (per a11y-plan §7 Screen Reader Support).
- A password input reads `MASKED_VALUE` in every tool result, and its typed text appears in no snapshot field and no painted frame. A transcript or an oracle record that keeps a tool answer keeps only the mask (per a11y-plan §7 Screen Reader Support).
- The driver's `disabled` refusal rests on the snapshot's `enabled` reading, which follows whether a `disabled` attribute is present. It is the first of three screen-level checks (`disabled`, `off-screen`, `covered`). A wrong-call count that sorts refusals by cause should read those cause words as the schema defines them (per a11y-plan §7 Screen Reader Support).
- Focus order is a stated table. `tab_order` and `ENABLED_TAB_ORDER` in the stand checks' shared module are asserted by `stand_keyboard`. Any stand markup change made for item 8 that moves focusability or order must move those tables in the same change (per a11y-plan §5 Keyboard Navigation).
- Every stand control's text/background pair is asserted row for row by `stand_contrast` (`TEXT_ROWS` and `STATE_ROWS` included). A stand style change moves that record (per a11y-plan §6 Visual Design Verification).
- The `a11y` leg runs six files: accessibility_hidden, accessibility_roles, focusability_updates, stand_keyboard, stand_contrast and stand_accessibility_ids. The three `stand_*` files also run in `stand-repeat` under the zero-failure budget. They must stay green after the chunk (per a11y-plan §9 CI Integration).

## Patterns to follow
- An agent can complete a stand task by keyboard as well as by `click`. A pressed Enter or a released Space on a focused stand button reads as its click, and through the driver `press enter` / `press space` on a Tab-focused `counter-increment` each name `counter-value` in the diff. A task choice or oracle may rely on this (per a11y-plan §5 Keyboard Navigation).
- Read state off the screen as the stand checks do. Flight booker and CRUD state pressed, invalid and selected through `aria-*` attributes alone, and these reach the snapshot text and diff as closed words. An oracle that checks a task's end state should read those words from the tool's answer, not the stand's classes or styles (per a11y-plan §7 Screen Reader Support).
- Every element an agent can act on carries an author key, so ids hold across processes. `DioxusDocument::unkeyed_actionable` returns nothing on the four lean tasks, so an id an agent reads in one session also names that element in a fresh session the pipe drives (per a11y-plan §7 Screen Reader Support).
- A check that reads `has_changes()` as "this step changed something" drains the changed set first. A freshly booted harness document starts with a non-empty set, and a settle neither reads nor drains it (per a11y-plan §2 A11y Strategy).

## Anti-patterns to avoid
- Never add a second role or name mapping beside the snapshot. Not in the oracle, the call count or the check the agent writes (per a11y-plan §7 Screen Reader Support).
- Never close item 8 with a stand markup edit (for example hiding `task-header-spacer` or changing its role) without restating the shared tables (`controls`, `tab_order`, `REGION_NAMES`) and re-running the a11y leg. Whether the spacer currently reads an interactive role or appears in `tab_order` is research's question (per a11y-plan §5 Keyboard Navigation).

## Contract bindings
- a11y ↔ tests: the stand's stated a11y tables (`controls`, `INPUT_NAMES`, `REGION_NAMES`, `tab_order`, `ENABLED_TAB_ORDER`) live in `tests/blitz-tests/tests/common/mod.rs`, shared with every stand check. A stand edit made for item 8 moves both (per a11y-plan §7 Screen Reader Support; a11y-plan §5 Keyboard Navigation).
- a11y ↔ driver/MCP: the cold agent's view of the stand, and any oracle built on the tool's answers, consumes the accessibility tree through the snapshot model, the MCP result being one more reader of it (per a11y-plan §7 Screen Reader Support).
- a11y ↔ CI: the `a11y` leg and `stand-repeat` both run the stand's a11y files. The swapped pipe stays out of CI and adds nothing to either leg (per a11y-plan §9 CI Integration).

- The completion oracle and the recorded verdict read role, name and state only from the tool's snapshot text or diff; no a11y-derived reading is computed a second way. A transcript copy shows any password value only as `MASKED_VALUE` (per a11y-plan §7 Screen Reader Support).
