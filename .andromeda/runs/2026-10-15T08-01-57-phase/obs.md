# obs extract

## Relevance
relevant — the swap rewrites a harness log the plan describes (the cold-agent pipe's events, verdict, call log and state area) and its candidate independent count reads escher's own `tool_call` span lines off the `mcp` role's stderr.

## Constraints
- obs-plan §3 (Cold-agent pipe log) requires the pipe's events to be JSON lines encoded by python3's `json` module embedded in the script, its state area under `target/cold-agent/`, with no `tracing` subscriber, OTel setup or third-party logger of its own; that paragraph describes the stub-era pipe. After the swap the spawned server is `escher-session mcp`, whose `main` installs `escher_telemetry::init` before anything else (per obs-plan §3, Logging stack). So the session's server writes escher's sink on its stderr, and the wrap amends §3 to say so. Whether the client's spawn makes that stderr reachable to the pipe at all is research's question.
- obs-plan §6 (Log format, the cold-agent pipe) requires the verdict to hold counts and identities only: no transcript text, tool argument, tool result or reply. Any field that replaces the stub-derived `final_count` or `counts_agree` (the completion oracle, the new call count, the check's result) keeps that shape: a closed word, a bool or a count, never screen or call content.
- obs-plan §4 (`tool_call` span) fixes one closed span per MCP `tools/call` at INFO, target `escher_driver`, with exactly two fields, `tool` (the verb table's word, unrecorded for an unknown tool) and `ending` (`accepted` · `refused` · `error`), parenting the `command` span of an instance verb; session verbs and `help` leave no `command` child. A count built on it has to map the stub's `ok|refused` onto `accepted|refused|error`. It also has to handle an unknown tool reading no `tool` value. And `cause` exists only on the `command` child (per obs-plan §4, command span), so whether every refused tool call (an MCP-level `malformed` included) carries a cause somewhere is research's question.
- obs-plan §6 (Logged events, escher-driver) requires that no span line prints at the default `warn`. A count read from `tool_call` lines therefore needs the server child started at `RUST_LOG=info` or below, and the pipe sets that in the server's environment, not in source. `RUST_LOG` is the one env var escher's sink reads (per obs-plan §6, Log format: per-module levels through `EnvFilter`).
- obs-plan §2 (Feature wiring) records that a workspace build adds `blitz_dom::document` INFO lines to the same stderr (9 lines built alone vs 11 built with the workspace over one CRUD flow, per obs-plan §6, Logged events, escher-driver). So a call count matches `span="tool_call"` lines and never counts raw lines, and it states which build the pipe launches.
- obs-plan §8 (Scrubbing, the cold-agent bullet) requires that no event or verdict key is in the content-named set. It also requires that `transcript.jsonl` is raw by design: never printed or logged, gitignored under `target/`, and its one committed copy masking host paths. With the real driver the transcript now carries tool results: ids, accessible names, control values (a password as the mask), snapshot text and diff, and a `screenshot`'s base64 PNG. Any committed copy of the live run's transcript is held to that rule.
- obs-plan §9 (Cold-agent pipe state) requires the state area to stay local only and gitignored, uploaded by no CI leg (CI runs only the shim contract tests), removed by `cold-agent.sh cleanup` alone (which touches nothing else under `target/`), and the per-run `mktemp -d` directory removed on exit. `calls.jsonl` and `stub-state.json` retire with the stub. Any new file goes into that table at the wrap: a captured server stderr, the agent's check, or an oracle's output. An oracle that drives its own session names a state directory that holds only `session.sock` and no log or screen content (per obs-plan §9, Session state directory).

## Patterns to follow
- JSON-line events through python3's `json` module, never assembled in bash: the cold-agent and agent-run harness logs both do this (per obs-plan §3, Cold-agent pipe log / Agent-run harness log).
- `mcp_log` is the precedent for reading the `mcp` role's stderr. It reads at `trace` under both builds into assertions only, and counts one `tool_call` line per call with 0 id, name, typed-sentinel and shot-prefix needles (per obs-plan §3, Logging stack; obs-plan §8, Values logged as-is). Use it as the model for any reading of the server's stderr the pipe or its contract tests make.
- A check that reads a sink capture reports a kind and a count on failure, never a captured line (`host_log`, `stand_act_spans`' parents, per obs-plan §3, Logging stack).
- The cold-agent marker-string contract test proves that no transcript text, tool argument, tool result or reply enters an event or the verdict (per obs-plan §8, Scrubbing). Extend it to the driver's real result content.

## Anti-patterns to avoid
- Adding a field to `tool_call` or `command` (a call sequence number, an argument, a result size) to serve the pipe's count or oracle. obs-plan §4 keeps the `tool_call` span at its two closed fields and forbids fielding any argument, `Outcome`, screen text or shot byte. The chunk's Boundaries already exclude any telemetry change.
- Printing `transcript.jsonl`, `client.log` or a captured server stderr, or copying any tool result text into `events.jsonl` or `verdict.json` (per obs-plan §6, Log format, the cold-agent pipe; obs-plan §8, Scrubbing).
- Building an event, the verdict or an MCP config document through shell quoting instead of the embedded python `json` encoder (per obs-plan §3, Cold-agent pipe log).

## Contract bindings
- obs §6 verdict and event fields ↔ tests §3 (cold-agent pipe): `.github/scripts/test_cold_agent.py` asserts the verdict's key set and the marker-string rule, so a renamed or replaced verdict field moves both the contract test and §6.
- obs §4 `tool_call` span ↔ the pipe's independent call count (if adopted): the span's two field names and its `ending` words become a contract the pipe reads, so a change to them in `packages/escher-driver/src/mcp.rs` breaks the count.
- obs §8 cold-agent scrubbing ↔ security-plan §Input Validation (the two cold-agent rows) and §Logging: transcript host-path masking and the content-named set the events must avoid.
- obs §9 cold-agent state area ↔ arch §Occupied Resources: `target/cold-agent/`, the per-run directory and the session's own stdio are the pipe's whole footprint, and a new file or a server stderr capture is registered in both.

## Acceptance criteria contributions
- Live and shim runs leave `events.jsonl` and `verdict.json` with 0 content-named keys and 0 occurrences of marker strings planted in tool arguments and results: an element id, an accessible name, a typed sentinel, and a shot's first 64 base64 characters (per obs-plan §8, Scrubbing).
- If the independent count reads the server's stderr: with the server at `RUST_LOG=info` or below, the number of `span="tool_call"` lines equals the transcript's tool-call count. The match is by span name, not line count, and the build the pipe launches is stated (per obs-plan §4, `tool_call` span; obs-plan §6, Logged events, escher-driver).
- Any captured server stderr holds 0 id needles, 0 name needles, 0 typed-sentinel occurrences and 0 shot base64 prefixes at the level the pipe sets (per obs-plan §8, Values logged as-is).
- Every file the pipe writes lies under `target/cold-agent/` or the per-run directory removed on exit. `cleanup` removes no other `target/` path, and no CI leg uploads any of it (per obs-plan §9, Cold-agent pipe state).
