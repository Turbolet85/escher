## Relevance
relevant — the chunk rewrites the cold-agent run pipe (test-plan §3 "Cold-agent run pipe") and its contract tests (test-plan §4 "Cold-agent pipe"), and may land the agent's check as a new test asset.

## Constraints
- The pipe's surface stays the four verbs `run <task> | status | cleanup | logs`, with exit grammar `0` · `1` (a `failed` verdict) · `2` usage (checked before any precondition, including a task outside the allowlist) · `3` precondition. The pipe binds no port or socket and reads no environment variable of its own. The swap changes only the allowlisted task (today the one task `counter`) and the spawned server (per test-plan §3 Cold-agent run pipe, Invocation / Exit grammar).
- The verdict is `passed` only on positive evidence: client exit 0, a `result` with subtype `success` and `is_error` false, `isolated`, `counts_agree`, at least one tool call, and task completion read from something other than the reply. `isolated` means the init tools are exactly the server's tools, one MCP server is connected, skills and slash commands are empty, `apiKeySource` is none, and no cwd or memory path names the repo root. `wrong_calls` is recorded and never decides the outcome. The swap has to restate the `stub`-specific terms of `isolated` (three tools, server `stub`), `counts_agree` (checked against the stub's `calls.jsonl`) and `task-unmet` (`final_count` from `stub-state.json`) for the `escher` server, each with a source that is not the transcript or the reply (per test-plan §3 Cold-agent run pipe, Verdict).
- State stays inside `target/cold-agent/` and is gitignored. `cleanup` removes that directory alone, is idempotent and leaves `target/agent-run/` untouched. The per-run session directory is a `mktemp -d` outside the repository, removed after the run. The state list (`calls.jsonl`, `stub-state.json`) changes with the swap (per test-plan §3 Cold-agent run pipe, State / `run counter`).
- The live run is never part of CI (there is no CI secret). The proof is the contract tests plus a live run on the operator host, with token usage and cost recorded. The founder's recorded budget was one live run, and it has been spent (per test-plan §3 Cold-agent run pipe, Proof).
- The server the pipe spawns is the `mcp` role: `escher-session mcp` alone (anything after it is usage). It holds its session in process and ends with nothing on stdout. Its task set is `counter` · `flight-booker` · `timer` · `crud` (per test-plan §3 `session-binary`). A check that drives that stdio child bounds every read and kills and reaps the child in its guard's `Drop` (per test-plan §3 `session-checks`).
- On stderr only, the `mcp` role writes one closed `tool_call` span line under `escher_driver` per `tools/call`, holding only `tool` and `ending` (`accepted` · `refused` · `error`). That line is the parent of a `command` line when the call runs through `Session::run`, and `help` has no `command` line. Stdout carries protocol lines only. Research has to answer two questions: does this line give a usable independent call count, and does the `claude` client pass server stderr to `client.log` or anywhere else the pipe can read? (per test-plan §3 Stand log format).
- A process-lifecycle check bounds every wait and kills and reaps any child a failing check still holds. It sends the child's streams to null unless it reads them, so child libtest lines never reach a parent runner's count (per test-plan §2 Test levels observed, Process-lifecycle checks).

## Patterns to follow
- Contract tests for the pipe put a `claude` shim on PATH. The shim drives the real server as a minimal MCP client and prints a stream-json transcript, so no live model or credential is used. Each failure reason (`client-exit` · `no-result` · `not-isolated` · `counts-disagree` · `no-tool-call` · `task-unmet`), the usage and precondition exits, and cleanup idempotence each get their own case. The stub's own test class (`ColdAgentStubTest`, 6) is tied to the stub and has to retire or move with it (per test-plan §4 Cold-agent pipe). Research has to answer whether the `ci-scripts` leg, which runs Python only, can reach a built `escher-session` binary for the shim to drive (per test-plan §9 Pipeline facts, Legs).
- MCP child tests drive `escher-session mcp` over piped stdin through the shared `Speaker` in `examples/seven_guis/tests/common/mod.rs` (`mcp_server`, `mcp_log`). The one real-client trial ran `claude -p` with the pipe's flags and `--allowedTools mcp__escher`. Its first request was `server/discover`, answered `-32601` (per test-plan §6 E2E Test Strategy, MCP).
- Event and verdict lines are encoded by python3's `json` module embedded in the script: `run.start` and `run.end` are printed and appended to `events.jsonl`, while `status` and `cleanup` are printed only. They are harness metadata, not an escher-telemetry sink (per test-plan §3 Cold-agent run pipe, Events).
- If the agent's check lands as a blitz-tests file, it is one test-target file per behaviour under `tests/blitz-tests/tests/` (per test-plan §2 Test directory + naming conventions). A `stand_*.rs` name is selected by `agent-run.sh run stand` with no script change (per test-plan §3 Agent-run contract, `run {selection}`). It also joins the `stand-repeat` zero-failure budget: three rounds, no retry (per test-plan §10 Quality Gates, Flakiness budget).

## Anti-patterns to avoid
- Never pass on the agent's reply or on an empty session. Completion comes from evidence the pipe reads itself (per test-plan §3 Cold-agent run pipe, Verdict).
- Never put transcript text, a tool argument, a tool result or the reply into an event or verdict field, and never add a content-named field (per test-plan §3 Cold-agent run pipe, Events).
- Never fire the live run from CI or put a credential there. The contract tests stay shim-only (per test-plan §3 Cold-agent run pipe, Proof).

## Contract bindings
- tests ↔ obs: if the independent call count reads the `tool_call` span line, the pipe depends on obs-plan §6 Log format and the closed `tool` / `ending` sets (test-plan §3 Stand log format). The pipe's events stay harness metadata, outside escher-telemetry's sink (obs-plan §3; test-plan §3 Cold-agent run pipe, Events).
- tests ↔ security: the `isolated` reading (`apiKeySource` none, the operator's own login), the committed transcript masked of host paths, and the stub-validation row that retires with the stub all bind to security-plan §Input Validation's cold-agent rows (test-plan §3 Cold-agent run pipe, Verdict / Proof).
- tests ↔ arch: the spawned `mcp` role and its task set follow arch §Standard Contracts → Driver session (test-plan §3 `session-binary`). The pipe's footprint (`target/cold-agent/`, the session's stdio) falls under arch §Occupied Resources (test-plan §3 Cold-agent run pipe, State).

## Acceptance criteria contributions
- `python3 -m unittest discover -s .github/scripts` (the `ci-scripts` leg) passes with `test_cold_agent.py` reading the swapped pipe: the new tools, the new independent call count and the new completion oracle. It uses a shim only, with no live model and no credential. The CI-scripts test tally is re-stated (per test-plan §4 Cold-agent pipe).
- Shim cases show the verdict reading `failed`, with the matching reason, for a client exit, a missing or unsuccessful result, an isolation breach (an extra tool, a second server, a cwd naming the root, `apiKeySource` other than none), counts that disagree, no tool call, and an unmet task. An empty session never passes (per test-plan §3 Cold-agent run pipe, Verdict).
- `events.jsonl` and `verdict.json` carry no scrub-set key and no transcript marker. `cleanup` is idempotent and leaves `target/agent-run/` intact (per test-plan §3 Cold-agent run pipe, Events / State).
- The live run of the swapped pipe happens once, on the operator host, off CI. Its verdict, wrong-call count, tokens and cost are recorded as chunk evidence (per test-plan §3 Cold-agent run pipe, Proof).
