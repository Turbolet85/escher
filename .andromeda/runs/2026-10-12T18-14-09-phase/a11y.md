# a11y extract

## Relevance
partial — the chunk adds no control, role, focus path or key binding. It touches a11y in three places: the painted pixels it exports (the focus ring, the caret and state colours are painted a11y surface), an element crop addressed through the snapshot model, and the masked-password reading that a screenshot must not undo.

## Constraints
- The tier stays `0 — SC 2.1.1 · 1.4.3 · 2.4.3`. A screenshot is a new reader of what blitz-paint paints, so it must take the same paint path as a windowed frame and must not change painted colours or focus indication. It only reads SC 1.4.3 / 2.4.3 surface and must not alter it (per a11y-plan §1 A11y Scope Summary).
- A password input's value reads the fixed mask `MASKED_VALUE`, and its typed text is in no field of the snapshot or of the tree. A screenshot must not carry that text out as pixels either. The scope's CARRY records the hypothesis that the engine paints a password's characters like any text input's. Whether the code already masks it on a rendered frame is research's question (per a11y-plan §7 Screen Reader Support).
- An element screenshot is addressed through the snapshot model, so it is one more reader of that model. Its target and bounds come from the snapshot node read for the stable id, with no second role, name or id mapping. An id the snapshot does not read is refused like every id-addressed verb (per a11y-plan §7 Screen Reader Support).
- A focused text input paints a caret (honouring `caret-color`) and a selection highlight, and focused controls paint the default-stylesheet or author focus outline. Determinism must hold with a control focused, so caret painting must not vary between two runs. Whether a caret blinks, or depends on time, on the headless paint path is research's question (per a11y-plan §6 Visual Design Verification).
- The viewport carries a light/dark colour scheme and a zoom level, and a scale change invalidates text shaping. For identical pixels on repeat, the screenshot's colour scheme, zoom and scale must be the session's pinned ones. Whether the stand's headless boot pins the colour scheme and scale is research's question (per a11y-plan §6 Visual Design Verification).
- Nodes hidden by `display: none` or `visibility: hidden` are not in the accessibility tree. An `aria-hidden="true"` node stays in the tree, marked hidden. So which ids an element screenshot can address follows the tree's exclusion rules, not paint visibility (per a11y-plan §4 ARIA Patterns & Roles).
- The engine's changed set is marked by focus moves and in-document writes. A screenshot is not an acting step, so it must not mark the set or move focus. The snapshot's `focused` reading and the tree's focus must be the same after a screenshot as before it (per a11y-plan §2 A11y Strategy).

## Patterns to follow
- The snapshot-consumer pattern: `DioxusDocument::snapshot` → `to_text` → `diff` → the MCP tool result. Each reads the one model and nothing else. An element screenshot locates and crops from the snapshot node in the same way (per a11y-plan §7 Screen Reader Support).
- The masked-value proof shape from `stand_mcp_masked`: a test-only password input in a fixture beside the stand (no stand task gains one), a typed sentinel, and the sentinel counted 0 times in every output, in both layout modes. Apply the same shape to the image (per a11y-plan §7 Screen Reader Support).
- The stand's focus checks drive focus through the harness's `press` / `press_with` and a click, then read `focused` off the snapshot and the tree's focus. Reuse them to put a control in a focused state before screenshotting it (per a11y-plan §5 Keyboard Navigation).
- A cue is asserted without colour: the flight booker's invalid state is read as `aria-invalid` and a `disabled` attribute, never from a pixel colour. A check that turns on a control's state reads that state from the snapshot, not from the image (per a11y-plan §8 Cognitive Accessibility).

## Anti-patterns to avoid
- Do not add a second role, name or bounds mapping for the element screenshot (for example, resolving an id by walking the DOM or the paint tree on its own). The snapshot model is the one reader (per a11y-plan §7 Screen Reader Support).
- Do not let any output carry a password's typed text, as pixels or otherwise, where the snapshot reads `MASKED_VALUE` (per a11y-plan §7 Screen Reader Support).
- Do not prove a control's state by its painted colour alone (per a11y-plan §8 Cognitive Accessibility).

## Contract bindings
- a11y ↔ security: the password-mask reading (a11y-plan §7) is the same masking as the security plan's rule that a password's or file input's value crosses only as the mask. A screenshot is a new form of that crossing, which is the founder's P4 question in scope.
- a11y ↔ design: painted focus rings, caret and state colours (a11y-plan §6) are design-system §Color Palette tokens. A screenshot exports them, and a future contrast harness could read them, but that harness is another route entry's work (scope Boundaries).
- a11y ↔ tests: the stand checks run in both layout modes (`for incremental in [false, true]`), and the focus and mask checks reuse the shared stand tables in `tests/blitz-tests/tests/common/mod.rs` (a11y-plan §7).

## Acceptance criteria contributions
- (a11y) Two screenshots of the same test-only password input, each after a different typed sentinel of equal length, are pixel-identical, and neither shows the sentinel. The check passes in both layout modes and fails, never skips, if a typed character is painted in the clear (per a11y-plan §7 Screen Reader Support).
- (a11y) An element screenshot of a stand control is the size of the `bounds` its snapshot node reads. An id the snapshot does not read is refused `stale` / `not-found` with no image produced (per a11y-plan §7 Screen Reader Support).
- (a11y) With a text input focused through a Tab press (caret and focus outline painted), two screenshots taken in separate runs on the same host are pixel-identical (per a11y-plan §6 Visual Design Verification).
- (a11y) After a `screenshot` call, the snapshot's `focused` node and the accessibility tree's focus are the same as before the call, and a diff taken across the call is empty (per a11y-plan §2 A11y Strategy).
