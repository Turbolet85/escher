# security extract

## Relevance
relevant — `screenshot` is a new verb on all three external surfaces (socket `call`, `escher-session` command line, MCP `tools/call`), and its result takes screen content out of the process in a new form (pixels), which is the crossing question this plan tracks.

## Constraints
- The crossing rule decides whether the image needs the founder: per security-plan §Input Validation (Driver session socket row), a new field of a closed value set inside an already ratified carrier is not a widening, while a field holding authored text, an open value set, a new carrier or a new exit still is. Pixels hold every name and value the screen paints, in an open value set, and a file written by the driver or an MCP image content block would be a new exit or carrier. Per security-plan §Threat Model Summary (local IPC and local stdio vectors), the ratified crossings list ids, names, masked values, snapshot text and diff, not images. So the screenshot's result form is a halt-for-ratification question at P4, never settled silently. Any new exit (a file the driver writes, a new stream) also needs an arch §Occupied Resources registration first.
- A typed password must not leave as pixels. Per security-plan §Input Validation (password and file `input` value row), the `MASKED_VALUE` mask is snapshot-only ("the DOM is untouched"), and every driver exit so far masks by construction because it reads the snapshot. A raster reads the painted DOM, not the snapshot. Whether the engine paints a password's characters in the clear is research's question (the CARRY's hypothesis, to be measured on a rendered frame). The same row and security-plan §Data Protection (Local user data handled) say a file input's `value` attribute holds the chosen file's full host path. Whether paint draws that path or file name is also research's question.
- `screenshot` joins the closed `'static` verb table and is checked by `validate` before anything runs. Per security-plan §Input Validation (Driver command schema row), that means bounded argument kinds (`id` is 1–1024 bytes), the fixed refusal order, no `Session` in `validate`, and no `unwrap`/`expect`/`panic!`/`unreachable!` or index on anything a call supplies. An id the screen does not read is refused `stale`/`not-found` with nothing run, and the session keeps no `NodeId` between calls. A new argument kind, such as an output path, widens this validated surface, and each earlier widening of it was ratified by the founder.
- The cause set is closed at eight. Refusals and session errors are fixed `'static` texts that hold nothing a call supplied. Per security-plan §Error Handling (Error format), `Refusal`, `Cause` and `Fault` have no `String` field, and each `SessionError` is one row of `SESSION_ERRORS` with a fixed kind, meaning and remedy that holds no path. A missing-font failure or an encode failure must take that typed form, and a new cause or error row changes a closed table.
- Answers are bounded. Per security-plan §API Security (Local session socket row), an answer on the wire is at most 1,048,576 bytes on its JSON line, and past that it is `oversize`/`AnswerTooLarge` with the call already run. Per security-plan §Input Validation (MCP server row), an MCP result's text is at most 1,048,576 bytes (`wire::MAX_ANSWER_BYTES`) and is replaced by `AnswerTooLarge`'s result past that. A PNG of the pinned viewport must be measured against these bounds, and P4 decides whether to change them (the founder ratified the current bounds together with the crossing).
- The command line writes back nothing the caller typed. Per security-plan §Input Validation (CLI arguments (escher-session) row), the closed argv reader checks a call before any session is touched, has four endings with fixed statuses, and writes back no path, label, id or value in any ending. Stdout carries the command's answer only. A `--id` or output argument follows the same rules, and no path on argv may panic.
- No agent-supplied URL or path is routed through the fetch or font path. Per security-plan §Input Validation (`@font-face` source row), escher routes no agent- or user-supplied URL through that path because no driver verb takes a URL and the stand boots offline on its bundled font. Per security-plan §Input Validation (`file:` URLs (net provider) row), `blitz-net` reads `file:` URLs with no path restriction. "Fails, never skips, without fonts" must fail with a typed error, never fetch a fallback font.

## Patterns to follow
- Order of a call: `Session::run` validates first, then the executor looks up the id fresh on the current screen and refuses with nothing run and the instance unchanged. Per security-plan §Input Validation (Driver command schema row). `screenshot` reuses this lookup, so it adds no new id path.
- Program text the tool itself states about the verb (its help, its result fields' help, any remedy) is fixed `'static` table text. Per security-plan §Input Validation (MCP server row) and the founder's 2026-10-12 ruling recorded there, that text rides the ratified carriers. Text from the screen does not.
- Written forms come from the crate's hand-written JSON writer only, and `serde_json` reads but writes nothing. Per security-plan §Input Validation (MCP server row) and §Dependency Security (Pinning, the `serde_json` entry).
- A new dependency (for example a PNG encoder, if the raster path does not already bring one into the escher-driver or stand graph, which is research's question) gets a hand review of the lock delta. Per security-plan §Dependency Security, that means licence, repository, build script and dependents, `--locked`, the committed `Cargo.lock`, and the cargo-deny audit leg green with no blanket allow.
- One `command` span per call. Per security-plan §Logging & Monitoring (escher's own sink), the span is built by hand under `escher_driver` with fixed words, bools and counts only. Its MCP parent `tool_call` holds `tool` and `ending` only.

## Anti-patterns to avoid
- Do not field or log an `Outcome`, an image, its bytes or encoding, an output path, an id or anything a call supplied. Do not put any of these in a `Refusal`/`Fault`, a test name or an assertion message. Per security-plan §Input Validation (Driver command schema row).
- Do not carry the reference raster code's panics into the driver path. Per security-plan §Error Handling (Panic paths), `examples/screenshot.rs` `unwrap()`s network and file errors and `apps/browser/src/capture.rs` unwraps archive and file errors. The driver's version returns typed errors.
- Do not let a font-missing screenshot render with a host font or reach `blitz-net` for a font. Per security-plan §Input Validation (`@font-face` source row).

## Contract bindings
- security ↔ obs: the screenshot's `command` span fields (and any new field) must keep the scrub rule. The `host_log` / `mcp_log` needle measurements (0 ids, 0 names, 0 typed sentinel at `trace`, both builds) extend to a flow that includes `screenshot` (obs-plan §3; security-plan §Logging & Monitoring).
- security ↔ tests: a password-in-pixels check on a fixture with a typed password, beside `stand_act_filled` / `stand_mcp_masked`, in both layout modes (test-plan §3; security-plan §Input Validation password row).
- security ↔ arch: any new exit (a file the driver writes, an MCP image content block, a new stream) is an arch §Occupied Resources registration plus a security-plan amendment, ratified first (security-plan §Threat Model Summary).

## Acceptance criteria contributions
- A password typed through the driver's `type` and then captured by `screenshot` does not show its characters in the image, in both layout modes, measured on the rendered frame. A file input's host path likewise does not appear, or the result is recorded as measured and owned (per security-plan §Input Validation (password and file `input` value row)).
- `screenshot` with a bad argument is refused `malformed`, and with an id the screen does not read it is refused `stale`/`not-found`, with nothing run and the next snapshot unchanged, on the command line, the socket and MCP. No refusal or session-error answer holds the supplied id, path or argument text (per security-plan §Input Validation (Driver command schema row)).
- With escher's sink installed at `RUST_LOG=trace`, a host or `mcp` role that runs a flow including `screenshot` writes 0 id needles, 0 name needles and 0 typed-sentinel occurrences to stderr under both builds. The screenshot's span lines hold fixed words and counts only (per security-plan §Logging & Monitoring).
- A screenshot answer over 1,048,576 bytes ends `oversize`/`AnswerTooLarge` on the wire and over MCP, without a panic or a truncated image, unless P4 records a different bound ratified by the founder (per security-plan §API Security (Local session socket row)).
