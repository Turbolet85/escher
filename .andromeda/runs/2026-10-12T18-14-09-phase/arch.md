# arch extract

## Relevance
relevant: the chunk adds an eleventh verb to escher-driver's one verb table, served on all three surfaces. It also gives the driver crate a raster path and sends a new content class (pixels) over carriers the plan records as ratified for named content only.

## Constraints
- `screenshot` joins the one closed verb table as a row with its level, help, argument and result shapes. `Command` (or `SessionCommand`) is a closed set that gains a variant. `Session::run` stays the one entry point and runs `validate` before anything else. An id it addresses resolves on the screen as it reads now and is refused `stale` / `not-found` from the session's record of ids. The refusal causes stay closed at eight unless a new cause is decided. Whether an off-view or clipped element reuses `off-screen` is P4's to decide. (per architecture §Standard Contracts → Driver session)
- What a caller is answered with has one written form: a line of JSON written by hand in the crate-private `json` module. No serialization crate writes output, and `serde_json` only reads MCP requests. The answer bound is 1,048,576 bytes on the wire (`oversize` / `AnswerTooLarge`, the call not rolled back) and for an MCP tool result. An image result has to fit inside these rules or be decided against them at P4. (per architecture §Standard Contracts → Driver session)
- The socket, the command line's stdout and the `mcp` role's stdio are ratified carriers for ids, names, masked values, snapshot text, the diff, closed-set fields and the program's own `'static` table text. Content from a screen, a new carrier or a new exit still counts as a widening. Pixels of the screen are screen content, and an image written to a file is a new exit. Either one is a founder question. (per architecture §Established Decisions → Driver session)
- §Occupied Resources records one listener and no network port. Its Filesystem row lists every path the tree writes. A screenshot written to disk needs a caller-named location registered there. The driver has no default state location and reads no env var, so it cannot pick a path itself. (per architecture §Occupied Resources → Filesystem; §Occupied Resources → Network ports and listeners)
- escher-driver's dependency set is recorded as exactly four crates: blitz-test-harness, dioxus-native-dom with `accessibility`, `tracing`, `serde_json`. It names no app and has no `[features]` table. A raster path in the crate (blitz-paint, an anyrender CPU renderer, a PNG encoder) changes that recorded set and its `Cargo.lock` delta, so it is a decision to record, not a silent add. Whether the raster belongs in escher-driver or in the caller's boot (the stand) is P3/P4's question. (per architecture §Established Decisions → Driver session; §Occupied Resources → Names)
- New dependencies are declared once in `[workspace.dependencies]` and consumed as `{ workspace = true }`. In-repo crates are declared with `default-features = false`. (per architecture §Conventions → Manifests)
- The session holds no viewport, font or scheme setting, so a screenshot reads what the caller's boot pinned. On the stand that is the pinned viewport, scale, color scheme and the single bundled-font context with system fonts off, offline. Determinism and "fails without fonts" therefore bind to the stand's boot. (per architecture §Standard Contracts → Headless stand; §Standard Contracts → Driver session)

## Patterns to follow
- The raster path the plan records: `paint_scene(PaintScene, &mut BaseDocument, scale, width, height, x_offset, y_offset)` into a CPU image renderer, the way the `screenshot` example renders through `VelloCpuImageRenderer`. Painting assumes style and layout are already resolved, which here means after settle. (per architecture §Standard Contracts → Paint and shell; §Established Decisions → Renderer backends; §Stack and Technologies → Rendering abstraction and backends)
- A verb joins the table the way `scroll` (refusal-detection) and `help` (self-description) did. The change runs through the verb row, the `Command` variant, the executor arm, the JSON writer and the MCP `inputSchema`. It also updates the counts `describe()` and `tools/list` serve, which become eleven verbs. (per architecture §Standard Contracts → Driver session)
- An element crop reads the snapshot node's `bounds`, which are viewport-relative and come from the existing reader. It never adds a second geometry computation. The in-view reading is `BaseDocument::visible_region`, as the `off-screen` refusal and `scroll`'s `in_view` use it. (per architecture §Standard Contracts → Dioxus DOM bridge; §Standard Contracts → Driver session)
- Library errors are typed enums with `Display`. The `.unwrap()` / `panic!` style of the examples is not carried into the driver. (per architecture §Conventions → Error handling)
- blitz-tests keeps one test target per file directly under `tests/`, and `test_blitz_tests_targets.py` pins the manifest. (per architecture §Conventions → Tests)

## Anti-patterns to avoid
- No `NodeId` crosses any carrier, and the command span fields no screen content. The plan lists the screen text and its length as never fielded, so image bytes or an image's size must not become a span field. (per architecture §Standard Contracts → Driver session)
- Never render with a host font. The stand's font context is the bundled single font with system fonts off. A fallback to `system-fonts` breaks the stand's pinned boot. (per architecture §Standard Contracts → Headless stand)
- Do not add a dependency, carrier, file output, env var or crate without recording it. A new listener, port, env var or workspace crate is an §Occupied Resources registration. (per architecture §Occupied Resources → Names; §Occupied Resources → Environment variables)

## Contract bindings
- arch ↔ security: pixels leaving the process over the socket, stdout or stdio (and any file) are a crossing question, as is a password painted in the clear (the CARRY). These bind to the ratified-crossing records in §Established Decisions → Driver session and §Occupied Resources → Network ports and listeners, and to the security plan's crossing rows.
- arch ↔ tests: both layout modes must produce identical layouts, so a screenshot of one stand state is expected to match across `incremental` false and true. Checks go in one blitz-tests target per file, or in seven_guis tests for the binary and MCP role. (per architecture §Design Philosophy → One incremental pipeline, safe identities; §Conventions → Tests)
- arch ↔ obs: the `command` span keeps its eight fixed-word or count fields, and the `tool_call` span its two. A screenshot adds no content-bearing field. (per architecture §Standard Contracts → Driver session; §Cross-cutting Patterns → Logging and timing)

## Acceptance criteria contributions
- `VERBS` holds `screenshot` as one row, and `describe()`, MCP `tools/list` and the command line's usage line all read it from that row. A call naming it is no longer refused `unknown-verb`. Its id goes through `Session::run`'s `validate` and then the id resolution (`stale` / `not-found`) before anything renders. (per architecture §Standard Contracts → Driver session)
- The screenshot answer is written by the crate's hand-written `json` writer, or by a form P4 decides and records, and no serialization crate writes it. An answer over 1,048,576 bytes reads `oversize` / `AnswerTooLarge` on the wire and over MCP, never a truncated image. (per architecture §Standard Contracts → Driver session)
- escher-driver's dependency list and the `Cargo.lock` delta are either unchanged or stated and recorded as a decision, and any new crate comes through `[workspace.dependencies]`. There is no new listener, port or env var. Any file the verb writes goes to a caller-named path that is registered. (per architecture §Established Decisions → Driver session; §Conventions → Manifests; §Occupied Resources → Filesystem)
- A screenshot of a stand state renders at the stand's pinned viewport and scale with only its bundled font. It is byte-identical across `incremental` false and true, and across two separate boots. (per architecture §Standard Contracts → Headless stand; §Design Philosophy → One incremental pipeline, safe identities)
