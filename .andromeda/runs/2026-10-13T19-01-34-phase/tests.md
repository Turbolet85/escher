# tests extract

## Relevance
relevant — the chunk changes engine input behaviour that a standing stand check pins (`stand_act_range`, rewritten here rather than deleted), and it needs new checks of arrow-key stepping, click-by-position and the `input` event that run on the harness and the driver.

## Constraints
- Every stand and driver check of the new range behaviour runs in both layout modes, with no sleep and no wall-clock read, and asserts the returned diff equal to the check's own `before.diff(&after)` and equal across the two modes. This is the shape of the driver-action checks (per test-plan §5 Session ↔ held instance). If range state is held in layout construction, the incremental and non-incremental documents must stay identical (per test-plan §2 Differential oracle).
- The rewritten `stand_act_range` and any new `stand_*` file declare `mod session_common;` and use its `hold` / refusal readers like the other thirteen `stand_act_*` files. Stand tables (`controls`, `rendered`) are read from `tests/common/mod.rs` as stated expectation and are never restated per file (per test-plan §3 Crate-local test helpers).
- A new check of the engine alone (a range value stepped, clamped and snapped) is a blitz-tests integration file, one test target per behaviour. It is not added to upstream's `tests/all.rs` (per test-plan §2 Directory pattern). A unit test inside blitz-dom goes in an inline `#[cfg(test)] mod tests` block and builds its DOM through `DocumentMutator` with `resolve(0.0)` (per test-plan §4 Conventions; per test-plan §2 Test levels observed, blitz-dom pipeline tests).
- Harness input reaches the document through its real event-dispatch pipeline, and `dispatch_recorded` bypasses Dioxus VirtualDom forwarding (per test-plan §5 Boundaries covered, Harness ↔ event pipeline). So a check that an app's `oninput` runs with the new value must drive the Dioxus document through the input helpers or the driver, not through `dispatch_recorded`.
- The harness's `key_event` uses `Code::Unidentified` and fills text only for pressed character keys. Synthesized pointer events set page, screen and client coordinates to the same values (per test-plan §3 blitz-test-harness, Input helpers). Whether the engine's new arrow-key handling keys on `Key` (which `press` sets) or on `Code` (which it does not) is research's question. So is whether `click_at` at a chosen x reaches a position-based handler.
- The two runners build different engine features. `cargo test --workspace` turns on blitz-dom `tracing` and `writing-mode`; `-p blitz-tests` turns on neither. A green per-package run is not the workspace leg's green, and a check that reads a sink's capture counts lines by target, never in total (per test-plan §9 Engine features by runner).
- Timer time moves only through `TimerTicks` / the driver's `advance`, and the elapsed display is capped at the duration (per test-plan §8 Time (seven_guis timer)). A check that moves the Timer's duration slider reads the duration and the elapsed cap on the harness clock and never waits on wall time.

## Patterns to follow
- `stand_act_*` as the model for driver checks: a `Call` run through `Session::run` on a held stand session, settled, with the diff read and both layout modes compared (per test-plan §5 Session ↔ held instance).
- Harness input helpers `press`, `click`, `click_at` and `center_of` for the engine-level reading, each pumping after dispatch (per test-plan §3 blitz-test-harness, Input helpers and Inspection helpers). `click_at` is the harness route to "a click at a chosen position along the track" if P4 picks it.
- A minimal inline-HTML fixture beside the stand where the stand lacks a case, such as an off-centre boot value or a different `min`/`max`/`step`, seeded as an inline string constant or a `format!`-built page (per test-plan §7 Seed strategies, Inline HTML). Fixtures run under the stand's pinned `stand::options(incremental)` or explicit `HarnessOptions` (per test-plan §7 Builders and options).
- Stand checks assert unconditionally under the bundled DejaVu Sans, with no font-skip path (per test-plan §2 Test levels observed, Font-dependent tests).

## Anti-patterns to avoid
- An assertion held inside an `if` on a measured value, which passes without asserting. Two text-input tests do this today (per test-plan §4 What unit tests cover, Conditional assertions). A range check asserts the stepped, clamped and snapped values unconditionally.
- Reading an empty or skipped run as a pass. `agent-run.sh run` gives `failed` when no test line parsed (per test-plan §3 Agent-run contract, `run {selection}`). Deleting `stand_act_range` instead of rewriting it would leave its behaviour unpinned (the scope's measured-starting-point CARRY).
- Logging content from a new engine call site. Engine telemetry stays behind `#[cfg(feature = "tracing")]`. Under the workspace build, a new engine line beside a driver call would change what `stand_act_spans` and `host_log` count by target (per test-plan §9 Engine features by runner).

## Contract bindings
- tests ↔ obs: `stand_act_spans` and the seven_guis `host_log` / `mcp_log` captures read exactly one `escher_driver` line per call and count engine lines by target under the workspace build (per test-plan §9 Engine features by runner; per test-plan §5 Session ↔ held instance). Any engine `tracing` site added for a range step or `input` event binds to obs §3's sink rules.
- tests ↔ a11y: the `a11y` CI leg runs `accessibility_hidden`, `accessibility_roles` and `focusability_updates` (per test-plan §9 Pipeline facts, Legs). The slider's role and focusability readings stay green there. The keyboard harness and the SC 2.1.1 sweep are out of scope (scope §Boundaries).
- tests ↔ arch/driver: `click` and `press` reach the slider through `Session::run` with no driver code change expected (scope). If the schema's help text on range inputs moves, escher-driver's inline schema unit tests and `cli_commands` / `mcp_server` read it (per test-plan §5 Session ↔ held instance).
- The keyed contract "Session lifecycle" does not apply: the chunk adds no socket, wire or host behaviour.

## Acceptance criteria contributions
- `stand_act_range` is rewritten to the new reading, not deleted, and still carries its `stand_` prefix. It shows an arrow press stepping the Timer's slider by its step, clamped to `[min, max]`, and a click setting the value by position, with the app's `oninput` result visible in the returned diff, in both layout modes. `bash scripts/agent-run.sh run stand` ends with `run.end` outcome `passed` and 0 failed (per test-plan §3 Agent-run contract; per test-plan §5 Session ↔ held instance).
- The existing readings that touch the slider or the Timer stay green unchanged: `stand_snapshot_state`, where the range input reads the app's duration, and `stand_timer` / `stand_act_timer` (per test-plan §1 Coverage scope, tests/blitz-tests; per test-plan §8 Time (seven_guis timer)).
- Every new or rewritten check passes under both `cargo test -p blitz-tests --locked` and the workspace leg, `bash .github/scripts/ci-leg.sh fast` (per test-plan §9 Engine features by runner; per test-plan §9 Pipeline facts, Local pre-push gate).
- If the range state touches layout construction, `incremental_oracle` stays green and each new engine check runs `for incremental in [false, true]` (per test-plan §2 Test levels observed, Differential oracle).
