# security extract

## Relevance
relevant — the chunk is a founder-ruled boundary widening: engine behaviour that changes for every document with an `input type="range"`, the browser app's remote pages included, driven by numbers read from author markup.

## Constraints
- The range interaction model reaches remote content: per security-plan §Threat Model Summary (vector "remote web content", entry point the browser's parsing of arbitrary remote HTML) the arrow-key step, the click-by-position and the `input` event apply to untrusted documents too, so every value they read from the markup (`min`, `max`, `step`, `value`) is untrusted input.
- security-plan §Input Validation requires the widening to be stated there as a row of its own: what the engine now reads from a range input's attributes, how each read is bounded, and the founder's ruling written verbatim as he gave it («Пусть будет а», 2026-10-07, relayed by the overseer; the English wording "a minimal range interaction model in the engine" is the overseer's), recorded at this chunk's wrap. No such row exists in the plan today.
- security-plan §Input Validation (rows "Markup numeric attributes" and "Markup attributes" / `attr_parsed`) requires a numeric markup attribute to be parsed fallibly — a parse failure yields the default, never a panic — so the range's `min` (default 0), `max` (default 100), `step` (default 1) and `value` reads take that shape.
- security-plan §Input Validation (rows "Layout values" and "Markup numeric attributes" / `rowspan`) requires degenerate numbers to be discarded or clamped before use (zero, infinite and NaN values discarded; values kept finite; a span clamped to a range), so a `step` of 0, a negative or non-finite step, `min > max`, a huge value or a click position off the track must produce a finite value inside `[min, max]` on the step grid, with no division by zero, no unbounded loop and no panic.
- security-plan §Error Handling (Graceful degradation) requires event handling to degrade without panicking — `handle_ui_event` returns early with no target, stale node ids resolve through `get` to `None` — so the new keyboard and pointer paths add no `unwrap`, `expect`, `panic!`, `unreachable!` or slab index on an author-supplied value or a possibly stale node; whether the touched `events/keyboard.rs` / `events/pointer.rs` paths already meet this is research's question.
- security-plan §Logging & Monitoring requires engine telemetry to stay behind the `tracing` feature and escher's sink to print only safe fields of an engine target, and states that no new user-content log field is to be added: a range's value, its attributes or the `input` event's data are fielded at no new log site.
- security-plan §Input Validation (Driver command schema row) fixes the driver's surface — eleven verbs, six argument kinds, nine causes, the command span's eight fields of fixed words and counts — and the scope adds no verb; the range's changed value leaves the process only as a control value inside the ratified carriers (Driver session socket row; MCP server row), and any moved help text stays fixed `'static` table text (security-plan §Error Handling, the `SESSION_ERRORS` / help text ruling of 2026-10-12).

## Patterns to follow
- The `aria-selected` · `aria-pressed` · `aria-invalid` row of security-plan §Input Validation is the house shape for a new read of author markup on every document: parsed fallibly against a closed rule, no log site, no panic path, nothing of the attribute's text carried out as typed, a long or unrecognized value handled — the range attribute reads follow it.
- security-plan §Input Validation row "Markup attributes" / `disabled`: presence of `disabled` makes an element ignore pointer selection and click default actions; the range's click and arrow-key default actions honour the same reading (whether they do is research's question).
- security-plan §Error Handling (Graceful degradation): stale node ids resolve through `get` / `contains_key`, never by index — the new dispatch paths resolve targets the same way.
- security-plan §Dependency Security (Pinning): any dependency the change takes is reviewed by hand and the audit leg (`ci-leg.sh audit`) reads `advisories ok` with `deny.toml` unchanged; none is expected.

## Anti-patterns to avoid
- Writing a range's value, attribute text or `input` event data into a log, span field or event — per security-plan §Logging & Monitoring (the sink's scrub sets; add no new user-content log fields).
- Adding a new exit or carrier for range state without a founder question — per security-plan §Input Validation (Driver session socket row: the founder's rule of 2026-10-10 that a new field of a closed value set inside a ratified carrier is not a widening, while an open value set, a new carrier or a new exit still is). AccessKit Increment/Decrement/SetValue actions (inbound from an assistive technology) or a numeric value newly written on the accessibility node would be such a question; whether the node already carries a range's numeric value is research's question.
- A panic, division by zero or unbounded step loop on author-supplied `step` / `min` / `max` — per security-plan §Input Validation (Layout values rows) and §Error Handling (Graceful degradation).

## Contract bindings
- security ↔ a11y: the accessibility node's value for a slider and any AccessKit action on it ride the platform adapter crossing recorded in security-plan §Input Validation (`id` row and `aria-*` row: author-derived content classes on that crossing were each ratified by the founder); keyboard reach (SC 2.1.1) is a11y's, the crossing is security's.
- security ↔ obs: no new engine log field holding the value — obs-plan's silent census and observed-absent list are where the same fact is kept (security-plan §Logging & Monitoring).
- security ↔ tests: the rewritten `stand_act_range` and a degenerate-attribute fixture carry the no-panic / bounded-value proof; the existing `stand_act_spans`, `host_log` and `mcp_log` checks carry the no-new-log-content proof (security-plan §Logging & Monitoring measured readings).
