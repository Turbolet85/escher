# a11y extract

## Relevance
partial — the chunk gives a role-Slider control keyboard and pointer behaviour for every document (SC 2.1.1 surface), but builds no keyboard harness, no SC 2.1.1 sweep and no AccessKit action path.

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary); arrow-key stepping of a focused range input is SC 2.1.1 surface for the stand's `timer-duration` slider, and focusability and focus order are a11y surface — so a pointer click that focuses the slider (an open P4 decision) changes a11y-visible state and must be stated, not incidental.
- `input type="range"` maps to `Role::Slider` (per a11y-plan §4 ARIA Patterns & Roles, Form input); the chunk must not move that role or the slider's accessible name — the stand's input names are stated once in the shared `controls` / `INPUT_NAMES` tables (per a11y-plan §7 Screen Reader Support, Accessibility tree output), never re-mapped.
- Focusability and Tab order are defined by the engine's focusable rule (an `input` with no tabindex is focusable) and `focus_next_node` / `focus_prev_node` (per a11y-plan §5 Keyboard Navigation, Focus order per layout); range handling must leave the stand's forward focus sequence unchanged — two Tab presses still reaching the slider, as the scope measured.
- The accessibility tree refreshes on change only through the engine's changed set, which a focus or checked change and a text control's input mark (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle); a range value change that reaches the tree or the snapshot diff must mark the changed set — whether a value write from the new range path (or the app's re-render of `value`) marks it is research's question.
- The tree gives an element node no value property; the snapshot reads `value` from the element — the editor's text, else the `value` attribute (per a11y-plan §7 Screen Reader Support, Accessibility tree output); so whether a stepped or clicked range value reads back in the snapshot depends on what the engine/app writes into `value`, and adding an AccessKit numeric value would be a new tree property — a P4 decision, not implied by the plan.
- The stand contrast record holds `timer-duration` as its one `no-text` row of 18 (per a11y-plan §6 Visual Design Verification, Color contrast); a range change that paints text or moves a thumb must leave that row's classification unchanged or move the record with it.

## Patterns to follow
- Checkbox and radio clicks toggle state, dispatch `input` and move focus to the control (per a11y-plan §5 Keyboard Navigation, Focus restoration) — the engine's existing shape for a form control's pointer default action, the nearest precedent for a range click that sets a value and fires `input`.
- Text inputs handle arrow keys and Home/End on the focused editor (per a11y-plan §5 Keyboard Navigation, Keyboard handling) — the precedent for key handling scoped to the focused control; Tab / Shift+Tab stay the engine's focus movers.
- The stand's keyboard focus check drives `Key::Tab` through the harness's `press` / `press_with` and asserts the focused control reads `focused` and is the tree's focus, in both layout modes (per a11y-plan §3 A11y Assertion Harness Contract, Keyboard test harness; per a11y-plan §5 Keyboard Navigation, Test harness pattern) — the shape for the rewritten `stand_act_range` arrow-key rows.
- Snapshot, text and diff are readers of the one model with no second role or name mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output) — a range value change is proven by the diff naming the slider (and its display) by stable id, read off the model.

## Anti-patterns to avoid
- No second role or name mapping in any reader or check of the range change — role and name come from the tree `accessibility_tree` returns (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- No new stand control or focus change left unkeyed or unnamed: every element an agent can act on reads an author key, checked by `DioxusDocument::unkeyed_actionable` (per a11y-plan §7 Screen Reader Support, actionable-key rule) — a fixture added for the off-centre click keeps its controls keyed and labelled.

## Contract bindings
- a11y ↔ tests: the rewritten `stand_act_range` runs in both layout modes in the workspace `test` leg; the `a11y` CI leg stays its three files (`accessibility_hidden`, `accessibility_roles`, `focusability_updates`) unless the plan is amended (per a11y-plan §9 CI Integration).
- a11y ↔ design: `stand_contrast`'s `timer-duration` no-text row binds design-system §Color Palette (per a11y-plan §6 Visual Design Verification, Color contrast).
- a11y ↔ security: the range model is a behaviour change for every document, remote pages included — the widening stated in security-plan §Input Validation; any AccessKit Increment/Decrement/SetValue action would cross the platform adapter, whose ActionRequested handling is an unhandled TODO (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).

## Acceptance criteria contributions
- (a11y) Keyboard: with `timer-duration` focused by Tab, right/left arrow change its value by `step` within `[min, max]`, and the snapshot's `focused` reading stays on the slider and it stays the tree's focus, in both layout modes (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- (a11y) Role and name: after the change the slider still reads `Slider` with its non-empty accessible name, and the stand's forward focus sequence is unchanged (per a11y-plan §7 Screen Reader Support, Accessibility tree output; per a11y-plan §5 Keyboard Navigation, Focus order per layout).
- (a11y) Change reach: a stepped or clicked value is named by the snapshot diff on the slider's stable id (or the value it drives) — the changed set marked so the tree refresh sees it (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- (a11y) Contrast record: `stand_contrast` still reads 18 rows, pass 9 · fail 5 · exempt-inactive 3 · no-text 1, `timer-duration` no-text (per a11y-plan §6 Visual Design Verification, Color contrast).
