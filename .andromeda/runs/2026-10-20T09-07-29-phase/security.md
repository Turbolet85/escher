# security extract

## Relevance
relevant — the walk is reached through the driver's validated schema and its ratified carriers (socket `call`, command line, MCP, kept check). Any new verb, argument, result field, cause or log field is a boundary question, and per inputs#I1 that fork belongs to the founder.

## Constraints
- Every call that reads a part must pass `validate` (or `validate_session`) before anything runs. The verb table is closed, each argument kind has a bound, there is no `unwrap`/`expect`/`panic!`/index on anything a call supplies, and no `Session` appears in the validator's signature. A new verb, or a new argument on `snapshot` (for example a part index or cursor), widens this validated surface. A widening needs a ruling and does not land silently (per security-plan §Input Validation, Driver command schema row).
- A part may carry only the content classes the screen's crossing already ratified: ids, accessible names, control values and snapshot text. No `NodeId` may cross. A new field of a closed value set (for example a count or a "more parts" boolean) inside an already ratified carrier is not a widening. An open value set, authored text, a new carrier or a new exit is a widening. So if the walk uses a cursor or token that crosses out and back in, it must carry no `NodeId`, and it re-enters as call-supplied input with a bound (per security-plan §Threat Model Summary, local IPC and local stdio vectors).
- Answer bounds stay unchanged. On the socket an answer is at most 1,048,576 bytes on its JSON line, past which it becomes `oversize` with the call already run. A socket request line is at most 16,384 bytes. An MCP result is at most 1,048,576 bytes, its request line at most 65,536, and an over-bound result becomes `AnswerTooLarge`. Today a whole over-budget snapshot is held only by these bounds. Whether the code answers it whole on every carrier is research's question (per security-plan §API Security, Local session socket row; per security-plan §Input Validation, MCP server row).
- A part's text must read a password's or file input's value as the fixed mask `MASKED_VALUE`, exactly as the whole snapshot does. Masking applies on every carrier and in a kept check's `answer` (per security-plan §Input Validation, password and file `input` value row; per security-plan §Data Protection, Files (kept checks)).
- The session's record of ids must be fed from the session's own snapshots and never from a call's argument. It holds at most 4096 ids, each no longer than `MAX_ID_BYTES`, and must never be printed, logged or put in a field. Whether a part read feeds it as `snapshot` and `lint` do, and how the 4096 cap behaves when one large screen holds more ids than that, are research's questions (per security-plan §Input Validation, Driver command schema row).
- Refusal causes are closed at eight, each with a fixed `'static` name, meaning and remedy. A `Refusal` or `Fault` has no `String` field. A bad or out-of-range part request must map to an existing cause (`malformed` from `validate`). A new cause would be a ratification, and no refusal may echo a call-supplied value (per security-plan §Error Handling, Error format).
- Under `--record`, a recorded step for any new verb or argument must still be read by the strict `Check::from_bytes`. That reader takes closed keys, `tool` one of the instance verbs, argument names from that verb's schema, `answer` a required JSON object, and at most 400 records / 1,048,576 bytes. A step it cannot spell is not recorded (per security-plan §Input Validation, Recorded check row; per security-plan §Input Validation, Driver recording directory row).

## Patterns to follow
- Build calls with the shared builder `command::call_of`, used by both the MCP server and the recorder, so a replayed or MCP-borne walk step goes through `validate` inside `Session::run` and nothing else (per security-plan §Input Validation, Recorded check row).
- Write answers with the crate's hand-written JSON writer (`to_json`). `serde_json` only reads requests and writes nothing. Bound an MCP result through `ToolResult::bounded` (per security-plan §Input Validation, MCP server row).
- Take values from the masked snapshot reader (`DioxusDocument::snapshot`). The diff and text forms read values only from the snapshot, so a part built from one snapshot inherits the mask (per security-plan §Data Protection, Local user data handled).
- Proof fixtures stay offline: the shared fixture boot and `HeldNet`. No agent- or user-supplied URL goes through `blitz-net`, and no committed check holds typed text, a host path or a secret (per security-plan §Data Protection, Files (committed checks)).

## Anti-patterns to avoid
- Adding a field to the `command` or `tool_call` span: a part's text, its length, a part index or the part count. The command span keeps its eight fixed-word, bool and count fields. The screen text and its length are named as never fielded (per security-plan §Input Validation, Driver command schema row; per security-plan §Logging & Monitoring, escher's own sink).
- Keeping a `NodeId` between calls, or handing one out as a walk cursor. The executor keeps none between calls, and none crosses (per security-plan §Input Validation, Driver command schema row).
- Adding a panic path (`unwrap`, `expect`, `panic!`, `unreachable!`, a slice index) on a call-supplied part index or cursor in the validator or the executor (per security-plan §Input Validation, Driver command schema row).

## Contract bindings
- security ↔ obs: the eight-field `command` span and the `tool_call` span's two fields. Their stderr captures (`stand_act_spans`, `host_log`, `mcp_log`) are the witness that no id, name or part text reaches a log.
- security ↔ tests: the cold-agent pipe's `valid_step` admits `tool` as one of the twelve verbs. The committed `tests/blitz-tests/checks/counter-{cli,mcp}.json` replay (`stand_replay`) must stay unchanged if `snapshot`'s answer inside the budget is unchanged. A new verb moves both the verb count and the cold-agent validator.
- security ↔ arch: a new verb, argument or result field lands in `VERBS`, `describe()` and the MCP listing, which is fixed `'static` table text inside the ratified carriers. Which shape it takes is the founder's fork (inputs#I1), its most conservative option named.

## Acceptance criteria contributions
- A walk call with an out-of-bound, wrong-kind or unknown part argument is refused by `validate` with nothing run and the snapshot unchanged. Its refusal JSON on the command line, socket and MCP holds no value the call supplied (per security-plan §Input Validation, Driver command schema row; per security-plan §Error Handling, Error format).
- On an over-budget fixture holding a password input with a typed value, every part's text reads `MASKED_VALUE`, and a sentinel typed into it appears in no part, no kept check and no stderr capture (per security-plan §Input Validation, password and file `input` value row).
- Each part's answer on the fixture is under 1,048,576 bytes on the socket and over MCP: no `oversize` and no `AnswerTooLarge` (per security-plan §API Security, Local session socket row).
- A stderr capture at `RUST_LOG=trace` over a full walk shows `command` spans holding only their eight fixed fields, with 0 id needles, 0 name needles and no part text (per security-plan §Logging & Monitoring, escher's own sink).
