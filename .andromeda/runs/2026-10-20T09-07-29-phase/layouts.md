## Constraints
- The headless stand mounts one lean task in TaskShell through `task_in_shell` (`main#main > #task-shell`, `#task-header > #back-btn + #task-title` above `#task-body`), and every driver consumer of that mount (the host role, the `mcp` role) adds no markup, id, class, style, wrapper or order, so a held instance reads as a fresh boot. A paged screen read must keep that true. Whether the code already keeps it once a part-wise read exists is research's question (per layout-templates §Surface: desktop-native → Primary screens).
- layout-templates §Surface: desktop-native → Primary screens says the Cells task carries author ids `cell-{A..Z}{0..25}` on its 676 data cells and `cell-input` on its edit input. That makes it the stand's large-screen case. The stand stays as built, so an over-budget screen for this chunk is a fixture page and moves none of those ids (per layout-templates §Surface: desktop-native → Primary screens).
- The harness viewport defaults to 800 × 600 at scale 1 in light mode. A fixture whose screen passes the budget is laid out in that viewport unless the plan says otherwise (per layout-templates §Surface: desktop-native → IA notes).
- A screen can hold scrolling boxes inside the viewport. `visible_region` reads the part of the viewport an element can be seen through, and the pinned viewport itself is scrolled only on an in-file fixture taller than it. If the screen is cut by region, a part's edge has to account for nodes inside a scrolling box and nodes below the viewport. Whether the snapshot already lists nodes outside the visible region is research's question (per layout-templates §Surface: desktop-native → IA notes).
- Every `escher-session` command answers one uncoloured line of JSON on stdout and ends in one of four ways (accepted 0 · refused 1 · usage 2 · session error 3). No ending writes back anything the caller typed. The usage line is built from the verb table, and `help` answers the fixed self-description. A part-wise read on the command line keeps all of this (per layout-templates §Surface: cli → Primary screens).
- The `mcp` role lists the verb table's verbs as tools in table order, with `lint` after `screenshot` and `help` last. Each tool's description is the verb's help followed by `. Returns: ` and its result fields. The command line's usage line and `help` read the same with and without `--record`. Any new verb, argument or result field for the walk lands in each of these listings (per layout-templates §Surface: cli → Primary screens).

## Patterns to follow
- The precedent for adding a driver verb is `lint` (since 2026-10-19-visual-lint). It took its place in the verb table, its flags were spelt as the schema spells them, it answered one JSON line on stdout and as one MCP text block, and it was kept under `--record` like every instance verb (per layout-templates §Surface: cli → Primary screens).
- A screen that needs more room than the stand gives was built as an in-file fixture. One example is the fixture taller than the viewport that `scroll` is proven on, with no stand markup, id, class or style moved (per layout-templates §Surface: desktop-native → IA notes).
- The Cells grid uses one author id per element, generated by a fixed scheme (`cell-{A..Z}{0..25}` through `col_label(c)`). A large fixture can follow that pattern so every node in a part carries a stable id an agent can address (per layout-templates §Surface: desktop-native → Primary screens).

## Anti-patterns to avoid
- Do not add or move stand markup, ids, classes, styles, wrappers or order to produce an over-budget screen, and do not mount Cells into the lean `stand` boot for this purpose (per layout-templates §Surface: desktop-native → Primary screens).
- Do not let a part-wise answer write more than one line or coloured output on stdout, or write back anything the caller typed (an id, a cursor or offset value, a path) in a usage line, refusal or session error (per layout-templates §Surface: cli → Primary screens).
