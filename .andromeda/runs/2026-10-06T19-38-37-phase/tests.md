Whether the code at HEAD still reads those pins as written is research's question.

The a11y leg runs three named files, none a stand check (per test-plan §9 Pipeline facts → Legs), so re-spelled ids on accessibility nodes are gated by the fast `test` leg only.

## Patterns to follow
- The `element_id` unit-test shape: a `DioxusDocument` built from a plain `fn() -> Element` app, re-rendered by a signal flip inside the runtime, a detached node staled through the mutator; the snapshot unit tests add a resolve before reading (per test-plan §3 Crate-local test helpers → dioxus-native-dom). The edited-variant comparison at unit level fits this shape — two apps, ids of the elements left in place compared.
- The stand-check shape: boot a lean task in TaskShell with `stand::options(incremental)`, drive one interaction through the harness input helpers (each pumps after dispatch), read through the inspection helpers (per test-plan §3 blitz-test-harness → Construction · → Input helpers · → Inspection helpers).
- The fresh-process proof shape: the test binary re-executing its own `#[ignore]` child (per test-plan §1 Coverage scope → tests/blitz-tests) — the re-pinned persistence check keeps this leg and its ignored test.
- Test data is inline (literals and in-code builders), with the pinned stand options as the one shared builder (per test-plan §7 Seed strategies · §7 Builders and options); the plan records no fixture file or loader convention for the stand, so the edit-proof fixture's form is P4's to settle.
- Time in a timer-task boot is the `TimerTicks` stand-in every headless-stand boot provides in context (per test-plan §8 Hand-written fakes and stubs → Time (seven_guis timer)) — a timer variant booted outside the stand's boot must supply the same.

## Anti-patterns to avoid
Test-plan §11 reads `NO RECORDED INTENT`; nothing is cited from it. The bans below are read from measured sections.
- A runtime skip or a font-availability early return in a stand check — the stand checks have no skip path (per test-plan §2 Test levels observed → Font-dependent tests · §8 Real dependencies kept).
- Counting a run with no parsed test line as a pass, or a stand file the `stand` selection cannot see (per test-plan §3 Agent-run contract → `run {selection}`).
- A third-party test framework (snapshot, property or mock library) for the id pins — none is in use and blitz-tests depends on dev-dependencies only (per test-plan §3 Runners and invocation → Third-party test frameworks · §8 Observed absent · §5 Boundaries covered → tests/blitz-tests crate).

## Contract bindings
- tests ↔ architecture: the id grammar is a locked contract (architecture §Standard Contracts → Dioxus DOM bridge) and the checks pin its spelling; the test plan's own text counts and describes those checks (test-plan §1 Coverage scope → dioxus-native-dom · → tests/blitz-tests; §3 Crate-local test helpers → dioxus-native-dom), so the wrap's drift pass re-reads them after the re-pin.
- tests ↔ a11y: the id rides every accessibility node as `author_id` and is asserted by a stand check outside the a11y CI leg (test-plan §1 Coverage scope → tests/blitz-tests; §9 Pipeline facts → Legs). Rule 2's "focusable or role-bearing" reader is a11y surface; the check's wiring into the 5-command discipline is the `stand_` prefix (test-plan §3 Agent-run contract → `run {selection}`).
- tests ↔ obs: agent-run events are harness metadata, not a telemetry sink, and nothing between a `failures:` line and the next `test result:` reaches an event (test-plan §3 Agent-run contract → Events). The actionable-element check's failure text — the element and the remedy — is therefore readable in `run.log` and in the cargo output, never in `events.jsonl`; an agent reading only events sees `failed` for the test and nothing more.
- tests ↔ security: no new dependency is expected; a new dev-dependency would fall under the audit leg in the same workflow (test-plan §9 Pipeline facts → Legs).
