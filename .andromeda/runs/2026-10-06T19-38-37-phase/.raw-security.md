## Constraints
- **One author-key predicate, reused by the anchor.** security-plan §Input Validation → Markup attributes · `id` (stable element id) requires an HTML `id` to count as an author key only when it is non-empty, free of `/` and the first claim in document pre-order; every other value gives no key. Rule 1's "nearest keyed ancestor" must be decided by that same predicate, so a rejected `id` (empty, `/`-bearing, later duplicate) never anchors a path. Whether the code already exposes that predicate as one reusable reader is research's question.
- **No `id` value may make two ids equal.** The same row requires that no author-supplied `id` can produce a collision, which today rests on keys never holding `/` and paths always holding it. The anchored spelling changes that separation, so the plan must show the new grammar keeps author keys, anchored paths, component paths and document paths mutually distinct — including an author key spelled like a component name, and one keyed container shared by two tasks. Whether the chosen spelling holds this is a P3/P4 question, not a settled fact.
- **No panic, `None` for what does not resolve.** The row requires a non-element, stale or detached node to read `None` and no id path to panic, with tree ids resolved through `BaseDocument::get_node` and never by indexing the slab. This binds the new ancestor walk (rule 1) and the actionable-element check (rule 2) alike (also security-plan §Error Handling → Graceful degradation).
- **Ids hold nothing process-local.** The row requires the id to carry no `NodeId`, `ElementId`, `ScopeId` or pointer, and a keyed segment to carry a model-assigned key — never a list index, pointer, hash, clock or process-local value. Author keys added to stand tasks under rule 2 (CRUD rows the likely case) must be derived the same way and must themselves pass the author-key predicate; a per-row `id` that duplicates another is silently demoted to a path by the first-claim rule, which the rule-2 check is then required to catch.
- **No new exit for the id.** The row requires the id to be computed on demand, written to no log, DOM or vdom, and to leave the process only through the platform accessibility adapter as AccessKit `author_id` (ratified crossing), never on a `TextRun`, the document root or the synthetic `Window` node; the snapshot is an in-process reader that adds no crossing. The re-spelled ids ride that one crossing unchanged; the check and the edit-proof fixture must add no wire form, file, socket, event or driver command (also security-plan §API Security — no served surface exists).
- **The check's failure text names structure, not content.** security-plan §Logging & Monitoring → Log format and backends requires engine telemetry behind each crate's `tracing` feature and records that escher's sink redacts content-named fields while the chained panic hook and raw libtest output stay unscrubbed. The rule-2 failure message therefore names the element by id / tag / role and the remedy, never by text content, attribute value or input value, and the check adds no log emission of its own.
- **No new dependency, env read or lockfile change expected.** security-plan §Dependency Security → Pinning / CI integration requires `--locked` builds, a committed `Cargo.lock` and the cargo-deny audit leg on every push; §Secret Management → Environment values read lists the only env reads source may make. If P3/P4 finds the chunk needs a crate or an env read, that is a registration and a security-plan amendment first, not a silent add.

## Patterns to follow
- The author-key acceptance rule as the single gate for anything that treats an `id` as identity (security-plan §Input Validation → Markup attributes · `id` (stable element id)).
- The snapshot's reader shape for the new check: takes no external argument, resolves each tree id through `get_node`, omits a node that does not resolve, returns data instead of logging (same row).
- `Option` / typed results on lookups that may miss, as `try_element_to_node_id` and `try_doc` do (security-plan §Error Handling → Graceful degradation).
- Any diagnostic emission compiled only under the crate's `tracing` feature, with no content-named field (security-plan §Logging & Monitoring → Log format and backends).

## Anti-patterns to avoid
Drawn from the sections below; §Security Anti-Patterns holds no recorded intent.
- Indexing the slab with a tree id or a possibly stale `NodeId`, or using the unwrapping `element_to_node_id`, in the ancestor walk or the check (security-plan §Input Validation → Markup attributes · `id` (stable element id); §Error Handling → Panic paths → Dioxus nodes).
- Putting a list index, pointer, hash, clock, `NodeId`, `ElementId` or `ScopeId` into an id or into a new author key (security-plan §Input Validation → Markup attributes · `id` (stable element id)).
- Writing an id into the DOM, the vdom, a log, an event or a file, or giving the check or fixture a wire form (same row; security-plan §API Security).

## Contract bindings
- **security ↔ architecture.** security-plan §Input Validation → Markup attributes · `id` (stable element id) restates the id grammar and cites `element_id.rs`, `snapshot.rs` and the stand checks by line; the grammar amendment in architecture §Standard Contracts → Dioxus DOM bridge makes that row stale, so it is part of the wrap's cascade.
- **security ↔ a11y.** The id's only exit is AccessKit `author_id` through the platform accessibility adapter (same row); re-spelled ids reach assistive technology through the a11y plan's tree, and the nodes that must never carry one are the same set on both sides.
- **security ↔ tests.** The row's guarantees are evidenced by `stand_element_ids.rs`, `stand_id_persistence.rs` and `stand_snapshot.rs`; the re-pin must keep those properties asserted (uniqueness, `None` on stale, same id across re-render / remount / second process), not only move the expected strings.
- **security ↔ obs.** The rule-2 failure text and any diagnostic sit under the scrub and feature-gating rules of security-plan §Logging & Monitoring → Log format and backends.

## Acceptance criteria contributions
- (security) On every stand task and the edit-proof fixture, in both layout modes, no two elements read the same id, and an element whose `id` is empty, `/`-bearing or a later duplicate neither reads as an author key nor anchors a descendant's path (per security-plan §Input Validation → Markup attributes · `id` (stable element id)).
- (security) A non-element, stale or detached node reads `None` from the id reader and is skipped by the actionable-element check, with no panic, after the grammar change (per security-plan §Input Validation → Markup attributes · `id` (stable element id); §Error Handling → Graceful degradation).
- (security) No id produced by the new grammar or by an added author key contains a `NodeId`, `ElementId`, `ScopeId`, pointer, list index, hash or clock value, and each still reads the same across a re-render, a remount and a second process (per security-plan §Input Validation → Markup attributes · `id` (stable element id)).
- (security) The chunk's diff adds no dependency, env read, listener, file or log write of an id: `Cargo.lock` is unchanged, or `bash .github/scripts/ci-leg.sh audit` passes if it is not (per security-plan §Dependency Security → CI integration; §Secret Management → Environment values read; §API Security).
