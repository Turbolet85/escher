## Relevance
relevant — the chunk changes a locked Standard Contract (the stable-element-id grammar, architecture §Standard Contracts → Dioxus DOM bridge) inside one existing crate and re-pins the stand checks that contract names as its evidence.

## Constraints
- **The id grammar is a locked contract, and this chunk departs from it on a recorded ratification.** architecture §Standard Contracts → Dioxus DOM bridge fixes the three-tier order (author key → component path → document path) and every segment spelling. Rule 1 (anchor at the nearest keyed ancestor) is not in that contract; the founder's answer (scope, inputs#I1) is the ratification and the section's amendment is the wrap's. The chunk therefore owes the wrap an exact statement of the new grammar — tier order, anchored-path spelling, how a component boundary composes with the anchor — in the form that section uses. Whether the section's present wording matches `element_id.rs` at HEAD is research's question.
- **The contract's invariants on an id must hold under the new grammar** (architecture §Standard Contracts → Dioxus DOM bridge): computed on demand and written to neither the DOM nor the vdom; no `NodeId`, `ElementId`, `ScopeId` or pointer in it; `element_ids()` pairwise distinct over every element reachable from the document root, in document pre-order; `element_id` answering `None` — never a panic — for a non-element, stale or detached node (the stale-id rule also at architecture §Design Philosophy → One incremental pipeline, safe identities). An anchored-path spelling must not be able to equal an author key or a component/document path; the contract requires author keys to be `/`-free, which is the separator the scope's distinctness question turns on.
- **Persistence is part of the same contract** (architecture §Standard Contracts → Dioxus DOM bridge): the same id across a re-render, a remount and a second process, on each lean task, in both layout modes. The rule change must not make an id depend on anything that differs between those runs.
- **What counts as an author key is already defined** (architecture §Standard Contracts → Dioxus DOM bridge): the HTML `id`, non-empty, `/`-free, and the first claimant in document pre-order — a later claimant falls back to a path. Author keys added to the stand for rule 2 must satisfy all three, or the rule-2 check would flag the very element that was keyed. The same section records the document skeleton `DioxusDocument::new` builds outside the VirtualDom, one element of which reads an author key; whether that makes every vdom-rendered stand element "under a keyed ancestor" (so the no-keyed-ancestor case is nearly empty on the stand) is research's question, and it bears directly on the scope's component-boundary collision concern.
- **A Dioxus `key:` and an author key are separate mechanisms** (architecture §Standard Contracts → Dioxus DOM bridge): the contract requires the CRUD row's `key:` to sit on the `for` item itself so the list diffs by key, and records that a `key:` placed deeper does not key the list. Giving rows an HTML `id` must leave that `key:` placement intact.
- **Workspace placement and crate boundary.** The derivation lives in `dioxus-native-dom`'s crate-private `element_id` module behind `DioxusDocument::element_id` / `element_ids` (architecture §Existing Scopes → dioxus-native-dom). blitz-dom owns the base accessibility tree and `DioxusDocument` only overrides it (architecture §Standard Contracts → Document core); the scope's "no engine change" boundary matches that split. A new public method on `DioxusDocument` for the actionable-element check is an addition to the Dioxus DOM bridge contract — it re-exports through dioxus-native (same section) and lands in a published library crate (architecture §Inherited Defaults → Publishability) — so it is recorded at wrap, not a silent add.
- **Feature gating decides where the check can live.** `element_id(s)` is ungated; the `accessibility_tree` override and the `snapshot` module compile only under `accessibility`, and a crate taking the Dioxus crates at the workspace pin gets them only by naming the feature — blitz-tests names it on dioxus-native-dom, seven_guis names none (architecture §Standard Contracts → Dioxus DOM bridge; §Cross-cutting Patterns → Config management; §Established Decisions → [Default features]). A check that reads an AccessKit role must be `accessibility`-gated; one placed inside seven_guis would need a manifest feature change, one in blitz-tests would not.
- **No new resource.** No listener, port, env var, crate, binary or dependency (architecture §Occupied Resources → Network ports and listeners / Environment variables / Names; §Conventions → Manifests). The edit-proof fixture belongs in an existing crate — the registry and the directory tree hold no slot for a new one (architecture §Infrastructure Patterns → Directory structure).

## Patterns to follow
- **Boot through the stand contract** — pinned viewport, bundled font, offline, a fresh VirtualDom per boot, via `stand::boot` and `stand::options(incremental)` (architecture §Standard Contracts → Headless stand). A fixture "booted the same way as the task" either extends that surface (`LeanTask`, `app::Task`, `task_in_shell` — a contract addition recorded at wrap; `TaskShell` is required to stay private) or goes through the harness's component/vdom constructors with the stand's options (architecture §Standard Contracts → Test harness). Note for P4: a component-path segment is derived from the component's type name (architecture §Standard Contracts → Dioxus DOM bridge), so an edited variant rendered by a differently named component changes path segments by itself — the fixture's form must not confound that with the edit under test.
- **Test shape** (architecture §Conventions → Tests): unit tests in `#[cfg(test)] mod tests` at the end of the source file; one integration file per behaviour in `tests/blitz-tests/tests/`, opening with a `//!` doc naming the behaviour; every scenario `for incremental in [false, true]`; a test first asserts its fixture produces the condition under test — the shape the "may still change" measured negatives need.
- **Reuse existing readers; add no parallel one.** The snapshot contract requires every field to come from a reader the engine already has, and `SnapshotNode.id` to be the `author_id` verbatim with lookup by id (architecture §Standard Contracts → Dioxus DOM bridge). The "focusable or role-bearing" reader for rule 2 should be composed the same way; the snapshot then inherits the new grammar with no change of its own.
- **Visibility, docs and results** — crate internals `pub(crate)`, modules open with `//!`, public items carry `///` (architecture §Conventions → Visibility and naming / Documentation), and rustdoc warnings are errors over every workspace library crate (architecture §Conventions → Formatting and lints). An offender-listing API returns typed data rather than panicking (architecture §Cross-cutting Patterns → Error handling).

## Anti-patterns to avoid
- Writing an id (or an anchor marker) into the DOM or the vdom, or letting a `NodeId`, `ElementId`, `ScopeId` or pointer into one, to make anchoring cheaper (banned by architecture §Standard Contracts → Dioxus DOM bridge).
- Reaching into blitz-dom for the actionable reader or the anchor walk — the id is a Dioxus-bridge concern and the engine stays driven from outside (architecture §Design Philosophy → Radically modular, embeddable engine; §Standard Contracts → Document core). If research finds the reader needs an engine change, that is the scope's founder question, not a quiet edit.
- Compiling role- or snapshot-dependent code outside the `accessibility` gate, or gating `element_id(s)` behind it (architecture §Cross-cutting Patterns → Config management; §Conventions → Feature gating).

The stand and harness surfaces the fixture uses are architecture §Standard Contracts → Headless stand / Test harness.
