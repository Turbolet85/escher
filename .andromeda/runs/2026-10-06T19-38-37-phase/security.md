# security extract

## Relevance
partial — the chunk re-spells the stable element id, whose derivation from the markup `id` attribute and whose single exit from the process are both specified in security-plan §Input Validation; it touches no auth, served API, secret or network surface.

## Constraints
- security-plan §Input Validation (row "Markup attributes · `id` (stable element id)") requires that no `id` value can make two elements' ids equal; the anchored grammar of rule 1 must keep that property, so an anchored path has to stay distinct from every author key, every component path and every document path, whatever the author writes in the key (a key spelled like a component name or a path segment included). Whether the grammar chosen at P4 keeps it is research's question, not a settled fact.
- security-plan §Input Validation (same `id` row, restated here in full) requires an author key to be read only from an `id` that is non-empty, free of `/` and the first claim in document pre-order; an ancestor may anchor a descendant's path only when it passes those same three tests, so an empty, `/`-bearing or later-duplicate `id` anchors nothing.
- security-plan §Input Validation (the `id` row's stale-node clause) requires a non-element, stale or detached node to read `None` and no id path to panic; the new nearest-keyed-ancestor walk and the rule 2 check must resolve every node through a fallible lookup, never by indexing with a tree id. Whether the ancestor walk already does so is research's question.
- security-plan §Input Validation (the `id` row's exit clause) requires the id to be computed on demand, written to no log, DOM or vdom, and to leave the process only through the platform accessibility adapter as AccessKit `author_id`; the re-spelled ids ride that one registered crossing, and the rule 2 check must add no wire form, file, socket, event or driver command.
- security-plan §Input Validation (the `id` row's content clause) requires an id to carry no `NodeId`, `ElementId`, `ScopeId` or pointer, and a keyed segment to come from a model-assigned value — never a list index, pointer, hash, clock or process-local value; every author key the stand tasks gain under rule 2 must be a literal or a model-assigned identifier, and never text a user typed (a CRUD person's name, a field's value).
- security-plan §Logging & Monitoring requires engine telemetry to stay behind each crate's `tracing` feature and names the content fields escher's sink redacts (`text`, `value`, `attrs`, `html`, `path`, `error` among them); the chunk adds no log or `tracing` call site that carries an element id, an accessible name or attribute content, and the check's failure text reaches libtest output only.
- security-plan §Dependency Security requires `--locked` builds, a committed lockfile and the cargo-deny audit leg on every push; the scope expects no new crate, so `Cargo.lock` is expected unchanged, and a dependency that P4 finds it needs is reviewed by hand and audited before it lands.

## Patterns to follow
- One place computes ids and every reader copies the result verbatim: security-plan §Input Validation describes `DioxusDocument::snapshot` as an in-process reader that copies the id unchanged and adds no crossing. An offender-listing API for rule 2, if P4 chooses one, follows the same shape — no argument that selects by untrusted input, no side effect, no output channel of its own.
- Fall back, never fail: security-plan §Input Validation gives an unusable `id` no key and lets the element read its path instead. The anchored grammar keeps that fallback order (author key, else anchored path, else component path, else document path) with no error path and no panic.
- Skip what does not resolve: security-plan §Error Handling (Graceful degradation) records stale node ids resolving to `None` through `get` and being skipped. The edit-proof fixture's remount and before/after comparison rely on that behaviour for dropped pre-edit nodes.
- Checks log metadata, not content: security-plan §Logging & Monitoring records that the agent-run contract's events carry no content-named field and no captured test output or panic text. The new stand check's message naming an element and its remedy stays in the raw run log, which that section records as unscrubbed and gitignored; whether any evidence file committed by this chunk carries such text is P5's to check.

## Anti-patterns to avoid
The plan's own anti-pattern section records no intent; these bans are read from the sections cited.
- Deriving a new author key from user-entered or process-local data (a typed name, a list index, a pointer, a hash, a clock) — security-plan §Input Validation bars each of these from an id, and the id reaches the platform accessibility adapter.
- Making the id legible to another channel to serve the check — writing it into the DOM or vdom, emitting it in a log or event, or serializing the offender list — security-plan §Input Validation keeps the platform adapter as the id's only exit until a later, separately registered entry.
- Indexing the node slab with an id taken from the accessibility tree or from a pre-edit document — security-plan §Error Handling (Panic paths) lists the unwrap-on-missing-node paths this crate already has; the chunk adds none.

## Contract bindings
- security ↔ architecture: the id grammar is locked in architecture §Standard Contracts → Dioxus DOM bridge and restated in security-plan §Input Validation (the `id` row, with line ranges into `element_id.rs` and the stand checks). Rule 1 makes that row's grammar text and its line anchors stale; the wrap's amendment has to cover the security plan in the same cascade as the architecture.
- security ↔ a11y: the re-spelled id is the AccessKit `author_id` on every element node (security-plan §Input Validation), so the a11y plan's identity leg and the security plan's exit clause describe one crossing and must be re-read together after the re-pin.
- security ↔ tests: `stand_element_ids.rs`, `stand_id_persistence.rs` and `stand_snapshot.rs` are the evidence security-plan §Input Validation cites for the uniqueness, no-panic and same-across-processes claims; the re-pin keeps those three claims asserted, not only the new spellings. The edit-proof fixture carries no real personal data and no credential (security-plan §Secret Management, "Never in code").
- security ↔ observability: the redacted-field set in security-plan §Logging & Monitoring is the obs plan's scrub set; a new field name on any new event would be an amendment to both, and the chunk is expected to add none.

## Acceptance criteria contributions
- A check proves that, under the anchored grammar, no author `id` can make two elements read the same id: an empty key, a `/`-bearing key, a later-duplicate key and a key spelled like a component name or a positional segment each leave every id on the screen distinct, in both layout modes (per security-plan §Input Validation)
- `element_id` / `element_ids` and the rule 2 check read `None` or skip, with no panic, for a non-element node, a detached node and a node id dropped by the fixture's edit or remount (per security-plan §Error Handling)
- A census of the chunk's diff over `packages/dioxus-native-dom/src/` and `examples/seven_guis/src/` finds no new `tracing`, `log`, `println!` or `eprintln!` call site carrying an element id, an accessible name or attribute content, and no new file, socket or env read (per security-plan §Logging & Monitoring)
- `bash .github/scripts/ci-leg.sh audit` passes and the chunk's diff leaves `Cargo.lock` and every manifest's dependency tables unchanged, or names each change with its hand review (per security-plan §Dependency Security)
