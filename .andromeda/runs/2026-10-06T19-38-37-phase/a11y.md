# a11y extract

## Relevance
partial — the chunk adds no UI surface, but it re-spells the ids that ride every accessibility node, defines "actionable" from the a11y readers (focusability, AccessKit role), and adds HTML `id` attributes to stand controls whose names and focus order the plan pins.

## Constraints
- The a11y tier is 0 — SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary). The chunk's edits to the stand tasks (author keys added) must leave keyboard operability, focus order and painted colours as they are; the plan requires each lean task's forward focus sequence and the single-focused-node reading to hold (per a11y-plan §5 Focus order per layout · §8 Error recovery). Whether a new `id` attribute matches any existing stand selector and so changes a painted colour is research's question.
- a11y-plan §7 Accessibility tree output requires that in a Dioxus document every element node carries its stable element id as AccessKit `author_id` and that no `TextRun`, document-root or `Window` node carries one; a11y-plan §2 Accessibility tree lifecycle requires the wrapper's `Document::accessibility_tree` override to be the path that reaches the platform tree. The anchored paths and new author keys must arrive on the nodes through that same carriage. Whether the override already takes its value from the one computation in `element_id.rs`, so the grammar change flows through with no second edit, is research's question.
- a11y-plan §7 Accessibility tree output requires a `<label>` to name its `<input>` through the `for`-target id (else its first nested input), and requires the stand's inputs to keep a non-empty accessible name. An author key IS the HTML `id`, so an `id` added, renamed or claimed earlier by another element under rule 2 must not break or redirect a `for` binding. Whether rule 2 forces any existing stand `id` to be renamed, and whether any new key duplicates a `for` target, is research's question.
- a11y-plan §2 Role derivation and §4 Per-component pattern catalog define the one role mapping (the `role` attribute, else the HTML element mapping, else unknown). Rule 2's "role-bearing" leg must be defined over the roles that mapping yields. Under it a click-handling `div` reads a generic role, and under a11y-plan §5 Focus order per layout it is not focusable without a `tabindex` — so an element an agent acts on by pointer can read as neither. Whether CRUD's person rows are such elements, and so fall outside the chosen reader, is research's question; it bears on SC 2.1.1 (per a11y-plan §1) and returns to the founder if the answer needs a focusability change.
- a11y-plan §5 Focus order per layout makes focusability a function of runtime state (`disabled` removes it; disabled-ness is keyed two ways), and a11y-plan §4 Hidden content excludes `hidden`, `display: none` and `visibility: hidden` nodes from the tree. The check's verdict on an element must not change with that state: a control that is disabled or hidden at the moment the check reads must still be held to the keyed requirement. Whether the chosen entry point (accessibility tree, snapshot or DOM walk) sees such elements is research's question.
- a11y-plan §1 A11y Scope Summary (Dioxus crates · blitz-tests) and §2 Feature exposure require the `accessibility_tree` override and the snapshot to sit behind dioxus-native-dom's `accessibility` feature, which a crate gets only by naming it. A check leg that reads the AccessKit role must live behind that feature, and the id an element reads must be the same with the feature on or off.

## Patterns to follow
- Accessibility assertions are Rust tests in blitz-tests over the AccessKit tree, built after resolve and matched node by node (per a11y-plan §3 A11y testing tool pick); a tree node maps back to its DOM element through the integer node id (per a11y-plan §3 A11y testing tool pick · §1 blitz-traits node ids) — the route by which a failing check can name the element.
- Stand accessibility checks run in both layout modes and assert id, role and name together per control (per a11y-plan §7 Accessibility tree output).
- Focus order is asserted by walking `focus_next_node` and reading the harness's focused-node query (per a11y-plan §3 Focus management test harness · §8 Error recovery).
- A stand input takes its name from a `<label for>` or an `aria-label` (per a11y-plan §7 Accessibility tree output); a control that gains an author key keeps the naming route it has.

## Anti-patterns to avoid
a11y-plan §11 A11y Anti-Patterns holds no recorded intent — nothing is cited from it. The items below follow from measured sections.
- A second role or name mapping built for the actionable reader — the plan requires consumers to take role and name from the tree `accessibility_tree` returns (per a11y-plan §7 Accessibility tree output · §2 Role derivation).
- Adding `tabindex` or altering `disabled` handling on a stand element only to make it satisfy or escape the check — it changes the Tab order the plan pins (per a11y-plan §5 Focus order per layout · §8 Error recovery).
- Treating the CI `a11y` leg as the gate for the new check — that leg runs three named engine test files and no stand assertion (per a11y-plan §9 CI Integration).

## Contract bindings
- architecture §Standard Contracts → Dioxus DOM bridge (the id grammar) ↔ a11y-plan §7 Accessibility tree output: the grammar change re-spells every `author_id`; the two must be amended together at wrap.
- tests (test-plan §3) ↔ a11y-plan §3 / §7 / §8: `stand_accessibility_ids.rs` and `stand_snapshot.rs` pin ids alongside role, name and focus order — a re-pin moves the id strings only, never the role, name or sequence expectations.
- CI (tests §9) ↔ a11y-plan §9 CI Integration: the new stand check runs in the workspace test leg; whether it also joins the `a11y` leg is a plan question, not settled by the a11y plan.
- layouts §Focus management ↔ a11y-plan §5 Focus order per layout: the per-task tab sequence is unchanged by this chunk.
- obs: the a11y plan defines no violation schema (a11y-plan §3's closing block is marked not measured) — the wording of the check's failure (element + remedy) has no a11y-plan authority and is tests' to set.

## Acceptance criteria contributions
- (a11y) After the grammar change and the new author keys, every element node of each lean stand task's accessibility tree carries an `author_id` equal to that element's id, and no `TextRun`, document-root or `Window` node carries one, in both layout modes (per a11y-plan §7 Accessibility tree output).
- (a11y) Every stand interactive control reads the same role and the same non-empty accessible name as before the chunk — each `<label for>` still resolves to its input — in both layout modes (per a11y-plan §7 Accessibility tree output · §2 Role derivation).
- (a11y) Each lean task's forward focus sequence through `focus_next_node` has the same members in the same order as before the chunk, and after one focus move exactly one node reads focused (per a11y-plan §5 Focus order per layout · §8 Error recovery).
- (a11y) The actionable-element check holds a control to the keyed requirement whatever its state: the flight booker's Book button reads an author key both enabled and disabled (per a11y-plan §5 Focus order per layout · §8 Error recovery).
