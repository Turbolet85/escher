# obs extract

## Relevance
partial — the merge adds no escher instrumentation, but it rewrites engine files that carry feature-gated log sites (`mutation_writer.rs`, `document.rs`, `mutator.rs`, `window.rs`, `render.rs`) and it changes `Cargo.toml` and the workspace version. The sink's guarantees and the span shapes must survive the merge, and the feature wiring they rest on must be measured again.

## Constraints
- obs-plan §2 Telemetry Strategy requires every engine `tracing` call site to compile only under the crate's `tracing` feature, with a no-op path when the feature is off. That covers any log site upstream's 16 commits add or move, for example in `mutation_writer.rs`, `dioxus_document.rs`, `window.rs` or `render.rs`. Whether upstream's new hunks hold an ungated `tracing`/`log` call or a `println!` is research's question.
- obs-plan §2 Feature wiring states the measured fact that a workspace-wide build turns `blitz-dom/tracing` on and a `-p seven_guis` or `-p blitz-tests` build leaves it off. That fact was read from cargo's resolved feature graph. The merge changes the root `Cargo.toml`: the taffy git rev becomes registry `0.15`, the nine `=` pins move to beta.3, and `blitz-tests` gains `cursor-icon`. Whether the merged graph still unifies features the same way is research's question, and P3 must read it again rather than assume it.
- obs-plan §8 Scrubbing requires the sink's allowlist to stay as it is: two prefix sets (`ENGINE_TARGET_PREFIXES`, `ESCHER_TARGET_PREFIXES`) and five scrub sets. An engine target prints only its safe fields, and a record from any other target is dropped whole at every level. §8 Scrubbing also records that no engine call site is edited. The merge must change nothing in `packages/escher-telemetry` and must not reach scrubbing through an engine call site.
- obs-plan §8 Values logged as-is records engine log sites that carry content as-is. One example is the dioxus-native-dom mutation `trace!` sites, which log text-node contents and attribute values. Their safety under escher's sink rests on the `dioxus_native` engine-prefix scrub. Whatever the `mutation_writer.rs` conflict resolution keeps (upstream's `is_bool_attr` path or our constant), its log sites must stay under an allowlisted engine target so the content scrub still applies.
- obs-plan §4 Span / Trace Coverage fixes the `command` span at eight fields of closed words and counts, and the `tool_call` span at two (`tool`, `ending`). Neither may hold an id, a name, typed text or a shot's image, size or dimensions. The merge must leave `packages/escher-driver` free of any new field. Upstream does not touch escher's crates, and research should confirm that.
- obs-plan §3 Observability Harness Contract (Service identity and line format) reads `service.version` from each binary's own `CARGO_PKG_VERSION`. A workspace version bump from 0.3.0-beta.2 to 0.3.0-beta.3 can change that string on any crate that inherits the workspace version. §6 Log format quotes a captured line with `service.version=0.3.0-beta.2`. Whether any check or committed reading asserts the old version string is research's question.
- obs-plan §3 Observability Harness Contract (Logging stack) fixes the install sites: `escher_telemetry::init` is installed in `seven_guis_native` and `escher-session` only, and nowhere else. The headless stand, its checks and their shared modules install no subscriber, except the named children and recorders. Upstream's five new test files, each now its own target, must install no subscriber and read no env var. Whether they do is research's question.

## Patterns to follow
- Prove the sink holds by the needle method in obs-plan §8 Values logged as-is. Run `host_log` and `mcp_log` again after the merge at `RUST_LOG=trace` under both builds (`-p seven_guis` and `--workspace`). The method counts id needles, name needles, typed-sentinel occurrences and occurrences of a shot's first 64 base64 characters. Do not take it on trust from a clean textual merge.
- Read the feature wiring from cargo's resolved feature graph, as obs-plan §2 Feature wiring did. Re-measure the line count by level on a sink-installing host built each way, and record a moved count as re-measured, never assumed.
- Prove span shape with the in-process recorder (`stand_mcp_tools`) and the re-run sink children (`stand_act_spans`), per obs-plan §3 Observability Harness Contract (Logging stack) and §4 Span / Trace Coverage. Each reads its capture into assertions only and never prints a captured line.
- Prove the formatter's last-word drop with `telemetry_drop`, per obs-plan §6 Log Coverage (Log format, escher's sink). A `RUST_LOG` directive that names a non-allowlisted target still prints nothing.

## Anti-patterns to avoid
- Editing an engine call site, inherited or upstream-new, to scrub or silence it. Scrubbing lives in the sink's allowlist, not at call sites (obs-plan §8 Scrubbing).
- Adding a field to `command` or `tool_call`, or an event to escher-driver, while resolving a merge-touched path. The fields are fixed, and a shot's image, size or dimensions, any argument, and any `Outcome`/`Command` `Debug` are never fielded (obs-plan §4 Span / Trace Coverage).
- Letting a check that reads a sink-installing binary print what it captured on failure. Captured streams go into assertions only, and a failure reports a kind and a count (obs-plan §3 Observability Harness Contract, Logging stack).

## Contract bindings
- obs ↔ tests: the sink's guarantees and span shapes are proven by `host_log`, `mcp_log`, `stand_act_spans`, `stand_mcp_tools` and `telemetry_drop`. These run in the `fast` leg's workspace tests, plus `-p seven_guis` for the two host readings under both builds. The agent-run harness log (`scripts/agent-run.sh` events) is the test contract's metadata, not the sink (obs-plan §3 Observability Harness Contract; test-plan §3).
- obs ↔ security: the target allowlist and content-named scrub set (obs-plan §8 Scrubbing) back the security rule that a sink-installing binary's stderr carries no id, name or typed text at any `RUST_LOG` level. An upstream log site that carries content is covered only through that sink (security-plan §Logging & Monitoring).
- obs ↔ CI: each ci.yml leg writes its merged output to `target/ci-logs/{leg}.log`, uploaded only on failure (obs-plan §9 CI Integration). The merge's fork-CI verdict is read from those legs.
