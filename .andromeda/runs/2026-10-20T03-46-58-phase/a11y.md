# a11y extract

## Relevance
relevant: the chunk adds a driven form control whose role, accessible name, value, focusability and Tab position are all tier-0 a11y surface (SC 2.1.1 · 2.4.3).

## Constraints
- The tier-0 target is SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary). A select is a focusable form control, so SC 2.4.3 (focus order) and SC 2.1.1 (keyboard operability) both apply to it. SC 1.4.3 applies only if the fixture's text gets a contrast row.
- A select's role is engine-mapped: `<select multiple>` maps to `ListBox`, any other `<select>` to `ComboBox` (per a11y-plan §4 ARIA Patterns & Roles, Per-component pattern catalog: Select). The single-choice select in this chunk's scope must read `ComboBox`. The plan records no mapping for `option` or `optgroup`, so what an option maps to (scope cites `ListBoxOption`) and whether options become tree nodes are research's questions.
- Focusability rules (per a11y-plan §5 Keyboard Navigation, Focus order per layout):
  - `select` is in the native focusable set, with no `tabindex` needed.
  - It is not focusable when it carries `disabled`, read by presence on a form control (`ElementData::is_disabled`), or when it is inert.
  - Tab and Shift+Tab walk `focus_next_node` / `focus_prev_node`.
  - "Tab order kept" therefore means the select takes the stop its document position gives it, and every other stop stays where it was.
- The keyboard activation list never names `select` (per a11y-plan §5 Keyboard Navigation, Keyboard handling). Enter goes to `button` · `summary` · `input` submit/reset/button · `a[href]`, and Space to `button` · `summary` · `input` submit/reset/button/checkbox/radio. Whether a focused select takes any key today is research's question.
- Any new default action for select keys or pointer input changes engine behaviour for every document. The range input's arrows · `Home` · `End` and its click/pointerdown arms were each ratified by the founder before they landed (per a11y-plan §5 Keyboard Navigation, Keyboard handling and Focus restoration). An equivalent select model is a founder fork, not an implementation detail.
- What the snapshot reads (per a11y-plan §7 Screen Reader Support, Accessibility tree output):
  - `role` and `name` come from the accessibility tree, with no second mapping.
  - `value` is the editor's text, else a range input's current value (`range_input_value`), else the `value` attribute.
  - `enabled` follows the presence of `disabled`.
  - So whether a select's chosen option reaches `value` (attribute, option `value`, or option text) is research's question for `packages/dioxus-native-dom/src/snapshot.rs`.
- Naming (per a11y-plan §7 Screen Reader Support, Accessibility tree output):
  - A `<label>` names only the bound `input` element, by `for` or by nesting. `aria-label` and `aria-labelledby` name any element.
  - So a select named by `<label for>` may read an empty name. Whether the label loop admits `select` is research's question.
  - Every interactive-role node on the stand must read a non-empty name, and `ComboBox` is in `INTERACTIVE_ROLES`.
- The actionable-key rule: every element an agent can act on reads an author key, and `DioxusDocument::unkeyed_actionable` is the check (per a11y-plan §7 Screen Reader Support, Accessibility tree output). The fixture's select must carry an author key. Whether its options count as actionable, and need keys of their own, is research's question.
- A select's change must reach the engine's changed set, marking it the way a range move does through `apply_range_move`. Otherwise the shell's tree refresh and the driver's diff will not see the chosen option (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle). Note: a harness settle neither reads nor drains that set.

## Patterns to follow
- The range input is the precedent interaction model for a control the engine had no behaviour for (per a11y-plan §5 Keyboard Navigation, Keyboard handling and Test harness pattern):
  - a current value held apart from the attribute;
  - each change fires one `input` event and marks the changed set, and a no-change move fires none;
  - a disabled control takes neither keys nor a click;
  - `range_input_interaction` states key and click tables;
  - `stand_act_range` asserts the role, the name and an unchanged forward focus sequence after a driver step.
- A test-only element on a fixture page, never added to a stand task (per a11y-plan §7 Screen Reader Support, Accessibility tree output). Precedents are the textarea on `stand_snapshot_state`'s in-file fixture and the password input of the shared `fixtures::password_named` in `tests/blitz-tests/tests/fixtures/mod.rs`.
- A focus walk in which, at every Tab and Shift+Tab step, the engine's focus, the snapshot's `focused` node and the tree's focus all agree (per a11y-plan §5 Keyboard Navigation, Test harness pattern). The pattern comes from `stand_keyboard`, whose readers `tab_order` and `focused` live in `tests/blitz-tests/tests/common/mod.rs`. Note that `Harness::focused()` falls back to the root and never reads `None`.
- Assertions read off the built tree as a stated table with its row count asserted, in both layout modes (per a11y-plan §3 A11y Assertion Harness Contract). The role pin is `accessibility_roles`' `assert_role`, which already holds the `ComboBox` / `ListBox` rows.

## Anti-patterns to avoid
- No second role or name mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output). The snapshot, its text form, its diff and the MCP result each stay readers of the tree's role and name. A select's role or name must not be special-cased in `snapshot.rs`.
- Do not make options focusable or read `aria-activedescendant` without a ruling (per a11y-plan §5 Keyboard Navigation, Per-surface keyboard shortcuts). The CRUD listbox's unread active descendant is kept as SC 4.1.2 work outside the tier-0 target, by the founder's F2 (2026-10-14), and is pinned by `accessibility_active_descendant_unread`.
- Do not move the stand's Tab tables (per a11y-plan §5 Keyboard Navigation, Test harness pattern). `tab_order` and `ENABLED_TAB_ORDER` cover the four lean tasks, and this chunk's boundary keeps the stand as built, so a stand-table move signals scope drift.

## Contract bindings
- a11y ↔ tests (per a11y-plan §9 CI Integration):
  - The `a11y` leg runs six fixed files (`accessibility_hidden` · `accessibility_roles` · `focusability_updates` · `stand_keyboard` · `stand_contrast` · `stand_accessibility_ids`) and their per-file counts.
  - A new fixture check lands in the workspace `test` leg unless the plan widens the a11y leg.
  - A new test inside one of those six files moves the leg's recorded counts.
- a11y ↔ driver refusal (per a11y-plan §7 Screen Reader Support, Accessibility tree output). The driver's `disabled` refusal reads the snapshot's `enabled == Some(false)`, so a disabled select must be refused `disabled` with nothing dispatched. This binds to the driver's refusal schema in architecture §Standard Contracts.
- a11y ↔ security (per a11y-plan §2 A11y Strategy, Role derivation):
  - The chosen value would leave as a control `value` inside the ratified snapshot crossing.
  - A new verb, argument or engine default action is the security plan's boundary question.

## Acceptance criteria contributions
- On the select fixture, in both layout modes, the single-choice select's tree node reads role `ComboBox` and a non-empty accessible name, and its snapshot node's `role` and `name` equal that tree node's (per a11y-plan §4 ARIA Patterns & Roles; per a11y-plan §7 Screen Reader Support).
- On the fixture, in both layout modes, a Tab / Shift+Tab walk of the stated sequence reaches the select at its document position as a form control, with the engine focus, the snapshot's `focused` node and the tree's focus agreeing at every step. A `disabled` select is skipped. The stand's `tab_order` / `ENABLED_TAB_ORDER` and the a11y leg's per-file counts stay unmoved (per a11y-plan §5 Keyboard Navigation; per a11y-plan §9 CI Integration).
- After the driver chooses an option by the select's stable id:
  - the snapshot's `value` reads the chosen option;
  - the step's diff names the select with `value` in `differs`;
  - `unkeyed_actionable` returns nothing on the fixture.
  (per a11y-plan §7 Screen Reader Support)
- If the chunk adds keyboard default actions for a select, a focused, enabled select is operable by keyboard alone. A disabled one takes no key and no click. Each change fires one `input` event, and a no-change key fires none, in both layout modes (per a11y-plan §5 Keyboard Navigation, Keyboard handling).
