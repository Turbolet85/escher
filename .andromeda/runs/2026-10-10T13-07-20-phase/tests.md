## Relevance
relevant — the chunk is two engine fixes whose whole proof is tests: a regression check per fix, two pinned checks restated, three unit-test-held texts restated (test tier `0`, per test-plan §1 → Test tier).

## Constraints
- Every check that reads a screen through the stand or a driver call runs in both layout modes (`for incremental in [false, true]`) and its readings are equal across the two; the regression check of each fix and both restated checks are bound by it (per test-plan §5 → Session ↔ held instance; test-plan §2 → Differential oracle).
- The two runners compile different bodies of the bounds reader: test-plan §9 → Engine features by runner states that the workspace build resolves blitz-dom with `writing-mode` on and the per-package build (`-p blitz-tests`, what `agent-run.sh run` uses) with it off, and that `writing-mode` selects which body of `BaseDocument::physical_unrounded_geometry` is compiled. The bounds fix is required green under BOTH `cargo test -p blitz-tests --locked --test {name}` and the workspace leg. Whether both bodies carry the defect, and whether one fix site covers both, is research's question (per test-plan §9 → Engine features by runner).
- test-plan §5 → Session ↔ held instance states the two engine readings as "pinned as they read, not fixed" in `stand_act_scroll` and `stand_act_obstructed`, and states that `stand_act_scroll`'s CRUD flow reads a row's centre against the list's `bounds` taken BEFORE the scroll because a scrolled box's own bounds read shifted. Restating the two pinned tests is required with the fix; whether the before-the-scroll workaround in the first four `stand_act_scroll` tests still holds, is redundant, or must be restated once the box reads true bounds is research's question (per test-plan §5 → Session ↔ held instance).
- The three limit sentences are held by escher-driver unit tests against stated tables: `refusal.rs` pins each cause's name, meaning and remedy as fixed text (non-empty, remedies pairwise distinct, no `/` in any text), `schema.rs` pins every verb's help and each verb's argument and result shapes. A restated sentence requires its table row restated in the same change, and a restated `Cause::Covered` meaning must hold no `/` (per test-plan §4 → escher-driver).
- Other stated tables sit in the blast radius and must be re-read, not assumed: `stand_act_ids` asserts both row counts of its 77-node table (70 accepted, 7 refused, each task's `task-header-spacer` among the `covered` rows as a zero-height box hit through to the header); `stand_act_diff` and `stand_diff` hold each returned diff equal to the check's own `before.diff(&after)` and to a stated node list; `stand_snapshot` holds each control's snapshot bounds at its bounding client rect; `stand_act_spans` reads the three diff lengths on each acting call's span line. Whether any of these rows moves under either fix — in particular under decision 2's choice of which boxes stop a hit — is research's question (per test-plan §1 → tests/blitz-tests).
- A new check is one `.rs` file per behaviour directly under `tests/blitz-tests/tests/`, auto-discovered as its own target; the manifest gains no `[[test]]` table (pinned by `BlitzTestsTargetsTest`), a `stand_` prefix is what places a file in the `run stand` selection, and an in-process check carries no `cfg(unix)` gate so the windows and macos matrix legs run it (per test-plan §2 → Directory pattern; test-plan §4 → blitz-tests targets; test-plan §1 → Surfaces under test).
- Fixtures beside the stand are in-file, inline HTML or components, booted with the stand's pinned options (`seven_guis::stand::options(incremental)`: 800×600, scale 1.0, bundled font, no net provider) and assert unconditionally — the stand checks have no font skip path. The `covered` case has no stand control, so its regression check is a fixture bound by this rule (per test-plan §7 → Builders and options; test-plan §7 → Seed strategies; test-plan §2 → Font-dependent tests).

## Patterns to follow
- Reuse the shared modules instead of restating them: `tests/common/mod.rs` (`boot`, `by_id`, `node`, the `controls` and `rendered` tables) and `tests/session_common/mod.rs` (`hold`, the call builders `click` · `type_into` · `scroll` · `snapshot`, `act` returning `Acted { settled, busy, diff, advanced_ms, in_view }`, `refused`, `refused_unchanged`, `focused`) (per test-plan §3 → Crate-local test helpers).
- For the engine-level half of each fix, the shape of `scroll_into_view_nested`: parsed pages at 800 × 600, both layout modes, read through the harness's inspection helpers (`hit`, `hit_node`, `layout_rect`, `center_of`) and input helpers (`click_at`, `wheel_at`, `scroll_into_view`), which route through the real event-dispatch pipeline; a blitz-dom in-file unit test instead builds its DOM through `DocumentMutator`, the HTML parser being a circular dev-dependency there (per test-plan §1 → tests/blitz-tests; test-plan §3 → Inspection helpers; test-plan §3 → Input helpers; test-plan §2 → blitz-dom pipeline tests).
- Red before green, recorded: each regression check is read red on the unfixed engine and green on the fixed tree, and a mutation control turns its named test red and reads green on the restored tree, written to the chunk's `evidence/controls.md` as earlier chunks did (per test-plan §4 → escher-driver; test-plan §5 → Session host ↔ what it writes).
- A regression test is named for the bug it guards and documents the bug in its header; a stated table carries its row count asserted (per test-plan §2 → Test function naming; test-plan §4 → escher-driver).
- For decision 4: on the fork WPT is a host run, never a CI job — `cargo run -rp wpt css svg` (release build), writing `wptreport.json` and `wpt_expectations.txt`, with the `wpt` cli's `diff --format json` for a before/after reading; attr tests read element layout and harness tests run real testharness.js; a case the runner cannot run is ported to Rust in blitz-tests. What a before/after reading costs on the dev host is research's question (per test-plan §1 → Surfaces under test; test-plan §3 → Runners and invocation; test-plan §2 → WPT conformance; test-plan §2 → WPT ports).

## Anti-patterns to avoid
test-plan §11 records no intent; the bans below are stated in other sections.
- Never read a green per-package run as the workspace leg's green — the same check file has read green under `-p blitz-tests` and red under the workspace leg, and here the two builds compile different bounds readers (per test-plan §9 → Engine features by runner).
- No sleep, no wall-clock read and no pass of the check's own beside the driver's in a driver-action check, and no runtime skip in a stand check (per test-plan §5 → Session ↔ held instance; test-plan §2 → Font-dependent tests).
- No assertion message that prints what a call supplied — a failing row is named by its index — and no second copy of a role, name or id mapping beside the shared tables, which are stated expectation only (per test-plan §4 → escher-driver; test-plan §3 → Crate-local test helpers).

- tests ↔ a11y: the `a11y` leg (`accessibility_hidden`, `accessibility_roles`, `focusability_updates`) runs in the same workflow as the test leg, and the stand checks tie snapshot ids, roles and names to the accessibility tree; a hit or bounds change is read against them (per test-plan §9 → Legs; test-plan §1 → tests/blitz-tests).
