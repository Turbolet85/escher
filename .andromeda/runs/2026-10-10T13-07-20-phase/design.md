# design extract

## Relevance
partial — the chunk renders no new UI and binds to no token; the plan reaches it only through its engine-behaviour records (the hit walk's stacking order, scroll motion, scrollbar geometry and behaviour, the bundled-font stand) and the `escher-session` output form.

## Constraints
- design-system §Depth Strategy (Engine depth behavior) requires the hit walk's order — positive-z hoisted children, then paint children in reverse, then negative-z hoisted children: the hit fix may stop a hit at a scrolling box's edge, and inside the box's own area that order must read as before. The section states no rule for a point outside a box's area — which boxes stop a hit, and at which edge, is decision 2's, not the plan's.
- design-system §Depth Strategy (Engine depth behavior) requires the stacking-context root set (opacity, fixed or sticky position, z-index, transforms, atomic paint effects, `isolation`) to decide what is hoisted: a hoisted child of a scrolling box is hit through its stacking context, so whether an edge stop at the box also cuts off a hoisted descendant that paints outside the box is research's question.
- design-system §Motion (This project's values) requires a programmatic into-view scroll to write every scrolling box that holds its target at once, innermost first, with the requested behaviour applied to the viewport alone, and the driver's `scroll` to be instant inside one settled step: the scope lists `packages/blitz-dom/src/scrolling.rs:776` as a caller of the geometry reader, so whether the bounds fix changes what that caller reads — and so where an into-view scroll lands — is research's question; the requirement stands either way.
- design-system §Motion (This project's values) requires the overlay scrollbar behaviours — a hover where a hidden thumb would be does not summon it, the thumb changes appearance on hover and while dragged, a wheel event over a scroller cancels a smooth scroll in progress: each is a pointer reading on a scrolling box, so each must read the same after the hit fix. Whether thumb hits go through the walk the chunk edits is research's question.
- design-system §Spacing (Engine spacing) requires the overlay thumb geometry (thickness, thin thickness, margin, minimum length, in CSS px) to lie inside its box: neither fix may move a thumb or the area it answers on; whether the geometry reader the chunk edits feeds the thumb's placement is research's question.
- design-system §Typography (Loading) requires the headless stand to run on one bundled font for every generic with system fonts off, and records that blitz-tests text measures 0x0 without the `system-fonts` feature so font-dependent assertions pass vacuously: a bounds assertion of this chunk — on the stand or on a fixture beside it — must not rest on a box sized by unmeasured text.
- design-system §Surface: cli (Component Patterns) requires `escher-session` to print one line of JSON keyed by the driver schema's own words, with no colour, no ESC byte on any answer line and the same output piped or not: the three restated limit sentences are schema texts, so wherever one is written in an answer it must keep that form. Which of the three reaches an answer line today is research's question.

## Patterns to follow
- An engine behaviour is recorded against a named reference — expected pixels taken from Chromium, overlay timings documented as Chromium's, paint levels per CSS 2.1 Appendix E (design-system §Depth Strategy, Engine depth behavior; design-system §Motion, This project's values): state the true reading of each fix against a named spec or engine the same way.
- A measured engine reading enters the plan as a dated record with its check and its chunk report beside it (design-system §Motion, This project's values — the nested into-view scroll, ratified and "as measured at" its report): the two fixes' readings are recorded in that shape at the wrap, never by this phase.
- The stand's determinism comes from its boot, not from the check: bundled font through `build_single_font_ctx`, system fonts off (design-system §Typography, Loading), on a viewport whose logical size is the physical size divided by hidpi × zoom, default scale 1.0 (design-system §Surface: desktop-native, Tokens). A fixture beside the stand takes the same boot; whether any check of this chunk reads bounds at a scale other than 1.0 is research's question.
- Stand styling is untokenized and recorded by file and line (design-system §Color Palette, Core Colors; design-system §Border Radius): a case the stand lacks goes to a minimal fixture, leaving the stand's task styles as recorded.

## Anti-patterns to avoid
- No animation on the way to a fix: a nested scrolling box is never animated by an into-view scroll, and the document holds one scroll animation at a time (design-system §Motion, This project's values). The plan records reduced-motion handling as observed absent (design-system §Motion, Reduced motion), so a new animated path would have no override to bind to.
- No colour, ESC byte or terminal test in anything `escher-session` writes, restated sentences included (design-system §Surface: cli, Component Patterns).
- No colour token or CSS custom property introduced into the engine or integration crates for a fixture's sake — the plan records none there (design-system §Color Palette, Token sets).

## Contract bindings
- design ↔ tests: the plan's records name the checks that hold them — `tests/blitz-tests/tests/paint_order.rs` (design-system §Depth Strategy), `scroll_into_view_nested.rs`, `fragment_navigation.rs`, `scrollbars.rs`, `scrollbar_drag.rs`, `stand_act_timer.rs` (design-system §Motion). They are the design-side regression set for both fixes, run in both layout modes where the file does so.
- design ↔ a11y: no token, focus colour or state colour changes, so the contrast (SC 1.4.3) and not-colour-alone bindings are not triggered; the motion binding is not triggered while no animation is added (design-system §Motion, Reduced motion). Bounds and hit targets as accessibility surface are a11y's to state.
- design ↔ layouts: where a box stands on the screen is the layouts distiller's; this extract covers the engine-behaviour records only.
- design ↔ wrap (drift): the plan cites lines in the files the chunk edits (`packages/blitz-dom/src/node/node.rs`, `document.rs`, `scrolling.rs`) and its hit-walk sentence states order with no edge rule (design-system §Depth Strategy, Engine depth behavior); both are re-pointed or restated at the wrap, per the scope's boundary on the masters.

## Acceptance criteria contributions
- (design) Inside a scrolling box's own area a hit answers the same element as before the fix, in stacking order; `paint_order` stays green (per design-system §Depth Strategy, Engine depth behavior).
- (design) An into-view scroll still writes every nested scrolling box at once and the driver's `scroll` stays one instant settled step; `scroll_into_view_nested` stays green in both layout modes (per design-system §Motion, This project's values).
- (design) Overlay scrollbar hover, drag and wheel-cancel readings are unchanged; `scrollbars`, `scrollbar_drag` and `fragment_navigation` stay green (per design-system §Motion, This project's values).
- (design) Every `escher-session` answer line that carries a restated sentence is one line of JSON with no ESC byte, the same piped or not (per design-system §Surface: cli, Component Patterns).
