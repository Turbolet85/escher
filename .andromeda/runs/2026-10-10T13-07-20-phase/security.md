## Relevance
partial — the chunk opens no surface, input class, secret or dependency; it changes what two engine readers return (a box's client rect, the hit walk), and those readings feed surfaces the plan already bounds: the driver's refusal detection, its fixed refusal and help texts, the content of a call's answer, and every document the engine lays out, remote content included.

## Constraints
- The driver's validated surface stays as the plan states it — nine verbs in two levels, six argument kinds, eight refusal causes; a new verb, argument, result field or cause is a widening that needs its own ratification, and the scope builds none (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- The screen-level refusals keep their one fixed order — `disabled`, then `off-screen`, then `covered` — and a refused call runs nothing and leaves the snapshot and both focus readings as they were, in both layout modes; the fixes may change which targets meet `off-screen` or `covered`, never the order or the nothing-run rule. Whether the executor's code needs any edit for that to hold on the fixed engine is research's question (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- Each of the three restated sentences stays a fixed `&'static str` that holds no path and nothing a call supplied; the cause set stays closed at eight and `Cause`, `Fault` and `Refusal` gain no `String` field (per security-plan §Error Handling, "Error format (typed errors)", the escher-driver refusal item).
- A call's answer keeps the content classes already ratified to cross — ids, accessible names, control values (masked where the plan says), the snapshot's text and the diff — with no `NodeId` crossing and the answer bound unchanged; changed `bounds` figures and a shorter `changed` list are the same classes, and a new field or class in an answer would be a new crossing question (per security-plan §Input Validation, row "Driver session socket (escher-driver)").
- The edited hit walk and geometry reader add no panic path: they run over every document the engine holds, so a possibly stale id is resolved through `get`, never indexed, and hit testing keeps its early return when there is no DOM (per security-plan §Error Handling, "Graceful degradation (no panic)"). The accessors the plan lists as panicking on a node that lacks the field or its computed styles (`layout_data`, `layout_style()`) are not to be newly reached on a node that may lack them (per security-plan §Error Handling, "Panic paths", DOM internals). Whether the present walk already guards each is research's question.
- Scroll offsets stay clamped to their range and a programmatic scroll to a missing node stays without effect — the geometry reader has a caller in the scrolling code, so the fix must not change that reading's bounds check (per security-plan §Input Validation, row "Scrolling | Targets"). Whether the into-view scroll's result changes with the fix is research's question, and the scope already marks it a finding to ask.
- The fixes add no log record and no field: the driver's one record stays the command span with its eight fields of fixed words, bools and counts — a diff's three sizes may be fielded, its content never — and any engine call site stays behind the crate's `tracing` feature (per security-plan §Input Validation, row "Driver command schema (escher-driver)"; per security-plan §Logging & Monitoring, "Log format and backends").

## Patterns to follow
- Validate first, then detect, then act: `Session::run` returns `validate`'s refusal before anything else runs, and nothing public runs a `Command` that did not come from `validate` — a restated check drives the fixed engine through that same path (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- A refusal or help text is amended on a recorded word of the founder or the operator, the cause set and every other text standing as they were — the three restated sentences follow that, on the operator's word by the take-up directive (per security-plan §Error Handling, "Error format (typed errors)", the escher-driver refusal item).
- Ids are looked up anew on every call, resolved through `get_node` and never by index, and the session keeps no `NodeId` between calls — a regression fixture that names a box or a control by id follows it (per security-plan §Input Validation, row "Markup attributes | `id` (stable element id)").
- Screen-level refusals are measured in both layout modes with the instance read unchanged after each refused call (per security-plan §Input Validation, row "Driver command schema (escher-driver)").

## Anti-patterns to avoid
- Putting an id, an accessible name, a control value, a bounds figure taken from a run or any call-supplied text into a cause's meaning, a help text, a `Fault` or a `Refusal` — the restated sentences describe the rule, never a case (per security-plan §Error Handling, "Error format (typed errors)", the escher-driver refusal item).
- Fielding or logging an `Outcome`, a `Command`, a diff's nodes or the screen text while debugging the fixes — the plan lists each as never fielded (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- Adding a wire request, a listener or a command to expose a hit or a rect for the proof — the one listener and its three requests are the registered surface (per security-plan §API Security, row "Local session socket (escher-driver)").

## Contract bindings
- security ↔ tests: the refusal-order and nothing-run mandates are proven by the stand and fixture checks the scope restates (`stand_act_scroll`, `stand_act_obstructed`) and by the new regression checks; the both-modes requirement binds to the test plan's layout-mode contract (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- security ↔ obs: the command span's `changed` count will read differently for a step that scrolls a box; it stays a count, and the span's field set is the obs plan's as well as this plan's (per security-plan §Input Validation, row "Driver command schema (escher-driver)"; per security-plan §Logging & Monitoring, "Log format and backends").
- security ↔ architecture: the plan records as built that `covered`'s meaning ends with the scrolled-out-content sentence and that three help texts say the scrolled-box bounds limit; restating them makes that record stale, and the scope leaves the masters to the wrap (per security-plan §Error Handling, "Error format (typed errors)", the escher-driver refusal item).
- security ↔ founder's file (scope decision 5): the plan's surface for scripts is the script-execution vector, and its rows on script-facing arguments state no rule for a rect or an event coordinate a script reads; whether a script-visible or event-visible reading changes with the fix is research's question, and where it changes what an agent meets or widens a boundary it is a ratification, not a silent change (per security-plan §Input Validation, rows "JS API arguments").
