# a11y extract

## Relevance
partial — the chunk adds no UI or a11y surface, but its "blitz-tests green" baseline includes the suite's accessibility, focusability and contrast-stroke tests, and the build it measures has to include the default `accessibility` feature.

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary). The baseline reading is the first measurement against that target, so a red in an a11y-bearing test belongs to this tier's surface. It is not an unrelated failure.
- `accessibility` is a default feature across blitz-dom, blitz-shell, blitz and both Dioxus crates, and blitz-tests builds blitz-dom with `accessibility` and takes `accesskit` as a dev-dependency (per a11y-plan §1 A11y Scope Summary). The measured `cargo build --workspace` / test run must use the default feature set. Whether the CI/commands form research confirms adds any `--no-default-features` or feature override is research's question.
- The browser app's `accessibility` feature is NOT in its default set (per a11y-plan §1 A11y Scope Summary). A default-features workspace build therefore does not compile the browser's a11y path. Record this as a coverage note beside the baseline, not as a gap to close here.
- The a11y assertion harness is Rust tests in blitz-tests over the AccessKit tree, using `build_accessibility_tree()` after `resolve` plus the `assert_role` / `unknown_tags` helpers (per a11y-plan §3 A11y Assertion Harness Contract). This chunk runs that harness as it is and adds no test (scope Boundaries).
- Contrast-verification harness setup and the a11y CI gate are bootstrap items owned elsewhere (per a11y-plan §3 Bootstrap phases (derive for route / setup-project): `contrast-verification-harness-setup`, `a11y-ci-gate-wire`). Neither is in this chunk: scope rules out new tooling and CI.
- On this host the Unix AccessKit platform adapter path (`accesskit_unix`) is the one compiled (per a11y-plan §2 A11y Strategy, Platform adapters). Whether it builds cleanly on this Arch-based host, and which system libraries it needs, is research's question. If it does need any, they belong in the host-facts record.

## Patterns to follow
- Record the a11y-bearing blitz-tests files by name inside the baseline's test reading, so later a11y chunks can read against it. Per a11y-plan §3 A11y Assertion Harness Contract, §5 Keyboard Navigation (Focus order) and §6 Visual Design Verification (Color contrast), those files are `accessibility_hidden.rs`, `accessibility_roles.rs`, `focusability_updates.rs`, `interaction_state_teardown.rs`, `harness_smoke.rs`, `scrollbars.rs` (contrast stroke) and `scrollbar_drag.rs`. Whether each currently passes is the run's to measure.
- Run the incremental and non-incremental variants as the suite has them. The focus and contrast assertions above run inside that same pipeline (per a11y-plan §5 Keyboard Navigation and §6 Visual Design Verification). Add no a11y test (scope Boundaries).

## Anti-patterns to avoid
- Do not narrow the measured build or test run with `--no-default-features` or by dropping `accessibility`. That would leave the a11y tier's assertion surface out of the "green" claim (per a11y-plan §1 A11y Scope Summary and §3 A11y Assertion Harness Contract). a11y-plan §11 A11y Anti-Patterns records no intent, so this ban comes from §1/§3 scope and is not a plan-listed anti-pattern.

## Contract bindings
- a11y ↔ tests: the a11y assertion harness IS a subset of the blitz-tests suite this chunk runs (per a11y-plan §3 A11y Assertion Harness Contract). The baseline's test reading is also the a11y harness's first recorded reading.
- a11y ↔ CI: the a11y CI gate (per a11y-plan §9 CI Integration and §3 Bootstrap phases `a11y-ci-gate-wire`) binds to the later "Fork CI reached" / "CI gate legs" entries, not to this chunk.

## Acceptance criteria contributions
- (a11y) The baseline's build and `blitz-tests` run use the workspace default features, `accessibility` included. The recorded command shows no `--no-default-features` or feature override that drops it (per a11y-plan §1 A11y Scope Summary).
- (a11y) The baseline test record lists pass/fail for the a11y-bearing blitz-tests files: `accessibility_hidden`, `accessibility_roles`, `focusability_updates`, `interaction_state_teardown`, `harness_smoke`, `scrollbars`, `scrollbar_drag` (per a11y-plan §3 A11y Assertion Harness Contract and §5 Keyboard Navigation). Any red among them is recorded as the baseline's reading and is never skipped or filtered out.
