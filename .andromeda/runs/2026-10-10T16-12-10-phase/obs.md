# obs extract

## Relevance
partial — the chunk's scope names no new span, event, metric, sink or subscriber, but it changes three things the obs plan's boundaries are stated over: the state a diff node carries inside an `Outcome` (obs-plan §3, §4), an engine file whose crate logs only behind its `tracing` feature (obs-plan §2), and the stand screens the sink's leak measurements are taken on (obs-plan §8).

## Constraints
- The driver's one log record stays the `command` span of `Session::run` with its eight fields of fixed words, bools and counts; obs-plan §4 requires that no `Outcome`, `Command`, `Call` or argument is fielded, so the three new states are never a span field — a changed pressed, selected or invalid reading reaches a log only as the `changed` count (per obs-plan §4).
- A state name such as `selected`, `pressed` or `invalid` is not in the escher targets' content-named scrub set, so the sink would print it if it were ever fielded under `escher_driver`; the scrub is no backstop here and the ban on fielding is the only guard (per obs-plan §8 → Scrubbing).
- `Outcome` derives `Debug`, and its `Debug` prints what its diff holds; obs-plan §3 requires that nothing in escher-driver logs, fields or `Debug`-prints one, and that an `Outcome` is written in one place only, `Outcome::to_json`, as a command's answer — the widened `NodeState` / `DiffNode` rides that one path (per obs-plan §3 → Logging stack).
- A command's answer is one line of JSON on stdout and never a log line; the sink writes to stderr only — the new diff-node keys appear on stdout as an answer and nowhere on stderr (per obs-plan §3 → Logging stack).
- Engine telemetry is compiled in only with a crate's `tracing` cargo feature and each gated call has a no-op path when it is off; if the accessibility builder gains a log site for an attribute it reads (an unrecognised `aria-invalid` token, say), it takes that form — whether the builder needs any log site at all is the plan's and P4's question, not a mandate of obs-plan (per obs-plan §2 → Telemetry mechanism).
- Under escher's sink an engine-target event prints only the safe field set and redacts every other field, the message included; an attribute value is not in that set, and in the upstream apps' unscrubbed subscribers attribute values are logged as-is — so no new engine field may carry an ARIA attribute's value or name a content-bearing attribute (per obs-plan §8 → Values logged as-is · Scrubbing).
- The headless stand, its `stand_*` checks and their shared modules install no subscriber, read no env var and print nothing, the two re-run children of `stand_act_spans` and `stand_id_persistence`'s child aside; the chunk's new checks through real input follow that, and a "measured first" reading taken at P3 is read into an assertion or an evidence file, never through an installed sink (per obs-plan §3 → Logging stack).

## Patterns to follow
- The span records lengths, not content: the diff's three list lengths are fielded and the diff's nodes are not. A step that flips a mode button or selects a row is expected to move `changed` (and possibly `added` / `removed`, if a role change alters which nodes the tree keeps) — whether `stand_act_spans` pins exact counts on a flight-booker or CRUD step that this chunk changes is research's question (per obs-plan §4).
- A check that reads a sink-installing process reads both streams into its assertions only, and its failure prints a kind and a count, never a captured line or what the host wrote (per obs-plan §3 → Logging stack).
- Where a check reads an accepted command's empty stderr it removes `RUST_LOG` from the child's environment; a new command-line check of the three states does the same (per obs-plan §3 → Logging stack).
- Engine features differ by runner: a workspace-wide build turns `blitz-dom/tracing` on and `-p blitz-tests` / `-p seven_guis` leave it off, so any reading of what the builder logs is taken under both builds and stated by build (per obs-plan §2 → Feature wiring).
- dioxus-native-dom logs every DOM mutation, `set_attribute` included, at debug with attribute values; the stand's new state attributes pass through that existing site on every state change. Whether that site is compiled into either sink-installing binary under either build, and whether the line count by level then moves, is research's question (per obs-plan §6 → Logged events (dioxus-native, dioxus-native-dom)).

## Anti-patterns to avoid
- Fielding a diff node's state — or an `Outcome`, a `DiffNode` or a `NodeState` with `Debug` — on the command span or on any new event: obs-plan §4 lists what is never fielded and why (it would print an id, an accessible name or a control's value), and a `NodeState` carries `value` beside the three new states (per obs-plan §4).
- Adding a second driver log record (an event, or a span on `snapshot`'s reader, on the diff or on the JSON writer) to say which state changed: obs-plan §4 states the driver emits no event and the span is `run`'s alone (per obs-plan §4).
- An unconditional `println!` / `eprintln!` in the accessibility builder or in a stand check to show a state while measuring it: the engine's log sites are feature-gated and the stand checks print nothing (per obs-plan §2 → Telemetry mechanism; obs-plan §3 → Logging stack).

## Contract bindings
- obs ↔ security: the scrub sets and the "0 id needles · 0 name needles · 0 typed-sentinel occurrences" readings of obs-plan §8 are the measured side of security-plan §Surfaces (an `Outcome` is never logged or fielded; the span holds no call-supplied or screen-read content). Whether three state words in the snapshot's text and the diff sit inside the ratified crossing is the security extractor's reading (scope decision 5); obs binds only that they stay off stderr.
- obs ↔ tests: `stand_act_spans` (in-process capture, both layout modes) and seven_guis' `host_log` (the real host on `crud` at `RUST_LOG=trace`, both builds) are the checks that hold obs-plan §8's readings; the chunk edits the CRUD rows' markup and possibly their roles, which is the screen `host_log` and the id / name needle sets are taken from — whether the needle sets (15 ids, 6 names on CRUD) and the by-level line counts still hold after the markup change is research's question (obs-plan §8 → Values logged as-is; test-plan §3).
- obs ↔ a11y: the accessibility builder is blitz-dom engine code, so any diagnostic it emits is bound by the engine feature gate and the engine safe-field set (obs-plan §2, §8), while what it reads and writes on the node is the a11y plan's.
- The keyed contract of obs-plan §3 (Bootstrap phases — `otel-sdk-install`, `pii-scrubbing-wire`) is not turned on by this chunk; not read.

## Acceptance criteria contributions
- The `command` span of `Session::run` still records exactly its eight fields (`verb` · `cause` · `settled` · `busy` · `passes` · `added` · `removed` · `changed`) after the change; no field, event or line names a selected, pressed or invalid reading (per obs-plan §4).
- `stand_act_spans` and `host_log` pass under both builds (`-p` alone and `--workspace`) with their captures holding 0 id needles, 0 name needles and 0 occurrences of typed text — the needle sets re-derived from the changed screens if the stand's markup moved them, and said so in the report (per obs-plan §8 → Values logged as-is).
- Every new check and shared helper of this chunk installs no subscriber, reads no env var and writes no `println!`; a failing assertion message holds no id, accessible name or control value (per obs-plan §3 → Logging stack).
- Any log site the chunk adds in `packages/blitz-dom/src/accessibility.rs` is `#[cfg(feature = "tracing")]` with a no-op path and carries no attribute value; if none is added, the report says the builder gained no log site (per obs-plan §2 → Telemetry mechanism; obs-plan §8 → Scrubbing).
