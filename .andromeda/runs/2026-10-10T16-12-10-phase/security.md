# security extract

## Relevance
partial — no new surface, verb, argument, listener, secret or dependency is in scope; security binds at four points: what the ratified crossing carries (decision 5), the builder's new reads of untrusted markup, the password/file mask, and the log.

## Constraints
- **The crossing names carriers, not state fields (decision 5).** security-plan §Input Validation (Driver session socket row) requires that an answer carry ids, accessible names, control values, the snapshot's text and the diff, and nothing else of the screen; it lists the text and the diff as whole carriers and states no rule for a field added inside one. The plan therefore neither ratifies nor forbids three state words by name: the reading "inside the crossing" holds by the plan's wording only while each state crosses as a closed word or bool inside those two carriers (per security-plan §Input Validation, Driver session socket row). The plan records every earlier widening as ratified by the founder one by one; it holds no recorded answer for this one.
- **No raw attribute text crosses.** A state written out as the attribute's own text (an `aria-invalid` value passed through as typed by the author) is attribute-value content, a class security-plan §Input Validation (Driver session socket row) does not list among what an answer carries, and one security-plan §Input Validation (Markup attributes `id` row) requires the neighbouring in-process reader never to hold. Such a reading is a widening and goes to the founder; a closed token set does not raise it.
- **The states get a second exit, which decision 5 does not name.** security-plan §Input Validation (Markup attributes `id` row) records the platform accessibility adapter as a crossing ratified for ids as `author_id`, text runs, labels and accessible names, refreshed on change. A state set on the accessibility node by the builder reaches that adapter in a windowed build. Whether the node already carries comparable states (checked, disabled) to the adapter, so that the three add no class there, is research's question; the scope's decision 5 checks the socket and the command line only.
- **The new reads take untrusted markup.** security-plan §Input Validation (Markup attributes `aria-label` · `<label for>` row) requires the builder's attribute reads to work on any parsed content — the browser app's remote HTML included — with no new input class and no lookup that panics; security-plan §Error Handling (Graceful degradation) requires a defined non-panicking reading where input is absent or stale. Each of the three attributes needs a defined reading for an empty, unknown, mixed-case, over-long or repeated value and for an element whose role does not support it.
- **The mask is untouched by the model's growth.** security-plan §Input Validation (Markup attributes — password and file `input` value row) requires a password's or a file input's `value` to read the fixed mask in the snapshot, its text, a diff entry and an answer's written form, and the typed text or host path to occur in no id, name or value; security-plan §Data Protection (Local user data handled) requires the same of a chosen file's path. New `NodeState` fields, text tokens and JSON keys must leave that reading as it is and give typed text no new field to appear in.
- **No new log content.** security-plan §Input Validation (Driver command schema row) requires the command span to hold eight fields of fixed words, bools and counts, and never a `Command`, `Outcome`, argument, screen text or node; security-plan §Logging & Monitoring (Log format and backends) requires that a sink-installing host's stderr hold no id, name or typed text at any level. A node changed by one of the three states may move the `changed` count and nothing else; the builder, the snapshot and the driver gain no field, event or print that holds a state, an attribute value, an id or a name.
- **The schema change is a result shape only.** security-plan §Input Validation (Driver command schema row) requires a closed `'static` table of nine verbs, six argument kinds with bounds and one refusal order, with each added verb recorded as a ratified widening; security-plan §Error Handling (Error format, the escher-driver refusal item) requires eight causes whose names, meanings, remedies and help texts are fixed strings holding nothing a call supplies. The diff node's new keys and the restated help texts stay inside that: no verb, argument kind, bound or cause is added, and every restated text stays a fixed string.

## Patterns to follow
- The in-process reader shape of security-plan §Input Validation (Markup attributes `id` row): take no caller argument, resolve every tree id through `get_node` and never by index, omit a node that does not resolve, hold no `NodeId` in what is returned, log nothing.
- The stated-parse shape of security-plan §Input Validation (Markup attributes `attr_parsed` row and `disabled` row): a parse failure reads as absent, and where presence and parsed value could differ the plan states which one a snapshot field follows. Each of the three states needs the same one-line statement of what it follows.
- The bridge rule of security-plan §Input Validation (Dioxus mutations — Boolean attributes with a falsy value row): a falsy value clears only a name on the bridge's boolean list, and any other attribute holding `false` is written as text. Whether the three `aria-*` names are outside that list — so the stand's false readings arrive as the text `false` and must be read by value, not presence — is research's question.
- The text-form rule of security-plan §Input Validation (Markup attributes `id` row): fields that hold content are written quoted in `str`'s `Debug` form so none holds a line break or a bare quote; a state is a bare fixed word.
- The needle measurement of security-plan §Logging & Monitoring (Log format and backends): a typed sentinel, id needles and name needles counted in a host's stderr at `trace` and in an in-process capture, in both layout modes.

## Anti-patterns to avoid
- A log record, span field, `println!` or `Debug` print of a state, an attribute value, an `Outcome` or a diff node anywhere on the new path (per security-plan §Logging & Monitoring, Log format and backends; security-plan §Input Validation, Driver command schema row).
- An index, `unwrap`, `expect` or `unreachable!` on an attribute value or a tree id in the builder's or the snapshot's new reads (per security-plan §Input Validation, Markup attributes `aria-label` · `<label for>` row; security-plan §Error Handling, Graceful degradation).
- A silent addition beside the result shape — a verb, an argument, a refusal cause, an env read, a listener or a crate (per security-plan §Input Validation, Driver command schema row; security-plan §API Security, Local session socket row; security-plan §Secret Management, Environment values read).

## Contract bindings
- **obs** — the command span's eight fields and the sink's scrub sets: obs owns the schema, security-plan §Logging & Monitoring owns what may never be printed; a `changed` count that now moves on a state flip is inside both.
- **a11y** — the platform adapter is a11y's surface and security's crossing (security-plan §Input Validation, Markup attributes `id` row); which role may carry which state is a11y's, whether a state is a new content class through the adapter is security's.
- **tests** — the mask checks and the needle checks are test-plan checks that hold security-plan §Input Validation (password and file `input` value row) and security-plan §Logging & Monitoring; they run `for incremental in [false, true]`.
- **arch** — the diff node's shape lives in the one verb table (arch §Standard Contracts, Driver session); security-plan §Input Validation (Driver command schema row) binds what that table may gain without a ratification. No §Occupied Resources entry is owed while nothing is added beside the shape.
- **route / founder** — a reading under which the three states widen either crossing is not the operator's (scope decision 5); security-plan §Input Validation (Driver session socket row) records each widening with its ratifier, and the wrap restates the row either way.

## Acceptance criteria contributions
- Each of the three states is written in the snapshot's text and in a diff node's JSON as one of a closed set of words or a bool; an authored attribute value outside the read set (an arbitrary string, an empty one, an over-long one) occurs 0 times in the text and in an answer's written form, in both layout modes (per security-plan §Input Validation, Driver session socket row).
- A document carrying each of the three attributes with an empty, unknown, mixed-case and repeated value, and on an element whose role does not support it, builds its accessibility tree and its snapshot with no panic and a defined reading, in both layout modes (per security-plan §Input Validation, Markup attributes `aria-label` · `<label for>` row).
- With the new fields in the model, a password typed through the driver occurs 0 times in the snapshot's text and in the acting call's answer written out whole, and its value reads the mask (per security-plan §Input Validation, Markup attributes — password and file `input` value row).
- On a hosted flow that flips each of the three states, the command span still has eight fields and the host's stderr at `RUST_LOG=trace` holds 0 id needles, 0 name needles and 0 occurrences of a typed sentinel; `Cargo.lock` is unchanged (per security-plan §Logging & Monitoring, Log format and backends).
