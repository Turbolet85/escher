# a11y extract

## Relevance
relevant — the chunk edits the accessibility builder (an a11y-scope entity per a11y-plan §1 A11y scope), adds ARIA state attributes and possibly roles to stand controls, and extends the snapshot that a11y-plan §7 states as a consumer of the accessibility tree. The plan holds no statement of `aria-selected`, `aria-pressed`, `aria-checked` or `aria-invalid` anywhere: every constraint below is drawn from what it states about the builder, the snapshot and the stand around them.

## Constraints
- The a11y target is tier 0, SC 2.1.1 · 1.4.3 · 2.4.3, and the blitz-dom accessibility tree is a scope entity that is a default feature of the engine — so the builder change is a11y surface for every document, not for the stand alone (per a11y-plan §1 A11y Scope Summary).
- a11y-plan §7 (Accessibility tree output) requires the snapshot to take role, name and focus from the tree `accessibility_tree` returns with no second role or name mapping, and states that the tree gives an element node no value, checked or disabled property, which is why those three are read from the element. The three new states must take one of these two routes, named — decision 1 turns on it, and whether the builder today writes any state property on an element node is research's question.
- a11y-plan §5 (Script and framework exposure) requires that a falsy Dioxus value of an attribute outside the bridge's boolean list is still written, as the string `"false"`. An `aria-*` state attribute rendered from a Rust `bool` therefore reaches the DOM present in both readings, so the builder must read the attribute's value and never its presence; whether the three names are outside that list today is research's question.
- a11y-plan §2 (Role derivation) requires a node's role to come from its `role` attribute, else the HTML element mapping, and records as an open TODO that a strong native role can be overridden by the attribute. A role put on a stand row or mode button (decision 2) goes through that path and through the ARIA role-name map of a11y-plan §4 (Per-component pattern catalog); whether each candidate role name (and its container's) is in that map, and what an unmapped name reads as, is research's question.
- a11y-plan §7 (Accessibility tree output, the actionable-key rule) requires every actionable element to read an author key and states the CRUD rows as keyed by an `id` alone with no `tabindex`, role, focusability or Tab-order change, the check reading the role from a closed interactive list. A role or `tabindex` on the rows changes what that rule's check reads and must leave it returning nothing on the four lean tasks and Home.
- a11y-plan §5 (Focus order per layout) defines focusability by tag, `tabindex`, `href` and `disabled` and the Tab sequence by it. A state attribute alone must not move the stand's focus order (SC 2.4.3); if decision 2 makes a row focusable, the row must then be operable from the keyboard (SC 2.1.1) and the new sequence is stated and asserted, not left to fall out.
- a11y-plan §2 (Accessibility tree lifecycle) requires a mutation of an in-document node to mark the changed set, which the shell's refresh hands the platform tree, and records the refresh's windowed witness as still owed; a11y-plan §1 (A11y scope, Dioxus crates) states that neither stand binary builds a platform adapter. So the three states are proven at the document level here; nothing in this chunk may claim an assistive technology reads them.

## Patterns to follow
- Engine assertions are Rust tests in blitz-tests over the AccessKit tree — build the tree after `resolve`, map the element's `NodeId` to its AccessKit node, match on the node's property — one test file per attribute family (per a11y-plan §3 A11y testing tool pick). The check of the three attributes on a minimal HTML fixture follows it.
- The two ARIA attributes the builder is stated to read are each read by value, with the edge value pinned by a test — `aria-hidden` keeps the node and marks it, a whitespace-only `aria-label` names nothing (per a11y-plan §4 Per-component pattern catalog, Hidden content; a11y-plan §7 Accessibility tree output). Each new attribute's value set gets the same treatment: its true reading, its `"false"` reading and its absence.
- The stand's expected roles and input names are stated once, as tables of the stand checks' shared module, as stated expectation and never a second mapping (per a11y-plan §7 Accessibility tree output). A stand control whose role changes under decision 2 is restated in that one table.
- A state is proven on the stand through real input, in both layout modes, as "exactly this control's node reads it" and, where the tree carries it, "and it is the tree's reading" — the shape the `focused` checks take (per a11y-plan §5 Test harness pattern).
- The text form and the diff are readers of the snapshot model and of nothing else, and a diff reports a change on the element by its stable id (per a11y-plan §7 Accessibility tree output). The three states reach the text and the diff through the model only.

## Anti-patterns to avoid
- No second role or name mapping — in the snapshot, its text, its diff, the driver's schema or a test table (per a11y-plan §7 Accessibility tree output).
- No change to what `enabled` and `checked` read: `enabled` follows the presence of `disabled`, and `checked` is the checkbox or radio state (per a11y-plan §7 Accessibility tree output). Folding an `aria-checked` reading into `checked` changes the second.
- No state carried by colour alone as the proof of it: the flight booker's invalid cue is asserted without colour today, and the new `aria-invalid` reading stands beside that cue, not in place of its check (per a11y-plan §8 Error recovery).

a11y-plan §11 holds no recorded ban list; the three above are derived from the sections each cites.

## Contract bindings
- **tests (CI legs)** — a11y-plan §9 states the `a11y` leg as three named test targets that add no stand assertion. A new engine accessibility test target runs in the workspace test leg only unless that leg's list is widened; whether it is widened is a tests-domain decision this chunk raises.
- **tests (stand harness)** — the stand checks' shared tables of a11y-plan §7 (Accessibility tree output) are the tests domain's shared module; a role change binds the two.
- **layouts (focus management)** — if decision 2 changes a row's or a mode button's focusability, the per-surface tab sequence of a11y-plan §5 (Focus order per layout) changes with it.
- **design (colour palette)** — the invalid field's red styling and the class-only marks of the active mode and the selected row are as-built design tokens; a11y-plan §8 (Error recovery) covers the invalid cue only, and the plan records no contrast pair for any of the three marks (its token-pair block in §6 is unmeasured — nothing is cited from it).
- **architecture (merge surface)** — the builder's file and the role-override TODO of a11y-plan §2 (Role derivation) are upstream-owned; a role-validity rule added here ("read the state only on a role that supports it") touches that TODO's ground.
- The keyed contract of a11y-plan §3 (Bootstrap phases) is not turned on by this chunk and was not read.

## Acceptance criteria contributions
- (a11y) On a minimal HTML fixture, an element carrying each of the three attributes reads the state on its accessibility node, with a `"false"` value and an absent attribute each read as decision 1 sets them, in a blitz-tests test over the built tree (per a11y-plan §3 A11y testing tool pick).
- (a11y) On the stand, after real input and in both layout modes: exactly the active flight mode reads pressed, exactly the selected CRUD row reads selected, an invalid date reads invalid and a valid one does not — and where the builder writes the state on the node, the snapshot node's reading equals the accessibility node's (per a11y-plan §7 Accessibility tree output).
- (a11y) Every stand interactive control still reads a mapped role and a non-empty accessible name, the actionable-key check still returns nothing on the four lean tasks and Home, and each lean task's forward focus sequence and the Tab / Shift+Tab readings are unchanged — or the changed sequence is stated and asserted (per a11y-plan §7 Accessibility tree output; a11y-plan §5 Test harness pattern).
- (a11y) The flight booker's non-colour invalid cue check still passes beside the new invalid reading (per a11y-plan §8 Error recovery).
