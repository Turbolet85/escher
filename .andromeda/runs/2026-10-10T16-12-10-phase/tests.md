## Constraints
- **A state is proven through real input, in both layout modes, on the stand — and on an in-file fixture booted with the stand's options where the four lean tasks lack a case.** The plan states this as the standing shape of every snapshot-state check (`stand_snapshot_state`); the three new states take the same shape, and a value the stand never shows (a tri-state `mixed`, an `aria-invalid` token other than `true`, if decision 1 admits one) is a fixture's case, not a stand edit (per test-plan §1 → Coverage scope → tests/blitz-tests).
- **Two runners build the same check file against different engine features, and a green per-package run is not the workspace leg's green.** Every new or restated check is read under `cargo test -p blitz-tests --locked --test {name}` and under `cargo test --workspace --locked`; whether the accessibility builder's new readings sit on a path either feature set compiles differently is research's question (per test-plan §9 → Pipeline facts → Engine features by runner).
- **tests/blitz-tests is one test target per file, auto-discovered; the manifest gains no `[[test]]` table.** A new check file is a new target, moves the plan's file and target counts, and is picked up by `run stand` only through a `stand_` prefix; the manifest shape is pinned by `BlitzTestsTargetsTest` (per test-plan §2 → Test directory + naming conventions → Directory pattern; §4 → What unit tests cover → blitz-tests targets).
- **The stand checks' shared tables are stated once, in `tests/common/mod.rs`, as expectation.** If decision 2 changes a role the `controls(task)` table states, or adds or removes a node the accessibility tree keeps, that table and `rendered(task)` are restated there, never shadowed per file; whether either moves is research's question (per test-plan §3 → Crate-local test helpers → blitz-tests (stand checks)).
- **Existing checks state exact node sets and assert their row counts.** `stand_diff`, `stand_act_diff` and `stand_act_ids` each hold a step against the nodes stated for it (a flight choice, a CRUD row click, the 12 accepted clicks split into those that change the screen and those that do not, the 77-node / 70-accepted / 7-refused split). A mode button that now reads pressed or a row that now reads selected joins those diffs, so the tables are restated with their counts — a table is never loosened to "contains". Which rows move is research's question (per test-plan §1 → Coverage scope → tests/blitz-tests).
- **The snapshot's unit tests cover the model, the text form and the diff separately, compiled only under the crate's default `accessibility` feature, on a document built with the no-op HTML parser.** A new state field is pinned at unit level in each of the three files it reaches (the reader, the state tokens and their fixed order, a changed state naming its node alone); an attribute is written through `DocumentMutator` and the document resolved before the snapshot is read, and parsed markup is pinned in blitz-tests, where the harness has the real parser (per test-plan §3 → Crate-local test helpers → dioxus-native-dom; §1 → Coverage scope → dioxus-native-dom).
- **The driver's written form and its one table are pinned by unit tests that state each table in the test and assert its row count.** A new diff-node key changes what `json.rs`'s node test and `schema.rs`'s shape test state (the node fields); the JSON writer's node rows are tested over plain parts, the crate naming no virtual DOM; and the command-line check reads that each instance verb "answers exactly its fields". Whether those three read red on the model change before they are restated is research's question (per test-plan §4 → What unit tests cover → escher-driver; §6 → Drivers per surface → Command line).

## Patterns to follow
- **Seen absent before seen read.** The plan's snapshot-state and driver chunks each record a red reading before the green one and a mutation control per new test, in the chunk's `evidence/`; the scope's "measured first" is the same instrument — the three states read absent on HEAD, then each new check read red with its reader removed (per test-plan §4 → What unit tests cover → escher-driver; §1 → Coverage scope → tests/blitz-tests).
- **Engine-level reading on a `BaseDocument` built through `DocumentMutator`, parsed-markup reading in blitz-tests.** A unit test inside blitz-dom cannot use the HTML parser (a circular dev-dependency); the plan's integration-level accessibility checks sit in tests/blitz-tests (`accessibility_names`, `accessibility_roles`) — the engine's new ARIA readings follow one level or both (per test-plan §2 → Test levels observed → blitz-dom pipeline tests; §1 → Coverage scope → tests/blitz-tests).
- **A session-held step through the shared builders.** A check that reads "the step that changes it returns that node in its diff" runs the call through `Session::run` with `session_common`'s `click` / `type_into` / `act` / `refused_unchanged`, and compares the returned diff with its own `before.diff(&after)` and across the two modes (per test-plan §3 → Crate-local test helpers → blitz-tests (session checks); §5 → Boundaries covered → Session ↔ held instance).
- **Text size held against an in-file ceiling and the budget.** Each stand screen's text is asserted under its file's own ceiling and under `SNAPSHOT_TEXT_BUDGET`; new state tokens move the measured sizes, so the ceilings are re-read and restated, and the hosted `snapshot` byte counts the plan records by hand smoke are re-measured if cited (per test-plan §1 → Coverage scope → tests/blitz-tests; §6 → Drivers per surface → Command line).
- **A hosted answer is read through seven_guis' shared runner.** If the new JSON keys are asserted on the binary's stdout, the check uses `tests/common/mod.rs` (`run`, `client`, `keys`, the `Started` guard) and stays `cfg(unix)`-gated; whether `flight.sh` or `cli_commands` read a field the chunk changes is research's question (per test-plan §2 → Test levels observed → Command-line checks and shell flows).

## Anti-patterns to avoid
- test-plan §11 (Test Anti-Patterns) reads NO RECORDED INTENT and §10 sets no gate — nothing is cited from either; the bans below are stated by the sections named.
- **No sleep, no wall-clock read and no font skip path in a stand check.** Stand checks assert unconditionally under the bundled font and move time only by delivered ticks or the driver's `advance` (per test-plan §2 → Test levels observed → Font-dependent tests; §5 → Boundaries covered → Session ↔ held instance).
- **No pass read from a partial or empty run, and no line counted in total across targets.** An empty `run` is never a pass, and a check that reads a sink's capture counts lines by target because the workspace build adds an engine line (per test-plan §3 → Agent-run contract → `run {selection}`; §9 → Pipeline facts → Engine features by runner).
- **No assertion message, test name or failure print that carries what a call supplied or a screen read.** Driver assertions carry a row index only and the log checks print a kind and a count only; a new state check on a password or masked fixture keeps the mask assertions it sits beside (per test-plan §4 → What unit tests cover → escher-driver; §5 → Boundaries covered → Session host ↔ what it writes).

## Contract bindings
- **tests ↔ a11y (the a11y CI leg).** `ci-leg.sh a11y` runs three named files only; a new check of the engine's ARIA-state reading is outside that leg unless its list is extended, and the leg and its job are pinned by `LegScriptTest` and `CiWorkflowTest`. Whether the new check belongs in the leg is the a11y plan's call (per test-plan §9 → Pipeline facts → Legs; §4 → What unit tests cover → CI workflows and leg script).
- **tests ↔ obs (the command span and the stand log).** The driver's one log record holds eight fixed fields, pinned by `execute.rs`'s unit test and read by `stand_act_spans` and `host_log` with 0 ids, 0 names and 0 typed text; three new state words belong to a command's answer, never to a span field or a log line (per test-plan §3 → Stand log format; §1 → Coverage scope → escher-driver).
- **tests ↔ security (the socket's answer).** A hosted answer carries ids, names, values, the snapshot's text and the diff under a 1,048,576-byte bound; whether three state words inside that text and diff are inside the ratified crossing is the security plan's reading (scope decision 5), and the checks that drive a call over the socket are the ones that would witness it (per test-plan §3 → Session lifecycle, `session-wire` and `session-proof`).
- **tests ↔ agent-run (the 5-command discipline).** A new `stand_*.rs` file enters `run stand` with no script change, and its events are harness metadata, not a telemetry sink (per test-plan §3 → Agent-run contract → Events).
