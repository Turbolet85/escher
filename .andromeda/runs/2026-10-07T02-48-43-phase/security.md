# security extract

## Relevance
partial — the chunk adds tests and restructures one private function and five stand checks; it opens no crossing, input class, secret path or dependency, so the security plan binds it only through what must stay unchanged (the id grammar and its no-panic readers, the snapshot's no-exit and mask properties, the dependency gates).

## Constraints
- The restructured `VdomWalk::walk` must leave the stable-id grammar exactly as security-plan §Input Validation (row `Markup attributes | id (stable element id)`) states it: the author-key admission rule, the three `/`-bearing path tiers, the anchored path as the only id holding `//`, no empty segment in a component or document path, and the non-collision property the row derives from them. "Every id unchanged" is a security property here, not only a functional one: the row requires that no `id` value can make two ids equal.
- security-plan §Input Validation (row `Markup attributes | id (stable element id)`) requires that a non-element, stale or detached node reads `None`, that no path panics, and that the id is computed on demand and written to no log, DOM or vdom. The refactor may add no log call site, no cache written into the DOM or vdom, and no indexing of a slab by a possibly stale id. Whether the current `walk` already satisfies each of these is research's question; the plan states the target.
- The mutant in `place_children` (`&&` to `||` on the Dioxus-key filter of a `{tag}[{key}]` segment) sits on the grammar security-plan §Input Validation (row `Markup attributes | id (stable element id)`) relies on. That row states only that a keyed list row's segment carries its Dioxus key; whether the plan's non-collision claim covers a Dioxus key that is empty or holds `/` is research's question, and the killing test should pin the filter's two conditions separately so the row's claim has a named witness.
- New and restructured checks, and any shared table or helper, must keep the snapshot, its text and a diff inside the process: security-plan §Input Validation (rows `Markup attributes | id (stable element id)` and `Markup attributes | aria-label · <label for>`) requires that these are returned to their caller only and reach no log, event, socket, file or command, with tests as the only callers. That statement is recorded PROVISIONAL in the plan (pending the founder at the Epoch 3 boundary) and this chunk must not widen it. A `println!`, `dbg!` or an assertion message that formats snapshot content would put that content into the unscrubbed raw test output security-plan §Logging & Monitoring (the agent-run contract bullet) describes.
- The password and file-input mask must survive the restructure of `stand_snapshot_text.rs` and any table or helper moved out of the stand checks: security-plan §Input Validation (row `password and file input value (the snapshot's value)`) requires that the typed text and a file's host path occur in no id, name or value of any snapshot node, text line or diff entry, and cites `stand_snapshot_state.rs`, `stand_snapshot_text.rs` and `stand_diff.rs` as its evidence. Whether the function being restructured (`every_node_is_one_line_with_its_five_fields`) holds any of those assertions is research's question; a check that comes under the ceiling by dropping one is a regression against this row.
- New tests reading a node that may be gone (the `flush_queued_mounted_events` case: queued elements "still in the document") must resolve it through the non-panicking readers security-plan §Error Handling (Graceful degradation) lists, not the unwrapping ones security-plan §Error Handling (Panic paths) lists (`element_to_node_id`, `NodeHandle::node` / `node_mut`).
- No dependency edge is assumed. If the new test file needs one, security-plan §Dependency Security (Pinning; Audit tool; Supply chain integrity → Lockfile verification) requires a `workspace = true` inherited version, a committed `Cargo.lock`, `--locked` on every leg, and a passing cargo-deny advisories check with per-ID ignores only. The mutation tool the audits used is not among the pinned CI tools security-plan §Dependency Security (Pinning) records; whether the kill witness stays a dev-host run or enters `ci.yml` is research's question, and only the latter triggers the pinning rule.

## Patterns to follow
- Resolve tree and node ids through `BaseDocument::get_node` / `get`, never by index, and omit or skip a node that does not resolve — the reader shape security-plan §Input Validation (`id` row) requires of `snapshot`, `unkeyed_actionable` and `accessibility_tree`.
- In-process readers take no argument, log nothing and never panic (security-plan §Input Validation, `id` row); a helper extracted from `walk` or from a stand check keeps that shape.
- Absent or unparsable input degrades to `Option` / `None`, as security-plan §Error Handling (Graceful degradation) records for `try_element_to_node_id` and `try_doc`; the existing stale-id panic guards that section cites are the model for a new test touching a remounted or removed node.
- Dev-dependencies inherit from the workspace, and the integration-test crate stays unpublished, per security-plan §Dependency Security (Pinning).
- Source reads only the environment values security-plan §Secret Management (Environment values read) enumerates; a `TMPDIR` set for a mutation re-run is the tool invocation's environment, not a source read, and stays out of source and committed scripts unless registered.

## Anti-patterns to avoid
- security-plan §Security Anti-Patterns records no intent, so no ban is cited from it; the bans below follow from the measured sections.
- Printing or formatting snapshot text, a node name, a value or a typed secret into test output or an assertion message (security-plan §Input Validation, `id` and password/file rows; §Logging & Monitoring, agent-run contract bullet).
- Editing `create_head_element`, `flush_queued_mounted_events`, `Document::id` or `handle_event` to make a mutant killable in a way that adds an unwrap, an index by id or a new panic path to the lists in security-plan §Error Handling (Panic paths).
- A `create_head_element` test that builds a URL-bearing head element (`link`, `script src`, `style` with `@import`) against a document whose net provider can read disk or network: security-plan §Input Validation (row `file: URLs (net provider)`) records no path restriction and §API Security (rows Request size limit, Request timeout) records no cap or timeout. Which provider the test's document carries is research's question.

## Contract bindings
- security ↔ tests: the stand checks are the plan's cited evidence for the id grammar, the no-exit property and the mask (security-plan §Input Validation cites `stand_element_ids.rs`, `stand_id_persistence.rs`, `stand_snapshot.rs`, `stand_snapshot_text.rs`, `stand_snapshot_state.rs`, `stand_actionable_keys.rs`, `stand_diff.rs` by file:line). Moving tables and bodies stales those citations, and the ones into `element_id.rs`; reconciling them is the wrap's, and the test-plan's §3 keyed contracts name the same checks.
- security ↔ obs: the raw libtest output is unscrubbed (security-plan §Logging & Monitoring); escher's allowlist scrub does not reach it, so content kept out of test output is the only control.
- security ↔ a11y: the stable id leaves the process only as AccessKit `author_id` through the platform adapter (security-plan §Input Validation, `id` row; PROVISIONAL for the refresh on change). An id that changed under the `walk` refactor would change what crosses there.
- security ↔ architecture: a new test target is not a new workspace crate; a new crate, env var, port or socket would be an arch §Occupied Resources registration and a security-plan amendment first. The id grammar is also stated in arch §Standard Contracts and must read the same in both.
