# tests extract

## Relevance
relevant — all four CARRYs are test work or are guarded by tests (new mutant-killing tests, three restructured stand checks, shared stand tables, a refactor whose only guard is the test suite); test tier `0` per test-plan §1.

## Constraints
- **Home of the new test file is not chosen by the plan.** test-plan §2 (Test directory + naming conventions) records two homes — inline `#[cfg(test)]` modules beside the code, and `tests/blitz-tests/tests/` with one file per behaviour — and §1 (blitz-vibey-script) records a third precedent, a package's own `tests/` directory. Whichever P4 picks, test-plan §1 (Workspace (CI)) and §9 (Legs) require it to run under the workspace `test` leg with default features and `--locked`. What each home can reach of the private and `pub(crate)` functions the mutants sit in is research's question.
- **Agent-run reach follows the file's home and name.** test-plan §3 `run` requires every selection to be a `-p blitz-tests` run, and `stand` to be one `--test` stem per `tests/blitz-tests/tests/stand_*.rs` present. So: a new file under that directory with the `stand_` prefix becomes a stand check with no script change (§3 Proof); a new file in another crate is outside every agent-run selection and is reached by the workspace leg only; and whatever holds the shared control tables must not land as a `stand_*.rs` test target that carries no test. How `tests/blitz-tests` declares or discovers its targets, and where a shared module can sit without becoming one, is research's question.
- **Both layout modes, same tasks, same assertions.** test-plan §1 (tests/blitz-tests) requires each of the stand checks this chunk restructures or re-points — element ids, id persistence, the snapshot text, the accessibility ids, the snapshot — to hold in both layout modes over the lean tasks. A restructure that drops a mode, a task or an assertion breaks that coverage statement.
- **Stand determinism is kept by any shared table, helper or new stand-based test.** test-plan §3 (Construction), §7 (Builders and options) and §8 (Real dependencies kept) require stand checks to boot through `seven_guis::stand` with its pinned options and bundled font, fresh per boot; §2 (Font-dependent tests) requires them to assert unconditionally, with no skip path. In-file fixtures boot with the stand's options (§1, tests/blitz-tests).
- **Unit-level construction has stated limits.** test-plan §3 (Crate-local test helpers, dioxus-native-dom) requires the crate's unit tests to build a `DioxusDocument` from a plain app, drive it by the documented build/dirty/poll sequence, resolve before reading anything layout-dependent, and stale an id by dropping the node through the mutator; the same paragraph states the default config's HTML parser is a no-op at unit level, with parsed markup pinned in blitz-tests instead. test-plan §5 (Harness ↔ event pipeline) states `dispatch_recorded` bypasses Dioxus VirtualDom forwarding, while the input helpers route through the real dispatch pipeline (§3 Input helpers). Which driving path actually reaches the two `handle_event` negations, the mounted-event flush and the head-element creation is research's question.
- **Feature gating follows the surface read.** test-plan §1 (dioxus-native-dom) requires tests of the snapshot and actionable surfaces to compile only under the crate's default `accessibility` feature; §3 (Feature gating) records the general pattern. A new test that reads either surface carries the same gate; whether any of the seven mutants needs that surface is research's question.
- **No threshold gate exists to satisfy or to lean on.** test-plan §9 (Local pre-push gate; Legs; Coverage) requires the `fast` and `doc` legs and records coverage as measured with no threshold; §10's gate section is marked not yet measured. The plan carries no mutation-score contract and no complexity-ceiling contract — both are the audits' measures. How a kill is witnessed without passing vacuously, and how the ceiling is read before and after with the same collector, are research's questions, not test-plan mandates.

## Patterns to follow
- A regression test is named for the behaviour it guards and documents what it guards (test-plan §2, Test function naming) — the fit for one test per mutant, named for what that mutation would break.
- The dioxus-native-dom construction recipe and its existing VirtualDom-against-document test (test-plan §3 Crate-local test helpers; §5 Dioxus VirtualDom ↔ DioxusDocument) for a test that drives a real `VirtualDom`; `Harness::from_vdom` / `from_component` with pumping input helpers (§3 Construction, Pump semantics, Input helpers) for one that needs real input.
- A red-before-green record under the chunk's `evidence/` — the plan cites one as the measurement behind a test claim (test-plan §3 Crate-local test helpers, closing citation). It is the recorded precedent for showing a test fails on the broken code and passes on the real one.
- One statement shared by every check: the stand's pinned options live once in `seven_guis::stand` and every check reads them (test-plan §7 Builders and options; §3 Construction) — the shape the shared control tables follow.
- A stand check added under the `stand_` prefix is picked up with no script change and its count is re-measured and recorded (test-plan §3 Proof; §9 Local baseline).

## Anti-patterns to avoid
- test-plan §11 reads NO RECORDED INTENT — nothing is extracted from it; the bans below are contract statements from other sections.
- A pass with nothing asserted. test-plan §3 `run` requires an empty run never to read as a pass; §4 (Conditional assertions) records two inherited tests that assert only inside a branch and so can pass without asserting. A mutant test, a restructured check or a kill witness of that shape proves nothing.
- A skip path in a stand check. test-plan §2 (Font-dependent tests) keeps the runtime skip to the pre-existing font-dependent tests only; stand checks have none, and a shared helper must not introduce one.
- Driving a Dioxus handler behaviour through `dispatch_recorded`. test-plan §5 (Harness ↔ event pipeline) states it bypasses document-specific handling, so a test built on it cannot observe `DioxusEventHandler`.

## Contract bindings
- **obs ↔ tests:** test-plan §3 Events binds the agent-run events to harness metadata, not an escher-telemetry sink (obs-plan §3), and requires that captured stdout and panic text never reach an event. The chunk adds no event, no script change and no log field; assertion text stays in `run.log` only.
- **security ↔ tests:** the scope's rule that a stand check never prints snapshot content or puts it in an assertion message is security-plan §Input Validation's (as the scope names it); test-plan §1 (tests/blitz-tests) requires a typed password to appear in no snapshot, text or accessibility-tree field. Shared tables and helpers keep that shape.
- **a11y ↔ tests:** `stand_accessibility_ids.rs` is where test-plan §1 pins the controls' roles, names, `author_id` and Tab order, and its control table is one of those to be stated once — so the shared table becomes a11y evidence read by several checks. The `a11y` leg's three files (test-plan §9 Legs) are not among this chunk's files.
- **CI scripts ↔ tests:** test-plan §4 (Agent-run contract; CI workflows and leg script) pins the scripts and legs by contract tests. The chunk assumes no script, leg or workflow change; a test home that needs one is a §3 / §9 contract change, not a silent add.
- **The plan's own citations:** test-plan §1 (dioxus-native-dom — the unit-test count and the `element_id.rs` line ranges), §3 (Crate-local test helpers; Proof) and §9 (Local baseline) cite lines and counts this chunk moves. Reconciling them is the wrap's, per the scope.
