## Patterns to follow
- **Two recorded homes for a test, and one precedent for a third.** architecture §Conventions → Tests records in-file `#[cfg(test)] mod tests` unit tests and one-behaviour-per-file integration tests in `blitz-tests`; architecture §Design Philosophy → Headless, measurable, testable places integration tests in that crate's `tests/` directory; architecture §Existing Scopes → blitz-vibey-script records the one package that carries its own `tests/` directory. The operator's "a new test file" rules out the first; P4 chooses between the other two against the dependency constraint above.
- **Integration-test shape.** Per architecture §Conventions → Tests: a file covers one behaviour and opens with a `//!` doc naming it; scenarios run `for incremental in [false, true]`; names are descriptive snake_case; assertion helpers are `#[track_caller]`; a test first asserts its fixture produces the condition under test — the last is what keeps a mutant-killing test from passing vacuously.
- **Drive through the harness and the stand, with an in-file fixture where the stand lacks the case.** architecture §Standard Contracts → Test harness (`Harness<DioxusDocument>`, `from_component` / `from_vdom`, input synthesis through the real dispatch pipeline) and → Headless stand (`LeanTask` with `ALL`, `options(incremental)`, `boot`); architecture §Existing Scopes → blitz-tests records the in-file-fixture precedent beside the stand checks. The one Dioxus key the plan records on the lean stand is the CRUD row's model-assigned integer (§Standard Contracts → Dioxus DOM bridge), so whether the stand offers an empty or slash-bearing key, an `onmounted` listener, or a handler that cancels or stops an event — or a fixture must — is research's question.
- **Flattening idioms already in the codebase.** architecture §Conventions → Unsafe and borrowing records let-chains in `if` conditions as an established idiom — a way to remove nesting from `walk` without changing its order of evaluation; architecture §Conventions → Documentation requires the module's `//!` docs and each item's `///` to stay true, the id grammar they state included.
- **Shared test state is a departure the wrap records.** architecture §Conventions → Tests records per-file repetition of helpers as the as-built pattern (the pointer-event builder repeated per file); the one statement of each control table is the first shared module among the integration tests, so that convention line is amended at wrap rather than silently contradicted.

## Anti-patterns to avoid
- **A test-only door into the crate.** No `pub`, `#[doc(hidden)] pub` or `cfg(test)` shim that exposes `walk`, `place_children` or the vdom walk to a test, and no second id derivation alongside the one — architecture §Standard Contracts → Dioxus DOM bridge keeps one computation that every reader shares (the actionable check is recorded as taking its ids from `element_ids()`, "never a second id or role computation"), and §Existing Scopes → dioxus-native-dom keeps the module private.
- **Editing inherited code to make it testable.** The four functions under test sit in the Dioxus bridge crate the fork adopted (architecture §Project Intent → Crate purposes), and architecture §Project Intent (the Upstream sync line) names the next sync's merge base; a rewrite of an inherited function widens the merge the next route entry performs. Whether each of the four is inherited unchanged is research's question. A mutant that can be killed only by changing the function is a finding to surface.
- **A silent registry add.** A new dev-dependency, feature, env read, spawned child or workspace member introduced for a test's convenience — architecture §Occupied Resources and §Conventions → Manifests make each an explicit registration; a `Cargo.lock` change also re-keys the fork's CI cache (§Occupied Resources → CI infrastructure).
