## Constraints
- The a11y tier is 0 with targets SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary); this chunk claims no capability, so it must leave the stand's keyboard and focus-order evidence exactly as strong as it finds it. No contrast (SC 1.4.3) surface is touched.
- a11y-plan §7 (Accessibility tree output) requires every element node of a Dioxus document to carry its stable element id as AccessKit `author_id`, and no `TextRun`, document-root or `Window` node to carry one. The restructured `VdomWalk::walk` feeds those ids, so "every id unchanged" is an a11y requirement as well as an id one. Whether `stand_element_ids`, `stand_id_persistence`, `stand_id_edits` and `stand_accessibility_ids` together pin every `walk` branch that reaches an `author_id` is research's question.
- a11y-plan §7 (Accessibility tree output) requires the stand's interactive controls to carry an HTML-AAM role and a non-empty accessible name, with the inputs named by `<label for>` and `aria-label`, in both layout modes, Tab order unchanged. The `controls` table (id · `Role`) and `INPUT_NAMES` the chunk states once are the expected values of that requirement: the one statement must hold every row and every task each restating check holds today. Whether the two restated copies are row-for-row identical today is research's question; a difference between them is a finding to surface, not to merge silently.
- a11y-plan §7 (Accessibility tree output) requires the snapshot, its text form and its diff to take role and name from the tree with no second role or name mapping. A shared table is test expectation only: it must stay on the test side and must not become a helper that derives a role or a name for the code under test.
- a11y-plan §5 (Test harness pattern) and §8 (Error recovery) record the stand's focus assertions: each lean task's forward focus sequence through `focus_next_node`, and the Tab / Shift+Tab key-press check with exactly the focused control reading `focused`. Any of these that reads a shared table after this chunk must assert the same sequence, per task, in both layout modes.
- a11y-plan §3 (A11y testing tool pick) requires accessibility assertions to be Rust tests in blitz-tests over the AccessKit tree, and §1 (blitz-tests) records `accesskit` as a dev-dependency there with `blitz-dom` and `dioxus-native-dom` built with `accessibility`. A table typed with `accesskit::Role` therefore constrains where the one statement can live: a dev-dependency does not reach a crate's `[lib]` target, and §1 (Dioxus crates) records the seven_guis stand as naming no `accessibility` feature. Whether `tests/blitz-tests/lib.rs` or `seven_guis::stand` can hold a `Role`-typed table without a new dependency edge is research's question; the scope assumes no new edge.
- a11y-plan §2 (Feature exposure) records `accessibility_tree`, `snapshot`, `to_text`, `diff` and `unkeyed_actionable` as gated by dioxus-native-dom's `accessibility` feature. If the new test file lives in `packages/dioxus-native-dom/` and reads any of them, it must build with that feature on; whether the seven mutants' tests need any gated item is research's question.

## Patterns to follow
- Assert on the AccessKit tree the document returns: match nodes by role and name after resolve, mapping an element's `NodeId` to its AccessKit node id (per a11y-plan §3 A11y testing tool pick).
- Run every stand a11y assertion in both layout modes, per task (per a11y-plan §7 Accessibility tree output; §5 Test harness pattern).
- Prove focus through real input — a pointer click, a `Key::Tab` press, Shift+Tab — and read both the snapshot node's `focused` and the tree's focus (per a11y-plan §5 Test harness pattern; §7 Accessibility tree output).
- Read focusability and focus from the harness's existing queries rather than a new reader (per a11y-plan §3 Focus management test harness).

## Anti-patterns to avoid
- a11y-plan §11 (A11y Anti-Patterns) reads `> NO RECORDED INTENT`, so no recorded ban is extracted. The two below are derived from measured sections and are this extract's reading, not the plan's list.
- Sharing a table by narrowing it: dropping a control, a task, an input name or a layout mode from the role/name/focus assertions so the three checks come under the ceiling (against a11y-plan §7 Accessibility tree output).
- A shared helper that computes an expected role or name from the element (tag, attribute) instead of stating it, which would be a second role or name mapping on the test side mirroring the engine's (against a11y-plan §7 Accessibility tree output; §4 Per-component pattern catalog).
