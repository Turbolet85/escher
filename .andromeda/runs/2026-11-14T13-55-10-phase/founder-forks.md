## F1 — Which carriers reach exploration?
Exploration drives a held app breadth-first and leaves each path as a kept check. Today it would be reached:

- **A — In process only (Recommended, the provisional answer).** A Rust call, `escher_driver::explore`, used by tests and
  by in-process code that boots an app; no verb, role, argument, exit or span is added to the command line, MCP or the
  session socket. Why: it widens nothing, follows the start-in-a-state precedent (your C, inputs of that chunk), and a
  carrier can be added later as an addition, reusing the same entry. Trade-off: an agent over MCP or the command line
  cannot ask for an exploration yet.
- **B — A binary role, like `coverage`.** `escher-session explore <app> --budget <n> --record <dir>`: one process, a
  fresh in-process session per path, one stdout line of ids, closed words and counts. A boundary widening (a new role and
  answer on the command line).
- **C — A driver verb on every carrier.** `explore` the fifteenth verb, on the socket, the command line, MCP and in kept
  checks. The widest: a new verb, new argument kinds and a report answer on every ratified carrier.

## F2 — Does exploration follow navigation?
A step can navigate: a link click, Enter on a link, a form submission to another URL.

- **A — Follows none (Recommended, the provisional answer).** The held instance navigates only as its boot configured
  it; every harness-built session (the stand, the fixtures) has no navigation provider, so a navigating action loads
  nothing. Exploration drives such an action like any other, adds no provider and never switches documents. Why: no
  page, URL or file is loaded that the boot did not already load; nothing new crosses. Trade-off: a multi-page app is
  explored one document at a time.
- **B — Follows navigation within the app.** Exploration installs a navigation provider and explores the next document
  it names. A boundary widening: it loads documents the app's boot did not, and a navigation's URL becomes an input.
