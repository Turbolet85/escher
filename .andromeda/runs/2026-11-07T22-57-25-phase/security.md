@extract_section name=relevance
relevant: the graph read crosses the ratified driver carriers (session socket, CLI, MCP stdio, recorded checks), adds a snapshot field, reserves a new stable-id form and carries state values, so the widening, validation, masking and logging rules all bind it.
@extract_section name=constraints
- Widening rule: per security-plan §Input Validation (driver session socket, the widening rule), a new field of a closed value set inside an already ratified carrier is not a boundary widening, and a field holding authored text, an open value set, a new carrier or a new exit is one. The «reacts to a click» boolean in the snapshot and diff therefore falls on the not-widening side. A graph verb whose answer carries component names, handler event names or registered state names (open value sets) falls on the widening side, which makes it the founder's fork at P4. Whether the graph's content is closed or open is a planning question.
- Command schema: per security-plan §Input Validation (driver command schema), a new graph verb enters the closed `'static` table that `validate` checks (twelve verbs and seven bounded argument kinds today), and its refusals use the fixed order. Nothing public may run a `Command` that did not come from `validate`, and the socket, the command line and MCP all go through it. Nothing a call supplies may reach `unwrap`, `expect` or a panic, and no `NodeId` may be kept between calls.
- Stable element id: per security-plan §Input Validation (markup attributes, the stable element id), no HTML `id` may be able to make two ids equal, and no `NodeId` crosses any carrier. The reserved virtual-node form (`{canvas element}` + `{virtual key}`) must keep that guarantee against all four current forms. Keying the graph on the agent-visible node must not let a `NodeId` (`Target.node`) leave escher.
- Masking: per security-plan §Input Validation (markup attributes, masked values), a password's or file input's value reads as the fixed `MASKED_VALUE` on every carrier, never as its text, its length or a file's host path. Per security-plan §Data Protection (local user data handled), a file input's value holds a full host path that must not reach the snapshot, its text or a diff. Any state or control value the graph carries falls under both rules.
- Logging: per security-plan §Logging & Monitoring (escher's own sink), `escher_telemetry::init` redacts the content-named fields of `escher_` targets and drops records from non-allowlisted targets. Per security-plan §Input Validation (driver command schema), the one `command` span per call holds fixed words, bools and counts only, never a call's content. So no new log site, span field or print may carry a node, component name, handler, state or value, and the crate installs no subscriber and reads no env var.
- Recorded checks: per security-plan §Input Validation (recorded check), a recorded graph step is read by the strict, bounded `Check::from_bytes` (closed keys, schema-named arguments, anything else refused `malformed`, no panic path), and a replayed step still passes `validate` inside `Session::run`. Per security-plan §Data Protection (files, committed checks), a committed check holds no typed text, host path, name or secret.
- Refusals: per security-plan §Error Handling (escher-driver's command refusal), a refusal of the new verb is a typed `Refusal` from the closed cause set, with a fixed name, meaning and remedy, no `String` field and no path. MCP protocol errors use fixed codes and messages with no `data`.
@extract_section name=patterns
- Closed in-process readers: per security-plan §Input Validation (markup attributes), ARIA states and closed values are read through closed parses that carry no attribute text, with no log site and no panic path. The «reacts to a click» reading can follow the same shape.
- `MASKED_VALUE` / `MASKED_STAND_IN`: per security-plan §Input Validation (markup attributes, masked values), every carrier applies the same masking, including the snapshot, its text, diffs and kept checks.
- Bounded MCP results: per security-plan §Input Validation (MCP server), tool arguments are typed and then passed to `validate` / `validate_session`, results are bounded, and the request `id` is the one client-sent value written back.
- One gate for all carriers: per security-plan §Input Validation (CLI arguments, escher-session), `escher_driver::command_line` checks a call through `validate` before it asks for the session address. A new verb's CLI form reuses that path and its four fixed exit statuses.
@extract_section name=anti_patterns
- Per security-plan §Input Validation (driver command schema): never let a graph read run outside `validate` / `Session::run`, and never `unwrap`, `expect` or panic on anything a call supplies.
- Per security-plan §Error Handling (escher-driver's command refusal): never put a `String` or anything a call supplied into a `Refusal` or a `SessionError`.
- Per security-plan §Threat Model Summary (local stdio, the driver's MCP server): never assume a result stays local. What a client does with a result, sending it to a model provider included, is the client's, so the graph must carry no unmasked value.
@extract_section name=bindings
- obs: the escher-telemetry content-named field set and allowlist (security-plan §Logging & Monitoring) bind to obs's redaction rules for any new `escher_` span or event.
- tests: `NODE_FIELDS`, `describe()`, the schema help texts and every pin that counts them move with the new snapshot field. The committed stand-Counter checks (`tests/blitz-tests/checks/counter-cli.json`, `counter-mcp.json`) stay read only through `Check::from_bytes` (security-plan §Data Protection).
- arch: the reserved virtual-node id form and the move off `Target.node: NodeId` are contract changes. The widening call on the graph's carried content is the founder's fork at P4 (security-plan §Input Validation, the widening rule).
@extract_section name=acceptance
- Every new graph verb, outcome, MCP tool and recorded step goes through `validate`. A malformed or out-of-table call is refused as a typed `Refusal` with nothing run, and no `NodeId` appears in any reply, MCP result or kept check (per security-plan §Input Validation).
- A password or file input on a graphed screen reads as `MASKED_VALUE` in the graph answer, the snapshot text and diffs, never as the value, its length or a host path (per security-plan §Input Validation).
- No added log site, span field or print carries a node, component name, handler, state name or value. A host-log read during a graph call holds none of them (per security-plan §Logging & Monitoring).
- A reserved virtual-node id cannot equal any author-key, anchored, component or document-path id, whatever `id` attribute the document authors (per security-plan §Input Validation).
