# obs extract

## Relevance
partial — the chunk adds no telemetry of its own. It widens what a kept check holds (each answer kept whole). It also moves replay into CI and stand-repeat logs. Both touch obs-plan's never-logged rule, its scrub readings and its CI artifact rows.

## Constraints
- obs-plan §3 Logging stack (its `detail: absence · logs` block, the session-recording line) sets the bar for recording code: `stand_session_recording`, seven_guis `recording` and the `recording` module install no subscriber, read no env var and print nothing, and their readings go into assertions only. The kept check is written through the crate's `json` writer as a file at rest and is never a log line, field or print. A new replay target, a public replay API in escher-driver (if P4 makes one) and the extended `Check::from_bytes` reader must hold the same bar.
- obs-plan §4 Span / Trace Coverage requires that every call handed to `Session::run`, a replayed step included, opens one `command` span with its eight fields only, "a recording held or not". The never-fielded list there covers any `Outcome`, `Refusal`, argument and the screen text. So a step's kept `answer`, its `digest` and anything the replay compares must never become a span field. That section also records no span, event or line on the recording path (`Session::recording_into`, the recorder, `Check::from_bytes`). Whether a replay runner keeps that silence is P4's to decide; obs-plan states only the current absence.
- obs-plan §6 Log Coverage (Logged events, escher-driver) requires escher-driver's only stderr records to be the closed `command` and `tool_call` span lines, holding fixed words and counts. Each MCP call keeps one `tool_call` span with `tool` and `ending` alone, a recording-failed call ending `error`. Replaying a check over MCP must not add a third record class or a field.
- obs-plan §8 PII Scrubbing & Compliance (Values logged as-is) says screen content leaves only in its answer: 0 id, name and typed-sentinel needles, and 0 of a shot's base64 prefix, in the host's and the `mcp` role's stderr at `trace` under both builds. Once the F3 B widening keeps each answer whole at rest, the kept check holds ids, names, values, snapshot text and diffs. That content must still reach no log line.
- obs-plan §9 CI Integration (Recording directory row) states that a recording directory is local only, uploaded by no CI leg, written under `target/tmp/` by the checks, and holds "no screen reading". Kept checks committed to the repository and answers kept whole both contradict that row as written. It must be amended at the wrap, not left stale.
- obs-plan §9 CI Integration (Per-leg CI log row) states that each leg's merged output goes to `target/ci-logs/{leg}.log` and is uploaded as artifact `ci-log-{job id}` on failure, described as "unscrubbed build output (no user data — §8)". A red replay in `test` or `stand-repeat` writes its failure text there. What that text may name (step index, differing keys, answer content) decides whether the row's "no user data" still holds; that is a P4 question.
- obs-plan §6 Log Coverage (Log format, the agent-run harness) requires one `test` event per libtest result line, with nothing between `failures:` and the next `test result:` read. A replay target run by `agent-run.sh run stand` must keep its failure text out of `events.jsonl`, leaving it only in the never-printed `run.log`.

## Patterns to follow
- The silence probe over every new or changed test file and shared module, per obs-plan §3 Logging stack: `println!|eprintln!|print!|dbg!|std::env|env::var|escher_telemetry|tracing_subscriber|UnixListener|TcpListener|bind\(`, last line reading 0.
- The needle reading of a sink-installing binary at `RUST_LOG=trace` under both builds (`-p seven_guis` and `--workspace`), by `host_log` and `mcp_log`. Both drain both streams into assertions only, count the recording needles (the directory name and the kept check's contents) and leave the span counts unchanged (obs-plan §3 Logging stack, §8 Values logged as-is).
- The hand-written in-process `Recorder` in `stand_mcp_tools` (obs-plan §3 Logging stack) and `stand_act_spans`'s re-run children over an in-memory capture (obs-plan §4). These are the patterns for asserting that a replayed call's spans keep their fields and parentage without installing escher's sink in a check.
- When a check fails, it reports a kind and a count, never what the host wrote. This is `host_log`'s failure form (obs-plan §3 Logging stack), and a red replay that names "which step changed" should follow it.

## Anti-patterns to avoid
- Never field a kept `answer`, its `digest`, an `Outcome`, a `Step` or any argument on the `command` or `tool_call` span, and never print one with `Debug` (obs-plan §4 Span / Trace Coverage, its never-fielded list).
- Never log, print or field the kept check, its path or its recording directory, and never put the check in a span, an event or an agent-run event (obs-plan §3 Logging stack, session-recording line; obs-plan §6 Log format, agent-run harness).
- Never let a replay failure put answer content (ids, names, values, snapshot text) into a CI-uploaded log unexamined, because §9's "no user data" claim rests on it (obs-plan §9 CI Integration, Per-leg CI log row).

## Contract bindings
- obs ↔ tests (test-plan §3, agent-run contract): a `stand_*` replay target is picked up by `agent-run.sh run stand`. Its events carry `file` · `test` · `outcome` only, per obs-plan §6 Log Format (agent-run harness), and the harness state stays under `target/agent-run/`, per obs-plan §9 CI Integration (Agent-run harness state row).
- obs ↔ security (security-plan §Surfaces, the kept check's content): obs-plan §8's needle readings and §9's Recording directory row must state the same at-rest content as the security plan once the F3 B widening lands. The committed-check location is P4's question for both.
- obs ↔ CI (`ci-leg.sh` `stand-repeat`, `test`): the per-leg log and its failure-only artifact, per obs-plan §9 CI Integration (Per-leg CI log row).

## Acceptance criteria contributions
- Every new or changed replay test file and shared module, and escher-driver's changed `recording` module, reads 0 on the silence probe: no subscriber, no env read and no print, with readings going into assertions only (per obs-plan §3 Logging stack).
- `host_log` and `mcp_log`, run on a recording host and a recording `mcp` role at `RUST_LOG=trace` under both builds, read 0 recording needles. The needles now include the ids, accessible names and a typed sentinel held in the kept `answer` keys, and the `tool_call` and `command` span counts are unchanged (per obs-plan §8 PII Scrubbing & Compliance).
- A replayed call's `command` span records only its eight fields, and a replayed MCP call's `tool_call` span only `tool` and `ending`. No span line carries an answer's text, its digest or the check's path (per obs-plan §4 Span / Trace Coverage).
- obs-plan §9's Recording directory row and Per-leg CI log row are true after the chunk. Specifically, the row states where committed checks live and that kept answers hold screen readings, and a red replay's failure text in `target/ci-logs/{leg}.log` holds only what that row admits (per obs-plan §9 CI Integration).
