# a11y extract

## Relevance
partial — the chunk adds no UI surface, key binding, focus behaviour or painted colour, but each kept `answer` holds the snapshot's role, name, state and focus readings, and the new `stand_*` replay target joins the CI legs that already run the stand's a11y checks.

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary). The scope puts the engine and the eleven verbs' behaviour out of scope, so the chunk must leave each of those three criteria's stand readings where they are. If the "behaviour changed under it" witness alters a stand task, that change must stay inside a test-only variant and never reach a committed stand task.
- The stand's Tab sequences are stated tables (`tab_order`, `ENABLED_TAB_ORDER` in `tests/blitz-tests/tests/common/mod.rs`). `stand_keyboard` asserts them, together with Enter and Space on each stand button (per a11y-plan §5 Keyboard Navigation, Test harness pattern). A committed stand markup or order change made to give the replay a red witness would move those tables, so it is out of bounds for this chunk.
- `stand_contrast` asserts every stand control, text row and colour state row for row (18 control rows, `TEXT_ROWS` 14, `STATE_ROWS` 19) (per a11y-plan §6 Visual Design Verification, Color contrast). A behaviour-change variant must change no committed stand colour.
- The snapshot, its text, its diff and every driver and MCP result are readers of the accessibility model, each with no second role or name mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output). A kept `answer` is the driver's line as written, so it must be stored and compared as that line. It must not be re-derived or re-mapped.
- The same section requires a password or file input's value to read `MASKED_VALUE` wherever the model is read, with the typed text in no field (per a11y-plan §7 Screen Reader Support, Accessibility tree output). The new `answer` key inherits this reading. Whether the code already writes every kept answer through the masked reading is research's question.
- The `a11y` CI leg runs a fixed list of six test files with stated per-file counts (per a11y-plan §9 CI Integration). The same section records that the `stand_*` a11y files also run three times in `stand-repeat`. A new `stand_*` replay target joins `stand-repeat` by name or glob, and the a11y leg's file list and counts stay as stated unless a decision moves them.

## Patterns to follow
- The a11y checks are Rust tests in blitz-tests. Each one asserts in both layout modes, and their expectations are stated once in shared tables (per a11y-plan §3 A11y Assertion Harness Contract). Run the replay target the same way, `for incremental in [false, true]`. Whether today's `replay` helper in `tests/blitz-tests/tests/session_common/mod.rs` already does this is research's question.
- Stated tables are never a second mapping. `controls`, `INPUT_NAMES` and `REGION_NAMES` live in the stand checks' shared module beside `tab_order` (per a11y-plan §7 Screen Reader Support, Accessibility tree output). If a replay test asserts more than a step's digest or answer equality, it reads these tables.
- Keyboard through the driver is already proven: `stand_act_keys` presses `enter` and `space` on a Tab-focused `counter-increment` (per a11y-plan §5 Keyboard Navigation, Test harness pattern). A recorded CLI or MCP session that includes `press tab` / `press enter` steps would let the replay go red when focus order or keyboard activation changes. This is optional coverage, not a mandate.

## Anti-patterns to avoid
- Do not re-derive a kept answer's roles, names or state words from anything but the driver's written line, which would be a second role or name mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- Do not edit a committed stand task's markup, keys or colours to produce the red witness. That would move the asserted Tab-order and contrast tables (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
