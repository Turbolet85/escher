# a11y extract

## Relevance
partial — the chunk adds no UI surface, markup, focusable element or painted colour; a11y bears on it only where the schema's vocabulary meets the accessibility tree's readings: the `disabled` cause, the id an acting verb is addressed by, the role · name · state a result shape carries, the masked value, and the `accessibility` feature the driver crate does not name today.

## Constraints
- The tier is 0 with three criteria (SC 2.1.1 · 1.4.3 · 2.4.3), and focusability, focus order and painted colour are its surface; a schema-only chunk must leave all three as they are — no `tabindex`, role, markup or style edit on the stand rides along with a verb definition (per a11y-plan §1 A11y Scope Summary).
- Disabled-ness is keyed two ways in the engine — one reading on the attribute's presence, the other on its parsed value — so "disabled" and "not focusable" are different facts and a control can be the first without the second; the schema's `disabled` cause and its remedy text must name ONE of those readings and say which (per a11y-plan §5 Keyboard Navigation, Focus order).
- The snapshot's `enabled` follows the presence reading, read from the element because the tree gives an element node no disabled property; a `disabled` cause that an agent meets after reading a snapshot must agree with that `enabled` field, or the agent is refused on a control the snapshot called enabled. Which reading the cause takes is the plan's to state; whether any code already decides it is research's question (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- The identity an acting verb's id argument names is the stable element id every element node carries as AccessKit `author_id`; text-run, document-root and window nodes carry none, so they are not addressable and the argument shape must not admit a second identity for them (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- Role and name have one mapping — the tree's — and the snapshot, its text form and its diff are each stated as readers of it with no second mapping; a result shape that carries role, name or state must be a further reader of the snapshot model's fields, never a role or name vocabulary of the schema's own (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- A password input's value, and a file input's, read a fixed mask in the snapshot and the typed text or path appears in no field; any result shape or refusal text that can carry a control value carries that masked reading and has no field for the raw one (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- `escher-driver` names no feature of `dioxus-native-dom`, and the plan defers the choice to "the entry that first reads the snapshot through a session"; the snapshot model, its text form, its diff and the actionable-key check all sit behind that crate's `accessibility` feature. If this chunk's result shapes name those types, this chunk IS that entry and must decide the feature explicitly and record what the `escher-session` host then builds; whether the shapes need the types at all is the plan's question (per a11y-plan §1 A11y Scope Summary, Dioxus crates · §2 A11y Strategy, Feature exposure).

## Patterns to follow
- The remedy precedent: the actionable-key check returns each finding with its tag, its role and a remedy, reading focusability and role from readers the engine already has — a cause-with-remedy pair in the schema follows that shape rather than inventing a second one (per a11y-plan §7 Screen Reader Support, Accessibility tree output — the actionable-key rule).
- Expected roles, input names and rendered ids are stated once, as tables in the stand checks' shared module, and described as stated expectation, never a second mapping; a check of this chunk that runs against the held stand instance reads those tables instead of restating them (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- A check that reads `has_changes()` as "this call changed something" drains the changed set first — the set is non-empty on a freshly booted harness document, and settle neither reads nor drains it. This is the reading a "refused call leaves the instance as it was" check would rest on if it uses the flag (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- Focus order (SC 2.4.3) and keyboard operation (SC 2.1.1) are proven on the stand through key presses — Tab and Shift+Tab driven by the harness's `press` / `press_with`, in both layout modes. Whether the verb set holds a key-press verb is the plan's membership question; a set without one cannot express that proof through the driver, and that consequence belongs in the decision's record (per a11y-plan §5 Keyboard Navigation, Test harness pattern · §3 A11y Assertion Harness Contract, Keyboard test harness).
- Cause definitions lean on readings the engine already makes: an element excluded from the tree (the `hidden` attribute, `display: none`, `visibility: hidden`) has no node to address, while `aria-hidden` keeps the node and marks it hidden; hit-testing already excludes `visibility: hidden` targets and passes through `pointer-events: none`. "Not found" and "covered by another element" are worded against those, with detection left to "Refusal detection" (per a11y-plan §4 ARIA Patterns & Roles, Hidden content · §6 Visual Design Verification, Visibility and hit-testing).

## Anti-patterns to avoid
- A role enumeration, a name derivation or a state vocabulary defined inside the schema beside the tree's — a second role or name mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- Wording the `disabled` cause or its remedy in terms of focusability, or treating "focusable" as "enabled" — the two are keyed differently and diverge on `disabled="false"` and a bare `disabled` (per a11y-plan §5 Keyboard Navigation, Focus order).
- A result field or a refusal text that can hold a password's typed text or a file input's path (per a11y-plan §7 Screen Reader Support, Accessibility tree output).

## Contract bindings
- a11y ↔ tests: a stand-facing check of this chunk binds to the shared tables of the stand checks' module and to the both-layout-modes rule; the a11y CI leg runs three named test files and adds no stand assertion, so a new check lands in the workspace test leg, not the a11y leg (per a11y-plan §7 Screen Reader Support, Accessibility tree output · §9 CI Integration).
- a11y ↔ security: the masked-value reading binds to security-plan §Error Handling — what a refusal's text and a result may carry (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- a11y ↔ architecture: the feature decision binds to the driver session's row in architecture §Standard Contracts and to `escher-driver`'s manifest — naming `dioxus-native-dom`'s `accessibility` feature changes what the `escher-session` host builds (per a11y-plan §1 A11y Scope Summary, Dioxus crates).
- a11y ↔ a11y keyed contracts: §3's one keyed contract (bootstrap phases) is not turned on by this chunk; nothing is bound to it.

- (a11y) If any result shape carries a control value or names a snapshot type: the shape reads the mask for a password and a file input and has no raw-text field, and `escher-driver`'s manifest names the `accessibility` feature explicitly with the host's resulting build recorded; if no shape does, the report says so and the feature stays unnamed (per a11y-plan §1 A11y Scope Summary, Dioxus crates · §7 Screen Reader Support, Accessibility tree output).
