## Relevance
relevant — the chunk adds the first checks that drive a hosted instance through a binary, moves several statements the plan pins by test (the socket's grammar, the verb table, the host's stdout and stderr), and owes two standing proofs the plan names as unmeasured (test tier `0`, per test-plan §1 Test Scope Summary).

## Constraints
- A check that needs a session process starts and stops its own host, bounds every wait, holds the host behind a kill-and-reap guard, removes its state directory at `stop`, sends the child's streams to null unless it reads them, and is `cfg(unix)`-gated (per test-plan §2 Test Strategy → Process-lifecycle checks; per test-plan §3 Session lifecycle → `session-checks`). The windows and macOS matrix legs run every test target (per test-plan §1 Test Scope Summary → Surfaces under test, Native platforms), so the shell-flow check is gated like the other host checks; whether the flow script runs as written on the macOS runner is research's question.
- Where the CLI binary lives decides which runner reaches its checks: a check reaches a real binary only as its own package's, through `CARGO_BIN_EXE_*` (per test-plan §2 Test Strategy → Process-lifecycle checks), while `agent-run.sh run stand` selects `tests/blitz-tests/tests/stand_*.rs` alone and the seven_guis host checks are run per package (per test-plan §3 Agent-run contract → `run`; per test-plan §1 Test Scope Summary → apps (rdme, bump, examples, accesskit_xplat)). The plan chooses the binary's home with that in view.
- The two runners build the same check against different engine features — the workspace leg compiles blitz-dom's `tracing` call sites in and selects another body of the bounds reader, the per-package build neither — so the typed-sentinel proof is read under both builds, a sink capture is counted by target and never in total, and a per-package green is not the workspace leg's green (per test-plan §9 CI Integration → Engine features by runner). That section states the seven_guis binaries' stderr by level under the workspace build as not measured: that reading is this chunk's to take, and what it holds is research's question.
- No check sleeps or reads a wall clock; time on a hosted Timer moves only by `advance` through the stand's step, in whole ticks with the remainder dropped per call, and what is reported is the time delivered, not what the display gained (per test-plan §5 Integration Test Strategy → Session ↔ held instance; per test-plan §8 Mocking & Stubbing Discipline → Time (seven_guis timer)).
- The in-process driver checks run in both layout modes and hold a returned diff equal across them (per test-plan §5 Integration Test Strategy → Session ↔ held instance); the in-process proof of every stand screen under `SNAPSHOT_TEXT_BUDGET` is `stand_snapshot_text` (per test-plan §1 Test Scope Summary → tests/blitz-tests), and the snapshot command's proof of the same cap sits beside it. The plan states no layout-mode requirement for a check through the host binary; whether the host can be booted in the other mode, and whether the CLI's proof needs it, is research's question and the plan's choice.
- The closed tables are pinned by unit tests that go red by design when the tables move: schema.rs holds the verb table to six verbs in a stated order with each argument and result shape, wire.rs holds the lifecycle grammar to its two requests and its line bounds, and the section states that no test drives the schema over the socket (per test-plan §4 Unit Test Strategy → escher-driver; per test-plan §3 Session lifecycle → `session-wire`). Lifecycle commands entering the one table, and any growth of the wire, restate those tests' stated tables and row counts in the same change; whether the crossing uses the socket's grammar at all is the plan's. escher-driver names no virtual DOM, so a unit test cannot build a held instance — a JSON form is unit-tested over built values, anything needing a screen in `stand_*` or the seven_guis tests (per test-plan §1 Test Scope Summary → escher-driver).
- `escher-session` is pinned to an empty stdout on every path and to a stderr-only, uncoloured log by `host_binary` and `host_log` (per test-plan §3 Session lifecycle → `session-binary`; per test-plan §3 Test Harness Contract → Stand log format). A command answering on stdout is either another binary or those assertions restated — the plan's choice; and a host that runs driver commands writes the command span's line, which that section states neither binary writes today, so `host_log`'s line and needle readings are re-derived, not assumed.

## Patterns to follow
- The shared session helpers — a short state directory under `CARGO_TARGET_TMPDIR`, `clear`, `host_command`, the `READY` and `EXIT` bounds, the `Host` guard, the call builders and the `act` · `refused` · `refused_unchanged` · `focused` readers in `tests/session_common/mod.rs`, and seven_guis' `tests/common/mod.rs` for checks on the real binary — are extended, not restated per file (per test-plan §3 Test Harness Contract → Crate-local test helpers, blitz-tests (session checks); per test-plan §3 Session lifecycle → `session-state`, a socket path leaves about a hundred bytes).
- `host_log` is the shape of a proof on a sink-installing host: needles read from the stand booted in the test's own process, each stream drained by a thread from the spawn on, the session reached with `attach` under a bound, and a failure printing a kind and a count only (per test-plan §5 Integration Test Strategy → Session host ↔ what it writes). The typed-sentinel proof extends it.
- A table is stated in its test with its row count asserted, every assertion over a call carries a row index only, and each new named test is turned red by a mutation control and read green on the restored tree (per test-plan §4 Unit Test Strategy → escher-driver).
- A new `tests/blitz-tests/tests/stand_*.rs` file is picked up by `run stand` through its prefix with no script change, and the run's `run.end` counts are re-read after it lands (per test-plan §3 Agent-run contract → `run`; per test-plan §3 Agent-run contract → Proof).
- The standing exit grammars are precedent for decision 4's options, not an answer to it: `escher-session` exits `0` after `stop`, `1` on an error with its message on stderr and `2` on any other argv with nothing booted (per test-plan §3 Session lifecycle → `session-binary`), and the agent-run script checks usage before any precondition (per test-plan §3 Agent-run contract → Exit grammar, every verb). A shell script that becomes a standing check has the contract-test shape of `test_agent_run.py` — run in a temp dir against a shim on PATH (per test-plan §4 Unit Test Strategy → Agent-run contract).

## Anti-patterns to avoid
- Waiting for a sink-installing host to exit before reading its pipes, or letting a child's own libtest lines reach the parent's output, where `agent-run.sh` counts them as tests; and adding an `#[ignore]` host child without noting that a bare `--ignored` run blocks on it (per test-plan §2 Test Strategy → Process-lifecycle checks).
- Reading a zero from a host that installs no log sink as a statement about one that does, or the in-process capture as the binary's own stderr (per test-plan §3 Session lifecycle → `session-checks`; per test-plan §5 Integration Test Strategy → Session host ↔ what it writes).
- Counting a capture's lines in total, or closing the chunk on a per-package green (per test-plan §9 CI Integration → Engine features by runner); and reading an empty run as a pass (per test-plan §3 Agent-run contract → `run`).

## Contract bindings
- tests ↔ obs: the stand log format — stderr only, no ANSI, one line per event and one per closed span, the target allowlist — is obs-plan §3 and §6 Log format, with the by-level and typed-text readings in obs-plan §8; the test side is `host_binary`, `host_log`, the `telemetry_*` files and `stand_act_spans` (per test-plan §3 Test Harness Contract → Stand log format). A hosted `type` is where the plan says typed text is first measurable on a binary's own log.
- tests ↔ architecture: the session checks drive the contract of architecture §Standard Contracts → Driver session; the keyed contract's seven labels restate it for tests, and `session-wire` and `session-binary` move with whatever decisions 1, 2 and 4 settle (per test-plan §3 Session lifecycle).
- tests ↔ security: no assertion message, test name or failing log carries an id, a name, a value or a call-supplied argument — row index, kind and count only (per test-plan §4 Unit Test Strategy → escher-driver; per test-plan §5 Integration Test Strategy → Session host ↔ what it writes) — the test-side half of the security plan's rule on what a refusal and a log may hold.
- tests ↔ CI: if the flow becomes a leg or a script under `.github/scripts`, the leg must be in `ci-leg.sh`'s list and the workflow invariants and the `ci-scripts` leg's count move with it (per test-plan §4 Unit Test Strategy → CI workflows and leg script; per test-plan §9 CI Integration → Legs).
- tests ↔ agent-run harness: the agent-run script starts and binds nothing; a session host and its socket are a surface of the session library and of the checks that start them, not of that contract (per test-plan §3 Agent-run contract → Invocation; per test-plan §3 Agent-run contract → State).
