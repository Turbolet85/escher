# a11y extract

## Relevance
partial — the chunk adds no markup, style, token or focusable element (no SC 1.4.3 surface), but its commands carry the accessibility-derived snapshot (role · name · state · focus) out of the process, drive focus and keys on a hosted instance (SC 2.1.1 · 2.4.3 as read, never as changed), and decision 6 may expose the actionable-key check.

## Constraints
- a11y-plan §1 A11y Scope Summary (A11y tier) sets the target at tier 0 — SC 2.1.1 · 1.4.3 · 2.4.3; a command-line surface must leave focusability, focus order and painted colours of every stand task as they are — the CLI reads and drives them, it changes none.
- a11y-plan §7 Screen Reader Support (Accessibility tree output — the snapshot-model bullet) requires that the snapshot, its text form and its diff take role, name and focus from the tree `accessibility_tree` returns, with no second role or name mapping; a JSON form of an outcome (decision 4, either option) is one more reader of that model and is bound by the same rule. Whether the plan's chosen JSON form reads the model only is research's question.
- a11y-plan §7 Screen Reader Support (Accessibility tree output — the snapshot-model bullet) requires `enabled`, `checked` and `value` to be read from the element as that bullet states them, a password's or a file input's value as the fixed mask `MASKED_VALUE` with the typed text in no field; a command's stdout that carries `value` must carry the mask, never the text behind it.
- a11y-plan §7 Screen Reader Support (Accessibility tree output — the snapshot-model bullet) requires the driver's `disabled` refusal to rest on the snapshot's presence reading of `disabled` and on no other, with nothing dispatched and focus unchanged; a refused command's JSON and exit code must report that reading, not a second disabled-ness test at the CLI.
- a11y-plan §5 Keyboard Navigation (Focus order per layout) defines focusability and the Tab / Shift+Tab order, and notes the two keyings of disabled-ness (state and click target by presence, focusability by parsed value); a `press` reaching a hosted instance must move focus by that order, and a shell flow must not assume a control reading not enabled is unfocusable.
- a11y-plan §7 Screen Reader Support (Accessibility tree output — the actionable-key rule) requires every element an agent can act on to read an author key, checked by `DioxusDocument::unkeyed_actionable` with no second role mapping; if decision 6 exposes it, the command is a wire form of that one check, not a re-implementation.
- a11y-plan §1 A11y Scope Summary (A11y scope — Dioxus crates) records the `accessibility` feature's reach into the stand's binaries through `escher-driver` and that no platform adapter is in their graph; a new CLI binary, crate or dependency edge is a change to that record and its graph is re-measured. Whether the chunk's binary changes the reach is research's question.

## Patterns to follow
- Stated-expectation tables: a11y-plan §7 Screen Reader Support (Accessibility tree output — the `author_id` bullet) names the stand checks' shared tables (`controls`, `INPUT_NAMES`, `rendered`) as the single statement of expected roles, names and ids; a check of the CLI's output reads those tables rather than restating a role or a name.
- Focus proven three ways: a11y-plan §5 Keyboard Navigation (Test harness pattern) describes the stand's key-press focus check — click, Tab, Shift+Tab, exactly one node reading `focused` and it being the tree's focus; a hosted-command focus check follows that shape through `click` and `press`.
- Both layout modes: a11y-plan §7 Screen Reader Support (Accessibility tree output) states its stand readings in both layout modes; the scope notes the host boots one mode — whether the CLI's a11y-facing proof needs both is the plan's question, answered against this pattern.
- Drain before reading change: a11y-plan §2 A11y Strategy (Accessibility tree lifecycle — the changed-set bullet) states a settle neither reads nor drains the changed set and that a freshly booted document reads non-empty; a hosted command that reports "changed" takes it from the snapshot diff, never from `has_changes()`.
- State as text beside colour: a11y-plan §6 Visual Design Verification (State color) records status printed as a word alongside its colour; the CLI's uncoloured stdout carries accepted / refused and a refusal's cause as words, which is that pattern with the colour removed.

## Anti-patterns to avoid
- a11y-plan §11 A11y Anti-Patterns reads NO RECORDED INTENT; nothing is drawn from it. The bans below follow from measured sections.
- A second role, name or state mapping in the JSON producer or in a CLI check — banned by the single-reader rule of a11y-plan §7 Screen Reader Support (Accessibility tree output — the snapshot-model bullet).
- Reporting a text change as a text-run entry, or a diff entry without the element's stable id — a11y-plan §7 Screen Reader Support (Accessibility tree output — the snapshot-model bullet) requires a text change to be reported on the element whose accessible name it changes.
- Adding the stand flow or a CLI check to the `a11y` CI leg as if it were a stand a11y assertion — a11y-plan §9 CI Integration states that leg runs three named test files and adds no stand assertion.

## Acceptance criteria contributions
- (a11y) For each hosted stand task, the `snapshot` command's output gives every node the role and name its accessibility node holds, checked against the shared stand tables, and no node reads focused at boot (per a11y-plan §7 Screen Reader Support — Accessibility tree output).
- (a11y) A hosted `click` or `type` on a control reading not enabled (`crud-delete`, `flight-return-date`) exits refused with cause `disabled`, and a following `snapshot` reads the same focus as before the call (per a11y-plan §7 Screen Reader Support — Accessibility tree output).
- (a11y) A hosted `press` of Tab on a fresh boot returns a diff in which exactly `back-btn` gains `focused`, and Shift+Tab after a Tab names exactly the controls whose focus moved (per a11y-plan §5 Keyboard Navigation — Test harness pattern).
- (a11y) If decision 6 exposes the actionable-key check: its command returns no element on each of the four hosted lean tasks, from `DioxusDocument::unkeyed_actionable` and no other reader (per a11y-plan §7 Screen Reader Support — Accessibility tree output, the actionable-key rule).
