# obs extract

## Relevance
partial — obs tier 0 (per obs-plan §1 Obs Scope Summary); the chunk adds a binary whose stdout is an answer and whose stderr is the sink's, makes a sink-installing host run driver commands for the first time, and owes the typed-text measurement in that host's log (obs-plan §2 · §3 · §4 · §6 · §7 · §8 · §9). No metric, SLO or OTel work: §5 records none for the driver, §10 and §11 read `NO RECORDED INTENT` and are not cited.

## Constraints
- **Sink install on every escher binary, stderr only.** obs-plan §3 → Logging stack (subscriber installation) requires an escher binary to install `escher_telemetry::init(escher_telemetry::service_identity!())` first thing in its native `main` — before argv is read — to report an `Err` on stderr and continue, and to write nothing to stdout on any path. A CLI binary is a third install site under that rule; whether the chunk's binary is a new one or a grown `escher-session` is the plan's, and either way the count of install sites §3 states changes.
- **stdout carries no sink byte; the sink is uncoloured.** obs-plan §6 → Log format (escher's sink) requires one line per event and per closed span on stderr with no ANSI, levels from `RUST_LOG` defaulting to `warn`. The chunk's "uncoloured JSON on stdout, nothing else there" therefore requires that no sink line, at any `RUST_LOG` setting, lands on the CLI's stdout — and that the CLI's stdout is not the host's stdout or stderr by inheritance. Where a CLI-started host's two streams go is not stated by the plan: it is research's and the plan's question.
- **The command span stays `run`'s, eight fields, fixed words and counts.** obs-plan §4 (the `packages/escher-driver` entry) requires one `escher_driver` / `command` span per call handed to `Session::run`, opened before `validate`, with `verb` · `cause` · `settled` · `busy` · `passes` · `added` · `removed` · `changed` and nothing else. The span is emitted in whichever process calls `Session::run`; if the call crosses to the host, that is the host's stderr, not the CLI's. Which process emits it, and whether a lifecycle command added to the one verb table passes through `run` (and so records a `verb` word the table must then hold), is research's question.
- **No span or event is mandated for the crossing.** obs-plan §4 records `serve`, `start`, `attach`, `stop`, the lifecycle wire and `Harness::settle` as carrying no span of their own and states no requirement to add one. If the plan adds a record for a call arriving or an outcome leaving, obs-plan §4's field rule applies to it unchanged: schema words, bools and counts only.
- **The escher scrub set does not cover what a call carries.** obs-plan §8 → Scrubbing requires an `escher_*` target's fields to print except a fixed content-named set; of the driver's argument names only `text` is in it (obs-plan §4). An `id`, a `key`, an accessible name, a session label or a state-directory path fielded under any other name on an `escher_*` target would print whole — so the chunk's new code in the CLI, the host and the wire adds no field holding what a call supplied or a screen read.
- **`Debug` of the driver's values is content.** obs-plan §3 → Logging stack (subscriber installation) records that `Command`, `Call`, `ArgValue` and `Outcome` print ids, typed text, names and values under `Debug` and requires that nothing prints, logs or fields any of the four. The CLI's stderr diagnostics (usage, a tool error, a wire error) are bound by that: a JSON form on stdout is the answer, a `{:?}` of the same value on stderr is a log.
- **The panic path is past the scrub.** obs-plan §7 → Panic hooks and obs-plan §8 → Values logged as-is require the reader to assume the chained std hook prints a raw panic message to stderr and leaves the exit code unchanged. A panic, `expect` or `unwrap` message in the CLI's argv parsing, the wire decoding or the JSON writing that formats call-supplied or screen-read content would reach stderr unscrubbed; and a panic's exit status is one more ending for the chunk's exit-code table (scope decision 4).

## Patterns to follow
- The host's own stderr lines are fixed strings holding no path, label, id or value, with a usage ending and a failed-start ending told apart by exit status (per obs-plan §6 → Logged events, the examples entry for `escher-session`). The CLI's non-sink diagnostics follow that shape; whether the host's existing statuses constrain the CLI's exit-code table is research's question.
- A check that spawns a sink-installing binary drains both streams from the spawn on, reads them into assertions only, and on failure prints a kind and a count — never what the binary wrote (per obs-plan §3 → Logging stack (subscriber installation), the `host_log` and `host_binary` readings). The typed-sentinel check and the timer-host check take this shape; `host_log` is the standing check to extend.
- The by-level reading is a fixed table: stderr lines and stdout bytes at four `RUST_LOG` settings, with id needles, name needles and the supplied texts counted (per obs-plan §8 → Values logged as-is). The host-that-runs-commands reading extends the same instrument rather than inventing a second one.
- A session state directory holds the socket file alone while a session is up and nothing after `stop`; no log, event or screen content is written into it (per obs-plan §9 → Telemetry artifact handling, the Session state directory row). An answer to the orphaned-host decision that writes a registry, a pid or a log there changes that row and is stated, not silent.
- `service.name` is the package's, so two binaries of one package read alike in a log line (per obs-plan §3 → Service identity and line format). If the CLI and the host must be told apart on stderr, that follows from where the binary lives, not from a new field.

## Anti-patterns to avoid
- Fielding an argument by its schema name, or a `Command`, `Call`, `Outcome`, `Refusal` or `Fault` with `Debug`, on the command span or any new record (per obs-plan §4, the never-fielded list).
- Reading a zero from a child that installs no sink as proof of absence: a `RUST_LOG` set on such a child is inert and its zero says nothing about a host that installs one (per obs-plan §3 → Logging stack (subscriber installation), the `stand_session_quiet` reading). The sentinel proof is read on the real `escher-session` binary, with its sink installed, at `trace`.
- Installing `tracing_subscriber::fmt::init()` or any stdout subscriber in the CLI or the host: it writes to stdout and is unscrubbed (per obs-plan §3 → Logging stack (subscriber installation), the upstream apps' line; obs-plan §8 → Scrubbing, its reach).

## Contract bindings
- **obs ↔ security** — the first hosted `type` discharges or fails the measurement obs-plan §8 → Values logged as-is records as owed ("typed text in a host's log"); it binds to security-plan §Input Validation and to the crossing asked as scope decision 1. obs-plan §8 governs logs only: what the JSON on stdout may carry is security's and the founder's, not this extract's.
- **obs ↔ tests** — obs-plan §2 → Feature wiring binds to test-plan §9 (Engine features by runner): the workspace-wide build compiles blitz-dom's `tracing` call sites in, the package-alone build does not, and the two seven_guis binaries' stderr by level under the workspace build is recorded as not measured. The sentinel proof is therefore read under both builds and counts nothing by line where they differ (scope CARRY 11).
- **obs ↔ tests (harness log)** — a new check reaches the agent-run contract as one `test` event per libtest result line, with captured output never read into an event (per obs-plan §3 → Agent-run harness log; obs-plan §6 → Log format (the agent-run harness)); a shell-flow check that runs outside libtest has no event form there, which is tests' to place.
- **obs ↔ tests / CI** — a leg's merged stdout and stderr is written to `target/ci-logs/{leg}.log` and uploaded on failure (per obs-plan §9 → Telemetry artifact handling, the Per-leg CI log row): what a failing flow check prints lands in an uploaded artifact, so it prints kinds and counts, not a captured stream.
- **obs ↔ architecture** — a new binary or crate is a new row in obs-plan §1 → Instrumentation scope and a new install site in obs-plan §3 → Logging stack (subscriber installation), beside its arch §Occupied Resources registration.
- **obs keyed contract** — obs-plan §3 Bootstrap phases (derive for route / setup-project): `pii-scrubbing-wire` states its discharge for the binaries that install the sink, so a further sink-installing binary extends the reach that key names; `otel-sdk-install` requires no OTel crate, no egress and no exporter credential path in 0.1.0, which the CLI keeps.
- **Plan statements the chunk would make stale (for the wrap)** — obs-plan §2 → Telemetry mechanism (the command span "reached by no code path" in either binary), obs-plan §6 → Logged events (which processes run a command under the sink; the host's wire), obs-plan §8 → Values logged as-is (the host-log measurement) and obs-plan §3 → Logging stack (the install-site count). Whether each is in fact made false is read from the built code, not from here.

## Acceptance criteria contributions
- With a hosted `type` of a sentinel string run through the CLI, the sentinel occurs 0 times in the `escher-session` binary's stderr at `RUST_LOG=trace`, read in a package-alone build and in the workspace-wide build, engine lines included (per obs-plan §8 → Values logged as-is; obs-plan §2 → Feature wiring).
- At `RUST_LOG` unset, `info` and `trace`, every CLI command's stdout parses whole as its JSON answer and holds 0 sink lines and 0 escape sequences; sink lines appear on stderr only (per obs-plan §3 → Logging stack (subscriber installation); obs-plan §6 → Log format (escher's sink)).
- In the process that runs `Session::run` for a hosted command, at `RUST_LOG=info` each command leaves one closed-span line whose own fields are a subset of the eight, and the stderr of both the CLI and the host holds 0 id needles, 0 name needles and 0 occurrences of any call-supplied text at `info`, `debug` and `trace` (per obs-plan §4; obs-plan §8 → Scrubbing).
- At `RUST_LOG` unset an accepted command leaves 0 sink lines on the stderr of the CLI and of the host (per obs-plan §6 → Log format (escher's sink); obs-plan §4) — whether any non-sink diagnostic is printed on an accepted command is research's question.
