## Constraints
- **The crossing is a boundary widening, asked before it is built.** security-plan §Threat Model Summary (Attack surface → local IPC — the driver session's socket) requires the wire to be the lifecycle only and to carry no element id, accessible name, control value, snapshot text or diff, and records the socket itself as a widening that stood on the founder's choice. A call going in and an outcome coming out contradicts that row as written, so the plan requires the founder's ratification and an amendment of that vector (and of the rows named below) before any code carries one. The earlier "returned to its caller only" answers are scoped to in-process returns and do not cover this chunk (per security-plan §Input Validation → Markup attributes, `id` (stable element id) row).
- **Whatever form carries a call keeps the socket row's discipline.** security-plan §Input Validation → Driver session socket (escher-driver) row requires a closed grammar, a stated byte bound on a request and on a reply, a version check, a refusal that changes nothing, a read and write time bound and one connection at a time. The bounds that row states were sized for lifecycle messages; a call's `text` argument and a snapshot's text exceed them, so the plan must state the new bounds explicitly rather than lift the old ones silently. Whether the wire code as built can be grown inside that discipline, or needs another form, is research's question.
- **Every call that arrives from outside passes `validate` first, through the one table.** security-plan §Input Validation → Driver command schema (escher-driver) row requires a closed verb table, five argument kinds each with its bound, one fixed refusal order, no `unwrap` / `expect` / `panic!` / `unreachable!` / index on anything a call supplies, and nothing public running a `Command` that did not come from `validate`. That row names this check as the one every later surface's input passes through; the argv-to-`Call` step and any wire decoding in the host are new input paths in front of it and owe the same no-panic, typed-result rule. Lifecycle commands join that table; no second table is stated.
- **Access is the filesystem's and nothing else — and it now guards content.** security-plan §Authentication & Authorization → Local IPC access (driver session socket) row requires an owner-only state directory and socket file, records that there is no handshake, token or peer-credential check, and records that `start` does not check the answering pid is the child it spawned. With screen content on the wire the file modes are the only guard for it; any answer to "how a session is started and addressed" (decision 2) must keep those modes and must not add a credential path without an amendment. Whether the unchecked pid matters once commands cross is research's question.
- **A session's address stays a caller-named path with the state-directory checks.** security-plan §Input Validation → Driver session state directory (escher-driver) row requires the directory's mode checks, the refusal of a directory open to group or others, the too-long-path and already-running edges, deletion limited to the socket file and the directory (non-recursive), and the path as a parameter — never an env read or a cwd-relative default. A CLI that names sessions any other way (a default location, a registry of sessions, a list command for decision 5) is a new surface that row does not cover and needs its own amendment. security-plan §API Security → Local session socket (escher-driver) row records that a host whose client died keeps running with no idle expiry; whichever answer decision 5 takes is recorded there.
- **The masks hold through every form the output takes.** security-plan §Input Validation → Markup attributes, password and file `input` value (the snapshot's `value`) row requires a password's or a file input's value to read as the fixed mask — never the text, its length or a host path — in the snapshot, its text and a diff; security-plan §Data Protection → Local user data handled requires the same of a chosen file's path. A JSON view of the model (decision 4) must be built from the snapshot model, not from the DOM, so the mask cannot be bypassed. Whether the code path chosen for JSON reads only the model is research's question.
- **stdout is the answer; no log gains content.** security-plan §Logging & Monitoring → Log format and backends (escher's own sink) requires a sink-installing binary's stderr to carry no stable id and no accessible name at any `RUST_LOG` level and records typed text in a sink-installing host's log as still not measured — this chunk owes that measurement. The driver's one log record stays the command span with its eight fixed fields, and no `Command`, `Call`, `ArgValue`, `Outcome`, `Refusal`, `Fault`, argument, screen text or label is ever fielded (per security-plan §Input Validation → Driver command schema (escher-driver) row). A CLI binary that installs the sink installs it stderr-only.

## Patterns to follow
- **Closed argv, refuse before anything runs.** A fixed argument count and a closed table of accepted words; anything else prints a usage line on stderr and exits with the usage status having booted nothing and created no state; an error's message is fixed text with no path, label, id or value in it (per security-plan §Input Validation → CLI arguments (escher-session) row; the same shape in the CLI arguments (agent-run.sh) and (cold-agent.sh) rows). The escher-session row also requires that binary to write nothing to stdout on any path — whether the host binary keeps that property once commands reach it, with all answers printed by the client process, is the plan's to state.
- **A refusal is a typed value from a closed set.** A refusal's JSON form is produced from the cause's fixed name, meaning and remedy and, beside `malformed`, the schema's own argument name — it cannot hold anything a call supplied, because none of `Cause`, `Fault` and `Refusal` has a `String` field (per security-plan §Error Handling → Error format (typed errors), the escher-driver command refusal). A session edge and a usage error get the same treatment: fixed text, no echo of the caller's input.
- **A refused request changes nothing, and what is recorded about a call is metadata only.** The stub pattern — a named cause, no state change, a call log that never holds an argument value (per security-plan §Input Validation → Cold-agent MCP stub (cold_agent_stub.py) row) — is the model for a host that now answers commands.
- **Session-lived state is bounded.** The record of ids is bounded by count only and the plan records that nothing bounds it in bytes and no test exercises it (per security-plan §Input Validation → Markup attributes, `id` (stable element id) row); a hosted, long-lived session is where that gap becomes reachable, so decision 8's bound lands with a check. No command waits on a load and time moves only by `advance`, within its stated range (per security-plan §API Security → Settle and loads in flight row).
- **A new dependency enters under the existing gates.** A serialization or argument-parsing crate, if one is added, is declared through the workspace manifest, built `--locked`, reviewed by hand (licence, repository, build script, proc-macro flag, direct dependent) and read by the audit leg; an advisory is fixed or ignored by ID with a written reason (per security-plan §Dependency Security → Audit tool and → Pinning).

## Anti-patterns to avoid
- security-plan §Security Anti-Patterns reads `NO RECORDED INTENT`; nothing is cited from it. The bans below come from the sections named on each.
- Never print, log or field a `Call`, `Command`, `ArgValue`, `Outcome`, `Refusal` or `Fault` — their `Debug` forms hold ids, typed text, names and values — and never put any of that in a test name or an assertion message; the JSON on stdout is written by a deliberate form, not by `Debug` (per security-plan §Input Validation → Driver command schema (escher-driver) row).
- Never let a process-local handle cross: no `NodeId`, `ElementId`, `ScopeId`, AccessKit id or pointer in any wire or JSON form — and if the actionable-key check is exposed (decision 6) its output is a second crossing for ids that must leave `UnkeyedActionable.node` behind (per security-plan §Input Validation → Markup attributes, `id` (stable element id) row).
- No new env read, credential, listener or port: source reads no secret and its env reads are a closed list (per security-plan §Secret Management → Environment values read); the one listener is the session's local socket and no served network API exists (per security-plan §API Security, opening paragraph).

## Contract bindings
- **security ↔ architecture** — the socket's grown wire, any new binary, workspace crate or dependency, and how a session is addressed are §Occupied Resources and §Standard Contracts (Driver session) registrations that must agree with the amended security-plan rows (§Threat Model Summary local IPC vector; §Input Validation Driver session socket, state directory and command schema rows; §API Security Local session socket row).
- **security ↔ observability** — the typed-sentinel measurement in the host's stderr and the "no content in a log" rule bind to obs-plan's account of what a command-running host's stderr carries; the sink's scrub and drop rules are the shared contract (security-plan §Logging & Monitoring → Log format and backends).
- **security ↔ tests** — the proofs land in the standing checks the plan names (`host_log`, `host_binary`, the session-lifecycle keyed contract) and no real secret or host path enters a fixture or committed evidence (security-plan §Secret Management → Never in code); the dependency audit is a CI leg (security-plan §Dependency Security → CI integration).
- **security ↔ a11y** — only if decision 6 exposes the actionable-key check; then its output form is bound by the `id` row above.

## Acceptance criteria contributions
- (security) A sentinel typed through the hosted `type` command occurs 0 times in the `escher-session` binary's stderr at `RUST_LOG=trace`, read both in a per-package build and in the workspace leg's build, with no stable id and no accessible name in it either (per security-plan §Logging & Monitoring → Log format and backends, escher's own sink).
- (security) A password typed through the CLI reads the fixed mask in the command's stdout JSON, and the typed text occurs 0 times in everything the command writes to stdout and stderr (per security-plan §Input Validation → Markup attributes, password and file `input` value (the snapshot's `value`) row).
- (security) A request outside the wire's grammar or over its stated bound, and an argv outside the command's closed form, are each refused with nothing run — the held instance's screen reads the same before and after, no process panics, and the refusal or error text holds nothing the caller supplied (per security-plan §Input Validation → Driver session socket (escher-driver) row and → Driver command schema (escher-driver) row).
- (security) If a dependency is added, `bash .github/scripts/ci-leg.sh audit` reads `advisories ok` on the new lock with no blanket allow and no ignore added without a written reason, and the build stays `--locked` (per security-plan §Dependency Security → Audit tool).
