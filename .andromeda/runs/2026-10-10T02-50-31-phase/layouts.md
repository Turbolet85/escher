## Relevance
partial — the chunk adds a screen to the plan's `cli` surface and drives the headless stand mount of `desktop-native` without touching its markup; the plan holds no row for a driver command line, both surfaces' headers mark tooling context, expression level and signature placement `NOT YET MEASURED` (nothing is extracted from those facets), and §Decisions Log reads `NO RECORDED INTENT` (nothing extracted).

## Constraints
- The session host's command-line contract stands unless the chunk amends it: layout-templates §Surface: cli → Primary screens (the `escher-session` row) requires a closed argv of exactly two arguments, the usage line on stderr with exit 2 on any other argv having booted nothing and created no state, exit 0 after a stop and 1 with an error's fixed message on stderr, nothing on stdout on any path, and unix only in 0.1.0. A chunk that makes the host run commands either keeps each of these or restates the row; whether the code holds each of them today is research's question.
- The host stays a consumer of the stand's mount, not an author of it: layout-templates §Surface: desktop-native → Primary screens requires that the host boot one lean task through the stand's own boot only and add no markup, id, class, style, wrapper or order, that a held instance read as a fresh boot, and that the TaskShell mount and the pinned viewport hold after commands in both layout modes. Commands that arrive from another process fall under the same requirement; whether the existing check of it covers commands that cross a process boundary is research's question.
- A flow addresses the stand by the ids the plan lists: layout-templates §Surface: desktop-native → Primary screens requires each lean task's controls and value displays to carry author ids that are their stable element ids, and each CRUD row to carry an id that follows its person under filter, Create and Delete. A shell-scripted flow names targets from that list and needs no new id; an id the flow wants and the list lacks is a markup change this chunk's scope excludes.
- Bounds a command prints are read at the pinned viewport: layout-templates §Surface: desktop-native → Primary screens requires the headless stand to mount at one fixed viewport size, scale and colour scheme with the bundled font, and layout-templates §Surface: desktop-native → IA notes records the harness default it matches. A snapshot command's bounds are comparable across runs only under that pin; the CLI adds no viewport argument that the plan knows of.
- The nested scroller's readings must survive the crossing: layout-templates §Surface: desktop-native → IA notes requires an into-view scroll to move every scrolling box that holds its target, innermost first, then the viewport; it names the CRUD list as the box that clips its rows and the task body as not that box, and requires a driver `click` on a row below the list's box to be refused `off-screen` and a driver `scroll` to bring it inside the list. The same section records the list's bounds at boot, the reference the scope's shifted-bounds finding (CARRY 8) is measured against. Whether a `click` and a `scroll` issued from the command line read the same as in process is research's question.
- The plan gives no layout for the new command line: layout-templates §Surface: cli → Primary screens holds one row per agent-invocable command (usage line, argv shape, what each stream carries, exit codes) and none for a driver CLI. Command and argument names, the shape of stdout and the exit codes are not derivable from this plan (scope decisions 2 to 4); a row of that shape for the new binary is a plan amendment owed once they are given.

## Patterns to follow
- Usage on stderr with exit 2, stdout left empty: the form every escher-authored command in layout-templates §Surface: cli → Primary screens takes on a wrong argv (the `agent-run.sh`, `cold-agent.sh` and `escher-session` rows).
- A usage error is decided before any precondition is checked and before any state exists (layout-templates §Surface: cli → Primary screens, the `cold-agent.sh` and `escher-session` rows).
- stdout carries machine output only and the raw output of what ran is kept off it, in a named file or on stderr (layout-templates §Surface: cli → Primary screens, the `agent-run.sh` and `cold-agent.sh` rows). Those two rows use JSON lines, one object per event; that is precedent for an option under scope decision 4, not a binding on it.
- A cli row states usage, streams and exit codes and points to test-plan §3 for the exit grammar, the event schema and the session contract instead of restating them (layout-templates §Surface: cli → Primary screens, all three escher rows).
- Names reach a stand control by attributes alone, with no added element (layout-templates §Surface: desktop-native → Primary screens): the route for anything a snapshot must read differently, should the chunk find one.

## Anti-patterns to avoid
- Adding or moving stand markup, an id, a class, a style, a wrapper or element order to make a flow scriptable, or selecting by the stable ids in CSS (layout-templates §Surface: desktop-native → Primary screens requires none of these).
- Writing to the session host's stdout on any path while its row stands (layout-templates §Surface: cli → Primary screens, the `escher-session` row).
- Taking the upstream WPT runner's terminal output as a model: layout-templates §Surface: cli → Output structure — wpt runner records output that differs between a terminal and a pipe and rewrites lines in place with ANSI cursor escapes. The plan records it as built and states no ban; the ban on escape sequences and on terminal-dependent output is the chunk scope's own.

## Contract bindings
- layouts ↔ tests: the cli rows hand the exit grammar, the event schema and the session contract to test-plan §3 (→ Session lifecycle, keyed contract `session-lifecycle`); the driver CLI's exit codes and JSON shape bind there, and the layouts row cites them.
- layouts ↔ security: the ids, names and values that layout-templates §Surface: desktop-native → Primary screens lists become stdout content of a command; that crossing is security-plan §Input Validation's (scope decision 1), not a layout question.
- layouts ↔ obs: layout-templates §Surface: cli → Primary screens (the `escher-session` row) requires the host's stderr log lines to carry the service identity; what a command-running host's stderr holds, and a new binary's identity, bind to obs-plan.
- layouts ↔ architecture: the into-view scroll and visible-region semantics in layout-templates §Surface: desktop-native → IA notes are the engine contract architecture §Standard Contracts states; the two engine findings (CARRYs 8 and 9) change what that section's readings would say.
- layouts ↔ a11y: the plan holds no focus-order section and the chunk adds no focusable element; a binding to a11y-plan arises only if the actionable-key check is exposed (scope decision 6).
