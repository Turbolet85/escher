## Constraints
- a11y-plan §9 requires the `a11y` leg (`ci-leg.sh a11y`, ci.yml's `a11y` job) to keep running its six named test files, three of them stand checks (`stand_keyboard`, `stand_contrast`, `stand_accessibility_ids`). Its `LegScriptTest` a11y tuple in `.github/scripts/test_ci_workflows.py` pins it. A leg restructure, a dedicated repeat leg or a changed CI job must leave that set and that pin intact (per a11y-plan §9).
- a11y-plan §9 records that the leg was widened on the founder's F4 with no new job, no required status check and no repository setting, and that the job sits in the slow tier, restoring the test job's cache and saving none. Making any of these a11y files part of a new gate, such as a flake budget that fails CI, is a new-gate fork for the founder, not a lean (per a11y-plan §9).
- a11y-plan §5 (Test harness pattern) requires the stand keyboard walk to run in both layout modes against the shared tables `tab_order` and `ENABLED_TAB_ORDER`. A flake measurement must repeat that walk as written and never weaken a row or a table to reach a budget (per a11y-plan §5).
- a11y-plan §6 (Color contrast) requires `stand_contrast`'s three tables (control rows, `TEXT_ROWS`, `STATE_ROWS`) to be asserted row for row in both layout modes. The hover and active rows are reached by `move_mouse_to` and `mouse_down_at`. Whether those input-driven rows behave the same on every repeat is research's question (per a11y-plan §6).
- a11y-plan §2 (Feature exposure) puts dioxus-native-dom's `accessibility_tree` override, `snapshot`, `to_text`, `diff` and `unkeyed_actionable` behind its `accessibility` feature. a11y-plan §1 records that `escher-driver` names that feature unconditionally. If dioxus-native-dom is in the "driver crates" set, its coverage reading counts only when those modules are built with the feature. Whether `cargo llvm-cov --workspace --locked` builds them that way is research's question (per a11y-plan §2).
- a11y-plan §1 lists `accessibility` among blitz-dom's default features, and `custom-widget` requires it. CARRY 7's upstream line runs `--no-default-features` and names `accessibility` again. Whether the fork's `clippy` leg already lints blitz-dom with `accessibility` together with `file-input` and `custom-widget` is research's question (per a11y-plan §1).
- a11y-plan §3 records that `accessibility_states` runs in the workspace `test` leg and per package, not in the `a11y` leg. A budget or floor that names "a11y checks" must state which leg carries each file (per a11y-plan §3).

## Patterns to follow
- Stand checks read stated expectations from the shared module `tests/blitz-tests/tests/common/mod.rs`: `tab_order`, `ENABLED_TAB_ORDER`, `focused`, `controls`, `INPUT_NAMES`, `REGION_NAMES`. A new or restated stand check reads those tables and never re-derives them (per a11y-plan §7, §5 Test harness pattern).
- Every stand a11y assertion runs `for incremental in [false, true]`, both layout modes. A repeat count counts both modes as one check run (per a11y-plan §5 Test harness pattern).
- A check that reads `has_changes()` as "this step changed something" drains the changed set first. The set is non-empty on a freshly booted harness document, so an undrained read is a fixture error, not a flake (per a11y-plan §2 Accessibility tree lifecycle).
- A leg's file set is pinned by a tuple in `test_ci_workflows.py`. A changed leg moves its pin in the same commit (per a11y-plan §9).

## Anti-patterns to avoid
- Never drop a stand a11y file from the `a11y` leg, quarantine it, or mark it flaky-tolerated to meet a budget. Its place in the leg is the founder's F4 ruling (per a11y-plan §9).
- Never assert a second role or name mapping in a new or restated check. The stand tables are stated expectations read off the tree, never a mapping of their own (per a11y-plan §7).

## Contract bindings
- a11y ↔ tests: the `a11y` leg (a11y-plan §9) is a test-plan §9 leg, pinned in `.github/scripts/test_ci_workflows.py`. The flakiness budget (test-plan §10) covers its three stand files.
- a11y ↔ tests: if the coverage floor's crate set takes `dioxus-native-dom`, the reading depends on the `accessibility` feature reaching it (a11y-plan §2 Feature exposure, §1). That binds the floor (test-plan §10) to the feature graph.
