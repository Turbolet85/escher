## Constraints
- obs-plan §3 Bootstrap phases (`otel-sdk-install`) requires an OTel SDK install, recorded absent in §2 Absent and §3 OTel SDK init. The scope makes it opt-in, so the plan's absence record is the baseline the off-by-default path must preserve: with the switch off, nothing exports. §2 Absent searched the workflows and Cargo.toml for `opentelemetry|otel`, so new OTel crates widen that record (per obs-plan §2 Absent; §3 OTel SDK init).
- obs-plan §3 Bootstrap phases (`pii-scrubbing-wire`) requires a scrub wire, recorded absent in every slice of §8 Scrubbing (absent). The values to redact are the ones §8 "Values logged as-is" records: visited and resource URLs (`url`), raw href and document URL, element attribute names and values, outer HTML (`html`), CSS property values (`value`), and dioxus text-node contents and attribute values. Whether the scrub works over field names alone, or also has to cover values interpolated into message strings (for example the href and attributes at pointer.rs:753/758, or `debug_log_node`), is research's question (per obs-plan §8 Values logged as-is).
- obs-plan §2 Telemetry mechanism records `tracing` call sites compiled only under `#[cfg(feature = "tracing")]`, each with a no-op path when the feature is off. The bootstrap must keep that per-crate gating; turning on the subscriber must not force `tracing` on in engine crates (per obs-plan §2 Telemetry mechanism; §2 Feature wiring).
- obs-plan §3 Logging stack records native subscribers installed with `tracing_subscriber::fmt::init()` in the browser, rdme and todomvc (default writer: stdout); wasm_hello installs `tracing_wasm`; the WPT runner uses `env_logger`. The stand is not in that list. Whether `seven_guis_native` installs any subscriber today is research's question. Replacing the browser, rdme and WPT installs is out of scope unless research shows it costs nothing (per obs-plan §3 Logging stack).
- obs-plan §7 Panic hooks records `console_error_panic_hook` installed in WASM builds (including `examples/seven_guis/src/lib.rs:13`) and a separate WPT panic hook that captures message, file, line, column and backtrace. The new native panic hook must chain the previous hook rather than replace it, and must leave the WASM hook and the WPT hook alone (per obs-plan §7 Panic hooks).
- obs-plan §6 Logged events records stdout writes that bypass any subscriber: `debug_log_node` and `Node::print_tree` use `println!`, and examples and tests use `println!`/`eprintln!`. A stderr-only subscriber does not stop these from reaching stdout. Whether any of them run on the stand's path is research's question (per obs-plan §6 Logged events — blitz-dom, blitz-dom (node)).
- obs-plan §1 records obs tier 0, so instrumentation depth stays at the bootstrap. New spans and metrics are out of scope, consistent with §4 and §5 recording only absence (per obs-plan §1 Obs Scope Summary).

## Patterns to follow
- Feature-gated install: the browser and rdme install their subscriber only under their own `tracing` cargo feature (apps/browser/src/main.rs:73-74; apps/readme/src/main.rs:61-62). Gate the bootstrap the same way, with the OTel exporter behind a separate optional feature (per obs-plan §3 Logging stack; §2 Feature wiring).
- Feature forwarding: a top-level `tracing` feature forwards to dependent crates' `tracing` features (packages/blitz/Cargo.toml:14,17; packages/dioxus-native/Cargo.toml:67). The stand turns on engine telemetry this way rather than through new dependencies (per obs-plan §2 Feature wiring).
- Panic capture shape: the WPT hook records message, file, line and column (wpt/runner/src/panic_backtrace.rs:12-38). This is the existing precedent for the fields the new panic event carries (per obs-plan §7 Panic hooks).
- Embedder drain: JS errors and messages reach the embedder through `take_js_errors` / `take_messages`, capped at 256 retained, not through the subscriber. A bootstrap that wants them logged and scrubbed drains them through this API (per obs-plan §3 Embedder drain of script diagnostics).

## Anti-patterns to avoid
- Adding a new log field or OTel span attribute that carries URLs, attribute values, outer HTML, text content or CSS values, including the bootstrap's own startup event (for example logging the endpoint URL or argv), outside the scrub path (per obs-plan §8 Values logged as-is).
- Unconditional telemetry calls in engine crates, or a bootstrap that forces engine `tracing` features on by default; the no-op fallback must survive (per obs-plan §2 Telemetry mechanism).
- Building an exporter or opening a connection when OTel export is not explicitly enabled. The plan's baseline is "no telemetry backend" (per obs-plan §3 Bootstrap phases `otel-sdk-install`; §2 Absent).

## Contract bindings
- obs ↔ security: the §8 scrub list (§3 `pii-scrubbing-wire`) and the OTel outbound endpoint (§3 `otel-sdk-install`) bind to the security plan (§Logging & Monitoring redaction, and the §Surfaces amendment the scope requires before a new outbound host). The redact field set the security side ratifies must match §8 "Values logged as-is" (per obs-plan §8; §3 Bootstrap phases).
- obs ↔ arch: the bootstrap's crate, env vars (opt-in and filter switches) and OTel endpoint are arch §Occupied Resources registrations. The obs side contributes the names, since §2 records no naming convention yet (per obs-plan §3 Bootstrap phases).
- obs ↔ CI/tests: logs moved to stderr land in the per-leg `target/ci-logs/{leg}.log` and the failure artifact. §9 records that artifact as unscrubbed build output with no user data. If tests start emitting scrubbed or unscrubbed user-content events into those logs, the §9 row's "no user data" claim is at stake (per obs-plan §9 Telemetry artifact handling).
- obs ↔ deps audit: the optional OTel crates enter `Cargo.lock` and so fall under the audit leg's reach, and they must not disturb the coupled pins (per obs-plan §3 Bootstrap phases `otel-sdk-install`).
