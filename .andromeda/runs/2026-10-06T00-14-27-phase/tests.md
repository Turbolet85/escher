## Constraints
- The test harness is Rust's standard built-in one: `#[cfg(test)]` modules with `#[test]` and `assert!`/`assert_eq!`, plus `#[tokio::test]` only for async work. test-plan §3 (Runners and invocation, "Rust tests") records no third-party framework (no proptest, insta, criterion or mock library). The bootstrap's tests stay on that harness. Pulling in a test framework or a tracing-test crate is a new dependency, so it is a decision, not a default.
- The done-gate is the CI legs run through `bash .github/scripts/ci-leg.sh {leg}`: `fast` (fmt → clippy → test → ci-scripts) plus `doc`, all `--locked`, per test-plan §9 (Pipeline facts, "Legs" / "Local pre-push gate"). New OTel crates in `Cargo.lock` must also pass the `audit` leg (`cargo deny check advisories`), per test-plan §9 "Legs".
- CI's `test` leg runs `cargo test --workspace --locked` with default features only (test-plan §1 Coverage scope "Workspace (CI)"; §9 "Legs"). Tests behind the opt-in OTel feature are gated the way test-plan §3 "Feature gating" gates the SVG tests, on `test` plus the feature. Whether any existing leg compiles and runs a non-default-feature test of a new crate is research's question. If none does, the export path has no CI proof and the chunk must name or add the leg that runs it.
- ci.yml and ci-leg.sh are pinned by `test_ci_workflows.py`, which covers the leg list, `--locked`, per-leg log upload, SHA-pinned `uses:` and `permissions: contents: read` (per test-plan §4 What unit tests cover, "CI workflows and leg script"). Any leg or job the chunk adds or changes must keep that suite green, extending its pins where the invariant set grows (it currently runs 23 tests).
- No regression against the measured baseline: `cargo test --workspace` at 407 passed · 0 failed · 3 ignored on the dev host, and `ci-leg.sh coverage` exit 0 with no threshold applied (per test-plan §9 "Local baseline" and §9 "Coverage"). Adopting the bootstrap in the stand must not turn any existing test red.
- A test that installs the global `tracing` subscriber or a panic hook changes state for its whole process. test-plan §5 (Boundaries covered, "tests/blitz-tests crate") records integration tests as one file per behaviour, and each file builds as its own test binary. That is the existing way to isolate process-global installs such as "idempotent, safe to call twice" and "panic hook chains the previous hook" from each other and from the rest of the suite.

## Patterns to follow
- Unit tests sit inline in `#[cfg(test)] mod tests` next to the code (pure pieces such as scrub field matching and resource-identity construction). Process-global behaviour goes into a dedicated integration-test file named for the behaviour it guards. Per test-plan §4 Conventions "Test file location", §2 "Test directory + naming conventions" and §5 "tests/blitz-tests crate".
- Stand-ins are hand-written fakes that record calls (`RecordingShell`, `RecordingNetProvider`, `RecordingHandler`), not a mocking library, per test-plan §8 (Hand-written fakes and stubs; Observed absent). A test of scrubbing or OTel export follows that shape: a recording writer, layer or exporter that captures what reached the sink, so the test can assert on redacted fields and on service identity without a collector.
- Opt-in or no-op switches are proven on both sides. test-plan §8 records `debug_timer` swapping in a zero-cost dummy when `enable` is off. The OTel opt-in gets the same two-sided proof: export off builds no exporter, export on routes through the scrubber and carries `service.name` / `service.version`.
- Regression tests are named for what they guard (per test-plan §2 "Test function naming"), for example a test named for "logs never on stdout" or for "panic hook chains the previous hook".

## Anti-patterns to avoid
- No test that passes without asserting. test-plan §4 "Conditional assertions" records text-input tests that assert only inside an `if`, and §5 "HTML parser ↔ DOM" records `parses_some_html` with no assertion. A redaction or stdout-silence test must assert unconditionally on the captured output.
- No real network in the export test. test-plan §8 records network stand-ins as hand-written providers, and the workspace binds no port or socket (CLAUDE.md critical warning). The opt-in export test uses a recording exporter, never a live OTLP collector, endpoint or listener.

## Contract bindings
- tests ↔ security: new OTel crates are gated by the `audit` leg (cargo-deny, `deny.toml`) in the same workflow, per test-plan §9 "Legs". That leg misses advisories in optional chains (security rules §Dependencies), and the OTel crates enter behind an optional feature, so the hand review stays required.
- tests ↔ obs: the scrub layer's field list and the stderr/file sink are obs-plan §8/§3 content. tests owns only the proof, which is asserting those field names come out redacted and nothing reaches stdout. test-plan §3's log-format and status binding reads NOT YET MEASURED, so no harness-greps-the-log contract exists to bind to yet.
- tests ↔ CI coverage: the `coverage-tooling-install` bootstrap item is discharged by the `coverage` leg (per test-plan §3 `coverage-tooling-install`). The new crate's files enter that leg's per-file report, with no threshold.

## Acceptance criteria contributions
- (tests) `cargo test -p {bootstrap crate}` passes. Its tests assert unconditionally that: a second init call is harmless; no byte reaches stdout; the panic hook logs a `tracing` error event and chains the previous hook; every user-content field name obs-plan §8 lists comes out redacted; and with the opt-in off, no exporter is built. Per test-plan §3 (Runners and invocation, "Rust tests").
- (tests) The opt-in OTel path's feature-gated tests run in a named CI leg, not only on default features. Any ci.yml or ci-leg.sh change keeps `python3 -m unittest discover -s .github/scripts` green, with its pins extended for the new invariant. Per test-plan §3 "Feature gating" and §4 "CI workflows and leg script".
- (tests) `bash .github/scripts/ci-leg.sh fast`, `doc` and `audit` all exit 0 after the OTel crates enter `Cargo.lock`. The workspace test count holds at or above 407 · 0 · 3 with the stand adopting the bootstrap. Per test-plan §9 "Legs" and §9 "Local baseline".
- (tests) `bash .github/scripts/ci-leg.sh coverage` exits 0 and its per-file table lists the bootstrap crate's source files. No threshold applies. Per test-plan §9 "Coverage".
