# a11y extract

## Relevance
partial — the chunk adds no UI surface, but it restructures the CI legs (fast/slow split, caches, profile, job exclusion) that carry the engine's existing accessibility assertions and its default `accessibility` feature builds; the named a11y CI leg itself is out of scope (owned by "CI gate legs").

## Constraints
- a11y-plan §1 A11y Scope Summary sets tier 0 at SC 2.1.1 · 1.4.3 · 2.4.3 and lists `accessibility` as a default feature of blitz-dom, blitz-shell, blitz and both Dioxus crates — any default-feature CI build or test leg this chunk reshapes (e.g. `build-features-default` / `test-features-default`) must keep building with that feature on; whether those jobs build the default feature set today is research's question.
- a11y-plan §3 A11y Assertion Harness Contract (tool pick) requires accessibility assertions to be Rust tests in blitz-tests over the AccessKit tree (`accessibility_hidden.rs`, `accessibility_roles.rs`) — the fast/slow split must place them in a leg that runs on every build-branch push; whether CI's `matrix_test` runs them today is research's question.
- a11y-plan §5 Keyboard Navigation (Focus order per layout) records `focusability_updates.rs` as the engine's focus-order/focusability assertions (the SC 2.1.1 / 2.4.3 surface) — same placement requirement as the a11y tests; they must not be relegated to a leg that the common push skips.
- a11y-plan §3 A11y Assertion Harness Contract requires the test harness to build blitz-dom with the accessibility feature (blitz-test-harness Cargo.toml) and blitz-tests to carry `accesskit` as a dev-dependency — a cached or feature-subset fast leg must not compile the test crates with features that drop it.
- a11y-plan §2 A11y Strategy (Platform adapters) requires `accesskit_xplat` to select windows / macos / unix / android adapters per target — excluding signing-secret jobs must not remove the only compile coverage of the macOS / Android adapter modules; whether that coverage lives only in the excluded jobs is research's question.
- a11y-plan §9 CI Integration and §3 Bootstrap phases (`a11y-ci-gate-wire`) record CI accessibility checks as absent and owed — per the chunk boundary this chunk does not wire that gate; it only leaves the workflow in a shape the gate can join.

## Patterns to follow
- a11y-plan §3 A11y Assertion Harness Contract — the a11y assertions are plain `cargo test` integration-test files (`assert_role`, `unknown_tags`, `test_that` matchers on `role()` / `is_hidden()`), so the host-reproducible local invocation is the same per-file command CI runs (`cargo test -p blitz-tests --test accessibility_roles` etc.), not a separate a11y tool.
- a11y-plan §3 A11y Assertion Harness Contract (Focus management test harness) — focused-node inspection lives in `blitz-test-harness` inspect queries; focus assertions ride the ordinary test leg, needing no window or GPU, so they fit a headless fast leg.
- a11y-plan §6 Visual Design Verification (State color) — the WPT runner prints each result's status word as text beside its colour; any CI log or failure-artifact output this chunk adds keeps status in text, not colour alone.

## Anti-patterns to avoid
- Do not add a named a11y leg or a11y gate in this chunk — a11y-plan §3 Bootstrap phases `a11y-ci-gate-wire` is owned by "CI gate legs" per the chunk boundary (a11y-plan §11 records no anti-pattern list: NO RECORDED INTENT).
- Do not speed a fast leg by building with `--no-default-features` or a feature subset that drops `accessibility` (per a11y-plan §1 A11y Scope Summary, default-feature status).

## Contract bindings
- a11y ↔ tests: a11y-plan §3 Bootstrap phases `a11y-ci-gate-wire` binds to the test plan's CI section (a11y step in the same workflow) — deferred to "CI gate legs"; this chunk's fast/slow leg structure is the workflow that step will later join.
- a11y ↔ tests: the existing a11y and focusability assertions (a11y-plan §3, §5) execute inside the blitz-tests leg — their CI placement is decided by this chunk's fast/slow split.

## Acceptance criteria contributions
- (a11y) On the pushed build-branch sha, the CI leg that runs on every push executes `accessibility_roles`, `accessibility_hidden` and `focusability_updates` and they pass (per a11y-plan §3 A11y Assertion Harness Contract; a11y-plan §5 Keyboard Navigation).
- (a11y) Every default-feature build/test leg after the change still compiles blitz-dom with `accessibility` enabled — no leg's feature flags drop it (per a11y-plan §1 A11y Scope Summary).
- (a11y) The local invocation for the blitz-tests leg runs the same command as the workflow and reproduces the a11y test results on the dev host (per a11y-plan §3 A11y Assertion Harness Contract).
- (a11y) After the signing-secret jobs are excluded, `accesskit_xplat` still compiles in at least one non-excluded leg per platform it targets in CI today, or the loss is recorded as a P4 decision (per a11y-plan §2 A11y Strategy, Platform adapters).
