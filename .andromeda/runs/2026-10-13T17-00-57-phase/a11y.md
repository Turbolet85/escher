# a11y extract

## Relevance
relevant — the chunk builds the contrast measurement for SC 1.4.3, one of the three criteria in the tier, and discharges the bootstrap key `contrast-verification-harness-setup`.

## Constraints
- a11y-plan §1 A11y Scope Summary sets the tier at `0 — SC 2.1.1 · 1.4.3 · 2.4.3`. SC 1.4.3 is the only criterion this harness reads against. SC 1.4.11 (non-text) and SC 2.4.7 (focus visible) are outside the tier, so a pair's verdict names SC 1.4.3 and its threshold (4.5:1, or 3:1 for large text) and nothing else.
- a11y-plan §3 A11y Assertion Harness Contract records the contrast verification harness as observed absent. It defers to §6, and its keyed contract `§3 Bootstrap phases` lists `contrast-verification-harness-setup` as not yet discharged. This chunk is that harness. It measures and records only. The wrap amends §3 and §6 with what it measured, and the code delivers no gate.
- a11y-plan §6 Visual Design Verification (Color contrast) requires the ratio to be the WCAG relative-luminance ratio. The engine already holds a helper that matches Chrome's `GetContrastRatio`, used for border bevels and scrollbar thumbs. Whether the harness reuses that `pub(crate)` helper or states its own formula, the two must agree. A second formula that disagrees with the painted bevels is a defect.
- a11y-plan §6 Visual Design Verification (Color scheme, zoom and user preferences) says the viewport carries a light/dark colour scheme and a zoom level (`1.0` unzoomed), and a colour-scheme change rebuilds the stylist device. Each pair is measured under the stand's pinned scheme and zoom 1.0, and the record states them. A reading taken under a different device is not the stand's reading.
- a11y-plan §5 Keyboard Navigation (Focus order per layout) keys disabled-ness two ways. The `DISABLED` state (`:disabled`) follows the attribute's presence, while focusability follows its parsed value. The SC 1.4.3 inactive-component exemption must follow the presence reading, which also selects the `:disabled` colours. It must not follow focusability.
- a11y-plan §7 Screen Reader Support (Accessibility tree output) states the stand's roles and input names once, as the tables `controls` and `INPUT_NAMES` in the stand checks' shared module. These are a stated expectation, never a second role or name mapping. The set of controls measured and each pair's stable id come from that table and the snapshot's ids.
- a11y-plan §8 Cognitive Accessibility (Error recovery) records the flight booker's invalid date as an `invalid` class with red styling, alongside `aria-invalid` and a disabled Book. That state changes a control's colours. If the chunk measures it beyond the boot rest state, it is a separate recorded pair, never folded into the rest-state reading.

## Patterns to follow
- a11y-plan §3 A11y Assertion Harness Contract (tool pick): accessibility assertions are Rust tests in blitz-tests. The state check there reads one stated table, asserts its row count, and runs in both layout modes. It runs in the workspace test leg and per package, and the `a11y` leg keeps its three files. The per-pair check takes the same shape: one table over the lean tasks' controls, the row count asserted, run `for incremental in [false, true]`.
- a11y-plan §5 Keyboard Navigation (Test harness pattern): stand checks drive the booted stand through the test harness, in both layout modes, and read results by stable id (`back-btn`, `crud-name`). Per-pair results are keyed by the control's stable id the same way.
- a11y-plan §6 Visual Design Verification (State color, not-color-alone): the WPT runner prints each result's status word as text alongside its colour. Each pair's verdict (pass / fail / exempt-inactive / no-text) is recorded as a word, not as a colour or a bare number.
- a11y-plan §7 Screen Reader Support (Accessibility tree output): the snapshot is a reader of the model with no second mapping, and `enabled` reads `Some(false)` on the presence of `disabled`. The inactive exemption reads `enabled` the way the driver's `disabled` refusal does.

## Anti-patterns to avoid
- A second role, name or control mapping for the stand inside the harness. a11y-plan §7 Screen Reader Support (Accessibility tree output) states the expectation once, in the shared tables (`controls`, `INPUT_NAMES`, `rendered`), and every reader reads the model.
- Deciding the inactive exemption from focusability or from the attribute's parsed value. a11y-plan §5 Keyboard Navigation (Focus order per layout) shows that `disabled="false"` matches `:disabled` yet stays focusable, so a focusability key misclassifies exactly the pairs whose colours `:disabled` sets.
- Adding the new check to the `a11y` CI leg or making it gate. a11y-plan §9 CI Integration fixes that leg at its three test files and records that it adds no stand assertion. Gating is the route entry "Stand a11y assertions".

## Contract bindings
- a11y ↔ a11y-plan keyed contract `§3 Bootstrap phases` (`contrast-verification-harness-setup`): this chunk discharges the key. The wrap amends the key's line, and §3 and §6, with the measured reading.
- a11y ↔ tests: the check is a blitz-tests stand check sharing `tests/blitz-tests/tests/common/mod.rs` (`controls`, `LeanTask::ALL`). It runs in both layout modes in the workspace test leg (a11y-plan §3 A11y Assertion Harness Contract, tool pick), not in the `a11y` leg (a11y-plan §9 CI Integration).
- a11y ↔ design: each measured pair is a design-system colour pair as built (the stand's stylesheet colours). A failing pair is recorded here and re-coloured, if at all, by a later route entry. Design's §Color Palette is the token side of the binding.
- a11y ↔ engine paint: the ratio must agree with blitz-paint's Chrome-matching helper (a11y-plan §6 Visual Design Verification, Color contrast). Exposing that helper is a visibility change in an engine crate, which P4 decides.
- Research's questions, not attested here: whether blitz-test-harness or blitz-dom already exposes a reader for computed `color` / `background-color` with the canvas fallback, whether the stand's table covers the CRUD rows, and whether the flight booker's primary button pair really falls under 4.5:1.

## Acceptance criteria contributions
- Every row of `controls(task)` over `LeanTask::ALL` ends in exactly one recorded result. A measured result holds the stable id, foreground and background colours, the ratio, the computed font size and weight, the SC 1.4.3 threshold that applies, and pass/fail. The other two kinds are "no text pair" (`timer-duration`) and "exempt — inactive". The record's row count equals the table's row count (per a11y-plan §1 A11y Scope Summary and §7 Screen Reader Support, Accessibility tree output).
- The harness's ratio equals blitz-paint's `contrast_ratio` on stated control pairs, including black on white = 21:1 and a colour on itself = 1:1 (per a11y-plan §6 Visual Design Verification, Color contrast).
- The per-pair record is identical with incremental layout off and on (per a11y-plan §3 A11y Assertion Harness Contract, tool pick).
- A control reads "exempt — inactive" exactly when its snapshot node's `enabled` is `Some(false)` at boot, and never on focusability alone (per a11y-plan §5 Keyboard Navigation, Focus order per layout).
