# arch extract

## Relevance
relevant — the chunk adds a read-only measurement to existing workspace crates: the headless harness or the stand checks' shared module, possibly a blitz-paint visibility change, and a stand check. Arch governs where it lives, what it may widen and how the check is shaped.

## Constraints
- The harness lives in an existing workspace unit: `blitz-test-harness` (its modules harness · input · inspect · settle · screenshot) or the stand checks' shared module `tests/blitz-tests/tests/common/mod.rs`. A new workspace crate is a §Occupied Resources → Names registration, never a silent add (per architecture §Occupied Resources; per architecture §Existing Scopes).
- A dependency is declared once in `[workspace.dependencies]` and consumed as `{ workspace = true }`. Whether a package enters `Cargo.lock` is stated, as every prior escher chunk recorded it, and builds stay `--locked` (per architecture §Conventions → Manifests).
- The measured document is the stand as `seven_guis::stand` boots it, with its pinned constants: `VIEWPORT_WIDTH` 800 · `VIEWPORT_HEIGHT` 600 · `HIDPI_SCALE` 1.0 · `COLOR_SCHEME` `ColorScheme::Light`, bundled `DEJAVU_SANS` through `font_ctx()`, and offline through `options(incremental)`. Boot through `boot(LeanTask, HarnessOptions)` over `LeanTask::ALL`, and set no second set of pins (per architecture §Standard Contracts → Headless stand).
- Engine crates keep their internals `pub(crate)` / `pub(super)`. Making blitz-paint's `contrast_ratio` public is a public-API widening of an upstream engine crate, and that crate is a merge surface at the next sync (per architecture §Conventions → Visibility and naming; per architecture §Project Intent → Upstream sync). blitz-test-harness takes blitz-paint with `default-features = false`, so no `svg` and no `scrollbars` in a per-package build. Whether `contrast_ratio` compiles outside the `scrollbars` feature is research's question; the plan cites it beside Chromium's scrollbar contrast ratios (per architecture §Standard Contracts → Test harness; per architecture §Design Philosophy → Behave like a browser, and cite the spec).
- Behaviour is written against a named spec or engine. A ratio the harness states for itself names its formula: WCAG 2.x relative luminance, or Chrome's `GetContrastRatio`, which blitz-paint mirrors (per architecture §Design Philosophy → Behave like a browser, and cite the spec).
- If the harness reads the raster, it reads it as `Harness::screenshot_rect` defines it: no tick and no pump, painted through blitz-paint into `VelloCpuImageRenderer`, then composited over opaque white. A rect is clipped to the viewport, an empty one is `EmptyRect`, and a font-less document is `FontsUnavailable`. No path prints, panics or logs, and a new harness reader keeps that (per architecture §Standard Contracts → Test harness).
- The measurement is read-only. It runs no `doc.mutate()`, no input and no settle-changing step. Ids from the changed set or a traversal are read through `get` / `contains_key`, never by indexing, because a stale `NodeId` panics (per architecture §Conventions → DOM API patterns; per architecture §Standard Contracts → Scrolling, selection, tree).

## Patterns to follow
- Text is painted from its container element's resolved styles. Paint's own colour source for a control's text is the computed `color` of the element that holds the text (per architecture §Design Philosophy → Behave like a browser, and cite the spec). Computed styles are read through blitz-dom's resolved-style module (`getComputedStyle()`) (per architecture §Existing Scopes → blitz-dom: CSSOM and styles).
- The stand checks state their shared tables and helpers once, in `tests/blitz-tests/tests/common/mod.rs`, read by `mod common;`. The control set is that module's `controls(task)`, and each test-target file covers one behaviour and opens with a `//!` doc naming it (per architecture §Conventions → Tests).
- A new harness surface is added the way `screenshot` was: a private module with its types re-exported from the crate root, `///` on every public item, and the export list stated in the contract (per architecture §Standard Contracts → Test harness; per architecture §Conventions → Documentation).
- Integration scenarios run `for incremental in [false, true]`, and a test first asserts that its fixture produces the condition under test, for example that a pair is read and not absent (per architecture §Conventions → Tests).

## Anti-patterns to avoid
- An unconditional `println!` or log site in an engine crate. Engine tracing is gated per call site with `#[cfg(feature = "tracing")]`, and the harness's readers log nothing (per architecture §Conventions → Feature gating).
- Reaching through `DocumentMutator::doc`, or writing any colour onto the stand. The chunk records a failing pair and does not re-colour it (per architecture §Conventions → DOM API patterns).
- A new env var, port, listener or driver verb to carry the result. Env reads are the registered set alone, and a driver carrier would be a new crossing (per architecture §Occupied Resources → Environment variables; per architecture §Established Decisions → [Driver session]).

## Contract bindings
- arch ↔ a11y: the harness is the "contrast verification harness" that a11y-plan §3 records absent and §6 records not measured. The wrap amends those readings, and arch §Standard Contracts → Test harness gains the harness's export only if it lands in blitz-test-harness.
- arch ↔ tests: the check is a `tests/blitz-tests/tests/stand_*.rs` target, run by the workspace `test` leg. The `a11y` CI leg is its three named files (per architecture §Existing Scopes → blitz-tests), and gating on SC 1.4.3 belongs to "Stand a11y assertions", not to this chunk.
- arch ↔ design: the measured pairs are the stand's as-built colours, which design-system.md §Color Palette records. A pair the harness reads below threshold is a design reading, not an arch change.
- arch ↔ upstream sync: a blitz-paint visibility change is a merge surface beside `packages/blitz-paint/src/render.rs`, which the arch plan already names for the password mask (per architecture §Established Decisions → [Painting]).

## Acceptance criteria contributions
- The harness code lives in `blitz-test-harness` or in `tests/blitz-tests/tests/common/mod.rs`. No new workspace crate, env var, port or listener, and no package entering `Cargo.lock` (per architecture §Occupied Resources).
- The measuring check boots each `LeanTask::ALL` task through `seven_guis::stand::boot` with `stand::options(incremental)` and runs in both layout modes, `for incremental in [false, true]`, with identical per-pair results across the two (per architecture §Conventions → Tests; per architecture §Standard Contracts → Headless stand).
- If blitz-paint's `contrast_ratio` is reused, its visibility is the only blitz-paint edit. It compiles in blitz-test-harness's `default-features = false` build, and `cargo doc --workspace --no-deps --locked` stays green under `-D warnings` (per architecture §Conventions → Visibility and naming; per architecture §Conventions → Formatting and lints).
- Every new public harness item carries `///` docs, and calling it prints, logs and mutates nothing: the snapshot and the changed set read the same before and after a measurement (per architecture §Standard Contracts → Test harness).
