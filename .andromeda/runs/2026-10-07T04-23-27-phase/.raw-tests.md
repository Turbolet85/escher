# tests extract

## Relevance
partial — the chunk writes no test and edits no source; its whole proof is test-plan's gate runs (the local `fast` and `doc` legs, the fork's CI verdict on HEAD) on an unchanged tree.

## Constraints
- The local gate the chunk must run is `bash .github/scripts/ci-leg.sh fast`; test-plan §9 Local pre-push gate requires its four legs in a fixed order, stopping at the first red — a red leg ends the run, the later legs are then unrun, not passed (per test-plan §9 Local pre-push gate).
- The second local gate is `bash .github/scripts/ci-leg.sh doc`; test-plan §9 Legs requires it to document the whole workspace, and requires every cargo leg to pass `--locked` — so both legs also witness that the lockfile is untouched (per test-plan §9 Legs).
- The `test` leg inside `fast` is the workspace run with default features, the same command CI's fast `test` job runs; the dev host and CI run one script, so the local verdict and the CI verdict are the same legs (per test-plan §1 Workspace (CI) · §9 Legs).
- The fork's CI verdict on HEAD is reachable because test-plan §9 Platform requires ci.yml to trigger on `build/**`; a green there means the four fast jobs and every job that `needs` them, the windows/macos test matrix and the ios/android builds included (per test-plan §9 Platform · §9 Fast/slow split · §1 Surfaces under test, Native platforms).
- A green fork CI does not include Web Platform Tests: the `wpt` job is repository-guarded to upstream and on the fork WPT is a host run. The chunk merges nothing, so its scope owes no WPT run — but the CI verdict must not be read as conformance evidence (per test-plan §1 Surfaces under test, Web Platform Tests · §9 WPT workflow).
- The reference the `fast` run's workspace totals are held against is the latest re-count in test-plan §9 Local baseline (the 2026-10-07-audit-corrections entry: result lines · passed · failed · ignored). Whether the unchanged tree still reads those totals is /implement's measurement, not attestable from the plan (per test-plan §9 Local baseline).
- Whether `upstream/main` still sits at the merge base, and whether the CI run on HEAD has concluded, are git and network readings the plan cannot attest — research's and /implement's question, to be measured, never inferred.

## Patterns to follow
- Run each gate through `ci-leg.sh {leg}` rather than a hand-typed cargo line; the leg's merged output lands in `target/ci-logs/{leg}.log`, truncated at the leg's start, which is the evidence file to read counts from (per test-plan §9 Failure logs · §9 Legs).
- Record the run the way earlier chunks did in the baseline's re-count chain: result lines and passed · failed · ignored, with the commit the run stood on and "timings not re-measured" where they were not — the 2026-10-06-upstream-sync-element-identity entry is the sync-shaped precedent (per test-plan §9 Local baseline).
- If the stand checks are read on their own, use the agent-run contract — `boot`, then `run stand`, then `cleanup` — and compare its `ok` stand-event count with the latest re-count in the contract's Proof line; the scope does not require this run, the workspace `test` leg already executes those files (per test-plan §3 Agent-run contract, `run {selection}` · Proof).
- Font-dependent pre-existing tests may skip at runtime, while the stand checks assert unconditionally under the bundled font — so the stand checks' count is the host-independent part of the totals (per test-plan §2 Font-dependent tests · §9 Fonts).

## Anti-patterns to avoid
- Reading an in-progress, partial or absent run as a pass: the plan's run contract treats an outcome as passed only on positive evidence, and an empty run is never a pass (per test-plan §3 Agent-run contract, `run {selection}`).
- Dropping `--locked`, or substituting a narrower command (one package, one file) for the workspace legs the gate names (per test-plan §9 Legs · §9 Local pre-push gate).
- test-plan §11 Test Anti-Patterns reads `NO RECORDED INTENT` — nothing is extracted from it; the two bans above come from §3 and §9 alone.

## Contract bindings
- tests ↔ a11y: the `a11y` leg is a job of the same ci.yml and its three files also run inside the workspace `test` leg, so the CI verdict and the `fast` run both carry the a11y assertions (per test-plan §9 Legs · §9 Cache).
- tests ↔ security: the `audit` leg (cargo-deny advisories) is a job of the same workflow and part of the CI verdict; the chunk changes no dependency or lockfile, so it adds nothing to that leg (per test-plan §9 Legs).
- tests ↔ obs: the four `telemetry_*` integration files run inside the workspace `test` leg and pin the stand log format obs-plan §3 owns; the agent-run events are harness metadata, not an escher-telemetry sink (per test-plan §3 Stand log format · §3 Agent-run contract, Events).
