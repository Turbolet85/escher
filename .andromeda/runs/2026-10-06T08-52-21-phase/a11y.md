# a11y extract

## Relevance
partial — the chunk adds no UI surface and intends no focusability, focus-order or painted-colour change. Accessibility-node identity is out of scope (it is v010-03). Its a11y exposure is the stand markup it may add for author keys, and the engine paths those attributes feed.

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary). Any key markup added to the lean tasks or the TaskShell chrome must leave keyboard operability (2.1.1), painted contrast (1.4.3) and focus order (2.4.3) of every stand control unchanged.
- Focusability is derived from `tabindex`, `href` and `disabled` and the element kind. Setting or removing those attributes recomputes it, and Tab / Shift+Tab walk focussable nodes in order (per a11y-plan §5 Keyboard Navigation, "Focus order per layout (engine)"). Whatever attribute carries an author key must not be one of these, and its insertion must not reorder focussable stand controls.
- A node's role comes from its `role` attribute, else the HTML element mapping, else `Role::Unknown` (per a11y-plan §2 A11y Strategy, "Role derivation" · §4 ARIA Patterns & Roles). An author-key or id carrier must not be the `role` attribute, and must not change an element's tag.
- Elements carrying `hidden`, `display: none` or `visibility: hidden` are excluded from the accessibility tree with their children, and `aria-hidden="true"` marks a node hidden (per a11y-plan §4 "Hidden content" · §6 Visual Design Verification, "Visibility and hit-testing"). The id derivation must not add or depend on these. The plan records that a Dioxus `hidden: false` is written as the literal `"false"`, so a presence read takes it as set (per a11y-plan §5 "Script and framework exposure"). Do not introduce such a boolean attribute while keying stand controls.
- AccessKit node identity is the engine `NodeId` mapped by `as_u64` (per a11y-plan §1 "blitz-traits node ids" · §3 A11y Assertion Harness Contract, `assert_role`). This chunk must leave that mapping intact, because tying the stable id to accessibility nodes is v010-03. Whether any current code path would be displaced by a new id store is research's question.
- The a11y CI leg runs `accessibility_hidden`, `accessibility_roles` and `focusability_updates` (per a11y-plan §9 CI Integration). A change in blitz-dom or dioxus-native-dom must keep that leg green.

## Patterns to follow
- To prove that a markup addition kept roles intact, use the role-assertion pattern: `build_accessibility_tree()` after `resolve`, matched on `role()` / `is_hidden()`, plus the `assert_role` / `unknown_tags` helpers (per a11y-plan §3 A11y Assertion Harness Contract).
- Use the harness's focused/hovered node queries for any focus check on the stand (per a11y-plan §3 "Focus management test harness").
- Use the stand-check style of asserting a state cue without colour, by attribute presence (per a11y-plan §8 Cognitive Accessibility, "Error recovery", `stand_flight_booker.rs`). An id check reads attributes or ids the same structural way, not painted output.

## Anti-patterns to avoid
- Carrying an author key on `role`, `tabindex`, `aria-*`, `hidden` or `disabled`. Each one is an input to role, hidden-ness or focusability derivation (per a11y-plan §4 · §5 "Focus order per layout (engine)").
- Rewiring the AccessKit `NodeId(node_id.as_u64())` mapping, or adding the stable id to accessibility nodes, in this chunk (per a11y-plan §3 `assert_role`; v010-03 owns it).

## Contract bindings
- a11y ↔ tests: the `a11y` CI leg (`bash .github/scripts/ci-leg.sh a11y`) runs in the same `ci.yml` workflow as the workspace test leg (per a11y-plan §9 CI Integration). This chunk's new `stand_*.rs` checks join the test leg, not the a11y leg.
- a11y ↔ design/layouts: stand focus rings and painted colours (seven_guis inputs replace the outline with a border colour or box-shadow on focus, per a11y-plan §6 "Focus ring") must not move if keyed markup changes selectors or classes.

## Acceptance criteria contributions
- `bash .github/scripts/ci-leg.sh a11y` passes on the chunk's tree, with its three test files' counts unchanged (per a11y-plan §9 CI Integration).
- If stand markup gains author keys, every stand element's AccessKit role and hidden state are identical before and after the change on each lean task: no new `Role::Unknown` and no node newly excluded or `is_hidden` (per a11y-plan §4 ARIA Patterns & Roles · §3 A11y Assertion Harness Contract).
- On each lean task, the set and order of focussable stand controls (the Tab sequence) are identical before and after the key markup is added (per a11y-plan §5 Keyboard Navigation, "Focus order per layout (engine)"). The plan records that no test yet asserts a Dioxus control's focusability or Tab order (per a11y-plan §8 "Error recovery"), so whether a check must be added for this is P4's call.
