# a11y extract

## Relevance
partial — the chunk adds no UI and changes no markup, and the stand's a11y/contrast/keyboard harnesses are Epoch 6. It does fix the boot that every later a11y check runs on: the pinned colour scheme and scale, the `accessibility` feature reaching the headless build, and the focus surface of TaskShell and the four tasks.

## Constraints
- The a11y tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary). The headless boot is the base on which later chunks assert keyboard operability, contrast and focus order, so it has to boot the same tree the windowed app renders. Scope says the same: "changes no markup the windowed app renders".
- `accessibility` is a default feature of blitz-dom, both Dioxus crates and blitz-shell, and `blitz-test-harness` builds blitz-dom with it (per a11y-plan §1 A11y Scope Summary; per a11y-plan §3 A11y Assertion Harness Contract). Any new dependency edge (blitz-tests → seven_guis, the harness → a font asset, a seven_guis test target) must keep it on. Do not use `default-features = false` without re-adding `accessibility`. Whether the stand's crate currently forwards it is research's question.
- The pinned viewport's colour scheme and zoom/scale are a11y-relevant state. The viewport carries a light/dark colour scheme and a zoom level. A colour-scheme change rebuilds the stylist device, and a total-scale change invalidates text shaping (per a11y-plan §6 Visual Design Verification, "Color scheme, zoom and user preferences"). Name the pinned value once and make it the scheme the windowed stand paints. Painted colours are SC 1.4.3 surface that the later contrast harness will measure against this pin.
- The focus-order rules decide what is focusable in TaskShell and the tasks. Focusable elements are non-disabled `button`/`input`/`select`/`textarea`, `<a href>`, and any element with `tabindex >= 0`. Disabling a button removes its focusability (per a11y-plan §5 Keyboard Navigation, "Focus order per layout"). Whether TaskShell's back button is a native `button` element is research's question. The chunk must not change how it is rendered.
- Synthesized interactions have focus side effects: clicking a non-interactive area clears focus, and checkbox/radio clicks move focus to the control (per a11y-plan §5 Keyboard Navigation, "Focus restoration"). A proof check's focus state follows the synthesized click and is real engine behaviour. Do not mask it.
- The flight booker's invalid-date state is recorded as an `invalid` class with red styling plus a disabled Book button (per a11y-plan §8 Cognitive Accessibility, "Error recovery"). The proof check for "flags an invalid date" reads the class and the disabled state, which is the non-colour signal. It must not read the colour.

## Patterns to follow
- Use the harness's existing inspection surface for focus. It exposes focused-node and hovered-node queries (per a11y-plan §3 A11y Assertion Harness Contract, "Focus management test harness"). Do not add a stand-specific focus query.
- If a proof check reads semantics, use the existing accessibility-tree assertion idiom: call `build_accessibility_tree()` after `resolve`, then match `tree_update.nodes` on `role()` / `is_hidden()`. To map a DOM `NodeId` to an AccessKit `NodeId`, use `NodeId(node_id.as_u64())` as in `assert_role` (per a11y-plan §3 A11y Assertion Harness Contract, "A11y testing tool pick").
- Button and disabled semantics map through the engine's HTML-AAM mapping: button→Button, and a disabled control carries the `DISABLED` state (per a11y-plan §4 ARIA Patterns & Roles, "Per-component pattern catalog"; per a11y-plan §5 Keyboard Navigation, "Focus order per layout").

## Anti-patterns to avoid
- Do not let a new dependency edge or test target build the stand or harness without blitz-dom's `accessibility` feature (per a11y-plan §1 A11y Scope Summary). Feature unification can hide this locally and expose it in a narrower build. a11y-plan §11 A11y Anti-Patterns records no intent, so this ban comes from §1's default-feature inventory.
- Do not assert the flight booker's invalid state by painted colour alone (per a11y-plan §8 Cognitive Accessibility, "Error recovery"). The state's non-colour carriers are the class and the disabled Book button.
- Do not reshape TaskShell or the task markup, such as swapping a button for a clickable `div`, to make a headless entry point easier. a11y-plan §4 ARIA Patterns & Roles ("Application markup") records clickable-`div` controls in the browser app as the non-native pattern. The stand's controls are focus surface under SC 2.1.1 / 2.4.3 (per a11y-plan §1 A11y Scope Summary).

## Contract bindings
- a11y ↔ tests: ci.yml's `a11y` leg runs a fixed list: `accessibility_hidden`, `accessibility_roles` and `focusability_updates` (per a11y-plan §9 CI Integration). The stand checks run in the workspace test leg (`ci-leg.sh fast`), and the a11y leg's list stays unchanged. Adding stand a11y assertions to it is Epoch 6.
- a11y ↔ design (deferred): the bootstrap phase `contrast-verification-harness-setup` is open, since contrast checks are observed absent (per a11y-plan §3 Bootstrap phases). This chunk's pinned colour scheme and scale are the viewport that harness will measure. It binds to design-system §Color Palette when that harness is built. This chunk does not discharge the phase.
- a11y ↔ harness API: a colour-scheme or scale field on `HarnessOptions` is a11y-relevant viewport state (per a11y-plan §6 Visual Design Verification). Any public addition is the arch §Standard Contracts amendment the scope already names.
