## architecture §Design Philosophy
- blitz-paint paints a `blitz_dom::BaseDocument` by pushing `anyrender` drawing commands into an impl `anyrender::PaintScene` (packages/blitz-paint/src/lib.rs:1-2)
- `paint_scene` assumes styles and layout in the document are already resolved; the `PaintScene` implementation decides whether to rasterize, convert to a vector format (SVG/PDF) or serialize the commands (packages/blitz-paint/src/lib.rs:34-42)
- Custom widgets are painted ahead of time into pre-computed `Scene`s keyed by `(document id, node id)` to avoid borrow-checker issues while recursing the tree (packages/blitz-paint/src/lib.rs:31-32; packages/blitz-paint/src/lib.rs:52-59)
- The painter is a short-lived struct holding per-scene render parameters so they are not passed down as arguments (packages/blitz-paint/src/render.rs:104-129)
- Text is rendered as part of its container element's inline layout, not as separate text nodes; text nodes are never rendered directly (packages/blitz-paint/src/render.rs:278-286; packages/blitz-paint/src/render.rs:610-614)
- Several paint routines state that they mirror a named browser's behaviour (Chrome contrast ratio, Blink dash gap, WebKit/Blink colour shading, Firefox decoration-per-box, Chromium scrollbar contrast) (packages/blitz-paint/src/color.rs:27-28; packages/blitz-paint/src/text.rs:97-99; packages/blitz-paint/src/render/border.rs:17-19; packages/blitz-paint/src/text.rs:583-586; packages/blitz-paint/src/render.rs:768-770)
- blitz-shell is described as the event loop, windowing and system integration layer (packages/blitz-shell/src/lib.rs:3)
- blitz-test-harness wraps any `blitz_dom::Document` headlessly: no window, GPU or compositor is required (packages/blitz-test-harness/src/lib.rs:1-14)

## architecture §Established Decisions
- blitz-paint default features are `["svg"]`; `scrollbars` is off by default "while the feature matures" (packages/blitz-paint/Cargo.toml:13-23)
- blitz-shell default features are `accessibility`, `clipboard` and `file-dialog` (packages/blitz-shell/Cargo.toml:13-14)
- blitz-shell's `data-uri` feature enables a data-uri-only NetProvider, "only needed if you aren't using the regular NetProvider" (packages/blitz-shell/Cargo.toml:23-24)
- blitz-test-harness is `publish = false` (packages/blitz-test-harness/Cargo.toml:4)
- The default event loop uses `ControlFlow::Wait` (packages/blitz-shell/src/lib.rs:63-64)
- Windows are created invisible and made visible after AccessKit initialises, to avoid AccessKit panics (packages/blitz-shell/src/window.rs:140-155)
- The renderer's window surface is released in `View::drop` before the window is dropped, because a GPU surface outliving its window segfaults on Wayland (packages/blitz-shell/src/window.rs:123-131)
- A window is dropped before the event loop exits, citing winit issue 4135 (packages/blitz-shell/src/application.rs:52-60; packages/blitz-shell/src/application.rs:150-160)
- Safe-area insets are ignored on macOS so drawing is not kept out of the titlebar (packages/blitz-shell/src/window.rs:32-41)
- On wasm32, surface resizes are debounced by `RESIZE_DEBOUNCE_MS = 100` because wgpu's surface.configure clears the canvas and flickers during a drag (packages/blitz-shell/src/window.rs:527-528; packages/blitz-shell/src/window.rs:609-619)
- On iOS, redraw requests are tracked with a flag and issued in `about_to_wait`, citing winit issue 3406 (packages/blitz-shell/src/window.rs:115-120; packages/blitz-shell/src/application.rs:179-186)
- The paint layer stack is capped at `LAYER_LIMIT: u32 = 1024`; layers past the limit are not pushed (packages/blitz-paint/src/layers.rs:6; packages/blitz-paint/src/layers.rs:60-64)
- Elements whose transformed bounding box is non-finite or exceeds f32 range are culled (packages/blitz-paint/src/render.rs:404-419)
- Gradient background layers with more than 500 tiles are not drawn (packages/blitz-paint/src/render/background.rs:590-593)
- `input type=hidden` is skipped in the painter rather than through the style engine, "for performance reasons" (packages/blitz-paint/src/render.rs:306-310)
- Nothing is painted while the document has pending critical resources (packages/blitz-paint/src/render.rs:176-178; packages/blitz-shell/src/window.rs:418-433)
- Text decoration geometry is built explicitly rather than relying on backend dash support, "so it renders consistently across renderers" (packages/blitz-paint/src/text.rs:274-278)
- Mask isolation layers use an opacity of `1.0 - f32::EPSILON` to force renderers to allocate an isolated buffer (packages/blitz-paint/src/render/mask.rs:29-35)
