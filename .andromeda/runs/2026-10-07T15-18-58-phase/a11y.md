# a11y extract

## Relevance
partial — the chunk adds no UI surface, markup, role, key binding or colour; it is in the domain through one reading (`disabled` told from the snapshot's `enabled`) and through the focus, hit-test and hidden-element rules its `covered`, `off-screen` and "refusal leaves the instance unchanged" claims lean on. §10, §11 and §12 read `> NO RECORDED INTENT` and the §3 violation-schema block reads `> NOT YET MEASURED`: nothing is extracted from them.

## Constraints
- a11y-plan §7 (Accessibility tree output — the snapshot-model bullet) requires `enabled` to follow the PRESENCE of `disabled` on an element that can be disabled, and states the driver's `disabled` cause on that same presence reading; the detection reads the snapshot's `enabled`, never the attribute's value and never a second disabled-ness test of its own. Whether the executor can reach that reading for the target without a second snapshot model is research's question.
- a11y-plan §5 (Focus order per layout — the "keyed two ways" bullet) requires disabled-ness to stay keyed two ways: element state and the pointer click target on the attribute's presence, focusability on its value parsed as a bool. So a control the driver refuses `disabled` can still be focusable and hold focus; the detection must not change focusability or the Tab order, and the scope's open `press` question (a focused control that is disabled) turns on this split — whether such a control exists on a lean stand screen is research's question.
- a11y-plan §5 (Script and framework exposure — the falsy-boolean-attribute bullet) requires a falsy Dioxus `disabled` to remove the attribute; a stand control rendered `disabled: false` must therefore read enabled and be acted on, not refused. Whether each stand control the chunk names as its `disabled` case carries the attribute by presence at the moment of the call is research's question.
- a11y-plan §5 (Focus restoration) records that a click moves or clears focus (a checkbox or radio click focuses the control; a click on a non-interactive area clears focus). A refused action dispatches nothing, so it must leave the focused reading exactly as it was — focus is a11y surface under the tier in a11y-plan §1 (SC 2.1.1 · 2.4.3). Whether the hit test or bounds read placed in front of the click moves focus or hover is research's question.
- a11y-plan §6 (Visibility and hit-testing) requires `visibility: hidden` / `collapse` elements never to be hit-test targets and `pointer-events: none` elements to be transparent to hits while their descendants are still tested. The `covered` reading must agree with those rules: an overlay that is transparent to hits does not cover its target, and a hit on a descendant of the target is the hit test's own answer, not a second covering rule in the driver.
- a11y-plan §4 (Per-component pattern catalog — Hidden content) requires `hidden`, `display: none` and `visibility: hidden` to exclude an element and its children from the accessibility tree, while `aria-hidden="true"` keeps the node and marks it hidden; a11y-plan §7 (Accessibility tree output — the diff clause) requires an element hidden and shown by `hidden` to leave and return with its descendants. An id whose element is excluded reads no snapshot node, which bears on decision 1 (`stale` against `not-found`) and on whether a hidden element can be `off-screen` or `covered` at all — research's question which cause such an id receives today.
- a11y-plan §2 (Accessibility tree lifecycle — the changed-set bullet) requires the changed set to hold exactly what a step marked, with hover, layout and a harness settle marking nothing. A refused action must leave that set as it found it, so no platform-tree refresh is owed to a call that did nothing; whether the detection's reads mark it is research's question.

## Patterns to follow
- A11y assertions are Rust tests in blitz-tests over the AccessKit tree, built with the `accessibility` feature — per a11y-plan §3 (A11y testing tool pick); the new refusal checks sit in that crate, beside the stand checks.
- Roles, input names and rendered ids the stand checks expect are stated once in the shared module's tables — per a11y-plan §7 (Accessibility tree output — the `author_id` bullet); a new check reads those tables, never restates a role or a name.
- The stand's own disabled case is asserted without colour (the Book button gaining `disabled` after a typed non-date) — per a11y-plan §8 (Error recovery); the `disabled` refusal is proven on such a state reached through real input, enabled and disabled both.
- Focus is asserted as "exactly the focused control's snapshot node reads `focused`, and it is the tree's focus", in both layout modes — per a11y-plan §5 (Test harness pattern); the "instance unchanged" check for a refusal reuses that form.
- Every element an agent can act on reads an author key, checked by `DioxusDocument::unkeyed_actionable` — per a11y-plan §7 (Accessibility tree output — the actionable-key bullet); the minimal fixture's target and its covering element follow it.

## Anti-patterns to avoid
- No second role or name mapping: the driver's schema defines no role or name set of its own and every reader takes role and name from the snapshot — per a11y-plan §7 (Accessibility tree output — the snapshot-model bullet). A detection that classifies a target by tag or by its own interactive-role list breaks it.
- No telling `disabled` from the attribute's value or from focusability — per a11y-plan §5 (Focus order per layout — the "keyed two ways" bullet); the two keys disagree by design and only the presence reading is the cause's.
- No fixture or stand edit that changes a `tabindex`, role, accessible name or Tab order to manufacture a case — per a11y-plan §7 (Accessibility tree output — the `author_id` bullet, "Tab order unchanged"). (a11y-plan §11 holds no recorded bans; none is cited from it.)

## Contract bindings
- a11y ↔ architecture / security: the snapshot's `enabled` reading (a11y-plan §7, Accessibility tree output) is the source of the driver's `disabled` cause, whose wording lives in the driver schema (architecture §Standard Contracts — Driver session; security-plan §Input Validation, as the scope cites them). a11y-plan §7's clause "named and worded only, with nothing yet detecting it" is a status this chunk makes false — an amendment owed at the wrap.
- a11y ↔ tests: the `a11y` CI leg runs three named test files and adds no stand assertion — per a11y-plan §9; the new refusal checks run in the workspace test leg, and joining the a11y leg is not this chunk's unless the plan says so.
- a11y ↔ layouts / design: none — the scope touches no stand markup, id, class or style, so no focus-order or contrast pair is in play (a11y-plan §6's token-contrast block is `> NOT YET MEASURED`).
