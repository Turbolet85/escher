## Relevance
relevant — the chunk changes what the driver's executor refuses and may give the session a memory of ids; it stays in process, so it adds no crossing, but it touches three recorded clauses (security-plan §Input Validation, the Driver command schema row and the `id` row; §Error Handling, the `Refusal` bullet).

## Constraints
- **Validate first, then detect, and a refused call runs nothing.** security-plan §Input Validation (Driver command schema row) requires `Session::run` to call `validate` first and return its refusal before anything else runs, and requires an id-level refusal to be returned "with nothing run". The four causes this chunk detects sit in that same position — after `validate`, in front of the click — and each must leave the instance unchanged. Whether a hit test, a bounds read or a viewport read can be made without dispatching anything or mutating the document is research's question.
- **No panic path and no clock on anything a call supplies.** security-plan §Input Validation (Driver command schema row) requires the executor to hold no `unwrap`, `expect`, `panic!` or `unreachable!` on call-supplied data and to read no clock; the `id` row of the same section requires the resolved node to be read through `get_node`, never by index. The detection's new reads (the snapshot's `enabled`, the hit test at the click point, the target's bounds, the viewport) are bound by both. Whether each engine reader the detection calls is itself panic-free on a node that no longer resolves is research's question.
- **A refusal holds nothing of the call, and the cause set stays closed at eight.** security-plan §Error Handling (Error format, the escher-driver `Refusal` bullet) requires `Cause`, `Fault` and `Refusal` to have no `String` field, each cause to carry a fixed `&'static str` name, meaning and remedy holding no path, and a `Fault` to carry at most the schema's own name for an argument. A detected `stale`, `disabled`, `covered` or `off-screen` therefore names its class only — no id, accessible name, control value, coordinate, bounds or covering element's id may be added to it.
- **The session's id memory is an amendment, never a silent add.** security-plan §Input Validation (Markup attributes `id` row) records as a property that the lookup is made anew on every call, that the session keeps no id and no `NodeId` between calls, and that no field of `Session`, `Outcome` or `Refusal` holds a `NodeId`. Decision 1 (telling `stale` from `not-found`) contradicts the first two clauses if it lands on a remembered set: the plan must then state what is remembered (text ids only, never a `NodeId`), what counts as "read", how long it lives and what bounds it — the plan holds no size or lifetime rule for such a memory today, only the 1 to 1024 byte bound on one `id` argument — and the clause is amended with the operator's decision cited.
- **In process only: nothing of a refusal crosses the socket.** security-plan §Input Validation (Driver session socket row) requires the wire to stay `hello` and `stop` with no element id, accessible name, control value, snapshot text or diff on it; §Error Handling (the `Refusal` bullet) records a refusal as held in process only. The chunk must leave the wire grammar, the reply shape and the listener untouched.
- **The crate stays silent about ids, names and values.** security-plan §Input Validation (Driver command schema row) requires that nothing in escher-driver prints, logs or fields a `Command`, `Call`, `ArgValue` or `Outcome`, each of which prints ids, typed text, names or values under `Debug`. security-plan §Logging & Monitoring (escher's own sink) adds the reason a field would not be caught: under an `escher_*` target the sink redacts a fixed list of field names and `id` and `name` are not on it. The detection adds no log line, span, event or `Debug` print.
- **`disabled` is the snapshot's presence reading.** security-plan §Input Validation (Markup attributes `disabled` row) requires `NodeState::enabled` to follow the attribute's presence — a `disabled="false"` and a bare `disabled` both read `Some(false)` — and never the focusability parse. The `disabled` cause is told from that reading alone; a second, attribute-value reading in the executor would split the answer.

## Patterns to follow
- **Refuse in one fixed order, one answer per call.** security-plan §Input Validation (Driver command schema row) records `validate`'s shape — the first failure in a fixed order, one answer per call; the screen-level causes follow it, with the order stated in the plan so that a target holding two causes at once always reads the same one.
- **Resolve, then read, never hold.** security-plan §Input Validation (Markup attributes `id` row) records the lookup as a linear search of `element_ids()` and a `get_node` read, with an unresolved node refused and no panic; security-plan §Error Handling (Graceful degradation) records stale node ids resolving to `None` through `get` and hit testing returning early when there is no DOM. Every new read in the detection takes the same shape: a miss is a refusal or a skip, never an index.
- **A step that ran and did not go quiet is a result, not a refusal.** security-plan §API Security (Settle and loads in flight row) requires that no driver command waits on a load, that no verb carries an argument or result field of a wait, and that `settled: false` stays an outcome. Detection decides before the step and never waits for a target to become enabled, uncovered or visible; if decision 2 lands on an action that brings its target into view, that scroll is part of the one settled step.
- **A verb joining the table is bounded like the five.** security-plan §Input Validation (Driver command schema row) requires a closed `'static` table whose every argument is one of five kinds with a stated bound. If decision 2 lands on a sixth verb, each of its arguments takes a kind and a bound, it passes through `validate`, and the row's "five verbs" clause is amended with the operator's decision cited.
- **The mask holds on the refused path.** security-plan §Input Validation (Markup attributes, password and file `input` value row) requires typed text to occur nowhere in what a driver call returns. A `type` aimed at a refused target dispatches no text, and the refusal it returns holds none.

## Anti-patterns to avoid
(security-plan §Security Anti-Patterns reads `> NO RECORDED INTENT`; nothing is taken from it. The bans below come from the sections cited.)
- **No call-supplied or screen-read text in a refusal, or in anything that prints one.** No `String` field, formatted remedy, id, name, value or coordinate in `Cause`, `Fault` or `Refusal` (security-plan §Error Handling, the `Refusal` bullet).
- **No `NodeId` kept across calls.** A session memory, if decision 1 grants one, holds text ids; a `NodeId` field on `Session`, `Outcome` or `Refusal` is banned (security-plan §Input Validation, Markup attributes `id` row).
- **No detection by dispatch.** Probing a target by sending it a pointer event, or acting and then reading the diff to decide whether to refuse, breaks "refused with nothing run" (security-plan §Input Validation, Driver command schema row).
