## Relevance
relevant — the chunk's proof is integration checks over a held driver session (test tier `0`, per test-plan §1 Test Scope Summary), it changes the expectation of two standing `stand_act_*` files, and its two reserved decisions each land on a unit-pinned table or a keyed contract clause.

## Constraints
- **Where the proof lives.** test-plan §1 (escher-driver) requires the executor's verbs and refusals to be covered by the `stand_act_*` integration files in blitz-tests, not by a unit test in the crate — a unit test there cannot build a held instance. A unit test in `execute.rs` is admissible only for a pure table (as the key table is); a detection that needs a screen is proven through `Session::run` on a booted session.
- **What a refused call must show.** test-plan §5 (Session ↔ held instance) requires a refused call to leave the instance unchanged and to read as a text holding none of the bytes the call supplied, in both layout modes, with no sleep and no wall-clock read in the check. Each of the four newly returned causes owes the same three readings the four refusals named there carry today.
- **The 77-node acceptance row is the measure of a false refusal.** test-plan §1 (tests/blitz-tests, `stand_act_ids`) states a driver `click` naming the id of every node of the four lean tasks' snapshots as accepted, and each control's diff as equal to a twin's selector click — empty for the controls a click does not change, the disabled ones among them. Under this chunk that row's expectation changes for the disabled controls; which other nodes turn refused (a container whose click point hits a descendant, a node with no box) is research's question, and the plan's answer to "another element" decides it.
- **The deleted-row expectation is pinned.** test-plan §1 (tests/blitz-tests, `stand_act_refused`) states the id of a row the driver just deleted as refused `not-found`, in a table of four refused calls. Decision 1 (`stale`) changes that row; the table stays a stated table with its row count, whichever way the decision lands.
- **The keyed contract states the opposite of a remembering session.** test-plan §3 Session lifecycle (`session-start`) requires an id to be looked up among the ids the screen reads now, and a refused call to have run nothing. Decision 1 amends that clause; a detection in front of the click must keep "a refused one has run nothing". `session-proof` counts the six driver-action files and moves with any file or test added.
- **A reworded text or a sixth verb turns unit pins red by design.** test-plan §4 (escher-driver) requires refusal.rs to pin the eight causes in order with each name, meaning and remedy against a stated table (remedies pairwise distinct, no `/`), schema.rs to pin five verbs in a stated order with their shapes, and command.rs to pin `validate`'s first-failure order. Decision 2 moves those stated tables in the same change, with the recorded reason; a change that leaves them untouched while the texts move is a failing leg.
- **In-process checks run on every platform leg.** test-plan §1 (Surfaces under test → Native platforms) requires the windows and macOS matrix to run the workspace's tests, and test-plan §2 (Process-lifecycle checks) reserves the `cfg(unix)` gate for checks that start a host process. A refusal check holds its session in process and carries no platform gate.
- **Counts are re-measured, never forecast.** The chunk stales the counted rows at test-plan §1 (escher-driver; tests/blitz-tests), §3 Session lifecycle (`session-proof`), §3 Agent-run contract (Proof), §5 (Session ↔ held instance, its list of refused causes) and §9 (Local baseline); the report owes the readings those rows are amended from, taken from the run's own listing.

## Patterns to follow
- **Shared session builders.** A check declares `mod session_common;` and builds its calls with the module's builders and `act(session, call)`, whose result is `None` for a refused call; a session is booted with `hold(task, incremental)`. A builder more than one file needs goes there, not into a second copy (per test-plan §3 Crate-local test helpers, blitz-tests session checks). Tables of controls and rendered ids come from `mod common;` and are stated expectation, never a second mapping (per test-plan §3 Crate-local test helpers, blitz-tests stand checks).
- **A minimal fixture is in-file and booted with the stand's options.** The cases the lean tasks lack are proven on a fixture inside the check's own file, booted with `stand::options(incremental)` — the pinned 800 × 600 viewport, scale 1.0, bundled font, no net provider (per test-plan §1 tests/blitz-tests, the in-file fixtures of `stand_snapshot_state`, `stand_diff`, `stand_act_diff`; per test-plan §7 Builders and options). The covered fixture, and an off-screen one if research finds no lean-task case, follow it.
- **The check holds the driver's answer against its own reading.** The standing driver checks compare what a call returned with the check's own `before.diff(&after)` and with a twin driven by selector (per test-plan §1 tests/blitz-tests, `stand_act_diff` and `stand_act_ids`). For a refusal that is: the check states, from the harness's inspection surface (`hit` · `hit_node` · `layout_rect` · `center_of`, per test-plan §3 blitz-test-harness, Inspection helpers), that the fixture's target really is covered or outside the viewport, then asserts the cause. Whether those readers answer what the executor needs is research's question.
- **`disabled` is proven on the presence reading, through the app.** The snapshot's `enabled` reading is pinned as not enabled for a present `disabled` attribute whatever its value, and on the stand as not enabled until the app enables the control (per test-plan §1 dioxus-native-dom, the snapshot builder tests; per test-plan §1 tests/blitz-tests, `stand_snapshot_state`). The refusal follows the same two edges: refused while the reading is not enabled, accepted after the app enables it.
- **A mutation control per detection.** The executor's standing proof records controls that each turn a named check red (per test-plan §4 escher-driver). Each of the detections added here owes one — the detection removed, its named check red — recorded in the chunk's evidence.

## Anti-patterns to avoid
- **A sleep, a wall-clock read, or a pump or tick of the check's own around a driver call.** The driver checks move time only through `advance` and delivered ticks, and settle neither advances nor waits (per test-plan §5 Session ↔ held instance; per test-plan §8 Hand-written fakes and stubs, Time (seven_guis timer)). The same holds for a skip path: a stand check asserts unconditionally under the bundled font (per test-plan §2 Font-dependent tests).
- **An id, a name, a value or a coordinate in a test name or an assertion message.** Assertions over a call carry a row index only, so a failing log prints no argument value (per test-plan §4 escher-driver); a test's name is written into the agent-run `test` event and `events.jsonl` (per test-plan §3 Agent-run contract, Events).
- **Reading a selection that ran nothing as green.** `run` passes only when cargo exited 0, no test failed and at least one test line parsed; a new file is selected by its `stand_` prefix and `session_common/` is not a target (per test-plan §3 Agent-run contract, `run`).

(test-plan §11 Test Anti-Patterns holds no recorded intent; the three above are stated by the sections cited.)

## Contract bindings
- **tests ↔ architecture.** test-plan §3 Session lifecycle (`session-start`, `session-wire`) restates architecture §Standard Contracts → Driver session: the per-call lookup, "a refused one has run nothing", and nothing of a call or an outcome on the socket. An amendment under decision 1 moves both in one cascade.
- **tests ↔ security.** The "none of the supplied bytes" assertion of test-plan §5 (Session ↔ held instance) and the row-index-only assertions of test-plan §4 (escher-driver) are the checks behind security-plan §Input Validation's rule that a refusal holds nothing of the call.
- **tests ↔ obs.** Agent-run events are harness metadata, not an escher-telemetry sink, and nothing between `failures:` and the next result line reaches an event (per test-plan §3 Agent-run contract, Events → obs-plan §3). The chunk adds no log line; test-plan §3 Stand log format's zero-id, zero-name reading for the sink-installing binaries is unchanged by it.
- **tests ↔ a11y.** The `disabled` cause reads the snapshot's `enabled`, whose pins are test-plan §1 (dioxus-native-dom; tests/blitz-tests `stand_snapshot_state`) → a11y-plan §7. Those pins state a disabled element as still focusable, so a `press` on a focused disabled control is reachable — whether it is refused is the plan's question (scope, "Which actions"). The `a11y` CI leg's three files are not touched (per test-plan §9 Pipeline facts, Legs).
