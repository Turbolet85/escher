# a11y extract

## Relevance
relevant: the snapshot's id, role, name and focused/enabled state are read from the accessibility surface, so it either re-exposes that surface or contradicts it. The chunk adds no painted UI, key binding or focus behaviour.

## Constraints
- The tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3`, and `accessibility` stays a default feature of blitz-dom and both Dioxus crates. The workspace takes the Dioxus crates with `default-features = false`, and the seven_guis stand binary names no `accessibility` feature, while blitz-tests builds blitz-dom and dioxus-native-dom with it (per a11y-plan §1 A11y Scope Summary). Research must answer two questions. Does the snapshot's role/name source exist in the build the stand proof runs under? What does a feature-off build get (scope already marks the second one as a P4 decision)?
- **Role** follows a11y-plan §2 A11y Strategy (Role derivation). The engine takes the `role` attribute first, then the HTML-AAM element mapping, then `Role::Unknown`. A recorded TODO says a `role` attribute can override strong native semantics, which goes against WAI-ARIA 1.2. The snapshot role must be that same reading, not a second mapping. Whether the snapshot carries the TODO's behaviour through or works around it is research's question.
- **Name** follows a11y-plan §7 Screen Reader Support (Accessibility tree output):
  - A trimmed, non-empty `aria-label` becomes the `label`, and a whitespace-only one names nothing.
  - A bound `<label>` is pushed onto its `<input>`'s `labelled_by` after the whole tree is built.
  - Text nodes become `TextRun` nodes, and they label their parent.
  - The snapshot name must resolve the same name. That includes the `labelled_by` indirection and the deferred label binding, so neither can be dropped.
- **Id** follows a11y-plan §7 (Accessibility tree output). In a Dioxus document, every element node carries its stable element id as AccessKit `author_id`. No `TextRun`, document-root or `Window` node carries one, and the `Window` root's id is `u64::MAX`. Every snapshot node must carry a non-empty id, so research must answer two questions. Do text runs or roots become snapshot nodes, and if so, where do they get an id? The current build maps 15 stand controls, each with an HTML-AAM role and a non-empty name in both layout modes. The snapshot must keep that mapping as it is.
- **Visibility/inclusion** follows a11y-plan §4 ARIA Patterns & Roles (Hidden content) and a11y-plan §6 Visual Design Verification (Visibility and hit-testing):
  - `hidden`, `display: none` and `visibility: hidden` exclude a node and its descendants.
  - `aria-hidden="true"` keeps the node but marks it `is_hidden`.

  The scope's P4 inclusion fork has to agree with those rules. A snapshot node for an element that AT never sees needs a stated reason.
- **State: focused** follows a11y-plan §5 Keyboard Navigation (Focus order per layout). Focusing an element sets the `FOCUS`/`FOCUSRING` element states. a11y-plan §7 says the tree reports the focused DOM node as tree focus. Focus order is SC 2.4.3 surface, so the `focused` field must mark the same node the engine treats as focused.
- **State: enabled** follows a11y-plan §5 (Focus order per layout and Script and framework exposure). The engine keys disabled-ness in two ways:
  - The `DISABLED`/`ENABLED` state and the click target use the attribute's presence.
  - Focusability uses the attribute's value parsed as a bool.

  A falsy Dioxus `disabled`/`checked` attribute is removed. Other Dioxus booleans, `hidden` among them, are written as the literal `"false"`. This chunk fills `enabled` from one of these readings, and the choice should be named here, but proving it correct is v010-05's job.

## Patterns to follow
- The AccessKit-tree assertion pattern in a11y-plan §3 A11y Assertion Harness Contract (A11y testing tool pick): call `build_accessibility_tree()` after `resolve`, match `tree_update.nodes` on `role()`/`is_hidden()`, and use the `assert_role` and `unknown_tags` helpers. This is the oracle a snapshot-vs-AccessKit equality check is built from.
- The stand identity check described in a11y-plan §7 (Accessibility tree output): stand controls are asserted by `author_id`, role and non-empty name `for incremental in [false, true]`, with the Tab order unchanged. A new `stand_snapshot*.rs` check should use the same shape.
- The focused-node query in a11y-plan §3 (Focus management test harness, `blitz-test-harness` inspect) is an independent oracle for the snapshot's `focused` field.
- State asserted without colour, from a11y-plan §8 Cognitive Accessibility (Error recovery). The headless-stand check asserts flight booker's invalid date through the `invalid` class and the `disabled` attribute, not through red styling. Snapshot state should be read from DOM/element state the same way, never from painted colour.
- The `Document::accessibility_tree` trait-method route in a11y-plan §2 (Accessibility tree lifecycle) is how DioxusDocument's override reaches consumers. A snapshot built from the accessibility tree must call that method so it gets `author_id`, not blitz-dom's base builder.

## Anti-patterns to avoid
- Do not key snapshot nodes on `NodeId` or on the AccessKit `NodeId(node_id.as_u64())` interop mapping. a11y-plan §3 (A11y testing tool pick) and a11y-plan §1 (blitz-traits node ids) record that mapping as a test convenience. The stable element id is `author_id` (a11y-plan §7).
- Do not derive role or name a second time in a way that can disagree with the AccessKit tree, for example by mapping roles from tag names again or by ignoring `labelled_by`. a11y-plan §2 (Role derivation) and a11y-plan §7 (Accessibility tree output) record the single source.
- Do not read a Dioxus boolean attribute other than `disabled`/`checked` by presence, `hidden` included. The literal `"false"` would read as set (a11y-plan §5, Script and framework exposure). (a11y-plan §11 A11y Anti-Patterns reads NO RECORDED INTENT, so it adds no bans.)

## Contract bindings
- a11y ↔ tests: the new stand snapshot check lives in `tests/blitz-tests/tests/` beside the stand accessibility check described in a11y-plan §7. CI's `a11y` leg runs a fixed named list (`accessibility_hidden`, `accessibility_roles`, `focusability_updates`), per a11y-plan §9 CI Integration. Whether the snapshot check joins that list or stays only in the workspace `test` leg is a decision this chunk must make (it touches `ci-leg.sh` and the CI-script contract tests).
- a11y ↔ obs: the accessible names and `value` the snapshot carries are user content. Any span on the snapshot build logs counts only, under the CLAUDE.md telemetry warning. a11y-plan defines no violation-JSON schema, so the chunk binds to no a11y violation log.
- a11y ↔ layouts: stand focus/Tab order must stay unchanged (a11y-plan §7 records it as asserted unchanged). This chunk reads focus and must not move it.

## Acceptance criteria contributions
- For every stand control in counter, flight booker, timer and CRUD, the snapshot node with a given id has the same role and the same resolved accessible name as the AccessKit node whose `author_id` equals that id. This holds for `incremental in [false, true]` (per a11y-plan §7 Screen Reader Support; a11y-plan §2 A11y Strategy).
- After the harness focuses a stand control, exactly one snapshot node reads `focused = true`, and it is the node the harness's focused-node query reports (per a11y-plan §3 A11y Assertion Harness Contract; a11y-plan §5 Keyboard Navigation).
- No snapshot node exists for an element that the accessibility tree excludes as `hidden`, `display: none` or `visibility: hidden`, unless the P4 inclusion rule states a reason (per a11y-plan §4 ARIA Patterns & Roles).
- The `a11y` leg's three tests and the stand accessibility identity check still pass unchanged, with the 15 controls' roles, names and Tab order intact (per a11y-plan §9 CI Integration; a11y-plan §7 Screen Reader Support).
