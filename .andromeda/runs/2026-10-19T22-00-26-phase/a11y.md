## Patterns to follow
- Shared stand tables are stated once in `tests/blitz-tests/tests/common/mod.rs` and read by every check that needs them, as `tab_order` was moved there (per a11y-plan §8 Cognitive Accessibility, Error recovery). The fixture boot and the shared fixtures follow the same "stated once" shape.
- One shared reader classifies several stated tables, each asserted row for row with its count (per a11y-plan §6 Visual Design Verification, Color contrast; per a11y-plan §3 A11y Assertion Harness Contract, state checks with their row counts asserted).
- Every moved check still runs in both layout modes, as the a11y checks do (per a11y-plan §3 A11y Assertion Harness Contract).
- Keyboard-driven stand checks go through the harness's `press` / `press_with` and read the focused node back per step (per a11y-plan §3 A11y Assertion Harness Contract, Keyboard test harness). A shared fixture that a check types into keeps that input path.

## Anti-patterns to avoid
- Widening or narrowing the a11y leg's `--test` list, or its job, as a side effect of a test move. The leg's six files and its unchanged job are recorded on the founder's F4 (per a11y-plan §9 CI Integration).
- Restating a shared stand table (focus order, contrast rows) file-private again in a moved check, which would undo the 2026-10-13 move (per a11y-plan §8 Cognitive Accessibility, Error recovery).
- Reading `has_changes()` straight after a shared fixture boot as "the step changed something" without draining first (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
