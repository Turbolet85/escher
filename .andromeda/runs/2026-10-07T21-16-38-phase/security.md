# security extract

## Relevance
relevant — the chunk gives `escher-driver` its first log emission, on the one code path that handles ids, typed text, accessible names and control values; no new boundary, listener, secret or auth surface is in scope.

## Constraints
- security-plan §Input Validation (row "Driver command schema (escher-driver)") requires that nothing in the crate prints, logs or fields a `Command`, a `Call`, an `ArgValue` or an `Outcome` — each derives `Debug` and prints ids, typed text, accessible names or control values. The span and any event stating its readings must therefore be built from fixed words and numbers only; whether a `#[instrument]` or a `?value` field anywhere on the `run` path would field one of the four is research's question.
- security-plan §Error Handling (the `Refusal` bullet under "Error format (typed errors)") requires the refusal cause to stay one of eight fixed `&'static str` names holding nothing a call supplied. The span's refusal field takes that name only. The same bullet states a refusal is "held in process only" and that nothing prints, logs or sends one: this chunk makes the cause name the first part of a refusal to reach a log, so that clause is an amendment this chunk owes, and a `Refusal` or `Fault` fielded whole is outside what the scope's three readings ask for.
- security-plan §Logging & Monitoring (the bullet "escher's own sink") requires an `escher_` target's record to print every field except a fixed content-named set — the scrub is by field NAME, not by value. A content value fielded under any other name prints in clear; so no id, key name, typed text, accessible name or control value may be a field value under any name, and no field may take an argument's schema name. Whether the sink as built judges a SPAN's fields by that rule at all, or only an event's, is research's question — a span-field path that bypasses the formatter's decision would be an unscrubbed path.
- security-plan §Input Validation (row "Markup attributes | `id` (stable element id)") requires that escher's own code write the stable id to no log, event, socket or file, that the platform accessibility adapter stay the only exit escher's own code gives the id, and that the session's record of ids be read by no public item and written to no log. The span adds no exit: the diff reading is three counts, never a `DiffNode`, an id, a parent or a removed-id list.
- security-plan §Input Validation (rows "`aria-label` · `<label for>` (accessible names)" and "password and file `input` value") requires that escher's own code log no accessible name and that a snapshot, its text and a diff reach no log, event, socket or file. The span fields nothing of an `Outcome`'s screen text or diff beyond counts; the mask (`MASKED_VALUE`) is a property of the snapshot model, not a licence to field a value.
- security-plan §API Security (row "Settle and loads in flight") requires a settle outcome to name a busy class only — no URL, request, node, id, name or value — and states settle reads no clock; security-plan §Input Validation (row "Driver command schema (escher-driver)") states the executor reads no clock. The span's settle reading is the class word and whether it went quiet. If the plan has the driver itself measure how long the wait took, the executor reads a clock: that contradicts a recorded clause and is a decision plus an amendment, not a silent add; whether a duration can come from the subscriber's own span timing instead is research's question.
- security-plan §API Security (opening paragraph and row "Local session socket (escher-driver)") and §Threat Model Summary (vector "local IPC — the driver session's socket") require the one listener's wire to stay lifecycle-only (`hello`, `stop`) and carry nothing of the screen. Nothing of a span, a call or an outcome crosses the socket, and the chunk adds no listener, port or IPC endpoint.

## Patterns to follow
- The sink's three-outcome target allowlist, stderr only, with `escher_`-prefixed targets admitted and every other target dropped whole — log the span's record under `escher_driver` and rely on no other target (per security-plan §Logging & Monitoring, bullet "escher's own sink"; §Bootstrap phases, `logging-redaction-wire`).
- Metadata-only log records: counts, fixed class words and identities, never an argument value — the shape the agent-run contract's events and the cold-agent stub's call log already take (per security-plan §Logging & Monitoring, bullets "The agent-run test contract" and "The cold-agent pipe").
- Refuse-first ordering with nothing run on a refusal: `validate` before anything else, then the executor's fixed refusal order. A span opened in front of `validate` must not change that order or make a refused call touch the instance (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- Dependency edges inherited with `workspace = true`, `Cargo.lock` committed, every cargo leg `--locked`, and the advisory audit re-read on every push — the `tracing` edge into `escher-driver` follows it (per security-plan §Dependency Security, "Pinning" and "CI integration").
- `RUST_LOG` as the one environment read, through `escher_telemetry`'s filter, non-secret; the driver library reads no env var of its own (per security-plan §Secret Management, "Environment values read").

## Anti-patterns to avoid
- Fielding a `Command`, `Call`, `ArgValue`, `Outcome` or a caller-supplied verb string with `Debug` or `Display` — including through an instrumented function's arguments — or naming a span field after an argument (per security-plan §Input Validation, row "Driver command schema (escher-driver)").
- Treating the scrub set as a safety net for content: a value placed under a field name outside the content-named set prints unredacted under an `escher_` target (per security-plan §Logging & Monitoring, bullet "escher's own sink").
- Putting an id, name, typed text or value into a panic or assertion message in a process where the sink is installed: the chained std panic hook prints the raw panic message to stderr, outside the scrub (per security-plan §Logging & Monitoring, bullet "escher's own sink"). Whether the check's writer-capturing install also chains that hook is research's question.

## Contract bindings
- **obs ↔ security (scrubbing):** the span's field names and target bind to obs-plan §4 (the owed span) and §8 → Scrubbing; the content-named field set and the target allowlist are stated once in security-plan §Logging & Monitoring and must read the same in both after the chunk.
- **tests ↔ security (the leak check):** the stand check that reads captured sink text is the security proof of this chunk; it binds to test-plan §1 / §4 and must carry no id, name, value or typed text in a test name or assertion message.
- **arch ↔ security (resources):** no new listener, port, env var or workspace crate — architecture §Occupied Resources stays unchanged; architecture §Standard Contracts (Driver session: "silent"; Telemetry) changes with the security-plan clauses below.
- **security-plan amendments this chunk owes at wrap:** §Input Validation, row "Driver command schema (escher-driver)" (the "nothing in the crate prints, logs or fields" clause, and "reads no clock" if a duration is measured in the driver); §Error Handling, the `Refusal` bullet ("nothing prints, logs or sends one yet"); §Logging & Monitoring, bullet "escher's own sink" (what an `escher_driver` record prints; the "typed text is not measured … where no sink is installed" clause, since the check runs `type` in process with the sink's formatter installed — the sink-installing HOST's reading stays unmeasured, per the scope's boundary).

## Acceptance criteria contributions
- (security) Driver commands run on a stand task with escher's formatter installed over a captured writer — at least a `click` and a `scroll` by id, a `type` of a known text, and a refused call naming an id — leave captured text holding 0 occurrences of each stable id, accessible name, typed text and control value those commands handled, in both layout modes and at the most verbose level the check sets (per security-plan §Logging & Monitoring)
- (security) Every refused call's record carries a cause value that is one of the eight cause names and nothing else of the refusal or the call; a source census of `packages/escher-driver/src` finds no `Command`, `Call`, `ArgValue`, `Outcome` or `Refusal` fielded with `Debug`/`Display`, no `#[instrument]` on a function taking a `Call`, and no field named `id`, `text`, `key`, `shift` or `ms` (per security-plan §Input Validation)
- (security) A refused call still changes nothing with the span in place: the existing refused-call checks (snapshot and both focus readings unchanged, nothing run) pass unedited (per security-plan §Input Validation)
- (security) `bash .github/scripts/ci-leg.sh audit` passes; the `tracing` dependency in `packages/escher-driver/Cargo.toml` is `workspace = true`; and the `Cargo.lock` diff adds an edge only, no new package — whether it does is read from the diff (per security-plan §Dependency Security)
