## Relevance

## Constraints
- The new check is one test-target file per behaviour under `tests/blitz-tests/tests/`, and its stem carries the `stand_` prefix and matches the selection pattern so `run stand` picks it up with no script change (per test-plan §1 → tests/blitz-tests; per test-plan §3 → Agent-run contract → `run {selection}`).
- A check that runs a driver call through `Session::run` runs in both layout modes and holds no sleep and no wall-clock read; in a Timer flow it makes no pass but the driver's (per test-plan §5 → Session ↔ held instance). A settle-wait reading that is a duration therefore cannot be asserted against a clock in the check — which readings of the wait are assertable is research's question.
- `escher-driver` cannot build a held instance at unit level, so the span of a real call is proven in the `stand_*` integration files, not by a unit test in the crate (per test-plan §1 → escher-driver). What stays unit-testable there is pure and tabular: a table stated in its test with its row count asserted, inline in a `#[cfg(test)] mod tests` of the source file (per test-plan §4 → Conventions → Test file location; per test-plan §4 → What unit tests cover → escher-driver).
- The sink's behaviours are process-global and test-plan §1 places them in integration files of their own, never inline unit tests (per test-plan §1 → escher-telemetry). Whether one once-per-process install can serve every `#[test]` of the new file, or the check needs its own test binary re-run on one `#[ignore]` child, is research's question; the child form carries the whole of test-plan §2 → Process-lifecycle checks (bounded waits, the kill-and-reap guard, child streams to null unless read, `cfg(unix)`).
- A `tests/blitz-tests` file is compiled and run on the windows and macos matrix legs, not on linux alone, so an in-process check must hold there ungated (per test-plan §1 → Surfaces under test → Native platforms); only a process-lifecycle form is `cfg(unix)`-gated (per test-plan §2 → Process-lifecycle checks).
- test-plan §3 states `Harness::settle` as reading no clock but the harness's, advancing no time and logging nothing, and its return as `Settled { passes, animating }` or `NotSettled { busy }` (per test-plan §3 → blitz-test-harness (`Harness`) → Pump semantics). A span reading taken inside `settle` would contradict that statement and its unit pins (per test-plan §4 → What unit tests cover → blitz-test-harness); whether the driver can read the wait from settle's return alone is research's question.
- If the plan edits `escher-telemetry`'s formatter, the stated log-line format and the stated per-level readings of the two sink-installing binaries are requirements the edit must keep, and the five `telemetry_*` files, `host_log` and `host_binary` are the standing checks of them (per test-plan §3 → Stand log format). `stand_session_quiet` requires that the session library's path write nothing of the screen when no sink is installed (per test-plan §5 → Session host ↔ what it writes); whether a `tracing` call site in `escher-driver` keeps that with no subscriber is research's question.

## Patterns to follow
- Build calls and read their results through the shared session module — `hold`, the call builders, `act`, `refused`, `refused_unchanged` — declared with `mod session_common;`; extend that module only for what a second reader would share, and keep a per-file `SECRET` per file (per test-plan §3 → Crate-local test helpers → blitz-tests (session checks); per test-plan §3 → Crate-local test helpers → blitz-tests (stand checks)).
- State the expected diff from the check's own `before.diff(&after)` and hold the call's returned diff equal to it; a diff-size reading in the span record is then compared with that count, never with a literal alone (per test-plan §5 → Session ↔ held instance).
- Read the leak needles from the stand itself, booted in the check's own process — stable ids, accessible names — and report a failure as a kind and a count only (per test-plan §5 → Session host ↔ what it writes). Typed text and a password come from an in-file fixture booted with the stand's options where the tasks lack the case (per test-plan §1 → tests/blitz-tests, `stand_act_diff`).
- Drive `advance` through the stand's time step, which `hold` gives the Timer's session, and the `time-unavailable` refusal through a session carrying none; time moves by delivered ticks only (per test-plan §8 → Hand-written fakes and stubs → Time (seven_guis timer)).
- Prove each new check red first by a mutation control recorded in the chunk's evidence — the plan records them per chunk for the schema and for the executor (per test-plan §4 → What unit tests cover → escher-driver); and re-measure, never forecast, the counts the plan carries: the crate unit counts, `run stand`'s `run.end` and the workspace result lines (per test-plan §3 → Agent-run contract → Proof; per test-plan §9 → Local baseline).

## Anti-patterns to avoid
- No assertion message, test name or failing log that prints a call-supplied value: an assertion over a call carries a row index only, and a refused call's text holds none of the bytes the call supplied (per test-plan §4 → What unit tests cover → escher-driver; per test-plan §5 → Session ↔ held instance).
- No sleep, no wall-clock read and no pump or tick of the check's own inside an acting flow — a delivered tick is applied by the next pass, and settle neither advances the timer nor waits on one (per test-plan §5 → Session ↔ held instance; per test-plan §8 → Hand-written fakes and stubs → Time (seven_guis timer)).
- If a child process is used: never wait for its exit before reading a sink-installing host's pipes, and never let the child's libtest lines reach the parent's output, where the agent-run parser would count them as tests (per test-plan §2 → Process-lifecycle checks).

## Contract bindings
- tests ↔ obs: the line format the check reads from the captured sink — time, level, target, service identity, then fields, with the target allowlist and the redaction applied — is stated in test-plan §3 → Stand log format and owned by obs-plan §3 and §8; a span record's shape and field names are obs's, the check that reads them is tests'.
- tests ↔ obs: the agent-run events are harness metadata, not an escher-telemetry sink, and carry no scrub-set key; nothing between a `failures:` line and the next result line reaches an event (per test-plan §3 → Agent-run contract → Events) — a span record never becomes an event field.
- tests ↔ security: the row-index-only assertion rule and the kind-and-count failure form are the test-side half of the rule that nothing of a call or an outcome is printed (per test-plan §4 → What unit tests cover → escher-driver; per test-plan §5 → Session host ↔ what it writes); the rule itself is security-plan's.
- tests ↔ arch: the statement that `escher-driver` depends on nothing naming a virtual DOM fixes where its executor is tested (per test-plan §1 → escher-driver); the new `tracing` edge is arch's, its test placement is unchanged by it.
- The keyed contract `Session lifecycle` (test-plan §3) is not bound: nothing of a call, an outcome or a span crosses the socket in this chunk.
