# obs extract

## Relevance
relevant — obs-plan §4 names this route entry as the owner of the one span per driver command, and §8 → Scrubbing is the layer its record must pass; the plan holds no naming convention, no budget and no recorded anti-pattern list for it, so those are the plan's to set from research.

## Constraints
- obs-plan §4 Span / Trace Coverage (the `packages/escher-driver` line) requires one span per driver command, covering the command — the executor and the settle wait each acting verb runs; it records both as carrying no span today, so whether the crate is still span-free and `tracing`-free at HEAD is research's question, not a fact this extract attests.
- obs-plan §4 Span / Trace Coverage fixes the value domain of the span's refusal-cause field: one of the eight fixed cause names, class words that hold nothing a call supplied. No other value may reach that field.
- obs-plan §4 Span / Trace Coverage requires that no argument be fielded under its schema name and that no command, call or outcome value be fielded through `Debug` — it states what each would print, and that only one of the argument names is in the sink's scrub set (§8), so the scrub is not a backstop for the rest.
- obs-plan §8 PII Scrubbing & Compliance → Scrubbing requires the record to be logged under a target the sink's allowlist admits as an escher target (the `escher_` prefix set; the driver's own target is named there as admitted). A record under any other target is dropped whole at every level — so an absent line must first be ruled against this rule before it is read as a missing call site.
- obs-plan §8 PII Scrubbing & Compliance → Scrubbing governs field names under an escher target: every field prints as written except the content-named set, which prints redacted. A span field must therefore be named outside that set on purpose (a count or a class word that lands in it prints as redacted and proves nothing), and must carry only fixed words and numbers, since a name outside the set is printed unjudged.
- obs-plan §6 Log Coverage → Log format (escher's sink) defines what the sink writes as one line per printed event, on stderr, with the service identity, every field passing the §8 scrub, and the level taken from `RUST_LOG` with the default stated there. The section speaks of events only; whether the sink as built writes anything for a span, and whether a span's fields reach the scrub decision at all, is research's question — the plan does not answer it.
- obs-plan §3 Observability Harness Contract → Logging stack (subscriber installation) records the session library, its executor, the settle loop, the stand checks and their shared session module as installing no subscriber, taking no `tracing` dependency and printing or logging nothing, and records the sink as installed by two binaries only, stderr only, nothing on stdout. This chunk ends the "silent" half of that statement for the driver: the stderr-only / nothing-on-stdout half stays binding, and the statement itself is owed an amendment at the wrap.

## Patterns to follow
- A hand-written escher event with a fixed message and a small set of fixed-word or numeric fields, as the telemetry crate's own install and panic events are recorded (obs-plan §6 Log Coverage → Logged events → escher-telemetry) — the shape a per-command record should take if the plan states the span's readings on an event.
- A call record that holds a sequence, a verb word, an outcome word and a cause word and never an argument value (obs-plan §6 Log Coverage → Log format (the cold-agent pipe), the stub's call log) — the same discipline for the span: verb from the table, cause from the eight names, sizes as counts.
- A check that reads a sink's output into its assertions only and reports a failure as a kind and a count, never as what was written (obs-plan §3 Observability Harness Contract → Logging stack, the `host_log` check) — the form the new captured-writer check should take, so a failing run prints no id, name or value.
- The two recorded ways a crate takes `tracing`: behind a cargo feature with a no-op path, as the engine crates do, or unconditionally, as the telemetry crate does (obs-plan §2 Telemetry Strategy → Telemetry mechanism). Which the driver takes is the plan's; whichever it is, the binaries' engine `tracing` features stay off as that section records.

## Anti-patterns to avoid
- Fielding an argument by its schema name, or a command, call, argument value or outcome through `Debug` (which an instrumented function does to its arguments unless each is skipped) — banned by obs-plan §4 Span / Trace Coverage.
- Emitting the record under a target outside the allowlist — the stand's own module path included — or reading the resulting silence as proof that nothing leaked (obs-plan §8 PII Scrubbing & Compliance → Scrubbing; the same section's "Values logged as-is" records that a dropped record writes zero bytes).
- Treating the sink's redaction as the guard for content: a field relies on the scrub only if its name is in the content-named set, and typed text in a sink-installing host's log is recorded as not measured (obs-plan §8 PII Scrubbing & Compliance → Values logged as-is) — this chunk's in-process reading does not close that.

## Contract bindings
- obs ↔ security: the span's record is the first driver-originated log content; obs-plan §8 Scrubbing binds to the security plan's clauses that nothing prints, logs or fields a refusal, a call or an outcome — those clauses need the cause name and the counts carved out and nothing else.
- obs ↔ tests: the new check installs the escher formatter over a captured writer in a test process, which obs-plan §3 Logging stack records no stand check or shared session module doing today; the test plan owns where that check lives and how a once-per-process install is isolated from the other checks in its binary.
- obs ↔ tests (existing readings): obs-plan §8 Values logged as-is records the `escher-session` host's line counts by level, and §3 Logging stack records `host_log` as the check reading that host at `trace`. That host runs no command, so no per-command record is expected in it; whether the driver's new `tracing` edge changes those counts is research's question, and the check must still pass.
- obs ↔ architecture: the Driver session contract's "silent" wording and the Telemetry contract's account of what the sink prints both move with obs-plan §4 and §6.
- obs-plan §3 Bootstrap phases (derive for route / setup-project): `otel-sdk-install` — no OTel crate, egress or credential path may enter with the span; `pii-scrubbing-wire` — recorded as discharged for escher's own sink, and the span's record must stay inside that discharge.

## Acceptance criteria contributions
- Each of the six verbs run through the executor leaves exactly one record in the captured sink output, under the driver's `escher_`-prefixed target, in both layout modes; a refused call leaves one too (per obs-plan §4 Span / Trace Coverage).
- A refused call's record carries a cause equal to one of the eight fixed cause names and to the cause the call returned; a call that ran carries none; an acting verb's record carries its settle reading and a diff size equal to the counts of the diff the call returned (per obs-plan §4 Span / Trace Coverage).
- The captured sink text holds none of the stable ids, accessible names, typed text, keys or control values the commands handled, no field named by an argument's schema name, and no field printed as redacted (per obs-plan §8 PII Scrubbing & Compliance → Scrubbing).
- Every record is one line in the sink's format with the service identity, written to the sink's writer only — nothing on stdout — and silent at the default level unless the chosen level is at or above it (per obs-plan §6 Log Coverage → Log format (escher's sink)).
