## Constraints
- test-plan §5 Integration Test Strategy → "Session host ↔ what it writes" names this route entry as the owner of the check `stand_session_quiet` does not make: that file's host installs no log sink, so its `RUST_LOG=trace` is inert and its green says nothing about a host that installs escher's sink. The chunk's check must therefore run against the real sink-installing binary and search stderr for a stable id and an accessible name; typed text stays outside it (test-plan §5 → "Session host ↔ what it writes" records it as not measurable yet).
- test-plan §2 Test Strategy → "Process-lifecycle checks" requires a check that captures a sink-installing host at `debug` or below to drain its pipe while the host runs, or to capture to a file — a wait-for-exit-then-read shape blocks on the unfixed binary instead of failing. The red-before-green run of this chunk depends on that shape.
- test-plan §2 Test Strategy → "Process-lifecycle checks" requires every such check to start and stop its own host, bound every wait, hold the host behind a guard that kills and reaps it, keep its state directory under `CARGO_TARGET_TMPDIR` and removed at `stop`, send any child stream it does not read to null, and be `cfg(unix)`-gated. Reaching the package's own binary is through `CARGO_BIN_EXE_*`, which only that package's own tests see.
- test-plan §3 → Session lifecycle (`session-binary`, `session-state`, `session-checks`) fixes what the new check may assume of the host: the argv shape and task set, exit `0` after `stop`, stdout empty on every path, stderr lines stamped with the service identity, a state directory holding the socket alone while up and absent after `stop`, and a short state-directory path (the socket address bounds its length).
- test-plan §1 Test Scope Summary → "escher-telemetry" places the sink's decision branches in inline unit tests of the crate and its process-global behaviours in the four `telemetry_*` integration files of blitz-tests. The drop rule's proof follows that split: decision branches (native `tracing` and bridged `log`, engine target, escher target, outside target) as unit tests; anything that needs an installed global subscriber as an integration file. Whether the existing unit and integration checks emit under targets the new allowlist drops is research's question — the plan records their count and subject, not their targets.
- test-plan §3 Test Harness Contract → "Stand log format" is the plan's statement of what the two seven_guis binaries write, and it records that `host_binary` exercises `escher-session`'s format and empty stdout. Whether `host_binary`'s service-identity assertion still has a stderr line to read once outside-allowlist records are dropped (which target and level that line comes from) is research's question; the check must stay green without weakening the assertion.
- test-plan §9 CI Integration → "Local pre-push gate" and "Legs" bind the work to `bash .github/scripts/ci-leg.sh fast` and the `doc` leg, every cargo leg `--locked`; test-plan §1 Test Scope Summary → "Native platforms" records that the windows and macos matrix legs also run the workspace's tests, so a new check that spawns the unix-only host must compile and be gated out, not fail, off unix.

## Patterns to follow
- `examples/seven_guis/tests/host_binary.rs` is the standing precedent for a check that spawns `escher-session` through `CARGO_BIN_EXE_*`, run as `cargo test -p seven_guis --locked --test host_binary` (per test-plan §1 Test Scope Summary → "apps (rdme, bump, examples, accesskit_xplat)"; test-plan §2 Test Strategy → "Directory pattern"). The blitz-tests module `tests/session_common/mod.rs` (bounds, state-dir helper, the `Host` guard) belongs to another package's test tree (per test-plan §3 Test Harness Contract → "blitz-tests (session checks)"); whether the seven_guis check reuses `host_binary`'s own helpers or needs its own is research's question.
- One test-target file per behaviour, named for the behaviour, with the bug and its measurement documented at the top of the file (per test-plan §2 Test Strategy → "Directory pattern" and "Test function naming").
- Inline `#[cfg(test)] mod tests` beside the code under test, built-in harness with `assert!`/`assert_eq!`, no third-party test framework (per test-plan §4 Unit Test Strategy → "Test file location"; test-plan §3 Test Harness Contract → "Rust tests").
- A process-global behaviour that needs its own process uses the test binary re-run on one `#[ignore]` child (per test-plan §2 Test Strategy → "Process-lifecycle checks"; the telemetry files' ignored child is counted at test-plan §9 CI Integration → "Local baseline").
- The windowed binary's one recorded reading is a bounded boot smoke — `RUST_LOG={level} timeout 10 target/debug/seven_guis_native`, exit 124, read from stderr — recorded as evidence with its form (per test-plan §3 Test Harness Contract → "Stand log format"). The by-level measurement of this chunk extends that form; whether any part of it can become a repeatable check is research's question.

## Anti-patterns to avoid
- Reading a zero from a host that installs no sink as proof about one that does (per test-plan §5 Integration Test Strategy → "Session host ↔ what it writes"; test-plan §3 → Session lifecycle `session-checks`).
- Letting a spawned child's libtest lines reach the parent's output, or waiting for the host's exit before reading a pipe it is still filling — `agent-run.sh` counts stray lines as tests, and an undrained pipe turns a red check into a hang (per test-plan §2 Test Strategy → "Process-lifecycle checks").
- Counting an empty or zero-test run as a pass (per test-plan §3 Test Harness Contract → "`run {selection}`").
