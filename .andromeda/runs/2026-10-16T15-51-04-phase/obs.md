# obs extract

## Relevance
partial. The chunk is a structural refactor that adds no instrumentation. It does move the site of one of escher's two spans (`tool_call`, in `mcp.rs`) and the modules beside it, and it must keep both spans, their target and their log lines exactly as the plan states them. `document.rs`'s log sites stay in upstream's untouched body.

## Constraints
- obs-plan §4 requires the `tool_call` span to stay built by hand with `tracing::info_span!(target: "escher_driver", "tool_call", tool = Empty, ending = Empty)`. It is opened and entered once per MCP `tools/call` only, before that request's params are read, and held until its reply is written. It has exactly two fields, `tool` and `ending`, both closed words. An instance verb's `command` span stays its child by nesting. Splitting `mcp.rs` must keep where the span opens and closes relative to the params read and the reply write. Whether the split moves the span site into a submodule is research's question (per obs-plan §4).
- obs-plan §4 requires the `command` span to stay unchanged: target `escher_driver`, name `command`, level INFO, opened before `validate` and held until `run` returns, with its eight fields `verb` · `cause` · `settled` · `busy` · `passes` · `added` · `removed` · `changed`. Each field is recorded only where it applies. The split of `schema.rs` must not change the table words and `Cause::name` words the span records (per obs-plan §4).
- obs-plan §6 (Log format) puts the span's target in every printed line (`{time} {LEVEL} {target} …`). A span site moved into a child module must therefore keep its explicit `target: "escher_driver"`, or the line's target text changes to the module path. The sink still admits such a target by its `escher_` prefix (per obs-plan §8 → Scrubbing). Whether every span site in the moved code names its target explicitly is research's question (per obs-plan §6).
- obs-plan §3 (Logging stack) requires escher-driver to install no subscriber and read no env var. The `schema` module also reads no clock and prints nothing. `serve_mcp`'s replies are written only by the crate's hand writer, and `serde_json` reads requests and writes nothing. Every new submodule split out of `mcp.rs` or `schema.rs` inherits that silence (per obs-plan §3).
- obs-plan §2 (Telemetry mechanism) requires escher-driver to keep taking `tracing` ungated: `{ workspace = true }` and no `[features]` table. The split adds no feature gate, no `#[cfg(feature = "tracing")]` around a driver span and no telemetry dependency (per obs-plan §2).
- obs-plan §4 records `serve_mcp` itself and the rest of its protocol (`initialize` · `ping` · `tools/list` · a protocol error outside a tool call) as writing no span, event or line of their own. The framing, listing and result-writing submodules must stay that way (per obs-plan §4).
- obs-plan §2 (Telemetry mechanism) requires each blitz-dom log site to be compiled only under `#[cfg(feature = "tracing")]` with a no-op path when the feature is off. The cited `document.rs` sites sit in upstream's body, which this chunk leaves byte-for-byte, so the move must not touch them (per obs-plan §2).

## Patterns to follow
- The span is built by hand with `info_span!` and an explicit `target: "escher_driver"`, with no `#[instrument]`, and its fields are created `Empty` and recorded where they apply (per obs-plan §4).
- The in-process span recorder in `stand_mcp_tools` is a hand-written `tracing::Subscriber` (`Recorder`) under `with_default`. It checks that each `tool_call` is the parent of its `command`, and a mutation that leaves the span unentered turns it red. It is the existing guard that the split keeps the span's nesting (per obs-plan §3 Logging stack; obs-plan §4).
- The silence census for check files is 0 env reads, 0 prints and 0 subscribers per file, by the probe `println!|eprintln!|print!|dbg!|std::env|env::var|escher_telemetry|tracing_subscriber|UnixListener|TcpListener|bind\(`. If escher's `document.rs` test modules move to a `blitz-tests` target, the new file follows it, as each newly arrived target has (per obs-plan §3 Logging stack).
- Stderr is read at `trace` under both builds, `-p seven_guis` and `--workspace`, by `mcp_log` and `host_log`. The readings: one `tool_call` line per call, `command` lines unchanged, 0 id, name, typed-sentinel and base64 needles (per obs-plan §6 escher-driver; obs-plan §8 Values logged as-is).

## Anti-patterns to avoid
- Adding or renaming a field on either span. Fielding an argument, `Command`, `Call`, `ArgValue`, `Outcome`, `Refusal` or `Fault` is also banned, including with `Debug`, while moving code: the plan lists these as never fielded (per obs-plan §4).
- Leaving a moved span or event on the default module-path target. Adding a span, event or log line to the MCP protocol path (framing, listing, result writing) as part of the reorganisation (per obs-plan §4; obs-plan §6 Log format).
- Installing a subscriber, reading an env var or printing from a new escher-driver submodule (per obs-plan §3 Logging stack).

## Contract bindings
- obs ↔ tests: `tests/blitz-tests/tests/stand_mcp_tools.rs` (the `Recorder`), `tests/blitz-tests/tests/stand_act_spans.rs` (the sink over an in-memory capture in its re-run children), `examples/seven_guis/tests/mcp_log.rs` and `examples/seven_guis/tests/host_log.rs` all read the two spans' records. The split must leave them green unedited (per obs-plan §3 Logging stack; obs-plan §6).
- obs ↔ security: the scrub sets and the "never fielded" list bind to security-plan §Input Validation (the driver's two log-record spans). `tool` and `ending` stay outside the content-named set (per obs-plan §8 Scrubbing).
- obs ↔ tests (feature wiring): an inline blitz-dom test runs with `blitz-dom/tracing` on under a workspace build. A test moved to a `blitz-tests` target runs with it off under `cargo test -p blitz-tests`, so the move can change which feature set the moved tests compile under. Whether any moved test depends on that is research's question (per obs-plan §2 Feature wiring).
- obs ↔ reconcile: the plan cites span sites by line, `packages/escher-driver/src/mcp.rs:537-540` and `packages/escher-driver/src/mcp.rs:598-632` (§2, §4, §6). These citations move with the split and are the wrap's to re-point (per obs-plan §4).
