# a11y extract

## Relevance
relevant. The chunk changes the AccessKit tree (an id on each node) and the role and accessible name of every stand control. Both are a11y surface under the tier-0 target (per a11y-plan §1 A11y Scope Summary). SC 4.1.2 is not one of the tier's three criteria, so roles and names are a stand requirement here, not a tier mandate.

## Constraints
- a11y-plan §1 A11y Scope Summary sets tier 0: SC 2.1.1 · 1.4.3 · 2.4.3. Adding names to the stand must leave focusability and Tab order unchanged. Under a11y-plan §5 Keyboard Navigation → Focus order per layout, focusability depends on the element kind, `tabindex`, `href` and `disabled`. So a name fix (`aria-label`, `<label>`) must not add a `tabindex` or swap the element kind of a control.
- a11y-plan §2 A11y Strategy → Role derivation requires a node's role to come from its `role` attribute, else the HTML-AAM element mapping, else `Role::Unknown`. "Non-`Unknown` role" is measured against that path. Which stand controls currently fall to `Unknown` is research's question.
- a11y-plan §7 Screen Reader Support → Accessibility tree output records three things: text nodes become `TextRun` nodes that label their parent, element nodes carry their tag, and the root is a `Window` node with id `u64::MAX`. The "no id on text or root" rule has to hold for both of those non-element node kinds. Whether the parent-labelled-by-TextRun path gives a button a non-empty accessible name, and whether `<label for>` or `aria-label` gives inputs, selects, sliders and progress meters a name at all, is research's question. §4 records only label→`Label` as a role.
- a11y-plan §1 (blitz-traits node ids) and §3 A11y Assertion Harness Contract (the `assert_role` helper) both use `NodeId::as_u64()` as the AccessKit key. The stable id must ride alongside that key without changing what the key means.
- a11y-plan §2 → Accessibility tree lifecycle says the tree is rebuilt on poll when the document has changed, with `changed_nodes` as the documented change set. The coherence check after a re-render binds to that refresh path. Whether an incremental update re-carries the id on changed nodes is research's question.
- a11y-plan §1 and §2 → Feature exposure: `accessibility` is a default feature in blitz-dom, and dioxus-native-dom only forwards it. The id carrier and any hook crossing between the two crates must compile out cleanly behind that feature.
- a11y-plan §4 ARIA Patterns & Roles → Hidden content: `aria-hidden` keeps a node in the tree but marks it hidden, while `hidden`, `display: none` and `visibility: hidden` drop the node. The proof's set of element-bearing nodes is therefore the set of built nodes, not the set of DOM elements.

## Patterns to follow
- The test shape in a11y-plan §3 A11y Assertion Harness Contract: call `build_accessibility_tree()` after `resolve`, then match `tree_update.nodes` with `test_that` matchers. Reuse the `assert_role` mapping (`NodeId` → AccessKit `NodeId(as_u64)`) and the `unknown_tags` helper for the non-`Unknown` assertion. The harness already builds blitz-dom with `accessibility`. A headless tree read would sit beside the focused and hovered queries in the harness's inspect module (§3 Focus management test harness).
- The per-component mapping in a11y-plan §4 → Per-component pattern catalog gives each lean-four control its expected role: button, input by `type` (text, number, range), select (ComboBox unless `multiple`), progress, and the list elements. Assert against that mapping rather than a role list invented for the test.
- The stand-check style in a11y-plan §8 Cognitive Accessibility → Error recovery: assert a cue as structure (an attribute or class), never as colour.
- The CI placement in a11y-plan §9 CI Integration: the `a11y` leg runs a fixed, named test list. Whether the new `stand_*` file joins that list or runs only in the workspace test leg is a P4 call. The bootstrap key `a11y-ci-gate-wire` is already discharged (§3 Bootstrap phases).

## Anti-patterns to avoid
- Do not force a role by putting a `role` attribute on a native control. a11y-plan §2 → Role derivation records a TODO: native strong semantics can currently be overridden, contrary to WAI-ARIA 1.2. Native elements with a label or `aria-label` are the safe fix.
- Do not replace a native control with a clickable `div`, the pattern a11y-plan §4 → Application markup records in the browser app. It loses the HTML-AAM role and the native focusability (§5 Focus order per layout).
- Do not write a Dioxus `hidden: false` in stand markup. a11y-plan §5 → Script and framework exposure records that it is written as the literal `"false"`, which a presence read takes as set and which would drop the node from the tree. This is recorded but not established.

## Contract bindings
- a11y ↔ tests: the proof check is a blitz-tests assertion over the AccessKit tree (a11y-plan §3 A11y Assertion Harness Contract), run `for incremental in [false, true]`. Whether it is wired into the `a11y` CI leg binds to a11y-plan §9 CI Integration and to the tests plan's CI legs.
- a11y ↔ arch: the id source is the Dioxus DOM bridge (`element_id` / `element_ids`, arch §Standard Contracts → Dioxus DOM bridge). Carrying it into blitz-dom's tree build (a11y-plan §1 blitz-dom accessibility tree) is a new provider or hook, so it binds to arch's `DocumentConfig` provider contract.
- a11y ↔ obs: the a11y plan defines no violation schema or log format, so it has no coverage here. Both the stable id and the accessible name are author content, and any tracing of them binds to the obs plan's allowlist scrub, which is the obs extractor's to state.

The count of such controls is non-zero and each named control is found by id (per a11y-plan §4 ARIA Patterns & Roles → Per-component pattern catalog; §2 A11y Strategy → Role derivation).

- The focusable set and the Tab order of each lean task are the same before and after the chunk's markup changes (per a11y-plan §5 Keyboard Navigation → Focus order per layout; §1 A11y Scope Summary, SC 2.1.1 · 2.4.3).
- `bash .github/scripts/ci-leg.sh a11y` still passes (accessibility_hidden, accessibility_roles, focusability_updates), including the semantic-page assertion that only `<html>` and `<body>` map to `Role::Unknown` (per a11y-plan §9 CI Integration; §2 A11y Strategy → Role derivation).
