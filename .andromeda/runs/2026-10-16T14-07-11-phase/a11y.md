# a11y extract

## Relevance
partial — the handler splits (A) move the engine's keyboard-activation, button-focus and range-input arms, which a11y-plan §5 records as the SC 2.1.1 / 2.4.3 surface; the README (B) carries no a11y surface.

## Constraints
- Tier 0 targets SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary); a refactor of the keyboard and focus arms has to keep SC 2.1.1 and SC 2.4.3 as they now read. It must not change them.
- The Enter / Space activation gates stay unchanged through the split of `handle_key_or_input_event` and `handle_key_up`'s routing. These gates are a pressed Enter on the focused `button`, `summary`, `input` of type `submit` · `reset` · `button` or `a` with `href`, and a released Space on `button`, `summary` or `input` of type `submit` · `reset` · `button` · `checkbox` · `radio`. Each needs no `disabled` attribute (presence). Arm order also stays: text input, then range, then activation. The Click still reaches the app's handlers before `handle_click` (per a11y-plan §5 Keyboard Navigation, Keyboard handling).
- The range input's key model stays as it is: ArrowRight/ArrowUp step up, ArrowLeft/ArrowDown step down, Home goes to min and End to max. It acts only when focused with no `disabled` attribute. Each change fires exactly one `input` event, a no-change move fires none, and each change marks the changed set (per a11y-plan §5 Keyboard Navigation, Keyboard handling).
- Focus restoration on click stays as it is through the split of `handle_click` and `handle_pointerdown`. A click on a `button` or an `input` of type `submit` · `reset` · `button` focuses it and ends the walk matched. A `disabled` attribute stops the walk first. A click on a range input focuses it and changes no value. A main-button pointerdown, after the `disabled` arm, sets the value from the hit's fraction. A click on any other element still clears focus (per a11y-plan §5 Keyboard Navigation, Focus restoration).
- Disabled-ness is read by presence everywhere: the element state, the pointer click target, Enter/Space activation and focusability. An extracted function must not switch to a value parse (per a11y-plan §5 Keyboard Navigation, Focus order per layout).
- A focus move, a checked change and a range value change each mark the changed set, and the shell's accessibility-tree refresh depends on those marks. An extracted arm must keep every mark it made (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).

## Patterns to follow
- `stand_keyboard` (`tests/blitz-tests/tests/stand_keyboard.rs`) is the behaviour pin for activation and focus. It covers the Tab walks against `tab_order` / `ENABLED_TAB_ORDER`, the 20 + 4 Enter/Space rows, click-focus, the disabled-presence rows and the `<div disabled tabindex=0>` limit pin. It should stay green unchanged in both layout modes (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- `range_input_interaction` (the 7-row keys table and 5-row clicks table, one `input` per change, focus after every click, disabled taking nothing) and `stand_act_range` pin the range arms. They should stay green unchanged (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- Run the a11y leg exactly as CI does: `bash .github/scripts/ci-leg.sh a11y`. It covers accessibility_hidden · accessibility_roles · focusability_updates · stand_keyboard · stand_contrast · stand_accessibility_ids, and its per-file counts are recorded. Compare the counts read after the split against the recorded ones (per a11y-plan §9 CI Integration).
- The headless refresh check in `stand_accessibility_ids` is the witness that the changed-set marks survive. After a drain, a Tab leaves `has_changes()` true and the tree's focus moves, and Enter on `counter-increment` rewrites `counter-value`'s name (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).

## Anti-patterns to avoid
- Do not change an a11y-recorded behaviour, such as an activation gate, a focus outcome, an `input` event count or a disabled-presence read, under a refactor label. Each is a founder-ratified engine change for every document (2026-10-13), so a needed change is a fork for the founder (per a11y-plan §5 Keyboard Navigation, Keyboard handling and Focus restoration).
- Do not edit or re-baseline the a11y pins (`stand_keyboard`, `range_input_interaction`, `focusability_updates`, the a11y leg's file list) to make a split pass (per a11y-plan §9 CI Integration).

## Contract bindings
