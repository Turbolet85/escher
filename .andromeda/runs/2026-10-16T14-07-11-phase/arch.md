relevant — part A is a refactor inside blitz-dom's events and node modules, on the merge surface of five ratified direct engine changes; part B rewrites the front page that arch §Project Intent → Front page describes.

## Constraints
- The range interaction model (its rules, its key, pointerdown and click default actions, and one `input` event per change with none for a move that changes nothing) and keyboard activation plus a button click's focus (the closed element/type matches, the `disabled` presence check, Enter handled after the text-input and range arms) are ratified direct engine changes for every document. A split must leave every one of them exactly as it is, per architecture §Established Decisions → [Scrolling and input]. Whether each arm the audit names sits where the plan's citations put it (events/keyboard.rs, events/pointer.rs) is research's question.
- `handle_click`, `handle_pointerdown` and `handle_key_or_input_event` keep their signatures. `BaseDocument::apply_range_move` stays the one write · mark · `Input` · redraw path for the range key and pointerdown arms. `dispatch_activation_click` stays the one path that queues the activation Click, so the app's handlers still run before `handle_click`, per architecture §Standard Contracts → Events.
- Extracted functions stay crate-internal (`pub(crate)` / `pub(super)` or private). `RangeRules`, `RangeMove` and the range helpers stay crate-internal, and `RangeInputData` stays the one exported range type with its one public method `value()`. No new public item and no new re-export, per architecture §Standard Contracts → Nodes and widgets and architecture §Conventions → Visibility and naming.
- No new crate, listener, env var or other registered name. The work stays inside `packages/blitz-dom` (`events/`, `node/range.rs`) and the root `README.md`, per architecture §Occupied Resources → Names and architecture §Infrastructure Patterns → Directory structure.
- The range and keyboard changes are flagged upstreamable against the upstream merge base. Their merge surface is `events/keyboard.rs`, `events/pointer.rs`, `events/mod.rs`, `node/range.rs` and the rest of the files the decision lists. The upstream-authored arms of the three handlers are not reshaped, so the next sync's diff stays confined to escher's own arms, per architecture §Established Decisions → [Scrolling and input] and architecture §Project Intent (Upstream sync line).
- The README stays escher's own page and keeps the elements the plan lists for it. These are: what escher is, built vs planned, how to run the driver's command line and the MCP role, `help` on both surfaces, its Blitz lineage, the licence, the Author / Contact section, and the fork's `ci.yml` badge as its one image. No build, doc or test step reads it, per architecture §Project Intent → Front page.
- Gates: fmt, workspace clippy `-D warnings`, upstream's blitz-dom clippy line (`--no-default-features … --all-targets`) and rustdoc `-D warnings` over the workspace all hold on the changed blitz-dom code, per architecture §Conventions → Formatting and lints and architecture §Inherited Defaults (Code quality).

## Patterns to follow
- Event-producing functions take a `dispatch_event` callback. An extracted arm that dispatches (focus events, `input`, the activation Click) takes the same callback as its parent instead of reaching for the driver, per architecture §Conventions → DOM API patterns.
- Modules open with `//!` docs, items carry `///`, and spec URLs are cited next to the implementation. The WHATWG range-state citations and the gate rationale move with the code they annotate into each named function and each `parse_float` step, per architecture §Conventions → Documentation.
- Unit tests stay in the `#[cfg(test)] mod tests` at the end of `node/range.rs`. The split `parse_float` steps are covered there, not by a new test file, per architecture §Conventions → Tests.
- Every behaviour check runs in both layout modes (`for incremental in [false, true]`), since incremental and non-incremental layout must stay identical, per architecture §Design Philosophy (One incremental pipeline, safe identities) and architecture §Conventions → Tests.

## Anti-patterns to avoid
- A behaviour change hidden in a refactor. This includes reordering the Enter arm ahead of the text-input or range arms, widening or narrowing an activation gate's element/type set, parsing `disabled` as a boolean instead of by presence, or adding an event for a no-op move. Each of these is an engine change for every document, which belongs to the founder, per architecture §Established Decisions → [Scrolling and input] and architecture §Established Decisions → [DOM semantics].
- Touching the upstream-merged entrants (`dispatch_hover_change`, `set_attribute` / `clear_attribute` and the others the scope names) or re-spelling the project's name outside the README's prose. Either one widens the upstream merge surface or edits plan text this chunk does not own, per architecture §Project Intent (Upstream sync line) and architecture §Project Intent → Front page.
