@extract_section name=relevance
relevant — a new read answered on the session socket, the command line, MCP and a kept check crosses the ratified local-IPC and MCP-stdio boundaries, and the verb-table change touches the closed command schema
@extract_section name=constraints
- The read must enter only through `validate` / `validate_session` against the closed `'static` verb table, with nothing public running a `Command` that did not come from `validate`; an `id` naming no element is refused with nothing run (per security-plan §Input Validation, "Driver command schema").
- What the read answers must be closed words and booleans (ids, verb names, refusal cause names, an owner's id), never an attribute's text, a password's or file input's unmasked value, or a `NodeId` (per security-plan §Input Validation, "Driver session socket"; and per security-plan §Threat Model Summary, the local-IPC and MCP-stdio vectors).
- The widening rule decides the boundary question: a new field of a closed value set inside an already ratified carrier is no widening, but a new verb, a new carrier, an open value set or authored text is a widening, and so the founder's fork (per security-plan §Input Validation, "Driver session socket — the widening rule").
- A refusal cause the read names must be one of the closed `Refusal` causes with its fixed name and remedy and no `String` field, so a cause cannot carry anything a call supplied; only its fixed name may reach a log (per security-plan §Error Handling, "escher-driver's command refusal").
- The schema and its validation must hold no `unwrap`, `expect` or panic on call input, read no clock and keep no `NodeId` between calls; the `command` span holds fixed words, bools and counts only, never the read's content (per security-plan §Input Validation, "Driver command schema — no unwrap").
- If the read is recordable, a kept check of it must stay owner-only (`0600` in a `0700` directory) and be read back only through the strict `Check::from_bytes`, every replayed step passing `validate` again (per security-plan §Data Protection, "Files (kept checks)"; and per security-plan §Input Validation, "Recorded check").
- The MCP listing and result for the read must stay bounded, with protocol errors a fixed code and message holding no `data`, and no print or panic outside the tests (per security-plan §Input Validation, "MCP server").
@extract_section name=patterns
- `lint` and `graph`: read-only verbs added on every ratified carrier as a ratified boundary widening; the precedent for how this read's carrier is brought to the founder (per security-plan §Threat Model Summary, the session-socket and MCP-stdio vectors' detail).
- The masked-value rule: a password's or file input's value reads as the fixed `MASKED_VALUE` on every carrier; any per-node control reading in the new answer follows it (per security-plan §Input Validation, "Markup attributes — a password's or file input's value").
- The stable element id: an author key or a positional path, computed on demand and written to no log, with no `NodeId` crossing; it is also the basis for the actionable-key check's author-key versus positional reading (per security-plan §Input Validation, "Markup attributes — the stable element id").
- Escher's own log sink: an allowlist subscriber that redacts content-named fields on `escher_` targets; a new field the read logs goes through it (per security-plan §Logging & Monitoring, "escher's own sink").
@extract_section name=anti_patterns
- No free-text or `String` refusal reason, and no reason text built from document content: the cause comes from the closed `Refusal` table (per security-plan §Error Handling).
- No second validation path beside `validate`, and no closed verb-name list outside the schema table that could disagree with the table the socket, CLI and MCP check against (per security-plan §Input Validation, "Driver command schema").
@extract_section name=bindings
- security ↔ arch: whether the new read is a new verb or a field on an existing carrier, and whether `VerbSpec` gains target or refusal metadata, is a contract and boundary change, the founder's fork; security sets the widening test, arch owns the shape (per security-plan §Input Validation, "the widening rule").
- security ↔ obs: the `command` span records `verb` and, when refused, `cause` alone; the field rules come from security-plan §Logging & Monitoring, and the span's schema belongs to obs.
- security ↔ tests: any committed check of a stand session holds no typed text, host path or secret, and no `screenshot` step (per security-plan §Data Protection, "Files (committed checks)").
@extract_section name=acceptance
- Every cause the read lists for a node is one of the closed `Refusal` cause names, and on the stand it equals the cause an actual call on that node and verb returns; the answer has no free-text field (per security-plan §Error Handling).
- On a fixture holding a password and a file input, the read's answer on the socket, CLI and MCP holds `MASKED_VALUE` or no value, never the typed text, its length or a host path, and holds no `NodeId` (per security-plan §Input Validation).
- A malformed or over-bound call to the read, or one with an unknown `id`, is refused through `validate` with nothing run and no panic, on the CLI (exit 1 or 2) and on MCP (fixed error, no `data`) (per security-plan §Input Validation).
- The founder's ruling on the carrier and the verb-table change is recorded before any new verb or open-valued field lands on a ratified carrier (per security-plan §Threat Model Summary).
