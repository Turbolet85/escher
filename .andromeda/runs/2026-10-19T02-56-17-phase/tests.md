# tests extract

## Relevance
relevant — the chunk adds a driver-session feature (a kept check written by the host, the command line and the MCP role) whose proof lives in the session checks, the process checks of `examples/seven_guis/tests/`, the stand-repeat leg and the escher-driver coverage floor; the folded CARRY is a blitz-tests clock check.

## Constraints
- A check that needs a session process starts and stops its own host (its test binary re-run on one `#[ignore]` child, or `CARGO_BIN_EXE_escher-session`), bounds every wait, holds the host behind a kill-and-reap guard, keeps its state directory under `CARGO_TARGET_TMPDIR`, sends the child's streams to null unless it reads them, and is `cfg(unix)`-gated when it holds a session over the socket; a check driving the `escher-session mcp` child goes through the shared `Speaker` and is not unix-gated (per test-plan §2 Process-lifecycle checks; per test-plan §3 Session lifecycle `session-checks`).
- test-plan §3 Session lifecycle `session-state` requires the state directory to hold `session.sock` alone while a session is up and to be absent after `stop` or the idle expiry, and test-plan §5 Session host ↔ what it writes requires `stand_session_quiet` to read nothing of the screen (typed text, a stable id, an accessible name) in that directory and a listing of `session.sock` alone. A kept check written there would move both readings, so where the check lives is a P4 fork. Whether `stand_session_quiet` asserts the listing exactly is research's question.
- test-plan §5 Session host ↔ what it writes requires a sink-installing binary (`host_log` for the host role, `mcp_log` for the `mcp` role) at `RUST_LOG=trace` to read 0 typed-sentinel occurrences, 0 id needles and 0 name needles on stderr under both the `-p seven_guis` and the workspace build, with exactly one `command` span line per call and one `tool_call` line per tool call. Recording must leave those counts as they are (per test-plan §5 Session host ↔ what it writes).
- test-plan §3 Stand log format requires stderr-only logging with closed span fields: `command`'s eight fields and `tool_call`'s `tool` and `ending`. A field, record or line that holds recorded content is outside the format (per test-plan §3 Stand log format).
- test-plan §3 Session lifecycle `session-proof` requires the in-process driver checks to run `Session::run` in both layout modes. A recorded-session check held in process follows that rule, and its counts are restated in `session-proof` at the wrap (per test-plan §3 Session lifecycle `session-proof`).
- test-plan §10 Flakiness budget requires the stand checks to hold a zero-failure budget over three rounds with no retry. A new `tests/blitz-tests/tests/stand_*.rs` file joins that leg by its prefix. A new seven_guis process check does not: the stand-repeat leg lists those checks by name (`cli_commands` · `cli_flow` · `host_binary` · `host_log` · `host_timer` · `mcp_server` · `mcp_log`), so adding one means adding its name to the leg (per test-plan §10 Flakiness budget).
- test-plan §10 Coverage floors requires `packages/escher-driver` to read at least 97 % line coverage at the `coverage` leg's floor. Recording code added to the crate is held to that floor (per test-plan §10 Coverage floors).

## Patterns to follow
- In-process session checks share `tests/blitz-tests/tests/session_common/mod.rs`: `hold(task, incremental)`, the call builders (`click`, `type_into`, `press`, `advance`, `scroll`, `snapshot`, `screenshot`), `act` · `shot` · `refused` · `refused_unchanged` · `focused`, and for a hosted session `state_dir`, `host_command`, `READY` · `EXIT` and the `Host` guard. Extend that module rather than adding a parallel helper (per test-plan §3 blitz-tests (session checks)).
- Process checks of the binary share `examples/seven_guis/tests/common/mod.rs`: the bounded `run` · `client` runner with its `Ran` result, the answer readers (`keys` · `number` · `cause` · `string_at`), the `Started` guard and `Speaker` for the `mcp` child. A new recording check reads through `mod common;` like the seven targets that exist now (per test-plan §1 Test Scope Summary, apps entry).
- The replayable-check shape that already exists is the cold-agent judge's: closed step keys (`tool` one of the eleven verbs, `arguments` an object, `expect` a list of strings), at most 400 steps, a malformed check never replayed, and replay on fresh `escher-session mcp` children with every step validated again, 30 s per reply, each child killed and reaped. A recorded-check reader meant for replay can mirror these limits (per test-plan §3 Cold-agent run pipe, The server and the check's judge).
- escher-driver unit tests sit inline in `#[cfg(test)]` modules. Each table is stated in its test with its row count asserted, every assertion over a call carries a row index only, and the chunk's new tests are seen red under named mutation controls with sha-equal restores. A recording format's writer and reader take the same discipline as `json.rs` and `wire.rs`: round trip, bounds at the edge, a strict decoder (per test-plan §4 escher-driver).
- The folded CARRY extends the clock checks: `virtual_clock_engine` is an engine check on a parsed page in both layout modes, reading the fade, the double click and the smooth scroll by the clock alone. The CARRY's sub-document carried clock, pan and fling reads join it in the same form (per test-plan §1 Test Scope Summary, blitz-tests clock checks).

## Anti-patterns to avoid
- Taking a zero read from a host that installs no log sink as proof that recording is never logged. That read says nothing about a host that does install one, so the never-logged claim is proven on the sink-installing `escher-session` (host and `mcp` roles), not on the re-run test binary (per test-plan §3 Session lifecycle `session-checks`; per test-plan §5 Session host ↔ what it writes).
- Putting an id, name, value, typed text or recorded content in a test name, an assertion message or a failure print. A failing check prints a row index, a kind or a count only (per test-plan §4 escher-driver; per test-plan §5 Session host ↔ what it writes).
- Letting a host child's own libtest lines reach the parent's output, where `agent-run.sh` would count them as tests (per test-plan §2 Process-lifecycle checks).
