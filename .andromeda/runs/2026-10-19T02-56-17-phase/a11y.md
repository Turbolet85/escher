# a11y extract

## Relevance
partial — session recording adds no UI surface, focus stop, colour or key binding. It touches a11y only through the screen readings a kept check may carry (role, name and state taken from the accessibility tree, a password's mask) and through the a11y and stand-repeat legs that its checks must leave unchanged.

## Constraints
- The a11y target is tier 0, SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary). A recorded `press` sequence (Tab, Shift+Tab, Enter, Space) replays an SC 2.1.1 / 2.4.3 path. The plan requires that path to stay the engine's own focus and activation behaviour: the recorder adds nothing to it and changes nothing in it.
- a11y-plan §7 Screen Reader Support (Accessibility tree output) requires the snapshot to take role, name, focus and the `selected` / `pressed` / `invalid` readings from the tree `accessibility_tree` returns, with no second role or name mapping. A kept check that stores step answers stores those readings as the snapshot and diff write them, and it does not derive them again. Whether the chosen file form keeps answers at all is a P4 question.
- a11y-plan §7 Screen Reader Support (Accessibility tree output) requires a password input to read the fixed `MASKED_VALUE` in the snapshot and the tree, with its typed text in no snapshot or tree field and no painted frame. Any screen reading a recording keeps must carry that mask. The `type` call's own text is call input, not a screen reading: how a recording holds it is the security plan's question. Whether the code already keeps the mask on every path a recording would read is research's question.
- a11y-plan §2 A11y Strategy (Accessibility tree lifecycle) states two facts: a freshly booted harness document's changed set is non-empty, and a settle neither reads nor drains it. A round trip that replays on a fresh session and reads `has_changes()` as "this step changed something" therefore drains first.
- a11y-plan §9 CI Integration fixes the `a11y` leg at six files with stated per-file counts. It also runs every `stand_*` file three times in `stand-repeat` under the zero-failure budget. A new `stand_*` recording check joins `stand-repeat` by its name, and the chunk leaves the a11y leg's files and counts as they are.
- a11y-plan §3 A11y Assertion Harness Contract makes accessibility assertions Rust tests in blitz-tests, run in both layout modes. A recording round-trip check on the stand that asserts any focus or tree reading follows the same rule.
- a11y-plan §7 Screen Reader Support (Accessibility tree output) states the driver's `disabled` refusal on the snapshot's presence reading of `enabled` and nothing else, so a replayed `click` or `type` is refused or accepted by the same reading. The recorder does not change refusal order or meaning.

## Patterns to follow
- Keyboard steps are driven through the harness's `press` / `press_with`, and the focused node is read back after each step, as `stand_keyboard` does (per a11y-plan §3 A11y Assertion Harness Contract, Keyboard test harness; a11y-plan §5 Keyboard Navigation).
- Expected focus, role and name values are stated once, in the stand checks' shared tables `tab_order`, `controls`, `INPUT_NAMES` and `REGION_NAMES` (`tests/blitz-tests/tests/common/mod.rs`). A round-trip assertion reads those tables and does not restate them (per a11y-plan §7 Screen Reader Support; a11y-plan §8 Cognitive Accessibility, Error recovery).
- The tree the shell hands the adapter is read through `&dyn blitz_dom::Document`, as `stand_accessibility_ids` reads it, wherever a check compares a replayed screen to the tree (per a11y-plan §7 Screen Reader Support).
- Every check runs `for incremental in [false, true]`, both layout modes (per a11y-plan §3 A11y Assertion Harness Contract).

## Anti-patterns to avoid
- Never hold a second role, name or state mapping in the recorder or its reader. Readings are stated expectations taken from the snapshot, never re-derived (per a11y-plan §7 Screen Reader Support).
- Never write a password input's typed text into any kept screen reading. The snapshot's `MASKED_VALUE` is the only value form (per a11y-plan §7 Screen Reader Support).
- Never read a fresh session's undrained changed set as a step's change in a replay check (per a11y-plan §2 A11y Strategy).

## Contract bindings
- a11y ↔ security: a password's `MASKED_VALUE` in every kept screen reading (a11y-plan §7) binds to the security plan's password handling, which the working entry names. Whether typed call text is kept at rest is the security plan's question.
- a11y ↔ tests: a new `stand_*` recording check joins `stand-repeat` (a11y-plan §9 ↔ test-plan §10 zero-failure budget). The a11y leg's six files are pinned by `LegScriptTest`'s a11y tuple in `.github/scripts/test_ci_workflows.py` and stay unchanged.

## Acceptance criteria contributions
- (a11y) `bash .github/scripts/ci-leg.sh a11y` reads green with its six files and per-file counts unchanged: accessibility_hidden 6 · accessibility_roles 6 · focusability_updates 4 · stand_accessibility_ids 8 · stand_contrast 5 · stand_keyboard 14 (per a11y-plan §9 CI Integration).
- (a11y) In the round trip, a stand session recorded with a `type` into a password input keeps `MASKED_VALUE` in every kept screen reading of that input. Its typed sentinel occurs 0 times in those readings, in both layout modes (per a11y-plan §7 Screen Reader Support).
- (a11y) A recorded keyboard session on a lean task, replayed on a fresh session, lands focus on the same ids in the order `common::tab_order` states, in both layout modes (per a11y-plan §8 Cognitive Accessibility, Error recovery; a11y-plan §5 Keyboard Navigation).
