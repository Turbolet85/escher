# security extract

## Relevance
relevant — the chunk adds a new at-rest carrier of driver call content and screen readings (typed text, a password's included) on both external driver surfaces (the session socket's host and the `mcp` stdio role).

## Constraints
- A kept check is a new carrier and a new exit. Per security-plan §Threat Model Summary (the "local IPC — the driver session's socket" and "local stdio — the driver's MCP server" vectors), every widening of what those surfaces carry, and of where it goes, is recorded as the founder's ratification. Per security-plan §Data Protection ("At rest — per medium"), the at-rest media the plan lists are the browser's sqlite history and the HTTP cache, and no driver-written file. So the check's medium, its content classes (call inputs; screen readings, if expectations are kept) and its location are a founder fork, and the plan needs an amendment to add the medium. Whether a recording can stay inside an already ratified carrier is P4's question.
- Owner-only at rest follows security-plan §Input Validation (the "Driver session state directory" row): a caller-named path passed as a parameter, never an env read or a cwd-relative default; a directory created `0700`; a present directory open to its group or others refused. The same row requires that `stop` and the idle expiry remove only the socket and then the directory, non-recursively, and that "nothing else is ever deleted". A check kept inside the state directory therefore conflicts with that teardown. Where the file lives, and whether it outlives `stop`, is research's question and then P4's.
- Password handling per security-plan §Input Validation (the "password and file `input` value" row). Every screen reading the driver hands out reads a password's or a file input's value as `MASKED_VALUE`: the snapshot, its text, the diff, socket answers, MCP results and the painted pixels. The text "reaches no log, event or file". A recorded screen reading (an expectation) must therefore hold the mask, never the typed text, its length or a file's host path. The row covers outputs only: a recorded `type` call's `text` argument is call input, and the plan states no at-rest rule for it. Keeping, masking or refusing a typed password in the record is a founder fork, and a masked input would not replay.
- The reader of a recorded check is a new input boundary. Per security-plan §Input Validation (the "Driver command schema" row), every step goes through `validate` or `validate_session` before it runs. Nothing public runs a `Command` that did not come from `validate`. No `unwrap`, `expect`, `panic!`, `unreachable!` or index may act on anything the file supplies.
- The read is bounded and closed per security-plan §Input Validation (the "Cold-agent check" row), the existing replayable-check precedent: a size cap, a JSON array, a step cap, closed keys, `tool` one of the eleven verbs, and anything outside these never replayed.
- Per security-plan §Logging & Monitoring (escher's own sink), the driver keeps exactly two spans. `command` has eight fields of fixed words and counts. `tool_call` holds `tool` and `ending` only. Content-named fields are redacted, and a record from any other target is dropped. Recording adds no field and no event that holds a check's content, a call's arguments, a screen reading or the check file's path. On a sink-installing binary, stderr carries no id, name or typed text at any `RUST_LOG` level.
- Per security-plan §Error Handling (the escher-driver `Refusal` row), a refusal and a session error hold only fixed `&'static` texts and nothing a call supplied. Any new failure from recording, such as an unwritable or unreadable check, follows that rule, with no path in its message. Per security-plan §Input Validation (the "Driver session state directory" row), `StateDirTooLong`'s fixed message holds no path.

## Patterns to follow
- The state-directory discipline per security-plan §Input Validation (the "Driver session state directory" row) and §API Security (the "Local session socket" row): `0700` / `0600` modes, refusal of a group- or other-open directory, the path as a parameter only. The MCP role takes no `--session` (per security-plan §Input Validation, the "CLI arguments (escher-session)" row: `mcp --session d` is usage), so giving it a location is an argv change under that row's closed reader, not an env read.
- The cold-agent check as the closest replayable form per security-plan §Input Validation (the "Cold-agent check" row) and §Logging & Monitoring (the cold-agent pipe row). Its features: closed-key steps `{tool, arguments, expect}`, a parse under hard byte and step bounds, a replay on fresh `escher-session mcp` children with every step re-validated by the server, and `check.json` written as parsed and never printed.
- Written forms come from the crate's hand-written JSON writer (`to_json`), and `serde_json` only reads, per security-plan §Input Validation (the "MCP server" row: "`serde_json` reading and writing nothing") and §Dependency Security (`serde_json` a root workspace dependency). A new crate for the file form goes through the cargo-deny audit per security-plan §Dependency Security.
- Leak proof by needle sweep per security-plan §Logging & Monitoring (escher's own sink): the `host_log` / `mcp_log` captures by build and level, counting typed sentinels, id needles, name needles and the first 64 base64 characters of a shot, each expected at 0.

## Anti-patterns to avoid
- Printing, logging or span-fielding a check, a call's arguments, a recorded screen reading or the check file's path; or writing a recording to stdout or stderr as a log line (per security-plan §Logging & Monitoring, escher's own sink).
- Taking the check's location from an env var or a cwd-relative default, or adding a read the plan does not list (per security-plan §Input Validation, the "Driver session state directory" row; per security-plan §Secret Management, "Environment values read").
- Writing a typed password, its length or a file input's host path into a recorded expectation; or replaying a step that skipped `validate` (per security-plan §Input Validation, the "password and file `input` value" row and the "Driver command schema" row).

## Contract bindings
- security ↔ obs: the two driver spans' closed field sets and the sink's target allowlist and scrub set (obs-plan §3; `packages/escher-telemetry/src/format.rs`). Recording must leave both unchanged.
- security ↔ tests: the stderr needle sweeps (`examples/seven_guis/tests/{host_log,mcp_log}.rs`) and the masked-password checks (`tests/blitz-tests/tests/stand_mcp_masked.rs`, `stand_act_filled`) extend to a recorded session. The session-lifecycle contract (`.andromeda/registries/contracts/test-plan/session-lifecycle.md`) holds the non-recursive teardown the check's location must respect.
- security ↔ arch: a new at-rest file resource, or any new argv flag or env read, is registered in `.andromeda/architecture.md` §Occupied Resources before it lands. The founder rules on the widening first.
- security ↔ next entry («Recorded-check replay»): the reader's bounds and its per-step re-validation are this chunk's input boundary, and the next entry's replay under agent-run, CI and stand-repeat relies on them.

## Acceptance criteria contributions
- A recorded check from a CLI-hosted session and from the `mcp` role is created owner-only: the file is not group- or other-readable, its directory is `0700`, and a group- or other-open location is refused with nothing written. The chosen location also survives, or is removed by, `stop` and the idle expiry exactly as the ruling states, and nothing else is deleted (per security-plan §Input Validation, the "Driver session state directory" row).
- A password typed through `type`, once on the command line and once over MCP, during a recorded session: every recorded screen reading of that input reads `MASKED_VALUE`. The typed text's occurrence count in the file matches the founder's ruling (0 under a mask-or-refuse option), and it appears 0 times in any recorded expectation (per security-plan §Input Validation, the "password and file `input` value" row).
- The stderr of the `escher-session` host and of the `mcp` role, during a recorded flow at `RUST_LOG=trace` under both builds, holds 0 typed-sentinel occurrences, 0 id needles, 0 name needles and 0 occurrences of the check file's path. The `command` and `tool_call` span field sets stay unchanged (per security-plan §Logging & Monitoring, escher's own sink).
- The check reader refuses each of the following with nothing run and no panic: an oversize file, a non-array file, a step with an unknown key, and a step whose `tool` is outside the eleven verbs. Every step it accepts reaches `validate` or `validate_session` before it runs (per security-plan §Input Validation, the "Cold-agent check" and "Driver command schema" rows).
