## Relevance
partial: no new API, secret, auth or dependency surface in scope, but every engine fix reads remote pages' markup in every document and its readings exit by ratified carriers, so the markup-attribute rows, the carriers' widening rule and the refusal texts bind; item 6's rows and CARRY 2 and 3 add no crossing unless a fork makes one.

## Constraints
- Any fix taken must stay inside the crossings the plan already records: no carrier, verb, argument, key name, result field, cause, session error, exit, log field or span added (the scope's `VERBS` twelve, `NODE_FIELDS` thirteen, eight causes). The widening rule separates a closed-value field in a ratified carrier from authored text, an open value set, a new carrier or a new exit; the latter set escalates to the founder as a boundary question. The rule decides widening only and exempts no engine change from its own P4 fork (per security-plan §Input Validation, Driver session socket widening rule; `.andromeda/security-plan-detail/input-validation.md:39`).
- Native checkedness (item 3): any `toggled` written from a native `checkbox` or `radio` must be a closed value carrying no attribute text, on the adapter crossing whose states the founder ratified on 2026-10-10. The plan's sentence that nothing else writes `toggled`, and its measured absence, move with the fix. Whether a fix moves `NodeState.checked` or `.pressed`, or any wire reading, is research's question; no windowed AT reading may be claimed from a headless proof (per security-plan §Input Validation, Markup attributes control-states row; `.andromeda/security-plan-detail/input-validation.md:222-224`).
- `inert` focus fixup (item 2): the plan's `inert` row requires a presence check only, with no value read, text carried out, print, log site, env read or panic path, and its known-limit sentence moves with a fix. Whether a fixup fires events that a remote page's script can observe is research's question, read against the script-execution vector (per security-plan §Input Validation, Markup attributes `inert` row; per security-plan §Threat Model Summary, script execution vector).
- Transformed scrolling box (item 1): transforms are remote-authored in every document, so any `visible_region` change must hold on degenerate input, a zero scale or a non-invertible or non-finite matrix included, with no panic path and geometry kept finite. Whether a scale is in the fix's reach is P3's to measure (per security-plan §Input Validation, Layout values and Paint values rows; per security-plan §Threat Model Summary, remote web content vector).
- Select limits (item 4): a `multiple` choice, an `optgroup` option, a painted popup, a clickable option or a new `change` each touches the `select` row's closed key match and its listed exits for the choice; a further exit is a boundary question. A `change` on a text input must leave a password's or file input's value masked on every carrier and out of every log, since a file input's `value` holds a host path (per security-plan §Input Validation, Markup attributes `select` row and password-and-file value row; per security-plan §Data Protection, Local user data handled).
- Refusal texts: moving the `off-screen` or `covered` meaning must keep each a fixed `'static` string holding nothing a call supplies, with the cause set, its order and the names unchanged; only a cause's fixed name reaches a log (per security-plan §Error Handling, escher-driver's command refusal row; `.andromeda/security-plan-detail/error-handling.md:8-9`).
- Select-option overlap (item 5): any `lint.rs` `overlaps` change must keep a finding to stable ids, closed defect words and numbers, with no `NodeId`, page text, colour or control value, and with no finding or count fielded on a span (per security-plan §Input Validation, Driver command schema row; `.andromeda/security-plan-detail/input-validation.md:58-59`).

## Patterns to follow
- A markup-attribute read in every document: a closed parse or presence check with no log site or panic path, exiting only as a closed enum or boolean (per security-plan §Input Validation, Markup attributes control-states and `inert` rows).
- An engine change's own record: stated as an engine change for every document and, where it widens, ratified with the founder's word, as the range-input and keyboard-activation rows record theirs (per security-plan §Input Validation, Markup attributes `input type="range"` and keyboard-activation rows).
- A choice or value change goes through one path, with its exits enumerated in the row: the model a `multiple` select or a checkbox `change` would extend (per security-plan §Input Validation, Markup attributes `select` row).
- A stated limit sits in the cause's fixed text and is pinned by a named test, and the text moves when the limit does (per security-plan §Error Handling, escher-driver's command refusal row).

## Anti-patterns to avoid
- An attribute's text, an option's label or a typed value reaching a log, span or print: the engine's log sites and the upstream subscribers include sinks that stay unscrubbed, so escher's sink allowlist is no licence to log it (per security-plan §Logging & Monitoring, Log format and backends, escher's own sink).
- A `String` field on a refusal, or a refusal text built from anything a call supplied (per security-plan §Error Handling, escher-driver's command refusal row).
- A new `unwrap`, `expect` or panic on what a page or a call supplies in a fix's added lines; the plan's Panic paths list is an inventory, not a licence (per security-plan §Error Handling, Graceful degradation and Panic paths; per security-plan §Input Validation, Driver command schema second row).
