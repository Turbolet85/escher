## Patterns to follow
- A stated table per behaviour with its row count asserted, read off the built tree, in both layout modes (per a11y-plan §3 A11y testing tool pick: `accessibility_states`, `accessibility_merged_states`).
- Drive keys through the harness's `press` / `press_with` and read the focused node back per step (per a11y-plan §3 Keyboard test harness; a11y-plan §5 Test harness pattern's `stand_keyboard` walk).
- Contrast rows read by `Harness::text_contrast` through one shared reader, exempt exactly where the snapshot's `enabled` reads `Some(false)` (per a11y-plan §3 Contrast verification harness; a11y-plan §6 Color contrast).
- Expected roles and names stated once, in the shared module's tables beside `tab_order` and `ENABLED_TAB_ORDER` (per a11y-plan §7 Accessibility tree output).
- Prove a tree change through `&dyn Document`, the path the shell hands the adapter, in the headless form the stand already uses, its windowed witness staying with its own residual (per a11y-plan §2 Accessibility tree lifecycle).

## Anti-patterns to avoid
- A second role or name mapping, in a check or in the snapshot's readers (per a11y-plan §7 Accessibility tree output).
- A second contrast formula, threshold or exempt rule for the served pages' rows or the lint (per a11y-plan §6 Color contrast).
- Reading `has_changes()` as "this step changed something" without draining first, a fresh harness document's set being non-empty (per a11y-plan §2 Accessibility tree lifecycle).
