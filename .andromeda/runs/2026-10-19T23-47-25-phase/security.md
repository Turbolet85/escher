# security extract

## Relevance
relevant — the inferred `lint` verb widens the driver's validated command surface and puts new content on every ratified carrier (socket answer, command-line stdout, MCP result, kept check), and it may add a read-only blitz-dom reader that runs on every document, remote pages included.

## Constraints
- Adding a verb to the closed `'static` verb table widens the validated surface. Each earlier verb (`scroll`, `screenshot`, `help`, the session verbs) went in only with the founder's ratification. A `lint` instance verb therefore needs his ruling before it lands, and its argument shape must use the six existing argument kinds and their bounds. `validate` keeps its fixed refusal order, has no panic path on anything a call supplies, and receives no `Session` (per security-plan §Input Validation, Driver command schema row).
- A finding's answer can rely on one rule for each carrier. A new field of a closed value set inside an already-ratified carrier is not a widening, so a finding may hold a closed defect-class word, booleans, measured numbers and stable ids. A field holding authored text, an open value set, a new carrier or a new exit is still a widening and goes to the founder. Quoting truncated text or naming a colour from page content would therefore be a fork (per security-plan §Input Validation, Driver session socket row).
- The answer bound applies to `lint` unchanged: 1,048,576 bytes on the socket's JSON line (past it `ok v3 oversize`, the call having run) and on an MCP result's text (`AnswerTooLarge`). On the stand at boot, and on a fixture with many findings, `lint` must stay under that bound. Whether the code already bounds a findings list is research's question (per security-plan §Input Validation, Driver session socket row and MCP server row).
- The password and file-input mask must hold on every reading `lint` writes. A finding about a password or file `input` must not carry its value, its length or its host path. The mask is `MASKED_VALUE` on every carrier and in a kept check's `answer` (per security-plan §Input Validation, Markup attributes: password and file `input` value row).
- The `command` span keeps its eight fields of fixed words, bools and counts. A `lint` call records `verb` and, if refused, `cause`. A findings count would be a new log field, and none of the following is ever fielded: an `Outcome` (`Debug` prints its ids, names and values), a finding, an id, or a reason (per security-plan §Input Validation, Driver command schema row; per security-plan §Logging & Monitoring, escher's own sink).
- Refusals stay closed at eight causes, each with fixed texts. A refused `lint` holds nothing a call supplied and leaves the instance unchanged. Adding a ninth cause would change that ratified set (per security-plan §Error Handling, Error format: escher-driver's command refusal).
- The strict reader `Check::from_bytes` accepts `tool` only from the seven instance verbs. It needs one of two decisions. Option one: `lint` joins that closed set, its `answer` kept whole at rest in the `0600` file and masked. Option two: `lint` is named as not recorded. Whether the reader and the replay already handle an eighth instance verb is research's question (per security-plan §Input Validation, Recorded check row; per security-plan §Data Protection, Files: kept checks).

## Patterns to follow
- Follow the `screenshot` verb as the template for a read-only instance verb. It runs no step, dispatches nothing, changes nothing and reads no clock. It is validated first inside `Session::run`, with an optional `id` resolved the way `click` resolves one (`stale` / `not-found`). It has one written form, hand-written `to_json`, and the MCP server writes it with no `serde_json` output (per security-plan §Input Validation, Driver command schema row and MCP server row).
- On the `escher-session` command line, `lint` should follow the existing pattern. Each ending (accepted, refused, usage, session error) writes back nothing the caller typed. The answer goes to stdout as one line of JSON. A write to a closed pipe is dropped, not a panic (per security-plan §Input Validation, CLI arguments (escher-session) row).
- A new read-only blitz-dom reader, such as one for truncated text, runs on every document, remote pages included. Like the `inert` and `aria-*` readers, it should carry no print, log site, env read or panic path, and it should carry no page text out (per security-plan §Input Validation, Markup attributes rows: `inert`, control states).
- The contrast reading should reuse `Harness::text_contrast`, which is read-only from computed styles, as `stand_contrast` does. It should not be a new paint or pixel path. A shot's pixels are the only image content already ratified to cross (per security-plan §Threat Model Summary, local IPC: the driver session's socket).

## Anti-patterns to avoid
- Do not put a finding's reason into a log or span field, whether as an id, a name, a value, a measured box or a contrast pair. Do not add a findings count to the `command` span without the founder's ruling (per security-plan §Logging & Monitoring, escher's own sink).
- Do not carry authored page text in a finding without a widening ruling: no truncated string, no label text beyond the snapshot's already-ratified `name` (per security-plan §Input Validation, Driver session socket row).
- Do not use `unwrap`, `expect`, `panic!` or `unreachable!` in the executor or the MCP server on anything a `lint` call supplies (per security-plan §Input Validation, Driver command schema row and MCP server row).

## Contract bindings
- security ↔ obs: the `command` and `tool_call` spans' fixed field sets, and the sink's scrub and drop rules, bind to obs-plan's driver span contract. A `lint` span reading is pinned by the in-process span capture and the host and `mcp` stderr needle runs (per security-plan §Logging & Monitoring).
- security ↔ tests: the masked-carrier measurements, the session-recording reader and replay, and the `help` / MCP listing of `VERBS` each bind to blitz-tests' and seven_guis' CLI, MCP and recording checks. A new verb moves those tables (per security-plan §Input Validation, Recorded check row and MCP server row).
- security ↔ a11y: the contrast reading is the a11y plan's SC 1.4.3 reader, `Harness::text_contrast`. Security owns only that it stays read-only and carries no authored text out (per security-plan §Input Validation, Driver session socket row).
- security ↔ arch: the founder's fork on the new verb and on its answer's content is gathered with arch's driver contract. No listener, port, env var or crate is implied (per security-plan §API Security).

## Acceptance criteria contributions
- On a fixture holding a password input with a typed sentinel, a `lint` answer has 0 occurrences of the sentinel and reads any value as `MASKED_VALUE`. This holds in process, on the command line's stdout and in the MCP result, in both layout modes (per security-plan §Input Validation, Markup attributes: password and file `input` value row).
- Under escher's sink at `RUST_LOG=trace`, a `lint` call's `command` span line holds only schema fields: `verb`, plus `cause` if refused. The host's and the `mcp` role's stderr carry 0 id needles, 0 name needles and 0 reason readings, under both builds (per security-plan §Logging & Monitoring, escher's own sink).
- A malformed `lint` call is refused before anything runs, with the snapshot unchanged and no echo of the caller's text: an unknown argument, a wrong kind, or an out-of-bound `id` if one is taken. The CLI exits 1 and writes back nothing typed, and the MCP result is `isError` (per security-plan §Input Validation, Driver command schema row and CLI arguments (escher-session) row).
- A recorded session containing a `lint` call either replays through `Check::from_bytes` and `Check::replay`, with its `answer` kept masked, or leaves no `lint` record. A check whose `tool` is outside the accepted set is refused `malformed` (per security-plan §Input Validation, Recorded check row).
