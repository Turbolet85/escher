# obs extract

## Relevance
relevant — a new instance verb (`lint`, per scope's inference) runs through `Session::run` and an MCP `tools/call`, so it lands inside both escher-driver spans, the sink's line format and the needle checks; the readers it builds on (`Harness::text_contrast`, a possible new blitz-dom reader) are bound to stay silent.

## Constraints
- obs-plan §4 requires every call handed to `Session::run` to open exactly one `command` span (target `escher_driver`, INFO, `info_span!` by hand), its `verb` the verb table's own word. A read-only verb follows the `snapshot` / `screenshot` precedent: accepted, it records `verb` alone; refused, it records `verb` and `cause`, one of the eight `Cause::name` words. Whether a new `lint` verb gets a new cause is a schema question; any new cause name joins this closed set (per obs-plan §4).
- obs-plan §4 fixes the `command` span at eight fields. It lists what is never fielded: any argument, any `Command` / `Call` / `ArgValue` / `Outcome` / `Refusal` / `Fault`, screen text or its length, and a shot's image, size or dimensions. By the same rule, a finding's id, class, measured reason or contrast ratio is never fielded. A count of findings would be a ninth field, a new log field and the founder's fork (scope inputs#I1) (per obs-plan §4).
- obs-plan §4 requires an MCP `lint` call to open one `tool_call` span holding only `tool` (the table's word, a twelfth among its eleven) and `ending` (`accepted` · `refused` · `error`), parenting the `command` child the way every instance verb does (per obs-plan §4).
- obs-plan §6 (Logged events, escher-driver) lists the closed words a `command` / `tool_call` span line can carry: the verb table's eleven words, eight causes, three busy classes, bools and counts. Adding a verb extends that closed word set on the line. No line prints at the default `warn` (per obs-plan §6).
- obs-plan §8 (Scrubbing) leaves the sink's five scrub sets and the allowlist rule unchanged. An `escher_driver` pair prints unless its name is in the content-named set, so a field that held finding content would print unredacted unless its name happened to be scrubbed. No new field may hold anything a screen reads (per obs-plan §8).
- obs-plan §3 (Logging stack) requires escher-driver's modules (`execute`, `json`, `describe`, `mcp`, `recording`, `replay`, …) to install no subscriber, read no env var and print nothing. An `Outcome` is written by `to_json` alone, as a command's answer or an MCP result, and never logged. blitz-test-harness's `Harness::text_contrast` likewise prints, panics and logs nothing, and the crate takes no `tracing`. A new outcome variant carrying findings inherits all of this (per obs-plan §3).
- obs-plan §2 (Telemetry mechanism) requires any blitz-dom log site to be compiled only under `#[cfg(feature = "tracing")]` with a no-op path. Whether a new read-only reader (e.g. truncated text) needs a log site at all is research's question. The precedent readers (`visible_region`, `can_paint_text`, `layout_as_text_input`) add none (per obs-plan §2).

## Patterns to follow
- The `screenshot` precedent for a read-only verb (obs-plan §4; §6 Logged events): span line `span="command" verb="screenshot"`, plus `cause` when refused. No content byte, size or dimension appears on the line. This is measured by 0 occurrences of a content needle in the host's and the `mcp` role's stderr at `trace`.
- `stand_act_spans` (tests/blitz-tests/tests/stand_act_spans.rs) drives verbs through `Session::run` under the sink over an in-memory capture, with per-verb expectation rows (the CRUD `advance` row `Expect::Acts`). A `lint` row extends it. `stand_mcp_tools`'s hand-written `Recorder` asserts each `tool_call` parents its `command` child (obs-plan §4).
- `host_log` and `mcp_log` (examples/seven_guis/tests/) read a sink-installing `escher-session` at `trace` under both builds through the shared readers `Needles` / `stand_needles` / `occurrences` in examples/seven_guis/tests/common/mod.rs. Their assertion messages name a kind and a count, never a needle (obs-plan §8 Values logged as-is; §3 Logging stack).
- The silence census: each new check, fixture page and shared-module addition installs no subscriber, reads no env var and prints nothing, and its readings go into assertions only. The probe `println!|eprintln!|print!|dbg!|std::env|env::var|escher_telemetry|tracing_subscriber|UnixListener|TcpListener|bind\(` reads 0. tests/blitz-tests/tests/fixtures/mod.rs is already held to this (obs-plan §3 Logging stack).

## Anti-patterns to avoid
- Fielding a lint call's argument by its schema name, or an `Outcome` / `Command` with `Debug`, on the `command` or `tool_call` span. Either would print ids, names or values (obs-plan §4).
- Writing the lint answer anywhere but its answer carrier: no log line, event, `eprintln!` or span field for a finding. stdout carries the command's answer and never a log line (obs-plan §3 Logging stack; §6 Logged events).
- Adding a `tracing` dependency, event or span to blitz-test-harness's contrast path, or an ungated `println!` / `tracing` call to a new blitz-dom reader (obs-plan §4; §2 Telemetry mechanism).

## Contract bindings
- obs ↔ tests: the span shape (obs-plan §4) is asserted by `stand_act_spans` and `stand_mcp_tools`. The no-needle reading (obs-plan §8) is asserted by `host_log` and `mcp_log` under both builds (`-p seven_guis` and `--workspace`, the latter adding the `blitz_dom::document` INFO line per obs-plan §2 Feature wiring). Adding `lint` to `VERBS` moves the per-call line counts these checks read.
- obs ↔ security: obs-plan §8 Scrubbing (content-named set, allowlist) binds to security-plan's rule that a driver span adds no field holding what a call supplied or a screen reads. A finding-count field is a new log field and a founder's fork (scope inputs#I1).
- obs ↔ recording: obs-plan §9 (Recording directory row) states what a kept check holds at rest: each instance-verb call and its whole `answer`. Whether `lint` joins the recorded set (scope's inference) decides whether lint findings (ids, reasons) join that at-rest content, and that row moves if it does.
- obs ↔ a11y: text contrast read as `stand_contrast` reads it goes through `Harness::text_contrast`, which obs-plan §4 holds silent (no span, event or env read). A lint verb's contrast finding inherits that reader's silence.

## Acceptance criteria contributions
- An accepted `lint` through `Session::run` under the sink writes exactly one closed `command` line, `span="command" verb="lint"`, holding none of `settled` / `busy` / `passes` / `added` / `removed` / `changed` if the verb is read-only. A refused one adds only `cause`. The capture holds 0 id, name or reason needles, in both layout modes (per obs-plan §4).
- An MCP `lint` tool call writes one `tool_call` line, `tool="lint"` with its `ending`, as the parent of exactly one `command` child (per obs-plan §4).
- `host_log` and `mcp_log`, extended to a `lint` call, read 0 id needles, 0 name needles and 0 typed-sentinel occurrences at `RUST_LOG=trace` under both builds, with one span line per call (per obs-plan §8).
- The silence census over the new check(s), the planted-defect fixture page in tests/blitz-tests/tests/fixtures/mod.rs and any new blitz-dom or blitz-test-harness reader reads 0 print, subscriber and env-read sites. escher-driver still holds exactly its 2 `info_span!` sites (per obs-plan §3).
