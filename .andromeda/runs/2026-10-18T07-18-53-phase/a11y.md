# a11y extract

## Relevance
partial — the chunk changes no focus order, no key binding, no colour and no accessibility-tree read. Its a11y stake is that the standing tier-0 checks prove again, unchanged, under the one clock, and that three clock-adjacent reads stay inside what the plan requires: double-click timing beside click focus, the scrollbar thumb's painted cue, and the changed set that drives the tree refresh.

## Constraints
- The a11y target is tier 0, WCAG SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary). A clock change meets that target only if every check that measures it reads the same before and after. The plan's must-be-accessible critical paths read NOT YET MEASURED, so this chunk takes no critical-path obligation from them.
- Per a11y-plan §2 A11y Strategy (Accessibility tree lifecycle), the changed set is marked by a mutation of an in-document node, a focus or checked change and a text control's input. Node creation, hover, active, scroll and layout do not mark it. The shell rebuilds the platform tree only when the set it drains is non-empty. So the fade moving on the one clock must not mark the set by itself. Whether `advance` moving the instance's clock marks it on any path other than the app's own writes is research's question.
- Per a11y-plan §5 Keyboard Navigation (Focus restoration), a pointer click on a `button`, or on an `input` of type `submit` · `reset` · `button`, focuses it and ends the walk matched, and a click on a range input focuses it without moving its value. If the double-click timestamp (`last_mousedown_time`) moves onto the one clock, a driver `click`'s single-click focus and activation must stay as they are. Whether two driver `click`s on one point with no `advance` between them then count as a double click, and whether that moves any focus, selection or snapshot reading, is research's question.
- Per a11y-plan §5 Keyboard Navigation (Keyboard handling), Enter and a released Space on a focused activatable control each dispatch a Click built from `Node::synthetic_click_event_data`, which runs the app's handlers and then `handle_click`. Whether that synthetic path reads the double-click timestamp or any other clock is research's question. Either way, SC 2.1.1 activation must read the same.
- Per a11y-plan §6 Visual Design Verification (Color contrast), default scrollbar thumbs carry a thin contrast stroke so they show over content of the same colour, and a near-white author thumb must still visibly change on hover and drag. With the fade on the one clock, both readings must still hold in a frame where the thumb is shown. Whether either test's frame depends on the fade's elapsed time is research's question.
- Per a11y-plan §6 Visual Design Verification (Visibility and hit-testing), `scrollbar-width: none` suppresses overlay scrollbars and paints no scrollbar. The clock change must keep that suppression for every clock reading.
- Per a11y-plan §9 CI Integration, the `a11y` leg runs six files (`accessibility_hidden` · `accessibility_roles` · `focusability_updates` · `stand_keyboard` · `stand_contrast` · `stand_accessibility_ids`). The three `stand_*` files among them also run three times in `stand-repeat` under a zero-failure budget. Both stay green after the change.

## Patterns to follow
- Every stand a11y check runs in both layout modes and states its expectations as shared tables in the stand checks' common module (`tab_order`, `ENABLED_TAB_ORDER`, `focused`) (per a11y-plan §5 Keyboard Navigation, Test harness pattern). A new determinism proof that reads focus or a control's state reuses those readers rather than re-deriving them.
- A check that reads `has_changes()` as "this step changed something" drains the changed set first, because a freshly booted harness document holds the boot's own marks and a settle neither reads nor drains the set (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- `Harness::text_contrast` is read-only: no mutation, no input, no pump and no settle (per a11y-plan §6 Visual Design Verification, Color contrast). Contrast and state rows are read without moving the clock, so they must read the same at any virtual time.
- Hover and active colour states are reached through `move_mouse_to` and `mouse_down_at` and read off computed styles (per a11y-plan §6 Visual Design Verification, Color contrast). That input path must still reach the same `STATE_ROWS` once pointer timing reads the one clock.

## Anti-patterns to avoid
- Never edit the stated focus tables (`tab_order`, `ENABLED_TAB_ORDER`) or the Enter/Space rows to get a clock change through (per a11y-plan §5 Keyboard Navigation, Test harness pattern). A change that moves them is a focus-order or activation change and needs its own decision.
- Never read `has_changes()` without draining first, or count a fade or clock tick as a tree-refreshing change (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- Never prove an a11y reading in only one layout mode (per a11y-plan §5 Keyboard Navigation, Test harness pattern).

## Contract bindings
- a11y ↔ tests: the `a11y` leg's six files and the `stand-repeat` leg's three-round, zero-failure run of the `stand_*` a11y files (a11y-plan §9 CI Integration ↔ test-plan §10). Under the chunk's determinism claim, `stand-repeat` is where a wall-clock leak into those checks would show.
- a11y ↔ design: the scrollbar thumb's contrast stroke and its hover/drag change (a11y-plan §6 Color contrast ↔ design-system §Color Palette). The fade's opacity is what the one clock now drives.
- a11y ↔ driver surface: a driver `click` focusing a button (a11y-plan §5 Focus restoration) ↔ the double-click timestamp that the scope's inferred item moves onto the one clock.
