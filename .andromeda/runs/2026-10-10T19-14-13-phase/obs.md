# obs extract

## Relevance
relevant — the entry's third clause ("tool call parents its trace") is an obs deliverable, and the surface makes a process's stdout a protocol stream beside a stderr sink (obs tier 0, per obs-plan §1 Obs Scope Summary).

## Constraints
- Telemetry is `tracing` alone: obs-plan §2 Telemetry Strategy (Absent) records no telemetry backend, and the keyed contract obs-plan §3 Bootstrap phases (derive for route / setup-project), `otel-sdk-install`, requires that 0.1.0 ship no OTel crate, no egress and no exporter credential path. "Parents its trace" is therefore a `tracing` span relation, never an OTel trace context or an export. A trace identity carried between two processes (scope decision 5) has no coverage in this plan: the only place it would sit, the trace-context item of obs-plan §3 Observability Harness Contract, is marked not yet measured, so nothing is extracted from it and the fork arrives at the founder with no obs mandate behind either option.
- obs-plan §4 Span / Trace Coverage requires one span per call handed to `Session::run` — target `escher_driver`, name `command`, INFO, built by hand, opened before validation and held until the call returns — with eight fields and no more. A tool call's span is a second span around it; it must leave the command span's name, target, level and eight fields as they are. Whether a span entered by the MCP layer becomes the command span's parent with no change to `execute.rs` (contextual parenting in one process) is research's question.
- obs-plan §4 Span / Trace Coverage requires that a span field hold the schema's own word, a bool or a count: the verb table's word and never the caller's verb text, a refusal by its cause's name alone, and no argument, id, typed text, accessible name, control value, screen text or its length, and no `Command`, `Call`, `ArgValue`, `Outcome`, `Refusal` or `Fault` under `Debug`. The tool call's span is bound by the same rule; what MCP adds as call-supplied text — the tool name as the client spelled it, the JSON-RPC request id, the method string, the `arguments` object, a client's name or version from `initialize` — is fielded by none of them.
- obs-plan §8 PII Scrubbing & Compliance (Scrubbing) requires that only a target starting with `escher_` or an engine prefix print, and that every other target's record, span lines included, be dropped whole at every level. A tool-call span opened under any target outside the `escher_` family (the booting binary's own crate name, for one) would write nothing. Under an escher target every field prints except the content-named set, and obs-plan §4 Span / Trace Coverage notes that of the driver's argument names only `text` is in that set — so the scrub is no backstop for an id or a key fielded by name, and a field named `error` would print redacted.
- obs-plan §3 Observability Harness Contract (Logging stack) requires that a binary that boots apps install `escher_telemetry::init(escher_telemetry::service_identity!())` first thing in `main`, before argv is read and before anything boots, that the sink write to stderr only, and that `escher-driver` install no subscriber and read no environment variable. For this surface stdout is the protocol stream: no sink line, diagnostic or print may reach it, and a library-side MCP module prints nothing but protocol lines. That section also records `init` as having two install sites; a new entry point changes the count, an existing one does not — which is chosen is the operator's fork, and the plan's wording follows it.
- obs-plan §6 Log Coverage (Log format, escher's sink) requires one line per closed span and none on creation, entry or exit, and states that a line carries the span's own name and fields plus the layer's close fields — an event inside a span gains no span name and no span field. As that section reads, a closed-span line names no parent. Whether the parent relation is readable from the sink's lines at all, or only from a subscriber a check installs, is research's question; a new field or record shape on the line is a change to a founder-ratified record class (obs-plan §6 Log Coverage, the closed span's line) and is not assumed.
- obs-plan §7 Error Capture & Reporting (Panic hooks) requires that the chained hook redact the payload in escher's own event and then run std's default hook, which obs-plan §8 PII Scrubbing & Compliance (Values logged as-is) records as printing the raw panic message to stderr past the scrub. A panic whose message is built from what a client sent would put that content on stderr; the reader of client input must have no such path.

## Patterns to follow
- The hand-built span of obs-plan §4 Span / Trace Coverage: `tracing::info_span!` (no `#[instrument]`), every field created unrecorded and recorded only where it applies, the span entered ahead of validation so that a refusal lands inside it. That section also records that a call refused before it reaches a session opens no span — the MCP layer must choose, and state, whether a protocol-level rejection (a line outside JSON, an unknown method) leaves a span.
- The in-process capture of obs-plan §3 Observability Harness Contract (Logging stack), `stand_act_spans`: parents install nothing and re-run the test binary on ignored children, one with `RUST_LOG=info` and one with it removed; each child installs the sink through `escher_telemetry::init_with_writer` over an in-memory capture; the capture is read into assertions only and a failing parent relays the child's own failure message, never a captured line.
- The spawned-binary reading of obs-plan §3 Observability Harness Contract (Logging stack), `host_log`: the real sink-installing binary at `RUST_LOG=trace`, both streams drained from the spawn on, read into assertions only, a failure printing a kind and a count; and where a check reads an accepted command's empty stderr it removes `RUST_LOG` from the child's environment.
- The by-level reading of obs-plan §8 PII Scrubbing & Compliance (Values logged as-is): stderr line counts at unset · `info` · `debug` · `trace`, with id needles, name needles and a typed sentinel counted, taken under both builds — obs-plan §2 Telemetry Strategy (Feature wiring) requires the two to be told apart, since a workspace-wide build turns blitz-dom's `tracing` on and adds an engine INFO line beside a `type`.
- The call-log shape of obs-plan §6 Log Coverage (Log format, the cold-agent pipe): one line per tool call holding a sequence number, the tool, an outcome and a cause, never an argument value — the precedent if the pipe is pointed at the real server (scope decision 4).

## Anti-patterns to avoid
- obs-plan §11 Obs Anti-Patterns holds no recorded intent; the bans below are the mandates of other sections, stated as bans.
- Fielding or logging what a tool call supplied or what a tool result holds — an `arguments` object, an `Outcome` or a `Refusal` under `Debug`, the result's text or its byte length — on any span or event (per obs-plan §4 Span / Trace Coverage).
- Writing anything that is not a protocol line on stdout, or routing the sink anywhere but stderr (per obs-plan §3 Observability Harness Contract, Logging stack).
- Adding an event, a metric, a log file or an exporter where the plan requires one span per call: obs-plan §4 Span / Trace Coverage requires that the driver emit no event, and obs-plan §5 Metric Coverage (Absent) records no metric emission.

## Contract bindings
- obs ↔ security: the content that may cross the server's stdout (ids, names, values, the snapshot text, the diff) is security's crossing question (scope decision 1, security-plan §Input Validation); obs's side is that none of it reaches stderr or a span field (obs-plan §8 PII Scrubbing & Compliance, Scrubbing; the keyed contract obs-plan §3 Bootstrap phases (derive for route / setup-project), `pii-scrubbing-wire`). A trace identity on the socket (scope decision 5) is a new wire field of an open value set — security's and architecture's to register, with no obs mandate to cite.
- obs ↔ tests: the checks that read a sink are test-plan §4 checks built on the two capture patterns of obs-plan §3 Observability Harness Contract (Logging stack); if the cold-agent pipe runs the real server (test-plan §3), obs-plan §3 Observability Harness Contract (Cold-agent pipe log) requires that its events, verdict and call log stay free of tool arguments and results, and obs-plan §8 PII Scrubbing & Compliance (Scrubbing) requires that the raw transcript — which would then hold the stand's screen — stay unprinted, unlogged and under `target/`, any committed copy masked.
- obs ↔ architecture: a tool-call span is a new span site in a crate obs-plan §4 Span / Trace Coverage records as having exactly one; the server's entry point and the count of sink install sites (obs-plan §3 Observability Harness Contract, Logging stack) follow architecture §Standard Contracts (Driver session) and §Occupied Resources. obs-plan §3 Observability Harness Contract (Service identity and line format) requires `service.name` to be the package's name, so a second role or binary in the `seven_guis` package is not told apart by it.
- Not a binding: obs-plan §10 SLO Invariants & Telemetry Budgets and §12 Obs Decisions Log hold no recorded intent, and the naming-convention item of obs-plan §2 Telemetry Strategy is marked not yet measured — the new span's name and field names have no convention to cite beyond the built span of §4.

## Acceptance criteria contributions
- Each tool call that reaches `Session::run` leaves exactly one `command` span, closed, whose parent is the tool call's span, with the command span's eight fields unchanged — read by a check, in both layout modes (per obs-plan §4 Span / Trace Coverage).
- Every field of the tool call's span is a fixed schema word, a bool or a count; a refused call and a protocol-level rejection record nothing the client supplied (per obs-plan §4 Span / Trace Coverage).
- The MCP server process's stderr at `RUST_LOG=trace`, over a flow that includes a `type`, holds 0 id needles, 0 name needles and 0 occurrences of a typed sentinel, built alone and built with the workspace (per obs-plan §8 PII Scrubbing & Compliance, Values logged as-is).
- The server's stdout holds protocol lines only at every `RUST_LOG` level, and with `RUST_LOG` removed an accepted tool call leaves stderr empty (per obs-plan §3 Observability Harness Contract, Logging stack).
