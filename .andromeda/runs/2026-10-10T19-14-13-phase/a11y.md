# a11y extract

## Relevance
partial — the chunk adds no markup, style, token, focusable element or key binding, so no WCAG criterion of the tier (a11y-plan §1 A11y Scope Summary: SC 2.1.1 · 1.4.3 · 2.4.3) is triggered by a new UI surface; it is in the domain only as a new carrier of what the accessibility tree states (role, name, the three state readings, focus) and as a possible change to the stand binaries' dependency graph.

## Constraints
- a11y-plan §7 Screen Reader Support (Accessibility tree output, the snapshot bullet) requires the snapshot, its text form and its diff to take role, name, focus and the `selected` · `pressed` · `invalid` readings from the accessibility tree with no second role or name mapping; an MCP tool result is one more reader of those forms and may state no role, name or state reading of its own. Whether the MCP result path reuses the existing written form or builds another is research's question.
- a11y-plan §7 Screen Reader Support (Accessibility tree output, the snapshot bullet) requires the driver's schema to define no role or name set of its own, `role` and `name` being field names of its result nodes; a tool's description and input schema served by `tools/list` are held to the same — no role vocabulary, no name list.
- a11y-plan §7 Screen Reader Support (Accessibility tree output, the snapshot bullet) requires a password input's value, and a file input's, to read as the fixed mask `MASKED_VALUE`, the typed text in no field of the snapshot or of the tree; a tool result carries the mask and nothing else of those two controls.
- a11y-plan §7 Screen Reader Support (Accessibility tree output, the snapshot bullet) requires the `disabled` refusal to be detected on one reading only — the snapshot node's `enabled` reading not enabled, which follows the presence of the `disabled` attribute — with nothing dispatched and the focused ids and the tree's focus as they were before the call; a tool call refused `disabled` is held to that. Whether a call arriving over MCP reaches the same executor check is research's question.
- a11y-plan §1 A11y Scope Summary (the Dioxus crates bullet) requires that neither stand binary builds a platform adapter — `accesskit_xplat` and `accesskit_winit` in neither graph — while `escher-driver` names `accessibility` on `dioxus-native-dom` unconditionally; a new entry point or a new dependency under the scope's decision 2 must leave that reading as it is, or the plan is amended. Whether a JSON or MCP crate would move the stand's graph is research's question.
- a11y-plan §2 A11y Strategy (Accessibility tree lifecycle, the changed-set bullet) requires that a harness settle, and so the driver session's `act`, neither reads nor drains the engine's changed set; an MCP server that holds an instance in process adds no drain of its own. Whether the in-process option of the scope's instance fork touches the set is research's question.
- a11y-plan §9 CI Integration requires the `a11y` leg to stay its three test files and to add no stand assertion; the chunk's new checks belong to the workspace test leg, and none joins that leg unless the plan is amended.

## Patterns to follow
- A reading asserted through the new surface is asserted equal to the accessibility node's, in both layout modes — the pattern of the stand's state checks (a11y-plan §7 Screen Reader Support, Accessibility tree output; a11y-plan §3 A11y Assertion Harness Contract, the state-check bullet).
- Expected roles and input names are stated once, in the stand checks' shared tables (`controls`, `INPUT_NAMES`, `rendered`), as stated expectation and never a second mapping; a check of an MCP flow reads those tables where it needs a role or a name (a11y-plan §7 Screen Reader Support, Accessibility tree output, the `author_id` bullet).
- A scripted or agent-driven stand flow reaches a control by the stable id a snapshot lists: a CRUD person row is a listbox option no keyboard reaches, so it is taken by `click` and never by `press` (a11y-plan §5 Keyboard Navigation, Per-surface keyboard shortcuts).
- A flow does not expect focus after a `click` on a plain button — the plan records that such a click leaves no element focused, the question owned by a route entry — so a `press` that follows needs a focus the flow established another way (a11y-plan §5 Keyboard Navigation, Focus restoration).

## Anti-patterns to avoid
- A second role, name or state vocabulary in tool descriptions, input schemas or result text (a11y-plan §7 Screen Reader Support, Accessibility tree output, the snapshot bullet).
- Closing or masking, inside this chunk, a gap the plan records as open and route-owned — the CRUD list's empty accessible name, the option no keyboard reaches, the unread `aria-checked` — by editing stand markup or by filtering a tool result (a11y-plan §7 Screen Reader Support, Accessibility tree output, the stand-attributes bullet; a11y-plan §4 ARIA Patterns & Roles, ARIA state attributes).
- Pulling a platform adapter into a stand binary's graph through the new entry point (a11y-plan §1 A11y Scope Summary, the Dioxus crates bullet).

## Contract bindings
- a11y ↔ security: the mask reading of a password's and a file input's value and the three state readings as closed words are the content of the MCP crossing the scope puts to the founder (decision 1); the a11y plan states what the readings are (a11y-plan §7 Screen Reader Support), the security plan whether they may leave over a new carrier (security-plan §Input Validation). The a11y plan does not answer the crossing question.
- a11y ↔ tests: a check that reads a role, a name or a state through MCP runs in both layout modes and in the workspace test leg (a11y-plan §3 A11y Assertion Harness Contract; a11y-plan §9 CI Integration; test-plan §4 as the scope names it).
- a11y ↔ architecture: the snapshot's seven state fields and their written order are the model the tool result carries (a11y-plan §7 Screen Reader Support; architecture §Standard Contracts, Driver session).
- a11y ↔ obs: none from this plan — its violation-schema block reads not yet measured and is not coverage.
