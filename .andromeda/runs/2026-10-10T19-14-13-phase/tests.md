## Constraints
- **The commands the implementation must pass.** test-plan §9 (Local pre-push gate; Legs) requires `bash .github/scripts/ci-leg.sh fast` — fmt, clippy, the workspace test leg, the CI-scripts leg — and names `ci-leg.sh doc` among the legs; test-plan §1 (apps — `examples/seven_guis`) states the per-file form for the stand binary's checks, `cargo test -p seven_guis --locked --test {name}`; test-plan §3 `run` states the per-file form for blitz-tests, `cargo test -p blitz-tests --locked --test {name}`, and `bash scripts/agent-run.sh run stand` for the stand selection. The plan states no per-crate command for escher-driver's inline tests and names no `nextest`; the workspace leg (test-plan §1 Workspace (CI)) is the one runner it names for them.
- **A per-package green is not the gate.** test-plan §9 (Engine features by runner) requires a check to hold under both runners — the workspace build compiles the engine's `tracing` call sites and a second bounds-reader body that a `-p` build leaves out — and requires a check that reads a sink's capture to count lines by target, never in total. A check of the MCP server that reads its stderr (the tool call's span, the `command` span under it) is bound by both.
- **A check that holds a server process owns it.** test-plan §2 (Process-lifecycle checks) requires such a check to start and stop its own process — the package's own binary through `CARGO_BIN_EXE_*`, or the test binary re-run on one `#[ignore]` child — with every wait bounded, a guard that kills and reaps a process a failing check still holds, any state directory under `CARGO_TARGET_TMPDIR`, the child's streams sent to null unless the check reads them (a child's libtest lines must never reach the parent's output, where `agent-run.sh` counts them), and a `cfg(unix)` gate where a session crosses processes. An MCP server is a child whose stdin and stdout the check itself holds, so the stream rule applies to all three streams.
- **A captured stream is drained while the process runs.** test-plan §2 (Process-lifecycle checks) requires a check that captures a host installing escher's sink to drain its pipes from the spawn on, or capture to a file — a check that must fail red on a leaking sink cannot wait for exit before it reads. An MCP check also writes requests and reads replies on the same child: whether seven_guis' shared runner (one bounded run of the binary as a client, test-plan §1 apps — `tests/common/mod.rs`) can hold a long-lived child with a piped stdin is research's question.
- **Stdout is the answer, stderr the log, and neither leaks.** test-plan §3 (Stand log format) requires a sink-installing binary of the stand to write its log to stderr only, in the two ratified record classes, with no stable id, no accessible name and no typed text at any `RUST_LOG` level, and requires a command's stdout to be its answer and nothing else; test-plan §5 (Session host ↔ what it writes) states how that is proven — needles read from the stand itself, a typed sentinel, a failure printing a kind and a count only — and that a zero read from a host that installs no sink says nothing about one that does. The MCP server's stdout is the protocol; whether its entry point installs the sink, and so which of the two proofs applies, is research's question.
- **Driver checks run in both layout modes, with no sleep and no clock.** test-plan §5 (Session ↔ held instance) requires a call run on a held instance to be checked `for incremental in [false, true]`, the returned diff equal across the two modes, a refused call leaving the instance unchanged and reading as a text holding none of the bytes the call supplied, and a masked control reading `MASKED_VALUE`; test-plan §8 (Time — seven_guis timer) requires a Timer flow to move time by `advance` through `stand::timer_step` and by nothing else. A tool call that runs through `Session::run` inherits each.
- **The cold-agent pipe is a contract with its own tests.** test-plan §3 (Cold-agent run pipe — `run counter`, Verdict, Proof) fixes the pipe to one stdio server named `stub`, one task `counter`, an `isolated` reading that requires the init tools to be exactly the three stub tools, a `final_count` read from the stub's state, and a live run that is never part of CI; test-plan §4 (Cold-agent pipe) pins it with 27 contract tests in the CI-scripts leg. If decision 4 runs the real server through the pipe, each of those four readings changes with it, `test_cold_agent.py` is amended in the same change, and the CI-scripts leg's stated total (78, test-plan §4 CI workflows and leg script) is restated.

## Patterns to follow
- **Unit tests of the new module, as the crate's ten files have them** — test-plan §4 (escher-driver): inline `#[cfg(test)]` module beside the code, each table stated in its test with its row count asserted, one malformed witness per rule, round-trips where a form is both written and read, bounds tested at the edge and one past it, and a mutation control per named test read red and then green on the restored tree. A JSON-RPC request reader, the tool listing built from `VERBS` and the tool-result form are each such a table; the wire's and the command line's rows (test-plan §4 escher-driver — wire.rs, cli.rs) are the shape to follow.
- **What a unit test cannot hold goes to an integration target** — test-plan §1 (escher-driver) states the crate depends on nothing that names a virtual DOM, so a unit test cannot build a held instance and its writer's node rows are tested over plain parts; a tool call that runs on an instance is checked from `tests/blitz-tests/tests/` (in process, through `tests/session_common/mod.rs`, test-plan §3 Crate-local test helpers — blitz-tests (session checks)) or from `examples/seven_guis/tests/` (the binary as a process, test-plan §6 Command line).
- **A new file is a new target with no manifest line** — test-plan §2 (Directory pattern): one behaviour per file, auto-discovered in blitz-tests (the manifest's one `[[test]]` table stays as `BlitzTestsTargetsTest` pins it) and in seven_guis, shared helpers in the package's `common` / `session_common` module, never a second copy; a file named `stand_*.rs` is picked up by `agent-run.sh run stand` with no script change (test-plan §3 Proof), and its count is re-read there.
- **A scripted protocol client is a hand-written stand-in, in the language the target already uses** — test-plan §8 (Hand-written fakes and stubs; Observed absent) and test-plan §3 (Third-party test frameworks) record no mocking library and no added test framework; test-plan §2 (Command-line checks and shell flows) keeps a non-Rust asset as an asset of a `cargo test` target, not a runner of its own; test-plan §4 (Cold-agent pipe) shows the one existing minimal MCP client, a `claude` shim that drives the real stub over a pipe with no model and no credential. Whether that shim can drive the real server is research's question.
- **The command line's proof is the template for "every command is also a tool"** — test-plan §6 (Command line) proves each verb accepted and answering exactly its fields, a refusal with its cause, a line outside the grammar running nothing, and one whole flow per script leaving nothing behind; v010-13's listing claim reads against the same verb table.

## Anti-patterns to avoid
- **Printing what a call supplied in a failing assertion** — test-plan §4 (escher-driver) requires every assertion over a call to carry a row index only, so a failing log prints no argument value; an MCP check's assertion message, test name and panic text hold no id, name, value or request body. (test-plan §11 reads `NO RECORDED INTENT`; this ban is taken from §4.)
- **Reading a green or a zero from the wrong build or the wrong process** — test-plan §9 (Engine features by runner) and test-plan §5 (Session host ↔ what it writes): a `-p` run standing for the workspace leg, a line count taken in total rather than by target, or a silent stderr read from a process that installs no sink.
- **A wait that is not bounded, or a sleep standing in for a settle** — test-plan §2 (Process-lifecycle checks) and test-plan §5 (Session ↔ held instance): a bare `--ignored` run already waits on a host for its 1,800 s expiry, so a new `#[ignore]` child or a server read with no bound adds to it; a reply is read under a bound and the process reaped by its guard.

## Contract bindings
- **obs — the log-format binding.** test-plan §3 (Stand log format) binds every sink-installing stand binary to obs-plan §3 (the target allowlist) and obs-plan §6 → Log format (the event line and the closed-span line); the tool call's span and its fields are obs's to state, and tests reads them by target and by a fixed field set, as `stand_act_spans` does (test-plan §5 Session ↔ held instance). A span that parents the `command` span is a new record on that format.
- **security — refusals and crossings.** test-plan §4 (escher-driver; Cold-agent pipe) carries security's rule into the checks: a refusal and a failing assertion hold nothing of the call, a call log holds no argument value, and stdout carries only protocol frames. The MCP crossing itself (decision 1) is security-plan's; a committed transcript or evidence copy stays under the hygiene the pipe's contract names (test-plan §3 Cold-agent run pipe — Events).
- **arch — the session's contract.** test-plan §3 `session-checks`, `session-wire` and `session-binary` (the keyed contract Session lifecycle) bind a check of a hosted session to architecture §Standard Contracts → Driver session: the `v2` grammar, its three bounds and the binary's four endings. They are touched only if the server is a client of a hosted session, or under decision 5 (a new field on the wire restates `session-wire` and the wire's unit rows, test-plan §4 escher-driver — wire.rs); `session-proof` holds the crate's unit count (50) and is restated either way.
- **harness — the agent-run contract.** test-plan §3 (Agent-run contract — Invocation, State) starts and binds nothing of its own; a check that starts a process is a surface of that check, named there beside the two session checks if it joins the `stand_` selection.
- **CI.** test-plan §9 (Legs; Fast/slow split) — no new leg is implied; the new checks ride the workspace `test` leg, the unix-gated ones compiled out on the windows matrix leg (test-plan §5 Session host ↔ session socket), and the cold-agent contract tests ride `ci-scripts`.
