## Constraints
- layout-templates §Surface: cli → Primary screens (`escher-session`) requires every command of the binary to read `escher-session <verb> [arguments] --session <dir>` over the nine verbs of the one verb table, with `--session <dir>` exactly once on every command. An MCP entry point placed in this binary is a new command form: if it holds its own instance and names no session directory, it departs from that stated grammar, and the plan's entry is amended at the wrap rather than left reading "every command". Which form is taken is the operator's fork (where the instance lives, where the entry point lives).
- layout-templates §Surface: cli → Primary screens (`escher-session`) requires a first word the verb table does not hold to end as the refusal `unknown-verb` (exit 1), the one stated exception being the host role `serve`. A second role word for the MCP server must be placed deliberately on one side of that line — a role like `serve`, never a tenth verb by a side door (the scope's "no second list"). How the argv reader admits `serve` today, and whether a second role word fits the same path, is research's question.
- layout-templates §Surface: cli → Primary screens (`escher-session`) requires four endings (accepted · refused · usage · session error, exit 0 · 1 · 2 · 3), each answer one line of uncoloured JSON on stdout, and the usage ending one fixed line on stderr with stdout empty, nothing booted and no state created — a malformed `serve` is named among the usage cases. A malformed MCP-role command line must take the same usage ending; the MCP role's own stdout is a protocol stream, a fifth stdout shape the plan does not yet describe, so the four endings must stay as they read for the nine verbs.
- layout-templates §Surface: cli → Primary screens (`escher-session`) requires that no ending writes back anything the caller typed, and that the usage line is built from the verb table and the task names. A usage text that gains an MCP form keeps both properties; whether the built usage line names a role word at all today is research's question.
- layout-templates §Surface: cli → Primary screens (`escher-session`) requires the host role to boot one of four tasks named by one plain word (`counter` · `flight-booker` · `timer` · `crud`), its stderr log lines carrying `service.name=seven_guis`, unix only in 0.1.0. An MCP role that boots a task takes its task name from the same four words and the same service identity on stderr.
- layout-templates §Surface: desktop-native → Primary screens (seven_guis Home and TaskShell) requires the headless stand to skip Home and mount one lean task in TaskShell through `task_in_shell` at the pinned 800 × 600, scale 1.0, Light viewport with the bundled font, and requires a consumer of that mount (the `escher-session` host is named as the third) to boot through `seven_guis::stand` only, adding no markup, id, class, style, wrapper or order — a held instance reads as a fresh boot, in both layout modes. An MCP server that holds its own instance is a fourth consumer under the same rule; whether the code leaves any other boot path open is research's question.
- layout-templates §Surface: desktop-native → Primary screens (seven_guis Home and TaskShell) lists the author `id`s that are each lean task's stable element ids (the counter's two, the flight booker's six, the timer's five, CRUD's seven and `crud-person-{id}` per row). These are the ids an MCP tool call addresses and a tool result returns; the chunk adds, renames and removes none.

## Patterns to follow
- The host-role precedent: per layout-templates §Surface: cli → Primary screens (`escher-session`), `serve <task> --session <dir>` is a role of the same binary, outside the verb table, booting through the stand and silent on stdout. An MCP role in the same binary follows that placement (the scope's "by the command line's precedent"); it differs in one stated respect — its stdout carries the protocol — and that difference is what the plan's entry gains at the wrap.
- One stand mount, many consumers: per layout-templates §Surface: desktop-native → Primary screens (seven_guis Home and TaskShell), every headless consumer (the stand checks, the session host) reads the same `main#main > #task-shell` structure with `#task-header` above `#task-body`. A stand flow driven through MCP tools reads the same screens the command-line flows read, so its expected ids and structure are the plan's, not a list of its own.
- JSON-lines-only stdout with raw output kept in a file: per layout-templates §Surface: cli → Primary screens (`scripts/cold-agent.sh`), the pipe's usage is `cold-agent.sh <verb> [task]` with four verbs and the one task `counter`, every verb's stdout JSON lines only and the raw transcript under `target/cold-agent/`. If the founder's answer on the proof runs the real server through the pipe, the pipe's verb set, its one task and its stdout shape stay as that entry reads unless the plan is amended with them.
- Nested scrolling on the stand: per layout-templates §Surface: desktop-native → IA notes, `crud-list` is the box that clips its rows — a row past the list's box is refused `off-screen` until a `scroll` brings it in — while `task-body` is not the clipping box. A stand flow proven through MCP tools on CRUD meets the same structure and needs the same `scroll` step before a far row.

## Anti-patterns to avoid
- Adding markup, an id, a class, a style, a wrapper or an order change to the stand so that the MCP surface or its proof has something to address — banned by layout-templates §Surface: desktop-native → Primary screens (seven_guis Home and TaskShell), which states each consumer as adding none.
- Writing anything other than the command's answer on a command's stdout, or echoing what the caller typed in a usage, refusal or error ending — banned by layout-templates §Surface: cli → Primary screens (`escher-session`).
- Leaving the plan's `escher-session` entry reading "every command … over the nine verbs … `--session <dir>` exactly once" after a command form that breaks any of the three has shipped — the entry in layout-templates §Surface: cli → Primary screens (`escher-session`) is restated at the wrap, never left stale.
