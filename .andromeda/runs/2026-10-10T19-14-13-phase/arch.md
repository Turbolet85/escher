## Constraints
- **One table, one entry point.** architecture §Standard Contracts → Driver session requires the command and refusal schema to be stated once as `'static` data (`VERBS`, two levels) and requires every call to reach a held instance through `Session::run`, which runs `validate` first; a session-level verb goes through `validate_session`. An MCP tool is therefore a row of that table and a tool call a `Call` — per architecture §Standard Contracts → Driver session. A tool beyond the table is a widening of the validated verb set, which that section records as ratified by the founder each time it happened.
- **No second listener, no port.** architecture §Occupied Resources → Network ports and listeners requires exactly one local listener (the session socket, at the tree's one listener site) and no TCP or UDP port; architecture §Inherited Defaults → API style repeats it. The MCP transport must add none — a standard-stream transport is the only one that fits per architecture §Occupied Resources → Network ports and listeners.
- **The ratified crossing names two carriers, not three.** architecture §Established Decisions → [Driver session] records what crosses (an id and typed text in; ids, names, control values with the mask, snapshot text and diff out; no `NodeId`) as ratified for the socket and, through it, the command line. It does not name MCP, so the plan gives the chunk no standing answer for the MCP carrier — per architecture §Established Decisions → [Driver session]; the answer is decision 1's, and it is recorded there and in §Occupied Resources at wrap.
- **The session library's shape is locked.** architecture §Established Decisions → [Driver session] requires: a `std`-only cross-process path (no third-party IPC, named-pipe, pid-file or daemonizing crate), a library that names no app and takes its boot and its time step from its caller, installs no subscriber, reads no env var and has no default state location, and a dependency set recorded as three crates with no `[features]` table. A JSON reader crate or an MCP SDK (and any async runtime it brings) changes that recorded set — per architecture §Established Decisions → [Driver session]; it is a registration, never a silent add.
- **How a dependency enters.** architecture §Conventions → Manifests requires a dependency to be declared once in `[workspace.dependencies]` and consumed as `{ workspace = true }`; architecture §Stack and Technologies → Media lists `serde` as a workspace dependency while architecture §Stack and Technologies → Testing lists `serde_json` in the WPT runner's own manifest only, and architecture §Stack and Technologies → Language / runtime sets the MSRV a non-dev dependency must build under. A new row or a moved row in §Stack and Technologies is owed for decision 2 — per architecture §Stack and Technologies.
- **Written forms and what is never written back.** architecture §Standard Contracts → Driver session requires one written form per answer (outcome, refusal, session error — a line of JSON keyed by the schema's own words, written in the crate-private `json` module, output only), a `Refusal` and a `SessionError` that hold nothing a call supplied, and an ending that writes back nothing the caller typed. That section marks the writer question as re-opened at this surface; whatever decision 2 gives, an MCP result or protocol error stays under the nothing-written-back rule — per architecture §Standard Contracts → Driver session.
- **Unix only where a session crosses processes.** architecture §Standard Contracts → Driver session requires `serve` · `start` · `attach` · `stop` · `call` to return `Unsupported` off unix while a session held in process works on every target; architecture §Standard Contracts → CLIs requires the stand's driver binary to be an empty `main` on wasm. Which of the two the MCP server inherits follows from where the instance lives (the operator's fork) — per architecture §Standard Contracts → Driver session.

## Patterns to follow
- **The library owns the whole surface; the binary hands over argv, app names and a boot.** `command_line(args, apps, boot)` is the precedent: the surface lives in escher-driver, installs no subscriber and reads no environment, and the app-booting binary of seven_guis calls it — per architecture §Standard Contracts → Driver session and §Standard Contracts → CLIs. Whether an MCP entry point can take the same three inputs unchanged is research's question.
- **Private modules, re-exported at the crate root under `#![deny(missing_docs)]`.** A new module opens with `//!`, its public names join the root re-exports (the section counts them, so the count is amended at wrap) — per architecture §Standard Contracts → Driver session, §Conventions → Documentation and §Existing Scopes → escher-driver.
- **Closed, typed edges with fixed strings.** Every failure is a variant of a closed enum with a fixed kebab-case word and a fixed message (`SessionError`, `Cause`, `Fault`); a typed `Result`, never a panic on what a caller supplies — per architecture §Standard Contracts → Driver session and §Cross-cutting Patterns → Error handling. A protocol-level failure of the MCP reader follows the same shape.
- **A bounded, strictly decoded request line.** The socket's wire reads one request under a byte bound, decodes strictly, answers anything outside its grammar with a fixed refusal and runs nothing — per architecture §Standard Contracts → Driver session (the wire). The MCP reader's bound and its out-of-protocol answer follow that pattern.
- **A span built by hand, fields of fixed words and counts.** The command span is built with `tracing::info_span!` (no `#[instrument]`, no feature gate), each field created unrecorded and recorded only where it applies, under a target the sink's `escher_` prefix admits — per architecture §Conventions → Feature gating, §Standard Contracts → Driver session and §Standard Contracts → Telemetry bootstrap. Whether a span opened around `Session::run` in the same process already reads as the `command` span's parent with no change to `run` is research's question; across the socket it does not, and that is decision 5.

## Anti-patterns to avoid
- A second verb list, a tool description or input schema authored apart from `VERBS`, or any path that runs a `Command` that did not come from `validate` — banned per architecture §Standard Contracts → Driver session.
- A silent add: an HTTP or socket transport, a new env var, a new workspace crate, binary, cargo feature or dependency landed without its §Occupied Resources / §Stack and Technologies registration — banned per architecture §Occupied Resources → Network ports and listeners and §Occupied Resources → Names.
- A log line on the protocol's stdout, a subscriber installed by the library, or a span field that holds an id, a name, a value, an argument or any `Call` · `Command` · `Outcome` · `Refusal` — banned per architecture §Cross-cutting Patterns → Logging and timing and §Standard Contracts → Driver session (the never-fielded list).
