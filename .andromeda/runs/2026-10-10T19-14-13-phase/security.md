## Relevance
relevant — the chunk adds a third external-input surface on the driver's schema and a new carrier for ids, accessible names, control values, the snapshot's text and the diff; the plan records ratified crossings for the session socket and the command line only, and states that no MCP command exists.

## Constraints
- **The MCP carrier is an unratified crossing.** security-plan §Threat Model Summary (Attack surface, the vector "local IPC — the driver session's socket", its Trust boundary) and §Input Validation (the Driver session socket row; the `id` row) each name the carriers the founder ratified — the socket and the command line's stdout — and the `id` row states the id has two exits "and still no MCP command". The plan therefore requires a recorded ratification before a tool result carries any of the five content classes (scope decision 1), and a second one for a trace identity on the wire: §Input Validation (the Driver session socket row) requires that a field of an open value set, a new carrier or a new exit goes to the founder, and that the wire stays as that row states it (scope decision 5). What crosses, once ratified, is bound by the same rows: no `NodeId` crosses (§Input Validation, the `id` row), and a password's or a file input's value crosses only as the fixed mask (§Input Validation, the "password and file `input` value" row).
- **No listener, no auth surface, no new env read.** security-plan §API Security (opening paragraph and the "Local session socket" row) requires that the one listener stays the session socket and that no TCP or UDP port exists; §Authentication & Authorization (the "Local IPC access" row) requires that local access stays the filesystem's owner-only modes with no credential path added; §Secret Management ("Environment values read") requires that the escher-driver library and the binary that boots apps read no environment variable beyond `RUST_LOG` through `escher_telemetry::init`. A stdio MCP server must add to none of the three; if the server is a client of a hosted session, the state directory it is handed passes the checks of §Input Validation (the "Driver session state directory" row) unchanged.
- **Every tool call passes `validate` before anything is sent or run.** security-plan §Input Validation (the "Driver command schema" row) requires that each external surface reaches the schema through `validate` — a session-level verb through `validate_session` — that nothing public runs a `Command` that did not come from `validate`, and that a refused call changes nothing. That row also states "no MCP tool does yet": the MCP surface becomes the third surface the row must name. Whether the path the chunk chooses (a `Session` held in the MCP process, or `escher_driver::call` to a host) already validates on each side as the command line's does is research's question.
- **A request from the client is untrusted, bounded input, and no path on it panics.** security-plan §Input Validation (the Driver session socket row) requires a byte bound on a request, a strict closed grammar, and refuse-and-run-nothing for a line outside it or over the bound; §Input Validation (the "Cold-agent MCP stub" row) states the JSON-RPC shape of the same rule for an MCP server over stdio — an unparsable line and an unknown method each answered with a protocol error, a refused `tools/call` answered as a tool result naming its cause, no state change. §Input Validation (the "Driver command schema" row; the "CLI arguments (escher-session)" row) requires no `unwrap`, `expect`, `panic!`, `unreachable!` or index on anything a call supplies, an argument that is not text handled as an error, and a write to a closed pipe dropped rather than a panic. A JSON reader that enters this chunk — hand-written or a crate — is inside this requirement; the plan has no row for the real server's input and one is owed.
- **An error or a refusal holds nothing the client sent, and an answer cannot break the framing.** security-plan §Error Handling (Error format, the escher-driver `Refusal` entry) requires a closed set of eight causes with fixed texts, no `String` field in `Cause`, `Fault` or `Refusal`, and written forms of a refusal and a session error that hold nothing a call supplied; §Input Validation (the "CLI arguments (escher-session)" row) requires that no ending writes back a path, label, id or value the caller typed. Two points the plan does not settle and research must: JSON-RPC echoes a request's `id`, a client-supplied value — the plan states no rule for it, so its admitted forms and bound are a plan question for this chunk; and §Input Validation (the `id` row; the `aria-label` row) requires that an id or a name never puts a line break or a bare quote outside its field — whether the writer the chunk reuses keeps a raw line terminator out of a newline-delimited protocol line for every authored text (names, values, the multi-line snapshot text) is research's question.
- **The server's stdout is the answer, never a log; a span holds fixed words and counts only.** security-plan §Logging & Monitoring (Log format and backends, the "escher's own sink" entry and the "Stdout output" entry) requires a sink-installing binary to log to stderr only, admits two target families and drops every other target whole — so a tool-call span under a target the allowlist does not admit prints nothing, and one under an `escher_` target has its content-named fields redacted. §Input Validation (the "Driver command schema" row) requires that a span fields only schema words, bools and counts, and lists what is never fielded (any `Command`, `Call`, `ArgValue`, `Outcome`, `Refusal` or `Fault`, any argument, the screen text or its length, the session's label, the record of ids); it also states those types derive `Debug` and print ids, names and typed text — so none of them is formatted into a log line, a span field or an error message. The tool call's span and the parenting of `command` under it must hold to both.
- **A new dependency passes the audit gate, locked.** If scope decision 2 brings a serialization crate or an MCP SDK, security-plan §Dependency Security (Audit tool; Pinning; Supply chain integrity, "Lockfile verification") requires the lock committed, every cargo leg `--locked`, the audit leg green with per-ID ignores only, and a review by hand of each name that enters the lock, since that section states the audit's reach misses optional chains. An SDK that brings a network transport or an async runtime widens the graph the audit reads; whether such a crate can be taken with its HTTP transport features off is research's question.

## Patterns to follow
- The stub's handling of JSON-RPC over stdio — protocol error for an unparsable line and for an unknown method, a refused tool call as a tool result whose cause is named, an unknown tool name treated as a refusal, a call log that never holds an argument value (security-plan §Input Validation, the "Cold-agent MCP stub" row).
- The command line's closed reader — rules in one fixed order, the call checked by `validate` before the session address is asked for, a small fixed set of endings, nothing typed written back (security-plan §Input Validation, the "CLI arguments (escher-session)" row).
- The socket's two-sided bound — a bound on what comes in, a bound on the answer going out, and an over-bound answer reported as such with the call having run and not rolled back (security-plan §Input Validation, the Driver session socket row; §API Security, the "Local session socket" row). The plan states no bound for an MCP request or tool result; the operator's fork sets them and the plan records them.
- The command span's construction — built by hand, entered before `validate` so a refusal lies inside it, each field unrecorded until it applies, the verb fielded as the table's own word and never the caller's text (security-plan §Input Validation, the "Driver command schema" row).
- The log-hygiene measurement — the server run as a process under escher's sink at `RUST_LOG=trace`, id needles, name needles and a typed sentinel counted on stderr, under both builds (security-plan §Logging & Monitoring, the "escher's own sink" entry).

## Anti-patterns to avoid
security-plan §Security Anti-Patterns holds no recorded intent; the bans below are stated by other sections.
- Never field, log or `Debug`-print an `Outcome`, `Call`, `ArgValue`, `Command`, `Refusal` or `Fault`, a tool argument, a tool result or the screen's text — not in the tool call's span, not in a JSON-RPC error's message or data (security-plan §Input Validation, the "Driver command schema" row; §Logging & Monitoring, the "escher's own sink" entry).
- Never build an error, a refusal or a usage text from what the client supplied — an unknown tool name, an argument name, an id, a typed text (security-plan §Error Handling, Error format, the escher-driver `Refusal` entry; §Input Validation, the "CLI arguments (escher-session)" row).
- Never give a tool an argument that is a URL or a host path: security-plan §Input Validation (the "`@font-face` source" row) requires that escher routes no agent- or user-supplied URL through the net path, and §API Security (the "Request size limit" and "Request timeout" rows) states that path has neither a size cap nor a timeout. The tools are the verbs of the one table, none of which takes either.

## Acceptance criteria contributions
- A request line that is not JSON, is outside the protocol, or is over the request bound, and a tool call the schema refuses, each run nothing — the instance's snapshot reads the same before and after — panic nowhere, and get an answer in which nothing the client supplied in the call (an id naming no element, a typed text, an unknown tool name) occurs (per security-plan §Input Validation, the Driver session socket row and the "Cold-agent MCP stub" row; §Error Handling, Error format, the escher-driver `Refusal` entry).
- With the MCP server run as a process under escher's sink at `RUST_LOG=trace`, through a flow that takes a snapshot, clicks and types: stderr holds 0 id needles, 0 name needles and 0 occurrences of a typed sentinel, under both builds, and every stdout line is a protocol line (per security-plan §Logging & Monitoring, the "escher's own sink" entry and the "Stdout output" entry).
- A password typed through the `type` tool occurs 0 times in the tool result written out whole, and the entry's value reads the mask, in both layout modes; no result holds a `NodeId` (per security-plan §Input Validation, the "password and file `input` value" row and the `id` row).
- If a dependency enters: `bash .github/scripts/ci-leg.sh audit` reads green on the committed lock with no ignore added, every leg still passes `--locked`, and each name new to the lock is listed with its hand review (per security-plan §Dependency Security, Audit tool and Pinning).
