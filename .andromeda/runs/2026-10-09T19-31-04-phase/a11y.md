# a11y extract

## Relevance
partial — Item 1 (a textarea on a minimal fixture, its value read from the snapshot) is a11y surface by the snapshot's source; Item 2 touches the `a11y` CI job's package-install step only; no stand markup, focus behaviour or colour is in scope.

## Constraints
- The tier is `0 — SC 2.1.1 · 1.4.3 · 2.4.3` (per a11y-plan §1 A11y Scope Summary): the one a11y-bearing thing this chunk adds is a focusable text control on a test fixture, so SC 2.1.1 and SC 2.4.3 are the criteria in reach; SC 1.4.3 is not triggered (no painted colour changes).
- a11y-plan §7 Screen Reader Support (Accessibility tree output) requires the snapshot to read `value` from the element — the editor's text, else the `value` attribute — because the accessibility tree gives an element node no value property. The textarea check therefore reads the value from the snapshot node, never from the AccessKit tree, and expects the typed text itself: the fixed mask of that section is stated for password and file inputs only.
- a11y-plan §7 Screen Reader Support (Accessibility tree output) requires that the snapshot's role and name come from the tree `accessibility_tree` returns, with no second role or name mapping; a check's expected role and name are stated expectation only.
- a11y-plan §4 ARIA Patterns & Roles (Form input) requires `textarea` to map to `MultilineTextInput` under the HTML-AAM mapping; the fixture's textarea is expected to read that role on its snapshot node. Whether a Dioxus-built textarea's snapshot node already carries it is research's question.
- a11y-plan §7 Screen Reader Support (Accessibility tree output) states label binding for an `<input>` only — "the bound input must be an `input` element with a built node" — while `aria-label`, non-empty after trimming, names any element. As specified, a `<label for>` does not name a textarea, so the fixture's textarea takes its accessible name from `aria-label`. Whether the code binds a label to a textarea anyway is research's question.
- a11y-plan §7 Screen Reader Support (the actionable-key rule) requires every element an agent can act on — focusable, interactive role or listener — to read an author key; a textarea is focusable with no `tabindex` (per a11y-plan §5 Keyboard Navigation, Focus order), so the fixture's textarea carries an HTML `id` and reads it as its stable id.
- a11y-plan §9 CI Integration fixes the `a11y` job's shape: `bash .github/scripts/ci-leg.sh a11y` over three test files (6 + 6 + 3 tests), in the slow tier behind the four fast jobs, restoring the test job's cache and saving none, adding no stand assertion. Item 2's bound and retry on that job's install step must leave the leg, its test set, its tier and its cache behaviour as that section states them.

## Patterns to follow
- State proven through real input, in both layout modes: a pointer click, then key input, then the snapshot read, with exactly the focused control's node reading `focused` and being the tree's focus (per a11y-plan §7 Screen Reader Support, Accessibility tree output; per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- Expected roles and input names stated once, as tables in the stand checks' shared module — stated expectation, never a second mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output). Whether a fixture control's expectation belongs in those tables or beside its fixture is research's question.
- A11y assertions are Rust tests in blitz-tests, built with the `accessibility` feature on `blitz-dom` and `dioxus-native-dom` (per a11y-plan §3 A11y Assertion Harness Contract; per a11y-plan §1 A11y Scope Summary) — the new check needs no feature or dependency beyond that crate's.
- Focus is read through the harness's focused-node query (per a11y-plan §3 A11y Assertion Harness Contract, Focus management test harness).
- The CI a11y gate is discharged as the `a11y` job (per a11y-plan §3 Bootstrap phases, key `a11y-ci-gate-wire`, recorded in §9 CI Integration) — it is edited in place, not re-wired.

## Anti-patterns to avoid
- No second role or name mapping in the check or the fixture's helpers — the tree is the one source (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- No `<label for>` relied on as the textarea's only accessible name: the spec binds a label to an `input` element only, and an unnamed control fails the named-control expectation the stand checks hold (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- No textarea value asserted from the AccessKit tree, and no un-keyed textarea on the fixture (per a11y-plan §7 Screen Reader Support, Accessibility tree output and the actionable-key rule).
- a11y-plan §11 A11y Anti-Patterns reads `NO RECORDED INTENT`: nothing is extracted from it.
