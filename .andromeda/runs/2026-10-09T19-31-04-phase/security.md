## Constraints

- security-plan §Authentication & Authorization (the ci.yml `permissions` row) requires one workflow-level `permissions: contents: read` and no job-level grant in `ci.yml`. The bounded and retried install step — in place, as a script or as a local action — adds no `permissions:` block and needs no token.
- security-plan §Secret Management (Never in code · Environment values read) requires that source reads no secret and that env reads stay the listed, non-secret set. A script or action added under `.github/` references no `secrets.*` and no credential; a retry reaches no host the step does not already reach (scope §Boundaries). Whether the plan's env-read list is meant to cover CI shell scripts as well as Rust source is research's question if the script reads any variable.
- security-plan §Dependency Security (Lockfile verification) requires `Cargo.lock` committed and `--locked` on every `ci.yml` cargo leg. The chunk adds no crate: the new check uses what `blitz-tests` already has. Whether the textarea check needs any dev-dependency the crate lacks is research's question; if it does, §Dependency Security (Pinning) requires it inherited with `workspace = true`.
- security-plan §Input Validation (the password and file `input` value row) requires the snapshot's mask to be password- and file-only, every other element's `value` reading as before. A textarea's typed text reading back verbatim as the node's value is therefore the specified behaviour and not a leak; the fixture's typed text is synthetic, never a credential-shaped or personal string. If the textarea joins the fixture that holds the password input, the mask's standing assertions stay as they are.

- security-plan §Input Validation (the `id` row, the snapshot's crossing clause) requires the snapshot and its text to be returned to their caller only — no log, event, socket or file. The new check reads the snapshot in process; `packages/` is not edited, so no reader, text form or crossing is added. Whether the red reading kept as evidence is an excerpt holding fixture content only is the plan's to state.

## Patterns to follow
- A `uses:` line written as `owner/action@{40-hex sha} # {ref}` — the form security-plan §Dependency Security (Pinning) records for every action in `ci.yml`, the apt-caching action of another job included. Whether the eight steps can reuse that already-pinned action is the plan's, from research.
- Workflow security properties held by a test, not by review: security-plan §Dependency Security (Pinning) and §Authentication & Authorization each name an assertion in `.github/scripts/test_ci_workflows.py`. The scope's install-step invariant (every package-install step carries the bound and the retry) follows that pattern and lands beside them.
- CI tooling named with an exact version at its install site (security-plan §Dependency Security, Pinning — the audit and coverage tools). A retry helper brought from outside follows it; a retry loop written in the repository's own script needs no pin.
- A script that takes arguments checks them against a closed set and exits 2 with usage before doing any work (security-plan §Input Validation, the `agent-run.sh` and `cold-agent.sh` rows). It applies only if the stated-once install script takes a package list or a verb; a script with no argument has nothing to validate.
- Raw cargo/libtest output is treated as unscrubbed and kept under gitignored `target/` (security-plan §Logging & Monitoring, the agent-run contract entry). The mutant's red reading, if committed as evidence, is an excerpt, not a raw log dump.

## Anti-patterns to avoid
security-plan §Security Anti-Patterns holds no recorded intent; nothing is drawn from it. The bans below come from the sections cited.
- A floating action ref (`@v3`, `@main`, `@latest`) on a retry or timeout action in `ci.yml` — excluded by security-plan §Dependency Security (Pinning). The upstream-only workflows' `@latest` reference recorded there is not a precedent for `ci.yml`.
- A job-level `permissions:` grant, a `secrets.*` reference or a token env on the install path — excluded by security-plan §Authentication & Authorization (the ci.yml `permissions` row) and §Secret Management (Storage).
- Widening the mask to the textarea, or asserting a masked value for it, to make the check "safe" — security-plan §Input Validation (the password and file `input` value row) bounds the mask to those two input types, and the check's purpose is the verbatim reading.
