## Patterns to follow
- **An in-file fixture beside the stand.** Architecture §Existing Scopes → blitz-tests records `stand_snapshot_state.rs` as the snapshot's per-control state read through real input, with the control the lean tasks lack held on an in-file fixture; the fixture boots on the stand's own options (pinned viewport, bundled font, offline) per architecture §Standard Contracts → Headless stand (`stand::options(incremental)`).
- **The integration-test shape.** Per architecture §Conventions → Tests: the file opens with a `//!` doc naming the behaviour, the scenario runs `for incremental in [false, true]`, the test first asserts the fixture produces the condition under test, assertion helpers are `#[track_caller]`, and tables or helpers shared by stand checks live once in `tests/common/mod.rs`, read by `mod common;`.
- **A CI invariant is a `unittest` case in `test_ci_workflows.py`.** Per architecture §Stack and Technologies → CI/CD the workflow-invariant tests read the workflows with PyYAML and run in the `ci-scripts` leg; per architecture §Conventions → Tests the CI Python tests are `unittest`, one `TestCase` per function. An "every package-install step is bounded and retried" invariant takes that form.
- **One statement of a CI command, as a bash script under `.github/scripts/`.** Architecture §Infrastructure Patterns → CI/CD records `ci-leg.sh` as the single statement every linux job runs; if the install is stated once, that is the standing shape to mirror — a sibling script, not a new leg (constraint 4).
- **The conditional install is the same class.** Architecture §Stack and Technologies → CI/CD records the `ci-scripts` job ensuring PyYAML as Ubuntu `python3-yaml` — the scope's ninth install, and the job that runs the invariant tests themselves; the plan's decision on it is made knowing an unbounded hang there holds the leg that would detect one.

## Anti-patterns to avoid
- **Touching the upstream-only workflows.** `wpt.yml`, `wpt-post-results.yml` and `publish-browser.yml` run only behind the `github.repository == 'DioxusLabs/blitz'` guard (architecture §Occupied Resources → CI infrastructure); a bound added there is outside "fork CI" and risks the guard.
- **Reaching the private reader to test it.** `value` sits in a crate-private module (architecture §Existing Scopes → dioxus-native-dom); architecture §Conventions → Tests records the crate's tests reaching private state with no constructor, `pub` or `cfg(test)` shim added. No visibility change, re-export or shim in `dioxus-native-dom` to make the mutant killable — the check goes through the public snapshot.
- **A retry that widens the workflow's grant.** No job-level `permissions`, secret or token for the retry mechanism (architecture §Infrastructure Patterns → CI/CD: `contents: read` workflow-wide, no job-level grant).
