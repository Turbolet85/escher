## Constraints
- **The textarea is a case the plan's coverage statement does not name.** test-plan §1 Test Scope Summary (the `tests/blitz-tests` row and the `dioxus-native-dom` row) requires each control's state proven through real input in both layout modes and lists the value readings it holds — typed text on a text input, the password and file masks, the range input — with no textarea among them (the word occurs nowhere in the plan). The new check is therefore an addition to that statement, not a restatement of it; whether any standing check already reads a textarea's value is research's question, and so is whether the file the check lands in belongs to the test set the audit's `dioxus-native-dom/snapshot` unit runs.
- **A stand-option fixture check asserts unconditionally.** test-plan §2 Test Strategy → Font-dependent tests requires the headless-stand checks to carry no skip path: they run under the bundled font with system fonts off. test-plan §8 Mocking & Stubbing Discipline → Real dependencies kept states the same font as a kept real dependency. A fixture booted with the stand's options inherits both.
- **The gate is the workspace leg, and a per-file run is only the inner loop.** test-plan §9 CI Integration → Local pre-push gate names `bash .github/scripts/ci-leg.sh fast` (fmt → clippy → test → ci-scripts); test-plan §9 CI Integration → Engine features by runner requires that a green `cargo test -p blitz-tests --locked` is never read as the workspace leg's green, because the two build the engine with different features. Commands the implementation must pass: `cargo test -p blitz-tests --locked --test {name}` for the new check, then `bash .github/scripts/ci-leg.sh fast`.
- **The new check also runs on the windows and macos matrix legs.** test-plan §1 Test Scope Summary → Surfaces under test (Native platforms) states those legs run `test --all --tests --locked`, so a check that is not `cfg`-gated is compiled and run there. test-plan §3 Test Harness Contract → Input helpers records one platform difference in the text editor (the macOS Backspace arm); whether typed characters reach a textarea's editor identically on all three platforms is research's question.
- **Any edit of `ci.yml` stands under the workflow invariants.** test-plan §4 Unit Test Strategy → CI workflows and leg script requires, through `CiWorkflowTest`: every `uses:` pinned to a 40-hex commit SHA, each linux job's leg run through `ci-leg.sh`, the fast four with no `needs`, workflow-level `permissions` of `contents: read` with no job grant, no `secrets.`, and each leg job's `if: failure()` log upload. A retry taken from a third-party action falls under the SHA pin; whether a local composite action (`uses: ./…`) passes that pin as the test is written is research's question, and so is how the `if: failure()` upload behaves when the job dies in the install step before any leg log exists.
- **The plan states no bound and no retry on any install step.** test-plan §9 CI Integration → Legs describes the twelve linux jobs by their `ci-leg.sh` leg only, and test-plan §1 Test Scope Summary → CI Python scripts names the `ci-scripts` job's own PyYAML ensure step (the scope's ninth install) with no bound. Neither `apt-get`, a step timeout nor a retry occurs in the plan body, so Item 2 has no test-plan mandate to satisfy and none to contradict; the scope's expectation that the plan's quality-gates text "owns" the unbounded step is not borne out — test-plan §10 holds one unthresholded coverage reading and is otherwise marked. The statement of the bound is the wrap's amendment to §9.
- **The stand selection is by file prefix and its counts move.** test-plan §3 Test Harness Contract → Agent-run contract → `run` requires `run stand` to select one `--test` per `stand_*.rs` present, with no script change for a new file, and `tests/common/mod.rs` to be no target; an outcome is `passed` only when cargo exits 0, nothing fails and at least one test line parses. The last measured `run.end` in §3 → Proof (passed 109 · failed 0 · ignored 5 over 30 files) and the workspace count in test-plan §9 CI Integration → Local baseline (656 passed · 0 failed · 10 ignored, 154 result lines) are the baselines the chunk re-counts from; research re-reads both at HEAD rather than taking the plan's figures.

## Patterns to follow
- **An in-file fixture booted with the stand's options, beside the stand.** test-plan §1 Test Scope Summary (the `tests/blitz-tests` row) places the controls the lean tasks lack — checkbox, radio, password — on an in-file fixture of `stand_snapshot_state`; test-plan §3 Test Harness Contract → Construction gives the boot (`Harness::from_vdom` with `stand::options(incremental)`), and test-plan §7 Test Data & Fixtures → Builders and options states what those options pin. The check runs `for incremental in [false, true]`, as the same §1 row requires of every stand state check.
- **Real input through the harness helpers, never a raw dispatch.** test-plan §3 Test Harness Contract → Input helpers lists `click` and `type_text`, each pumping after its dispatch; test-plan §5 Integration Test Strategy → Harness ↔ event pipeline requires input to route through the document's real event pipeline and records that `dispatch_recorded` bypasses the Dioxus VirtualDom forwarding — so a Dioxus-built fixture is typed into with the helpers.
- **Shared tables and helpers are read from `tests/common/mod.rs`, per-file constants stay per file.** test-plan §3 Test Harness Contract → Crate-local test helpers (blitz-tests, stand checks) requires a check to declare `mod common;` and read `boot`, `node`, `by_id`, `tree_node`, `name` and `editor_text` from there, with the tables as stated expectation only.
- **A kill is shown by a mutation control: red on the mutated tree, green on the restored one, recorded as evidence.** test-plan §4 Unit Test Strategy → What unit tests cover (escher-driver) records this form three times — each control turning a named test red and reading green again on the restored tree, filed as the chunk's `evidence/controls.md`; test-plan §1 Test Scope Summary (the `dioxus-native-dom` row) records the earlier audit-corrections precedent, each surviving mutant turning at least one new test red.
- **Workflow rules are pinned in `test_ci_workflows.py`; a script's behaviour is proven with a shim on PATH.** test-plan §4 Unit Test Strategy → CI workflows and leg script gives both forms: `CiWorkflowTest` pins `ci.yml` properties over the parsed workflow, and `LegScriptTest` runs `ci-leg.sh` in a temp dir with a `cargo` shim on PATH to prove a failing leg's exit and log. If the install becomes a script, the same shim form (a stand-in for the package manager that fails or stalls) proves the retry and the bound locally; test-plan §3 Test Harness Contract → Cold-agent run pipe → `run counter` is the plan's one precedent for a `timeout`-bounded command whose expiry is a named failure rather than a propagated 124.

## Anti-patterns to avoid
_test-plan §11 reads NO RECORDED INTENT — nothing is cited from it; each ban below is stated in the section it names._
- A skip path or an assertion that can pass without asserting in a stand-option check — test-plan §2 Test Strategy → Font-dependent tests bans the skip for stand checks; a typed value that does not arrive must fail the check, never be stepped over.
- Reading a per-package or per-file green as the chunk's gate — test-plan §9 CI Integration → Engine features by runner states a green `-p blitz-tests` run is not the workspace leg's green.
- An unpinned `uses:`, a `secrets.` reference or a job-level permission grant brought into `ci.yml` by the retry mechanism — test-plan §4 Unit Test Strategy → CI workflows and leg script pins all three, and the `ci-scripts` leg turns red on any.

## Contract bindings
- **tests ↔ a11y:** the snapshot's `value` reading is a11y surface, and the fixture's textarea is an actionable element under the a11y actionable-key rule; the a11y CI leg's file list is fixed in test-plan §9 CI Integration → Legs (`accessibility_hidden`, `accessibility_roles`, `focusability_updates`) — a new `stand_*` check is not in that leg and reaches CI through the `test` leg and the matrix only.
- **tests ↔ architecture:** a script or local action added under `.github/` changes the CI pipeline's shape, which test-plan §9 CI Integration → Legs describes and arch §Infrastructure Patterns registers; the `ci-leg.sh` leg list itself is pinned by test-plan §4 Unit Test Strategy → CI workflows and leg script.
- **tests ↔ security:** the SHA pin on `uses:`, the absence of `secrets.` and the read-only `permissions` are security rules enforced by this domain's `CiWorkflowTest` (test-plan §4 Unit Test Strategy → CI workflows and leg script); the `audit` leg is untouched.
- **tests ↔ obs (5-command discipline):** the new check surfaces as `test` events and in `run.end` of `bash scripts/agent-run.sh run stand`, harness metadata that is no escher-telemetry sink (test-plan §3 Test Harness Contract → Agent-run contract → Events); no log format, status shape or scrub set is touched.
