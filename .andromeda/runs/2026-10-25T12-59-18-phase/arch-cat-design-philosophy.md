## Carried
- (.andromeda/architecture.md:7) A load in flight on the stand must reach the stand's document only through a provider the embedder (the stand's boot) supplies, never an internal HTTP client or an engine change.
  > - **Embedder services are injected, with no-op defaults** — networking, navigation, shell and parsing reach the DOM only through provider traits the embedder supplies; script fetches go through the embedder's net provider, never an internal HTTP client.
- (.andromeda/architecture-detail/design-philosophy.md:24) The stand's held load must be carried by a `NetProvider` set on `DocumentConfig` (the seam `HeldNet` uses in the fixtures), with every unset provider left on its `Dummy*` default, so the stand otherwise stays offline.
  > `DocumentConfig` carries trait-object providers `NetProvider`, `NavigationProvider`, `ShellProvider`, `HtmlParserProvider` (packages/blitz-dom/src/config.rs:40-47); when one is not supplied, `BaseDocument::new` falls back to `DummyNetProvider`, `DummyNavigationProvider`, `DummyShellProvider` and `DummyHtmlParserProvider` (packages/blitz-dom/src/document.rs:474-485; packages/blitz-traits/src/net.rs:19-30; packages/blitz-traits/src/net.rs:165-173; packages/blitz-traits/src/navigation.rs:10-20; packages/blitz-traits/src/shell.rs:11-66)
- (.andromeda/architecture-detail/design-philosophy.md:11) The stand extension must be external code that drives the headless DOM through its `DioxusDocument` wrapper. Networking stays in its own crate, so the stand's load does not move networking into blitz-dom or the stand. The select model and the load wait already stand in the engine, so no engine change is made.
  > blitz-dom is a flexible headless DOM (`BaseDocument`) designed to be embedded in and "driven" by external code, with most users expected to use a wrapper (`HtmlDocument` from blitz-html, `DioxusDocument` from dioxus-native) (packages/blitz-dom/src/lib.rs:3-10); it holds the DOM tree, CSS parsing and resolution, layout and event handling, while html parsing (blitz-html), networking (blitz-net), rendering (blitz-paint) and windowing (blitz-shell) live in separate crates (packages/blitz-dom/src/lib.rs:12-14)
- (.andromeda/architecture.md:9) The flight booker's one-way / return choice must be a real HTML `select` driven by the engine's spec-written select semantics, not a stand-local imitation. A semantics gap the stand would need closed in the engine is a P4 fork.
  > - **Behave like a browser, and cite the spec** — web semantics are written against named specifications and named browser engines.
- (.andromeda/architecture.md:11) Every stand change (Cells served to the driver, the select, the held load) and every stand pin it moves must read the same in both layout modes.
  > both layout modes produce identical layouts, a dropped node's id stops resolving instead of aliasing a reused slot
- (.andromeda/architecture-detail/design-philosophy.md:46) The re-pinned stand checks and the new ones must hold under incremental and non-incremental layout alike, with the incremental oracle unbroken.
  > Incremental and non-incremental layout run the same style → damage → box construction → layout pipeline; non-incremental marks every node damaged each resolve (packages/blitz-dom/src/document.rs:2223-2240; packages/blitz-dom/src/resolve.rs:87-93), so the two must produce identical layouts after any sequence of mutations (tests/blitz-tests/tests/incremental_oracle.rs:1-7)
- (.andromeda/architecture.md:13) The extended stand must be exercised with no window, through the headless harness the stand boots on and the driver serves.
  > the engine is exercised without a window through a headless harness, a WPT runner and phase-split benchmarks
- (.andromeda/architecture-detail/design-philosophy.md:60) The stand checks for Cells' parts, the select and the held load must run headless, with input synthesized through the real event-dispatch pipeline, and live as integration tests in blitz-tests' `tests/` directory.
  > The test harness runs headless: no window, GPU or compositor is required, and synthesized input routes through the real event-dispatch pipeline (packages/blitz-test-harness/src/lib.rs:1-19); integration tests live in the `tests/` directory of the blitz-tests crate (tests/blitz-tests/lib.rs:1)
