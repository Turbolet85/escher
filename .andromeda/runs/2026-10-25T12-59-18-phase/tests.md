# tests extract

## Relevance
relevant — the chunk moves the cold-agent run pipe and its contract tests, the stand's booted task set and its stated tables, and the stand checks the `stand-repeat` zero-failure budget runs.

## Constraints
- The cold-agent pipe's contract is fixed per test-plan §3 Cold-agent run pipe: exit grammar `0`·`1`·`2`·`3` with usage checked before any precondition, a task outside `TASKS` a usage error, the fixed prompt naming no element id and no app slug, `isolated` meaning exactly the twelve `mcp__escher__{verb}` tools and one server `escher`, and `outcome` `passed` only on positive evidence (`tasks_met` read from `snapshot` answers under the latest accepted `start`, never from the reply; `check_passed` and `check_can_fail`). New goals over v020-04…v020-09 change what `tasks_met` reads and what the prompt asks, so each verdict rule that moves is a contract change. Whether the pipe can judge goals such as a paged read, a `select` choice or a load wait from `snapshot` answers alone is research's question.
- test-plan §3 Cold-agent run pipe (Events, State) requires that no event or verdict field is content-named and that no transcript text, tool argument, tool answer, reply or check text reaches one. `server.log` is counted by span name and never printed or copied, and `check.json` is never printed. Any new verdict field the new goals add stays a bool, count or closed word.
- test-plan §4 Cold-agent pipe requires `test_cold_agent.py` to run the pipe under the `claude` shim and the fake `target/debug/escher-session` with no live model, credential or built binary, with one case per verdict path. That includes the prompt naming no stand id and the scrub-set and four-planted-marker cases. The fake's answers move with whatever new goal answers the judge reads, such as a paged `snapshot` or a select's value. The `ci-scripts` leg's stated count (104 tests over eight files, test-plan §4 detail) moves with it.
- test-plan §3 Crate-local test helpers (blitz-tests stand checks) gives `tests/common/mod.rs` as the one statement of the stand's tables: `controls(task)`, `INPUT_NAMES`, `rendered(task)`, `tab_order(task)`, `ENABLED_TAB_ORDER` and `REGION_NAMES`. A flight booker one-way/return `select` re-pins these tables, as well as the checks that read them (`stand_keyboard`, `stand_contrast`, `stand_element_ids`, `stand_actionable_keys`, the snapshot, diff and act checks). Serving `cells` adds its rows wherever a table is keyed by lean task.
- test-plan §3 Session lifecycle (`session-binary`) fixes `start`'s task as one of `counter` · `flight-booker` · `timer` · `crud`. Serving `cells` through `start`, the host role and the `mcp` role is a contract change to that row. test-plan §6 Command line requires `cli_commands` to start, answer and stop each task, and states each task's snapshot size inside the 10,000-byte budget, which a served over-budget screen breaks by design.
- test-plan §10 Flakiness budget gives the stand checks a zero-failure budget: `stand-repeat` runs every `stand_*.rs` file, the ten named blitz-tests targets and seven_guis' process checks three times with no retry. Any stand check that is added or moved, a load-in-flight one included, holds green there. Per test-plan §5 Wall time in the session checks, session checks take no sleep and no wall-clock read except `stand_virtual_clock`'s and `stand_load_wait`'s.
- test-plan §7 Builders and options states `stand::options(incremental)` with `net_provider: None`, and test-plan §8 Network names `HeldNet` as escher's one held network stand-in, which the harness counts loads through. A load in flight on the stand changes the stand's pinned options or adds a stand-in. test-plan §2 Font-dependent tests requires the headless-stand checks to keep asserting unconditionally under the bundled DejaVu Sans with no skip path.

## Patterns to follow
- A new stand check joins by its `stand_` prefix with no script change: `agent-run.sh run stand` selects one `--test` per `stand_*.rs` (test-plan §3 Agent-run contract), and `stand-repeat` does the same (test-plan §9 Legs).
- Held-session checks use `tests/session_common/mod.rs`: `hold(task, incremental)`, the call builders (`click`, `type_into`, `snapshot_part(n)`, `lint()`, …), and the readers `act`, `part`, `refused`, `linted`. Fixture boots go through `tests/fixtures/mod.rs` (`boot`, `hold`, `many_items`, `HeldNet`). A page with one reader stays in its check's file (test-plan §3 Crate-local test helpers).
- Command-line flows are POSIX `sh` assets of a `cargo test` target (`cli_flow` runs `examples/seven_guis/tests/flows/{counter,flight}.sh`), and no framework is added. `flight.sh` moves with the flight booker's control (test-plan §2 Command-line checks and shell flows).
- Recorded-check replay: a recorded session's check runs through `Check::replay`, red at the first step whose acceptance or kept answer differs. A committed check is kept fresh by a byte-for-byte comparison with what the binary records (test-plan §2 Recorded-check replay). This is the standing form for a "passes on replay" half that names the driver's own kept check.
- The cold-agent judge replays the agent's check on fresh `escher-session mcp` children, in full and then ablated, each reply under the 30 s `REPLY_BOUND` and each child killed and reaped (test-plan §3 Cold-agent run pipe). A served `cells` screen's replies must fit that bound.

## Anti-patterns to avoid
- The live cold-agent run never goes into CI, and no credential, transcript text or host path goes into committed evidence. Proof is the shimmed contract tests plus one operator-host run (test-plan §3 Cold-agent run pipe, Proof).
- The stand tables never become a second role or name mapping, because they are stated expectation (test-plan §3 Crate-local test helpers). No skip path is added to a stand check (test-plan §2 Font-dependent tests).
- `stand-repeat` gets no retry, no `--ignored` and no env var to make a load-in-flight or timing-sensitive stand check pass (test-plan §9 Legs).

## Contract bindings
- tests ↔ obs: the pipe counts wrong calls from the server's ` span="tool_call" ` lines and their ` ending="refused" ` / ` ending="error" ` (test-plan §3 Cold-agent run pipe), which binds to obs-plan §3/§4's `tool_call` span (`tool`, `ending` closed words). The pipe's events are harness metadata, not an escher-telemetry sink (obs-plan §3).
- tests ↔ a11y: `stand_keyboard` (`tab_order`, `ENABLED_TAB_ORDER`, Enter/Space), `stand_contrast` (`TEXT_ROWS`, `STATE_ROWS`) and `stand_act_select` run in the a11y leg as well as `stand-repeat` (test-plan §9 Legs). A flight booker `select` moves a11y-plan's SC 2.1.1 · 2.4.3 · 1.4.3 pins through those tables.
- tests ↔ security: the live run's carriage of the stand's screen to the model provider was proven once, on the founder's «Один запуск, до $3 (Рекомендую)» (test-plan §3 Cold-agent run pipe, Proof), and is bound by security-plan §Surfaces. Whether a second run over new screens needs his word again is research's reading.
- tests ↔ residuals: test-plan §5 detail (Session host ↔ what it writes) states that a paged `part` read through the `escher-session` host's own sink stays unmeasured because the host boots only the four lean tasks and none pages, and a `.andromeda/residuals.md` line owns it. Serving `cells` makes that read reachable. Whether this chunk takes it is P3/P4's question.

The run is never in CI (per test-plan §3 Cold-agent run pipe).
