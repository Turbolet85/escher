# security extract

## Relevance
relevant — the chunk fires a second live cold-agent run that carries the stand's screen to the model provider through the operator's login. It also widens the agent-written check's goals and serves new stand screens (Cells, a `select`, a load in flight) to an untrusted model.

## Constraints
- Before the run fires, someone must decide whether the ratified carriage covers a second run. Per security-plan §Threat Model Summary (Vector: local stdio, the driver's MCP server), the cold-agent pipe's carriage of the stand's screen to the model provider (ids, names and values in snapshot texts and diffs) was ratified for one run only, on «Один запуск, до $3 (Рекомендую)» (2026-10-15). That run made 43 calls and called no `screenshot`. Whether that ratification covers a second run, which would carry new screens (Cells' contents, the select's options and value, possibly a `screenshot` image block or a lint's findings), is P3's reading. If it is open, it becomes the founder's fork at P4, before the run fires.
- The run reaches the model provider only through the operator's own Claude Code login, held by the `claude` CLI outside the repository. Per security-plan §Secret Management (Storage, Development), that means no API key, no env read by the pipe, no CI secret, no new secret source and no auth library. Committed live evidence holds no key, auth header, credential-file name, token field or e-mail address.
- The agent-written check stays an untrusted input under its current bounds. Per security-plan §Input Validation (Cold-agent check row), that means: only the reply's last fenced json block, at most 65,536 bytes, a JSON array of at most 400 steps; closed step keys, with `tool` one of the twelve verbs; replay on fresh `escher-session mcp` children with every step re-validated by the server, a 30 s reply bound and each child killed and reaped; `check.json` is never printed. New goals (recording/replay, lint, `advance`, load wait, `select`, `snapshot` parts) must fit these bounds without loosening them. Whether a Cells boot or a held load fits the 30 s reply bound is research's question.
- The pipe's argv and prompt stay closed. Per security-plan §Input Validation (CLI arguments, cold-agent.sh), a verb or task outside the allowlist exits 2 before any precondition or `claude` call. The task reaches the agent only as a fixed prompt that names no element id and no app slug. A widened `STAND_PROMPT` or added task set keeps both rules.
- The pipe logs run metadata only. Per security-plan §Logging & Monitoring (the cold-agent pipe row), `events.jsonl` and `verdict.json` hold only counts, booleans and closed words: no transcript text, tool argument, tool answer, reply or check. `server.log` is counted by span name and never printed or copied. The replay children's stderr goes to `/dev/null`. The raw transcript is unscrubbed by design, gitignored under `target/`, and any committed copy has its host paths masked.
- A load in flight on the stand must not route agent- or user-supplied URLs through blitz-net. Per security-plan §Input Validation (`file:` URLs (net provider) row), blitz-net reads `file:` URLs with no path restriction. Per security-plan §API Security (Outbound requests), outbound requests have no response size limit and no request timeout. The stand's load is bounded only by `LOAD_WAIT` (per security-plan §API Security, Settle and loads in flight). Per security-plan §API Security, no served network API or port exists, so a stand load must add no listener or port. Per security-plan §Secret Management (Environment values read), every env read is enumerated, so any new one must be added there.
- Kept checks from this run stay private. Per security-plan §Data Protection (At rest, Files (committed checks)), only the two stand-Counter checks are committed. Any `--record` kept check of this run is a check of another session: it stays owner-only (`0600` in a `0700` directory) and is never committed (per security-plan §Data Protection, At rest, Files (kept checks)).

## Patterns to follow
- Extend the pipe's existing parse/judge/replay chain (`extract_check`, `judge_check`, `valid_step`, the full then ablated replay in `scripts/cold-agent.sh`) rather than adding a second reader of the model's reply (per security-plan §Input Validation, Cold-agent check row).
- Serving Cells to an agent that types formulas relies on the stand's own input checks: the tokenizer rejects unknown characters, reference cycles read `#CYCLE`, and division by zero is an error (per security-plan §Input Validation, Example apps, 7GUIs inputs row). Keep those checks as the guard, with no panic path on typed text.
- A real flight-booker `select` reuses the engine's select model as already recorded: the typeahead buffer is never carried out, and the choice leaves only through the ratified carriers as the snapshot's `value` (per security-plan §Input Validation, Markup attributes row).
- Mask committed transcripts and evidence for host paths (the session dir and the home prefix) before commit (per security-plan §Logging & Monitoring, the cold-agent pipe row). The deferred learning on host temp paths applies to every committed line.

## Anti-patterns to avoid
- Printing, copying or committing `check.json`, `server.log` or an unmasked `transcript.jsonl`, and adding a content-named field to `events.jsonl` or `verdict.json` (per security-plan §Logging & Monitoring).
- Adding an API key, an `ANTHROPIC_*` or other env read, or a CI secret to the pipe. CI runs only the shim contract tests (per security-plan §Secret Management).
- Giving the stand a network fetch or a URL the agent can name (per security-plan §Input Validation, `file:` URLs row).

## Contract bindings
- security ↔ obs: the wrong-call count is read from `server.log`'s `tool_call` span lines and their `refused` / `error` endings (per security-plan §Logging & Monitoring). This binds to obs-plan's `tool_call` span contract, whose fields stay `tool` and `ending` only (per security-plan §Input Validation, MCP server row).
- security ↔ tests: `.github/scripts/test_cold_agent.py` must move with the prompt and goals. It holds the scrub-set key check, the planted markers, `test_the_prompt_names_no_stand_id` and the usage-exit-2 cases (per security-plan §Input Validation, CLI arguments (cold-agent.sh); per security-plan §Logging & Monitoring).
- security ↔ arch: a load in flight on the stand that adds a provider, resource, listener or env read is an arch §Occupied Resources registration plus a security-plan amendment first (per security-plan §API Security; per security-plan §Secret Management, Environment values read).

## Acceptance criteria contributions
- The committed run evidence (transcript copy, events, verdict) passes a credential scan with 0 hits for key, auth header, credential-file name, token field or e-mail; the `"apiKeySource":"none"` field is allowed. It also holds no unmasked host path (per security-plan §Secret Management).
- The live run's `events.jsonl` and `verdict.json` hold 0 scrub-set keys, and `check.json`, `server.log` and the transcript are never printed by `status` or `logs` (per security-plan §Logging & Monitoring).
- `test_cold_agent.py` stays green. A task outside the allowlist exits 2 before any `claude` call, the widened prompt names no element id or app slug, and the check bounds (65,536 bytes, 400 steps, closed keys, twelve verbs, 30 s reply bound) are unchanged (per security-plan §Input Validation).
- The live run fires only once a founder's word recorded in the chunk's inputs covers its carriage of the new stand screens to the model provider (per security-plan §Threat Model Summary).
