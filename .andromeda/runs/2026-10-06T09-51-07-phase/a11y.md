# a11y extract

## Relevance
partial. The chunk proves the id persists and adds no new UI by intent. Its a11y exposure is limited to these possible changes: author-key or row-key edits in the lean tasks, a stand remount affordance, and re-render cases that toggle `disabled` or conditional siblings. Each of these touches the tier-0 surface, which is focusability, focus order and painted colour.

## Constraints
- The a11y tier is 0, with the target SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary). Any author `id` added to a lean control, any CRUD row re-keying (`crud.rs`) and any remount affordance must leave keyboard operability, focus order and painted colour of the lean four unchanged. Scope §Surfaces requires that no focusability, focus-order or painted-colour change happen.
- Focusability is derived from `tabindex`, `href`, `disabled` and the element type, and it is recomputed when those attributes change (per a11y-plan §5 Keyboard Navigation → Focus order per layout (engine)). An `id` attribute or a Dioxus `key` is not among those inputs. Whether adding an author `id` or re-keying a row actually leaves the cached focusability and Tab order unchanged is research's question. If a key change re-creates nodes, the question includes the case where re-created nodes change Tab order.
- Disabled-ness has two keys: attribute presence (`:disabled`, click target) and the bool-parsed value (focusability). A falsy Dioxus `disabled` removes the attribute (per a11y-plan §5 → Script and framework exposure). A re-render check that toggles `disabled`, such as flight booker's `.flight-btn`, must read the element's id across the toggle. It must not rely on the toggle to rename the element. Whether the toggle leaves the element's `{tag}:{n}` id stable is research's question.
- When a remount removes the focused node, focus must reset to the body, which is encoded as `None`, and blur side effects must run (per a11y-plan §5 → Focus restoration). This applies to any remount path this chunk adds, whether through app Back/Home navigation or a stand-side toggle. A remount must not leave focus on a stale `NodeId`, consistent with the versioned-slot invariant the scope keeps.
- Any Dioxus boolean other than `disabled`/`checked` is still written as the literal `"false"`. For `hidden`, a presence read would then drop the node from the a11y tree (per a11y-plan §5 → Script and framework exposure). A stand-side remount toggle or conditional branch must not express "shown" as `hidden: false`.
- The AccessKit node id is the DOM `NodeId` (`NodeId(node_id.as_u64())`) (per a11y-plan §3 A11y Assertion Harness Contract; a11y-plan §7 Screen Reader Support → Accessibility tree output). Putting the stable id on accessibility nodes is out of scope here and belongs to v010-03, so this chunk must not change how the a11y tree keys its nodes.

## Patterns to follow
- Focus-state assertions in stand checks should use the harness's focused/hovered node queries (per a11y-plan §3 → Focus management test harness). A remount check that wants to show focus did not survive on a stale node should read the focused node through these queries.
- Assert state cues without colour, as the headless-stand flight-booker check does: it checks the `invalid` class plus the `disabled` attribute appearing (per a11y-plan §8 Cognitive Accessibility → Error recovery). A re-render check that relies on the invalid/disabled toggle should assert the cue the same way and also assert that the id held.
- Focusability-follows-attribute tests set or clear the attribute after creation and then assert (per a11y-plan §5 → Focus order per layout (engine), `focusability_updates.rs`). Use this shape if research finds a key or id change touches focusability.

## Anti-patterns to avoid
- Do not add a remount affordance that works only by pointer, such as a clickable `div` like the browser's controls (per a11y-plan §4 ARIA Patterns & Roles → Application markup). If the affordance is rendered, it must be a native, focusable control so that SC 2.1.1 holds (per a11y-plan §1; §5 → Focus order per layout (engine)).
- Do not use `tabindex`, `disabled` or `hidden` as the means of stabilising an id. Author keys must be identity-only attributes (`id`, Dioxus `key`) so that focusability and tree membership are untouched (per a11y-plan §5 → Focus order per layout (engine); §4 → Hidden content).

## Contract bindings
- a11y ↔ tests: the `a11y` CI leg (`ci-leg.sh a11y`: `accessibility_hidden`, `accessibility_roles`, `focusability_updates`) runs beside the workspace test leg that carries the new `stand_*` persistence checks (per a11y-plan §9 CI Integration). Both legs must stay green. The new stand checks are not a11y-leg tests.
- a11y ↔ obs: the obs scrub prints only allowlisted fields (`node_id`, `status`, …) for `blitz*`/`accesskit_xplat` targets (per a11y-plan §3 → NOT-YET-MEASURED note citing obs §3/§6/§8; only the obs-format sentence is used, no a11y content from it). An element id carries author content, so no id may enter an a11y- or engine-target log field.
- a11y ↔ layouts: layout-templates records the lean tasks' author ids. Any new author `id` or row key changes that record, and focus order per surface must stay as recorded there (per a11y-plan §5 → Focus order per layout (engine)).
- a11y ↔ v010-03 (next entry): id coherence with the AccessKit tree is deferred there (per a11y-plan §7 → Accessibility tree output; scope §Boundaries).

## Acceptance criteria contributions
- (a11y) `bash .github/scripts/ci-leg.sh a11y` passes, with the same test count as before the chunk (per a11y-plan §9 CI Integration).
- (a11y) After any author-`id` or CRUD row-key change, every lean-task control that was focusable before stays focusable, and the Tab sequence over the lean four is unchanged (per a11y-plan §5 Keyboard Navigation → Focus order per layout (engine)).
- (a11y) In the remount check, if a control was focused before the remount, the focused node afterwards is the body (`None`) or a live node, never the stale pre-remount `NodeId` (per a11y-plan §5 → Focus restoration).
- (a11y) If a stand remount affordance is rendered, it is a native focusable control that can be activated without a pointer (per a11y-plan §1 A11y Scope Summary; §5 → Focus order per layout (engine)).
