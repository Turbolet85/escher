## Constraints
- Proof checks are Cargo integration tests in `tests/blitz-tests/tests/`, one file per behaviour, plain `#[test]` with `assert!`/`assert_eq!`, dev-dependencies only, and no in-file `#[cfg(test)]` modules in that crate (per test-plan §2 Test directory + naming conventions; §5 Boundaries covered, tests/blitz-tests crate; §4 Observed absent). A file must carry the `stand_` prefix for `run stand` to select it (per test-plan §3 Agent-run contract, `run {selection}`).
- Every stand boot goes through `seven_guis::stand::boot(LeanTask, HarnessOptions)` / `boot_timer`, each a fresh `VirtualDom` over `from_vdom` in TaskShell, with `stand::options(incremental)` as the pinned options (800×600, scale 1.0, Light, bundled font, no net, no base URL). The checks cover both layout modes, as the existing stand id check does (per test-plan §3 blitz-test-harness, Construction; §7 Builders and options; §1 Coverage scope, tests/blitz-tests stand line). Any remount affordance added to `stand.rs` must keep this boot surface intact for the existing `stand_*` checks.
- Stand checks have no font-skip path. They assert unconditionally under the bundled DejaVu Sans with system fonts off, so they measure the same on any runner, including in the `-p blitz-tests` package-alone build (per test-plan §2 Test levels observed, Font-dependent tests; §8 Real dependencies kept; §9 Pipeline facts, Fonts).
- Re-render triggers that must reach Dioxus have to go through the harness input helpers (click, type_text, press…), which pump after dispatch. `dispatch_recorded` bypasses Dioxus VirtualDom forwarding and does not pump (per test-plan §3 blitz-test-harness, Input helpers / Pump semantics; §5 Boundaries covered, Harness ↔ event pipeline). The timer re-render is driven by `TimerTicks::deliver(n)`, applied on the next pump; an undelivered source holds elapsed at 0.0 s (per test-plan §8 Hand-written fakes and stubs, Time (seven_guis timer)).
- If the fresh-process check runs through `scripts/agent-run.sh`, the five-verb contract stays fixed: the exit grammar 0/1/2/3, `run` selections `stand | all | {name}`, the event shapes, and state confined to `target/agent-run/`. Captured stdout and panic text never reach an event (per test-plan §3 Agent-run contract, Exit grammar / `run {selection}` / Events / State).
- Work closes on the local pre-push gate `bash .github/scripts/ci-leg.sh fast` (fmt → clippy → test → ci-scripts). The new result lines and counts are re-counted against the recorded baseline: 121 result lines, 441 passed · 0 failed · 4 ignored at 2026-10-06-stable-element-ids (per test-plan §9 Pipeline facts, Local pre-push gate / Local baseline).

## Patterns to follow
- The `element_id` unit-test idiom: build a `DioxusDocument` from a plain `fn() -> Element` app, re-render by flipping a `GlobalSignal` inside `vdom.in_runtime`, and stale a detached node only by dropping it through `DocumentMutator::remove_node_if_unparented`, because a re-render alone only detaches it (per test-plan §3 Crate-local test helpers, dioxus-native-dom). This bears on the remount proof. "The `NodeId` changed" must be shown against a node that was actually dropped, not merely detached. Whether a remount on the stand drops the old nodes or only detaches them is research's question.
- `dom_string` is the stable one-node-per-line serialization for snapshot-style assertions, already used for fresh-boot and incremental identity on the stand (per test-plan §2 Harness-driven tests; §1 Coverage scope, stand line). It is a fit for the evidence that "the re-render changed the DOM" and for a cross-process comparison payload.
- Slab and `ElementId` reuse is a known hazard. The randomized-stress test runs 1000 deterministic LCG template swaps to shake it out (per test-plan §2 Randomized stress). The remount check's "fresh `NodeId`" evidence must compare the versioned id, not a raw slot index that could be reused.
- Name each test for the behaviour or bug it guards, as `keyed_nodes_do_not_crash` and the stand checks do (per test-plan §2 Test function naming).
- For the fresh-process leg, the plan records process-global behaviour as tested in dedicated `telemetry_*` integration files, with one ignored `child_emits` test (per test-plan §1 Coverage scope, escher-telemetry; §9 Local baseline). Whether that file holds a re-exec-the-test-binary child pattern that the fresh-process check can reuse is research's question.

## Anti-patterns to avoid
- A check that passes without asserting. The plan records two text-input tests that assert only inside an `if` on measured size (per test-plan §4 What unit tests cover, Conditional assertions). A persistence check whose re-render changed nothing, whose remount kept the same `NodeId`s, or whose "two processes" share a PID is vacuous in the same way. It must fail unless the event happened.
- Treating an empty run as a pass. An empty run is never a pass under the agent-run contract (per test-plan §3 Agent-run contract, `run {selection}`). For the same reason, a cross-process id comparison over two empty id lists must fail, not pass.
- A runtime skip (`eprintln!` and return) on the stand. That is the pre-existing font-dependent pattern, which stand checks explicitly do not use (per test-plan §2 Test levels observed, Font-dependent tests).

## Contract bindings
- tests ↔ obs §3: agent-run events are harness metadata, not an escher-telemetry sink. If the fresh-process check routes through `agent-run.sh`, its events keep the declared shapes with no content-named key (per test-plan §3 Agent-run contract, Events; §4 What unit tests cover, Agent-run contract, where `logs` events carry no scrub-set key).
- tests ↔ obs stand log format: escher binaries log to stderr only, and stdout is silent (`telemetry_stdout_silent`) (per test-plan §3 Stand log format). If a child process carries its id list back over stdout, that channel must not conflict with the stdout-silent invariant. The ids carry author content, so they must never become log fields.
- tests ↔ CI-scripts leg: any change to `agent-run.sh` is pinned by `test_agent_run.py` in the `ci-scripts` leg, which ran 64 tests at the last measure (per test-plan §4 What unit tests cover, Agent-run contract / CI workflows and leg script).
