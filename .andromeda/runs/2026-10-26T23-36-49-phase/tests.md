# tests extract

## Relevance
relevant — two of the chunk's three targets are standing tests (an escher-driver unit test in `packages/escher-driver/src/mcp_tests.rs` and the blitz-tests stand check `stand_requirement_sweep`), and the third (`lint.rs::findings`) is guarded by unit tests, `stand_lint` and the escher-driver coverage floor; the complexity reading itself is no test-plan gate.

## Constraints
- The local pre-push gate is `bash .github/scripts/ci-leg.sh fast` (fmt → clippy → test → ci-scripts, stopping at the first red), and each linux leg is run through `ci-leg.sh` so it is host-reproducible; every cargo leg passes `--locked` (per test-plan §9 CI Integration → Pipeline facts, Local pre-push gate and Legs).
- `cargo test --workspace --locked` and `cargo test -p blitz-tests --locked` build the same test file against different engine features (`tracing` and `writing-mode` on in the workspace build only), so a green per-package run is not the workspace leg's green — the two touched tests and `stand_lint` must be read green under both builds (per test-plan §9 CI Integration → Engine features by runner).
- `stand_requirement_sweep` is a `stand_*.rs` file, so it sits inside the `stand-repeat` leg's zero-failure budget (three rounds, no retry); the refactored test must hold that budget (per test-plan §10 Quality Gates & Coverage Targets → Flakiness budget; detail `.andromeda/test-plan-detail/quality-gates-coverage-targets.md` gate-flakiness).
- `packages/escher-driver` holds a 97 % per-crate line floor read by `coverage_floor.py` at the end of the `coverage` leg; factoring `lint.rs::findings` into helpers changes the crate's counted lines, and a `#[path]` test-child file such as `mcp_tests.rs` is no record of the per-crate reading, so moving test code moves no coverage either way (per test-plan §10 Quality Gates & Coverage Targets → Coverage floors; detail gate-coverage-floor).
- The `every_0_2_0_requirement_names_its_witness_inside_stand_repeat` test's assertion set is stated: the nine `WITNESSES_020` rows v020-01 to v020-09 in order, each named test found as `fn {test}(` in its file, every non-`Unit` blitz-tests witness a `stand_*` file or one of `STAND_REPEAT_NAMED` (10), every `examples/seven_guis/tests/` witness one of `STAND_REPEAT_SEVEN_GUIS` (8), and `.github/scripts/ci-leg.sh`, read through `include_str!`, holding the `stand_*.rs` glob and `--test {name}` for all 18 — a factoring keeps every one of these assertions (per test-plan §1 Test Scope Summary → tests/blitz-tests; detail `.andromeda/test-plan-detail/test-scope-summary.md` scope-entities).
- MCP's unit tests pin the listing as the twelve verbs of the table, `snapshot`'s tool taking an optional integer `part` and naming its two counts — the rows `the_listing_is_the_twelve_verbs_of_the_table` must still assert after its factoring (per test-plan §4 Unit Test Strategy → escher-driver; detail scope-entities, escher-driver's `mcp_tests.rs` rows).
- blitz-tests keeps one target per file, pinned by `BlitzTestsTargetsTest`; the sweep's file and target name stay as they are, and a new helper lives in the file or a shared non-target module, never a new target (per test-plan §2 Test Strategy → Test directory + naming conventions, and §4 Unit Test Strategy → blitz-tests targets).

## Patterns to follow
- Table-driven assertions that carry a row index only: escher-driver's `command.rs` assertions over a call name the row, so a failing log prints no argument value — the shape a table walk in `mcp_tests.rs` or the sweep should take (per test-plan §4 Unit Test Strategy → escher-driver).
- Shared stand tables are stated expectation in `tests/common/mod.rs` and `tests/session_common/mod.rs` — modules with no test and no target, which a check reads through `mod common;` / `mod session_common;`; a table or helper only one check reads stays per-file (per test-plan §3 Test Harness Contract → Crate-local test helpers, blitz-tests (stand checks) and blitz-tests (fixtures)).
- Unit tests moved out of line sit in `#[cfg(test)]` `#[path]` child files with their test paths unchanged — `mcp_tests.rs` is one; a helper added there keeps the `mcp::tests` path (per test-plan §4 Unit Test Strategy → Conventions, Test file location).
- `Session::lint` is read by integration checks, not unit tests (the crate cannot build a held instance), so `lint.rs::findings`' unchanged output is witnessed by `stand_lint` in both layout modes and by lint.rs's inline unit tests (per test-plan §1 Test Scope Summary → escher-driver, and §5 Integration Test Strategy → Session ↔ held instance).
- Layout-dependent checks run `for incremental in [false, true]` / in both layout modes; the sweep and `stand_lint` already do, and a factoring keeps that loop (per test-plan §2 Test Strategy → Integration tests (tests/blitz-tests) and Differential oracle).

## Anti-patterns to avoid
- Reading a per-package green (`cargo test -p escher-driver` / `-p blitz-tests`) as the workspace leg's green (per test-plan §9 CI Integration → Engine features by runner).
- Turning a stated table into a second derivation of what it checks: the stand tables are stated expectation, never a second role or name mapping — a table walk must not compute its expected rows from `VERBS` or `ci-leg.sh` in a way that makes the test unable to fail (per test-plan §3 Test Harness Contract → Crate-local test helpers, blitz-tests (stand checks)).
- Reading an empty run as a pass: `agent-run.sh run {name}` fails a run with no parsed test line (per test-plan §3 Test Harness Contract → Agent-run contract, `run {selection}`).

## Contract bindings
- tests ↔ CI: `stand_requirement_sweep` reads `.github/scripts/ci-leg.sh` through `include_str!` and asserts its `stand-repeat` `--test` list (10 named blitz-tests targets, 8 seven_guis process checks); the chunk changes neither side (per test-plan §1 Test Scope Summary → tests/blitz-tests, and §9 CI Integration → Legs).
- tests ↔ CI scripts: `BlitzTestsTargetsTest` (`.github/scripts/test_blitz_tests_targets.py`, in the `ci-scripts` fast leg) holds the blitz-tests manifest the sweep's target sits under (per test-plan §4 Unit Test Strategy → blitz-tests targets).
- tests ↔ coverage gate: the `coverage` leg's `coverage_floor.py` binds escher-driver's 97 % floor to the refactored `lint.rs` (per test-plan §10 Quality Gates & Coverage Targets → Coverage floors).
- The code audit's complexity reading (rust-code-analysis 0.0.25, cognitive `> 15`) has no home in the test plan; whether it is a test-plan gate at all is research's question.
