## Relevance
relevant — the chunk is the keyboard harness for the tier-0 targets SC 2.1.1 and 2.4.3, which a11y-plan §3 (Keyboard test harness) points at §5 for.

## Constraints
- The a11y target is tier 0, SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary). This chunk serves 2.1.1 (Keyboard) and 2.4.3 (Focus order). It touches no colour, so 1.4.3 stays with §6 and its route owner.
- The focus order the harness asserts is the engine's. The plan records two things: the focusability rule in `packages/blitz-dom/src/node/element.rs`, and Tab / Shift+Tab moving focus to the next or previous focusable node through `focus_next_node` / `focus_prev_node`, with focus events dispatched (per a11y-plan §5 Focus order per layout). Whether the code at HEAD still matches the cited lines is research's question.
- a11y-plan §5 Focus order per layout records that disabled-ness is keyed two ways. The element state and the pointer click target follow the attribute's presence. Focusability follows its value parsed as a bool. So a bare `disabled` and `disabled="false"` both stay focusable while the snapshot reads them not enabled. This is folded defect (1). A fix changes `is_focussable` for every document, so it is a P4 fork. Until the founder rules, the harness records the reading and asserts no change to it.
- a11y-plan §5 Focus restoration records that a pointer click on a plain `button` leaves no element focused. After such a click no snapshot node reads `focused` and the tree's focus carries no author id. It also records that whether a click should focus the button is owned by a route entry, which is this one. Changing it is a pointer default action for every document (a fork). Until the founder rules, a check keeps the recorded reading.
- a11y-plan §5 Per-surface keyboard shortcuts records that the CRUD person rows are `option`s of a `listbox`, are not focusable, and that no keyboard reaches them. The CRUD forward focus sequence is pinned through `focus_next_node` in `stand_accessibility_ids` (per a11y-plan §8 Error recovery). Any `tabindex` answer moves that pinned sequence, so the pin has to be restated in the same change.
- a11y-plan §5 Keyboard handling records two kinds of key handling. Keys on text inputs: arrows, Home/End, Delete/Backspace, Enter as newline or submit. Keys on a focused, non-disabled range input: arrows and Home/End. It records no Enter or Space activation for a button, a checkbox or a select. Which activation keys the engine handles is research's question (`packages/blitz-dom/src/events/keyboard.rs`). On macOS, Backspace is left to the Apple standard keybindings (per a11y-plan §5 Keyboard handling).
- a11y-plan §5 Script and framework exposure records that a framework-written `inert: false` is removed by the bridge's 28-name `is_bool_attr`, so it no longer makes content inert. No check of ours reads it yet.

## Patterns to follow
- The existing stand key-press focus check drives `Key::Tab` and Shift+Tab through the harness's `press` / `press_with`, in both layout modes. At each step, exactly the focused control's snapshot node reads `focused` and that node is the accessibility tree's focus (per a11y-plan §5 Test harness pattern; per a11y-plan §3 Keyboard test harness, at `tests/blitz-tests/tests/stand_snapshot_state.rs:339-375`).
- Focus is read three ways that must agree: the stable id, the snapshot's `focused`, and the tree focus carrying `author_id`. The snapshot takes the focused node from the tree that `accessibility_tree` returns (per a11y-plan §7 Accessibility tree output). The harness's focused-node query is in `packages/blitz-test-harness/src/inspect.rs` (per a11y-plan §3 Focus management test harness).
- A keyboard check states its rows as a table with its row count asserted and runs `for incremental in [false, true]`, like `range_input_interaction`'s keys and clicks tables (per a11y-plan §5 Test harness pattern).
- Stand expectations are stated once, in the shared module `tests/blitz-tests/tests/common/mod.rs`: `controls`, `INPUT_NAMES` and `rendered`. That is stated expectation, never a second mapping (per a11y-plan §7 Accessibility tree output). The per-task forward sequence is already stated in `stand_accessibility_ids` (per a11y-plan §8 Error recovery).

## Anti-patterns to avoid
- Never compute the expected Tab order or roles from the engine's own readers inside the check. A second role, name or focus mapping is banned; the sequence is a stated table (per a11y-plan §7 Accessibility tree output).
- Never read `has_changes()` on a freshly booted harness document as "this step changed something" without draining first. The boot leaves the changed set non-empty, and settle neither reads nor drains it (per a11y-plan §2 Accessibility tree lifecycle).
- Never assert that a control whose snapshot `enabled` is `Some(false)` is skipped by Tab. Focusability reads the parsed value, not the presence (per a11y-plan §5 Focus order per layout).

## Contract bindings
- a11y ↔ tests (CI): the `a11y` leg runs exactly `accessibility_hidden`, `accessibility_roles` and `focusability_updates` (per a11y-plan §9 CI Integration). A new stand keyboard file runs only in the workspace `test` leg unless the leg's list is widened. Either way, the blitz-tests target pin (`.github/scripts/test_blitz_tests_targets.py`) moves with the file.
- a11y ↔ driver/tests: the driver-run Tab / Shift+Tab check (`stand_act_keys`) and the restated `stand_act_obstructed` focus reading read the same snapshot `focused` and tree focus (per a11y-plan §5 Focus restoration; per a11y-plan §7 Accessibility tree output). A focus-behaviour change moves both.
- a11y ↔ layouts: the per-task Tab sequence is the layouts' focus-management surface (`.andromeda/layout-templates.md`). A CRUD row `tabindex` answer restates it there and in `stand_accessibility_ids` (per a11y-plan §5 Per-surface keyboard shortcuts).

## Acceptance criteria contributions
- (a11y) On each of the four lean tasks, in both layout modes, the forward Tab sequence equals the stated sequence and wraps around, and Shift+Tab walks it in reverse. At every step the stable id, the snapshot's single `focused` node and the tree focus's `author_id` name the same control (per a11y-plan §5 Test harness pattern).
- (a11y) Enter and Space on each focused stand control are recorded against what the engine's keyboard default actions do: activated, toggled or chosen, or no effect. Each row is stated in a table with its count asserted (per a11y-plan §5 Keyboard handling).
- (a11y) A standing check calls `Harness::apple_keybinding` on the focused element on every OS, not only on the macOS CI leg (per a11y-plan §5 Keyboard handling).
- (a11y) Content rendered under a Dioxus `inert: false` is reached by Tab (per a11y-plan §5 Script and framework exposure).
