# arch extract

## Relevance
relevant — the chunk is test code in `tests/blitz-tests` over the `Harness`, the stand boot and the snapshot and accessibility readers, and each of its forks (`is_focussable`, the plain-button click, `Node::absolute_position`, an engine listbox keyboard model) would be an engine change for every document that this plan records.

## Constraints
- Each new check is one integration-test file that covers one behaviour and is its own test target directly under `tests/blitz-tests/tests/`. It opens with a `//!` doc that names the behaviour and any bug it guards. Its scenarios run in both layout modes, `for incremental in [false, true]`. It first asserts that the fixture produces the condition under test. Shared tables and helpers go only in `tests/blitz-tests/tests/common/mod.rs`, or in `tests/blitz-tests/tests/session_common/mod.rs` for a check that holds a `Session`. Both are modules in a subdirectory and are not test targets (per architecture §Conventions → Tests).
- blitz-tests sets no `autotests`, and its manifest holds exactly one `[[test]]` table, upstream's `tests/all.rs` with `test = false`. `test_blitz_tests_targets.py` (`BlitzTestsTargetsTest`) pins this, and the `ci-scripts` leg runs it. Research should check whether a new test file changes what that pin reads; the scope's "target pin moved with it" is an inference (per architecture §Standard Contracts → CI contracts).
- The focus read-back must use the readers the bridge contract names. The snapshot's `focused` is the `TreeUpdate`'s `focus`, never `get_focussed_node_id`, which falls back to the root element. The stable id comes from `element_id(s)` and is carried on the accessibility node as `author_id`. No snapshot field holds a `NodeId` (per architecture §Standard Contracts → Dioxus DOM bridge).
- Keyboard events target the focused node and fall back to the root. A focus change dispatches `blur`, `focusout`, `focus` and `focusin`. Each default-action event runs its handlers and then its default action unless it is cancelled. Activation-key readings are measured against this dispatch order (per architecture §Standard Contracts → Events; §Cross-cutting Patterns → Event processing).
- `disabled` is read two ways. Focusability parses it as a boolean, so `disabled="false"` and a bare `disabled` stay focusable. The element state, `:disabled` and the click target key on the attribute's presence (`packages/blitz-dom/src/node/element.rs`). The plan records this split as it stands. Unifying it is an engine change for every document (per architecture §Established Decisions → [DOM semantics]).
- Every direct engine change for every document carries three records: the founder's ratification, a flag that it is upstreamable against upstream `main` at 434e0661, and its merge surface, with a route owner. The plan counts five today. A click that focuses a `button` (`events/pointer.rs`), an `is_focussable` fix (`node/element.rs`), a `Node::absolute_position` fix (`node/node.rs`) and an engine listbox keyboard model would each join that list. None lands without that ruling (per architecture §Established Decisions → [Scrolling and input]).
- `Node::absolute_position` is left as it reads, by the operator's answer of 2026-10-10: a box that is itself scrolled reads less its own scroll offset. The harness's `layout_rect`, `layout_rect_of` and `center_of` are built on it, and `scrolled_box_absolute_position` pins the reading. A fix rewrites that pin and does not delete it (per architecture §Standard Contracts → Scrolling, selection, tree).

## Patterns to follow
- Boot each of the four lean tasks with `seven_guis::stand::boot(LeanTask, stand::options(incremental))`. Iterate `LeanTask::ALL`. Each boot uses a fresh `VirtualDom`, the pinned 800×600 viewport at scale 1.0, Light colour scheme, the bundled DejaVu font and the offline `DummyNetProvider` (per architecture §Standard Contracts → Headless stand).
- Synthesize keys through the harness's existing input surface:
  - `press_with` with the re-exported `Key` and `Modifiers`, so the test crate takes no `keyboard_types` dependency.
  - `apple_keybinding(command)`, which dispatches `UiEvent::AppleStandardKeybinding` to the focused element and pumps.

  Input helpers do not settle. Call `Harness::settle` explicitly where a step must be quiet. A new helper extends the harness's export list in this contract (per architecture §Standard Contracts → Test harness).
- Read per-task tables, such as `controls` and `INPUT_NAMES`, from the shared stand module `tests/blitz-tests/tests/common/mod.rs` by `mod common;` and do not restate them. The existing focus checks are the models for the step-and-read shape: the Tab and Shift+Tab check in `stand_snapshot_state`, the forward sequence in `stand_accessibility_ids`, and the driver focus checks in `stand_act_keys` (per architecture §Existing Scopes → blitz-tests).
- A focus move marks the changed set through `snapshot_node_and` when `FOCUS` is touched. Hover and layout mark nothing. A per-step diff or `has_changes` reading after a Tab follows from this (per architecture §Cross-cutting Patterns → Invalidation and state integrity).
- A stand-markup answer for the listbox, such as a roving `tabindex` or arrow keys in the CRUD's own handler, changes the app through the Dioxus bridge. A falsy `inert` reaches the DOM through the bridge's 28-name `is_bool_attr`, which clears `inert: false` (per architecture §Standard Contracts → Dioxus DOM bridge).

## Anti-patterns to avoid
- Do not read focus through `get_focussed_node_id`. It falls back to the root element and would make "nothing focused" read as a focused root (per architecture §Standard Contracts → Dioxus DOM bridge).
- Do not land an engine edit that changes behaviour for every document without the founder's recorded ratification and its upstreamable flag and merge surface. The engine files involved are `node/element.rs`, `events/pointer.rs`, `events/keyboard.rs` and `node/node.rs`. Without the ruling the chunk measures and records (per architecture §Established Decisions → [Scrolling and input]).
- Add no crate, env var, listener or carrier beyond what is registered. This harness is test code over existing readers, and any new resource is a registration first (per architecture §Occupied Resources → Names; §Occupied Resources → Network ports and listeners).
