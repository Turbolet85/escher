# tests extract

## Relevance
relevant — the chunk is test code: a stand keyboard harness landing as blitz-tests integration checks over the existing `Harness` input and inspection helpers, plus standing checks for the folded CARRY freight (test tier `0`, per test-plan §1).

## Constraints
- Each behaviour is one test-target file under `tests/blitz-tests/tests/`, picked up by Cargo's autotests. test-plan §4 (blitz-tests targets) requires `BlitzTestsTargetsTest` to hold: `autotests` not false, and exactly one `[[test]]` table (`all`, `test = false`). So a new file needs no manifest table, and the pin needs no change. The scope's "target pin moved with it" reads as "the pin stays green unchanged" (per test-plan §4 What unit tests cover → blitz-tests targets).
- A stand check boots each lean task fresh through `seven_guis::stand::boot(LeanTask, HarnessOptions)` (or `boot_timer` for the Timer) with `stand::options(incremental)` as the pinned options (per test-plan §3 blitz-test-harness → Construction). It reads shared tables and helpers (`controls`, `rendered`, `boot`, `by_id`, `tree_node`, …) from `tests/common/mod.rs` through `mod common;` and keeps no copy of them in the file (per test-plan §3 Crate-local test helpers → blitz-tests (stand checks)).
- Stand checks have no font skip path. They assert unconditionally under the bundled DejaVu Sans with system fonts off (per test-plan §2 Font-dependent tests).
- Keys go through the harness input helpers: `press`, `press_with` and `apple_keybinding`, each of which pumps after dispatch. test-plan §3 (Input helpers) says `key_event` fills `text` only for pressed character keys, using `Code::Unidentified` and `Location::Standard`. So whether Space reaches an activation default action through `press` is for research to read from the code. Focus is read back with the `focused` inspection helper (per test-plan §3 blitz-test-harness → Input helpers / Inspection helpers).
- For a box that is itself scrolled, `layout_rect`, `layout_rect_of` and `center_of` are built on the unfixed `Node::absolute_position` and read shifted by the box's own scroll offset. `get_client_bounding_rect` and the snapshot's `bounds` read where the box stands. So a check on an activation key on a scrolled box (CARRY 7) must not take its expected point from those three helpers (per test-plan §3 blitz-test-harness → Inspection helpers).
- The workspace build and the `-p blitz-tests` package build compile blitz-dom with different features (`tracing` on in the workspace graph). test-plan §9 (Engine features by runner) requires a new check to be green under both runners, every test `for incremental in [false, true]` (per test-plan §9 Pipeline facts → Engine features by runner).
- `Harness::apple_keybinding` today has a standing witness only on the macOS CI leg (`stand_act_keys`' `press backspace`, and `stand_act_filled`'s clearing), where the editor's own Backspace arm is compiled out. On Linux and Windows no standing check calls it (per test-plan §3 blitz-test-harness → Input helpers). A check that calls it directly runs on the windows and macos matrix jobs, which `needs` the fast four (per test-plan §9 Pipeline facts → Fast/slow split).

## Patterns to follow
- The focus read-back shape already pinned. `stand_snapshot_state` asserts that exactly the focused control reads `focused` after a click, a Tab press and Shift+Tab, with every node's readings equal to its accessibility node's. `stand_act_keys` asserts that the one focused node is the accessibility tree's focus. `stand_diff` asserts that a Tab and a Shift+Tab name exactly the controls whose `focused` reading moved, each step held against the file's own reading and equal across the two layout modes (per test-plan §1 Coverage scope → tests/blitz-tests).
- Measured-and-pinned for a defect not fixed. `scrolled_box_absolute_position` pins the shifted reading and is "red by design when the reader is fixed — rewritten then, not deleted". The same shape fits CARRY 1 (bare or `"false"` `disabled` still focusable), CARRY 4 (a click on a plain `button` leaves no focus) and CARRY 8 (no keyboard path to a listbox option) wherever the P4 fork is not taken (per test-plan §1 Coverage scope → tests/blitz-tests; test-plan §3 blitz-test-harness → Inspection helpers).
- A stated row table with its row count asserted. Examples: `accessibility_states` (9 · 10 · 11 rows) and `range_input_interaction`'s 7-row key table, one row per key and target. Each lean task's forward Tab sequence and its Shift+Tab reverse, wrap-around included, fit this shape (per test-plan §1 Coverage scope → tests/blitz-tests).
- `dioxus_falsy_boolean_attrs` reads a falsy Dioxus boolean attribute on both attribute paths and in both layout modes. It names 27 attributes and does not read `inert`. The CARRY 9 check, "content under `inert: false` is reached by Tab", follows that file's shape (per test-plan §1 Coverage scope → tests/blitz-tests).
- A control proves that a check can fail. Examples: `a_textarea_reads_back_typed_text` read red with its arm deleted and green restored, and `BlitzTestsTargetsTest` read FAILED on scratch manifests. The scope says no mutation runs (inputs#I1). Where a control is wanted anyway, take one that needs no mutation (per test-plan §1 Coverage scope → tests/blitz-tests; test-plan §4 What unit tests cover → blitz-tests targets).

## Anti-patterns to avoid
- Do not use `dispatch_recorded` for a stand activation key. It drives events against the underlying `BaseDocument` and bypasses Dioxus VirtualDom forwarding, so the app's own handlers never run. Use the pumping input helpers (per test-plan §5 Boundaries covered → Harness ↔ event pipeline).
- No conditional assertion that passes without asserting, as the two text-input tests do inside an `if` on measured layout. A focus or activation reading is asserted unconditionally (per test-plan §4 What unit tests cover → Conditional assertions).
- No `eprintln!` skip when a stand check finds no font. Stand checks have no skip path (per test-plan §2 Font-dependent tests).

## Contract bindings
- tests ↔ agent-run 5-command contract. `run stand` passes one `--test {stem}` per `tests/blitz-tests/tests/stand_*.rs` that exists. A `stand_`-prefixed harness file is picked up with no script change, and its `ok` events change the recorded `run stand` count. A file without the prefix is run only by `run all` or `run {name}` (per test-plan §3 Agent-run contract → `run {selection}` / Proof).
- tests ↔ a11y CI gate. The `a11y` leg runs exactly three files: `accessibility_hidden`, `accessibility_roles` and `focusability_updates`. Whether the keyboard harness joins it is a decision that a11y-plan §5 (the harness pattern) and `ci-leg.sh` / `test_ci_workflows.py` share. Until then it runs on the workspace `test` leg alone, as `accessibility_states` and `stand_contrast` do (per test-plan §9 Pipeline facts → Legs; test-plan §1 Coverage scope → tests/blitz-tests).
- tests ↔ driver session (only if a step goes through the driver). `stand_act_keys` runs Tab and Shift+Tab through `Session::run` with the `press(key, shift)` builder of `tests/session_common/mod.rs`. A driver-run step reuses that module through `mod session_common;` rather than restating the builder (per test-plan §3 Crate-local test helpers → blitz-tests (session checks)).
