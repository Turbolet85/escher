# security extract

## Relevance
partial — the harness is in-process test code adding no carrier, input class or listener; the chunk touches security surface only through the markup-attribute rows its folded focus defects sit on (`disabled`, falsy `inert`, range keys, listbox option states) and through any engine fork that would change them for every document, remote pages included.

## Constraints
- security-plan §Input Validation (Markup attributes · `disabled` row) records two readings that differ: presence alone sets the `DISABLED` state and blocks the pointer and range-key default actions, while focusability uses the boolean parse, so a bare or `"false"` `disabled` reads not enabled yet stays focusable. The harness must assert against that row as written. A fix to defect (1) changes this row for every document, remote HTML included. It is an engine change that needs the founder's ruling, and the row is amended at the wrap. Without a ruling the harness measures the split and records it, with no fix.
- security-plan §Input Validation (Markup attributes · `disabled` row) gates default actions on `disabled` *presence*. Any activation-key default action the chunk reads or adds (Enter or Space on a button, a checkbox, a select or an option) must hold the same gate. Whether `packages/blitz-dom/src/events/keyboard.rs` already gates Enter and Space on presence is a question for research.
- security-plan §Input Validation (Markup attributes · `input type="range"` row) requires the Timer slider's keys (arrows, `Home`, `End`) to act only on a focused range input with no `disabled` attribute, every other key doing nothing. When Tab lands on the slider, the harness's activation-key steps must not assume any other key moves it.
- security-plan §Input Validation (Dioxus mutations · Boolean attributes with a falsy value row) requires that a falsy value of one of the 28 `is_bool_attr` names, `inert` among them, be cleared, not written. That is the behaviour the folded `inert: false` check reads: content under it stays focusable. Whether the bridge does this today is research's question, since the plan states no check of ours reads it.
- security-plan §Input Validation (Markup attributes · `aria-selected` · `aria-pressed` · `aria-invalid` row) requires the states to be read by a closed-set match and written out as closed enums and booleans, never as the attribute's text. If the listbox-option fork is answered in stand markup (roving `tabindex`, `aria-selected` on the CRUD rows), the attributes must stay in that closed set. An engine listbox keyboard model would instead be a new every-document input path, needing its own row and the founder's ruling.
- security-plan §Error Handling (Graceful degradation) requires a stale node id to resolve to `None` through `get`, never by indexing. A per-step focus read-back must resolve the focused node through `get` or `get_node`, as security-plan §Input Validation (Markup attributes · `id` row) requires of every id reader ("never by index"), and no added path may panic on what a document supplies.
- security-plan §Dependency Security requires a new crate to be reviewed by hand, with the audit leg reading `advisories ok` and `deny.toml` unchanged. The harness should need no dependency beyond what blitz-tests and blitz-test-harness already take.

## Patterns to follow
- security-plan §Input Validation (Markup attributes · `input type="range"` row): an every-document default-action change is recorded as an engine change and a boundary widening, with the founder's ruling cited. The added engine lines are censused at 0 for print, log site, `unwrap`, `expect`, panic and env read, and the value leaves only through already ratified carriers. Any fork this chunk takes (`is_focussable`, click-focus on `button`, `Node::absolute_position`) should follow the same shape.
- security-plan §Input Validation (Markup attributes · `id` row): an in-process reader of the stable id or `author_id`, as the snapshot and `unkeyed_actionable` are, adds no crossing. It writes to no log, event, socket or file, and holds no `NodeId` outside the process. The harness's three per-step readings (stable id, the snapshot's `focused`, the accessibility focus `author_id`) stay in process the same way.
- security-plan §Logging & Monitoring (escher's own sink): engine call sites stay behind the `tracing` feature, and a record from an outside target is dropped whole. Test-side diagnostics are `println!` and `eprintln!` in tests only, never a new engine log field.

## Anti-patterns to avoid
- Do not add a field holding an id, an accessible name or a value to any log or span. security-plan §Logging & Monitoring requires that the sink-installing binaries' stderr carry 0 id needles and 0 name needles, and security-plan §Input Validation (Driver command schema row) lists exactly what the `command` and `tool_call` spans may field.
- Do not index the slab with an id that may be stale (security-plan §Error Handling, Graceful degradation and Panic paths).
- Do not land an every-document change to focusability, a pointer default action or keyboard default actions as a silent engine edit. security-plan §Input Validation (`disabled` row and `input type="range"` row) records each such change with the founder's ruling and amends its row.

## Contract bindings
- security ↔ a11y: the `disabled` row in security-plan §Input Validation (presence versus the focusability parse) is the security-side record of the focus defect that a11y-plan §5 owns. Whatever the harness measures, or a fork changes, moves both records together.
- security ↔ obs: no new log field, and the sink's id and name needle census in security-plan §Logging & Monitoring is unchanged. The harness adds no span and no field. If a driver-run keyboard check is added through the `escher-session` host or the `mcp` role, it stays under the existing `host_log` and `mcp_log` censuses.
- security ↔ tests: any engine fork's added lines take the range row's zero-print, zero-log-site, zero-panic census (security-plan §Input Validation, `input type="range"` row) as a gate reading. The blitz-tests target pin moves with the new file (tests domain).

## Acceptance criteria contributions
- The harness asserts the `disabled` split as security-plan §Input Validation (`disabled` row) states it: a bare and a `"false"` `disabled` read `enabled: Some(false)`. Without a ruled fix, the harness records which of them Tab still reaches. With one, the row is amended to the measured truth (per security-plan §Input Validation).
- No Enter, Space, arrow, `Home` or `End` step changes a control that carries a `disabled` attribute, in both layout modes (per security-plan §Input Validation, `disabled` and `input type="range"` rows).
- Content under a framework-written `inert: false` is reached by Tab, matching the falsy-clear rule (per security-plan §Input Validation, Dioxus mutations · Boolean attributes with a falsy value row).
- `Cargo.lock` gains no package and the audit leg reads `advisories ok` with `deny.toml` unchanged. Any engine line the chunk adds holds no print, log site, `unwrap`, `expect` or panic on document-supplied input, censused at 0 (per security-plan §Dependency Security and security-plan §Input Validation, `input type="range"` row).
