## Relevance
partial — the chunk adds no span, metric or event (scope §Boundaries, "Not Driver command spans"), but its executor holds ids and typed text inside a crate obs-plan requires to stay silent, and its `type` verb is the first thing that can reach the one reading obs-plan §8 still records as not measured (typed text in a sink-installing host's log — scope CARRY 4, owed here only under the socket answer of the P4 fork).

## Constraints
- obs-plan §1 Obs Scope Summary sets obs tier 0: instrumentation depth for this chunk is none added — no new telemetry dependency, backend or exporter rides in with the executor.
- obs-plan §3 Observability Harness Contract → Logging stack requires the session library `packages/escher-driver` to stay without a `tracing` dependency, a subscriber, an env read and any print or log — its settled step and its command and refusal schema included. The executor, the time step handed to a session and any id-resolution code are bound by the same rule; whether the crate still reads so once the executor lands is research's and the implement gate's question, not attested here.
- obs-plan §3 Observability Harness Contract → Logging stack requires an in-process headless boot (the stand's `boot` family and every `stand_*` check with its shared modules) to install no escher sink, and places a boot made by the `escher-session` binary under that binary's sink. So a command run in process meets no sink at all, and a command that reaches the host binary's instance runs under one — the P4 fork decides which obs surface this chunk's actions touch.
- obs-plan §4 Span / Trace Coverage assigns the one span per driver command to the route entry "Driver command spans" and requires that no `Command`, `Call` or `ArgValue` be fielded with `Debug` and no argument be fielded by its schema name — either would print an id and typed text. The only value domain §4 names as safe for a future field is the eight fixed cause names.
- obs-plan §8 PII Scrubbing & Compliance → Scrubbing requires every event under an `escher_` target to pass the content-named redaction set and every target outside the two prefix sets to be dropped whole. An event this chunk emitted under `escher_driver` would print any field outside that set — per §4, of the schema's argument names only `text` is in it, so an `id` or `key` field would print unredacted. The chunk therefore adds no user-content log field.
- obs-plan §8 PII Scrubbing & Compliance → Values logged as-is records typed text as NOT measured, because no command could type into a held instance, and records that the chained std panic hook prints a raw panic message to stderr past the scrub. Two requirements follow for this chunk: the typed-text reading becomes owed the moment a `type` command reaches the `escher-session` binary's own instance, and no panic or assertion message on an executor path that can run inside that binary may hold an id, a name, a control value or typed text.
- obs-plan §2 Telemetry Strategy → Telemetry mechanism requires the engine `tracing` features to stay off in both binaries of the seven_guis package. The manifest change scope CARRY 5 decides (a `dioxus-native-dom` feature named in `escher-driver`, reaching `seven_guis` through `seven_guis → escher-driver`) must turn on no `tracing` feature on the way; whether the feature it names forwards one is research's question.

## Patterns to follow
- The sink-reading check shape of obs-plan §3 Observability Harness Contract → Logging stack (`host_log`): spawn the real binary at `RUST_LOG=trace`, drain both streams from the spawn on, read them into assertions only, and on failure print a kind and a count — never what the host wrote. A typed-sentinel proof, if owed here, takes this shape and no other.
- The by-level reading of obs-plan §8 PII Scrubbing & Compliance → Values logged as-is: stderr line counts and fixed-needle counts per `RUST_LOG` setting, stdout bytes read beside them, recorded as evidence in the chunk's own `evidence/` — the form the typed-text reading joins.
- The host binary's own stderr of obs-plan §6 Log Coverage → Logged events (examples): fixed-string `eprintln!` lines holding no path, label, id or value, and nothing on stdout on any path. Any new host-side line for the time step (a session with no step, a step that fails) keeps that form.
- The refusal-cause names of obs-plan §4 Span / Trace Coverage as fixed class words holding nothing a call supplied — where this chunk needs to name an outcome in a test name, an assertion message or a returned error, it names the class, not the call.
- The session state directory of obs-plan §9 CI Integration → Telemetry artifact handling: created by the host, holding the socket file alone while a session is up, with no log, event or screen content written into it, under `target/tmp/` in checks and uploaded by no CI leg. New checks that start a session follow it.

## Anti-patterns to avoid
- obs-plan §11 Obs Anti-Patterns reads no recorded intent and is not cited; the bans below are drawn from the sections named on each.
- Fielding a `Command`, `Call` or `ArgValue` with `Debug`, or an argument under its schema name, in any log, event or panic message (obs-plan §4 Span / Trace Coverage).
- Reading a zero from a child that installs no sink as proof about a host that does — a `RUST_LOG=trace` set on a re-run test binary is inert and says nothing of the `escher-session` binary (obs-plan §3 Observability Harness Contract → Logging stack).
- Adding a `tracing` dependency, a subscriber, an env read, a `println!` or a stdout write to the session library or the host binary to debug an action or a time step (obs-plan §3 Observability Harness Contract → Logging stack).

## Contract bindings
- obs ↔ tests: the typed-sentinel reading lives in a test — the `host_log` check and the shared module `examples/seven_guis/tests/common/mod.rs` (obs-plan §3 Observability Harness Contract → Logging stack) bind to test-plan §3 and its keyed contract `session-lifecycle`; the check's file, name and count are the tests extractor's, its stream-handling rules are obs's.
- obs ↔ security: obs-plan §8 PII Scrubbing & Compliance → Scrubbing binds to security-plan §Input Validation (the `id` row) — a diff carries ids, accessible names and a text control's value and leaves the process through the returned value only, so the sink is not one of its exits. If the P4 fork puts a command on the socket, what crosses is security's registration; obs's side is that nothing of it is logged at either end.
- obs ↔ route entry "Driver command spans": the span per driver command and the cause field's domain stay owed there (obs-plan §4 Span / Trace Coverage); this chunk supplies the operation that span will later cover and adds none of it.
- obs ↔ a11y: scope CARRY 5's feature decision is a11y's for its AccessKit reach; obs's one tie is the `tracing` feature staying off in both seven_guis binaries (obs-plan §2 Telemetry Strategy → Telemetry mechanism). No a11y violation-JSON binding is recorded in obs-plan.
- obs-plan §3 Bootstrap phases (keyed contract, `pii-scrubbing-wire`): recorded as discharged for escher's own sink on ids and accessible names; it says nothing of typed text, so the reading above is not covered by it.
