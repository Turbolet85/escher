# a11y extract

## Relevance
partial — the chunk adds no markup, style or UI surface, but it decides the `accessibility` feature for the session library (CARRY 5), and every action's result is a diff over the snapshot's a11y readings (role · name · `enabled` · `focused`), reached through focus-moving input.

## Constraints
- The a11y tier is 0 with target SC 2.1.1 · 1.4.3 · 2.4.3 (per a11y-plan §1 A11y Scope Summary, A11y tier). The chunk touches no markup, so the stand's focusability and focus order must read the same after it as before; an executor that changes either is out of this chunk's scope.
- The feature decision is this chunk's: a11y-plan §1 A11y Scope Summary (Dioxus crates) records that a crate gets `accessibility` only by naming it, that `escher-driver` names no `dioxus-native-dom` feature, and that "the entry that first reads the snapshot through a session decides the feature then". Naming it in `escher-driver` reaches the windowed stand binary's build through `seven_guis → escher-driver`; the plan must name where the feature is declared and state what the stand binary and the `escher-session` host build afterwards. Whether a platform adapter then enters either build is research's question.
- The snapshot, its text form, its diff and the actionable-key check all stand behind dioxus-native-dom's `accessibility` feature (per a11y-plan §2 A11y Strategy, Feature exposure) — an executor that returns a diff cannot be built without it.
- A harness settle neither reads nor drains the engine's changed set, and the set is non-empty on a freshly booted harness document (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle). The executor's before/after snapshots must not be taken from, or gated on, that set; if the executor drains it, that is a change to what a later refresh sees and is named in the plan. Whether the executor's step path touches the set is research's question.
- The diff is a reader of the snapshot model and of nothing else, the snapshot a consumer of the accessibility tree: the executor must define no role or name set of its own, must address an element by the same stable id the snapshot node and the node's AccessKit `author_id` carry, and must return a password or file input's value as the fixed mask only (per a11y-plan §7 Screen Reader Support, Accessibility tree output). The same section records the actionable-key rule and that three stand tasks are not yet keyed — an action on those reads a positional id; which tasks the chunk's checks drive is the plan's.
- Disabled-ness is keyed two ways — element state and pointer click target on the attribute's PRESENCE, focusability on its PARSED value (per a11y-plan §5 Keyboard Navigation, Focus order). An action on a control carrying `disabled` must report `enabled` by presence, the reading the driver's `disabled` cause is worded on; whether the executor's dispatch for a resolved node passes through the presence-keyed click-target check is research's question, and naming the cause is "Refusal detection", not this chunk.
- An action moves focus as the engine's input does: a checkbox or radio click focuses the control, a click on a non-interactive area clears focus, removing the focused node resets it (per a11y-plan §5 Keyboard Navigation, Focus restoration); Tab and Shift+Tab move to the next and previous focusable node (per a11y-plan §5 Keyboard Navigation, Focus order). `press` acts on whatever holds focus, so each step's diff must name exactly the controls whose `focused` reading moved. On macOS the text editor leaves Backspace to the Apple standard key bindings (per a11y-plan §5 Keyboard Navigation, Keyboard handling) — whether a headless `press backspace` or `type` deletes there is research's question (CARRY 2).

## Patterns to follow
- A by-node click exists in the engine: `synthetic_click_event` builds a primary click at a node's centre, and a label click runs its bound input's default click (per a11y-plan §5 Keyboard Navigation, Keyboard handling). Whether the executor dispatches through it is the plan's; AccessKit `ActionRequested` is recorded as an unhandled TODO and is no existing path for a driver action (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- Stand expectations are stated once — the tables `controls`, `INPUT_NAMES` and `rendered` in the stand checks' shared module (per a11y-plan §7 Screen Reader Support, Accessibility tree output). A driver check that compares ids, roles or names reads those tables rather than restating them.
- The focus proof shape on the stand: after a pointer click, a Tab press and Shift+Tab, exactly the focused control's snapshot node reads `focused` and it is the accessibility tree's focus, in both layout modes (per a11y-plan §5 Keyboard Navigation, Test harness pattern; harness queries per a11y-plan §3 A11y Assertion Harness Contract, Focus management test harness).
- The diff proof shape on the stand: a text change is reported on the element whose accessible name it changes, by that element's id and never as a text-run entry; an element hidden and shown by `hidden` leaves and returns with its descendants (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- The `a11y` CI leg runs three named test files and adds no stand assertion (per a11y-plan §9 CI Integration); a new `stand_*` driver check runs in the workspace test leg, and the a11y leg's list is unchanged unless the plan says otherwise.

## Anti-patterns to avoid
- A second role or name mapping in the driver, or a diff entry built from anything but the snapshot model (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- Reading `has_changes()` or the changed set as "this step changed something" — it is engine-touched, non-empty at boot, and not the diff (per a11y-plan §2 A11y Strategy, Accessibility tree lifecycle).
- Reading `enabled` from focusability or from the parsed value of `disabled` — a `disabled="false"` and a bare `disabled` both read not enabled while both stay focusable (per a11y-plan §5 Keyboard Navigation, Focus order).

## Contract bindings
- a11y §1 A11y Scope Summary (Dioxus crates) ↔ architecture §Occupied Resources / §Standard Contracts (Driver session): the feature named for `escher-driver` changes the build graph of `seven_guis`; the a11y plane's own row is re-stated at the wrap, and the windowed witness stays owed on "Stand a11y assertions".
- a11y §2 A11y Strategy (Accessibility tree lifecycle) ↔ architecture §Cross-cutting Patterns (Invalidation and state integrity): the changed set beside the diff, and what the executor leaves in the set after a step.
- a11y §7 Screen Reader Support (Accessibility tree output) ↔ security-plan §Input Validation (the `id` row): a diff carries ids, accessible names and a control's value — masked for password and file inputs — and the first command that returns it re-asks the crossing question.
- a11y §7 Screen Reader Support (Accessibility tree output) ↔ the driver's refusal schema (architecture §Standard Contracts, Driver session): the `disabled` cause is worded on the snapshot's presence reading; detection is "Refusal detection".
- a11y §5 Keyboard Navigation (Test harness pattern) and §9 CI Integration ↔ test-plan §3 / §4: driver stand checks run in both layout modes and land in the workspace test leg.

## Acceptance criteria contributions
- For every stand element a driver check drives, the id the driver accepts equals the snapshot node's id and the accessibility node's `author_id`, in both layout modes (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- After a driver `click` that moves focus and after `press` of Tab and of Shift+Tab, the returned diff names exactly the controls whose `focused` reading moved, and the one node reading `focused` is the accessibility tree's focus, in both layout modes (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- A driver action that makes a control gain or lose the `disabled` attribute returns that control as changed with `enabled` following the attribute's presence, and its role and name equal the snapshot node's (per a11y-plan §7 Screen Reader Support, Accessibility tree output).
- The plan names the crate that declares `accessibility` for the session path, and the built result is measured: whether the windowed stand binary and the `escher-session` host now compile AccessKit code, with the stand's Tab order and its controls' roles and names unchanged and `bash .github/scripts/ci-leg.sh a11y` green (per a11y-plan §1 A11y Scope Summary, Dioxus crates; a11y-plan §9 CI Integration).
