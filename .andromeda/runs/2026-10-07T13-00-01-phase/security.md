# security extract

## Relevance
relevant — the chunk makes the driver's command schema executable for the first time (an id and typed text reach a held instance, a diff of ids · names · values comes back), and its open fork decides whether that content stays in process or crosses the one registered listener.

## Constraints
- **Validate first, and a refused call changes nothing.** security-plan §Input Validation (the "Driver command schema (escher-driver)" row) requires every call to pass `validate` — closed five-verb table, five bounded argument kinds, one fixed refusal order, no `unwrap` / `expect` / `panic!` / `unreachable!` / index on anything a call supplies, no `Session` in its signature — before anything runs. The executor must take its input only as a validated `Command` and must add no path that acts before, or around, that check. Whether a `Command` can be built at HEAD without passing `validate` (public fields or constructors) is research's question.
- **A refusal holds nothing of the call.** security-plan §Error Handling (Error format, the escher-driver `Refusal` entry) requires the cause set to stay closed at eight with fixed `&'static str` name, meaning and remedy, and no `String` field in `Cause`, `Fault` or `Refusal`. Whatever the executor returns for an id it cannot resolve or a target that cannot take the action must be built from that closed set (`Refusal::new(cause)`) and carry no id, typed text, key or accessible name; a new cause or a new field is a plan amendment, not an executor detail.
- **Id resolution never panics and never indexes.** security-plan §Input Validation (the "Markup attributes · `id` (stable element id)" row) requires that a non-element, stale or detached node reads `None`, that no path panics, that readers of the id resolve through `BaseDocument::get_node` (never an index) and skip a node that does not resolve, and that the id carries no `NodeId`, `ElementId`, `ScopeId` or pointer. The executor is the first reader that goes the other way (caller-supplied id → live node): it must keep all four, including for an id of up to 1024 arbitrary bytes that names nothing, and for a node dropped between resolution and dispatch. Whether an id → node lookup already exists, and whether it is panic-free, is research's question.
- **The diff and the typed text have no ratified crossing.** security-plan §Input Validation (the "Driver session socket (escher-driver)" row) and §API Security (the "Local session socket (escher-driver)" row) require the wire to stay `hello` / `stop` only, a request line of at most 64 bytes, a reply of at most 128 bytes carrying a pid, the label and a count — no element id, accessible name, control value, snapshot text or diff. The `id` row of §Input Validation records the diff as "returned to its caller only" with no log, event, socket or file carrying it. Run in process, the chunk keeps both. Run across the socket, it is a boundary widening that must be ratified and registered before the code lands: the request bound cannot hold a 1024-byte id or 4096-byte text, the reply bound cannot hold a diff, and security-plan §Authentication & Authorization (the "Local IPC access (driver session socket)" row) records owner-only file modes as the only access control — no handshake, token or peer-credential check, and `start` does not check that the answering pid is the child it spawned. The answer is the operator's at P4; this extract states the cost of each side, not a lean. (security-plan §Threat Model Summary, the "local IPC — the driver session's socket" vector, names the same boundary; that section's application-level summary is marked not measured and nothing is taken from it.)
- **A masked value stays masked through an action.** security-plan §Input Validation (the "Markup attributes · password and file `input` value" row) requires a password's or file input's value to read as `MASKED_VALUE` in the snapshot, its text and any diff, with the typed text occurring in no id, parent, name or value of any diff entry. The executor's result must therefore be `Snapshot::diff` over two `DioxusDocument::snapshot` readings and nothing else — no second value reader, no echo of a `type` command's text in its result. security-plan §Data Protection (Local user data handled) adds that a file input's `value` attribute still holds a host path in the DOM, so a result built from the DOM instead of the snapshot would carry it.
- **No id, name or typed text reaches a log, a span field or a panic message.** security-plan §Logging & Monitoring (Log format and backends, the "escher's own sink" entry) records that an `escher_*` target prints every field except eleven redacted names — `id` and `name` are not among them, and a message is printed — and that the chained std panic hook prints the raw panic message to stderr. §Input Validation (the "Driver command schema (escher-driver)" row) records that `Command`, `Call` and `ArgValue` print the id and the typed text under `Debug` and that nothing in the crate prints, logs or fields them. The executor must keep the crate silent on those values: no `{:?}` of a command in a log, an `expect` message, an assertion in non-test code or a `SessionError` text.
- **No command waits, and time moves only when asked.** security-plan §API Security (the "Settle and loads in flight" row) requires that no driver command waits on a load, that a step which ran and did not go quiet is a result (`settled: false` with its busy class) and not a refusal, that the outcome names a class only — no URL, request, node, id, name or value — and that time on a held instance moves only by `advance`, 1 to 60000 ms a call, with settle reading no clock inside its 64-pass bound. The `advance` wiring and the acting verbs' return must keep each of those; a retry loop, a sleep or a wall-clock read in the executor breaks the row.

## Patterns to follow
- The in-process reader shape of security-plan §Input Validation (the `id` row): take ids from `element_ids()` / the snapshot, resolve each node through `BaseDocument::get_node`, skip what does not resolve, log nothing, hold no process-local id in what is returned.
- Typed edges, not strings: a refusal as `Refusal::new(cause)` / `Refusal::malformed(fault)` per security-plan §Error Handling (Error format), and a host error as a fixed message with no path, label, id or value in it and nothing on stdout, per security-plan §Input Validation (the "CLI arguments (escher-session)" row) — the `advance` step's host mapping lives in that binary and inherits the rule.
- Caller-supplied capability as a parameter: security-plan §Input Validation (the "Driver session state directory" row) keeps the state directory "a parameter, never an env read or a cwd-relative default", and security-plan §Secret Management (Environment values read) records that the escher-driver library and `escher-session` read no env var beyond `RUST_LOG`. The time step a session's caller supplies follows the same shape — handed in at start, no env var, no new argv unless the plan names it.
- Manifest changes per security-plan §Dependency Security (Pinning · Audit tool): the `dioxus-native-dom` feature CARRY 5 decides is named through `workspace = true`, `Cargo.lock` stays committed, every build stays `--locked`, and `bash .github/scripts/ci-leg.sh audit` re-reads the graph. Whether naming `accessibility` in `escher-driver` adds a crate to any build graph (AccessKit into the windowed stand binary through `seven_guis → escher-driver`) is research's question.

## Anti-patterns to avoid
security-plan §Security Anti-Patterns reads `NO RECORDED INTENT`; nothing is taken from it. The bans below follow from the measured sections.
- Formatting a `Command`, `Call` or `ArgValue` with `Debug` — or interpolating an id, typed text or accessible name — into a log record, an `expect` / `panic!` message or an error's `Display`: security-plan §Input Validation (the "Driver command schema (escher-driver)" row) with §Logging & Monitoring (the sink's `escher_*` rule and the raw panic hook).
- Adding a verb, a longer line or a content-bearing reply to the session wire as an implementation step: security-plan §Input Validation (the "Driver session socket (escher-driver)" row) and §API Security (the "Local session socket (escher-driver)" row) make that a registered, ratified change first.
- Reaching a node for a caller-supplied id through a panicking accessor: security-plan §Error Handling (Panic paths, Dioxus nodes) lists `NodeHandle::node` / `node_mut` ("Node does not exist in the Document") and `element_to_node_id`'s unwrap, and (Graceful degradation) names `get` and `try_element_to_node_id` as the non-panicking forms.

## Contract bindings
- **security ↔ obs ↔ tests — typed text in a sink-installing host's log.** security-plan §Logging & Monitoring and §Input Validation (the "`aria-label` · `<label for>`" row) both record typed text as not measured "since no command can type yet". This chunk delivers the first typing command, so the measurement comes due where that command reaches the `escher-session` binary's own instance; it binds obs-plan's scrubbing contract and the standing check `examples/seven_guis/tests/host_log.rs`. An in-process `type` reaches no sink-installing host, so under that answer the reading stays owed and must be recorded as still not measured, not as zero.
- **security ↔ architecture — the crossing.** Under the socket answer, architecture §Occupied Resources and security-plan §Threat Model Summary · §Input Validation · §API Security · §Authentication & Authorization all carry the wire's present form and are amended before the code, with the operator's ratification.
- **security ↔ a11y — the feature's reach.** security-plan §Input Validation (the `id` row) records the platform accessibility adapter as the only exit escher's own code gives the id, under the `accessibility` feature, with its windowed witness still owed. If CARRY 5's feature choice makes the windowed stand binary build AccessKit, that exit opens on a binary the a11y plan treats as building none; the decision is shared with a11y-plan §1.
- **security ↔ tests — the keyed contract.** A change to what the session returns or accepts touches test-plan's `session-lifecycle` contract, which states the wire's bounds the constraints above cite.

## Acceptance criteria contributions
- A call refused at validation, and an acting command whose id names no element, each leave the held instance unchanged — the snapshots taken before and after diff empty — return a typed refusal from the closed cause set, and neither panics; the refusal's `Display` holds none of the supplied id or text (per security-plan §Input Validation, the "Driver command schema (escher-driver)" row, and §Error Handling, Error format)
- A sentinel typed through the driver's `type` into a password input occurs 0 times in the returned diff's ids, parents, names and values, and the entry's value reads `MASKED_VALUE`, in both layout modes (per security-plan §Input Validation, the "Markup attributes · password and file `input` value" row)
- Where a typing command reaches the `escher-session` binary's instance: the typed sentinel occurs 0 times in that binary's stderr at `RUST_LOG=trace` and its stdout is empty; where it does not, the report states the reading as not measured (per security-plan §Logging & Monitoring, the "escher's own sink" entry)
- The session wire is either byte-for-byte the registered one — `hello` / `stop` only, 64-byte request, 128-byte reply, no id · name · value · snapshot text · diff in a reply — or its new form is ratified and registered in the plan before the code that uses it; and `bash .github/scripts/ci-leg.sh audit` passes on the manifest and lockfile the chunk leaves (per security-plan §Input Validation, the "Driver session socket (escher-driver)" row; §API Security, the "Local session socket (escher-driver)" row; §Dependency Security, Audit tool)
