# obs extract

## Relevance
partial — the chunk adds no traceable operation of its own (per-command spans are a later entry's), but a session that is a process is a new escher binary and a new stderr line source, so the sink install, the service identity, the scrub and the no-export ruling all bind it.

## Constraints
- Obs tier 0 sets the depth: lifecycle-level events at most, no span, metric or exporter work in this chunk (per obs-plan §1 Obs Scope Summary — the tier line only; that section's telemetry-surface and must-trace parts are marked and carry nothing).
- A session binary must install escher's sink the way obs-plan §3 Logging stack records it for the windowed stand binary: at the top of the native `main`, ahead of any stand boot, an install failure reported and the process continuing, stderr the only stream. Stdout stays free of telemetry — it is the stream the later CLI entry's JSON will own.
- The install belongs to the binary, not to the session's library path: obs-plan §3 Logging stack requires the headless stand, its checks and their shared module to carry no subscriber install and no env read. A session driven in-process by a proof check therefore installs none. What a second install in one process returns is research's question.
- Every line of the new binary carries the service identity read from that binary's own package name and version (per obs-plan §3 Service identity and line format). The session binary's package name becomes a new `service.name` value — an expected wrap amendment to obs-plan §1 and §3, named in the plan.
- Line shape and level are the sink's, not the chunk's: one text line per event, levels from `RUST_LOG` with the recorded default (per obs-plan §6 Log format (escher's sink)). The chunk adds no second format, no log file and no new env read for logging.
- The scrub is by target prefix and by field name (per obs-plan §8 Scrubbing): an event at a target outside the engine prefixes prints every field except the content-named set, so content discipline for the session crate's own events sits at the call site. A lifecycle field named in that set (an endpoint `path`, an `error` cause) will print redacted — P4 names lifecycle fields knowing that. Whether the new crate's target falls under an engine prefix is research's question.
- Two exits sit past the scrub and bind the session process: the chained std panic hook prints the raw panic message to stderr, and bridged third-party `log` records print under their own target (per obs-plan §7 Panic hooks · §8 Values logged as-is, last bullet). Panic and `expect` messages in session code must therefore be content-free, and what any new dependency logs through `log` is research's question.
- No OTel crate, no egress and no exporter credential path enter with the session crate (per obs-plan §3 Bootstrap phases, `otel-sdk-install`).

## Patterns to follow
- The windowed stand binary's bootstrap — one `init` call with the `service_identity!()` macro, before launch (per obs-plan §3 Logging stack). Whether a session binary can reuse it unchanged is research's question.
- Two call-site models are on record (per obs-plan §2 Telemetry Strategy): engine and upstream crates gate each `tracing` call behind the crate's `tracing` feature with a no-op path; escher-telemetry depends on `tracing` unconditionally. An edit inside an engine crate or `stand.rs` follows the first; which model the new driver crate takes is P4's decision. The stand binary keeps the engine `tracing` features off (per obs-plan §8 Scrubbing, reach) — whether the session crate turns any on decides whether engine events reach its stderr at all.
- If the lifecycle leaves on-disk state (a pid or endpoint record, a status file), the two harness state areas are the model (per obs-plan §3 Agent-run harness log · §3 Cold-agent pipe log · §9 Telemetry artifact handling): one named directory under `target/`, gitignored, removed whole by the owner's own cleanup step which touches nothing else, uploaded by no CI leg, JSON written by an encoder and never hand-assembled. Such an area is harness metadata, not a telemetry sink, and is a new §9 row at wrap.
- Content-free event vocabulary as the cold-agent verdict and stub call log keep it (per obs-plan §6 Log format (the cold-agent pipe) · §8 Scrubbing): counts, outcomes, enumerated identities and a named cause — never an argument value or a result. For this chunk: the lean task's name, a lifecycle step, an outcome, a named edge cause.

## Anti-patterns to avoid
- No telemetry or diagnostic line on stdout from a session binary — the upstream apps' stdout subscribers are recorded as the unscrubbed case, not the model (per obs-plan §3 Logging stack · §8 Scrubbing, reach).
- No log field, event message or panic text carrying a stable element id, an accessible name, a control value or snapshot text: stderr is an exit from the process, and the scope opens none for that content at this chunk (per obs-plan §8 Scrubbing; scope "What may cross at this chunk").
- No span or `#[instrument]` in this chunk: the plan records none anywhere in the workspace and no naming convention for one (per obs-plan §4 Span / Trace Coverage), and the scope gives per-command spans to the "Driver command spans" entry.

## Contract bindings
- obs ↔ tests (test-plan §3, the agent-run contract): the session's proof checks run through `agent-run.sh`, whose events are built from libtest result lines only — captured stdout and panic text never reach an event (per obs-plan §6 Log format (the agent-run harness)). A check that spawns the session process captures that child's streams into its assertion only, as the re-executed child of the id-persistence check does (per obs-plan §3 Logging stack).
- obs ↔ security (security-plan §Input Validation / §Threat Model, only if P4 opens a crossing): the session's stderr is a second way out of the process beside the endpoint; the scrub's content-named set and the scope's "nothing but the lifecycle crosses" are one rule read from two sides (per obs-plan §8 Scrubbing).
- obs ↔ arch (§Occupied Resources): the sink reads one env var for its filter (per obs-plan §6 Log format (escher's sink)); any further env read, state directory or binary name the session adds is a registration there and an obs-plan §1 / §9 amendment at wrap.
- No heartbeat, status-endpoint or trace-propagation binding: the plan holds no measured contract for any of them, so the session's liveness and `attach` reachability are the lifecycle's own design at P4, not an obs obligation.

## Acceptance criteria contributions
- (obs) If the chunk adds a binary, its `main` installs `escher_telemetry::init` with the binary's own service identity before the stand boots, and an install failure is reported on stderr without ending the process (per obs-plan §3 Logging stack).
- (obs) A start → command → stop cycle of the session process puts no telemetry line on stdout; with the filter raised, each stderr line carries `service.name` and `service.version` of the session binary's package (per obs-plan §3 Service identity and line format · §6 Log format (escher's sink)).
- (obs) No event, field or panic message added by the chunk carries an element id, accessible name, control value or snapshot text, shown by a marker-string check or a read of every new call site (per obs-plan §8 Scrubbing).
- (obs) `Cargo.toml` and `Cargo.lock` gain no OTel, metrics or exporter crate, and the new code reads no env var for logging beyond the sink's own filter (per obs-plan §3 Bootstrap phases, `otel-sdk-install` · §6 Log format (escher's sink)).
