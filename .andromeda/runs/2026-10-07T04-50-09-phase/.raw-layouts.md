## Constraints
- The instance a session holds is the headless stand's screen, not Home: layout-templates §Surface: desktop-native › Primary screens (seven_guis Home and TaskShell) requires the headless stand to skip Home and mount one lean task inside TaskShell, with the header region (back button, title) above the task body. The session must hold that same hierarchy for its whole life; whether the existing boot path gives it unchanged to a long-lived holder is research's question.
- The held screen's viewport is pinned: the same bullet requires the headless stand's fixed viewport size, scale, colour scheme and bundled font. A session must not vary any of them between `start` and `stop`, and no lifecycle step may resize or re-theme the instance; whether the session's boot reuses the stand's options without overriding them is research's question.
- The task a session may name at `start` is one of the four lean tasks that bullet lists as mounted by the headless stand; the plan records no headless TaskShell layout for the other three tasks, so layouts gives no coverage for holding them.
- The stand's markup is closed to this chunk: the same bullet requires that the author ids on task controls and value displays add no class, style, wrapper or order, and that no task CSS selects by them. A seam the session needs from the stand must be a code seam, never a new element, wrapper, attribute-for-styling or reordering in a task's or TaskShell's markup.
- A CRUD row's id follows its person, not its position: the same bullet requires each row's author id to be built from the person's model-assigned id and to follow that person under filter, Create and Delete. On a held instance this is what "an id read before a command names the same element after it" must mean for rows — the check reads identity, not list position.
- The document skeleton is fixed and the app mounts into `main`; arbitrary `index.html` templates are not supported (layout-templates §Surface: desktop-native › IA notes). The session cannot rely on a custom document template or a mount point other than the skeleton's.

## Patterns to follow
- Address the held screen by the TaskShell region ids and the per-task author ids the plan lists, not by structure or position (layout-templates §Surface: desktop-native › Primary screens, seven_guis Home and TaskShell).
- The harness's default viewport and the stand's pinned viewport are recorded as the same size, scale and scheme (§Surface: desktop-native › IA notes; › Primary screens) — a session that boots through the stand's own options inherits it and needs no viewport parameter of its own.
- The two existing agent-invocable scripts are recorded with one shape: `<verb> [argument]` from the repository root, lifecycle-style verbs, usage printed to stderr on a usage error with exit 2, stdout carrying structured lines only and raw output kept in a file under `target/` (§Surface: cli › Primary screens, `scripts/agent-run.sh` and `scripts/cold-agent.sh`). The plan records this as what those two scripts do and states no rule for a new binary; if P4 gives the session process a command-line entry for start / attach / stop, this is the precedent to weigh, and the Driver CLI entry — not this chunk — owns the JSON stdout and exit-code contract.
- Each of those scripts is recorded with a Windows pass-through beside it (same anchor) — relevant only if the session's entry lands as a script rather than a Rust binary.

## Anti-patterns to avoid
- Adding an element, class, style, wrapper or order change to stand task or TaskShell markup — or a CSS selector keyed on an author id — to give the session a hook (layout-templates §Surface: desktop-native › Primary screens).
- Holding Home, the windowed stand or a differently sized viewport as "the session's instance": the plan's headless stand screen is TaskShell at the pinned viewport, and the windowed surface is a different screen the chunk's scope leaves untouched (same anchor).
- Treating a row's list position as its identity across commands on the held instance (same anchor, CRUD row ids).

## Contract bindings
- layouts ↔ architecture (stable element ids): the author ids the plan places on the lean tasks' controls are the stable element ids the session's cross-command id proof reads; the id contract itself is architecture's, the placement is layouts' (§Surface: desktop-native › Primary screens).
- layouts ↔ a11y: the chunk adds no focusable element, so layouts contributes no focus-order position; layout-templates carries no focus-order section to cite, and SC 2.4.3 stays with the a11y extract. The plan's note that the six task inputs are named by attributes alone (same anchor) is the layout side of the names the snapshot reads on the held instance.
- layouts ↔ tests: the pinned-viewport TaskShell hierarchy is the screen every session check observes; a check that asserts layout on it falls under the tests domain's both-layout-modes rule, which layouts does not own.
- layouts ↔ tests / security (cli): the plan defers the existing scripts' exit grammar and event schema to test-plan §3 (§Surface: cli › Primary screens); a session command-line entry, if P4 opens one, binds there and to the arch §Occupied Resources / security-plan registration the scope already names.
