# security extract

## Relevance
relevant — the chunk adds a long-lived process, a binary entry point, a workspace crate, lifecycle input and (if P4's fork says so) the project's first inter-process crossing; the plan has rows that bind each, and no row that covers the crossing itself.

## Constraints
- **No endpoint is covered by the plan.** security-plan §API Security records no served API, listener or socket, and §Authentication & Authorization records no auth code; §Threat Model Summary's attack-surface list names no driver or session vector. An `attach` that reaches a second process is therefore outside every recorded boundary: the plan requires that it be recorded (what the endpoint is, who reaches it, what is validated on it, what `stop` removes) before it counts as covered — an expected wrap amendment carrying the operator's answer, never a silent add. (§Threat Model Summary's application-level threat model reads NOT YET MEASURED; nothing is drawn from it.)
- **Ids, accessible names and control values stay in-process.** security-plan §Input Validation (rows `id` (stable element id), `aria-label` · `<label for>`, password and file `input` value) requires that the snapshot, its text, its diff and the unkeyed-actionable list are returned to their caller only — no log, event, socket, file or command carries them, and the platform accessibility adapter stays the id's only exit. That standing is PROVISIONAL pending the founder. A session command at this chunk must not move any of those content classes across a process boundary; opening that exit is another entry's question.
- **Masked values hold on a held instance.** security-plan §Input Validation (password and file `input` value row) and §Data Protection (Local user data handled) require that a password's text and a file input's host path are read only as the fixed mask through the snapshot model, while the DOM keeps the real value. A session keeps typed state alive across commands, so any reading the session exposes must go through the snapshot reader, never the DOM `value` attribute or the editor text.
- **Lifecycle input is validated against a closed set before anything runs.** security-plan §Input Validation (rows CLI arguments (agent-run.sh), CLI arguments (cold-agent.sh), Cold-agent MCP stub) requires a verb or selection outside the allowlist to be refused before any action, with a named cause and no state change. The task named at `start` must be one of the four lean tasks and nothing else; each lifecycle edge (`start` while up, `attach` when none, second `stop`, dead process) needs one named outcome.
- **No caller-supplied URL or path reaches a fetcher.** security-plan §Threat Model Summary (attack surface: remote web content; CLI input), §Input Validation (`file:` URLs (net provider) row) and §API Security (request size limit, request timeout rows) record an unrestricted `file:` read and no size cap or timeout in the net provider. The session's `start` takes a task name only; it must not accept a URL, a document path or HTML. Whether the stand's boot path already leaves no net provider reachable from the session is research's question.
- **The new binary logs through escher's scrubbed stderr sink, content-free.** security-plan §Logging & Monitoring (Log format and backends — escher's own sink, the agent-run and cold-agent bullets) and §Bootstrap phases (logging-redaction-wire) require escher's own binaries to log metadata only through the allowlist-scrubbed stderr subscriber; that section also records that the chained panic hook prints the raw panic message unscrubbed. So no session log field, and no `panic!`/`expect` message, may interpolate an id, a name, a control value or a host path.
- **New crate and dependencies stay inside the audit and the pins.** security-plan §Dependency Security (Audit tool, Pinning, CI integration) and §Supply chain integrity (Lockfile verification) require workspace-inherited versions, a committed lockfile, `--locked` builds, git deps pinned by rev, and a passing cargo-deny advisories leg with per-ID, reasoned ignores only. The audit's reach is its resolved graph, so any third-party crate the session adds (an IPC, pid-file or daemonizing crate in particular) needs a review by hand as well.

## Patterns to follow
- The cold-agent stub's crossing shape — stdio-only, no port, every argument validated, a refusal that names its cause and changes no state, a call log that never records an argument value (per security-plan §Input Validation, Cold-agent MCP stub row). It is the one ratified precedent for a process another process drives.
- Verb allowlist with usage on stderr, empty stdout and a non-zero exit before any precondition or spawn (per security-plan §Input Validation, CLI arguments (agent-run.sh) and (cold-agent.sh) rows; exit conventions per §Error Handling, External responses).
- Run state kept as metadata-only events under the gitignored `target/` tree, with raw output never printed back (per security-plan §Logging & Monitoring, the agent-run and cold-agent bullets). Whether a session needs any on-disk state at all is P4's fork.
- Resolve nodes through the checked lookup and skip what does not resolve; hold stable ids across commands, not process-local node ids (per security-plan §Input Validation, `id` row; §Error Handling, Graceful degradation). A held instance makes stale node ids a normal case, not an edge.
- Typed errors rather than panics on new input paths (per security-plan §Error Handling, Error format (typed errors)).

## Anti-patterns to avoid
security-plan §Security Anti-Patterns reads NO RECORDED INTENT, so nothing is cited from it; the bans below come from the sections named.
- Binding a TCP or Unix listener, a named pipe, or a credential/token file as an implementation detail of `attach` (per security-plan §API Security; §Authentication & Authorization).
- Writing snapshot text, a diff, ids, accessible names or control values to stdout, stderr, a log, an event file or a state file "for debugging" (per security-plan §Input Validation, `id` row; §Logging & Monitoring).
- Installing an unscrubbed subscriber (`fmt::init()`, `env_logger`) or printing to stdout from the session binary (per security-plan §Logging & Monitoring, Log format and backends; §Bootstrap phases, logging-redaction-wire).

## Contract bindings
- **arch §Occupied Resources ↔ security-plan §API Security / §Threat Model Summary** — the new crate name, any endpoint, and any new env var are registrations there and amendments here; one operator answer feeds both (the playbook's boundary-widening escalation).
- **obs (escher-telemetry scrub sets, panic hook) ↔ security-plan §Logging & Monitoring** — a new log field on the session binary must be on the allowlist or content-free; per-command spans belong to a later entry.
- **a11y (`accessibility` feature) ↔ security-plan §Input Validation** — the mask and the snapshot readers exist only under that feature; a session crate that reads the screen without it has no masked reader.
- **tests ↔ security-plan §Dependency Security (CI integration)** — the audit job is the security gate on the new crate; the lifecycle checks are where "stop leaves nothing" and "no content crosses" are witnessed.
- **security-plan §Secret Management** — source reads no secret and the env reads are an enumerated list; an env var the session reads (a state or endpoint location) extends that list and must not be secret-bearing.

## Acceptance criteria contributions
- `bash .github/scripts/ci-leg.sh audit` passes with the new crate and every dependency it adds in the committed lockfile, with no new ignore lacking an ID and a written reason (per security-plan §Dependency Security, Audit tool).
- A census of the new crate's source reads 0 for listener, socket and credential constructs — or exactly the one crossing the operator answered at P4, with a check that `stop` removes every artefact `start` created (per security-plan §API Security).
- A check drives each lifecycle edge and an unknown task name and reads one named refusal each, with no instance booted and no state left (per security-plan §Input Validation, CLI arguments (cold-agent.sh) and Cold-agent MCP stub rows).
- A check types a distinctive string into a control on the held instance, then reads everything the session process emitted or wrote (stderr, any state file): the string, and any stable id or accessible name, occur 0 times (per security-plan §Input Validation, `id` and password and file `input` value rows; §Logging & Monitoring).
