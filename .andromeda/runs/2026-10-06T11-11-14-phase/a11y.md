# a11y extract

## Relevance
partial — the chunk ships no UI surface, focus, key binding, colour or motion; a11y touches it only through the README's own Markdown accessibility (image alt text, heading outline) and through any accessibility capability claim the README makes, which must match the plan.

## Constraints
- Any accessibility statement in the README states the target as the a11y-plan §1 A11y Scope Summary tier (`0 — SC 2.1.1 · 1.4.3 · 2.4.3`) and nothing wider. It names no WCAG conformance level (AA/AAA) and no criterion outside those three. This follows the scope's "never invent capability" rule.
- a11y-plan §1 and §2 Feature exposure require that a README describing the accessibility feature says it is a default feature of the engine and Dioxus crates, and that the reference browser app leaves it out of its default set (per a11y-plan §1). It must not imply that accessibility is on everywhere.
- Screen-reader reach claims stay within a11y-plan §2 Platform adapters and §7 Platform adapter. Exposure is AccessKit through `accesskit_xplat`, and the per-platform gaps are recorded there: Android and Windows `set_focus`, and Android and macOS `set_window_bounds`, are empty or no-ops. The README claims no complete or equal assistive-technology support across platforms.
- Any README mention of an a11y gate in CI must match a11y-plan §9 CI Integration: a slow-tier `a11y` leg that runs the three existing accessibility, role and focusability test files and adds no stand assertion. Accessibility-tree identity and other a11y work still to come are PLANNED, not built. The scope's split between built and planned applies.
- Images that the README keeps or adds, such as a logo or CI badges, carry a text alternative. a11y-plan §7 Text alternatives records the alt-carrying fixture pattern (`servo.html`) against an image with no alt (`servo_header_reduced.html`). Whether any image survives the rewrite is a P4 lean.
- The rewritten README uses real Markdown headings in one outline. a11y-plan §4 Per-component pattern catalog maps headings to `Heading` and text to `Paragraph`, and that is how an AccessKit-rendered page exposes them. The one-outline rule itself is set by the scope, because the plan's heading-hierarchy coverage is not measured. Whether `apps/readme` (rdme) renders the root `README.md` through blitz-dom is research's question.

## Patterns to follow
- Image with a meaningful `alt`, and an empty `alt` only for pure decoration: a11y-plan §7 Text alternatives (servo.html fixture), and a11y-plan §4 Application markup (new-tab logo `alt: "Blitz"`, favicons `alt: ""`). Badge Markdown `![{label}](…)` keeps a descriptive label.
- Status shown as text, not colour alone: a11y-plan §6 State color (the WPT runner prints its status word next to its colour). A CI badge, if kept, carries its status in the badge text and alt, and the README states nothing through colour alone.
- Capability statements that cite a source: describe accessibility with the facts recorded in a11y-plan §1, §2 and §9 (tier, default feature, AccessKit adapters, CI leg), not with general phrases like "fully accessible".

## Anti-patterns to avoid
- An image or badge with no `alt` text. a11y-plan §7 records `servo_header_reduced.html` as the counter-example.
- Overclaiming accessibility, such as "WCAG AA compliant", "screen-reader ready on every platform" or "accessible by default everywhere". This contradicts a11y-plan §1 (tier 0, three SCs, the browser app's feature not default) and a11y-plan §2 Platform adapters (no-op adapters).

## Contract bindings
- a11y ↔ the scope's capability-honesty rule (intent and master records): the README's a11y claims must come from a11y-plan §1, §2 and §9 and from verified matrix entries. Accessibility-tree identity (v010-03) is PLANNED.
- a11y ↔ rdme (`apps/readme`): the README may be rendered by escher's own engine. If so, its headings and image alt text reach the AccessKit tree per a11y-plan §4 and §7, and rdme's focus-visible styling applies per a11y-plan §6 Focus ring. Whether rdme reads the root README is research's question.
- a11y ↔ tests (CI §9): the rewrite touches no test file, so the `a11y` leg (`bash .github/scripts/ci-leg.sh a11y`) must still pass unchanged.

## Acceptance criteria contributions
- Every image in the rewritten `README.md`, including logos and badges, has non-empty alt text, or the README has no images (per a11y-plan §7 Text alternatives).
- The README's headings form one outline: exactly one top-level `#` heading and no skipped levels. Each section of the five-part structure is a real Markdown heading, not bold text (per a11y-plan §4 Per-component pattern catalog; the outline rule is the scope's).
- Any accessibility statement in the README names only SC 2.1.1, 1.4.3 and 2.4.3. It claims no conformance level and no platform coverage beyond what is recorded (per a11y-plan §1 A11y Scope Summary and a11y-plan §2 Platform adapters).
- `bash .github/scripts/ci-leg.sh a11y` passes unchanged after the rewrite (per a11y-plan §9 CI Integration).
