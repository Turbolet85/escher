# obs extract

## Relevance
partial — the chunk serves fixed schema text over the two surfaces that hold escher-driver's two spans (`command` under `Session::run`, `tool_call` under each MCP `tools/call`) and the sink-installing `escher-session` binary; it adds no telemetry of its own, but anything it adds to the verb set, the MCP protocol or the command line meets the span, log-line and scrub rules below (obs tier 0, per obs-plan §1).

## Constraints
- obs-plan §4 requires the `command` span to keep its eight fields (`verb` · `cause` · `settled` · `busy` · `passes` · `added` · `removed` · `changed`), each recorded only where it applies, `verb` holding the verb table's own word and never the caller's text; a verb added to `VERBS` for self-description (CARRY 1's `help`) adds one word to that field's closed set and no field. Whether such a verb is handed to `Session::run` (and so refused `unknown-verb` like `start` · `status` · `stop`, its span still recording the table word) or answered outside it is research's question.
- obs-plan §4 requires the `tool_call` span to be opened once per MCP `tools/call` only, before its params are read, held until its reply is written, with exactly two closed-word fields — `tool` (the table's word, unrecorded for an unknown tool) and `ending` (`accepted` · `refused` · `error`) — an instance verb's `command` span its child and a server-answered verb leaving a `tool_call` with no `command` child; a self-description tool served over MCP follows the same shape.
- obs-plan §4 records `serve_mcp`'s protocol outside a tool call (`initialize` · `ping` · `tools/list` · a protocol error) and `command_line` with its argv reader as writing no record; a newly answered method (CARRY 6's `server/discover`), a newly spoken revision, or help served by the command line therefore writes none unless a new record is decided — and the scope's Boundaries admit no new record class.
- obs-plan §3 (Logging stack) requires stdout of `escher-session` to carry a command's answer only — one line of JSON per command line run, JSON-RPC protocol lines only in the `mcp` role, written by the crate's hand writer with `serde_json` reading requests and writing nothing — and the sink to write to stderr only; served help, verb lists and schemas are answers on stdout, never log lines, and the driver installs no subscriber and reads no environment variable.
- obs-plan §6 (Logged events, examples) requires every `escher-session` ending to stay as stated — usage a fixed line on stderr built from `VERBS` with stdout empty and status 2, a session error its object on stdout and fixed message on stderr with status 3, accepted/refused one JSON line on stdout with stderr empty when `RUST_LOG` is unset — every diagnostic a fixed string holding nothing the caller typed; a help ending or a richer usage line keeps that shape.
- obs-plan §8 (Scrubbing) requires every pair on an `escher_driver` closed-span line to pass the content-named scrub under the escher prefix set; `tool` and `ending` print because they are closed words outside that set, so any span field the chunk might add must hold a closed word or count, never served or call-supplied text.
- obs-plan §2 requires escher-driver to keep `tracing` as its one, ungated telemetry dependency, with its two span macros (`command`, `tool_call`) as its only emitters; the chunk adds no telemetry dependency, subscriber or event.

## Patterns to follow
- Hand-built spans with `tracing::info_span!(target: "escher_driver", …, field = Empty)`, fields recorded only where they apply, no `#[instrument]` (per obs-plan §4).
- In-process span assertion through `stand_mcp_tools`' hand-written `Recorder` installed with `tracing::subscriber::with_default` — no escher sink, no env read, prints nothing, each test under its own recorder because callsite interest is process-global (per obs-plan §3, Logging stack).
- Spawned-binary log reads: `mcp_log` and `host_log` start `escher-session` at `RUST_LOG=trace`, drain both streams, read them into assertions only under both builds, and a failure prints a kind and a count, never what the binary wrote (per obs-plan §3, Logging stack).
- A check that reads an accepted command's empty stderr removes `RUST_LOG` from the child's environment (per obs-plan §3, Logging stack).

## Anti-patterns to avoid
- Fielding any argument, `Command`, `Call`, `ArgValue`, `Outcome`, `Refusal` or `Fault`, the screen text, or (by extension) served help text on a span, or printing one with `Debug` in a log — obs-plan §4 lists them as never fielded and §3 (Logging stack) records that nothing in the crate logs or fields them.
- Writing a log line on stdout, or a served answer (help, verb list, schema) as a log record on stderr (per obs-plan §3, Logging stack; obs-plan §6, Log format: the sink is stderr only).
- Adding a span, event or line on the MCP protocol outside `tools/call` or on the command line's argv reader without a recorded decision (per obs-plan §4).

## Contract bindings
- obs ↔ tests: `stand_mcp_tools` (one `tool_call` per call, the parent of each `command`), `mcp_log` (one `tool_call` line per call, 0 typed sentinels, 0 id and 0 name needles at `trace`, both builds), `host_log` and `stand_act_spans` read the spans and stderr this chunk's new verbs or methods reach; a counted reading (obs-plan §6: one CRUD flow at `info` → 5 `tool_call` and 3 `command` lines) moves if a tool is added to a flow (per obs-plan §3; obs-plan §6).
- obs ↔ security: the span fields' closed-word rule (obs-plan §8, Scrubbing) is the obs side of security-plan §Surfaces' "add no field that holds what a call supplied or a screen reads"; whether a tenth verb word, a new answered method or a new revision is inside the ratified crossing is P4's reading against that plan.
- obs ↔ arch: the `verb` and `tool` fields' value set is `VERBS`' word set (obs-plan §4) — a verb added to the one table changes both spans' closed sets in the same edit.
- obs ↔ wrap (CARRY 8): obs-plan §3 (Logging stack) states "seventeen of the eighteen checks that hold a session" read `session_common`; `stand_mcp_tools` also reads it, so the chunk's report states the readers and its wrap re-counts that sentence — a report line, no plan task.

## Acceptance criteria contributions
- Every MCP `tools/call`, any self-description tool included, leaves exactly one closed `tool_call` span whose `tool` is a table word and `ending` one of `accepted` · `refused` · `error`; an instance verb nests one `command` child, a server-answered verb none; the `command` span keeps exactly its eight fields (per obs-plan §4).
- `mcp_log` and `host_log` stay green under both builds: the `mcp` role's and the host's stderr at `RUST_LOG=trace` hold 0 typed-sentinel occurrences, 0 id needles and 0 name needles, with served help, verb lists and schemas found on stdout only (per obs-plan §8, Values logged as-is; obs-plan §3, Logging stack).
- No new span, event or log line on `initialize` · `ping` · `tools/list` · any newly answered method (e.g. `server/discover`) or on the command line's help serving, and no new telemetry dependency or subscriber install site (per obs-plan §4; obs-plan §2).
- Every `escher-session` ending, a help ending included, keeps one JSON line on stdout or one fixed stderr line with the stated status, holding nothing the caller typed (per obs-plan §6, Logged events).
