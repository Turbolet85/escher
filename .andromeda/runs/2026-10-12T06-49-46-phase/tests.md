## Constraints
- test-plan §4 Unit Test Strategy (escher-driver) requires the served tables to be pinned against tables stated in the tests. schema.rs pins the nine verbs in a stated order and two levels, each with help, arguments and at least one result field, plus the twelve key names, node fields and busy classes. refusal.rs pins the eight causes, each with its meaning and remedy, against a stated table: remedies pairwise distinct and no `/` in any text. Each table is stated in its test with its row count asserted. A `help` verb, a help per node key, exit-status meanings or session-error text added to the one table must be re-stated in these tests, with counts asserted. Whether exit-status meanings or session-error remedies already sit in the table is research's question.
- test-plan §4 Unit Test Strategy (escher-driver) requires cli.rs to pin these: a line read by its rules in order (64 rows since 2026-10-10-mcp-surface, per test-plan §1 Test Scope Summary), the usage line built from the verb table and the app names, each ending's streams and status, and a line that is no command or is refused running nothing. A served help or schema output on the command line enters these row tables.
- test-plan §3 Test Harness Contract `session-binary` requires four endings with fixed exit statuses: `0` accepted with one uncoloured JSON line on stdout; `1` refused; `2` usage, with one fixed line on stderr and stdout empty, nothing booted and no state created; `3` session error. No ending may write back anything the caller typed. The `mcp` role is `mcp` alone, and anything after it is usage. Any new served form (help, schemas) must fit one of these endings without breaking them.
- test-plan §6 E2E Test Strategy (Drivers per surface → MCP) records `mcp_server` asserting that `tools/list` offers the nine verbs in order and that `server/discover` is answered as a protocol error that runs nothing. A tenth verb, a new method answered or a new revision spoken (CARRY 1, CARRY 6) changes rows this check pins. test-plan §1 Test Scope Summary (escher-driver) records mcp.rs's unit test "the listing is the nine verbs of the table" and its test that a result over the answer bound is replaced by the session error.
- test-plan §2 Test Strategy (Process-lifecycle checks) requires these of a process check: every wait bounded; a child driven over piped stdin through `Speaker` under the 30 s `REPLY_BOUND`, killed and reaped in its `Drop`; a host that installs escher's sink drained from spawn; socket-holding checks `cfg(unix)`-gated. `mcp_server` and `mcp_log` stay un-gated, bar the one command-line comparison, so the windows job runs them.
- test-plan §3 Test Harness Contract (Stand log format) requires a command's stdout to be its answer and nothing else: one line of JSON, no ESC byte, and an accepted command's stderr empty with `RUST_LOG` unset (exercised by `cli_commands`). The `mcp` role's stdout carries protocol lines only.
- test-plan §2 Test Strategy (Directory pattern) and test-plan §3 Test Harness Contract (Crate-local test helpers) both state that 17 checks read `tests/session_common/mod.rs` through `mod session_common;`. CARRY 8 says `stand_mcp_tools` also declares it. Whether it does is research's question, and the chunk report re-counts the readers for the wrap.

## Patterns to follow
- Stated-table unit tests with row counts asserted, plus mutation controls. Each control turns a named test red and reads green on the restored tree, recorded in the chunk's `evidence/controls.md` (per test-plan §4 Unit Test Strategy).
- seven_guis process checks go through the shared `tests/common/mod.rs`. For the command line: `Ran`/`run`/`client`, the answer readers `keys`, `number`, `cause` and `string_at`, and the `Started` guard that stops a started session. For the `mcp` role: `Speaker`/`Spoke`, every reply asserted free of an ESC byte. Every seven_guis target declares `mod common;` (per test-plan §1 Test Scope Summary).
- In-process MCP checks run `serve_mcp` over in-memory streams in both layout modes. Each compares a `snapshot` result byte for byte with `Session::run`'s output and reads span parentage with a hand-written in-process recorder, as `stand_mcp_tools` does (per test-plan §1 Test Scope Summary).
- A password check uses an in-file fixture booted with the stand's options, since the stand's four lean tasks hold no password input. A password typed by the driver occurs 0 times in what the call returns and reads `MASKED_VALUE`, as `stand_act_diff` and `stand_act_filled` do (per test-plan §5 Integration Test Strategy). Whether an MCP session can hold such a fixture (in process through `serve_mcp`, or through the binary's four-task boot) is research's question.
- A new blitz-tests file with a `stand_` prefix is auto-discovered as its own target. `agent-run.sh run stand` picks it up with no script change, and `BlitzTestsTargetsTest` pins one target per file (per test-plan §3 Test Harness Contract; per test-plan §4 Unit Test Strategy).

## Anti-patterns to avoid
- Assertions over a call must carry a row index only, so a failing log prints no argument value. No id, name or typed text may appear in a test name or assertion message (per test-plan §4 Unit Test Strategy).
- Do not count a sink capture's lines in total. Count by span and target, because the workspace build adds an engine line. Do not read a per-package green as the workspace leg's green (per test-plan §9 CI Integration).
- Do not wait for a sink-installing child to exit before reading its streams. Drain from spawn, or capture to a file (per test-plan §2 Test Strategy).
