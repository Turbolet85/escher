# security extract

## Relevance
relevant — the chunk changes what the two ratified carriers, the `escher-session` command line and the `escher-session mcp` role, write out, and it may grow the verb table, the MCP method set and the session-error texts, each of which the plan records as a validated surface or a ratified crossing.

## Constraints
- The verb table is a closed, validated external-input surface: security-plan §Input Validation (Driver command schema row) requires every call to pass `validate` / `validate_session` against a closed `'static` table of nine verbs and six bounded argument kinds before anything runs. It records each earlier verb added to that table (`scroll`, then `start` · `status` · `stop`) as a widening the founder ratified. A `help` verb added to `VERBS` (CARRY 1) therefore grows a validated surface and is the founder's fork (`inputs#I1`). It also changes the MCP row's "a name outside `VERBS` → `-32602 unknown tool`" and the tool count that v010-13 states. Whether self-description can be served without a tenth verb is P4's question.
- What either surface serves must be the program's own fixed text: security-plan §Error Handling requires each cause's name, meaning and remedy to be a fixed non-empty `&'static str` that holds no path. It also requires `Cause`, `Fault` and `Refusal` to have no `String` field. Help, result-shape, node-key and exit-status texts added to the one table (CARRY 1, 4, 5) need the same shape: fixed literals that hold nothing a call supplied or a screen reads.
- No ending writes back what the caller typed: security-plan §Input Validation (CLI arguments (escher-session) row) requires that no command's ending — usage line, refusal, session error or answer — writes back anything the caller typed (no path, label, id or value). It also requires the usage line (status 2, stdout empty) to be built from the verb table and the app names. Any served help or verb listing on the command line keeps both rules. A stated bound or remedy for `state-dir-too-long` (CARRY 3) must name the limit and never echo the `--session` path, and so must any other session error's.
- The MCP server's method set and bounds are recorded as ratified: security-plan §Input Validation (MCP server row) requires that only `initialize`, `ping`, `tools/list` and `tools/call` are answered. Every other method, `server/discover` included, gets `-32601`. Protocol errors are a fixed code and message with no `data`, a result is at most 1,048,576 bytes, and the only client-sent value echoed back is the `id`, as an i64 or a string of at most 128 bytes. Answering `server/discover`, or speaking `2025-11-25` or `2026-07-28` (CARRY 6), changes this row. Whether that is "a new field of a closed value set inside an already ratified carrier" or a new exit needs a reading against the founder's 2026-10-10 rule (security-plan §Input Validation, Driver session socket row). A widening goes to the founder.
- The writer stays hand-written: security-plan §Input Validation (MCP server row) requires replies to be written only by the crate's hand-written JSON writer, with `serde_json` reading and writing nothing. It also requires no print, `unwrap`, `expect` or `panic!` outside the tests. security-plan §Dependency Security records `serde_json` as a reader with no `preserve_order` feature. A served schema, for example an `outputSchema` or a `server/discover` body, is written by the same writer, with no new dependency or feature.
- The actionable-key check must not cross unbidden: security-plan §Input Validation (`id` row) records `DioxusDocument::unkeyed_actionable` as adding no crossing: no wire form and no driver, CLI or MCP command. Its `UnkeyedActionable.node` is a process-local `NodeId`, and the plan requires that no `NodeId` crosses. Exposing it as a command (CARRY 2) is a new exit for stable ids and is the founder's fork.
- Log records stay closed: security-plan §Logging & Monitoring requires the driver's log records to be the `command` span (eight fixed-word, bool and count fields) and the `tool_call` span (`tool` and `ending`, closed words) only. It also requires a sink-installing binary's stderr to carry no id, name or typed text at any `RUST_LOG` level. Serving help adds no span field, and no field holds served text or anything a call supplied.

## Patterns to follow
- The texts' one source: refusal and help texts are `'static` literals of the verb table and `CAUSES`, written by `Refusal::to_json` from a cause's fixed strings (security-plan §Error Handling). Self-description reads the same table rather than restating it.
- Session errors as fixed objects: each session error is written as `{"error":{"kind","message"}}`, with `kind` one fixed kebab-case word per variant and a fixed message (security-plan §Error Handling). A remedy or stated bound added here, if any, takes the same fixed-literal form.
- The MCP mask: an MCP tool result's text is `Session::run`'s own output, so the mask holds by construction (security-plan §Input Validation, password and file `input` value row). New result content follows that path and never builds a second writer of screen content.
- Needle checks: the existing checks that read for leaks (`host_binary` keeps the usage line free of anything typed; `mcp_server` finds no reply holding the refused id, the tool name or the filler; `mcp_log` / `host_log` count sentinels at `trace`) are the model for any new served output (security-plan §Input Validation, CLI and MCP server rows; §Logging & Monitoring).

## Anti-patterns to avoid
- A served text that formats in a caller value: no `String` field, `format!` of an argument, or path in a help, remedy, usage or session-error text (security-plan §Error Handling; §Input Validation, CLI arguments (escher-session) row).
- A new method, revision or verb answered without that reading: adding any of them without first reading it against the ratified-crossing rule and, if it widens, the founder's ruling (security-plan §Input Validation, MCP server and Driver command schema rows).
- Logging served self-description: logging or fielding the schema text, a help text, an `Outcome` or a `Refusal`, or carrying a `NodeId` out of the process (security-plan §Logging & Monitoring; §Input Validation, `id` row).

## Contract bindings
- security ↔ obs: the `command` and `tool_call` span field sets and the sink's zero-needle reading at `trace` (security-plan §Logging & Monitoring), which bind to the obs-plan's span contracts and the `mcp_log` / `host_log` checks.
- security ↔ tests: the owed password-over-MCP check (CARRY 7) needs a fixture with a password input. The stand's tasks hold none (scope, CARRY 7), so the fixture goes beside the stand, per the founder's 2026-10-06 ruling held by the test-plan. The mask contract is in security-plan §Input Validation (password and file `input` value row).
- security ↔ architecture: any new carrier, method or exit is an arch §Occupied Resources and security-plan amendment first. A revised MCP method set or verb count also rewrites the security-plan MCP server and Driver command schema rows and v010-13's claimed acceptance.

## Acceptance criteria contributions
- A password typed through an MCP `type` tool call into a fixture's password input appears 0 times in any tool result's text, `snapshot` and acting call alike, and the value reads `MASKED_VALUE`, in both layout modes (per security-plan §Input Validation, password and file `input` value row).
- Every self-description output on both surfaces is a fixed literal of the one table and holds nothing a caller typed: help, verb list, schemas, node-key help, exit-status meanings and any session-error remedy or bound. A needle check like `host_binary` / `mcp_server` finds no supplied id, path, text or tool name in it, the admitted MCP `id` echo excepted (per security-plan §Input Validation, CLI arguments (escher-session) and MCP server rows).
- The `mcp` role's and the host's stderr at `RUST_LOG=trace` over a flow that includes the new served output hold 0 typed-sentinel occurrences, 0 id needles and 0 name needles under both builds. The `command` and `tool_call` spans keep their field sets unchanged (per security-plan §Logging & Monitoring).
- Unless the founder ratifies a change, a method outside the four answered methods still gets `-32601` with a fixed message and no `data`. Every served result, `tools/list` included, stays within 1,048,576 bytes and is written without `serde_json` (per security-plan §Input Validation, MCP server row).
