# a11y extract

## Relevance
partial: the chunk adds no rendered UI, focus, key binding or colour. Its a11y reach is the served text that describes the snapshot model's role, name and state readings (node keys, `changed`, the `disabled` cause), the password-mask check over MCP (CARRY 7) and its fixture, and the stand's accessibility invariants, which must not move.

## Constraints
- Any help served for the node keys `selected`, `pressed` and `invalid` must state what the snapshot model reads. a11y-plan §7 (Accessibility tree output) requires the snapshot to take the three from the accessibility node, never from the element, and records the two limits of the boolean model: a mixed toggle reads `pressed` false, and a grammar or spelling error reads invalid. A served help that drops a limit or contradicts it misdescribes the model (CARRY 5).
- Help for `pressed` must not say it reflects `aria-checked`. a11y-plan §2 (Role derivation) records that `aria-checked` is not read, so a node's `toggled` is exactly its `aria-pressed` reading, and that the three are read by closed-set value match on any element.
- Served help for `role` and `name` must describe them as the snapshot node's readings, taken from the accessibility tree. a11y-plan §7 (Accessibility tree output) requires the driver's schema to define no role or name set of its own, `role` and `name` being only field names of its result nodes. A served schema that lists or enumerates roles would be a second mapping.
- The `disabled` cause's served meaning and remedy must keep the presence reading. Per a11y-plan §7 (Accessibility tree output), the cause is stated as "the element carries the `disabled` attribute, which the snapshot reads as not enabled", and the driver refuses on `enabled == Some(false)` and on nothing else. a11y-plan §5 (Focus order) records that a `disabled="false"` control reads not enabled yet stays focusable.
- A password's or a file input's value must read the fixed `MASKED_VALUE` in every carrier, an MCP `type` and read-back included (CARRY 7). a11y-plan §7 (Accessibility tree output) requires the typed text in no field of the snapshot or the tree, and requires an MCP tool result to be a further reader of the snapshot model and of nothing else, with no second role or name mapping.
- A fixture added beside the stand for the password check must leave the stand's own a11y readings as they are. a11y-plan §7 (Accessibility tree output) records that the 15 interactive controls carry an HTML-AAM role and a non-empty name in both layout modes with the Tab order unchanged, and that the actionable-key check returns nothing on the four lean tasks and Home. Whether the password check needs a new fixture or an existing one serves is research's question.
- A new or changed dependency of `escher-driver` must not bring a platform adapter into the stand graph. a11y-plan §1 (A11y Scope Summary) re-reads this at each dependency change: `accesskit_xplat` and `accesskit_winit` read 0 rows in `cargo tree --locked -p seven_guis -e normal`.

## Patterns to follow
- Readers of the snapshot model add no mapping of their own. `to_text`, `diff` and the MCP results each take role, name and state from the snapshot, which takes them from the accessibility tree (per a11y-plan §7, Accessibility tree output). Served help that describes a node key reads its words from the one table, not from a second source.
- Fixtures sit beside the stand with stated expectations: an in-file fixture element proven in both layout modes and named by `aria-label`, test-only, with no stand task gaining it. The textarea fixture of `stand_snapshot_state` is the shape to follow (per a11y-plan §7, Accessibility tree output). A password input maps to the `PasswordInput` role (per a11y-plan §4, Per-component pattern catalog, Form input).
- Stand a11y expectations are stated once, in the shared tables `controls` and `INPUT_NAMES` of `tests/blitz-tests/tests/common/mod.rs`, never as a second role or name mapping (per a11y-plan §7, Accessibility tree output).
- Every check that reads a snapshot runs in both layout modes (`for incremental in [false, true]`), as each state and focus reading in a11y-plan §7 (Accessibility tree output) was proven.

## Anti-patterns to avoid
- A second role or name mapping in the served schema or its help, such as an enumerated role list or a name rule restated outside the snapshot model (per a11y-plan §7, Accessibility tree output).
- Help text that claims more than the boolean model reads, for example that `pressed` distinguishes a mixed toggle or that `invalid` names its kind (per a11y-plan §7, Accessibility tree output; a11y-plan §2, Role derivation).
- A password's typed text in any served or returned field, MCP results included (per a11y-plan §7, Accessibility tree output).
