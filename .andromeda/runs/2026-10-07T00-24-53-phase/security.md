# security extract

## Relevance
relevant — the chunk builds a second in-process reading of the snapshot's content classes (stable ids, accessible names, a text control's value) and changes when the shell's accessibility update fires; it adds no input boundary, API surface, secret or dependency.

## Constraints
- **Exit.** security-plan §Input Validation (the `id` row) requires that the snapshot and its text be returned to their caller only — no log, event, socket, file or command carries either — and records that answer as PROVISIONAL, pending the founder at the Epoch 3 boundary. The diff carries the same content classes, so the same requirement binds it: a Rust value returned in process, with the platform accessibility adapter left as the id's only exit. The chunk neither settles nor widens the provisional answer.
- **Identity.** security-plan §Input Validation (the `id` row) requires that neither the id nor the snapshot carry a `NodeId`, `ElementId`, `ScopeId` or pointer. The engine's changed set is `NodeId`s; the diff type's subjects must be stable element ids only, so the mapping from the set to ids happens before the value is returned. Whether a drained-set accessor on `BaseDocument` is reachable from outside the process by any path is research's question (the plan records none).
- **Masking.** security-plan §Input Validation (the password and file `input` value row) and §Data Protection → Local user data handled require that a password's or a file input's value read as the fixed mask — never the text, never its length, never a file's host path — and that the text form read the model. A diff entry's value for those controls must therefore be the model's reading, and no diff field (an old/new pair, a change count, a per-keystroke record) may carry the length. Whether a change that leaves the masked reading identical (a second character typed into a password) counts as a change is the plan's to state; it must be decided on the model's reading, not on a second reading of the control.
- **Stale ids.** security-plan §Input Validation (the `id` row) requires the snapshot's reader to resolve each id through `BaseDocument::get_node`, never an index, to omit a node that does not resolve, and to panic on no path; §Error Handling → Graceful degradation records the same rule for stale node ids engine-wide. A changed set can hold the id of a node dropped later in the same step, so every read of a tracked id must use the resolving accessor. Per §Threat Model Summary (attack surface: remote web content, script execution) the mutations that fill the set can be driven by untrusted content in the windowed apps, so a panic there is a content-reachable crash.
- **Log fields.** security-plan §Logging & Monitoring (Log format and backends) requires engine log call sites to sit behind each crate's `tracing` feature, and records that escher's sink prints only an allowlisted field set for engine targets while the upstream apps' subscribers and the WPT runner's logger stay unscrubbed. Tracking code added to blitz-dom or blitz-shell is reachable by those unscrubbed sinks: it must add no field carrying a name, value, text or attribute, and library code must not print the set or the diff.
- **Check output.** security-plan §Logging & Monitoring (the agent-run contract entry) records that the raw cargo/libtest output is kept unscrubbed under `target/`. An assertion message, a `println!` or a `dbg!` holding diff content lands there, so the stand check must carry labels only (mode, id), per the §Input Validation `id` row's test shape. Whether an equality assertion over a whole diff value would print both operands on failure is research's question.
- **No new surface.** security-plan §API Security (no served API surface), §Secret Management (Environment values read) and §Dependency Security (Pinning; CI integration) bound the chunk's edges: no listener, socket, env read or dependency edge is expected. If a dependency edge does appear it must be workspace-inherited, built `--locked`, and pass the audit leg.

## Patterns to follow
- The in-process reader shape of security-plan §Input Validation (the `id` row): takes no argument, resolves through the non-panicking accessor, skips what does not resolve, logs nothing, adds no crossing. The diff is a further reader of that kind.
- Read the model, not the control: per security-plan §Input Validation (the password and file `input` value row) the mask is applied once, in the snapshot reader, and every later form reads the model. A diff built over two snapshot readings inherits the mask; a diff that consults the DOM for a value does not.
- If the diff is written as text: the field discipline of security-plan §Input Validation (the `id` and accessible-name rows) — each id and name a quoted field in `str`'s `Debug` form, so a line break or a bare quote in a name cannot forge a line or a field; one text form, no JSON form, no `Display` impl, no parser.
- Bounded state under untrusted input: security-plan §Threat Model Summary (attack surface → remote web content, trust boundary) records caps on recursion that remote content can drive. The plan states no bound for the changed set; whether a set written by every mutation stays bounded in a document nothing drains (a script that creates and drops nodes, a window with the accessibility update off) is research's question, and P4's to answer if it is not.
- Feature-gated log call sites with a no-op fallback, per security-plan §Logging & Monitoring (Log format and backends), should the tracking need any telemetry at all.

## Anti-patterns to avoid
(security-plan §Security Anti-Patterns reads NO RECORDED INTENT — nothing is cited from it; the bans below follow from the sections named.)
- Diff or drained-set content in a `tracing` field, a `println!` / `eprintln!` / `dbg!`, a file, or an assertion message (security-plan §Input Validation, the `id` row; §Logging & Monitoring).
- A `NodeId`, `ElementId`, `ScopeId` or pointer in the diff's public shape, or indexing the slab with a tracked id (security-plan §Input Validation, the `id` row; §Error Handling → Graceful degradation).
- A second reading of a password's editor text or a file input's `value` attribute to compute or describe a change, or any diff field from which the length can be recovered (security-plan §Input Validation, the password and file `input` value row; §Data Protection → Local user data handled).

## Contract bindings
- **security ↔ a11y.** Making `has_changes` truthful and draining the set changes when the shell pushes its AccessKit tree update. Security-plan §Input Validation (the `id` and accessible-name rows) registers the platform accessibility adapter as the one crossing ids and names take, and requires that a typed password occur in no accessibility-tree label or value. The fix may change the timing of that crossing, never what crosses or where; the a11y plan owns the tree-update wording.
- **security ↔ obs.** The allowlist scrub of security-plan §Logging & Monitoring is the obs pipeline's contract too: no new content-named field on an engine target, and none that would need a new allowlist entry.
- **security ↔ tests.** The stand check's output discipline (labels only) and the unscrubbed raw test log (security-plan §Logging & Monitoring); fixture values for the masked-control case are synthetic literals, never real credentials or real host paths; the diff is asserted in both layout modes.
- **security ↔ architecture.** No new listener, port, socket, env var or crate (security-plan §API Security; §Secret Management → Environment values read) — the architecture's resource registry stays untouched. The plan rows this chunk's behaviour will restate (§Input Validation: the `id`, accessible-name and masked-value rows) are wrap's to amend; phase amends none.

## Acceptance criteria contributions
- (security) The diff's public type holds no `NodeId`, `ElementId`, `ScopeId` or pointer field; every node it names is named by stable element id — read from the type definition (per security-plan §Input Validation, the `id` row).
- (security) A fixture step that types into a password input, and one over a file input holding a value, yields a diff (and a diff text, if one is built) in which the typed literal and the path occur nowhere and the value reads the fixed mask; no diff field varies with the typed length (per security-plan §Input Validation, the password and file `input` value row; §Data Protection → Local user data handled).
- (security) A census over the chunk's diff finds no new `println!` / `eprintln!` / `dbg!`, no `tracing` field, no file or socket write carrying the changed set or the diff in library code, any new log call site feature-gated, and the stand check's assertion messages carrying mode and id labels only (per security-plan §Input Validation, the `id` row; §Logging & Monitoring → Log format and backends).
- (security) A step that changes a node and then drops it before the drain produces a drain and a diff with no panic, in both layout modes (per security-plan §Error Handling → Graceful degradation; §Input Validation, the `id` row).
