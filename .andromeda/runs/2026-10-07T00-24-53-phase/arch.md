## Constraints
- **Placement — three existing crates, no new one.** The tracking (set, flag, drain) belongs to blitz-dom's `document` / `mutator` modules, the flag's caller to blitz-shell's `window` module, the diff to dioxus-native-dom beside its `snapshot` / `snapshot_text` modules (per architecture §Existing Scopes → blitz-dom · blitz-shell · dioxus-native-dom; §Infrastructure Patterns → Directory structure). §Occupied Resources → Names is the crate registry: a new workspace crate is a registration, and the scope assumes none. dioxus-native-dom's snapshot modules are recorded crate-private with their types re-exported from the crate root (§Existing Scopes → dioxus-native-dom) — the diff's module follows that shape.
- **Feature gate.** §Standard Contracts → Dioxus DOM bridge and §Cross-cutting Patterns → Config management require the snapshot model, its text form and the actionable check to compile only under dioxus-native-dom's `accessibility` feature, which a crate pinning `default-features = false` gets only by naming it (blitz-tests names it; seven_guis names none). A diff built on the snapshot sits under the same gate. Whether blitz-dom's changed set and flag are themselves gated by a feature today is research's question — the flag's shell caller is accessibility surface, the set is not necessarily.
- **Writes go through the mutator.** §Conventions → DOM API patterns requires mutations through `DocumentMutator` (flush on `Drop`) and names `DocumentMutator::doc` an escape hatch to avoid; §Standard Contracts → Mutation, query and CSSOM lists the `doc.mutate()` method set — the write sites tracking has to cover. That list is not the whole of what a snapshot reading depends on: §Design Philosophy → One incremental pipeline and §Cross-cutting Patterns → Invalidation and state integrity / Event processing record element-state changes (focus, hover, active, disabled) and event default actions as paths of their own. Whether focus, `checked` and a text control's editor value change through the mutator or beside it is research's question, and it decides where marking is added.
- **The snapshot's fields are wider than a mutated node.** §Standard Contracts → Dioxus DOM bridge defines a snapshot node's reading as id · role · name · state · bounds, with `name` drawn from a node's label or its `labelled_by` targets, `bounds` from the layout-resolved client rect, and `focused` from the tree's focus. A node can therefore change its reading without being the node a mutation wrote (a text child's edit renames its parent; a sibling's growth moves bounds at `resolve`, per §Infrastructure Patterns → Runtime threading and event flow, the `resolve` order). "Exactly the nodes whose snapshot changed and no others" cannot be assumed to equal the engine's mutated-`NodeId` set; how the two relate is P4's design on P3's reading.
- **Identity: stable element id out, versioned `NodeId` in.** §Standard Contracts → Dioxus DOM bridge requires that no snapshot field holds a `NodeId`, an AccessKit tree id, an `ElementId`, a `ScopeId` or a pointer, and that stable ids are computed on demand and written to neither the DOM nor the vdom — the diff's public type inherits both. Inside the engine, §Established Decisions → Node identity and §Cross-cutting Patterns → Invalidation and state integrity require stale ids to be read through `get` / `contains_key`. Two recorded behaviours bear on a tracked id: a node a re-render removes is DETACHED, keeps resolving and reads no stable id (§Standard Contracts → Dioxus DOM bridge), and `node_id_mapping` entries are not cleared on removal (§Established Decisions → DOM semantics) — so "the id still resolves" is not "the node is on screen".
- **Both layout modes read the same.** §Design Philosophy → One incremental pipeline requires incremental and non-incremental layout to stay identical; §Cross-cutting Patterns → Invalidation and state integrity records that non-incremental mode marks every node damaged each resolve and that every DOM mutation inserts box-construction damage. Damage is therefore not a mode-invariant source for a changed set: a set or flag derived from damage would differ across the two modes. Whether today's set touches damage at all is research's question.
- **No new resource, no new exit.** §Occupied Resources → Network ports and listeners · Environment variables · Filesystem · Process-wide state and threads are the registries; the chunk registers nothing in any of them. §Standard Contracts → Dioxus DOM bridge binds the snapshot text to leave the process through the returned value only (recorded PROVISIONAL, pending the founder at the Epoch 3 boundary) and to mask a password's or a file input's value as `MASKED_VALUE`; the diff carries the same content classes and takes the same binding unchanged.

## Patterns to follow
- **A default on the `Document` trait that a wrapper overrides.** §Standard Contracts → Document core records `accessibility_tree()` as a default method `DioxusDocument` alone overrides, and the trait as implemented by six types. Anything this chunk adds at trait level takes a default; a required method lands on all six implementors.
- **Read-only, argument-free readers on `DioxusDocument`, pure functions over `Snapshot`.** §Standard Contracts → Dioxus DOM bridge records `snapshot(&self)`, `unkeyed_actionable(&self)` and `Snapshot::to_text(&self)` in that shape — no document access in the pure half, no failure path, no log, no print, never a panic on an unresolvable node — with `Snapshot` / `SnapshotNode` / `NodeState` all `Debug`, `Clone`, `PartialEq` and `Snapshot::nodes()` / `get(&str)` as the pre-order and by-id readers. That is the comparison surface a before/after diff has without a second reading of any control.
- **One reader per field, never a second computation.** The same bullet requires every snapshot field to come from an existing reader and the actionable check to take ids from `element_ids()` and roles from `accessibility_tree` only. A diff that re-reads a control itself (a value, a name) would break it, and would bypass the mask.
- **A step is harness input plus a pump.** §Standard Contracts → Test harness (`click`, `type_text`, `pump`, `base` / `base_mut`) and → Headless stand (`options(incremental)`, `boot`, `boot_timer` with `TimerTicks::deliver`) are the surface a stand check drives; §Standard Contracts → Document core and §Design Philosophy → Embedder services record that `DioxusDocument` flushes vdom changes at `poll`. Where in that sequence a drain is taken — after the pump that resolves the action — follows from them.
- **Crate docs and visibility.** §Conventions → Visibility and naming (crate internals `pub(crate)` / `pub(super)`; the document's fields sit in that range) and → Documentation (`//!` on a module, `///` on a public item), held by the workspace rustdoc gate in §Conventions → Formatting and lints. A drain that the diff crate calls is a new public item on blitz-dom, documented as one.

## Anti-patterns to avoid
- **Reaching through `DocumentMutator::doc` to mark or read the set** — the escape hatch §Conventions → DOM API patterns asks callers to avoid; extend the mutator and the document's own write sites.
- **An engine or tree identifier in the diff, or a positional assumption about ids.** §Standard Contracts → Dioxus DOM bridge bans `NodeId` / AccessKit id / `ElementId` / `ScopeId` / pointer from the snapshot's fields; it also records that an unkeyed element's stable id changes when an earlier same-tag sibling or a wrapper is inserted before its path starts. A diff keyed by stable id reads such an element as one node gone and one appeared — a consequence to state in the plan, not to paper over with an engine id.
- **A silent change to when the shell's accessibility update fires, or a second consumer starving the first.** §Standard Contracts → Mutation, query and CSSOM records the shell's `update_tree` as called from `View::poll` on `has_changes()` and from `View::build_accessibility_tree` on `InitialTreeRequested`; §Cross-cutting Patterns → Invalidation and state integrity states the intent as "rebuilt on poll when the document changes". The plan records no drain contract and no owner of the set. Once a drain exists, who drains in the windowed shell and who in a headless step is a decision the chunk states — a drain taken by one reader empties the set for the other.
