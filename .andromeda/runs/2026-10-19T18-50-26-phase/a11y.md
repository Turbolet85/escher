# a11y extract

## Relevance
partial — the sync builds no UI, but the `:focus-within` commit (`38ca4e777`) moves engine focus code (`set_focus_to`, `clear_focus`, `clear_interaction_state_for_removed_node`, the Tab arm of `handle_key_or_input_event`, `node.rs` focus state), and focus order is tier-0 a11y surface that must be re-proven on the take.

## Constraints
- a11y-plan §1 A11y Scope Summary sets the tier as `0 — SC 2.1.1 · 1.4.3 · 2.4.3`. The take must leave keyboard operability, contrast and focus order as their standing checks read them, in both layout modes.
- a11y-plan §5 Keyboard Navigation (Focus order) requires the stated focusability rule: not inert (by presence on the element or an ancestor), no disabled form control (`ElementData::is_disabled`), and `tabindex >= 0` or a native focusable element. It also requires the Tab walk (`focus_next_node` / `focus_prev_node`) to skip inert and disabled candidates. Whether upstream's new not-in-document refusal in `set_focus_to`, and the Tab arm's four removed lines, leave this rule and the walk unchanged is research's question.
- a11y-plan §5 Keyboard Navigation (Focus order) records that `:focus` matches while `:focus-visible` and `:focus-within` never match (`packages/blitz-dom/src/stylo.rs:476-478`). If the take carries `38ca4e777`, that reading moves for every document. The plan line then has to be restated at the wrap from the measured site, and `:focus-visible`'s reading needs a fresh check too.
- a11y-plan §5 Keyboard Navigation (Focus restoration) requires two behaviours. Removing the focused node must reset focus to the body and run blur side effects, IME disable included (`interaction_state_teardown`). A pointer click on a button must still focus it through `generate_focus_events` / `set_focus_to`. Upstream changes `clear_interaction_state_for_removed_node`, `clear_focus` and `set_focus_to`. Whether both behaviours hold on the take is research's question. The known limit stays recorded as it is: HTML's focus fixup is not built, so an inert-made node keeps focus until focus moves. If the take changes that, it is a reading to record, not a silent fix.
- a11y-plan §2 A11y Strategy (Accessibility tree lifecycle) requires a focus change to mark the engine's changed set, so the shell's refresh rebuilds the platform tree. The `mutator.rs` conflict resolution must keep our `changed_nodes.insert(parent_id)` in `add_children_to_parent` beside upstream's `focus_within_old_chain`. Upstream's focus-within ancestor state goes through `mark_ancestors_dirty`, and no changed-set entry may be added or lost because of it.
- a11y-plan §6 Visual Design Verification (Color contrast) requires `stand_contrast`'s three tables (18 control rows, 14 `TEXT_ROWS`, 19 `STATE_ROWS`) to be asserted row for row in both layout modes. A row that moves under the newly matching `:focus-within` must be re-measured and recorded, never loosened.
- a11y-plan §9 CI Integration records the `a11y` leg as six files with per-file counts: accessibility_hidden 6 · accessibility_roles 6 · focusability_updates 4 · stand_accessibility_ids 8 · stand_contrast 5 · stand_keyboard 14. That list was widened on the founder's F4. The take's re-read of per-OS tallies must state any moved a11y-leg count.

## Patterns to follow
- Keep focus-order expectations in the stand checks' shared tables `tab_order` and `ENABLED_TAB_ORDER` (`tests/blitz-tests/tests/common/mod.rs`). Read the engine's focus, the snapshot's `focused` node and the tree's focus together at every step (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- Every focus-touching check runs `for incremental in [false, true]`, including `stand_keyboard`, `inert_subtree`, `stand_snapshot_state` and `stand_accessibility_ids` (per a11y-plan §5 Keyboard Navigation, Test harness pattern).
- The snapshot takes `focused` from the focused node of the tree `accessibility_tree` returns, never from selector or element state, with no second mapping (per a11y-plan §7 Screen Reader Support, Accessibility tree output). The take leaves this unchanged, matching the scope's out-of-scope line "the snapshot does not start reading `:focus-within`".
- A moved engine reading is recorded in the plan as "as measured at {chunk}/report.md", with its file:line sites (per a11y-plan §5 Keyboard Navigation, Focus order).

## Anti-patterns to avoid
- Never edit `tab_order`, `ENABLED_TAB_ORDER`, an `inert_subtree` expectation or a `stand_contrast` row to make the take pass. A moved reading is measured, explained and recorded (per a11y-plan §5 Keyboard Navigation, Test harness pattern, and §6 Visual Design Verification, Color contrast).
- Never silently add upstream's `focus_within.rs` or `focus_redraw.rs` to the `a11y` leg, or drop a file from it. The leg's file list is a recorded, founder-widened set (per a11y-plan §9 CI Integration). The two files register as blitz-tests targets under the test plan's rule.
- Never make the snapshot or the accessibility builder read `:focus-within` or the `FOCUS_WITHIN` state as a second focus source (per a11y-plan §7 Screen Reader Support, Accessibility tree output).

## Contract bindings
- a11y ↔ tests: the `a11y` leg (a11y-plan §9) runs inside the workspace and `stand-repeat` legs (test-plan §10). The new upstream targets bind to the blitz-tests target pin `.github/scripts/test_blitz_tests_targets.py` and to the per-OS tallies (test-plan §Per-OS test tallies), not to the a11y leg's list.
- a11y ↔ design: `stand_contrast` rows (a11y-plan §6) bind to design-system §Color Palette. They move only if a stand colour moves, and the stand CSS is stated to use no `:focus-within`.
- a11y ↔ layouts: the Tab sequences `tab_order` / `ENABLED_TAB_ORDER` (a11y-plan §5) bind to layout-templates' focus order per surface.
- a11y ↔ obs/arch: the changed-set and refresh contract (a11y-plan §2) binds to architecture §Cross-cutting Patterns (Invalidation and state integrity) through the `mutator.rs` resolution.
