# tests extract

## Relevance
relevant — the chunk adds pure serializer code (unit tier) and a new stand check (integration tier, agent-run contract), and it records a size figure that a test asserts.

## Constraints
- Test tier is `0` (per test-plan §1 Test tier); the plan sets no breadth mandate beyond the conventions below, so the chunk's breadth is the scope's three properties (completeness, determinism, size), not a tier quota.
- The serializer's unit tests belong inline, in a `#[cfg(test)] mod tests` block of the source file that holds it (per test-plan §4 Conventions; §2 Test directory + naming conventions), and compile under the same default `accessibility` feature the snapshot builder's unit tests compile under (per test-plan §1 Coverage scope, the dioxus-native-dom row). Whether a sibling module would inherit that gating is research's question.
- The stand check is a Cargo integration test, one file per behaviour, in `tests/blitz-tests/tests/`, depending on dev-dependencies only (per test-plan §5 Boundaries covered, the tests/blitz-tests crate row; §2 Test directory + naming conventions). A format whose check needs a parser crate is a manifest change to that dev-dependency set — whether blitz-tests already names one is research's question.
- The file's stem must start `stand_` for `run stand` to select it, and must match the selection pattern; no script change is expected for a new stand file (per test-plan §3 Agent-run contract, `run {selection}` and Proof).
- A stand check asserts unconditionally under the bundled font with system fonts off — no runtime skip path (per test-plan §2 Test levels observed, Font-dependent tests; §8 Real dependencies kept; §9 Pipeline facts, Fonts). The same check runs on the windows and macos matrix legs as well as the linux fast leg (per test-plan §1 Surfaces under test), so a byte-exact or byte-size assertion must hold on all three; whether any serialized field varies by platform is research's question.
- The plan records a line-coverage reading with no threshold and sets no quality gate or performance budget (per test-plan §10, its measured first line only; the rest of §10 is marked and nothing is drawn from it) — the chunk's size budget takes no number from the tests plan and is the chunk's own record.
- The chunk's new tests move the recorded counts — the stand `ok` event count and the workspace passed / failed / ignored and result-line figures (per test-plan §3 Agent-run contract, Proof; §9 Pipeline facts, Local baseline). The report must carry the figures re-counted from the run's own listing; amending the plan's rows is wrap's.

## Patterns to follow
- Stand boot: each lean task booted through `seven_guis::stand::boot` / `boot_timer` with `stand::options(incremental)` — the pinned options and the drive surface later stand checks use (per test-plan §3 blitz-test-harness, Construction; §7 Builders and options).
- Both layout modes: the existing snapshot stand checks cover each lean task in both layout modes, and the differential oracle compares the two documents step by step (per test-plan §1 Coverage scope, the tests/blitz-tests row; §2 Test levels observed, Differential oracle) — the serialized text is asserted identical across the two modes the same way.
- Snapshot unit-test helper: the dioxus-native-dom snapshot unit tests build a `DioxusDocument` from a plain app, run the initial build and resolve through `inner_mut()` before reading the snapshot; that helper's default config carries the no-op HTML parser, so parsed-markup cases are pinned in blitz-tests, not at unit level (per test-plan §3 Crate-local test helpers, the dioxus-native-dom row).
- Prior art for a text form: the harness's `dom_string` is a stable one-node-per-line tree serialization with geometry, described as suited to snapshot-style assertions (per test-plan §2 Test levels observed, Harness-driven tests; §3 blitz-test-harness, Inspection helpers) — an existing in-repo precedent for P4's format fork, not a mandate.
- Expected values as inline literals: fixtures and expected text are inline string constants or `format!`-built values, with no fixture files or loaders (per test-plan §7 Seed strategies, the Inline HTML and Inline literals rows).

## Anti-patterns to avoid
test-plan §11 carries no recorded bans; the entries below are drawn from §2 and §3.
- A skip-on-missing-font or other runtime skip in the stand check — the stand checks have no skip path (per test-plan §2 Test levels observed, Font-dependent tests).
- Treating printed output as the size record: agent-run events carry a test's file, name and outcome only, captured stdout and panic text never reach an event, and raw cargo output stays in `run.log` (per test-plan §3 Agent-run contract, Events and `logs`) — a measured size that must be evidence has to be asserted by the check or recorded by another named route, never read back from an event.
- Assuming a snapshot / golden-file test framework: none was observed in the slice the plan read (per test-plan §3 Runners and invocation, Third-party test frameworks) — whether the workspace carries one elsewhere is research's question; adding one is a dependency decision, not a test convention.

## Contract bindings
- tests ↔ security (the CARRY's crossing fork): a failing assertion that formats the serialized text into its panic message writes stand content into `target/agent-run/run.log` (per test-plan §3 Agent-run contract, `run {selection}` and State) and into `target/ci-logs/{leg}.log`, which CI uploads on failure as an artifact kept 7 days (per test-plan §9 Pipeline facts, Failure logs). That is a route by which ids, names and a text control's value leave the process through the test tier — it belongs in the operator's P4 fork beside "a test's stdout", with security-plan §Input Validation's rows re-read.
- tests ↔ security (password mask): the plan records the stand fixture check that a typed password reads the fixed mask and appears in no snapshot or accessibility-tree field (per test-plan §1 Coverage scope, the tests/blitz-tests row). The serialized text is a new field-carrying surface that claim does not yet name; whether the existing check already covers it is research's question.
- tests ↔ obs: agent-run events are harness metadata, not an escher-telemetry sink, and the stand's log is stderr-only under the allowlist scrub (per test-plan §3 Agent-run contract, Events; §3 Stand log format, binding obs-plan §3) — the serialized text enters neither.
- tests ↔ a11y: the a11y CI leg names three test files (per test-plan §9 Pipeline facts, Legs); a new stand file is not in that leg and runs in the `test` leg only.
- tests ↔ cold-agent pipe: not extended by this chunk — its stub offers only its three toy-counter tools (per test-plan §3 Cold-agent run pipe, The stub); the driver that would put a serialized snapshot in a tool result is out of scope.

## Acceptance criteria contributions
- `cargo test -p dioxus-native-dom` passes with the serializer's inline unit tests added to the crate's lib result line (per test-plan §4 Conventions; §1 Coverage scope, the dioxus-native-dom row).
- `cargo test -p blitz-tests --test {the new stand_ file}` passes: each of the four lean tasks, in both layout modes, booted with the stand's pinned options, asserting completeness, byte-identical repeat serialization and size under the recorded budget, with no skip path (per test-plan §3 blitz-test-harness, Construction; §2 Test levels observed, Font-dependent tests and Differential oracle).
- `bash scripts/agent-run.sh boot` then `run stand` exits 0 with `run.end` outcome `passed`, failed 0, and the `ok` stand events equal to the baseline re-read at this chunk plus the new file's test count, with `scripts/agent-run.sh` unchanged (per test-plan §3 Agent-run contract, `run {selection}` and Proof).
- `bash .github/scripts/ci-leg.sh fast` and `bash .github/scripts/ci-leg.sh doc` exit 0, the workspace counts in the report re-counted from that run's listing (per test-plan §9 Pipeline facts, Local pre-push gate, Legs and Local baseline).
