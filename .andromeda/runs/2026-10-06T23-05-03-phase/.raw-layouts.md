# layouts extract

## Relevance
partial — the chunk creates and modifies no surface, region or focusable element; layout-templates binds it only through the stand screen it serializes (desktop-native, seven_guis TaskShell) and through the CLI output contract its stand check runs under.

## Constraints
- The "stand screen" is one lean task mounted in TaskShell, Home skipped: layout-templates §Surface: desktop-native › Primary screens (the "seven_guis Home and TaskShell" bullet) requires the headless stand to boot Counter, FlightBooker, Timer or Crud through `task_in_shell`, as a header region over a body region. A "whole screen" serialization therefore spans the shell header and the task body, not the task body alone; which of those elements the snapshot tree keeps as nodes is research's question.
- The viewport is pinned: the same bullet requires the stand's fixed viewport size, scale, colour scheme and bundled font, and §Surface: desktop-native › IA notes (the test-harness default bullet) requires the harness default to match it. Every serialized `bounds` value, every measured screen size and every determinism claim holds at that pin only; the budget record states the pin it was measured at.
- The stand's markup is fixed by the plan: the same Primary screens bullet requires that author ids add no class, style, wrapper or order and that no task CSS selects by them, and that the six task inputs are named by attributes alone. The serializer must read the screens as they are; a change to the stand's elements to make a screen serialize smaller or cleaner is outside this chunk (scope: `stand.rs` read only).
- The id set per task is enumerated: the same bullet lists each lean task's controls and value displays by author id and requires that id to be the element's stable element id. That list is the layout-side reference for "every node carries its id"; whether every listed element reaches the snapshot as a node is research's question.
- The CRUD screen's row population is variable: the same bullet requires each row to carry an id derived from its person's model-assigned id, a three-row fixture, and rows that follow their person under filter, Create and Delete. The recorded size is the fixture state's size; whether the budget is also asserted after the list grows is P4's question, since the plan sets no row ceiling.
- The task body scrolls: the same bullet requires TaskShell's body to be a scrolling region, and §Surface: desktop-native › IA notes requires the document element to be the scrolling element with a viewport-relative client area. Whether the snapshot keeps nodes scrolled out of view, and whether their bounds are viewport- or page-relative, is research's question — it decides what "no truncation" means for a screen taller than the pin.
- No CLI surface is added here: §Surface: cli › Primary screens lists the repository's CLI screens and this chunk's entry point is an in-process API (scope: driver, CLI and MCP are Epoch 4–5). A new command, usage line or output screen would be a new entry in that section, not part of this chunk.

## Patterns to follow
- Boot each screen through the existing headless stand path (`task_in_shell` at the pinned viewport) rather than a bespoke fixture — per layout-templates §Surface: desktop-native › Primary screens.
- Read an element's identity from its author id and a CRUD row's from its person-derived id; never from position in the list — per the same bullet.
- Treat the fixed document skeleton (`html` › `head` + `body` › `main#main`, app mounted into `main`) as the tree's ancestry above the shell — per §Surface: desktop-native › IA notes. Whether the snapshot's root sits at the document, at `main` or at the shell is research's question; the serialized form's nesting follows whatever the model reports.
- If the stand check is run through the agent-run contract, its results reach stdout as one JSON object per event with raw cargo output kept in the run log — per §Surface: cli › Primary screens (the `scripts/agent-run.sh` bullet).

## Anti-patterns to avoid
- Adding an element, class, style, wrapper or reordering to a stand task, or selecting by an id in task CSS, to shape the serialized output — banned by §Surface: desktop-native › Primary screens.
- Taking Home, or temp converter / circle drawer / cells, as the "stand screen" the budget is measured on — the plan's headless stand population is the four lean tasks in TaskShell (same bullet).
- Writing the serialized screen text into the agent-run stdout stream as anything other than a JSON-line event — §Surface: cli › Primary screens requires JSON lines only on stdout; whether the text leaves the process at all is the scope's P4 crossing fork, not a layout decision.

## Contract bindings
- layouts ↔ a11y: the six task inputs' names are required to come from `for` / `aria-label` attributes alone (layout-templates §Surface: desktop-native › Primary screens); those names are the `name` field the serialized form carries — binds to a11y-plan's accessible-name coverage.
- layouts ↔ tests: the pinned viewport and the agent-run stdout grammar are layout-plan facts whose schema lives in test-plan §3 (layout-templates §Surface: cli › Primary screens defers the exit grammar and event schema there).
- layouts ↔ security: the enumerated author ids and CRUD row ids are the `id` content class the scope's wire-form crossing concerns (security-plan §Input Validation, the `id` row) — layouts supplies the population, security owns the crossing.
- Focus order: none — the chunk adds no focusable element, so nothing binds to a11y SC 2.4.3 here.

## Acceptance criteria contributions
- (layouts) Each of the four serialized stand screens is produced from a TaskShell boot of one lean task at the pinned viewport, scale, colour scheme and font, and the budget record names that pin (per layout-templates §Surface: desktop-native › Primary screens).
- (layouts) For each lean task, every author id the plan enumerates for that task and for the shell that the snapshot model keeps as a node appears in the serialized text exactly once (per layout-templates §Surface: desktop-native › Primary screens).
- (layouts) The CRUD screen's serialized rows carry the three fixture row ids, each once, in list order (per layout-templates §Surface: desktop-native › Primary screens).
- (layouts) The chunk's diff changes no element, class, style, wrapper or order under `examples/seven_guis/` (per layout-templates §Surface: desktop-native › Primary screens).
