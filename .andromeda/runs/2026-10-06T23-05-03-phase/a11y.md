# a11y extract

## Relevance
partial — the chunk adds no UI surface, key binding, painted colour or focus change, so it triggers none of the tier's three criteria directly (a11y-plan §1: tier 0 — SC 2.1.1 · 1.4.3 · 2.4.3); it is in the domain only because the text it writes is a second reading of what the accessibility tree says about a screen (a11y-plan §7 Accessibility tree output, the snapshot-consumer row).

## Constraints
- a11y-plan §7 (Accessibility tree output, snapshot-consumer row) requires the snapshot's role, name and focused node to come from the tree `accessibility_tree` returns, with no second role or name mapping. The serializer is bound by the same rule one step further out: it writes the model's role and name as given and derives neither from the tag, the attributes or the DOM.
- a11y-plan §7 (same row) requires `enabled`, `checked` and `value` to be read from the element because the tree gives an element node none of the three, and requires a password input to read the fixed marker `MASKED_VALUE` where it holds text and `""` where it holds none, its typed text in no field of the snapshot or of the tree. The serialized form must carry those values from the model and take no second reading of a control.
- a11y-plan §7 (the `author_id` row) requires every element node to carry its stable element id and no `TextRun`, document-root or `Window` node to carry one. The id a serialized node shows is that id; how the form writes a node that has none (or whether the model holds such nodes at all) is research's question.
- a11y-plan §5 (Focus order, the disabled-ness row) records that enabled-ness and focusability are keyed differently: a `disabled="false"` and a bare `disabled` read not enabled yet stay focusable. The form must therefore be able to write one node that is both not enabled and focused; `enabled` and `focused` are independent fields, never collapsed into one token.
- a11y-plan §4 (Hidden content) requires `hidden`, `display: none` and `visibility: hidden` elements and their children to be excluded from the tree, and an `aria-hidden="true"` node to be kept and marked hidden; §5 (Script and framework exposure, the falsy-boolean row) requires an element rendered `hidden: false` to stay in the tree and the snapshot. The serialized node set must equal the model's — nothing excluded reappears, nothing kept is dropped by compaction. Whether the model carries the `aria-hidden` mark at all, and so whether the form has anything to write for it, is research's question.
- a11y-plan §2 (Feature exposure) places the snapshot model behind dioxus-native-dom's `accessibility` feature, and §1 (the Dioxus crates row) records that the workspace takes both Dioxus crates with `default-features = false`, so a crate gets the feature only by naming it. A serializer beside the model sits behind the same gate, and the stand check reaches it only through a crate that names the feature (§1, the blitz-tests row).
- a11y-plan §1 holds the tier's SC 2.4.3 target and §7 (the actionable-key row) records the stand's keys as `id` attributes alone, with no `tabindex`, role, focusability or Tab-order change. The chunk reads the stand and must leave its markup, roles, names and Tab order as they are.

## Patterns to follow
- A11y assertions are Rust tests in blitz-tests over the AccessKit tree, built after `resolve` and matched node by node (a11y-plan §3, A11y testing tool pick); the serialization check belongs in that shape, one file per behaviour, not in a new tool.
- The stand checks compare each snapshot node's role and name to its accessibility node's, on each lean task and in both layout modes (a11y-plan §7, snapshot-consumer row); a serialization check extends the same comparison one step — serialized field against the model's field.
- Focus is put where the check needs it through real input — a pointer click, a Tab press, Shift+Tab — and then exactly the focused control's node reads `focused` and is the tree's focus (a11y-plan §5 Test harness pattern; §7 snapshot-consumer row). A check of the serialized `focused` state follows that route rather than setting focus by hand.
- State is asserted as a readable property, not as colour: the stand's invalid-date cue is checked through the `invalid` class and the Book button's `disabled` attribute (a11y-plan §8 Error recovery). The serialized `enabled` of that button is the same cue in text form and is a natural case for the check.
- A check that types to produce a `value` keeps to keys that act the same on every platform: a11y-plan §5 (Keyboard handling, the macOS row) records that Backspace is left to the Apple standard keybindings there.

## Anti-patterns to avoid
a11y-plan §11 records no bans; the three below follow from the constraint anchors above.
- A role or name table inside the serializer — a short alias computed from the tag, or a name rebuilt from text children — is a second mapping (a11y-plan §7, snapshot-consumer row). Any shortening for compactness is a rewrite of the model's own value, one to one.
- Reading a control again while serializing (its editor text, its `value` attribute) instead of the model's `value`; that path reaches a password's text past the mask (a11y-plan §7, snapshot-consumer row).
- Changing stand markup — a `tabindex`, a `role`, an `aria-label`, a `disabled` — to make a screen serialize smaller or more neatly; each is a11y surface under the tier (a11y-plan §1; §5 Focus order).

## Contract bindings
- a11y §7 (accessible names, control values, the password mask) ↔ security-plan §Input Validation (the `id`, accessible-names and password rows): the names and values this domain defines are the content classes the chunk's first wire form carries. The crossing is the security extract's; this extract only fixes where the content comes from.
- a11y §3 (A11y testing tool pick) and §5 (Test harness pattern) ↔ test-plan §3 harness: the new stand check runs through the same headless harness, in both layout modes.
- a11y §9 (CI Integration) ↔ tests CI: the `a11y` leg runs three named test files and holds no stand assertion; the plan does not require a new stand check to join it, so the new file is gated by the workspace test leg. Whether it should also be named in the `a11y` leg is a plan question, not a mandate found here.
- design-system §Color Palette, layout-templates focus order, obs log format: (none) — the chunk paints nothing, moves no focus, and a11y-plan defines no violation schema to emit.

## Acceptance criteria contributions
- (a11y) On each of the four lean tasks, in both layout modes, every serialized node's role and name equal the role and name of that element's accessibility node, and the serialized node set equals the model's — no excluded element present, no kept element missing (per a11y-plan §7 Accessibility tree output; §4 Hidden content).
- (a11y) Every serialized `enabled`, `checked` and `value` equals the model's for that node; a password input holding typed text serializes `MASKED_VALUE` and the typed text occurs nowhere in the serialized text (per a11y-plan §7 Accessibility tree output). Which screen or fixture supplies the password case is research's question.
- (a11y) At boot no serialized node reads focused; after a focus move made through real input exactly one does, and it is the accessibility tree's focus (per a11y-plan §7 Accessibility tree output; §5 Test harness pattern).
- (a11y) `bash .github/scripts/ci-leg.sh a11y` still passes and the stand's roles, names and Tab order are unchanged by the chunk (per a11y-plan §9 CI Integration; §1 A11y Scope Summary).
