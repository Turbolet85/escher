# security extract

## Relevance
relevant — the chunk builds the snapshot's first wire form, which the plan's three snapshot rows (§Input Validation: `id`, accessible names, password `value`) each record as absent; ids, accessible names and a text control's current text gain a form that can leave the process.

## Constraints
- **The crossing is an operator decision, not a lean.** security-plan §Input Validation (the `id` (stable element id) row and the `aria-label` · `<label for>` row) records the snapshot as an in-process reader with no wire form and the platform accessibility adapter as the id's only exit. A serialized text is a new form for all three content classes (ids, names, `NodeState::value`); through what it leaves the process in this chunk (returned `String` only · a test's stdout or assertion output · a committed evidence or budget record) must be ruled by the operator at P4 before any of the wider exits is built. The plan names no ruling for it yet.
- **The wire form carries the stable element id only.** security-plan §Input Validation (`id` row) requires that neither the id nor the snapshot carry a `NodeId`, `ElementId`, `ScopeId` or pointer; the serialized text inherits that requirement, including for tree structure (parent/child must be expressed by nesting or by stable id, never by a process-local handle).
- **A password's value is the fixed mask, taken from the model.** security-plan §Input Validation (password `input` value row) requires `MASKED_VALUE` for a non-empty password control and `""` for an empty one — never the text, never its length — and that the typed text occur in no id, name or value. The serializer must read `value` from the `Snapshot` it is given and take no second reading of the control. Whether the code at HEAD already masks on every path the serializer will read is research's question.
- **Ids, names and values are content-controlled strings.** security-plan §Input Validation records that accessible names are read from parsed content (remote HTML included, per the names row) and that an author key is any non-empty `id` without `/` (`id` row); a text control's value is whatever was typed. The text form must therefore keep a field's content from forging structure (a delimiter, quote or line break inside a name, value or id must not read as a second field or node). The plan records no escaping rule for a snapshot form; the nearest recorded one is §Input Validation, the `Serialization output | Escaping` row. Which escaping the chosen format needs is P4's, and whether an id, name or value can today hold a line break or the format's delimiter is research's question.
- **A file input's value may be a host path.** security-plan §Data Protection (Local user data handled) records that a chosen file's full path is stored in the file input's `value` attribute. The password row states its mask is password-only and every other element's `value` reads as before, so the plan holds no rule for a file input in the snapshot. Whether the snapshot's value reader reaches that attribute is research's question; if it does, what the snapshot reads there is an operator ruling at P4, beside the crossing.
- **The serialized text is never logged.** security-plan §Logging & Monitoring requires engine telemetry behind each crate's `tracing` feature and records escher's sink as an allowlist scrub in which `value` and `text` are redacted at any target; a serialized snapshot is content of the same class and must not become a log field, a `println!`/`eprintln!` in library code, or an agent-run event field (that section records the agent-run events as carrying no content-named field).
- **A new dependency edge passes the audit and the pins.** If the chosen format adds `serde`/`serde_json` (or any crate) to dioxus-native-dom or blitz-tests, security-plan §Dependency Security requires workspace-inherited versions, a committed `Cargo.lock`, `--locked` builds and a green `bash .github/scripts/ci-leg.sh audit`; that section also records that the audit's reach is cargo-deny's resolved graph, not the whole lockfile, so a new crate is read by hand as well. security-plan §API Security records no served surface or listener; the chunk adds none.

## Patterns to follow
- **The in-process reader shape** (security-plan §Input Validation, `id` row): the existing snapshot and actionable readers take no external argument, resolve nodes through `get_node`, omit what does not resolve, log nothing and never panic. The serializer follows it as a pure function of a `Snapshot` value — no document access, no failure path that panics on content.
- **Values come from one reader** (security-plan §Input Validation, password row and names row): the mask and the name resolution live in the model; the text form copies `SnapshotNode` fields verbatim (after format escaping) so both are inherited rather than re-derived.
- **Records are metadata, not content** (security-plan §Logging & Monitoring, the agent-run and cold-agent rows): committed and event-shaped records carry counts and identities. The size budget's record fits that shape as numbers — the cap it rests on, its unit, each screen's measured size, the headroom — without embedding a serialized screen, unless the operator rules a content-bearing record in.
- **Committed evidence is host-path-masked** (security-plan §Logging & Monitoring, cold-agent row): the one committed raw transcript has its host paths masked; any committed sample of serialized stand content follows the same rule.
- **Raw test output stays under `target/`** (security-plan §Logging & Monitoring, agent-run row): `run.log` and `target/ci-logs/` are recorded as unscrubbed, gitignored and never printed by `logs`; a stand check's assertion output lands there, so that channel is part of what the operator's crossing ruling covers.

## Anti-patterns to avoid
- security-plan §Security Anti-Patterns reads `NO RECORDED INTENT` — nothing is extracted from it; the bans below are read from other sections.
- Never emit the serialized text, or any id · name · value taken from it, as a `tracing`/`log` field or a library-side print (security-plan §Logging & Monitoring).
- Never read a control a second time to fill a serialized `value`, and never write a password's length or a per-character mask (security-plan §Input Validation, password row).
- Never put a process-local identifier (`NodeId`, `ElementId`, `ScopeId`, pointer, slab index) on the wire, including as a parent/child reference (security-plan §Input Validation, `id` row).

## Contract bindings
- **security ↔ obs:** the serialized text is user content under obs-plan §3 and escher-telemetry's scrub sets; the scrub redacts by field name (`value`, `text`, …), so a field named for the snapshot would not be covered — the binding is "no such field exists", not "the scrub catches it".
- **security ↔ tests:** the stand check's stdout and assertion-diff output (test-plan §3, the agent-run contract) is a channel for stand content into `target/agent-run/run.log`, `target/ci-logs/` and CI job logs; fixtures and expected texts carry only the stand's fictitious data and no host path.
- **security ↔ architecture:** the serializer is a new public API beside the model (arch §Standard Contracts) under the `accessibility` feature; no crate, port, socket, listener or env var is added (arch §Occupied Resources). A manifest change for a format crate touches the coupled-pin rule.
- **security ↔ a11y:** the snapshot reads the same accessibility tree and `author_id` the platform adapter carries (a11y-plan §3); a change to what a file input's `value` reads, if ruled, must not alter what the accessibility tree itself exposes without an a11y-plan read.
- **security ↔ wrap:** security-plan §Input Validation rows `id`, accessible names and password `value` each state "no wire form"; this chunk falsifies that sentence. Phase amends nothing — the three rows (and a file-input row, if ruled) are expected wrap amendments, with the operator's crossing ruling as their source.

## Acceptance criteria contributions
- A stand check types a known text into a password input, serializes the screen, and asserts the node's value reads `MASKED_VALUE` and the typed text occurs nowhere in the serialized text; an empty password serializes `""` (per security-plan §Input Validation, password `input` value row)
- Every identifier in each stand screen's serialized text equals a `SnapshotNode.id` of that snapshot; the serializer's input type exposes no `NodeId`, `ElementId`, `ScopeId` or pointer and the text holds none (per security-plan §Input Validation, `id` (stable element id) row)
- The serializer's source holds no `tracing`/`log` macro, `println!`, `eprintln!` or `dbg!` (census 0 over the new code), and no agent-run event field carries serialized content (per security-plan §Logging & Monitoring)
- Any committed record carrying serialized stand content (evidence, budget record, expected text) is within the operator's P4 crossing ruling and holds no host path — census 0 for the dev-host home prefix; if research confirms the file-input reach, the ruled reading for a file input is asserted by a check (per security-plan §Logging & Monitoring, cold-agent row · §Data Protection, Local user data handled)
