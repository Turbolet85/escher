## Goal
0.2.0 ends with one cold-agent run over its new capabilities, judged by the founder's bar (intent §7, v020-11). The
founder chose the stand as the ground and asked that it cover all the checks (inputs#I1). At P4 he confirmed four
things (inputs#I3). F1, «Да, весь стенд (Рекомендую)»: extend the whole stand. F2, «Страница загрузки рядом
(Рекомендую)»: a load page beside the 7GUIs tasks, its request answered in process. F3, «Один запуск, до $3
(Рекомендую)»: one live run, up to $3. F4, «Не больше 5% (Рекомендую)»: at most 5 % of calls wrong.

So the chunk builds three things. First, the stand grows until the driver serves a case for every 0.2.0 check: Cells
(a screen in parts), the flight booker's one-way / return choice as a real `select`, and a load page whose click meets
a load in flight. Second, the cold-agent pipe gets goals that make a fresh agent exercise recording, lint, `advance`,
the load wait, the select and the read in parts, with the founder's bar as a verdict reason. Third, it fires the one
live run on the operator's word.

The engine and the driver do not move (scope Boundaries). The select model, the load wait and the paged snapshot
already stand (arch §Established Decisions → select model; §Standard Contracts → Driver session). The stand is example
code and stays offline: the load page's request is answered by an in-process stand-in through the `NetProvider` seam,
as the fixtures already do (arch §Design Philosophy; test-plan §8).

## Implementation Steps
1. **The flight booker's choice as a controlled `select`** (`examples/seven_guis/src/tasks/flight_booker.rs`:66-81).
   - **The control:** the two `type-btn` buttons `flight-one-way` and `flight-return` give way to one single-choice
     `select` with id `flight-type`, named by `aria-label` "Flight type".
   - **Its options:** two, each with an author id. `flight-type-one-way` has value `one-way` and text "one-way flight".
     `flight-type-return` has value `return` and text "return flight". An option with no author key reads in
     `unkeyed_actionable` (test-plan §1, the select's limits).
   - **Its state:** each option's `selected:` reads the existing `flight_type` signal. An `oninput` handler writes the
     signal through a closed match: the value `return` becomes `"return"`, and every other value becomes `"one-way"`.
     The match never trusts `NativeFormData::valid`, which always reads true (security-plan §Input Validation, Forms).
     This is the controlled-select pattern of `select_interaction.rs`:34-46. A controlled app that writes no `selected`
     sees its choice revert (arch §Established Decisions → DOM semantics).
   - **Its look:** the declared look of the card's date inputs — 15px, `#1a1a1a` on `#ffffff`, `1px solid #c0c0c0`, the
     file's input radius and padding. Its focus cue is the `#3a5ce5` border the date inputs use, since the outline is
     removed ((sampler) visual-design-verification#3.4).
   - **CSS:** the `.flight-type-row` and `.type-btn*` rules go with the buttons, and no CSS selects by an id
     (layout-templates §Surface: desktop-native → Primary screens).
   - **Unchanged:** the dates, the Book button, the invalid and success colours, `aria-invalid`, the booking text and
     the card's shadow and radius (design-system §Color Palette → Semantic Colors; a11y-plan §8).
2. **Cells and the load page served by the stand** (`examples/seven_guis/src/stand.rs`).

     `boot`. Cells joins beside `LeanTask`, never as a fifth variant: 22 `stand_*` files iterate `LeanTask::ALL`
     against four-task tables (research.md §Graph impact).
   - **The load page's markup:** `boot_load(HarnessOptions)` mounts a small page in `TaskShell` titled "Load". Its
     `load-fetch` button "Load" adds a `link rel="stylesheet"` to `http://stand.test/load.css`, as `stand_load_wait`'s
     fixture does (stand_load_wait.rs:35-46). The page also holds a `load-done` paragraph "Loaded", hidden by a class
     the page's own style sets to `display: none`, which the loaded sheet shows. No CSS selects by id.
   - **The stand-in:** the page's boot alone carries one in-process `NetProvider`. It answers each request with that
     sheet's bytes from a thread of its own after 200 ms, as `LateNet` does (stand_load_wait.rs:48-60). It has no
     `is_noop` override, so the harness counts its load (test-plan §8 Network). It holds no `blitz_net`, print, env read,
     socket or listener (arch §Standard Contracts → Headless stand; obs-plan §3).
   - **Every other boot stays offline:** the provider rides only `boot_load`'s options, through `..options(true)`
     (stand_load_wait.rs:66-70). `options` keeps `net_provider: None` for every other caller (27 file names reference it,
     research.md §Graph impact).

## Constraints & rejected approaches
- **A fifth `LeanTask` variant for Cells (or the load page)** — rejected: 22 files iterate `LeanTask::ALL` against
  tables measured for four. Cells' 490 lint findings and its paged screen would break every per-task "0 findings" and
  "under the budget" pin (research.md §Graph impact).
- **A provider in `stand::options` itself** — rejected: 27 files reference it, seven of them non-stand checks. The
  load page's boot alone carries the stand-in.
- **`blitz_net` or a real host for the load** — rejected: the stand names no `blitz_net`, routes no supplied URL
  through the unrestricted `file:` reader and stays offline (security-plan §Input Validation, `file:` URLs; (sampler)
  input-validation#1.35, threat-model-summary#1.1). The founder chose the in-process page (inputs#I3 F2).
- **An `img` or media element as the load** — rejected: a Dioxus image or media event handler reaches an
  `unimplemented!()` conversion ((sampler) error-handling#2.1). A stylesheet is the load `stand_load_wait` proves.
- **A replay of the kept checks by the pipe** — rejected: no command line replays a kept check, `Check::replay` being
  in process only. The acceptance's «passes on replay» is the agent's own check, replayed on fresh children (scope,
  premise-corrected).
- **A new driver verb, argument, cause, session error, span field or log line** to judge the run — rejected: the
  judge reads counts from the `tool_call` lines and the transcript as today (obs-plan §4).
- **Committing a kept check of the live run, or printing `server.log`, `check.json` or the transcript** — rejected
  (security-plan §Data Protection; §Logging & Monitoring).
- **Re-firing the live run** after a failed verdict — rejected without the founder's new word: F3 is one run.
