## Goal
A driver session driven through the command line or the `mcp` role can be kept as a replayable check. Recording is off
unless whoever launches the driver names a recording directory: `escher-session start <task> --session <dir> --record
<dir>`, which passes it on to the host role, or `escher-session mcp --record <dir>`. The directory is created `0700`
or refused when open, and holds one new `0600` file per session. No tool call, verb, argument or result field names
it (founder fork F1 A, delegate, PROVISIONAL).

The kept check is the calls as they crossed in, each with whether it was accepted and a fixed 64-bit digest of the
answer the driver wrote for it. No screen reading reaches the file: no snapshot text, name, value, diff or pixel
(F3 C). The founder's own word may widen F3 to **B** later, keeping each answer whole except a shot's pixels; the form
is built so B adds one key beside `digest`. Text typed into a masked control (a password or file input) is replaced
by one fixed stand-in and the step is flagged `masked`. No byte, length or digest of the secret is kept (F2 B).

Nothing of a recording is logged: no `tracing` call site, no span field, no stderr line (obs-plan §4, §8;
security-plan §Logging & Monitoring).

The recorder lives inside `escher_driver::Session`, so both surfaces and an in-process caller record through one tap.
The same steps recorded over the command line and over MCP give byte-identical checks. `serve` and `serve_mcp` keep
their signatures (research §Graph impact: 0 of their 12 call sites move).

This chunk also ships a strict, bounded reader of the form and proves a recorded stand session replays: read back
and run again on a fresh session through `Session::run`, every step's digest and acceptance match, in both layout
modes. Running recorded checks as ordinary tests under agent-run, CI and stand-repeat, and red on behaviour change,
are the next entry's («Recorded-check replay»).

It also discharges the folded CARRY: a check that a sub-document's carried clock, pan and the fling read the
document's clock (arch §Standard Contracts → Document core; test-plan §1, the clock checks).

2. **The shared argument conversion** — move `call_of` out of `packages/escher-driver/src/mcp/result.rs:17`

3. **The recording module** — new `packages/escher-driver/src/recording.rs`, crate-private, with no `tracing` use. It
   holds:
   - **The digest.** `answer_digest(answer: &Result<Outcome, Refusal>) -> u64` is FNV-1a 64 (offset basis
     `0xcbf29ce484222325`, prime `0x100000001b3`), hand-written, over the UTF-8 bytes of the answer's written form:
     `Outcome::to_json()` or `Refusal::to_json()`. It is written in the file as 16 lowercase hex digits. It is public
     (step 8).
   - **The stand-in.** `MASKED_STAND_IN`, one fixed `&'static str`, which is what a recorded `type` into a masked
     control carries as its `text`.
   - **The form**, one JSON array written by the crate's own `json` module (never `serde_json`). It has two step
     shapes, with keys in this order and no other:
     - The opening record is `{"tool":"start","arguments":{"app":<label>}}`.
     - Every later step is `{"tool":<verb>,"arguments":{…},"masked":true?,"accepted":<bool>,"digest":"<16 hex>"}`.
       `arguments` holds each argument the call carried, by its schema name and its JSON kind, as the MCP server takes
       it. `masked` is present only on a `type` whose target was masked.
   - **The bounds.** `MAX_CHECK_STEPS = 400`, the opening record included (the cold-agent check's step cap, security-plan
     §Input Validation, the Cold-agent check row). `MAX_CHECK_BYTES = 1_048_576`, the answer bound.
   - **The writer.** It creates the file in the recording directory as `check-{n}.json`, `n` the smallest integer
     from 1 not yet present, with create-new and mode `0600`. It never replaces a file it did not create. After every
     recorded step it rewrites the whole array through a `0600` temporary file in the same directory and a rename
     over its own file, so a killed host leaves the steps so far.
   - **The reader.** `Check::from_bytes(&[u8]) -> Result<Check, Refusal>`. Anything outside the grammar is refused
     `malformed`, holding nothing of the file, with no `unwrap`, `expect`, `panic!`, `unreachable!` or index on read
     data (security-plan §Input Validation). It refuses: more than the byte bound; not a JSON array; the opening record not
     `start` with a string `app`; a later step whose `tool` is not one of the seven instance verbs; an unknown key; a
     wrong kind; `masked` on anything but a `type`, or not `true`; `digest` not 16 lowercase hex digits; more than
     `MAX_CHECK_STEPS`. It reads with `serde_json` (a reader only, arch §Driver session) and builds each `Call`
     through step 2's conversion. `Check::app() -> &str` and `Check::steps() -> &[Step]` read it. `Step` has
     `call() -> &Call`, `accepted() -> bool`, `digest() -> u64` and `masked() -> bool`.
4. **The session records** — `packages/escher-driver/src/session.rs` and `packages/escher-driver/src/execute.rs`.
   - **Turning it on.** Add `pub fn recording_into(self, dir: &Path) -> Result<Session, SessionError>`. It creates the
     directory `0700` (its parent must exist) or refuses `SessionError::RecordDirNotPrivate` when it is present and
     open to its group or others. It then creates the check file (step 3) and writes the opening record from the session's label.
     The session holds the recording in a crate-private field with no reader out of the crate, the same shape as
     `seen` (`session.rs:87-92`).

     as one step with its digest. The `type` arm tells the recorder whether its resolved target `is_masked_input`
     (step 1), from the executor's own resolution with no second resolve. That step's `text` is written as
     `MASKED_STAND_IN` and its `masked` as `true`.
   - **When it fails.** If a write fails or a bound would be passed, the recording ends: its file is removed, so no
     truncated check stands, and nothing further is recorded. The session marks `pub fn recording_failed(&mut self) ->
     bool`, which reads true once and then false, for its surfaces to read after the call. The call itself ran, and
     what it did is not rolled back (the `AnswerTooLarge` precedent).

## Constraints & rejected approaches
- A check inside the state directory: rejected by F1 A. It would break `session.sock`-alone and the directory's
  removal at `stop` (`host.rs:80-81`, `stand_session_quiet.rs:70-80`).
- A path named by a tool call or a verb argument: rejected by F1 A, since it gives the MCP client a write-anywhere
  primitive. No `--record` reaches the verb table.
- Keeping a typed secret, its length or a digest of it: rejected by F2 B.
- Any screen reading at rest (snapshot text, names, values, diffs, pixels): rejected by F3 C. Only the digest of each
  written answer is kept.
- `serde_json` as the check's writer: rejected by arch [Driver session]. The reader may use it.
- A new dependency for the digest (`sha2`, `fnv`): rejected. FNV-1a 64 is a few lines, and the dependency set is
  pinned.
- A recorder at each surface: rejected in the dialog. Two taps that must agree would move 12 call sites.
- A `tracing` call site, span field or log line for any recording event, the check's path or a count of its steps:
  never (obs-plan §4; the founder's 2026-10-09 ruling allows a diff's sizes only).
- A truncated check left standing after a failure: never. The file is removed and the call answers
  `recording-failed`.

## Implementation notes
- **What is at rest, exactly.** The calls as they crossed in, so a `click`'s target id, a `press`'s key, an
  `advance`'s `ms` and a `type`'s text into an unmasked control are kept. A masked control's text is never kept.
  Beside each call the file holds its acceptance and its answer's digest, and no screen reading. The call arguments
  are what a replay needs and what the next entry re-validates. On the operator's word at the P5 review (inputs#I3),
  F3 C covers answers only. The calls kept as they came in are the F1/F2 widening itself and stay PROVISIONAL with
  them:
  - target ids;
  - the `press` key;
  - the `advance` ms;
  - text typed into unmasked inputs.
- **F3 may widen.** The founder's own word may widen F3 to **B**: each answer whole as the driver wrote it, a shot's
  pixels excepted. The form leaves room: B adds an `answer` key after `digest`, and the reader takes it then. Until his
  word, no answer text is kept.
- **Determinism the digest rests on.** A whole shot's PNG is byte-identical across processes (CLAUDE.md, the headless
  screenshot); `advance` moves the one clock by exactly `ms`; `scroll` is instant (`blitz-test-harness/src/input.rs:240`).
  So an unchanged app replays every digest, the shot's included. The CARRY's pan and fling are not reached by any
  driver call; their check is the engine's own proof (scope.md §Freight).
