## Goal
An acting driver command that meets a load in flight waits it out within a stated bound. The acting commands are
`click` · `type` · `press` · `advance` · `scroll` on every carrier: in process, the socket, the command line and MCP.
Today the instance settles once, and a counted request still in flight reads
`settled: false, busy: "loads"` at once (packages/escher-driver/src/execute.rs:461-466;
packages/blitz-test-harness/src/settle.rs:163-170), so a caller has to poll an app that loads over the network.
After this chunk the driver keeps re-settling while the only work outstanding is a load. It returns `settled` as
soon as the load is answered and the screen goes quiet. If `LOAD_WAIT` passes first, it returns with today's
`busy: "loads"` reading.

`LOAD_WAIT` is a fixed **5 s**, the operator's answer «5 s (Recommended)» at this P4. It is a public constant
re-exported beside `IDLE_EXPIRY`, and the `settled` field's help states it. That help is the program's own fixed
table text on the ratified carriers, per the playbook's fixed-text rule, set by the founder on 2026-10-12.

The wait moves no virtual time. It measures wall time between settles, sleeping a short poll. It never ticks the
harness, never runs the session's time step and never drains the changed set. So `advance` stays the one mover of
the session's clock, a rule ratified by the founder on 2026-10-18 (per arch §Standard Contracts → Driver session;
design-system §Motion §Animation runtime; a11y-plan §5).

`Harness::settle` is untouched: it still reports a load at once and reads no clock (per arch §Standard Contracts →
Test harness).

No verb, argument, result field, `Outcome` variant, refusal cause, session error, exit status, span field, env read,
listener or dependency is added. The bound sits well under every 30 s reply bound that reads a call's answer (per
security-plan §API Security, «Settle and loads in flight» and «Local session socket» rows).

The capability is proven on an in-file fixture held in a session, in both layout modes:
- a body stylesheet answered by a stand-in on its own thread after 200 ms ends the wait settled, with its styled
  box changed in the returned diff;
- the same request never answered (`fixtures::HeldNet`) ends the wait at the bound with `busy: "loads"`.

## Implementation Steps
1. **The waiting settle, once, in `packages/escher-driver/src/session.rs`.**
   - Add `pub const LOAD_WAIT: Duration` (5 s) with a doc line saying what it bounds.
   - Add a crate-private function that settles the held harness through `Harness::settle` and, while the result is
     `Err(NotSettled { busy: Busy::Loads })` and the wall time since the function began is under `LOAD_WAIT`,
     sleeps a short fixed poll (a private const of 10 ms) and settles again.
   - It returns the first result that is not `Loads`, or the last `Loads` result once the next poll would pass the
     bound.
   - It stops at the deadline: it never sleeps past `LOAD_WAIT`, so the wait ends within one settle of the bound.
   - A `Render` or `Layout` result returns at once, unchanged.
   - Write the loop as a generic inner function over a settle closure, a bound and a poll, so its unit tests can
     drive it with a scripted closure and a short bound. The harness-facing function calls it with `LOAD_WAIT` and
     the poll.
   - The function reads `std::time::Instant` and calls `std::thread::sleep`. It does nothing else: no harness
     `tick`, no `advance_time`, no `TimeStep`, no `take_changed_nodes`, no print, no `tracing` call.
2. **`Session::act` settles through it** (packages/escher-driver/src/session.rs:196-204). Its doc moves from
   «Settling moves no time» to say the step is settled, and that a load in flight is waited for up to `LOAD_WAIT`
   while no time moves.
3. **`settled_step` settles through it** (packages/escher-driver/src/execute.rs:453-470).
   - All five acting verbs reach it: `acted` and the `advance` and `scroll` arms (graph: `settled_step` has 3
     callers, all in `execute.rs`).
   - `passes` stays recorded on `Ok` only. On a waited step it is the passes of the settle that went quiet.
   - The doc at :126 moves from «Settling moves no time and waits on no load» to «Settling moves no time; a load
     in flight is waited for up to `LOAD_WAIT`».
4. **State the bound in the schema** (packages/escher-driver/src/schema.rs:117-122). The `SETTLED` field's help
   becomes: whether the app went quiet after the step, with a load in flight waited for up to 5 s. It is written as
   fixed text, as the double click's «within 500 ms» is (schema.rs:192-194).
5. **Pin text against value** in `packages/escher-driver/src/schema_tests.rs`. Add one unit test asserting:
   - the `settled` field's help names `LOAD_WAIT` in seconds as the text states it;
   - `LOAD_WAIT` is under `ANSWER_BOUND`, the client's 30 s read, which is crate-private in `wire.rs`, so the pin
     reads it in crate.
6. **Re-export `LOAD_WAIT`** in `packages/escher-driver/src/lib.rs`, in the `session` line beside `Session`. The
   crate root's re-exports go from 55 to 56.
7. **Unit tests of the wait** in `session.rs`'s test module, driven through the generic inner function with a
   scripted settle closure:
   - (a) `Loads` twice and then `Ok` returns that `Ok`, after three settles;
   - (b) `Loads` on every call, with a 50 ms bound, returns `Loads`, its elapsed time at least the bound and under
     the bound plus one second;
   - (c) a `Render` result returns at once after one settle, without sleeping;
   - (d) an `Ok` returns after one settle.
8. **The check `tests/blitz-tests/tests/stand_load_wait.rs`**, both layout modes, every reading through
   `Session::run`. It declares `mod fixtures;` and `mod session_common;`.
   - **The fixture page, in-file:** one reader, so it stays in its check's file (test-plan §3 fixtures rule).
     - A button `fx-load` whose click renders a body `link` with `rel="stylesheet"` and
       `href="http://load.test/late.css"`.
     - A box `fx-box` whose height only that sheet sets; it reads zero height before the sheet.
     - Every element read carries an author `id` (layout-templates §Surface: desktop-native).
   - **The boot, in-file:** `Session::start` over `Harness::from_vdom` with `HarnessOptions { net_provider:
     Some(…), ..stand::options(incremental) }`. The stand's options are offline, and `fixtures::hold` takes no
     provider (research.md §Files inspected, stand.rs:57-65).
   - **The stand-in that answers on its own, in-file:** a `NetProvider` whose `fetch` spawns one thread per request.
     The thread sleeps 200 ms and then answers the handler with the sheet's bytes (`NetHandler` is
     `Send + Sync + 'static`, blitz-traits/src/net.rs:34). It overrides no `is_noop`, so the harness counts its
     loads. It holds no print, `tracing` call, env read, file, socket or listener.
   - **Arm 1, answered inside the bound:**
     - `click fx-load` returns `Acted` with `settled == true` and no `busy`;
     - its diff names `fx-box` changed with `bounds` in `differs`;

     - the wall time the call took is under `LOAD_WAIT`;
     - `session.harness().time()` reads the same before and after the call.
   - **Arm 2, never answered** (`fixtures::HeldNet`):
     - `click fx-load` returns `Acted` with `settled == false` and `busy == Some(Busy::Loads)`;
     - the wall time the call took is at least `LOAD_WAIT` and under `LOAD_WAIT` plus 2 s;
     - `HeldNet::held()` reads 1;
     - the harness's `time()` is unchanged.
   - Failure messages name a mode and an arm only, never an id, a URL or a screen reading (security-plan §Input

## Constraints & rejected approaches
- A wait inside `Harness::settle` — rejected. It would amend the test-harness contract (settle reads no clock and
  waits on no load) for every harness caller, where research found two production callers that both sit in
  escher-driver.
- A bound taken from the call, an env var or a file — rejected. That is a new input on the validated surface or a
  new env read (security-plan §Input Validation; §Secret Management).
- A wall read in blitz-dom, or moving the `VirtualClock`, the time step or the fade during a wait — rejected: it
  reopens the one-virtual-clock ruling, ratified by the founder on 2026-10-18.
- Draining or reading the changed set inside the wait — rejected (a11y-plan §2, the changed-set contract).
- A thread in the host or the `mcp` role for the wait — rejected. The wait runs on the calling thread
  (arch §Occupied Resources → Process-wide state and threads).
- Widening `fixtures::HeldNet` or adding the self-answering stand-in to `fixtures/mod.rs` — rejected. It has one
  reader, so it stays in its check's file (test-plan §3, the one-reader rule).
- An image as the fixture's load — rejected in favour of a stylesheet: no decode, and the same counted path
  `stand_settle` proves.
- A `has_changes()` witness of the load — rejected. A CSS or image load marks no changed node; the 6
  `changed_nodes.insert` sites are listed in research.md §Sweeps. The diff's `bounds` is the witness.
- A waited-time, «waited» or bound field on the `command` or `tool_call` span — not built: no ruling (obs-plan §4).
