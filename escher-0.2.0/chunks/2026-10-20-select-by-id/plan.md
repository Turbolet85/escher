## Goal
An agent drives a single-choice `select` by its stable id, like any control, and reads it in the snapshot with its
role, its name and its chosen value, its Tab stop unchanged (v020-08; intent §6 «Ready for a real app»; the residual
«no `select` interaction model», absorbed).

Research measured a `select` as nothing the driver can reach (research.md §Measured; `evidence/select-probe-readings.txt`):
it lays out 0×0 with every `option` `display: none`, reads no client rect, and so is left out of the snapshot; the tree
holds it as an empty `ComboBox`, a `<label>` names it not, and it takes no key. The operator answered the four founder
forks with their recommendations, as delegate, PROVISIONAL for the founder's own word (inputs#I2): the engine, in every
document, shows a select's chosen option as its content (F2), reads its options as its children in the tree and the
snapshot (F3), lets a focused select choose by the arrows, `Home`, `End` and typed prefix and focuses it on a click
(F1), fires `input` then `change` on each choice and binds a `<label>` to every labelable element HTML names (F4). No
driver verb, argument, key name, result field, refusal cause, exit or log field is added: an agent chooses with
`type --id <select> --text <label>` in one call, or `click --id` then `press arrow-down`.

The choice is held the way the radio group already holds one: as the `CHECKED` element state on the chosen option,
written through `snapshot_node_and`, which restyles `:checked` and marks the changed set (document.rs:735, :1660-1662;
stylo.rs:470). HTML says a chosen option matches `:checked`, so a user-agent rule shows exactly that option inside the
select's box, and layout needs no special code (per arch §Established Decisions → [Scrolling and input], the range
model's shape; arch §Design Philosophy, behave like a browser, cite the spec).

## Implementation Steps
1. **The select's rules** — new `packages/blitz-dom/src/node/select.rs`, cited to the WHATWG `select` element. Pure
   reads over the document, unit-tested inline over stated tables:
   - a select's **options**: its `option` children in tree order (an `optgroup`'s options are not listed — a stated
     limit, step 17);
   - its **chosen option**: the option carrying `CHECKED`;
   - its **value** (HTML's `select.value`): the chosen option's `value` attribute, else its text with ASCII whitespace
     stripped and collapsed; `None` with no chosen option;
   - an option's **label**: its `label` attribute when not empty, else its text, stripped and collapsed;
   - **the selectedness setting algorithm** for a single-choice select: none chosen → the first option that is not
     disabled; two or more → the last of them;
   - **a step**: next / previous option that is not disabled, first / last such option;
   - **a typeahead match**: the first option in order, not disabled, whose label starts with the typed text,
     compared case-insensitively (ASCII and Unicode simple lowercase).
   Declare the module in `packages/blitz-dom/src/node/mod.rs`.
2. **Seed the choice from the markup** — `packages/blitz-dom/src/node/element.rs`, beside the checkbox mirror at
   element.rs:443-452: an `option` created with a `selected` attribute carries `CHECKED`.
3. **Show the chosen option** — `packages/blitz-dom/assets/default.css`:
   - `select` takes `display: inline-block` and the border, padding and background `input` takes (default.css:75-80);
   - beside `option { display: none; }` (default.css:146-148), `select:not([multiple]) > option:checked` takes
     `display: inline`, so the chosen option's own text lays out as the select's content.
   **Measure this first**, before steps 4-16 build on it: on a page holding the step-17 fixture's selects, in both
   layout modes, a select reads a client rect at least as wide as its chosen label, and moving `CHECKED` to another
   option (through `snapshot_node_and`, as `toggle_radio` writes it) restyles it so the new label lays out. Record the readings in
   `evidence/checked-mechanism.md`. If the restyle does not follow the state, stop and report — the mechanism is the
   plan's premise.
4. **Re-seed on markup changes** — `packages/blitz-dom/src/mutator.rs`: a `selected` write or clear on an `option`
   whose parent is a `select` (beside the range re-seed at mutator.rs:367-378 and :490-500), and an `option`'s
   insertion under or removal from a `select` (`append_children` :707, `insert_nodes_before` :713,
   `insert_nodes_after` :841, `replace_node_with` :857, `remove_node` :590, `remove_and_drop_node` :614), record that
   select; the mutator's flush runs step 1's selectedness algorithm once per recorded select. A `selected` write sets
   that option chosen (the app keeps control, as a range `value` write does); every `CHECKED` write goes through
   `snapshot_node_and`. Fires no event.
5. **One write · mark · events · redraw path** — `packages/blitz-dom/src/events/keyboard.rs`, beside
   `apply_range_move` (:238): `apply_select_choice(select, option, dispatch_event)` clears `CHECKED` on the old chosen
   option and sets it on the new one through `snapshot_node_and` (as `toggle_radio`, document.rs:722-741), marks
   ancestors dirty, dispatches `Input` then `Change`, both carrying the select's new value, and requests a redraw. A
   choice of the option already chosen does nothing and fires nothing.
6. **Keys and typeahead** — `packages/blitz-dom/src/events/keyboard.rs`, a select arm in
   `handle_key_or_input_event` beside the range arm (:99-104), gated on the focused element being a `select` with no
   `multiple` that `ElementData::is_disabled` reads enabled, on a pressed `KeyPress`; its body a private
   `press_select_key`:
   - `ArrowDown` / `ArrowUp` → the next / previous option; `Home` / `End` → the first / last (step 1's step);
   - a `Key::Character` with no Ctrl, Alt or Meta held (Shift allowed) → typeahead: the text joins the document's
     typeahead buffer — which starts afresh when it belongs to another select or when 1 s of the document's clock
     (`Clock::now`, clock.rs:18) has passed since its last character — and the first option step 1 matches is chosen;
     no match changes nothing;
   - every other key does nothing (Enter and Space open nothing: no popup).
   The buffer lives on `BaseDocument` (`packages/blitz-dom/src/document.rs`): the select it belongs to, its text and
   the clock reading of its last character.
7. **A click focuses a select** — `packages/blitz-dom/src/events/pointer.rs`, a `select` arm in `handle_click`'s walk
   beside the `label` arm (:858-866) and the button arm: focus it through `generate_focus_events` / `set_focus_to`,
   as `click_button` does, clear the typeahead buffer and any text selection the click made inside it. The walk's
   disabled gate stops a disabled select first, as it does a button.
8. **The `change` event** — `packages/blitz-traits/src/events.rs`: `DomEventKind::Change` (`from_str` "change",
   :190-210) and `DomEventData::Change(BlitzInputEvent)` with its `name` and `kind` arms (:268-310, :340-350).
   `packages/dioxus-native-dom/src/dioxus_document.rs` hands `Change` to the app as `NativeFormData`, as `Input`
   (:377-380). `packages/blitz-vibey-script/src/runtime.rs` dispatches a real `Change` as its `change` event and keeps
   its own synthesized `change` for a checkbox or radio (:1671-1687) — never two for one choice. Every exhaustive
   match the new variant breaks gains its arm (the compiler names them).
9. **A `<label>` names every labelable element** — `packages/blitz-dom/src/document.rs`,
   `label_bound_input_element` (:678-703): both arms (`for`, and the first nested descendant) match HTML's labelable
   elements — `button`, `input` whose `type` is not `hidden`, `meter`, `output`, `progress`, `select`, `textarea` —
   in place of `input` alone; its name and signature unchanged. Its two callers move with it: the tree's label loop
   (accessibility.rs:53) and `handle_click`'s label arm (pointer.rs:860), which then focuses a select through step 7.
10. **The options in the tree** — `packages/blitz-dom/src/accessibility.rs`: `is_hidden_from_accessibility_tree`
    (:244-257) keeps an `option` whose parent is a `select` although it computes `display: none` (`hidden` and `inert`
    still exclude it); such an option's node writes `selected` from its own `CHECKED` state, true or false, its
    `aria-selected` unread there (HTML-AAM: a native option's selectedness is its state). The role mapping stays
    (`ComboBox`, `ListBoxOption`, accessibility.rs:472-476).
11. **Form submission** — `packages/blitz-dom/src/form.rs`: the select step at form.rs:270-274, a named select's
    chosen option's value as its entry, the option not disabled.
12. **The snapshot** — `packages/dioxus-native-dom/src/snapshot.rs`:

      reader; its signature takes the node so `Builder::visit` (:170) can pass it;

    No role or name is mapped here (a11y-plan §7: the tree's own).

## Constraints & rejected approaches
- A new driver verb or argument to choose — rejected by F1's answer: `type` and `press` reach the engine's own keys.
- A `SpecialElementData::Select` variant — rejected: the choice lives as `CHECKED` on the options, which the radio
  group already writes and `:checked` already reads; an enum variant is a source break for nothing.
- Special layout code painting a label — rejected: the user-agent rule shows the chosen option's own text.
- A popup, a windowed list or an option made clickable — not built (scope §Boundaries; F3 says an option is not
  clicked).
- An option made focusable, or `aria-activedescendant` read — rejected without a ruling (a11y-plan §5; the founder's
  F2 of 2026-10-14).
- A wall read for typeahead — rejected: the document's clock alone (arch, the document clock).
- Moving a select into the shared fixtures module or a stand task — rejected: one reader each; the stand stays as built.
- A role or name mapped in `snapshot.rs` — rejected (a11y-plan §7: no second mapping); only the value and an option's
  bounds are read there.
- A `change` event for a checkbox, radio or text input — not built here: F4 asked for the select; vibey-script's own
  synthesis stays the checkbox's.
