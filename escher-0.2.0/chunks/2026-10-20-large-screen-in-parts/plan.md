## Goal
A screen whose snapshot text passes `SNAPSHOT_TEXT_BUDGET` (10,000 bytes) is read by an agent in parts it can walk.
Today `snapshot` answers such a screen whole on every carrier, held only by the 1,048,576-byte answer bound
(research.md §Measured). On the founder's word (inputs#I2 — F1 «Аргумент part, части по умолчанию (Рекомендую)»,
F2 «Пустая часть (Рекомендую)», relayed by the overseer), `snapshot` gains an optional `part` argument, a whole number
of a new argument kind. Over the budget, `snapshot` with no argument answers part 1. A paged answer adds two count
fields, `part` and `parts`. A part past the last answers an empty text with the same two fields, and no new cause is
added. A screen inside the budget, asked with no argument, answers exactly as today.

A part is a run of consecutive lines of `Snapshot::to_text`, cut at line boundaries, at most the budget in bytes. The
parts concatenated in order are the whole text, so each node's line appears exactly once and byte-equal to its line in
the whole snapshot (research.md §Measured; a11y-plan §7 Screen Reader Support). The cut is a pure reader of the
snapshot model in dioxus-native-dom beside `to_text` (arch §Standard Contracts → Dioxus DOM bridge). The walk runs
through `Session::run` after `validate` like every instance verb (arch §Standard Contracts → Driver session;
security-plan §Input Validation, Driver command schema row). It therefore reaches the socket, the command line, MCP
and a kept check with no new verb, carrier, cause, exit or log field: the `command` span records `verb` alone for a
part read (obs-plan §4).

The proof is a fixture page over the budget, in both layout modes. It is driven through `Session::run` and through
`serve_mcp` in process, and its spelling is checked on every carrier on the lean stand (verification-matrix.json#v020-09).

## Implementation Steps
1. **The part cut** — in `packages/dioxus-native-dom/src/snapshot_text.rs`, beside `Snapshot::to_text`, add a public
   pure method `Snapshot::text_parts(&self, budget: usize) -> Vec<TextPart>`. `TextPart` is a new public struct holding
   `text: String` and `ids: Vec<String>`: the lines of its nodes, then their ids in pre-order. Lines are written by the
   same `write_line` as `to_text`. A part takes consecutive nodes of `nodes()` pre-order while its text stays at most
   `budget` bytes. A node's line is never split: a line longer than `budget` is a part alone and stands over it (a
   stated limit, step 4). A snapshot with no nodes is one empty part, so there is always at least one part. The
   function has no document access, no failure path, no log and no print. Its doc states the equality the cut keeps:
   the parts' texts concatenated in order are `to_text()`. Amend `SNAPSHOT_TEXT_BUDGET`'s doc, whose "never truncates
   or pages" stays true of `to_text`, to name `text_parts` as the reader that cuts the text into parts within it.
2. **Its unit tests** — in the same file's `mod tests`, over hand-built snapshots, assert:
   - parts concatenate to `to_text()` for a budget that cuts several times, and each part is at most the budget;
   - each node's id is in exactly one part's `ids`, in pre-order;
   - one node's line longer than the budget is a part alone;
   - an empty snapshot is one empty part with no ids;
   - a budget at least the whole text gives one part equal to `to_text()`;
   - a cut falls between two lines, never inside one: every part's text ends in `\n`.
3. **The re-export** — `packages/dioxus-native-dom/src/lib.rs` re-exports `TextPart` beside `SNAPSHOT_TEXT_BUDGET`
   (lib.rs:39), under the same `accessibility` gate as the snapshot model (arch §Cross-cutting Patterns → Config
   management).
4. **The schema** — in `packages/escher-driver/src/schema/spec.rs`, add `ArgKind::Part`, named `part` and bound "a
   whole number from 1 to 1000". In `packages/escher-driver/src/schema.rs`, add `pub const MAX_PART: u32 = 1000;`
   beside `MAX_MILLISECONDS` and give `SNAPSHOT` one optional argument `part` of kind `Part`. Its help: "the part of the
   screen to read, counted from 1; a screen over the budget is read in parts without it from part 1". Add two result
   fields after `text`: `part` (`FieldKind::Count`, `always: false`), "the part this answer holds, present when the
   screen is read in parts", and `parts` (`Count`, `always: false`), "how many parts the screen reads as, present with
   `part`". Rewrite `SNAPSHOT`'s help and `text`'s help to state:
   - a screen whose text is over 10,000 bytes is read in parts, each a run of whole lines of at most 10,000 bytes, and
     the parts in order are the whole text;
   - with no `part`, a screen over the budget answers part 1, and one inside it answers whole with no `part` or
     `parts`;
   - a part past the last is the empty text;
   - one element's line longer than 10,000 bytes is a part alone and longer than the budget;
   - each part is read from the screen as it stands, so a step between two reads gives parts of the new screen.
   `MAX_PART` is re-exported with the other bounds in `packages/escher-driver/src/lib.rs` (:154-158).

7. **The read** — in `packages/escher-driver/src/execute.rs`, add `Outcome::Part { text: String, part: u32, parts:
   u32 }`, documented as what `snapshot` returns when the screen is read in parts. The `Command::Snapshot { part }` arm
   takes the screen once through `read_screen` (execute.rs:331), which records every id of the screen as today, then:
   - with `part` `None` and `to_text()` at most `SNAPSHOT_TEXT_BUDGET` bytes → `Outcome::Screen { text }`, exactly as
     today;
   - otherwise → `text_parts(SNAPSHOT_TEXT_BUDGET)`. Take `n` = `part` or 1, and `parts` = the parts' count. When `n`
     ≤ `parts`, answer `Outcome::Part` with part `n`'s text. When `n` > `parts`, answer `Outcome::Part` with the empty
     text.

   The record takes the whole screen's ids, as `snapshot` and `lint` do. Every acting call already records the whole
   screen before it resolves its id (execute.rs:378-382), so a part-only record would change no `stale` or `not-found`
   reading (see Provenance). The part count can pass `u32` only far beyond the 1,000-part bound, so it is converted with
   `try_from` and saturates rather than panicking. `record_result` (execute.rs:276) adds `Outcome::Part { .. }` to the arm that
   records nothing beyond `verb`. `Session::run`'s doc gains one sentence on the part read. A part read runs no step,
   settles nothing and waits on no load, as `snapshot` does (arch history 2026-10-20-load-wait).

## Constraints & rejected approaches
- A new verb for a part — rejected by the founder's F1 (inputs#I2); `VERBS` stays twelve.
- A ninth refusal cause for a part past the last — rejected by the founder's F2 (inputs#I2); `CAUSES` stays eight.
- A held cut, or a cursor kept in the session between part reads — rejected. Each part read cuts the screen as it
  stands, because a `snapshot` read changes nothing (research.md §Measured), and a held cursor is state that a `NodeId`
  or a call-supplied token could leak through (security-plan §Input Validation, Driver command schema row).
- Repeating a part's ancestors at its head for context — rejected, because a node would then be read twice
  (v020-09's "exactly once"). A part's first line keeps its absolute indent.
- Changing `Outcome::Screen`'s fields — rejected for the new variant, since a changed variant moves 14 patterns
  (research.md §Sweeps).
- No field on the `command` or `tool_call` span for a part's number, count, size or text (obs-plan §4; security-plan
  §Logging & Monitoring).
- No stand task gains nodes, and Cells is not mounted in the lean boot (layout-templates §Surface: desktop-native →
  Primary screens).

## Implementation notes
- The fixture's size: 400 buttons named "Item nnn" with ids `item-nnn` write about 55 bytes per line. This is an
  estimate from the line form `snapshot_text.rs:57-92` writes, not a measurement, so step 12's first assertion reads
  the real size. Expect about 22 KB, three parts. The check asserts invariants, never a part count or a byte size: a
  part's bytes differ by runner, because `writing-mode` is on only in the workspace build and moves `bounds`
  (test-plan §9 Engine features by runner).
- `item-400` is below the 800 × 600 viewport, so its `click` alone would be refused `off-screen`; step 12 scrolls it
  first. That is the proof that an id read only in a later part is addressable as one read whole.
- The record of ids holds at most 4,096 (`session.rs:67`). The fixture's ~404 ids stay under it, and a screen past it
  forgets its oldest ids as today.
- Not paged, a stated limit: an acting verb's diff and a lint's findings have no budget of their own. On a large
  screen either can pass 10,000 bytes, held only by the 1,048,576-byte answer bound (research.md §Measured).
