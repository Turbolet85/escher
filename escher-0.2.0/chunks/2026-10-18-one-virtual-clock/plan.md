## Goal
In a headless run, every time the engine reads comes from one clock that only the driver moves, so two shots of one state read the same pixels (v020-06; intent §5, C1; the residual `absorbed:v020-06`). Today blitz-dom reads the wall clock directly in five places: the overlay scrollbar fade, double-click detection, the smooth-scroll start and frame, the fling frame and pan timing (research.md §Files inspected). CSS animations and transitions already read the time `resolve(time)` is handed (`stylo.rs:135`).

The founder forks were answered by the operator as delegate, PROVISIONAL (inputs#I2):
- **F1 B:** a document reads its time from a clock the embedder supplies through `DocumentConfig`, the wall clock by default. Every windowed and embedder-built document keeps today's behaviour. The headless harness supplies a virtual clock whose time is the harness's own, so `resolve(time)` and every engine read are one clock.
- **F2 A:** the driver's `advance --ms N` moves that clock by exactly N on every session, then hands N to the app's time step where one was handed. `advanced_ms` reads N.
- **F2b A:** `time-unavailable` is retired, and the refusal set closes at eight causes.
- **F3 A:** the 500 ms double-click window reads the one clock, so two driver `click`s on one point with no `advance` between them are a double click.

The technical forks were answered by the operator in the P4 dialog:
- one 800 ms sleep between two shots, the stand checks' single recorded no-sleep exception;
- the proof on the stand's CRUD list;
- all five reads through the clock.

Provenance: arch §Design Philosophy ("Embedder services are injected, with no-op defaults") and §Standard Contracts (Test harness, Driver session, Headless stand); security-plan §Input Validation (Driver command schema row) and §API Security (Settle and loads in flight); design-system §Motion; test-plan §2 Pixel tests, §3 Core, §5, §8 Time row, §10; obs-plan §3, §4; a11y-plan §5, §9.

## Implementation Steps
1. **The clock type** — new `packages/blitz-dom/src/clock.rs`:
   - A `Clock` trait (`Send + Sync`) with one method returning a monotonic `Duration` since the clock's own origin.
   - `WallClock`, which reads `web_time::Instant` against an origin taken when it is made.
   - `VirtualClock`, a cloneable handle onto one shared `Duration` (an `Arc` over an atomic or a mutex). It starts at zero, and only its `advance(Duration)` moves it.
   - Inline unit tests: a `VirtualClock` reads zero, then exactly the sum of what it was advanced by, and every clone reads the same. A `WallClock` never reads less on a later read.
   - Re-export `Clock`, `WallClock` and `VirtualClock` from `packages/blitz-dom/src/lib.rs`.
2. **The config field** — `packages/blitz-dom/src/config.rs`: `DocumentConfig` gains `clock: Option<Arc<dyn Clock>>`, documented as wall time when `None`, set to `None` in the hand-written `Default`. `BaseDocument` (`packages/blitz-dom/src/document.rs`, beside `subdocument_depth`, ~263/499) holds an `Arc<dyn Clock>`: the config's, else a new `WallClock`. ## Constraints & rejected approaches
- One clock from `resolve`'s time in every document (F1 A): rejected by the delegate's answer. It would also stall every wall-clock `HtmlDocument` check that drives a smooth scroll by `resolve(0.0)` in a loop (`fragment_navigation.rs:31-43`).
- A second clock beside the harness's: never. The harness's `time()` and the document's clock are one `VirtualClock` (arch extract, anti-patterns).
- A wall-clock read in escher-driver: never. The executor moves the harness's value and reads none (obs-plan §3; security-plan §Input Validation).
- Retuning `FADE_DELAY`, `FADE_DURATION`, the 300 ms smooth curve or the fling constants to make a shot repeat: never. Determinism comes from the clock (design extract).
- Routing a driver `scroll` through the smooth path to exercise the clock: never. The instant driver scroll is ratified (design-system §Motion).
- A stand markup change to show a scrollbar: never. The CRUD list after twelve Creates is the measured scene (layout-templates §IA notes).
- A time, clock reading, `advanced_ms` or image fact as a span or log field: never (obs-plan §4).
- A second sleep in a stand check: never. The 800 ms sleep in `stand_virtual_clock` is the one exception, and the double-click case shows its determinism without one.
