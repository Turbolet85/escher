## What it builds
- **The scrollbar fade on the one clock.** The overlay scrollbar's activity is stamped `Instant::now()` (`packages/blitz-dom/src/document.rs:1879`, `show_scrollbars`) and read by `Instant::elapsed()` in `scrollbar_opacity` (`document.rs:1870`) and `scrollbars_animating` (`document.rs:1887`), with `scrollbar_activity` also read in `resolve.rs:71`. In a headless run that paints overlay scrollbars, these read the virtual clock instead, so the fade moves only when the driver moves time. The residual's mechanism, measured at HEAD by this take-up's read.
- **The one clock is the headless instance's own**: `Harness` already holds an animation clock (`Harness::time`, starting at 0, moved only by `tick`, which no caller in the tree uses, and handed to `BaseDocument::resolve(time)` on every `pump` — `packages/blitz-test-harness/src/harness.rs:120-155`). `resolve(time)` already drives Stylo's CSS animations and transitions (`resolve.rs:83` → `stylo.rs:135`). This clock becomes the one every engine time read in a headless run takes, rather than a second clock beside it. How the document reads it outside `resolve` is founder fork F1 (research.md §Open questions).
- **Every other wall-clock read on a headless run's path** — the entry's "every time a headless run reads". Each was traced at P3 to whether a driver verb reaches it (research.md §Files inspected):
  - **double-click detection — reached by `click`, and it moves readings.** `last_mousedown_time` is stamped `Instant::now()`, and a second mousedown within 500 ms of wall time and 2 px counts as click 2 (`packages/blitz-dom/src/events/pointer.rs:394-407`). Two driver `click`s on one control therefore read differently by wall time: a text input selects the word instead of placing the caret (`pointer.rs:548-556`), a password input selects all (`pointer.rs:647-651`), and a `DoubleClick` event reaches the app (`pointer.rs:968-974`). The stand's Circle Drawer opens its dialog on `ondoubleclick` (`examples/seven_guis/src/tasks/circle_drawer.rs:72`), and `stand_non_lean_tasks.rs:82` and `password_caret_click.rs:107` lean on two clicks landing inside the 500 ms wall window. Whether two driver clicks with no `advance` between them read as a double click on the one clock is founder fork F3;
  - **the fade also gates a thumb hit.** `scrollbar_opacity` decides whether a hover or a press lands on a thumb (`document.rs:1928`, `pointer.rs:423`), so a driver `click` on a thumb within 0.7 s of a scroll lands differently by wall time today;
  - **settle's `animating` reading** comes from `is_animating()` (`packages/blitz-test-harness/src/settle.rs:174`), which includes the wall-clock fade (`document.rs:2148`). No driver answer carries it, but it moves onto the one clock with the fade;
  - pan and fling timing (`SystemTime::now()` at `pointer.rs:267` and `pointer.rs:717`, the fling frame at `packages/blitz-dom/src/scrolling.rs:871`) — `[premise-corrected: not reached by any driver verb — panning starts only for a finger pointer (pointer.rs:248-252), and the driver's input is the mouse]`. It moves onto the same clock as part of "every time the engine reads", not because a driver reading depends on it;
  - smooth scroll (`scrolling.rs:515`, `scrolling.rs:896`) — `[premise-corrected: not reached by a driver verb — `scroll` runs the harness's `scroll_into_view` with `ScrollBehavior::Instant` (packages/escher-driver/src/execute.rs:194, packages/blitz-test-harness/src/input.rs:240), and nested boxes are always written at once (scrolling.rs:713); an app's own smooth `scroll_to` or fragment navigation still reaches it]`. It moves onto the same clock for that reason;
  - the app's time: the stand's Timer reads the ticks the session's time step delivers (`examples/seven_guis/src/stand.rs:80-100`), and only outside a `TimerTicks` context, in the windowed binary, does it wait on `futures_timer::Delay` (`examples/seven_guis/src/tasks/timer.rs:55`). No other stand task and nothing in dioxus-native-dom reads a clock (research.md §Sweeps).
- **`advance` and the one clock.** Today `advance` hands its milliseconds to the session's time step alone and reports `advanced_ms = step(harness, ms).min(ms)`, and "the harness's animation clock stays where it was" (`packages/escher-driver/src/execute.rs:175-187`, `stand.rs:90-93`). A session with no time step refuses `advance` as `time-unavailable`, and only the Timer's session is handed one (`examples/seven_guis/src/session_host.rs:30-44`, `tests/blitz-tests/tests/session_common/mod.rs:36-52`). With nothing moving the clock in a driver session, a thumb shown by a scroll would never fade, which fails the acceptance's second clause. What `advance` moves, what `advanced_ms` reads and what becomes of `time-unavailable` change what an agent meets — founder fork F2 (inputs#I1).
- **Repeat shots identical** — the matrix acceptance (`verification-matrix.json#v020-06`): "In a headless run that paints overlay scrollbars, two screenshots of the same state taken right after a scroll, with wall time passing between them and no driver advance, read the same pixels, and the fade moves only when the driver advances time." Proven on the stand or a fixture beside it, in both layout modes. `show_scrollbars` acts only under `cfg!(feature = "scrollbars")`. Every blitz-tests build turns it on (`tests/blitz-tests/Cargo.toml:20`, `blitz-paint` with `scrollbars`), so a check there paints thumbs. A per-package `escher-session` build paints none (`blitz-test-harness` takes `blitz-paint` with default features off, and neither `seven_guis` nor `dioxus-native`'s defaults name `scrollbars`); a workspace build unifies it on. The proof therefore lives in blitz-tests, and it asserts that a thumb is painted before it compares shots.
- **The stated limit leaves the tool's text**: the residual records that "the `screenshot` verb's help states the limit and no check shoots inside that window". The sentence is `packages/escher-driver/src/schema.rs:276-277`, pinned at `packages/escher-driver/src/schema_tests.rs:83-84`, and `tests/blitz-tests/tests/stand_screenshot_repeat.rs:5` says "No scroll precedes a shot: an overlay scrollbar thumb fades by wall time". Once the fade reads the one clock, the sentence is retired, both comments are restated, and a check shoots inside the old window. This is the program's own `'static` text riding a ratified carrier (the founder's ruling of 2026-10-12), not a widening.

## Boundaries and surfaces
- **An engine change for every document**: the scrollbar fade and the other reads above live in blitz-dom, which every document runs, windowed ones included. A windowed run's fade must still fade by wall time. The windowed shell resolves with seconds since its first animation-time query (`packages/blitz-shell/src/window.rs:280-302`) and keeps frames coming while `is_animating()` reads true (`window.rs:416`). Whether the change moves windowed behaviour (one doc clock, `resolve`'s time, for every document) or leaves it untouched (a clock the embedder supplies through `DocumentConfig`, wall time by default — `packages/blitz-dom/src/config.rs:31-60` is the provider shape) is founder fork F1 (inputs#I1), read against `.andromeda/playbook.md`'s escalate patterns.
- **Incremental and non-incremental layout stay identical** (`incremental_oracle`); every new pipeline test runs `for incremental in [false, true]`.
- **DOM writes through `DocumentMutator`**; a stale `NodeId` read by `get`/`contains_key` — `scrollbar_activity` is keyed by `NodeId` and already pruned on removal (`document.rs:979`).
- **The driver's surfaces** — the verb table, its argument bounds (`advance --ms`), the refusal causes, the wire `v2`, the MCP tool listing, the `command` and `tool_call` spans — gain no verb, cause, field, carrier or log field from this chunk unless a P4 fork rules one in. No new crate, port, env var or listener.
- **Telemetry**: no new log site carries an id, a name, typed text or a time a screen reads; the sink's 0-needle captures stay green.
- **The a11y target** (WCAG SC 2.1.1 · 1.4.3 · 2.4.3): focus order, Enter/Space activation and contrast are untouched by a clock; their standing checks re-prove it. A double-click count moving onto the one clock is not a focus or activation change for a single click: `click_count` decides only text-input selection, password select-all and the `DoubleClick` dispatch (`pointer.rs:548-556`, `pointer.rs:647-651`, `pointer.rs:968-974`), while a button's focus comes from `click_button` regardless of it.
