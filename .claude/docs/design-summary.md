### Typography · spacing · depth · radius · motion
> NOT YET MEASURED / NO RECORDED INTENT — no project-wide type scale, spacing unit, elevation, radius or motion tokens. Engine facts: default generic size 16px (13px monospace); WASM builds bundle DejaVu Sans for every generic family, and so does the native headless stand (system fonts off, decoded by seven_guis' `woff` feature); since 2026-10-12-headless-screenshot a driver `screenshot` of an app whose font context resolves no `sans-serif` family is refused `fonts-unavailable` with nothing painted — a shot never paints text skipped — and the stand's bundled font passes that check; a programmatic into-view scroll never animates a nested scrolling box — each is written at once, the requested behaviour applying to the viewport alone — and the driver's `scroll` is instant in every box and in the viewport (ratified by the founder, 2026-10-07); since 2026-10-18-one-virtual-clock the harness's documents read one `VirtualClock` — the overlay scrollbar fade, smooth scrolling and the fling read it headlessly — and the driver's `advance` moves it by exactly its `ms` together with the app's own time (ratified by the founder, 2026-10-18), while `click`, `type` and `press` leave it where it was, so after a driver `scroll` a settle reads `animating` true until 700 ms of that clock pass; since 2026-10-20-load-wait the driver's load wait moves no clock — while an acting step waits on a load in flight, for at most `LOAD_WAIT` (5 s of wall time), the `VirtualClock` stands still, so a timer or an animation does not run during the wait.

## Primary surfaces
- **desktop-native** — winit windows; Dioxus apps via `dioxus_native::launch`; seven_guis Home (640px card column) and TaskShell (header + scrolling body) are the stand's screens — the headless stand's nested scroller is the CRUD list (`crud-list` clips its rows, not `task-body`), which a driver `scroll` moves; the headless stand skips Home and mounts one lean task in TaskShell under `main#main` at the pinned 800 × 600 Light viewport; each lean task's controls and value displays carry author `id`s (their stable element ids), as do each CRUD row (`crud-person-{person.id}`) and each of Home's seven task cards (`task-card-{slug}`), and, since 2026-10-14-stand-requirement-sweep, the controls of the three tasks outside the lean four (`temp-celsius` · `temp-fahrenheit`; `circle-undo` · `circle-redo` · `circle-canvas`, with `circle-diameter` · `circle-close` on the open dialog; `cell-{A..Z}{0..25}` · `cell-input`), added as `id:` lines alone, so `unkeyed_actionable()` reads 0 on all seven tasks, the dialog open included, and the six task inputs are named by `for` / `aria-label` attributes, and the flight booker and CRUD state `aria-pressed` · `aria-invalid` · `role="listbox"`/`role="option"` with `aria-selected` by attributes alone, adding no element, class, style, wrapper or order; since 2026-10-13-stand-keyboard-harness `crud-list` is a keyboard region (`tabindex="0"` and an `onkeydown`: ArrowDown selects the next visible row, the first when none is selected, ArrowUp the previous, Home the first and End the last, each filling `crud-name` and `crud-surname` as a row's click does), so CRUD's Tab sequence reads `back-btn` · `crud-filter` · `crud-list` · `crud-name` · `crud-surname` · `crud-create` (six stops, five until then), the focus on the list, never the row, adding no element, class, style, wrapper or row; since 2026-10-14-stand-a11y-assertions `crud-list` is named by `aria-label="People"` alone, its accessible name `People` in the tree and the snapshot, adding no element, class, style, wrapper, id or order; since 2026-10-19-visual-lint the stand's layout reads clean to the visual lint (`Session::lint`, escher-driver, in process and as the `lint` verb on every carrier) — at boot each of the four lean tasks reads 0 findings in both layout modes, through the verb as through the reader (no overlap, clipping, truncated text, off-screen element, zero-size element holding content or contrast failure), and after twelve Creates the last CRUD row, `crud-person-14`, reads `clipped` inside `crud-list`, agreeing with the driver's `off-screen` refusal of its `click`; no stand markup, id, class or style moved.
- **cli** — WPT runner (owo-colors status words + colour), `paint_bench`, `screenshot`, and `scripts/agent-run.sh` (the agent-run test contract: usage on stderr, JSON lines only on stdout), `scripts/cold-agent.sh` (the cold-agent run pipe, same CLI shape; its one task `stand`, the four lean apps in one client session given the driver's own MCP server `escher`, `escher-session mcp`), and `escher-session <verb> [arguments] --session <dir>` — escher's driver command line, built at 2026-10-10-driver-cli, its `help` (since 2026-10-12-self-description) reading no `--session` and answering the tool's self-description: one line of uncoloured JSON on stdout per command, keyed by the driver schema's own words, a fixed usage line or error message on stderr, no colour, no ESC byte and no terminal test, exit `0` accepted · `1` refused · `2` usage · `3` session error (the recording's `record-dir-not-private` and `recording-failed` among the session errors, with no new exit), read from the schema's `EXIT_STATUSES` table; since 2026-10-12-self-description `escher-session help` answers the tool's self-description the same way, one uncoloured line of JSON on stdout with no ESC byte, status `0`, reaching no session, and a session error's object carries its fixed `remedy`; since 2026-10-12-headless-screenshot `escher-session screenshot [--id]` answers one uncoloured line `{"width":…,"height":…,"png":"<base64>"}` on stdout with no ESC byte, status `0`, the image as base64 text inside the line; `escher-session snapshot [--part <part>]` (a whole number, 1 to 1000, outside it refused `malformed`, status `1`) answers one uncoloured line with no ESC byte, `{"text":…}` for a whole screen and `{"text":…,"part":n,"parts":m}` for a screen read in parts, status `0`; since 2026-10-19-visual-lint `escher-session lint`, the eighth instance verb of twelve, takes no argument (one named refused `malformed`) and answers one uncoloured line `{"findings":[…]}` on stdout with no ESC byte, status `0`, each finding keyed `id` · `defect` · `bounds` then its reason's keys — ids, closed words and numbers only — an app with no font it can paint text with refused `fonts-unavailable`, status `1`, and a `lint` step kept under `--record` like every instance verb; over MCP an accepted `lint` answers its JSON line of findings as one text block, the tool listed after `screenshot`; since 2026-10-10-mcp-surface its `mcp` role, `escher-session mcp` (since 2026-10-19-session-recording `escher-session mcp [--record <dir>]`, `--record <dir>` taken at most once on `start`, the host role and the `mcp` role, keeping the session as one owner-only replayable check `check-{n}.json` that holds per call its verb, arguments, acceptance, the answer's digest and, since 2026-10-19-recorded-check-replay, the answer itself as an `answer` key — the line the driver wrote, masked as on every carrier, a shot's kept as `{"width":…,"height":…}` without its `png` — read back and replayed by `Check::replay`), read by an agent's MCP client: newline-delimited JSON-RPC 2.0 protocol lines only on stdout — a tool result's text the screen text for a `snapshot` (its JSON line `{"text","part","parts"}` for a screen read in parts), the self-description's line for `help`, two content blocks for a `screenshot` — an `image` block (`mimeType` `image/png`, the PNG as base64) then a text block, the shot's line without `png` — and the JSON line otherwise, every reply still one line — uncoloured, no ESC byte and still no terminal test, nothing written there at its end.

## Component patterns
- Each Dioxus document starts as `<html><head></head><body><main id="main"></main></body></html>`; the app mounts into `main`.
- Viewport = window surface minus safe-area insets; the test harness defaults to 800×600 @1 light.
- Devtools overlays (content/padding/border/margin) and layout outlines exist as `DevtoolSettings`.
- Browser controls are clickable `div`s, not buttons (an a11y gap noted in a11y-plan §4).
