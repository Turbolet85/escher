## Harness contract (§3)

- **Tool:** Rust tests in `tests/blitz-tests` over the AccessKit tree — `build_accessibility_tree()` (or `Document::accessibility_tree()`, which a `DioxusDocument` enriches with each element's stable id as `author_id`) after `resolve`, `test_that` matchers on `role()` / `is_hidden()`, `assert_role(html, id, expected)` and `unknown_tags(html)` helpers.
- **Focus harness:** `Harness::focused()` / `hovered()`.
- **Keyboard harness:** a Tab and Shift+Tab key-press focus check exists on the stand, driven through the harness's `press` / `press_with` (`stand_snapshot_state.rs`); the headless keyboard harness itself is still to come.
- **Contrast harness:** built since 2026-10-13-stand-contrast-harness — `Harness::text_contrast` (blitz-test-harness, read-only) reads an element's text/background pair and font metrics from computed styles as a `TextContrast` (`ratio` by `contrast_ratio`, the WCAG 2.x formula restating blitz-paint's Chrome-matching helper; `required_ratio` 3.0 for large text, else 4.5); `stand_contrast` asserts the 18 stand control rows in both layout modes beside a painted-pixel witness — pass 9, fail 5 (the accent buttons, `#ffffff` on `#4a6cf7` at 4.39 against 4.5, so SC 1.4.3 is not met there), exempt-inactive 3, no-text 1; it records and gates nothing and runs in the workspace `test` leg, not the `a11y` leg.

## Engine behaviour (measured)
- Roles: `role` attribute → HTML-AAM mapping → `Role::Unknown`; landmarks, lists, tables, form inputs by `type`, links only with `href`.
- Hidden: `hidden` / `display:none` / `visibility:hidden` exclude the subtree; `aria-hidden` marks hidden.
- State (since 2026-10-10-snapshot-states): the builder reads `aria-selected`, `aria-pressed` and `aria-invalid` by value on every element — trimmed, lower-case, exact — onto the node's `selected`, `toggled` (`mixed` kept) and `invalid` (a value outside the list reads True); `aria-checked` is not read. The snapshot takes the three from the tree as `selected` · `pressed` · `invalid`, a boolean model with two limits (a mixed toggle reads not pressed; a grammar or spelling error reads invalid). Ratified by the founder (2026-10-10); what an assistive technology reads is unmeasured, the windowed witness owned by "Stand a11y assertions". Check: `accessibility_states` (4, both layout modes; outside the `a11y` leg).
- Stand markup (attributes only): the flight booker's mode buttons state `aria-pressed`, its date inputs `aria-invalid`; the CRUD list is a `listbox` and its rows `option`s with `aria-selected`. Two gaps stand open: a row is not focusable, so no keyboard reaches an option ("Stand keyboard harness"), and the list reads no accessible name ("Stand a11y assertions").
- Focus: Tab / Shift+Tab via `focus_next_node` / `focus_prev_node`; focusability recomputed on `tabindex` / `href` / `disabled`; focus resets to body on removal; `:focus-visible` / `:focus-within` never match.
- Disabled-ness is keyed two ways: the `DISABLED` state (`:disabled`) and click targeting on the attribute's presence, focusability on its value parsed as a bool — `disabled="false"` matches `:disabled` yet stays focusable. dioxus-native-dom removes a falsy value of its 28 boolean attributes — upstream's `is_bool_attr` predicate since 2026-10-13-upstream-sync-polish-and-ship (`disabled`, `checked`, `hidden`, `inert` among them; a framework-written `inert: false` is removed, so it no longer makes content inert), so a `hidden: false` element stays displayed, in the tree and in the snapshot; an attribute outside the list holding `false` is still written as `"false"`. The snapshot reads `enabled` by presence — the driver's `disabled` refusal cause is stated on the same presence reading ("the element carries the `disabled` attribute, which the snapshot reads as not enabled") and is detected on it and on nothing else: the driver refuses a `click` or a `type` as `disabled` when the snapshot reads the element not enabled, with nothing dispatched and focus as it was, and acts on the same control once it reads enabled (`stand_act_disabled.rs`), and the driver's schema defines no role or name set of its own — `checked` and `value` from the element (a password or file-input value reads the fixed mask `MASKED_VALUE` — and, since 2026-10-12-headless-screenshot, a password's typed text is in no painted frame either: blitz-paint paints its value as bullets, its caret at the bullet of its caret index, in every document and through every renderer that paints with blitz-paint, windowed included (ratified by the founder, 2026-10-12), two values of one length painting byte-identical frames, focused or not, in both layout modes (`password_painted_masked.rs`); which bullet a click lands on can depend on the real characters' widths — not measured, owned by a `CARRY:` on "Stand requirement sweep"; the windowed paint is not run; a textarea's typed text reads back as its `value`, proven on an in-file fixture where it is named by `aria-label`), and `focused` from the tree — proven after a click, a Tab press and Shift+Tab (`stand_snapshot_state.rs`). The snapshot's text form (`Snapshot::to_text`) reads that model, never the tree or a control: one line per node, its role and name the node's, with no second mapping (`stand_snapshot_text.rs`). The snapshot's diff (`Snapshot::diff`) is one more reader of that model: a text change is reported on the element whose accessible name it changes, by its id and never as a text-run entry, a hidden element leaves and returns with its descendants, and a focus move names exactly the controls whose `focused` reading moved (`stand_diff.rs`). Since 2026-10-10-mcp-surface an MCP tool result is one more reader of that model and of nothing else — a `snapshot` result is `to_text`'s output itself, equal byte for byte to `Session::run`'s screen text in both layout modes (`stand_mcp_tools.rs`), its crossing to an MCP client ratified by the founder (2026-10-10). Since 2026-10-12-self-description a password input typed through an MCP `type` reads `MASKED_VALUE` in the tool result, role `PasswordInput` and a non-empty name, the typed text in neither result, in both layout modes — a test-only element of `stand_mcp_masked.rs`'s fixture, no stand task or app gaining one; and two further readers of the same model state closed words only: the node keys' help that `help` serves (each key's reading, the boolean model's two limits among them) and `DiffNode::differs`, a changed node naming the readings that differ from before the step in node-key order — the Flight Booker's Book names eight nodes that only moved, each `differs` = `[bounds]` (`stand_diff.rs`). Since 2026-10-12-headless-screenshot the driver's `screenshot` is one more reader of the model's bounds and of nothing else in it — an element shot, addressed by stable id and refused as every id-addressed call is, is the node's bounds rounded outward and cropped to the part that can be seen — and a shot changes nothing: no focus moves, `has_changes` stays false and the next diff is empty, in both layout modes (`stand_act_screenshot.rs`).
- Stand cue: `stand_flight_booker.rs` asserts the invalid-date cue (`invalid` class + `disabled` Book) without colour; `stand_accessibility_ids.rs` pins each lean task's Tab sequence (`focus_next_node` from the root element) and asserts the 15 stand controls' roles and non-empty names; `stand_actionable_keys.rs` asserts every actionable element of the lean tasks and Home reads an author key (`DioxusDocument::unkeyed_actionable()` empty, in every state), with no `tabindex`, role or Tab-order change; no test asserts SC-level keyboard behaviour.
- Platform: accesskit_xplat adapters (windows, macos, unix, android, null); ActionRequested and AccessibilityDeactivated are unhandled TODOs; the tree is built on InitialTreeRequested and rebuilt on a poll that reported work when the document's changed set, taken by that poll, was non-empty — a focus move, a checked change, a rewritten name and other mutations mark it, a pointer move alone does not — through `Document::accessibility_tree` (ratified by the founder, 2026-10-07; before 2026-10-07 the poll-time refresh never ran; no windowed witness on the dev host — still owed, on "Stand a11y assertions"). A harness settle neither reads nor drains that changed set, and the set is non-empty on a freshly booted harness document — a check reading the flag as "this step changed something" drains first. Names come from text children, a trimmed-non-empty `aria-label` and `<label>` association (`for`-target or nested `<input>`). The seven_guis stand binary enables no `accessibility` feature, so the windowed stand builds no platform adapter; re-read at 2026-10-10-mcp-surface, when escher-driver took `serde_json` as a fourth dependency (one lock line, no package), no platform adapter joins the stand graph.
