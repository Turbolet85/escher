# Accessibility Rules

Path-scoped rules for the accessibility tree, keyboard/focus handling, painted colours and the stand.
Source: `.andromeda/a11y-plan.md` — tier 0, target SC 2.1.1 (keyboard) · 1.4.3 (contrast) · 2.4.3 (focus order).

## Accessibility tree
- `build_accessibility_tree` returns an AccessKit `TreeUpdate`; the root is a `Window` node with id `u64::MAX`, the focused DOM node is tree focus, AccessKit ids are `NodeId::as_u64()`.
- Role = `role` attribute, else HTML-AAM element mapping, else `Role::Unknown`; only `<html>` and `<body>` should map to `Unknown` on a semantic page. Known gap: strong native semantics can be overridden by `role` (contrary to WAI-ARIA 1.2).
- `hidden`, `display: none`, `visibility: hidden` exclude a node and its children; `aria-hidden="true"` keeps it, marked hidden.
- Text nodes become `TextRun` nodes and label their parent.

## Keyboard and focus (SC 2.1.1 · 2.4.3)
- Focusable = holds a sub-document, or not disabled and `tabindex >= 0`, or (no tabindex) `<a>/<area href>`, `button`, `input`, `select`, `textarea`, `frame`, `iframe`, `summary`. Cached focusability is recomputed on `tabindex`/`href`/`disabled` changes — keep that hook when adding focus-affecting attributes.
- Tab/Shift+Tab move through `focus_next_node` / `focus_prev_node`; removing the focused node resets focus to body and runs blur side effects.
- `:focus-visible` and `:focus-within` never match — a stand style that relies on them shows no focus ring.
- Keyboard-event and Tab-order tests are observed absent; the headless keyboard harness is owned by the working route's "Stand keyboard harness" chunk.

## Contrast (SC 1.4.3)
- `blitz-paint` carries a Chrome-matching WCAG contrast-ratio helper (`color.rs`); no contrast check exists over stand controls yet — owned by "Stand contrast harness".
