# Accessibility Rules

Path-scoped rules for the accessibility tree, keyboard/focus handling, painted colours and the stand.
Source: `.andromeda/a11y-plan.md` — tier 0, target SC 2.1.1 (keyboard) · 1.4.3 (contrast) · 2.4.3 (focus order). The reach is published in `docs/capabilities.md` under `## Accessibility reach` (tier 0, those three criteria and no other, the `a11y` leg's fourteen files, what an assistive technology reads unmeasured, the named limits — the focus fixup firing no `blur`, no popup painted and Enter and Space opening nothing on a single select, a `multiple` select's `size` unread, `aria-activedescendant` unread); its pin `.github/scripts/test_capability_statement.py` reads none of these claims, so a change that moves the reach is made in that document by hand.

## Accessibility tree
- `build_accessibility_tree` returns an AccessKit `TreeUpdate`; the root is a `Window` node with id `u64::MAX`, the focused DOM node is tree focus only where it is among the built nodes, else `u64::MAX`, the window, so the tree never names a node it did not build, AccessKit ids are `NodeId::as_u64()`.
- Role = `role` attribute, else HTML-AAM element mapping, else `Role::Unknown`; only `<html>` and `<body>` should map to `Unknown` on a semantic page. Known gap: strong native semantics can be overridden by `role` (contrary to WAI-ARIA 1.2).
- `hidden`, `display: none`, `visibility: hidden` exclude a node and its children — an `option` of a `select`, its child or under its `optgroup` (`is_select_option`), excepted from `display: none`, which every option of a single-choice select but its chosen one computes and a `multiple` select's rows do not: it stays in the tree, `hidden`, `inert` and `visibility: hidden` still excluding it; `aria-hidden="true"` keeps it, marked hidden; an element carrying `inert` is excluded with its children too, and so from the snapshot, and a hit passes through it, removing `inert` restoring the tree and the hit (the `inert` read ratified by the founder, 2026-10-18).
- State = ARIA state attributes read by value on every element — a select's option excepted, its `selected` its chosen state (`select::is_chosen`), true or false, with no `aria-selected` read, and its non-empty `label` attribute its `label` where it has no `aria-label` —, the toggle by role (trimmed, lower-case, exact): `aria-selected` `true`/`false` → `selected`; `aria-pressed` `true`/`false`/`mixed` → `toggled` on every role but the five checkable ones; `aria-invalid` `true`/`grammar`/`spelling` → `invalid`, absent, empty or `false` → nothing, any other value → `Invalid::True`. `aria-checked` `true`/`false`/`mixed` → `toggled` on a `CheckBox` · `Switch` · `RadioButton` · `MenuItemCheckBox` · `MenuItemRadio` role alone (`role="switch"` mapping to `Switch`), a native `input` of type `checkbox` or `radio` reading neither attribute — the toggle read per role ratified by the founder (2026-10-18), `accessibility_states`' fourth test its pin; each attribute is read once, and the one other write of `toggled` is a native checkbox's or radio's own checked state on a checkable role — `Toggled::True` or `False` from `checkbox_input_checked()`; under any other role it writes nothing, so `pressed` never begins to read on it, `accessibility_states`' `a_click_and_a_space_move_a_native_control_in_the_tree` its pin, what an assistive technology reads of it not measured. A Dioxus `bool` attribute arrives as the text `"false"`, so state the literal texts `"true"` and `"false"`: a presence read would read every control pressed. Since 2026-10-17-upstream-sync-engine-debts the builder also holds upstream's `aria-describedby` (→ `described_by`), `aria-description` (→ description), `aria-expanded` (a boolean), `aria-disabled` (`true` → `set_disabled`) and `aria-level` (a number, with the tag and role defaults) reads beside the three, as upstream wrote them; upstream's own `parse::<bool>` `aria-selected` and unfiltered `aria-label` reads were dropped in the merge, so there is still one read per attribute — keep it so. The snapshot takes the three from the tree node, never from the element, its `checked` is a native checkbox's or radio's state, else, on a checkable role, the node's `toggled` (`Mixed` reading false; ratified by the founder, 2026-10-18), reads no description, and reads `enabled` from the `disabled` attribute, so `aria-disabled` moves no snapshot reading; since 2026-10-12-self-description the driver's served node-key help (`help`) states the boolean model's two limits (a mixed toggle reads `pressed` false, a grammar or spelling error reads `invalid` true). Ratified by the founder (2026-10-10); what an assistive technology reads of them is unmeasured — the windowed witness, at an active assistive technology, which this version does not reach, owned by a `.andromeda/residuals.md` line that reads `re-carried:0.2.0` on the founder's F1 (2026-10-14), the headless half — the tree the shell hands the adapter — proven on the stand since 2026-10-14-stand-a11y-assertions.
- Text nodes become `TextRun` nodes and label their parent; an `aria-label` non-empty after trimming sets `label`; a `<label>` is pushed onto its bound labelable element's `labelled_by` (`for`-target, else first nested labelable element — a `button`, an `input` whose `type` is not `hidden`, a `meter`, `output`, `progress`, `select` or `textarea`; a hidden input is named by no label) after the whole tree is built; since 2026-10-17-upstream-sync-engine-debts an `aria-labelledby` loop runs after that `<label>` → input loop, clears `labelled_by`, pushes the referenced nodes and sets their computed text as the `label`, so it outranks a `<label>` and an `aria-label` (accname 2B) — an id naming no built node ignored, hidden targets read for the label, the `aria-label` the fallback when the targets hold no text. A `select` (role `ComboBox`, `ListBox` for `multiple`) keeps its `option` children, and those under an `optgroup`, in the tree as `ListBoxOption` nodes, under `display: none` too, each `selected` true or false from its chosen state and named by its non-empty `label` attribute, else its text; the snapshot reads a `select`'s `value` as `BaseDocument::select_value` (the chosen option's value, for a `multiple` select its first chosen option's in tree order, nothing with none chosen) and a closed select's options under it, each with its select's client rect as its `bounds` — which the driver's visual lint leaves out of its overlap reading in every document (`overlaps` skipping such an entry on either side, `Entry.in_closed_select` reading the element through `closed_select_of` and never the role, so CRUD's `role="option"` rows are not read as a select's), the stand's flight booker at boot reading no `overlap`, `stand_lint` reading `[0, 0, 0, 0]`. A `multiple` select carries `set_multiselectable` in the tree, its rows and groups reading their own client rects as their `bounds` and its rows linted as usual; an `optgroup` reads `Role::Group`, its non-empty `label` attribute its name, named in the tree and unpainted; what an assistive technology reads of them is not measured.
- `Document::accessibility_tree` (gated `accessibility`) is what the shell builds — on InitialTreeRequested and, on a poll that reported work, when the document's changed set taken by that poll was non-empty (ratified by the founder, 2026-10-07, its windowed witness, at the platform adapter, still owed and owned by a `.andromeda/residuals.md` line that reads `re-carried:0.2.0`, an active assistive technology this version does not reach, on the founder's F1 (2026-10-14), both halves proven headlessly on the stand since 2026-10-14-stand-a11y-assertions; before 2026-10-07 the poll-time refresh never ran); a `DioxusDocument` overrides it to set each element node's `author_id` to its stable element id — none on `TextRun`, document-root or `Window` nodes. The workspace pins the Dioxus crates `default-features = false`: the override — and the snapshot model built on it (`DioxusDocument::snapshot`, which takes role, name and focus from this tree, never a second mapping; its text form `Snapshot::to_text`, that text's parts `Snapshot::text_parts` and its diff `Snapshot::diff` read that model and map nothing again) — exists only where a crate names `dioxus-native-dom/accessibility` or depends on one that does (blitz-tests and escher-driver name it; seven_guis names none and gets it through escher-driver, so both its binaries compile these modules — with no platform adapter, so the stand binary still gives no assistive technology a tree).
- Every element an agent can act on — focusable, or an interactive role, or a listener — reads an author key (an HTML `id`); under the same feature `DioxusDocument::unkeyed_actionable()` returns the ones that read a positional path, each with its `remedy()`. `stand_actionable_keys` asserts it empty on the four lean tasks, Home and, since 2026-10-14-stand-requirement-sweep, the three non-lean tasks (Temperature Converter, Circle Drawer with its dialog open included, Cells — keyed by `id:` lines alone) and the load page the stand serves (`stand_load_page`), so a new control there needs an `id` — never a `tabindex`, role or focusability change made to satisfy the check.

## Keyboard and focus (SC 2.1.1 · 2.4.3)
- Focusable = holds a sub-document, or it is not inert (by presence on itself or an ancestor element, `Node::is_inert`) and is no disabled form control (`ElementData::is_disabled`: a `disabled` attribute present, any value, on a `button`, `input`, `select` or `textarea` alone; the narrowing and the `inert` read ratified by the founder, 2026-10-18) and has `tabindex >= 0`, or (no tabindex) `<a>/<area href>`, `button`, `input`, `select`, `textarea`, `frame`, `iframe`, `summary`. Cached focusability is recomputed on `tabindex`/`href`/`disabled` changes — keep that hook when adding focus-affecting attributes.
- `disabled` is keyed one way since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder): the `DISABLED` state (`:disabled`) reads PRESENCE, and the pointer-move gate, `ClickTarget::Disabled`, `handle_click`'s walk gate, the Enter and Space activation and focusability read `ElementData::is_disabled` — that presence on a `button`, `input`, `select` or `textarea` alone (ratified by the founder, 2026-10-18) — so `disabled="false"` and a bare `disabled` on a form control match `:disabled` and are not focusable, a bare `disabled` set after creation takes its focusability away, and a `<div disabled tabindex=0>` takes focus. dioxus-native-dom removes a falsy value of its 28 boolean attributes — upstream's private `is_bool_attr` predicate, a closed set, since 2026-10-13-upstream-sync-polish-and-ship (`disabled`, `checked`, `hidden`, `readonly`, `required`, `multiple`, `selected`, `open`, `autofocus`, `inert` among them; a framework-written `inert: false` is removed, while a truthy `inert` (by presence on itself or an ancestor element, `Node::is_inert`) takes focusability, hits and the tree away from its subtree (ratified by the founder, 2026-10-18) and Tab reaches the buttons under `inert: false`; HTML's focus fixup is built, in every document: `DocumentMutator::flush` calls `BaseDocument::clear_focus` where `focus_node_id` resolves to a node reading `is_inert()`, with no `inert` arm joining the attribute writes, so a subtree moved under an inert box is covered too; no DOM `blur` or `focusout` fires, and `disabled` and `hidden` take no part in it), so a `hidden: false` element stays displayed and in the tree; an attribute outside that list holding `false` is still written as `"false"`. The snapshot's `enabled` follows the presence reading.
- Tab/Shift+Tab move through `focus_next_node` / `focus_prev_node`; since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder) a pressed Enter on the focused node that is no disabled form control (`ElementData::is_disabled`; ratified by the founder, 2026-10-18 — a `disabled` attribute on a `summary` or an `a` gating neither key, as HTML does) dispatches a Click on a `button`, a `summary`, an `input` of type `submit`, `reset` or `button`, or an `a` with `href`, and a released Space (`handle_key_up`, routed by `events/mod.rs`) the same Click on a `button`, a `summary`, or an `input` of type `submit`, `reset`, `button`, `checkbox` or `radio` — a link takes no Space, a text input and a range input take neither key there; the Click (`Node::synthetic_click_event_data`) is queued by the event driver, so the app's handlers run, then `handle_click`, whose checkbox and radio arms dispatch, after `input`, a `change` with the same value, in every document, a checkbox always and a radio only where it was not checked before the click, the script runtime synthesizing none (`checkable_change_event`), while typing in a text input and a range's key and pointerdown fire `input` and no `change` (`text_range_no_change_event`); removing the focused node resets focus to body and runs blur side effects. Since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder) a pointer click on a `button` (any type) or an `input` of type `submit`, `reset` or `button` focuses it through `generate_focus_events` / `set_focus_to`, then submits the form owner when it is a submit button; a disabled form control still stops the walk first, a disabled ancestor `div` not (ratified by the founder, 2026-10-18), a click on a `select` focuses it through `generate_focus_events` / `set_focus_to`, clearing its typeahead and the document's text selection (a disabled select stopped by the walk's gate first, so it neither focuses nor acts; an option of a closed single select, under a group too, is not clicked — a driver `click` on one is refused `covered`; a click on a `multiple` select's row runs `click_select_row` behind `handle_click`'s `option` arm, a disabled select stopping it, otherwise focusing the select and clearing the typeahead and the text selection, a plain click choosing the row alone, Ctrl or Meta flipping it, Shift spanning and a disabled row changing nothing), and a click on any other element — a CRUD row or the list — still clears focus; two pointer clicks on one point within 500 ms and 2 px are a double click, read on the document's clock — on a harness-built document the harness's `VirtualClock`, so two driver `click`s on one point with no `advance` between them are a double click, selecting a word in a text input — while each still focuses its target as one click does (ratified by the founder, 2026-10-18). Since 2026-10-13-range-input-interaction (in every document, ratified by the founder) a focused `input type="range"` with no `disabled` attribute (read by presence) steps up on ArrowRight/ArrowUp, down on ArrowLeft/ArrowDown, to its minimum on Home and its maximum on End, every other key doing nothing; its current value is held apart from the `value` attribute (`RangeInputData`), sanitized to `[min, max]` on the step grid, each change marking the changed set and firing one `input` (none when nothing changes); a click focuses it without moving the value, and a main-button pointerdown sets it from the hit's fraction of the content box. A focused single-choice `select` (no `multiple`) that is no disabled form control (`ElementData::is_disabled`) takes a pressed ArrowDown / ArrowUp to the next / previous enabled option and Home / End to the first / last enabled option (with none chosen, ArrowDown reads as Home and ArrowUp as End), and a character pressed with no Ctrl, Alt or Meta as typeahead — the first enabled option whose label starts with the text typed, compared in lower case, the text kept for one select until 1 s of the document's clock passes; every other key does nothing (Enter and Space open nothing, a released Space activates no select); each change marks the changed set, dispatches one `input` then one `change` carrying the select's value and asks for a redraw, a key that changes nothing firing none; an `optgroup`'s options are the select's own in tree order, reached by keys and text, a disabled group's rows reading as disabled through `option_disabled`, and no popup is painted. A focused `multiple` select that is no disabled form control takes ArrowDown, ArrowUp, Home and End: alone they choose that row alone, with Shift they span from the anchor (with no cursor yet from the last chosen row), and with Ctrl or Meta they move the current row and change nothing; a Space with no typed text standing flips the current row and with text standing joins it, a character with no Ctrl, Alt or Meta chooses its match alone, its disabled rows are never chosen and Ctrl+A is not modelled; a `multiple` write or removal records the select (`record_select_of_multiple_write`), so removal settles it to one, and `set_option_selectedness` leaves its other options alone; `evt.values()` reads its set through `multiple_select_values`, one form entry per chosen option on `Input` and `Change`, while `value` stays `select_value`; the driver's `type` on one focuses it with no click and clears the typeahead, a text opening on a space typing nothing, and the driver's `press` holds no Ctrl, so a non-adjacent `multiple` set cannot be built through the driver, a limit its help states, its fix owned by a `.andromeda/residuals.md` line (target: next).
- `:focus-visible` never matches — a stand style that relies on it shows no focus ring — while `:focus-within` matches the focused element and its ancestors by the `FOCUS_WITHIN` element state, and `:open` matches a `details` or `dialog` carrying `open` by the `OPEN` element state (`ElementData::flush_open_state`, at element construction and on every `open` write or removal through the mutator; a `details`'s first `summary` activated flipping it), in every document — `open_state`'s 4 tests, in both layout modes, read the `open` attribute by presence at construction, move it through a mutator write and removal and a summary's click and Enter, and read `:open` matching.
- A Tab / Shift+Tab key-press focus check exists on the stand (`stand_snapshot_state`, through the harness's `press` / `press_with`; `stand_accessibility_ids` pins the lean tasks' `focus_next_node` sequence); a range-input key and click check runs in both layout modes (`range_input_interaction`, a disabled range taking neither keys nor a click; on the stand `stand_act_range` moves the Timer slider through the driver by click and key, and an arrow step after two Tabs leaves it focused with role `Slider`, its name and the forward focus sequence unchanged); since 2026-10-13-stand-keyboard-harness `stand_keyboard` drives Tab, Shift+Tab, Enter, Space and the CRUD list's keys headlessly on the four lean tasks through the same `press` / `press_with`, reading the focused node back per step in both layout modes, and pins the flight booker's `select#flight-type` moving its choice by its arrows (`the_flight_type_select_moves_its_choice_by_its_arrows`, 21 tests) — each task's stated sequence is the shared table `tab_order` (CRUD six stops, `crud-list` third: it takes `tabindex="0"` and an `onkeydown`, ArrowDown / ArrowUp / Home / End moving the selection, its rows not focusable), and through the driver `stand_act_keys` presses `enter` and `space` on a Tab-focused `counter-increment`; since 2026-10-14-stand-a11y-assertions the walk is also asserted in two enabled states, each reached by keyboard alone (`enable_by_keyboard`), against the shared table `ENABLED_TAB_ORDER` beside `tab_order` in the shared module — the flight booker after the return flight is chosen on `select#flight-type` by ArrowDown, five stops (its boot `tab_order` four, `back-btn`, `flight-type`, `flight-start`, `flight-book`); CRUD after a row is selected, eight — every `controls(task)` id lying in `tab_order` ∪ `ENABLED_TAB_ORDER`, and Enter and Space read as the click of `crud-update` and `crud-delete` (4 rows), so a control enabled after boot needs its place in `ENABLED_TAB_ORDER`, while the load page and Cells hold Tab-order, keyboard and contrast rows (`stand_keyboard`, `stand_contrast`, `stand_load_page`, `stand_cells_served`) — `stand_keyboard` walks the shared tables `LOAD_TAB_ORDER` and `CELLS_TAB_ORDER`, beside `tab_order` and `ENABLED_TAB_ORDER`, forward and back in both layout modes, the load page's button taking Enter and Space, Cells' arrows and Enter opening the moved-to cell's editor and its value committing by keyboard, Tab leaving an open editor and a click on another cell each committing it, and the arrows clamping at the grid's ends and bringing a cell into view — so SC 2.1.1 and 1.4.3 are asserted on the load page's `load-fetch` Button and on Cells' `cells-grid`; a select key and typeahead check runs in both layout modes — `select_interaction` (18 tests: a 14-row keys table and a 7-row typeahead table, one `input` and one `change` per change and none for no change, `has_changes` asserted per row, the typed text kept for one second of the document's clock, a disabled select taking no key and no click, an app writing `selected` re-seeding the choice) and, through the driver, `stand_act_select` (10 tests: Tab `fx-before` → `fx-pick` → `fx-named` → `fx-after` → `fx-before`, the disabled `fx-off` skipped, equal before and after the choices, an option chosen by a click then a key) — both in the `a11y` leg, both three rounds in the `stand-repeat` leg, `stand_act_select` by its `stand_` prefix and `select_interaction` by the leg's named `--test` list. Cells: `cells-grid`, named `Cells` by `aria_label` with no role, is one Tab stop; the arrows move `current`, clamped, and bring the cell into view; Enter opens the editor on `current`, focused, and the editor's Enter commits and returns focus to the grid; Tab leaving an open editor commits it; `.cells-grid:focus .cell.current` draws a 2px outline in the stand accent; role and cell semantics stay out, owned by a `.andromeda/residuals.md` line.
