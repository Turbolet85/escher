# Accessibility Rules

Path-scoped rules for the accessibility tree, keyboard/focus handling, painted colours and the stand.
Source: `.andromeda/a11y-plan.md` — tier 0, target SC 2.1.1 (keyboard) · 1.4.3 (contrast) · 2.4.3 (focus order).

## Accessibility tree
- `build_accessibility_tree` returns an AccessKit `TreeUpdate`; the root is a `Window` node with id `u64::MAX`, the focused DOM node is tree focus, AccessKit ids are `NodeId::as_u64()`.
- Role = `role` attribute, else HTML-AAM element mapping, else `Role::Unknown`; only `<html>` and `<body>` should map to `Unknown` on a semantic page. Known gap: strong native semantics can be overridden by `role` (contrary to WAI-ARIA 1.2).
- `hidden`, `display: none`, `visibility: hidden` exclude a node and its children — an `option` whose parent is a `select` excepted from `display: none`, which every option but a single-choice select's chosen one computes: it stays in the tree, `hidden`, `inert` and `visibility: hidden` still excluding it; `aria-hidden="true"` keeps it, marked hidden; an element carrying `inert` is excluded with its children too, and so from the snapshot, and a hit passes through it, removing `inert` restoring the tree and the hit (the `inert` read ratified by the founder, 2026-10-18).
- State = ARIA state attributes read by value on every element — a select's option excepted, its `selected` its chosen state (`select::is_chosen`), true or false, with no `aria-selected` read, and its non-empty `label` attribute its `label` where it has no `aria-label` —, the toggle by role (trimmed, lower-case, exact): `aria-selected` `true`/`false` → `selected`; `aria-pressed` `true`/`false`/`mixed` → `toggled` on every role but the five checkable ones; `aria-invalid` `true`/`grammar`/`spelling` → `invalid`, absent, empty or `false` → nothing, any other value → `Invalid::True`. `aria-checked` `true`/`false`/`mixed` → `toggled` on a `CheckBox` · `Switch` · `RadioButton` · `MenuItemCheckBox` · `MenuItemRadio` role alone (`role="switch"` mapping to `Switch`), a native `input` of type `checkbox` or `radio` reading neither attribute — the toggle read per role ratified by the founder (2026-10-18), `accessibility_states`' fourth test its pin; each attribute is read once and nothing else writes `toggled`, so the builder writes none from a native checkbox's or radio's own checked state — a measured absence, its fix owned by a `.andromeda/residuals.md` line (target: next). A Dioxus `bool` attribute arrives as the text `"false"`, so state the literal texts `"true"` and `"false"`: a presence read would read every control pressed. Since 2026-10-17-upstream-sync-engine-debts the builder also holds upstream's `aria-describedby` (→ `described_by`), `aria-description` (→ description), `aria-expanded` (a boolean), `aria-disabled` (`true` → `set_disabled`) and `aria-level` (a number, with the tag and role defaults) reads beside the three, as upstream wrote them; upstream's own `parse::<bool>` `aria-selected` and unfiltered `aria-label` reads were dropped in the merge, so there is still one read per attribute — keep it so. The snapshot takes the three from the tree node, never from the element, its `checked` is a native checkbox's or radio's state, else, on a checkable role, the node's `toggled` (`Mixed` reading false; ratified by the founder, 2026-10-18), reads no description, and reads `enabled` from the `disabled` attribute, so `aria-disabled` moves no snapshot reading; since 2026-10-12-self-description the driver's served node-key help (`help`) states the boolean model's two limits (a mixed toggle reads `pressed` false, a grammar or spelling error reads `invalid` true). Ratified by the founder (2026-10-10); what an assistive technology reads of them is unmeasured — the windowed witness, at an active assistive technology, owned by a `.andromeda/residuals.md` line (target: next) on the founder's F1 (2026-10-14), the headless half — the tree the shell hands the adapter — proven on the stand since 2026-10-14-stand-a11y-assertions.
- Text nodes become `TextRun` nodes and label their parent; an `aria-label` non-empty after trimming sets `label`; a `<label>` is pushed onto its bound labelable element's `labelled_by` (`for`-target, else first nested labelable element — a `button`, an `input` whose `type` is not `hidden`, a `meter`, `output`, `progress`, `select` or `textarea`; a hidden input is named by no label) after the whole tree is built; since 2026-10-17-upstream-sync-engine-debts an `aria-labelledby` loop runs after that `<label>` → input loop, clears `labelled_by`, pushes the referenced nodes and sets their computed text as the `label`, so it outranks a `<label>` and an `aria-label` (accname 2B) — an id naming no built node ignored, hidden targets read for the label, the `aria-label` the fallback when the targets hold no text. A `select` (role `ComboBox`, `ListBox` for `multiple`) keeps its `option` children in the tree as `ListBoxOption` nodes, under `display: none` too, each `selected` true or false from its chosen state and named by its non-empty `label` attribute, else its text; the snapshot reads a `select`'s `value` as `BaseDocument::select_value` (the chosen option's value, nothing with none chosen) and its options as its children, each with its select's client rect as its `bounds`.
- `Document::accessibility_tree` (gated `accessibility`) is what the shell builds — on InitialTreeRequested and, on a poll that reported work, when the document's changed set taken by that poll was non-empty (ratified by the founder, 2026-10-07, its windowed witness, at the platform adapter, still owed and owned by a `.andromeda/residuals.md` line (target: next) on the founder's F1 (2026-10-14), both halves proven headlessly on the stand since 2026-10-14-stand-a11y-assertions; before 2026-10-07 the poll-time refresh never ran); a `DioxusDocument` overrides it to set each element node's `author_id` to its stable element id — none on `TextRun`, document-root or `Window` nodes. The workspace pins the Dioxus crates `default-features = false`: the override — and the snapshot model built on it (`DioxusDocument::snapshot`, which takes role, name and focus from this tree, never a second mapping; its text form `Snapshot::to_text`, that text's parts `Snapshot::text_parts` and its diff `Snapshot::diff` read that model and map nothing again) — exists only where a crate names `dioxus-native-dom/accessibility` or depends on one that does (blitz-tests and escher-driver name it; seven_guis names none and gets it through escher-driver, so both its binaries compile these modules — with no platform adapter, so the stand binary still gives no assistive technology a tree).
- Every element an agent can act on — focusable, or an interactive role, or a listener — reads an author key (an HTML `id`); under the same feature `DioxusDocument::unkeyed_actionable()` returns the ones that read a positional path, each with its `remedy()`. `stand_actionable_keys` asserts it empty on the four lean tasks, Home and, since 2026-10-14-stand-requirement-sweep, the three non-lean tasks (Temperature Converter, Circle Drawer with its dialog open included, Cells — keyed by `id:` lines alone), so a new control there needs an `id` — never a `tabindex`, role or focusability change made to satisfy the check.

## Keyboard and focus (SC 2.1.1 · 2.4.3)
- Focusable = holds a sub-document, or it is not inert (by presence on itself or an ancestor element, `Node::is_inert`) and is no disabled form control (`ElementData::is_disabled`: a `disabled` attribute present, any value, on a `button`, `input`, `select` or `textarea` alone; the narrowing and the `inert` read ratified by the founder, 2026-10-18) and has `tabindex >= 0`, or (no tabindex) `<a>/<area href>`, `button`, `input`, `select`, `textarea`, `frame`, `iframe`, `summary`. Cached focusability is recomputed on `tabindex`/`href`/`disabled` changes — keep that hook when adding focus-affecting attributes.
- `disabled` is keyed one way since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder): the `DISABLED` state (`:disabled`) reads PRESENCE, and the pointer-move gate, `ClickTarget::Disabled`, `handle_click`'s walk gate, the Enter and Space activation and focusability read `ElementData::is_disabled` — that presence on a `button`, `input`, `select` or `textarea` alone (ratified by the founder, 2026-10-18) — so `disabled="false"` and a bare `disabled` on a form control match `:disabled` and are not focusable, a bare `disabled` set after creation takes its focusability away, and a `<div disabled tabindex=0>` takes focus. dioxus-native-dom removes a falsy value of its 28 boolean attributes — upstream's private `is_bool_attr` predicate, a closed set, since 2026-10-13-upstream-sync-polish-and-ship (`disabled`, `checked`, `hidden`, `readonly`, `required`, `multiple`, `selected`, `open`, `autofocus`, `inert` among them; a framework-written `inert: false` is removed, while a truthy `inert` (by presence on itself or an ancestor element, `Node::is_inert`) takes focusability, hits and the tree away from its subtree (ratified by the founder, 2026-10-18) and Tab reaches the buttons under `inert: false`; HTML's focus fixup is not built, so a node that holds focus when it becomes inert keeps it until focus moves, its fix owned by a `.andromeda/residuals.md` line (target: next)), so a `hidden: false` element stays displayed and in the tree; an attribute outside that list holding `false` is still written as `"false"`. The snapshot's `enabled` follows the presence reading.
- Tab/Shift+Tab move through `focus_next_node` / `focus_prev_node`; since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder) a pressed Enter on the focused node that is no disabled form control (`ElementData::is_disabled`; ratified by the founder, 2026-10-18 — a `disabled` attribute on a `summary` or an `a` gating neither key, as HTML does) dispatches a Click on a `button`, a `summary`, an `input` of type `submit`, `reset` or `button`, or an `a` with `href`, and a released Space (`handle_key_up`, routed by `events/mod.rs`) the same Click on a `button`, a `summary`, or an `input` of type `submit`, `reset`, `button`, `checkbox` or `radio` — a link takes no Space, a text input and a range input take neither key there; the Click (`Node::synthetic_click_event_data`) is queued by the event driver, so the app's handlers run, then `handle_click`; removing the focused node resets focus to body and runs blur side effects. Since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder) a pointer click on a `button` (any type) or an `input` of type `submit`, `reset` or `button` focuses it through `generate_focus_events` / `set_focus_to`, then submits the form owner when it is a submit button; a disabled form control still stops the walk first, a disabled ancestor `div` not (ratified by the founder, 2026-10-18), a click on a `select` focuses it through `generate_focus_events` / `set_focus_to`, clearing its typeahead and the document's text selection (a disabled select stopped by the walk's gate first, so it neither focuses nor acts; an option is not clicked — a driver `click` on one is refused `covered`), and a click on any other element — a CRUD row or the list — still clears focus; two pointer clicks on one point within 500 ms and 2 px are a double click, read on the document's clock — on a harness-built document the harness's `VirtualClock`, so two driver `click`s on one point with no `advance` between them are a double click, selecting a word in a text input — while each still focuses its target as one click does (ratified by the founder, 2026-10-18). Since 2026-10-13-range-input-interaction (in every document, ratified by the founder) a focused `input type="range"` with no `disabled` attribute (read by presence) steps up on ArrowRight/ArrowUp, down on ArrowLeft/ArrowDown, to its minimum on Home and its maximum on End, every other key doing nothing; its current value is held apart from the `value` attribute (`RangeInputData`), sanitized to `[min, max]` on the step grid, each change marking the changed set and firing one `input` (none when nothing changes); a click focuses it without moving the value, and a main-button pointerdown sets it from the hit's fraction of the content box. A focused single-choice `select` (no `multiple`) that is no disabled form control (`ElementData::is_disabled`) takes a pressed ArrowDown / ArrowUp to the next / previous enabled option and Home / End to the first / last enabled option (with none chosen, ArrowDown reads as Home and ArrowUp as End), and a character pressed with no Ctrl, Alt or Meta as typeahead — the first enabled option whose label starts with the text typed, compared in lower case, the text kept for one select until 1 s of the document's clock passes; every other key does nothing (Enter and Space open nothing, a released Space activates no select); each change marks the changed set, dispatches one `input` then one `change` carrying the select's value and asks for a redraw, a key that changes nothing firing none; a `multiple` select and an `optgroup`'s options are not modelled (a `multiple` select takes no key) and no popup is painted.
- `:focus-visible` never matches — a stand style that relies on it shows no focus ring — while `:focus-within` matches the focused element and its ancestors by the `FOCUS_WITHIN` element state.
- A Tab / Shift+Tab key-press focus check exists on the stand (`stand_snapshot_state`, through the harness's `press` / `press_with`; `stand_accessibility_ids` pins the lean tasks' `focus_next_node` sequence); a range-input key and click check runs in both layout modes (`range_input_interaction`, a disabled range taking neither keys nor a click; on the stand `stand_act_range` moves the Timer slider through the driver by click and key, and an arrow step after two Tabs leaves it focused with role `Slider`, its name and the forward focus sequence unchanged); since 2026-10-13-stand-keyboard-harness `stand_keyboard` drives Tab, Shift+Tab, Enter, Space and the CRUD list's keys headlessly on the four lean tasks through the same `press` / `press_with`, reading the focused node back per step in both layout modes — each task's stated sequence is the shared table `tab_order` (CRUD six stops, `crud-list` third: it takes `tabindex="0"` and an `onkeydown`, ArrowDown / ArrowUp / Home / End moving the selection, its rows not focusable), and through the driver `stand_act_keys` presses `enter` and `space` on a Tab-focused `counter-increment`; since 2026-10-14-stand-a11y-assertions the walk is also asserted in two enabled states, each reached by keyboard alone (`enable_by_keyboard`), against the shared table `ENABLED_TAB_ORDER` beside `tab_order` in the shared module — the flight booker after `flight-return`, six stops; CRUD after a row is selected, eight — every `controls(task)` id lying in `tab_order` ∪ `ENABLED_TAB_ORDER`, and Enter and Space read as the click of `crud-update` and `crud-delete` (4 rows), so a control enabled after boot needs its place in `ENABLED_TAB_ORDER`; a select key and typeahead check runs in both layout modes — `select_interaction` (7 tests: a 14-row keys table and a 7-row typeahead table, one `input` and one `change` per change and none for no change, `has_changes` asserted per row, the typed text kept for one second of the document's clock, a disabled select taking no key and no click, an app writing `selected` re-seeding the choice) and, through the driver, `stand_act_select` (5 tests: Tab `fx-before` → `fx-pick` → `fx-named` → `fx-after` → `fx-before`, the disabled `fx-off` skipped, equal before and after the choices, an option chosen by a click then a key) — both in the `a11y` leg, both three rounds in the `stand-repeat` leg, `stand_act_select` by its `stand_` prefix and `select_interaction` by the leg's named `--test` list.

## Contrast (SC 1.4.3)
- `blitz-paint` carries a Chrome-matching WCAG contrast-ratio helper (`color.rs`); since 2026-10-13-stand-contrast-harness `Harness::text_contrast` in blitz-test-harness (read-only) reads a control's text/background pair as a `TextContrast` (`contrast_ratio`, the WCAG 2.x ratio; `required_ratio` 3.0 for large text, else 4.5), and `stand_contrast` asserts three tables in both layout modes, read by one shared reader whose exempt class is exactly `enabled == Some(false)` — the 18 stand control rows, 14 `TEXT_ROWS` (the CRUD list rows and the text outside the controls) and 19 `STATE_ROWS` (the colour states reached by input, hover and active included) — so SC 1.4.3 is met on every measured non-exempt stand row: since 2026-10-14-stand-a11y-assertions the stand's accent is one step darker in every task CSS that declares it (rest `#3a5ce5`, hover `#2a4cd3`, active `#1f3fc1`, white on each 5.47 · 6.83 · 8.27; the operator's F5, a stand change and no engine change, design-system §Color Palette), where `#4a6cf7` read 4.39 and failed; `text_contrast` reads the declared `:hover` background after `move_mouse_to` and the `:active` one after `mouse_down_at`, and a button with no `:active` rule keeps its hover pair while pressed; the check runs in the workspace `test` leg, per package and in the `a11y` leg; since 2026-10-19-visual-lint `text_contrast` has its first non-test caller, the `contrast` reading of escher-driver's visual lint (`Session::lint` in process and the `lint` verb on every carrier, recorded; a `contrast` finding written `id` · `defect` · `bounds` · `ratio` · `required`, ids, closed words and numbers only), which reports a node below `required_ratio()`, exempt exactly where the snapshot's `enabled` reads `Some(false)` — the exempt rule `stand_contrast` asserts, with no second formula or threshold — so a change to `text_contrast` or that exempt rule moves both.
