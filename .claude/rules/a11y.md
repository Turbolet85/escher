# Accessibility Rules

Path-scoped rules for the accessibility tree, keyboard/focus handling, painted colours and the stand.
Source: `.andromeda/a11y-plan.md` — tier 0, target SC 2.1.1 (keyboard) · 1.4.3 (contrast) · 2.4.3 (focus order).

## Accessibility tree
- `build_accessibility_tree` returns an AccessKit `TreeUpdate`; the root is a `Window` node with id `u64::MAX`, the focused DOM node is tree focus, AccessKit ids are `NodeId::as_u64()`.
- Role = `role` attribute, else HTML-AAM element mapping, else `Role::Unknown`; only `<html>` and `<body>` should map to `Unknown` on a semantic page. Known gap: strong native semantics can be overridden by `role` (contrary to WAI-ARIA 1.2).
- `hidden`, `display: none`, `visibility: hidden` exclude a node and its children; `aria-hidden="true"` keeps it, marked hidden.
- State = three ARIA attributes read by value on every element, whatever its role (trimmed, lower-case, exact): `aria-selected` `true`/`false` → `selected`; `aria-pressed` `true`/`false`/`mixed` → `toggled`; `aria-invalid` `true`/`grammar`/`spelling` → `invalid`, absent, empty or `false` → nothing, any other value → `Invalid::True`. `aria-checked` is not read — do not fold it into `checked` or `pressed`: reading it so is owned by a `.andromeda/residuals.md` line (target: next) on the founder's C7 (2026-10-14), `accessibility_states`' fourth test standing as its pin. A Dioxus `bool` attribute arrives as the text `"false"`, so state the literal texts `"true"` and `"false"`: a presence read would read every control pressed. Since 2026-10-17-upstream-sync-engine-debts the builder also holds upstream's `aria-describedby` (→ `described_by`), `aria-description` (→ description), `aria-expanded` (a boolean), `aria-disabled` (`true` → `set_disabled`) and `aria-level` (a number, with the tag and role defaults) reads beside the three, as upstream wrote them; upstream's own `parse::<bool>` `aria-selected` and unfiltered `aria-label` reads were dropped in the merge, so there is still one read per attribute — keep it so. The snapshot takes the three from the tree node, never from the element, reads no description, and reads `enabled` from the `disabled` attribute, so `aria-disabled` moves no snapshot reading; since 2026-10-12-self-description the driver's served node-key help (`help`) states the boolean model's two limits (a mixed toggle reads `pressed` false, a grammar or spelling error reads `invalid` true). Ratified by the founder (2026-10-10); what an assistive technology reads of them is unmeasured — the windowed witness, at an active assistive technology, owned by a `.andromeda/residuals.md` line (target: next) on the founder's F1 (2026-10-14), the headless half — the tree the shell hands the adapter — proven on the stand since 2026-10-14-stand-a11y-assertions.
- Text nodes become `TextRun` nodes and label their parent; an `aria-label` non-empty after trimming sets `label`; a `<label>` is pushed onto its bound `<input>`'s `labelled_by` (`for`-target, else first nested input) after the whole tree is built; since 2026-10-17-upstream-sync-engine-debts an `aria-labelledby` loop runs after that `<label>` → input loop, clears `labelled_by`, pushes the referenced nodes and sets their computed text as the `label`, so it outranks a `<label>` and an `aria-label` (accname 2B) — an id naming no built node ignored, hidden targets read for the label, the `aria-label` the fallback when the targets hold no text.
- `Document::accessibility_tree` (gated `accessibility`) is what the shell builds — on InitialTreeRequested and, on a poll that reported work, when the document's changed set taken by that poll was non-empty (ratified by the founder, 2026-10-07, its windowed witness, at the platform adapter, still owed and owned by a `.andromeda/residuals.md` line (target: next) on the founder's F1 (2026-10-14), both halves proven headlessly on the stand since 2026-10-14-stand-a11y-assertions; before 2026-10-07 the poll-time refresh never ran); a `DioxusDocument` overrides it to set each element node's `author_id` to its stable element id — none on `TextRun`, document-root or `Window` nodes. The workspace pins the Dioxus crates `default-features = false`: the override — and the snapshot model built on it (`DioxusDocument::snapshot`, which takes role, name and focus from this tree, never a second mapping; its text form `Snapshot::to_text` and its diff `Snapshot::diff` read that model and map nothing again) — exists only where a crate names `dioxus-native-dom/accessibility` or depends on one that does (blitz-tests and escher-driver name it; seven_guis names none and gets it through escher-driver, so both its binaries compile these modules — with no platform adapter, so the stand binary still gives no assistive technology a tree).
- Every element an agent can act on — focusable, or an interactive role, or a listener — reads an author key (an HTML `id`); under the same feature `DioxusDocument::unkeyed_actionable()` returns the ones that read a positional path, each with its `remedy()`. `stand_actionable_keys` asserts it empty on the four lean tasks, Home and, since 2026-10-14-stand-requirement-sweep, the three non-lean tasks (Temperature Converter, Circle Drawer with its dialog open included, Cells — keyed by `id:` lines alone), so a new control there needs an `id` — never a `tabindex`, role or focusability change made to satisfy the check.

## Keyboard and focus (SC 2.1.1 · 2.4.3)
- Focusable = holds a sub-document, or it carries no `disabled` attribute (read by presence, any value, since 2026-10-13-stand-keyboard-harness) and `tabindex >= 0`, or (no tabindex) `<a>/<area href>`, `button`, `input`, `select`, `textarea`, `frame`, `iframe`, `summary`. Cached focusability is recomputed on `tabindex`/`href`/`disabled` changes — keep that hook when adding focus-affecting attributes.
- `disabled` is keyed one way since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder): the `DISABLED` state (`:disabled`), click targeting, the Enter and Space activation and focusability all read PRESENCE — `disabled="false"` and a bare `disabled` match `:disabled` and are not focusable, and a bare `disabled` set after creation takes focusability away; a known limit, pinned by `stand_keyboard`: a `<div disabled tabindex=0>` is not focusable where browsers apply `disabled` to form controls only and focus it — its narrowing to `button`, `input`, `select` and `textarea` owned by a `.andromeda/residuals.md` line (target: next) on the founder's C15 (2026-10-14), `stand_keyboard`'s pin standing. dioxus-native-dom removes a falsy value of its 28 boolean attributes — upstream's private `is_bool_attr` predicate, a closed set, since 2026-10-13-upstream-sync-polish-and-ship (`disabled`, `checked`, `hidden`, `readonly`, `required`, `multiple`, `selected`, `open`, `autofocus`, `inert` among them; a framework-written `inert: false` is removed, while the engine honours no `inert`: a truthy one takes no focusability away, and Tab reaches the buttons under `inert: true` and `inert: false` alike — owned by a `.andromeda/residuals.md` line (target: next) on the founder's F3 (2026-10-14), `stand_keyboard::the_engine_honours_no_inert` staying its pin and whether an inert subtree takes a hit unmeasured), so a `hidden: false` element stays displayed and in the tree; an attribute outside that list holding `false` is still written as `"false"`. The snapshot's `enabled` follows the presence reading.
- Tab/Shift+Tab move through `focus_next_node` / `focus_prev_node`; since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder) a pressed Enter on the focused node with no `disabled` attribute (presence) dispatches a Click on a `button`, a `summary`, an `input` of type `submit`, `reset` or `button`, or an `a` with `href`, and a released Space (`handle_key_up`, routed by `events/mod.rs`) the same Click on a `button`, a `summary`, or an `input` of type `submit`, `reset`, `button`, `checkbox` or `radio` — a link takes no Space, a text input and a range input take neither key there; the Click (`Node::synthetic_click_event_data`) is queued by the event driver, so the app's handlers run, then `handle_click`; removing the focused node resets focus to body and runs blur side effects. Since 2026-10-13-stand-keyboard-harness (in every document, ratified by the founder) a pointer click on a `button` (any type) or an `input` of type `submit`, `reset` or `button` focuses it through `generate_focus_events` / `set_focus_to`, then submits the form owner when it is a submit button; a `disabled` attribute still stops the walk first, and a click on any other element — a CRUD row or the list — still clears focus. Since 2026-10-13-range-input-interaction (in every document, ratified by the founder) a focused `input type="range"` with no `disabled` attribute (read by presence) steps up on ArrowRight/ArrowUp, down on ArrowLeft/ArrowDown, to its minimum on Home and its maximum on End, every other key doing nothing; its current value is held apart from the `value` attribute (`RangeInputData`), sanitized to `[min, max]` on the step grid, each change marking the changed set and firing one `input` (none when nothing changes); a click focuses it without moving the value, and a main-button pointerdown sets it from the hit's fraction of the content box.
- `:focus-visible` and `:focus-within` never match — a stand style that relies on them shows no focus ring.
- A Tab / Shift+Tab key-press focus check exists on the stand (`stand_snapshot_state`, through the harness's `press` / `press_with`; `stand_accessibility_ids` pins the lean tasks' `focus_next_node` sequence); a range-input key and click check runs in both layout modes (`range_input_interaction`, a disabled range taking neither keys nor a click; on the stand `stand_act_range` moves the Timer slider through the driver by click and key, and an arrow step after two Tabs leaves it focused with role `Slider`, its name and the forward focus sequence unchanged); since 2026-10-13-stand-keyboard-harness `stand_keyboard` drives Tab, Shift+Tab, Enter, Space and the CRUD list's keys headlessly on the four lean tasks through the same `press` / `press_with`, reading the focused node back per step in both layout modes — each task's stated sequence is the shared table `tab_order` (CRUD six stops, `crud-list` third: it takes `tabindex="0"` and an `onkeydown`, ArrowDown / ArrowUp / Home / End moving the selection, its rows not focusable), and through the driver `stand_act_keys` presses `enter` and `space` on a Tab-focused `counter-increment`; since 2026-10-14-stand-a11y-assertions the walk is also asserted in two enabled states, each reached by keyboard alone (`enable_by_keyboard`), against the shared table `ENABLED_TAB_ORDER` beside `tab_order` in the shared module — the flight booker after `flight-return`, six stops; CRUD after a row is selected, eight — every `controls(task)` id lying in `tab_order` ∪ `ENABLED_TAB_ORDER`, and Enter and Space read as the click of `crud-update` and `crud-delete` (4 rows), so a control enabled after boot needs its place in `ENABLED_TAB_ORDER`.

## Contrast (SC 1.4.3)
- `blitz-paint` carries a Chrome-matching WCAG contrast-ratio helper (`color.rs`); since 2026-10-13-stand-contrast-harness `Harness::text_contrast` in blitz-test-harness (read-only) reads a control's text/background pair as a `TextContrast` (`contrast_ratio`, the WCAG 2.x ratio; `required_ratio` 3.0 for large text, else 4.5), and `stand_contrast` asserts three tables in both layout modes, read by one shared reader whose exempt class is exactly `enabled == Some(false)` — the 18 stand control rows, 14 `TEXT_ROWS` (the CRUD list rows and the text outside the controls) and 19 `STATE_ROWS` (the colour states reached by input, hover and active included) — so SC 1.4.3 is met on every measured non-exempt stand row: since 2026-10-14-stand-a11y-assertions the stand's accent is one step darker in every task CSS that declares it (rest `#3a5ce5`, hover `#2a4cd3`, active `#1f3fc1`, white on each 5.47 · 6.83 · 8.27; the operator's F5, a stand change and no engine change, design-system §Color Palette), where `#4a6cf7` read 4.39 and failed; `text_contrast` reads the declared `:hover` background after `move_mouse_to` and the `:active` one after `mouse_down_at`, and a button with no `:active` rule keeps its hover pair while pressed; the check runs in the workspace `test` leg, per package and in the `a11y` leg.
