## Goal
Give the engine a minimal range interaction model for every document with an `input type="range"`, as the founder
ruled on 2026-10-07 («Пусть будет а», relayed verbatim by the overseer as his chosen option label; the English wording,
"a minimal range interaction model in the engine", is the overseer's). The model has four parts:
- The arrow keys step a focused range input by its `step`: right and up add one step, left and down take one away.
- Home goes to the minimum and End to the maximum.
- A pointer click sets the value by where it lands along the track, and the click focuses the control.
- Every change of value fires an `input` event, so an app's `oninput` runs with the new value.

The founder answered the three P4 forks himself (inputs#I2, inputs#I3; relayed verbatim by the overseer as his chosen
option labels, the English wording the overseer's):
- Q1 «Отдельное текущее значение»: the moved value is held as the control's own current value, apart from its `value`
  attribute (the default value).
- Q2 «Стрелки + Home/End (Рекомендую)»: all four arrows plus Home/End step the value.
- Q3 «Клик даёт фокус (Рекомендую)»: a click focuses the control.

Q1 was not the plan's recommendation, so the plan takes on its stated costs:
- a new `SpecialElementData` variant, a public type change (architecture §Standard Contracts → Nodes and widgets);
- construction seeds the value (`construct.rs`);
- a `value` attribute write re-seeds it, the reset a Dioxus re-render needs (the text input's precedent,
  `mutator.rs:359-368`);
- the snapshot and the form entry list read the current value;
- a larger upstream merge surface.

Today no key or click moves a range input. A key acts only on a focused node holding text-input data
(`events/keyboard.rs:68-100`). `handle_click` has no range arm, so a click on the slider matches nothing and clears
focus (`events/pointer.rs:614-817`). This was measured at 2026-10-07-act-by-id and is pinned by `stand_act_range`, which
this chunk rewrites rather than deletes. The value rules follow the HTML range state's sanitization and step rules,
cited at the code (per architecture §Design Philosophy, "Behave like a browser, and cite the spec"). Every markup number
is read fallibly to a finite value inside `[min, max]` on the step grid, with no panic path (per security-plan §Input
Validation, rows "Markup numeric attributes" and "Layout values"; §Error Handling, Graceful degradation).

The change stays off the driver and the app. The driver gains no verb, key name, cause or text: `click` already lands
at the centre of the bounds, and `press` already names the six keys (`packages/escher-driver/src/execute.rs:351-366`,
`command.rs`). The Dioxus bridge already carries an engine `Input`'s value to `oninput`
(`packages/dioxus-native-dom/src/dioxus_document.rs:377-380`). The Timer's markup does not move (per layout-templates
§Surface: desktop-native → Primary screens). Nothing is painted differently: blitz paints a range input as the default
sheet's bordered box, with no track or thumb (`packages/blitz-dom/assets/default.css:76-81`). The accessibility node
gains no numeric value and no action; either would be a new class on the adapter crossing (per security-plan §Input
Validation; a11y-plan §2).

## Implementation Steps
1. **The value rules, a new module of ours** — `packages/blitz-dom/src/node/range.rs`, exported from
   `packages/blitz-dom/src/node/mod.rs` as `RangeInputData`. It holds the current value, an `f64`, and the pure rules
   over the four attributes `min`, `max`, `step` and `value`, written against
   `https://html.spec.whatwg.org/multipage/input.html#range-state-(type=range)` and its step rules (the URL at the code):
   - **Parsing:** each number is read with the HTML float parser's rules. A parse error, NaN or an infinity counts as
     absent.
   - **Bounds:** `min` defaults to 0 and `max` to 100. A `max` below `min` reads as `min`.
   - **Step:** `step` defaults to 1. A value ≤ 0 or unparsable reads 1. `any` sets no step constraint and steps by 1
     on a key.
   - **Step base:** `min` when it parses, else the `value` attribute when it parses, else 0.
   - **Default value:** `min` when `max < min`, else `min + (max − min) / 2`.
   - **Sanitize:** an unparsable value reads the default value. It is then clamped to `[min, max]` and rounded to the
     nearest step-grid value, the greater on a tie. The result never exceeds the greatest grid value ≤ `max`.
   - **Moves:** one step up or down from the current value, then sanitized. The minimum and the maximum, each
     sanitized. A fraction in `[0, 1]` along the track, mapped to `min + fraction × (max − min)`, then sanitized.
   - **Format:** the current value as a string — the shortest round-trip form, `-0` written `0`. It is rounded to
     the decimals of `step` and the step base, so that 0.1 stepped three times from 0 reads `0.3`.
   - **Tests:** an inline `#[cfg(test)] mod tests` holds each rule as a stated table with its row count asserted. The
     degenerate rows must read finite, inside `[min, max]` and on the grid: `step="0"`, `step="-1"`, `step="any"`,
     `min > max`, `value="abc"`, `value="1e308"`, `min="NaN"`. The module holds no print, log site, `unwrap`,
     `expect`, panic or env read outside its tests. Every public item carries `///`.
2. **The node data** — `packages/blitz-dom/src/node/element.rs`:
   - Add `SpecialElementData::RangeInput(RangeInputData)` and `SpecialElementType::RangeInput`; the latter enum is
     `#[non_exhaustive]` and has no reader.
   - Add arms to the two exhaustive matches here, the `Clone` impl (375-391) and the `Debug` impl (893-913).
   - Add the accessors `range_input_data()` / `range_input_data_mut()`, shaped like `checkbox_input_checked` (594-608),
     and `range_input_value() -> Option<String>`, the formatted current value.
   - The third exhaustive match, the removal walk at `packages/blitz-dom/src/mutator.rs:1080-1103`, gets a
     `RangeInput(_) => {}` arm.
3. **Seeding at construction** — `packages/blitz-dom/src/layout/construct.rs`, in the input match at 437-458:
   - An `input` whose `type` is `range` (ASCII case-insensitive, as the match reads the other types) gets
     `RangeInputData` seeded from its sanitized `value` attribute.
   - The seed happens only when the element does not already hold it, as `create_checkbox_input` does (917-925), so
     a re-construction keeps a moved value.
   - Construction then continues exactly as today, with no early `return`, so the box built is unchanged.
   - An `input` that holds `RangeInput` but no longer reads `type="range"` has the data cleared to `None`.
4. **An attribute write re-seeds** — `packages/blitz-dom/src/mutator.rs` `set_attribute`, beside the text input's `value`
   branch (359-368):
   - On an element holding `RangeInput`, a `value` write sets the current value to the sanitized new attribute.
   - A `min`, `max` or `step` write re-sanitizes the current value against the new bounds.
   - `clear_attribute` (411) does the same for a removed `value`, `min`, `max` or `step`.
   - The mutator's own in-document marking of the changed set is kept; nothing reaches past it.
5. **The keys** — `packages/blitz-dom/src/events/keyboard.rs` `handle_key_or_input_event`, after the text-input branch
   (68-100). When the focused target is an element holding `RangeInputData`, it has no `disabled` attribute (presence,
   as `ClickTarget::Disabled` reads it), and the key event is pressed:
   - `ArrowRight` and `ArrowUp` step up, `ArrowLeft` and `ArrowDown` step down.
   - `Home` moves to the minimum and `End` to the maximum.
   - Every other key does nothing here.

   When the new value differs from the old one, the engine:
   - writes it into the data;
   - inserts the node into `changed_nodes`;
   - dispatches `DomEventData::Input(BlitzInputEvent { value })` carrying the formatted value;
   - requests a redraw, the shape of `keyboard.rs:119-127`.

   An equal value does nothing and fires no event. The node is resolved with `get`, never by index.
6. **The click** — `packages/blitz-dom/src/events/pointer.rs`:
   - **Pointerdown:** `handle_pointerdown` gains a `ClickTarget` arm for a hit element holding `RangeInputData`,
     taken after the `disabled` check (457), so a disabled range does nothing. On the main button its fraction is
     `(hit.x − (padding.left + border.left)) / content-box width`, clamped to `[0, 1]`; a content box of no width
     reads fraction 0. This is the frame the text input's caret mapping uses (459-462, 506-507), correct under
     scrolled boxes. The value set from the fraction then takes step 5's write, mark, `Input` and redraw when it
     changed.
   - **Click:** `handle_click` gains an arm for an `input` holding `RangeInputData`, placed after the `disabled`
     check (635-638). It focuses the control through `generate_focus_events` → `set_focus_to`, as the checkbox arm
     does (658-664), and breaks with `matched` true. It changes no value: a label's synthetic click focuses the
     slider and leaves its value alone.
   - The track is horizontal and left to right only.
7. **Form submission reads the current value** — `packages/blitz-dom/src/form.rs` `construct_entry_list`, in the entry
   at 316-319: an input holding `RangeInputData` submits its formatted current value before the `value` attribute
   fallback. Add an inline `#[cfg(test)] mod tests` that builds a form holding a range input through `DocumentMutator`,
   with `resolve(0.0)` (elements made with `qual_name!(…, html)`). It moves the value through the data and asserts
   that the entry list carries the moved value, not the attribute.
8. **The snapshot reads the current value** — `packages/dioxus-native-dom/src/snapshot.rs` `value` (198-225):
   - A range input reads `range_input_value()`, and an element without the data still reads its `value` attribute.
     The field's doc line (55-58) is updated to say so.
   - Rename the unit test `a_range_input_reads_its_value_attribute` (591-605) to
     `a_range_input_reads_its_current_value`; it still reads `15` at boot.
   - Add a unit test: an uncontrolled range input, with no `oninput`, focused and sent one `ArrowRight` key-down
     through the document's event handling, reads the moved value. Its `value` attribute still reads the boot value.
9. **The engine check** — new `tests/blitz-tests/tests/range_input_interaction.rs`. It opens with a `//!` doc and drives
   inline-HTML fixtures through `blitz_test_harness::Harness` in both layout modes (`for incremental in [false, true]`).
   It first asserts that the fixture holds a range input with the data seeded. It reads the current value through
   `ElementData::range_input_value` and the events through `dispatch_recorded`, and asserts unconditionally:
   - **Keys:** a stated table with its row count asserted. On `min=0 max=10 step=2 value=4`, focused:
     - right → `6`, up → `8`, left → `6`, down → `4`, End → `10`, Home → `0`;
     - Home again → no change and no `input` event;
     - each change → exactly one `input` event.
   - **Click:** `click_at` at content-box fractions 0, 0.25, 0.5 and 1, and at a point in the left padding, reads the
     sanitized value each maps to, computed from the input's laid-out box. After each click the harness's focused
     node is the input.
   - **Degenerate attributes:** a stated table of the step 1 rows, each driven by a right arrow and a centre click,
     completes with no panic. Each reads finite, inside `[min, max]` and on its grid.
   - **Decimals:** `step="0.1"` stepped three times from 0 reads `0.3`.
   - **Disabled:** a disabled range takes neither keys nor a click. The value is unchanged and no `input` event fires.
   - **Attribute writes:** `doc.mutate().set_attribute(value)` re-seeds the current value, sanitized (`7` on the step-2

   The file prints nothing, installs no subscriber and reads no env var. A failure message carries the mode and a row

## Constraints & rejected approaches
- Holding the moved value in the `value` attribute — rejected by the founder's Q1 answer (inputs#I2), though it was the
  plan's recommendation.
- A numeric value or Increment/Decrement/SetValue actions on the slider's accessibility node — rejected: a new class on
  the platform adapter crossing, a founder question (security-plan §Input Validation; a11y-plan §2).
- Painting a track or thumb, a drag, a `change` event, Page Up/Down, or a vertical or right-to-left track — rejected:
  outside the ruled minimal model. blitz-traits has no `change` event and the driver has no drag or Page key (scope,
  Boundaries).
- A new driver verb, key name, cause or help text — rejected: the six keys and the centre click already exist
  (`packages/escher-driver/src/command.rs`, `execute.rs:351-366`).
- Any edit to the Timer's markup, id, class or style, or a CSS selector on `timer-duration` — rejected (layout-templates
  §Surface: desktop-native → Primary screens). A position other than the centre is proven by the engine check's
  `click_at`, and on the stand by clicking after a key step has moved the value.
- An early `return` in the range construction arm — rejected: it would skip the construction an input gets today and
  could change its box. Construction must stay identical.
- A log site, span field or print holding a range value, attribute or click position — rejected (obs-plan §8;
  security-plan §Logging & Monitoring).
- Any mutation control or mutation-tier run — rejected on the founder's standing word (inputs#I1).
