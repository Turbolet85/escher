## Goal
Build the contrast verification harness that a11y-plan §3 records as observed absent and §6 records as NOT YET MEASURED,
and take its reading on every stand control. `blitz-test-harness` gains a `contrast` module: a WCAG 2.x contrast ratio,
and `Harness::text_contrast`, which reads a control's text colour and the background that text is painted on from the
engine's computed styles. The background is resolved up the ancestor chain to the canvas, by the rule blitz-paint paints
the canvas with. The module also states the SC 1.4.3 threshold the text's computed size and weight call for (per
a11y-plan §1, §3, §6; architecture §Standard Contracts → Test harness).

A new stand check, `stand_contrast`, boots each lean task through the stand in both layout modes. It measures every row
of the shared `controls(task)` table, 18 rows naming 15 controls, and records one result per row:
- **pass** or **fail** — the colours, the ratio, the size, the weight and the verdict against the threshold;
- **exempt-inactive** — the control reads not enabled;
- **no-text** — the range input, which paints no text.

The record is the check's own stated table: the check asserts the reading equals that table, row for row, in both modes.
A second test proves the measurement against what is painted: the pixel inside each measured control's left padding,
taken from the harness's raster, is the background the reader resolved (per test-plan §1, §3; a11y-plan §3, §7).

This chunk measures and records; it gates nothing and re-colours nothing. Asserting SC 1.4.3 on every control, and the
CI leg that gates merges on it, belong to "Stand a11y assertions" (working-route.md:94). The check runs in the workspace
`test` leg and per package, never in the `a11y` leg (per a11y-plan §9; test-plan §9). No engine crate changes. The
ratio is the harness's own, computed with the same `color` crate luminance blitz-paint's `pub(crate)` helper uses, so the
two agree by construction (per architecture §Conventions → Visibility and naming).

## Implementation Steps
1. **Take the colour type into the harness.** Add `color = { workspace = true }` to `[dependencies]` in
   `packages/blitz-test-harness/Cargo.toml` (`Cargo.toml:132` declares `color = "0.3"` for the workspace; blitz-dom
   already takes it, `packages/blitz-dom/Cargo.toml:75`). `Cargo.lock` gains the dependency line in blitz-test-harness's
   entry and no `[[package]]`. Record the lock delta in `evidence/counts.md`.

2. **The ratio.** In the new `packages/blitz-test-harness/src/contrast.rs`, state
   `pub fn contrast_ratio(a: Color, b: Color) -> f32`. `Color` is `color::AlphaColor<color::Srgb>`, the engine's colour
   model, the type `blitz_dom::util::ToColorColor::as_color_color` returns (`packages/blitz-dom/src/util.rs:166-179`).
   - Compute WCAG 2.x's `(L1 + 0.05) / (L2 + 0.05)`, the larger over the smaller, with `L` from the `color` crate's
     `OpaqueColor::relative_luminance` after the alpha is split off. That is blitz-paint's formula exactly
     (`packages/blitz-paint/src/color.rs:29-35`).
   - The `///` doc names WCAG 2.x and Chrome's `GetContrastRatio`, and says the alpha is ignored. A caller composites a
     translucent colour first.

3. **The reading.** In the same module, state `pub struct TextContrast` with public fields:
   - `text: Color` — the effective text colour, opaque;
   - `background: Color` — the effective background colour, opaque;
   - `ratio: f32` — `contrast_ratio(text, background)`;
   - `font_size_px: f32` — the computed `font-size` in CSS px;
   - `font_weight: f32` — the computed `font-weight`.

   Give it two methods:
   - `is_large_text()` — true when `font_size_px >= 24.0`, or when `font_size_px >= 56.0 / 3.0` (14 pt) and
     `font_weight >= 700.0` (WCAG 2.x "large scale": 18 pt, or 14 pt bold, at 1 pt = 4/3 CSS px).
   - `required_ratio()` — `3.0` when the text is large, else `4.5` (SC 1.4.3).

   Derive `Clone, Copy, Debug, PartialEq`. Put `///` on the struct, every field and both methods.

4. **The reader.** In the same module, add `impl<D: Document> Harness<D> { pub fn text_contrast(&self, node_id: NodeId) -> Option<TextContrast> }`,
   the impl-block shape of `inspect.rs` (`packages/blitz-test-harness/src/inspect.rs:26`). It reads, and changes nothing.

   **The text-bearing element** is one of:
   - `node_id` itself, when it is a text input (its element's special data is the text input's, which paints its value
     in its own computed `color` at its computed size, `packages/blitz-dom/src/layout/construct.rs:875-910`);
   - otherwise the parent element of the first text node, in tree order under `node_id`, whose text holds a character
     that is not whitespace. Paint strokes a glyph in the computed `color` of its brush node,
     `packages/blitz-paint/src/text.rs:616-638`, which reads the colour by `resolve_decoration_entry`, the node's
     inherited-text `color`, `packages/blitz-paint/src/text.rs:156-167`.

   No such element → `None`. The range input `timer-duration` is the stand's case.

   **The text colour and font** come from that element's primary styles:
   - its computed `color`, resolved to absolute and converted through `as_color_color`;
   - its computed `font-size` (the used size, in px);
   - its computed `font-weight`.

   **The background** walks from that element up its ancestors to the root. At each element, its computed
   `background-color`, resolved against its own `color` (`packages/blitz-paint/src/render/background.rs:334-336`), is
   gathered while it is not fully opaque, and the walk stops at the first fully opaque one. The gathered layers are
   composited source-over, the nearest on top, over the first opaque layer.
   - With no opaque layer before the root, the canvas follows `packages/blitz-paint/src/render.rs:193-219`: the root
     element's `background-color`, else `body`'s when the root's is transparent.
   - If the canvas is transparent too, the base is opaque white, the white `Harness::screenshot` composites over.

   **The text colour is composited** over the resolved background when its alpha is below 1.

   **An element on the walk returns `None`** when it lies between the text-bearing element and the first opaque layer,
   that element included, and it carries any of:
   - a background image layer that is not `none`;
   - an `opacity` below 1;
   - a `filter` that is not `none`.

   Colours alone do not determine such a pair, and the `///` doc says so. The stand has none (research.md, Sweeps).

   **Every node is reached through `get_node`.** No `NodeId` is indexed, and no `primary_styles()` result is unwrapped: a
   node without styles reads `None`. There is no `doc.mutate()`, no input, no pump and no settle. The reader prints, logs
   and panics on nothing (per security-plan §Error Handling, Panic paths; obs-plan §3, §4).
