## Goal
Prove that the stable element id built by `2026-10-06-stable-element-ids` persists on the stand. Every lean-task element keeps its id across a re-render, a remount, and a restart in a new process (`verification-matrix.json#v010-02`).

Research found that persistence holds by construction. The id is a pure function of the rendered component chain, Dioxus keys, tag structure and HTML `id` attributes. No runtime identity enters it, and no output depends on hash order (research.md §Patterns detected; per architecture §Standard Contracts → Dioxus DOM bridge). So the chunk's work is mostly proof: three stand checks, each built so that it fails unless its event really happened.

One code change closes the folded CARRY. CRUD rows are keyed by their list index, so after a Delete a person's row takes another person's id. Rows are re-keyed on a stable person id from `crud.rs`'s own model. Then a person's row id follows the person, which is what Epoch 4's act-by-id will rely on.

The remount runs through the app's own Back → Home → task-card navigation. The test boots `seven_guis::app::app` with the stand's pinned options, so `seven_guis` needs no new API and the remount is one a user can perform.

The fresh-process proof re-executes the test binary as a child. This is the in-repo precedent at `tests/blitz-tests/tests/telemetry_stdout_silent.rs:10-11` (per test-plan §1, the escher-telemetry process-global files).

   e. Because the fixture ids equal the old fixture indices, the first row still reads `TaskShell/Crud/div:0/div:1/div:0/div[0]`. The pin at `stand_element_ids.rs:227-231` holds unchanged.
2. **New stand check file** `tests/blitz-tests/tests/stand_id_persistence.rs`.

   - Input goes only through harness helpers (`click`, `type_text`); timer ticks go through `TimerTicks::deliver` + `pump`.
3. **Test `ids_hold_across_rerenders`.** For each lean task and both modes, read `doc.element_ids()` before (`B`) and after (`A`) the task's scripted re-renders. Then assert all of the following.
   - The re-render happened: `harness.dom_string()` after differs from before.
   - Every `NodeId` present in both `B` and `A` reads the same id in both.
   - The scripted re-renders:
     - **Counter:** click `#counter-increment` twice.
     - **Flight booker:** click `#flight-return`, which toggles `disabled` on `#flight-return-date`. Then click `#flight-book`, which inserts `p#flight-booked`. Assert the inserted node reads `flight-booked` and the ids of all earlier elements are unchanged.
     - **Timer** (via `boot_timer`): `deliver(5)` + `pump`. `#timer-elapsed` text changes and the ids are unchanged.
     - **CRUD:** the four scenarios below.
   - **CRUD scenarios.** Map each row's text (`"{last}, {first}"`) to its id before and after each scenario.
     - Filter: click `#crud-filter`, type `M`. One row remains, and `Mustermann, Max` reads the same id it read before the filter.
     - Delete: on a fresh boot, click the `Emil, Hans` row, then `#crud-delete`. `Mustermann, Max` and `Tisch, Roman` read the ids they read before, `…/div[1]` and `…/div[2]`. No row reads `…/div[0]` any more.
     - Create: type a name and surname, click `#crud-create`. The new row reads `TaskShell/Crud/div:0/div:1/div:0/div[3]`, and every earlier row reads its earlier id.
4. **Test `ids_hold_across_a_remount`.** Boot a test-side root in both modes: a `fn` component that provides `seven_guis::tasks::timer::TimerTicks::default()` as context and returns `seven_guis::app::app()`. Boot it with `Harness::from_vdom(VirtualDom::new(root), stand::options(incremental))`. Then, for each lean task's card in `#task-grid` (Counter 1, Flight booker 3, Timer 4, CRUD 5 by `:nth-child`, app.rs:24-67):
   a. Click the card and read `before = element_ids()`. Assert `#task-shell` is present. Also assert `before`'s id strings equal, in order, the id strings of `stand::boot(task, stand::options(incremental))`. This is the app-root/stand-root equality from research.md §Patterns detected.
   b. Click `#back-btn`. Assert `#task-shell` is absent and `#home` is present, so the task really unmounted.
   c. Click the same card again and read `after = element_ids()`. Assert:
      - `after`'s id strings equal `before`'s, in order.
      - No `NodeId` in `after` appears in `before`, so the remount minted fresh nodes.
      - `doc.element_id(n)` is `None` for every `NodeId` `n` in `before`, with no panic.
      - `harness.focused()` is not any `NodeId` of `before` (per a11y-plan §5 → Focus restoration).
5. **Test `ids_hold_across_a_fresh_process`, and its child.**
   - The parent computes the id strings of `stand::boot` for each lean task in both modes. The timer goes through `boot_timer` with no ticks delivered.
   - It then runs `std::process::Command::new(std::env::current_exe()…)` with `["--ignored", "--exact", "ids_in_a_child_process", "--nocapture"]`, the precedent form at `telemetry_stdout_silent.rs:10-11`.
   - The child, `#[test] #[ignore = "spawned as a child process by ids_hold_across_a_fresh_process"]`, prints one line `pid {std::process::id()}`. Then, for each task and mode, it prints one line per id, each prefixed with a fixed marker that the parent filters on.
   - The parent asserts:
     - the child exited successfully;
     - the child's pid differs from `std::process::id()`;
     - the child's id list is non-empty for every task and mode;
     - the child's list equals the parent's, in order.
   - The ids travel only over the child's captured stdout into the parent's assertion. They are never logged and never committed (per obs-plan §8; security-plan §Logging & Monitoring).
6. **Leave everything else unchanged.** That covers the manifests and `Cargo.lock`, `packages/` (`element_id.rs` included), `app.rs`, `stand.rs`, `counter.rs`, `flight_booker.rs`, `timer.rs` and `scripts/` (the diff-guard entry). ## Constraints & rejected approaches
- A `stand::boot_app` or a stand-side remount handle — rejected at P4 by the operator. The remount check boots `app::app` from test code, and `seven_guis::stand` gains nothing.
- Keeping CRUD rows keyed by `{i}` — rejected at P4 by the operator. After a Delete, an id an agent holds would name a different person (research.md §Patterns detected, index keys).
- Two boots inside one process as the "fresh process" proof — rejected. The matrix acceptance says "a restart in a new process", and only a separate OS process can expose process-global state leaking into an id.
- Routing the fresh-process check through `scripts/agent-run.sh` — rejected. It would change a contract pinned by `test_agent_run.py` for no gain, while the re-exec precedent needs no script.
- A person id from a pointer, hash, `RandomState`, clock or process counter — rejected. It would break the cross-process equality and the `id` row's no-pointer clause (security-plan §Input Validation).
- Adding an author `id`, wrapper, class or `tabindex` to make an id persist — rejected. Research found no lean-task re-render that shifts a positional part (scope.md, premise-corrected), and layout-templates bans structural ids.
- Asserting the remount only on ids — rejected. A check that does not also show fresh `NodeId`s and a vanished `#task-shell` would pass vacuously (test-plan §4 Conditional assertions).

## Implementation notes
- **Fixture ids equal the old indices.** Ids `0`, `1`, `2` keep `stand_element_ids.rs:227-231`'s first-row pin `…/div[0]` and `text_and_removed_nodes_read_no_id`'s single-removed-node assertion true. The test asserts only that exactly one row node left the list and reads `None`, which holds either way (`stand_element_ids.rs:251-269`).
- **Positional parts this chunk does not exercise.** `{tag}:{n}` and `{name}:{k}` stay positional. No lean-task re-render inserts an unkeyed element before another element (scope.md, premise-corrected: flight_booker.rs:107-109, crud.rs:63, counter.rs:11, timer.rs:74-76). A future task with an unkeyed conditional sibling would need an author key there.

Otherwise `Timer`'s coroutine falls back to a wall-clock `futures_timer::Delay` (timer.rs:53-56), and its text would change between reads. The ids would not change, but the boot stops being deterministic.
