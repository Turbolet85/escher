## What this chunk builds
The stable element id built by `2026-10-06-stable-element-ids` (`DioxusDocument::element_id` / `element_ids`) is proved to **persist**: an element keeps the same id across a re-render, a remount, and a fresh process. intent §Findings 1 names the gap this closes. A `NodeId` is a versioned slot that a remount re-mints, so an agent holding one between actions aims at nothing. An id that survives re-render and remount is what snapshot diffs (Epoch 3) and act-by-id (Epoch 4) rest on. Capability v010-02 (`verification-matrix.json#v010-02`, method `e2e`): "For each stand element, the id read before and after a re-render, a remount, and a restart in a new process is the same."

- **Re-render** — a state change that re-renders a task's components without unmounting them (counter increment, flight-booker field edit, timer tick, CRUD filter or selection) leaves every surviving element's id unchanged. The id is a pure function of the rendered component chain, keys, tag structure and `id` attributes, with no runtime identity and no hash-ordered output (research.md §Files inspected, element_id.rs:153-228). It is therefore persistent by construction for every element whose own path survives. `[premise-corrected: a disabled toggle is an attribute change, not a shape change (flight_booker.rs:89, 96; crud.rs:107, 121); the lean four's shape-changing re-renders are flight booker's p#flight-booked inserted as the last, author-keyed child (flight_booker.rs:107-109) and CRUD's keyed rows filtered, created and deleted (crud.rs:57-63) — research.md §Files inspected]` The re-render checks cover those shape changes as well as the text- and attribute-only ones.
- **Remount** — the same element, unmounted and mounted again, reads the same id. Verified (research.md): the stand has no remount path today. `stand::boot` mounts one task through `task_in_shell` with a no-op `on_back` (stand.rs:100-102). `seven_guis::app::app` is `pub` (lib.rs:1; app.rs:69-79) and navigates Home ⇄ task through `#back-btn` and `button.task-card`. Its task ids equal `stand::boot`'s by construction, because both roots are `ScopeId::APP` and render `task_in_shell` directly (app.rs:77, stand.rs:102, element_id.rs:47-54). Unmount detaches, and remount deep-clones templates into newly created slab nodes (mutation_writer.rs:189-193, 290-303; mutator.rs:533; document.rs:844-855). So every post-remount `NodeId` differs from the pre-remount one, and the check asserts that difference. Whether the remount goes through the app's own Back → Home → task-card path or through a stand-side handle is a P4 fork.
- **Fresh process** — a stand task booted in a second OS process reads the same id set as one booted in the first. Two boots inside one process do not satisfy "a restart in a new process" (the matrix acceptance verbatim). Verified (research.md): the repository already re-executes its own test binary as a child. `telemetry_stdout_silent.rs:10-11, 32-33` runs `current_exe()` with `--ignored --exact child_emits --nocapture` against an `#[ignore]` child test in the same file, with no env var, port or script involved. element_id.rs puts no process-global value into an id, and no output depends on hash iteration order (element_id.rs:153-228). The check is still the empirical proof of that.
- **Positional id parts (CARRY, folded verbatim):** "CARRY: positional id parts (from 2026-10-06-stable-element-ids) — the lean CRUD rows carry the Dioxus key `{i}`, their index in the people list, so a row's id follows its position, not its person: after a Delete the remaining rows re-read `TaskShell/Crud/div:0/div:1/div:0/div[0]` … and the DOM node dropped is the last row's (measured at `stand_element_ids::text_and_removed_nodes_read_no_id`); `{tag}:{n}` indices and the `{name}:{k}` component ordinal are positional too (arch §Standard Contracts → Dioxus DOM bridge)". Coordinates re-verified at take-up: `examples/seven_guis/src/tasks/crud.rs:63` carries `key: "{i}"`, and the named test is at `tests/blitz-tests/tests/stand_element_ids.rs:237`. The mechanism claim is that after a Delete a person's row reads its new position's id and the last row's DOM node is the one dropped. It is a measured claim from the prior chunk. It was re-derived at HEAD: `key: "{i}"` is the index in the full people list (crud.rs:57-63), and Delete removes `people[idx]` (crud.rs:126). Every later person therefore takes the key one lower, and the keyed diff drops the last key's node (research.md §Patterns detected). Whether a CRUD row's id must follow its **person**, which means re-keying the rows by a stable person identity in `crud.rs`'s model, or whether position-keyed is the persistence the acceptance asks for is a P4 fork. Two forms of the acceptance's "same element" are in play: the same DOM node, or the same semantic entity. A list edit is a re-render, so this fork decides what the CRUD re-render check asserts.
- **Positional `{tag}:{n}` and `{name}:{k}` parts** — an unkeyed sibling that appears or disappears before an element shifts that element's `n`. `[premise-corrected: no lean-task re-render inserts or removes an unkeyed element before another element. flight booker's only conditional element is the last, author-keyed p#flight-booked (flight_booker.rs:107-109), CRUD's rows are Dioxus-keyed (crud.rs:63), and counter and timer re-renders change text and style only (counter.rs:11, timer.rs:74-76) — research.md §Files inspected]` No grammar change and no new author key is needed for the lean four. The grammar stays this chunk's input, not its output. A future task with an unkeyed conditional sibling would need an author key there; that is out of scope here.
- **Proof checks** — stand checks per lean task, as integration tests in `tests/blitz-tests/tests/stand_*.rs` (one file per behaviour), under the workspace test leg, `for incremental in [false, true]`. Each check reads `element_ids()` before and after a re-render and a remount and asserts each surviving element's id is the same. A fresh-process check compares the id list across two processes. Every check must also show that the event really happened: the re-render changed the DOM, the remount minted fresh `NodeId`s, and the processes were distinct.
