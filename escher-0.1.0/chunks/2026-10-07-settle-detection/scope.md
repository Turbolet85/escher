## What this chunk builds
The driver's second piece, after the session: a way to know that a held headless instance has **gone quiet** after a step, and to reach that state without the caller sleeping, pumping or waiting on its own. intent §Principles orders it between change tracking (built) and the command and refusal model (next entry); intent §5 states the observed gap — "a check must pump or wait on its own" — and the expectation it serves: acting "returns only once the UI has settled, so a stand flow with a delayed update passes with no sleep anywhere in the check".

- **Quiescence is one answer over four sources** — the entry names them: render, layout, timers and pending loads. The instance is settled when none of the four has work outstanding; one source still busy means not settled.
- **Render** — the app's own pending work: a dirty component, a woken task, a queued mounted event. The signal is the one `Document::poll` already returns — `DioxusDocument::poll` returns `true` after a render pass and the sub-documents' answer when the VirtualDom has no work (`packages/dioxus-native-dom/src/dioxus_document.rs:256-286`); the trait default returns `false` (`packages/blitz-dom/src/document.rs:141-145`); `Harness::pump` discards it (`packages/blitz-test-harness/src/harness.rs:123-126`). One poll is not always enough: a poll delivers `mounted` events after it renders (`dioxus_document.rs:283` · `219-239`), so a `mounted` handler that writes state leaves a dirty component only the next poll renders (by code read, not measured — the bridge test covers delivery, not a handler's write).
- **Layout** — style and layout resolved for everything the last render changed. `[premise-corrected: one resolve is not always enough — resolve.rs:60-62 · 131-138]` `resolve` returns before styling while a head stylesheet is still loading (`packages/blitz-dom/src/resolve.rs:60-62`), and it ends by re-resolving the hover node against the fresh layout, leaving any restyle that causes "for the next resolve pass" and dropping the changed-or-not answer (`resolve.rs:131-138`; `refresh_hover` returns it, `document.rs:1942-1949`). A resolve never queues a device change itself — only `set_viewport` and the media setters do (`document.rs:1959-1963`) — and sub-documents are resolved inside their parent's pass (`resolve.rs:140-164`).
- **Timers** — a delayed update the app has scheduled. On the stand that is the Timer task's coroutine, which awaits the stand's tick seam (`TimerTicks`, `examples/seven_guis/src/tasks/timer.rs:10-41`): a delivered tick is applied only when the VirtualDom is next polled, so a tick delivered and not yet applied is outstanding work. The headless stand never takes the 100 ms wall-clock arm (`timer.rs:53-56`): `stand_root` always provides the tick context (`examples/seven_guis/src/stand.rs:100-103`). That coroutine is the only asynchronous source on the four lean tasks (grep `spawn(|use_effect|use_resource|use_future|onmounted|use_coroutine|async move` over `examples/seven_guis/src`: 5 hits, 2 in `timer.rs`, 3 in `circle_drawer.rs`, which is not a lean task).
- **What settle answers for a source that only time moves** is a decision this chunk makes and states, and the code narrows it: the engine's animating reader (`BaseDocument::is_animating`, `document.rs:2039-2056`) ORs in a canvas (always animating), a custom widget asking for redraw, a scroll animation and the overlay-scrollbar fade — and the last reads the wall clock (`scrollbars_animating`, `document.rs:1801-1806`, `Instant::elapsed`). The one existing loop that waits for it to read false sleeps 8 ms a turn under a 5 s timeout (`tests/blitz-tests/tests/fragment_navigation.rs:31-42`). So "wait until nothing is animating" cannot be built without a sleep; a periodic source never goes quiet on its own either. The stand's styles carry no transition, animation or keyframes (grep `transition|animation|@keyframes` over `examples/seven_guis/src`: 0 hits).
- **Pending loads** — a resource requested and not yet answered: an image, a stylesheet, a font, a sub-document. `[premise-corrected: the document tracks three of seven fetch sites, and one named collection is not a request list — research.md §Patterns detected]` The engine issues requests at seven sites (grep `net_provider.fetch|network_provider.fetch` over `packages/blitz-dom/src`) and tracks three kinds as pending: a head stylesheet (`pending_critical_resources`, `mutator.rs:1150-1154`, read by `has_pending_critical_resources`), an image by URL (`pending_images`, both image sites) and an iframe's HTML (`iframe_loads`, `iframe.rs:81-95`). A body stylesheet, an `@import` (`net.rs:225`), an `@font-face` source (`net.rs:503`) and a stylesheet reload (`document.rs:1114`) are in flight with no record on the document. `pending_style_image_nodes` is a work queue drained inside the same resolve (`layout/damage.rs:431`), not a list of requests. An answered load is applied by `handle_messages` at the start of `resolve` (`resolve.rs:49`; `document.rs:1243-1254`), never by `poll`. Every request does pass through the document's one `NetProvider` (`blitz-traits/src/net.rs:19-30`).
- **The loads leg needs a fixture** — the stand is offline (`net_provider: None`, `stand.rs:65`), so no lean task ever has a load pending: this leg is proven on a minimal fixture beside the stand (intent §Principles, "The stand is the proof" — the founder's ruling, 2026-10-06), with a hand-written net provider the check answers itself. The existing one (`ManualNetProvider`) is private to `tests/blitz-tests/tests/render_blocking_stylesheet.rs:17-30`.
- **A wait that ends** — settling is a bounded loop of polls and resolves, never a sleep and never a wall-clock read: `poll(None)` uses a no-op waker (`dioxus_document.rs:257-261`) and `resolve` takes the harness's own clock value (`harness.rs:125`). So the loop needs no clock, and its bound can be a count of passes. An instance that does not go quiet inside the bound ends in a typed outcome that says which source was still busy, rather than hanging the caller or returning as if settled — what this chunk builds, stated here as intent; the plan gives it its shape.
- **The check on the stand (the in-process leg of v010-10; the cap itself is not claimed here — Boundaries)** — a stand flow on the Timer task in which the update lands after the step through the async path, and the check holds the post-step state the moment the step returns: no `sleep`, no wait and no pump of its own anywhere in the check, in both layout modes. Today every such check pumps by hand after delivering ticks (`tests/blitz-tests/tests/stand_timer.rs:13-14` · `27-28` · `41-42`; `stand_session_state.rs:150-151` · `162-163`; `session_common/mod.rs:51-54`).
- **Reachable from the session** — the held instance is already reachable: `Session` hands out the bare harness (`packages/escher-driver/src/session.rs:53-61`), so anything the harness gains is callable through it with no session change; a session-level entry point is the plan's choice. The session host keeps the timer's `TimerTicks` handle alive for the session's life and does nothing with it (`examples/seven_guis/src/session_host.rs:34-45`). The driver-session scope's forward note — "the later Settle detection entry advances it" — stays a hypothesis: a recorded check pins the opposite today, "timer time moves only with delivered ticks" (`stand_session_state.rs:132-169`).
