## Patterns detected
- **Password value is unmasked today** (`snapshot.rs:177-193`; `construct.rs:449-453`): `value(element)` returns `Some(editor text)` for `input type="password"` — the type is absent from the excluded list and box construction gives it an editor. The equality the mask criterion needs: *for a password input whose editor holds a non-empty text T, the snapshot's `value` does not contain T* — false at HEAD by this read; the chunk's first test asserts it red-first.
- **No second path carries a typed password** (`accessibility.rs:74-104`; `mutator.rs:1245-1252`): the tree gives an element node no value, and a name comes only from text-node children, `aria-label` and a bound `<label>`. Typed text lives in the editor, not in a DOM text node, and a `value` attribute becomes a text child only for `button | submit | reset` inputs. So the mask belongs in `snapshot.rs` alone and nothing changes in the tree the platform adapter reads. The proof still asserts absence over every field of every node.
- **The password is painted in the clear** (`grep -rn -i password packages --include=*.rs --include=*.css` → 4 engine sites: `keyboard.rs:157`, `accessibility.rs:270`, `layout/mod.rs:241`, `construct.rs:451`; none masks): the engine lays out and paints a password input's characters like any text input's. Outside this chunk (paint, not the snapshot) — surfaced, not fixed.
- **`enabled` already follows the reader that decides what a click does** (`snapshot.rs:134-136`; `element.rs:445-451`; `pointer.rs:330`, `:457`, `:635`): presence of `disabled` is the `DISABLED` state, `:disabled`, and the click target's reading — one reader, three sites. The other reader, focusability, parses a bool (`element.rs:629`) and disagrees for `disabled="false"` and for a bare `disabled`. The HTML standard defines a boolean attribute by presence, so presence is the spec reading; the focusability parse is the engine's deviation.
- **A Dioxus document cannot carry `disabled="false"` through the bridge** (`mutation_writer.rs:215-224`, `:407-408`): `Text("false")`, `Bool(false)`, `Int(0)`, `Float(0.0)` and `None` are all cleared, for dynamic and static attributes alike. Markup set through `dangerous_inner_html` (`:409-410`) is parsed, not bridged, so it is the one way a Dioxus document holds the disagreeing input — the fixture for the reader pin.
- **A Dioxus `hidden: false` element is not displayed at all** (`mutation_writer.rs:280-282`, `:411-413`; `stylo.rs:1191-1194`; `accessibility.rs:114-124`): `Bool(false)` is written as `hidden="false"`; the presentational hint gives any `hidden` attribute `display: none`; a `display: none` node and its subtree leave the accessibility tree, hence the snapshot. The hypothesis holds by this three-link read — and it is wider than stated: the element is absent from the screen too, so the snapshot is *faithful to the screen*; the defect is the bridge writing `"false"`, where Dioxus's own web renderer removes the attribute (`inputs#I1`). Not run here; the regression test establishes it red-first.
- **Which of the seven `"false"` attributes the engine reads at all** (`grep -rn 'local_name!("(readonly|required|hidden|multiple|selected|open|autofocus)")' packages/{blitz-dom,dioxus-native-dom,blitz-shell,blitz-paint}/src` → 5 hits): `hidden` (`stylo.rs:1191`, presence → `display: none`), `open` (`document.rs:719`, presence → a `details` reads open; `default.css:894-900`, `:974`), `multiple` (`accessibility.rs:240`, presence → a `select` reads `ListBox`; `pointer.rs:772`, file dialog), `autofocus` (`mutator.rs:966`, value `"true"` only — a `"false"` is already inert). `readonly`, `required`, `selected`: 0 readers. **None of the seven feeds `enabled`, `checked`, `value` or `focused`.**
