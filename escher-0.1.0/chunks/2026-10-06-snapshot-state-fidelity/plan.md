## Goal
Make the snapshot's state record true, and prove it per control. The four fields every snapshot node already
carries — `enabled`, `checked`, `value`, `focused` — were filled from existing engine readers by the snapshot-model
chunk without proof. This chunk proves each reading on the headless stand through real input (a click, typed text,
a Tab key press), proves the two cases the 7GUIs tasks lack (a checkbox or radio, a password input) on a minimal
fixture beside the stand, and closes the one reading that is wrong today: **a password input's value reads its typed
text in the clear** (research.md §Patterns detected). After this chunk it reads a fixed mask (per security-plan
§Input Validation, the `id` and accessible-names rows; architecture §Standard Contracts → Dioxus DOM bridge).

Three decisions shape the work:
- **The mask is a fixed marker** — answered at P4's question round by the operator, 2026-10-06. An empty password
  field reads `""`; any non-empty one reads the same eight-character marker, whatever was typed, so neither the text
  nor its length reaches a snapshot or anything later built on it.
- **`enabled` follows the presence of `disabled`** — leaned per the code and the HTML standard, not asked: presence is
  the standard's reading of a boolean attribute, it is the engine's `DISABLED` state and the reading that decides
  whether a click acts (element.rs:445-451; pointer.rs:330, 457, 635), and it is the reader the snapshot already
  uses and architecture registers. The reader is not changed; it is named in the field's rustdoc and pinned where the
  engine's other reader (focusability) disagrees.
- **The bridge removes a falsy boolean attribute for Dioxus's own list** — answered at P4's question round,
  2026-10-06, and recorded **PROVISIONAL** on the direction given at the P5 review the same day, the way the
  falsy-`disabled` change was: the work proceeds on it and the founder's own word supersedes it. Today a Dioxus `hidden: false` element is written `hidden="false"`, given `display: none`
  and so gone from the screen, the accessibility tree and the snapshot. The bridge's falsy-clear list widens from
  `checked` and `disabled` to the 27 names Dioxus 0.7.10's web renderer treats this way (`inputs#I1`), which closes
  the entry's CARRY whole. No state field depends on it; it is the CARRY's own defect.

## Implementation Steps
1. **Mask a password's value** — `packages/dioxus-native-dom/src/snapshot.rs`, the private `value` reader
   (`:177-193`). For an `input` whose `type` is `password`, compared ASCII-case-insensitively, the reading it would
   have returned (the editor's text, else the `value` attribute) is replaced: an empty text reads `Some("")`, a
   non-empty one reads `Some` of the mask constant; where the reader returns `None` today it still does. Every other
   element reads exactly as before. The mask is one public constant in the same module, `MASKED_VALUE`, holding
   eight U+2022 characters; it is derived from nothing (no length, no id, no hash of the text).
2. **Name the readers in the field docs** — same file, the rustdoc of `NodeState` (`:40-53`): `enabled` says it
   follows the attribute's presence, the reading that decides whether a click acts, and that a `disabled="false"` or
   a bare `disabled` therefore reads not enabled; `value` says a password input reads `MASKED_VALUE` when it holds
   text and never the text. No field, type or derive changes.
3. **Export the constant** — `packages/dioxus-native-dom/src/lib.rs`, the gated `pub use snapshot::` line: add
   `MASKED_VALUE` to the list (the crate root exports by an explicit list; dioxus-native re-exports the crate whole).
4. **Unit tests for the readers** — `snapshot.rs`, its `#[cfg(test)] mod tests`, built through the module's existing
   `build` helper. Four tests, each asserting its fixture's condition first:
   - `a_password_input_reads_a_masked_value` — a password input holding a synthetic literal reads `MASKED_VALUE`; an
     empty one reads `""`; one written `type: "PASSWORD"` reads `MASKED_VALUE` too; no node's `id`, `name` or `value`
     contains the literal. Its lookups name only the id on failure — it does not go through the module's `node`
     helper, whose message formats the whole snapshot.
   - `disabled_in_parsed_markup_reads_not_enabled_whatever_its_value` — the reader pin. Inside a keyed `div` whose
     content is set through `dangerous_inner_html`, a `button` with `disabled="false"` and one with a bare `disabled`.
     Fixture condition: both elements are focusable to the engine (`is_focussable()`), which is where the two readers
     disagree. Behaviour: both read `enabled: Some(false)`.
   - `a_radio_reads_checked` — a checked and an unchecked radio read `Some(true)` and `Some(false)`.
   - `a_range_input_reads_its_value_attribute` — an `input` of type `range` with `value: "15"` reads `Some("15")`.
5. **Widen the bridge's falsy-clear list** — `packages/dioxus-native-dom/src/mutation_writer.rs`,
   `set_attribute_inner` (`:403-414`). The condition that clears a falsy `checked` or `disabled` becomes membership
   in a module-level constant list holding the 27 names of `inputs#I1`'s `isBoolAttr`, with a comment naming Dioxus
   0.7.10's web interpreter as its source. The `is_falsy` predicate (`:215-224`), the mutator calls and the existing
   `trace!` (`:388`) are untouched; no log site is added.
6. **The bridge regression file** — `tests/blitz-tests/tests/dioxus_falsy_boolean_attrs.rs` (new), opening with a
   `//!` doc that names the behaviour and the bug, in the shape of `dioxus_falsy_disabled.rs`. Built with
   `Harness::from_vdom` and `HarnessOptions` whose `incremental` is set, for `incremental in [false, true]`. Three
   tests:
   - `a_falsy_hidden_element_is_displayed` — a toggle app with a keyed, explicitly sized target carrying
     `hidden: hidden()`. At boot (false): no `hidden` attribute, a non-zero layout box, and the element is a node of
     `doc.snapshot()`. After the toggle (true): the attribute is present and the element is no snapshot node. After a
     second toggle: as at boot.
   - `every_listed_boolean_attribute_is_removed_when_falsy` — the test's own copy of the 27 names; for each, an
     element carrying it with a literal falsy value and one carrying it with a signal-driven falsy value read no such
     attribute (the bridge's static and dynamic attribute paths both).
   - `a_truthy_or_unlisted_attribute_is_kept` — the negative controls: a listed name set truthy keeps its attribute,
     and an unlisted attribute holding the text `false` (`aria-hidden`, a `data-` attribute) keeps the value `false`.
7. **The state proof on the stand** — `tests/blitz-tests/tests/stand_snapshot_state.rs` (new), opening with a `//!`
   doc naming the behaviour. Lean tasks boot through `stand::boot` / `stand::options(incremental)`; every test runs
   `for incremental in [false, true]`, addresses controls by author id through `Snapshot::get`, and asserts its
   fixture condition before the behaviour. Lookup helpers carry `#[track_caller]` and name only the id on failure;
   no assertion formats a snapshot, a node's value or a typed string. Four tests on the tasks:
   - `a_disabled_control_reads_disabled_until_the_app_enables_it` — flight booker: at boot `flight-return-date`
     reads `Some(false)` and `flight-book` `Some(true)`; after a click on `flight-return`, `flight-return-date` reads
     `Some(true)`; after a click on `flight-start` and one typed character, `flight-book` reads `Some(false)`. CRUD:
     at boot `crud-update` and `crud-delete` read `Some(false)` and `crud-create` `Some(true)`; after a click on
     `crud-person-0` both read `Some(true)`. For each of these controls the reading agrees with the presence of its
     `disabled` attribute as the harness reads it, and a non-control node (`task-title`) reads `None`.
   - `typed_text_reads_back_as_the_value` — CRUD: `crud-name`, `crud-surname` and `crud-filter` are empty at boot;
     after a click and `type_text` on each, its `value` is exactly the typed text, and a button still reads `None`.
     Flight booker: after a click on `flight-start` and one typed character its `value` is one character longer than
     at boot and holds that character.
   - `the_range_input_reads_the_apps_duration` — timer: `timer-duration` reads `Some("15")`, equal to its `value`
     attribute as the harness reads it.
   - `focus_reads_on_exactly_the_focused_control` — CRUD: nothing reads focused at boot; after a click on
     `crud-name` exactly `crud-name` does; after one `Tab` key press (`Harness::press`) exactly `crud-surname`; after
     Shift+Tab exactly `crud-name` again; after a click on `task-title` no node does. On a fresh boot one `Tab` press
     focuses exactly `back-btn`. After each move the focused snapshot node's id equals the `author_id` of the node
     the accessibility tree reports as `focus`.

     `doc.unkeyed_actionable()` is empty.

## Constraints & rejected approaches
- Masking in the accessibility tree — rejected: the tree gives an element node no value (accessibility.rs:74-104),
  so there is nothing to mask there, and changing it changes the platform tree the shell builds.
- A mask derived from the text (its length, a hash) or one mask character per typed character — rejected by the
  operator's answer: the mask is one fixed constant.
- A fifth `NodeState` field or a changed `value` type to mark a masked value — rejected: a shape change to a
  registered contract; the node's role (`PasswordInput`) already says what it is.
- Adopting the web interpreter's `truthy` predicate (anything but `true` is removed) — rejected: only the name list
  widens; the bridge's own `is_falsy` stays, so `hidden: "until-found"` is still written.
- Changing how the engine reads `disabled` for focusability, or how a button click moves focus — out: engine
  behaviour, pinned or recorded here, never edited (the `git diff --quiet` guard holds `packages/blitz-dom`).
- Adding a checkbox, radio or password input to a lean task, a fifth `LeanTask`, or a fixture under
  `examples/seven_guis/` — rejected: it changes the control set and the registered stand surface every `ALL`-walking
  check covers.
- Keying or naming a fixture control with a `tabindex` or a `role` — banned: it changes focusability and Tab order.
- `dispatch_recorded`, `focus_next_node` or a programmatic value set as the proof of a typed value, a toggle or a
  focus move — banned: the proof goes through `click`, `type_text` and `press`.
- An assertion or panic message that formats a snapshot, a node's value or the typed literal — banned: raw test
  output lands unscrubbed in `target/agent-run/run.log` and `target/ci-logs/`.
- A real-looking credential as the fixture's password — banned: the literal is plainly synthetic.
