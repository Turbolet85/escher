## What this chunk builds
The **fidelity of the snapshot's state record**: the four fields the snapshot model already carries on every node (`NodeState { enabled, checked, value, focused }`, packages/dioxus-native-dom/src/snapshot.rs:41-53, built by 2026-10-06-snapshot-model and filled from existing readers without proof) are made to read what the screen actually is, and that is proven per control (intent §Findings 2: "a disabled control reads disabled, a typed value reads its value"; requirements v010-05).

- **enabled — a disabled control reads disabled.** A control the app disables reads `enabled: Some(false)`, an enabled one `Some(true)`, and the reading follows the app's state as it changes (a control that becomes enabled after an action reads enabled in the next snapshot).
  - The stand carries disabled controls to prove this on: the flight booker's return-date input (`disabled: !is_return`) and Book button (`disabled: !dates_ok`), and CRUD's Update and Delete (`disabled: !has_selection`). Verified (examples/seven_guis/src/tasks/flight_booker.rs:91,98 · crud.rs:113,128; research.md §Files inspected).
  - CARRY, kept verbatim: "blitz-dom reads `disabled` two ways — presence for the DISABLED state, `:disabled` and click targeting, a parsed bool for focusability (arch §Established Decisions → DOM semantics) — so a snapshot's enabled/disabled must pick one reader". Verified at HEAD: presence sets the `DISABLED` state (element.rs:445-451) and decides the click target (pointer.rs:330, 457, 635); focusability parses a bool (element.rs:629) and so disagrees for `disabled="false"` and for a bare `disabled`. The snapshot reads presence (snapshot.rs:134-136) — the reader that decides what a click does. Which reader it follows is the plan's to state; a pin of what the snapshot reads where the two disagree is this chunk's. `[premise-corrected: a Dioxus document cannot hold disabled="false" through the bridge — every falsy form is cleared (mutation_writer.rs:215-224, 407-408) — so the disagreeing input reaches a Dioxus document only as parsed markup (dangerous_inner_html), which is where the pin is built]`
- **checked — a checked control reads checked.** A checked checkbox or radio reads `checked: Some(true)`, an unchecked one `Some(false)`, and toggling it through real input changes the reading.
  - The four lean tasks carry no checkbox or radio, so this case is proven on a **minimal fixture beside the stand** — the founder's ruling of 2026-10-06 ("the stand is the proof, plus minimal fixtures beside it for cases the 7GUIs tasks lack", carried on working-route lines 60 and 84). Verified (`grep -c 'checkbox|radio|select|password|option'` over examples/seven_guis/src/tasks/ and app.rs → 0 in every file). `[premise-corrected: the fixture is a component in the stand check's own test file, booted with stand::options(incremental) — the standing shape of stand_id_edits.rs:346-351 and stand_actionable_keys.rs:26-36 — not a new boot target in examples/seven_guis/]`
- **value — a typed value reads back.** Text typed into a field through the harness's input synthesis (the real event-dispatch pipeline, not a programmatic set) reads back as that node's `value` in the next snapshot.
  - Proven on stand text fields (CRUD's name / surname / filter inputs; the flight booker's date inputs). Verified: typing through `click` + `type_text` already drives these inputs (stand_crud.rs:32-36; stand_actionable_keys.rs:116-118), and the snapshot reads the editor's text (snapshot.rs:189-190).
  - `[premise-corrected: the lean tasks hold no select — the flight booker's flight-one-way and flight-return are buttons (flight_booker.rs:67-78) — and the engine has no select value model (box construction gives special data only to text-entry inputs, textareas, checkboxes and radios, construct.rs:440-459), so a select's value has no reader and is out of this chunk. The timer's range input (timer-duration) gets no editor either: its value reads the value attribute the app writes on every render ("15" at boot, timer.rs:46,85), which is the app's own state; the engine has no range interaction, so it cannot be changed through real input and is proven as read at boot only]`
- **value — a password value is masked.** A password input's text never appears in the snapshot: its `value` is masked. This is the entry's own requirement (the matrix acceptance of v010-05 does not state it) and it lands before any wire form exists — the next entry's CARRY records the hypothesis that a password input reads unmasked until this chunk masks it.
  - The lean tasks carry no password input, so this is proven on the minimal fixture too. Verified (the same census as above). A password input's value is unmasked at HEAD by a code read — box construction gives `type="password"` an editor (construct.rs:449-453) and the value reader does not exclude the type (snapshot.rs:177-193); the chunk's first test asserts it red-first. The masked form (absent · a fixed marker · one mask character per typed character) is a P4 decision.
  - The mask holds on every path a password's text could reach the snapshot by. Verified: the `value` field is the only path — the accessibility tree gives an element node no value, and a name comes only from text-node children, `aria-label` and a bound `<label>` (accessibility.rs:74-104); typed text lives in the editor, not in a DOM text node, and a `value` attribute becomes a text child only for button · submit · reset inputs (mutator.rs:1245-1252). So the mask is a `snapshot.rs` change and the tree the platform adapter reads is untouched; the proof still asserts absence over every field of every node.
- **focused — the focused control reads focused.** After focus moves to a control through real input (a click, Tab), that node and no other reads `focused: true`; with nothing focused, no node does.
  - Proven on stand controls in both directions (pointer focus and keyboard focus), since focus order is a11y surface (WCAG SC 2.4.3). Verified feasible: a click on a text input focuses it (pointer.rs:544-548); a `Tab` key press runs `focus_next_node` (keyboard.rs:23-33); a click that matches nothing clears focus (pointer.rs:813-816), and the tree's `focus` is then the `Window`, which is no snapshot node (accessibility.rs:60; snapshot.rs:139). `[premise-corrected: a click on a plain button does not focus it — handle_click has no button arm, so the click clears focus (pointer.rs:613-816); pointer focus is proven on a text input and on the fixture's checkbox, not on a button]`
