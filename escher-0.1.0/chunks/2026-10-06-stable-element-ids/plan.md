## Goal
Every element of a Dioxus document — and so every element of the four lean stand tasks — gets a **stable element id**: a
semantic string an agent can aim at. It is distinct from the engine's `NodeId`, a versioned slot index that a remount
re-mints (intent §Findings 1 OBSERVED; arch §Established Decisions → [Node identity]). The id is the author's key where
the author gave one, else the element's component path. Per the operator's word at this P4 (two questions, one round):
**the author key is the HTML `id` attribute**, read verbatim. **A Dioxus `key` is the list row's segment inside the
component path.** **The lean tasks' controls and value displays get author keys in this chunk.** Snapshot, diff, act-by-id
and screenshot (Epochs 3–5) address elements by this id, so it is the abstraction they rest on (intent §Principles).

Research settled where the id lives. A component path exists only in the Dioxus vdom: `VComponent.name`, `VNode.key` and
the template roots, all reachable through dioxus-core 0.7.10's public API (research.md §Files inspected). blitz-dom and
the harness see no components. So the id is **computed on demand in `dioxus-native-dom`** from a vdom walk joined with a
DOM walk, and read through two new public methods on `DioxusDocument`. Nothing is written to the DOM, so there is no
mutator write, no CSS, layout, focus or accessibility effect, and no incremental-layout interaction (per architecture
§Conventions → "DOM API patterns" and §Design Philosophy → "One incremental pipeline, safe identities"). The id's form
contains no `NodeId`, `ElementId`, `ScopeId` or pointer, so it is the same in every process. That is the property the
next entry, Id persistence (v010-02), proves; this chunk only must not foreclose it.

The proof is a new stand check, `tests/blitz-tests/tests/stand_element_ids.rs`. On each lean task, booted through
`seven_guis::stand` in both layout modes, it walks every element and asserts:
- every element reads exactly one id, and all ids are distinct;
- keyed elements read their key;
- every other element reads its component path, in the grammar below.

Unit cases in the new module cover the edges: duplicate and malformed author keys, Dioxus keys, and stale or non-element
nodes. Provenance: test-plan §3 (Construction · Inspection helpers) and §2 (Differential oracle) for the check shape;
security-plan §Input Validation and §Error Handling "Graceful degradation" for the no-panic edges; obs-plan §8 for the
no-logging rule; design-system §Color Palette / §Typography and a11y-plan §5 for the markup-only change to the tasks.

### The id grammar (the contract the checks pin)
An element's id is decided in this order:

1. **Author key** — the element's HTML `id` attribute, when its value is non-empty, contains no `/`, and no element
   earlier in document (pre-order tree) order already reads that same value as its key. The id is the value, verbatim.
   - A later duplicate, an empty value, or a value containing `/` is not a key. That element falls through to rule 2 or 3,
     so a hostile or repeated `id` never panics and never makes two ids equal (security-plan §Input Validation "Markup
     attributes").
2. **Component path** — for an element that a Dioxus component renders. The `/`-joined names of the components the vdom
   walk passes through from the base scope to the element's owning component, excluding the base scope itself, which
   dioxus-core names `"root"` (dioxus-core 0.7.10 `virtual_dom.rs:293`). These are followed by one element segment per
   DOM level, from the component's template root down to the element:
   - `{tag}[{key}]` for the root element of a Dioxus-keyed VNode (`VNodeInner.key`, nodes.rs:49);
   - otherwise `{tag}:{n}`, where `n` is the element's 0-based index among the element children of the same DOM parent
     that have the same owning component instance and the same tag name (local name).
   - A Dioxus key repeated among same-owner siblings falls back to `{tag}:{n}` for the later sibling.
3. **Document path** — for an element no component renders: the skeleton `html`, `head` and `body` that
   `DioxusDocument::new` builds outside the vdom (dioxus_document.rs:84-142), and any head element created outside a
   template. A leading `/`, then one `{tag}:{n}` segment per DOM level from the document root, with `n` the index among
   element siblings of the same tag: `/html:0`, `/html:0/head:0`, `/html:0/body:0`.

Uniqueness holds by construction:
- author keys are unique among themselves, by first-wins;
- every path contains `/` and no key does;
- component and document paths are unique among themselves, by the per-parent, per-owner, per-tag index.

Only element nodes have ids: a text, comment or placeholder node, the document root node, a stale `NodeId`, or a node
detached from the tree reads none.

## Implementation Steps
1. **New module `packages/dioxus-native-dom/src/element_id.rs`** — the derivation, crate-private except for what step 2
   exposes.
   a. **Vdom pass.** Walk from `VirtualDom::base_scope()` → `ScopeState::root_node()`, recursing through each `VNode`'s
      template roots and `dynamic_nodes`:
      - `DynamicNode::Component(c)`: push `c.name`, descend into `c.mounted_scope(idx, vnode, dom)`'s `root_node()`.
      - `DynamicNode::Fragment(items)`: recurse into each item.
      - Text and placeholder nodes: skip.
      For every STATIC template root (`template.roots[i]` is an element), resolve `vnode.mounted_root(i, dom)` →
      `ElementId` → `NodeId` through `DioxusState::try_element_to_node_id` (never the unwrapping `element_to_node_id`),
      and record `NodeId → (owner instance, component-name chain, Option<key>)`. The owner instance is the component
      scope the walk is in; a nested VNode rendered by the same component keeps the same owner. Keep the record keyed by
      `NodeId` and read DOM nodes through `BaseDocument::get_node` (stale-safe; arch §Established Decisions →
      [Node identity]).
   b. **DOM pass.** Walk the DOM pre-order from the document root through `BaseDocument::get_node` and each node's
      `children`.
      - An element recorded in (a) starts its owner's segment chain with its root segment.
      - Every other element inherits its parent's owner and appends `{tag}:{n}`, counting `n` per the grammar.
      - Elements reached before any recorded root are the document-path case.
      - Apply the author-key rule (first-wins, in this same pre-order) on top.
      Produce the id for every element node.
   c. Use only dioxus-core's PUBLIC API (`VNodeMount` is `pub(crate)` — research.md). Use no `ScopeId`, `ElementId`,
      `NodeId` or pointer value in any id string.
   d. **Inline `#[cfg(test)] mod tests`**, following `dioxus_document.rs:366-378`'s shape (a `VirtualDom`,
      `DioxusDocument::new(vdom, DocumentConfig::default())`, `initial_build`), with these 6 unit tests:
      - **(1) keyed list rows** read `{tag}[{key}]` paths;
      - **(2) duplicate HTML `id`** — the first element reads the key, the second its component path, and both differ;
      - **(3) empty `id` and an `id` containing `/`** read their component path;
      - **(4) a repeated Dioxus key** among siblings falls back to `{tag}:{n}`;
      - **(5) a stale `NodeId`** reads `None`: an element removed by a re-render (`mark_dirty` + `poll`), its old `NodeId`
        no longer resolving;
      - **(6) a text node and the document root** read `None`.
2. **`packages/dioxus-native-dom/src/dioxus_document.rs`** — add two `pub` methods on `DioxusDocument`, each with `///`
   docs stating the grammar's three rules:
   - `element_id(&self, node: NodeId) -> Option<String>` — `None` for a non-element, stale or detached node;
   - `element_ids(&self) -> Vec<(NodeId, String)>` — every element in document pre-order.
   Both compute on demand from steps 1a–1b and never panic. No change to `mutation_writer.rs` (where the PROVISIONAL

3. **`packages/dioxus-native-dom/src/lib.rs`** — `mod element_id;`. No new public type is needed: the methods return
   `String` and `NodeId`, and `NodeId` is already re-exported (lib.rs:21).

## Constraints & rejected approaches
- **Writing the id into the DOM** (a `data-escher-id` attribute through the mutator) — rejected. It would change
  `dom_string`, CSS matching and the mutation stream, and it needs mutator writes. A computed read gives the same id with
  none of these effects.
- **Computing the id in blitz-dom for any `BaseDocument`** — rejected. blitz-dom has no component information, and it
  would make remote-document `id`s an input to a new derivation (security-plan §Threat Model Summary). The surface is
  Dioxus-only in this chunk.
- **A `Harness` inspection helper** — not added. `Harness.doc` is `pub` (harness.rs), so a check reads
  `harness.doc.element_ids()`. A harness addition would be a second §Standard Contracts surface with no consumer yet.
- **A by-id lookup (`node_for_element_id`)** — not added. Acting by id is v010-09 (Epoch 4), and coherence across
  snapshot, a11y tree and driver is v010-03.
- **`ScopeId`, `ElementId`, `NodeId` or a pointer inside an id** — forbidden. They differ across processes and remounts,
  which would foreclose v010-02.
- **Do not edit `mutation_writer.rs`** — the PROVISIONAL falsy-`disabled` fix lives there (2026-10-06-headless-stand),
  and the id needs no mutation-path change.
- **Do not carry an author key on `role`, `tabindex`, `aria-*`, `hidden` or `disabled`; add no wrapper element, class or
  style for ids** (a11y-plan §4 · §5; design-system §Spacing).
- **No `tracing` of an id, key or path, and no new log field** — an author key is author content, and `path` is already a
  redacted field name (obs-plan §8; security history 2026-10-06-telemetry-bootstrap).
