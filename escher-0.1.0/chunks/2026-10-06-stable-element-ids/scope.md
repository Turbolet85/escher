## What this chunk builds
Every element of the stand gets a **stable element id**: a semantic name an agent can aim at, distinct from the engine's `NodeId` (a versioned slot index that a remount re-mints — intent §Findings 1 OBSERVED). The id is the author's key where the author gave one, else the element's component path. intent §Principles orders it right after the headless stand: snapshot, diff, driver and screenshot all address elements by this id, so it is the abstraction they rest on. Capability v010-01 (`verification-matrix.json#v010-01`): "On every stand task, every element in the screen reads an id; elements the author keyed read that key, and the rest read their component path."

- **An id per element** — every element node in a booted stand document has exactly one stable id, readable through a public read surface that a check — and later the snapshot and driver — can call. `[premise-corrected: the component path exists only in the Dioxus vdom (VComponent.name, dioxus-core 0.7.10 nodes.rs:533) — blitz-dom and the harness see none; Harness.doc is pub (harness.rs), research.md §Files inspected]` The read surface lives on `dioxus-native-dom`'s `DioxusDocument`; a stand check reaches it as `harness.doc`. No blitz-dom or harness change is needed for it.
- **Author key** — where the stand's author gave an element a key, the id is that key. What "the author's key" binds to is a P4 fork. Verified (research.md): Dioxus's `key:` lives on `VNodeInner.key` (dioxus-core 0.7.10 nodes.rs:49 — the key of a list item's template root) and never reaches the DOM (`WriteMutations` has no key-bearing method, `mutation_writer.rs`); it is sibling-unique, not document-unique; the stand's TaskShell chrome instead carries HTML `id:` attributes (`app.rs:125-167` — `home`, `task-shell`, `back-btn`, `task-title`, `task-body` …), and the four lean tasks carry none (`grep` over `tasks/{counter,crud,flight_booker,timer}.rs`: 0 `id:`). Whether the author key is the Dioxus `key`, the HTML `id`, a new escher attribute, or more than one of these in a fixed precedence is a P4 fork, closed against research.
- **Component path otherwise** — an element without an author key reads its component path. Verified (research.md): "component path" has no existing definition in the engine — the mutation writer sees templates, `ElementId`s and template-relative byte paths, not component names, and blitz-dom sees only the DOM tree; but dioxus-core's public API reaches every piece a path needs: `VirtualDom::base_scope` → `ScopeState::root_node` → `VNode` (`key`, template roots, dynamic nodes) → `VComponent.name` + `mounted_scope` for child components, and `VNode::mounted_root` → the ElementId of every static template root (→ NodeId via `try_element_to_node_id`). Static elements nested under a template root get no ElementId (dioxus-core `diff/node.rs:833-856`), so their segment comes from a DOM walk below their template root. The root component is named `"root"` by dioxus-core (`virtual_dom.rs:293`). The path's grammar is a P4 decision. The form must be one later chunks can keep identical across a re-render, a remount and a fresh process (v010-02, the next entry) — this chunk does not prove persistence, but it must not choose a form that rules it out (e.g. one containing a `NodeId`, an `ElementId` or a pointer).
- **Every stand element** — the four lean tasks (counter, flight booker, timer, CRUD) booted headlessly in TaskShell through `seven_guis::stand::boot` / `boot_timer` — chrome and task body alike. Verified (`dioxus_document.rs:84-142`): the skeleton `html > head + body > main#main` is built by `DioxusDocument::new` outside the vdom, so it has no component; its rule, and whether non-element nodes (text, comments, placeholders, the document root) carry ids, are P4 decisions; v010-01's acceptance names "every element".
- **Uniqueness** — two elements in one document never share an id. What happens when an author key repeats (two elements keyed alike, a keyed list rendered twice) — refuse, disambiguate, or last-wins — is a P4 decision; whichever rule is chosen is asserted.
- **Proof checks** — a stand check per lean task boots it headlessly, walks every element of the screen and asserts each reads an id; keyed elements read their key and the rest read their component path (the matrix acceptance verbatim). Under the workspace test leg (`ci-leg.sh fast`), as integration tests in `tests/blitz-tests/tests/stand_*.rs`, one file per behaviour.
