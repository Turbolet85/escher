## What this chunk builds
escher gets one telemetry bootstrap that every escher binary — the stand, and later the driver CLI and MCP server — installs at start. Today each app calls `tracing_subscriber::fmt::init()` on its own, which writes to stdout. There is no OTel SDK, no service identity, no panic logging outside WASM and the WPT runner, and no scrubbing (obs-plan §3, §7, §8; the obs-plan bootstrap contract labels `otel-sdk-install` and `pii-scrubbing-wire`).

- **Tracing subscriber** — one init entry point that installs a global `tracing` subscriber with an env-filter level, idempotent and safe to call twice.
- **Logs never on stdout** — the subscriber writes to stderr (or a file the caller names), never stdout. Stdout belongs to the driver CLI's JSON (working-route "Driver CLI") and to MCP's stdio transport ("MCP surface").
- **Service identity** — every event the sink writes carries the service name and version (`service.name` / `service.version`, the OTel resource keys an exporter will reuse). The values are read from the binary, not hand-typed.
- **Panic logging** — a panic hook logs the panic message and location as a `tracing` error event, then chains the previous hook so the default output and exit code don't change.
- **Scrub layer** — log fields that carry user content are redacted before they reach any sink: URLs, attribute values, outer HTML, text content and CSS values (obs-plan §8's list). This closes the CLAUDE.md invariant "no scrub layer exists yet".
- **Opt-in OTel export — DEFERRED at P4** (overseer, under the founder's standing delegation of technical forks, 2026-10-06). The exporter's outbound egress and its unconditional `OTEL_EXPORTER_OTLP_HEADERS` read are a boundary widening (playbook "Boundary widening", verdict escalate) that must reach the founder. Nothing in escher-0.1.0 needs an exporter. This chunk ships no OTel crate, no egress and no credential path. The obs-plan bootstrap item `otel-sdk-install` is carried as a route CARRY on "Driver command spans" (Epoch 4), the first entry whose spans an exporter would carry. The founder decides http-only vs TLS before that entry is taken up. The identity design below keeps `service.name` / `service.version` ready for an OTel resource.

## Boundaries
- In: the bootstrap itself, its tests, and adopting it in this repository's escher-owned binary entry points — the stand (`seven_guis_native`) at minimum.
- Out: new instrumentation (spans or metrics at engine call sites — obs-plan §4/§5 record no coverage target), SLO budgets (§10 has no recorded intent), and the driver's own logging (the Driver CLI and MCP chunks adopt the bootstrap when they exist).
- Out: re-plumbing upstream `blitz` apps (browser, rdme) and the WPT runner's `env_logger`, unless research shows it's free.
- Engine crates keep the invariant that `tracing` call sites are `#[cfg(feature = "tracing")]` with a no-op fallback. The bootstrap adds no unconditional `println!`.

- `[premise-corrected: ≥19 engine call sites interpolate user content into the message string — research.md §Patterns detected]` A subscriber-level scrub over field names covers only the named fields (`url`, `error`, `html`, `value`, `path`). It does **not** cover existing call sites without edits. URLs, attribute values, text and request dumps are also formatted into the event message at blitz-dom, dioxus-native(-dom), blitz and blitz-vibey-script sites, and `js_console` arrives through the `log` bridge. Events whose target is an engine crate or the `js_console` log target keep their level, target, location and allowlisted non-content fields. Their message and every other field value are redacted. No engine call site is edited. In the stand's default build, engine `tracing` call sites are compiled out (`dioxus-native/tracing` is off), so they reach the stand's sink only when that feature is turned on.
