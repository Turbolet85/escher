## Goal
Every AccessKit node that stands for a stand element carries that element's stable id, and every interactive control on the stand carries a role and a non-empty accessible name. intent §Findings 1 asks for "the same id in the snapshot, the accessibility tree and the driver". This chunk builds the accessibility-tree leg; the snapshot (Epoch 3) and the driver (Epoch 4) do not exist yet.

The id keeps one source, `DioxusDocument::element_id` / `element_ids` (per architecture §Standard Contracts → Dioxus DOM bridge; security-plan §Input Validation `id` row). It reaches the tree through a new `accessibility`-gated `Document` trait method. The method's default builds the tree exactly as `BaseDocument::build_accessibility_tree` does today. `DioxusDocument` overrides it to set AccessKit's `author_id` on each element node from `element_ids()`. The shell builds its platform tree through the trait method rather than from the inner `BaseDocument`. So the windowed app, the harness and any test all see the same carried id. Nothing is written into the DOM or the vdom, and the AccessKit `NodeId` keying stays `NodeId::as_u64()` (per architecture §Established Decisions → [Node identity]; a11y-plan §1 · §3).

The engine also gains two accessible-name sources: `aria-label` (accname-1.2 step 2C) and `<label>` association (HTML-AAM: a `for`-target or nested input labelled by its label). This was leaned by the operator at P4, 2026-10-06. The stand's six nameless inputs are named with attributes only: `for` on the four existing visible labels and `aria-label` on the two unlabelled flight-booker inputs. No element, class, style or order changes (per layout-templates §Surface: desktop-native → Primary screens; a11y-plan §2 → Role derivation, §4 · §5).

## Implementation Steps
1. **Trait method.** In `packages/blitz-dom/src/document.rs`, add to `trait Document` a defaulted method `accessibility_tree(&self) -> accesskit::TreeUpdate`, under `#[cfg(feature = "accessibility")]`. Its default body returns `self.inner().build_accessibility_tree()`, and its rustdoc says that a wrapper may override it to enrich nodes, as `DioxusDocument` does with stable ids. The inherent `BaseDocument::build_accessibility_tree` keeps its name and signature, so its 10 callers are unchanged (research.md §Graph impact). No implementor other than `DioxusDocument` overrides it.
2. **Name sources in the tree build.** In `packages/blitz-dom/src/accessibility.rs`, `build_accessibility_node`:
   - for an element whose `aria-label` attribute, trimmed, is non-empty, call `set_label` with the attribute value, citing accname-1.2 §2C in a comment;
   - after the visit, for every built `<label>` node, resolve `label_bound_input_element` (document.rs:627-660). When the bound input has a built node, `push_labelled_by` the label's AccessKit `NodeId` onto that input's node, citing HTML-AAM's input accessible-name computation. The pass runs after all nodes are built, because a label may precede or follow its input.
   - Nothing else about roles, `hidden`, `TextRun` or keying changes.
3. **Stable ids on the Dioxus tree.** In `packages/dioxus-native-dom/src/dioxus_document.rs`, implement `accessibility_tree` for `DioxusDocument` under `#[cfg(feature = "accessibility")]`:
   - build the base tree through `self.inner.borrow().build_accessibility_tree()`;
   - build a map from `element_ids()` keyed by `NodeId::as_u64()`;
   - for each `(accesskit::NodeId(raw), node)` in `tree.nodes` whose `raw` is in the map, call `set_author_id(id)`.
   - Nodes with no element id get no author id: `TextRun`s, the document root and the synthetic `Window` (`u64::MAX`).
   - The method never indexes the slab with a tree id.
   - In `packages/dioxus-native-dom/Cargo.toml`, add `accesskit = { workspace = true, optional = true }` and make `accessibility = ["blitz-dom/accessibility", "dep:accesskit"]`, following blitz-shell/Cargo.toml:15-17, 37.    - `label_for_names_its_input`: `<label for="a">A</label><input id="a">` makes the input's `labelled_by` contain the label's node, and the label's `labelled_by` holds a `TextRun` whose value is `A`.

## Constraints & rejected approaches
- A `DioxusDocument`-only inherent post-pass — rejected: the windowed shell builds from `self.doc.inner()` (window.rs:376-381), so the platform tree an AT reads would never carry the id.
- Writing the id into the DOM as an `id`/`data-*` attribute — rejected: arch §Standard Contracts → Dioxus DOM bridge says the id is written to "neither the DOM nor the vdom", and the security-plan `id` row says "written nowhere". It would also route the id through dioxus-native-dom's `set_attribute` debug trace (obs-plan §6 · §8).
- A `DocumentConfig` id provider — rejected: it has no path to the `VirtualDom` that `DioxusDocument` owns (dioxus_document.rs:67-70).
- Bumping accesskit — rejected and not needed: 0.25.0 has `author_id` (accesskit-0.25.0/src/lib.rs:2127-2129), and the pins are coupled with accesskit_xplat (CLAUDE.md).
- A `role` attribute on a native control, a new `<label>` element or wrapper, or a clickable `div` replacement — rejected: a11y-plan §2 records the native-semantics override TODO, and layout-templates §Surface: desktop-native forbids new wrappers, classes, styles or order.
- A Dioxus `hidden: false`, or any other boolean attribute written as `"false"`, in the stand markup — rejected (a11y-plan §5 → Script and framework exposure).
- Logging an id, an accessible name or a `TreeUpdate` dump, under any field and least of all the allowlisted `node_id` — banned (obs-plan §8; security-plan §Logging & Monitoring).
- Setting `html_id` — not this chunk: no criterion needs it, and it would be a second carrier of the author key.
