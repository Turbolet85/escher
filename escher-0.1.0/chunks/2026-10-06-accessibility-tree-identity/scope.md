## What this chunk builds
The stable element id built by `2026-10-06-stable-element-ids` and proved persistent by `2026-10-06-id-persistence` reaches the **accessibility tree**. Every AccessKit node that stands for a stand element carries that element's stable id, and the stand's interactive controls carry a role and an accessible name. intent §Findings 1 asks for "the same id in the snapshot, the accessibility tree and the driver". This chunk delivers the accessibility-tree leg of that requirement. The snapshot (Epoch 3) and the driver (Epoch 4) do not exist yet.

- **Id on every accessibility node.** For each stand element that has an AccessKit node, that node carries a string equal to `DioxusDocument::element_id(node_id)`. A node with no element (text, the document root) carries none. The id is read from the built tree, not from a parallel map, so a consumer of the accessibility tree alone can recover it.
- **Carrier field** (verified at P3): the pinned accesskit 0.25.0 `Node` has `author_id` / `set_author_id`, documented as "A way for application authors to identify this node for automated testing purposes. The value must be unique among this node's siblings" (accesskit-0.25.0/src/lib.rs:2127-2129). The stable id rides there, and no `NodeId`-derived AccessKit `NodeId` changes meaning. `html_id` also exists (2135-2140). It is the HTML `id` attribute, and the tree build sets neither today (research.md §Files inspected).
- **Id source (CARRY, folded verbatim):** "the stable element id is computed only in dioxus-native-dom (`DioxusDocument::element_id` / `element_ids`, a vdom walk joined with a DOM walk), since blitz-dom holds no component information; blitz-dom's `build_accessibility_tree` keys AccessKit nodes by `NodeId::as_u64()` and has no access to the id (arch §Standard Contracts → Dioxus DOM bridge; a11y-plan §2)". Its coordinates are re-verified at take-up: arch §Standard Contracts → Dioxus DOM bridge (architecture.md:134) states that `element_id(s)` live in `packages/dioxus-native-dom/src/element_id.rs` and write the id to neither the DOM nor the vdom. a11y-plan §2 names `packages/blitz-dom/src/accessibility.rs` as the tree builder.
- **Id-source mechanism** (verified at P3, the CARRY's claim): "blitz-dom holds no component information; `build_accessibility_tree` keys AccessKit nodes by `NodeId::as_u64()` and has no access to the id". Re-derived at HEAD: accessibility.rs:51 keys `NodeId(node.id.as_u64())`, and `DioxusDocument` owns the `VirtualDom` beside its `Rc<RefCell<BaseDocument>>` (dioxus_document.rs:67-70). The crossing is the P4 fork. `[premise-corrected: a provider or hook on BaseDocument cannot compute the id — a DocumentConfig provider has no path to the vdom that DioxusDocument owns (config.rs; dioxus_document.rs:67-70). And a dioxus-native-dom-only post-pass would not reach the windowed platform tree, because the shell builds from self.doc.inner() of a Box<dyn Document> (window.rs:376-381, 521-524; dioxus-native lib.rs:214-237) — research.md §Files inspected]`. The live options are:
  1. a defaulted, `accessibility`-gated `Document` trait method that builds the tree, which `DioxusDocument` overrides to set `author_id` from `element_ids()`, and which the shell calls on its `Box<dyn Document>`;
  2. a `DioxusDocument`-only inherent post-pass, which reaches tests but not the platform tree;
  3. writing the id into the DOM, which conflicts with arch's "written to neither the DOM nor the vdom" and would route the id through the `set_attribute` debug trace (obs extract).
- **Role and name on stand controls**: every interactive control of the lean four (counter, flight booker, timer, CRUD) and of the shell chrome has a non-`Unknown` role from the HTML-AAM mapping and a non-empty accessible name. `[premise-corrected: the controls are 15 — 9 buttons and 6 inputs (5 text, 1 range); the lean four have no select and no <progress> (timer-progress is a div); the shell chrome on the stand is back-btn alone — task cards are Home's (app.rs:122-150), never mounted by stand::boot — research.md §Patterns detected]`. Roles are verified: all 15 map to non-`Unknown` (Button / TextInput / Slider, accessibility.rs:211, 234-251). Names: `[premise-corrected: blitz-dom computes a name only from a control's direct text children (labelled_by TextRun, accessibility.rs:74-78); it reads no aria-label and no <label> association, so the 9 buttons are named and the 6 inputs (flight-start, flight-return-date, timer-duration, crud-filter, crud-name, crud-surname) are nameless]`. Both the engine and the markup are therefore in play. The engine gains an accessible-name source (`aria-label` → `label`, and/or `<label for>` / nested-label association through the existing `label_bound_input_element`, document.rs:627-660), and the stand markup supplies names for the six inputs. Which sources is a P4 fork.
- **Proof checks**: a stand check in `tests/blitz-tests/tests/stand_*.rs` (one file per behaviour), run under the workspace test leg `for incremental in [false, true]`. It builds the accessibility tree headlessly for each lean task and asserts three things. Each element-bearing node's carried id equals `element_id`. The set of carried ids is pairwise distinct. Every interactive control has a non-`Unknown` role and a non-empty name. The check must not pass vacuously: it asserts a non-zero node count and that the named controls are present by id.
- **Coherence after change**: after a re-render (counter increment, CRUD create or delete), a rebuilt tree still carries ids equal to `element_id`. `[premise-corrected: there is no incremental AccessKit update — every build walks the whole document (accessibility.rs:6-44, self.visit), the builder never reads changed_nodes (grep -c → 0), and the shell rebuilds the whole tree on has_changes() (window.rs:376-381); coherence after change is a full rebuild after pump]`
