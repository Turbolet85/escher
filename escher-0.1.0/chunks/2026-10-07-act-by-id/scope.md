## What this chunk builds
The driver's fourth piece, after the session, settle and the schema: **the schema's verbs run on a held instance**. intent §5 states what it serves — "acting by id returns only once the UI has settled, so a stand flow with a delayed update passes with no sleep" — and intent §3 what comes back: "after an action the driver returns exactly the nodes that changed; an action that changes nothing returns an empty diff". At HEAD the crate says of itself "no command runs through a session yet" (`packages/escher-driver/src/lib.rs:24-25`).

- **Driver actions addressed by stable id** — an action names its target by the element's stable id and takes effect on that element.
- **Which actions** — the schema's acting verbs, as the table states them: `click` and `type` take an `id`, `press` takes a `key` and an optional `shift`, `advance` takes `ms` (`packages/escher-driver/src/schema.rs:205-261`). `validate` already turns a `Call` into a typed `Command` (`command.rs:161`); this chunk gives a `Command` something that runs it.
- **The id an action takes is the element's `element_id`** — the string `DioxusDocument::element_id` / `element_ids` compute (`packages/dioxus-native-dom/src/dioxus_document.rs:209`, `:215`), the same one the snapshot and the accessibility node carry. How an id is resolved to the live node is the plan's.
- **"No coordinates or selectors" is the caller's side** — v010-09's acceptance reads "addressed by an element's stable id alone, with no coordinates or selectors". The harness's own helpers click by selector or at a point (`packages/blitz-test-harness/src/input.rs:97`, `:103`); what the executor dispatches inside the engine for a resolved node is the plan's, and the caller hands it an id only.
- **`press` names no element** — it carries a key, not an id, so it acts on whatever holds focus (the table's own help: "presses one key on the focused element", `schema.rs:238`). Found at P3: the crate cannot name a key today — `Harness::press_with` takes `keyboard_types::Key` and `Modifiers`, which neither of its two dependencies re-exports (research.md §Patterns detected). How that reads against v010-09's "every driver action … is addressed by an element's stable id alone" is settled at P4 against the cap, not assumed here.
- **Returning after settle** — an action returns once the instance has settled. The in-process step exists: `Session::act` runs a closure and settles (`session.rs:70-78`).
- **A step that ran and did not go quiet is a result, not a refusal** — the acting verbs' result carries `settled` and `busy` (`schema.rs:148`, `:155`), while `Session::act` returns `SessionError::NotSettled` today (`session.rs:77`); the executor reports the first shape.
- **With the diff** — the return names the nodes added, removed and changed.
- **The diff is `Snapshot::diff` over the snapshots taken before and after the step, returned unchanged** — `Snapshot::diff(&self, after: &Snapshot) -> SnapshotDiff` (`packages/dioxus-native-dom/src/snapshot_diff.rs:60`); the result fields `added` · `removed` · `changed` are the schema's (`schema.rs:163-178`).
- **The `snapshot` verb** — the table's fifth verb is a read, and the entry names actions. v010-04's command leg is a CARRY on "Driver CLI" (working-route.md:71), which also owns where the text first leaves the process. Whether one executor runs the whole table here, `snapshot` included, or leaves that verb unexecuted is the plan's; v010-04 is not claimable here either way.
- **What an id that names no element gets** — `[premise-corrected: the case has a cause whose stated meaning is exactly it — `not-found`, "no element on the screen reads the id", refusal.rs:60; ids resolve through `element_ids()` with no stored index, research.md §Patterns detected]` `validate` checks a call's shape and receives no `Session`, so it cannot know whether an id names anything; an executor that acts by id meets that case on its first unknown id. `Cause::NotFound` is named and worded, and "nothing returns the five yet" (the CARRY on working-route.md:64). Detecting the five screen-level causes is "Refusal detection" (Boundaries), which reserves two decisions — `stale` against `not-found`, and `off-screen` with no verb that scrolls. What this chunk returns for an id it cannot resolve, and for a target that cannot take the action, is the plan's, bounded by that entry.
- **Where a command runs — an open fork, the operator's** — in process on a `Session` its caller holds, or across the session socket into the `escher-session` host. The facts that bear on it, none of them a lean (re-read at P3: `serve` owns the session and passes only its label to the accept loop, `host.rs:35`, `:48`, so no request can touch the instance today; the wire's bounds are 64 and 128 bytes, `wire.rs:16`, `:20`, against an id of up to 1024 bytes and a diff):
  - the socket carries `hello` and `stop` only, and "the first command that carries one is a new crossing question" (`.claude/rules/security.md` §Surfaces);
  - this entry's own freight says of the diff "the first command that returns it asks the crossing question again" (CARRY 3) and asks for a typed sentinel read in the `escher-session` binary's stderr (CARRY 4) — the second needs a command that reaches that binary's instance;
  - "Driver CLI" carries the opposite placement: "the first command that reaches `validate` from outside the process is its own crossing question" and "where the text first leaves the process" (two CARRYs on working-route.md:71);
  - v010-10's note gives as a reason for not claiming it that an in-process closure is "no action an agent can run" (CARRY 6).
  The answer decides which of this entry's proofs can be made here (CARRY 4, and the claim leans on v010-09, v010-06, v010-03 and v010-10). It is asked at P4 with research's findings, before the plan is written. **Decided (the operator, 2026-10-07, at the P4 forks): in process.** A validated call runs on a `Session` its caller holds and returns its result as a value; the socket stays `hello` and `stop`, nothing of the screen crosses it, and the founder's "returned to its caller only" ruling still covers the diff and the snapshot text. CARRY 4's typed-sentinel reading is therefore not owed here: it stays "not measured" and goes to the entry whose command first reaches the host's instance.
