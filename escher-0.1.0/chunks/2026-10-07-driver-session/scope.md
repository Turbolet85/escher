## What this chunk builds
The driver's first piece: a **session** — one process that boots one headless stand instance and keeps it alive while commands arrive, instead of the fresh-per-boot document every stand check builds today (`seven_guis::stand::boot`, `examples/seven_guis/src/stand.rs:73`). intent §Principles orders the driver's parts as settle detection → the command and refusal model → CLI → MCP → screenshot; the session is the thing each of them runs against, so by "infrastructure ahead of the queue" it lands first. Every later driver entry (Settle detection, Command and refusal schema, Act by id, Refusal detection, Driver command spans, Driver CLI, MCP surface, Headless screenshot) consumes it.

- **One instance, held across commands** — a session owns exactly one headless stand instance for its whole life. State a command leaves behind (a click's effect, a typed value, focus) is what the next command reads; nothing is rebuilt between commands. An element's stable id read in one command names the same element in the next (v010-02's proof was across re-render, remount and fresh process; here it is the same live document).
- **Own lifecycle: start, attach, stop** — the session is started, attached to and stopped as three distinct steps, and it owns the whole of its own lifecycle: nothing outside it has to boot, track or clean up the instance. `start` brings up one instance; `attach` reaches an instance that is already up; `stop` ends it and leaves nothing behind.
- **The one process both surfaces drive** — the session is a process, and it is the same process whether the caller is the later CLI or the later MCP surface. Neither surface boots a stand of its own; each reaches the session.
- **Which task the instance holds** — verified (research.md §Files inspected, `stand.rs`): a session boots one of the four lean tasks (`LeanTask::ALL`, `stand.rs:24`), named at `start`, through the existing boot path with the pinned viewport, the bundled font and no network (`stand::options`, `stand.rs:58-69`). A different task is a different session. `stand::boot` hands the timer "a tick source nobody drives" (`stand.rs:71-75`), so a session holding the timer boots through `boot_timer` (`stand.rs:79`) and keeps its `TimerTicks` handle for its whole life — the later Settle detection entry advances it. No seam is missing from the boot.
- **Commands are serialized on the instance** — verified: `Harness<DioxusDocument>` is neither `Send` nor `Sync` (`DioxusDocument.inner: Rc<RefCell<BaseDocument>>`, `dioxus_document.rs:70`; `TimerTicks(Rc<RefCell<TickState>>)`, `timer.rs:10`). The thread that boots the instance serves every command on it; a session takes one command at a time by construction.
- **`attach` implies a crossing between two processes** — verified: a CLI whose every command is its own process invocation (v010-12: "a stand flow is scriptable in shell alone") can only reach a held instance by attaching to another, longer-lived process, and the project has no such crossing today — 0 listener, socket or pipe constructs in the tree (research.md §Patterns detected, the census), arch §Occupied Resources reads "Network ports and listeners: none" (`architecture.md:144`), and `.claude/rules/security.md` §Surfaces says a new socket, port, IPC endpoint or credential path is an arch §Occupied Resources + security-plan amendment first.
