## What this chunk builds
The requirement is v010-16 (requirements.md:22; intent §Findings 1, "stable across edits of the app's code (founder, 2026-10-06)"): an element left in place keeps its id when the app's code around it changes.

- **The edits that must keep an id.** Verified in shape against `element_id.rs` (research.md §Patterns detected):
  - an element that reads its **author key** keeps its id under every edit that leaves it in place: handler, state, text, attribute and style changes; siblings added or removed anywhere, an earlier same-tag sibling included; an ancestor wrapped or unwrapped. True today already — the key replaces the path (element_id.rs:170-176);
  - an **unkeyed** element keeps its id under every edit outside the subtree of the ancestor its path starts at, and under edits inside that subtree that do not touch its own relative path (later siblings, other-tag siblings, behaviour and content changes);
  - `[premise-corrected: the "no keyed ancestor" case is nearly empty — the document skeleton's mount element reads the author key main and is an ancestor of every vdom-rendered element (dioxus_document.rs:126-131; measured id list, research.md), so a literal "nearest keyed ancestor" always exists. Whether main, and a keyed container outside an element's own component, anchor it is the composition fork below]`.
- **The edits that may still change an id** — stated in the contract, not fixed. Verified by the same reading: for an unkeyed element, an earlier same-tag sibling added or removed between it and the point its path starts at, or a wrapper inserted there; for a keyed element, an edit of the key itself, or an earlier element claiming the same key (element_id.rs:174). Rule 2 is what keeps these cases away from anything an agent acts on.
- **The CARRY's mechanism claim** — "hypothesis: an edit that adds or removes an earlier same-tag sibling, or wraps an element, changes an unkeyed element's id (not measured)". Verified at HEAD, with one refinement: the index counts same-owner, same-tag siblings of one parent in order (element_id.rs:206-208; the unit pins `/div:1` and `/div:0 · /div:1 · /div:2` pass, 7 of 7 `element_id` tests), a level adds a segment (element_id.rs:219), and the shift reaches every unkeyed descendant — but it stops at a component boundary, where a template root of another owner restarts at its component chain (element_id.rs:217-220).
- **Rule 1 — the anchored path.** The id grammar in `dioxus-native-dom` (`element_id.rs`, the one place ids are computed) changes so that an unkeyed element's path begins at its nearest ancestor that reads an author key.
  - "Keyed ancestor" means an ancestor whose id IS its author key (the HTML `id`, non-empty, free of `/`, first claim) — verified: one predicate decides it (element_id.rs:170-174), and a Dioxus `key:` gives only a `{tag}[{key}]` segment unique per owner and parent (element_id.rs:210-215), so it does not anchor.
  - **Spelling — settled by the founder (inputs#I2):** an anchored path reads `key//segment`, a double slash after the anchor key and no leading mark ("A leading # starts a comment in bash and zsh … intent finding 7 wants stand flows scriptable in shell alone"). A bare `key/segment` was ruled out because a key spelled like a component name would equal that component's path (the pin at element_id.rs:347). Checked for collisions as the founder asked, none found: an author key holds no `/`, an unanchored path holds no empty segment, a document path starts with `/`, and a Dioxus tag cannot hold a `/` (research.md §Open questions).
  - **Composition — settled by the founder (inputs#I2):** the anchor acts inside one component. A component's template root keeps restarting at its component chain (element_id.rs:217-220), so `TaskShell/Counter/div:0` is unchanged and still depends on nothing in the DOM above the Counter component; the anchor applies to unkeyed elements under a keyed element of the same component. Anchoring across the boundary was ruled out: every task's root would read the same id under `task-body` on four screens, and component names would leave task ids.
  - Ids stay computed on demand and written to neither the vdom nor the DOM, with no `NodeId`, `ElementId`, `ScopeId` or pointer in them (element_id.rs:1-15) — verified as today's state; the v010-02 properties (same id across a re-render, a remount and a fresh process) must survive the rule change.
- **Rule 2 — the actionable-element check.** A check that fails when an element an agent can act on reads a positional path instead of an author key, and whose failure names the element and the remedy (give it an `id`).
  - `[premise-corrected: two engine readers exist for the founder's words — Node::is_focussable (blitz-dom node.rs:546) and the accessibility tree's role — and neither catches the one stand element an agent demonstrably acts on without a key: CRUD's person row is a div with an onclick, so it reads Role::GenericContainer and is not focusable (crud.rs:67-78; accessibility.rs:219). A third reader exists: an element with a Dioxus listener carries data-dioxus-id (mutation_writer.rs:316-323). Without that third reader the check finds nothing to key on the four lean tasks]`.
  - The role leg is state-independent (a disabled button still reads `Role::Button`), the focusability leg is not — verified in the a11y plan's own terms (a11y extract, §5); the check must hold a control to the rule whatever its state.
  - **The reader — settled by the founder (inputs#I2):** an element is actionable when it is focusable, or carries an interactive role, or carries an event listener. CRUD's person row is therefore held to the rule and gains an author key built from the person's model id; no focusability or `tabindex` change is made to it.
  - **Where the check lives — settled by the founder at the P5 review (inputs#I3):** "a public function in dioxus-native-dom that returns the actionable elements reading a positional path, each with the element and the remedy. The stand check asserts it is empty. The rule is for app authors, so the check must be callable outside the stand tests, and the later CLI and driver will reuse it. A contract addition is fine here; record it for the wrap." It reads the accessibility tree's role, so it sits behind the crate's `accessibility` feature like the snapshot (lib.rs:17-24); `dioxus-native` re-exports it through `pub use dioxus_native_dom::*` (packages/dioxus-native/src/lib.rs:27).
  - **What gets keyed — settled by the founder at the P5 review (inputs#I3):** "Key the seven Home task cards in this chunk too, and measure the three non-lean tasks with the same function: report their counts and pin a CARRY for them instead of leaving them unmeasured." Verified what that touches: the 15 lean-task controls already read author keys (stand_accessibility_ids.rs:15-44); the unkeyed listener-bearing elements in the stand's source are CRUD's person row (crud.rs:67) and Home's task-card button (app.rs:135) — 17 listener sites swept, 15 keyed. The three non-lean tasks (temp converter, circle drawer, cells) are measured by the function at implement, their counts reported, and a CARRY is owed at wrap.
- **Proof on the stand.** v010-16's acceptance reads "On the stand, after an edit of a task's code that leaves an element in place, that element reads the same id as before the edit." The stand is compiled Rust, so an edit is modelled as a before/after pair. Verified what a fixture can use: `TaskShell` is private and `task_in_shell` takes only the app's `Task` enum (app.rs:153-172), so a fixture cannot mount in the shell without a new stand API; `stand::options(incremental)` is public and is what `stand::boot` itself passes to `Harness::from_vdom` (stand.rs:58-69, 90-91); the lean-task components are public; and two components named alike in two modules read the same path segment (element_id.rs:38-41), so a before/after pair does not confound the edit with a rename. The form of the fixture is a P4 decision; the edit classes proven are the ones listed above, the "may still change" ones included as measured negatives. Per intent §Principles ("Where the tasks lack a case … a minimal fixture beside the stand proves it").
- **Existing id pins move once.** `[premise-corrected: the sweep for path-shaped ids found pins in element_id.rs (18 lines), stand_element_ids.rs (8), stand_snapshot.rs (4), stand_id_persistence.rs (2), stand_accessibility_ids.rs (1), snapshot.rs (1) and the doc comment at dioxus_document.rs:197 — but with the anchor acting inside one component and the rows keyed (inputs#I2), only the CRUD-row pins move (stand_element_ids.rs:231, stand_id_persistence.rs:15, stand_accessibility_ids.rs:271, stand_snapshot.rs:289-293 · 421); the TaskShell/{Component}/ pins and the unit pins stand]`. v010-01 and v010-02 (both verified) must still read true afterwards; v010-01's acceptance spells "every other element reads its component path", which the anchored tier makes incomplete — a premise-correction for the wrap, not a weakening.
