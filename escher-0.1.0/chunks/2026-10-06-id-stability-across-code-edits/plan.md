## Goal
An element left in place keeps its stable id when the app's code around it changes (v010-16; intent §Findings 1).
The founder settled what that means at this phase (inputs#I1, inputs#I2, inputs#I3), as two rules:

1. **Anchored paths.** An unkeyed element under an element of its own component that reads an author key takes
   its path from that element: `{key}//{relative path}`. A component's template root keeps starting at its
   component names, as today, so the anchor acts inside one component only. An edit outside the keyed element
   then no longer renames what is inside it (per architecture §Standard Contracts → Dioxus DOM bridge, amended
   at wrap on the founder's ratification).
2. **Actionable elements are keyed.** Every element an agent can act on — focusable, or carrying an interactive
   role, or carrying an event listener — reads an author key. The rule is for app authors, so its check is a
   public function of `dioxus-native-dom` that returns the actionable elements reading a positional path, each
   with the element and the remedy; the later CLI and driver reuse it (inputs#I3). The stand check asserts it
   returns nothing.

The chunk changes the id grammar in one place (`element_id.rs`), adds the library check as a new gated module,
keys the two kinds of stand element the check finds — CRUD's person rows and Home's seven task cards — measures
the three non-lean tasks with the same function, adds two stand checks (the edit proof and the actionable-key
check) and re-pins the five places that spell a row's id. No engine change and no new dependency
(research.md §Graph impact; security-plan §Dependency Security).

## Implementation Steps
1. **Anchor rule** — `packages/dioxus-native-dom/src/element_id.rs`, `element_ids` and `place_children`
   (`place_children` @ `element_id.rs:163` and `:175` are its only call sites, research.md §Graph impact). Where
   an element reads its author key (the existing predicate at 170-174: HTML `id`, non-empty, no `/`, first
   claim), each child that continues the same owner's path reads `{key}//{segment}` in place of
   `{parent path}/{segment}`; deeper same-owner descendants extend that path with `/` as today. A child that is
   a template root of another owner still restarts at its component chain (217-220), unchanged. An element
   whose `id` fails the predicate anchors nothing. The precedence becomes: author key → anchored path →
   component path → document path. Nothing else about the walk changes: ids stay computed on demand, written
   to neither tree, and free of `NodeId`, `ElementId`, `ScopeId` and pointers.
2. **Grammar docs** — the module `//!` of `element_id.rs` (1-15) and the `DioxusDocument::element_id` doc comment
   in `packages/dioxus-native-dom/src/dioxus_document.rs` (185-199) state the four tiers and the `//` spelling,
   and the sentence "Paths always contain `/` and keys never do" is extended with why an anchored path equals no
   other id (a key holds no `/`; a component path has no empty segment; a document path starts with `/`).
3. **Grammar unit tests** — seven new tests in `element_id.rs`'s `mod tests`, each an app as a plain
   `fn() -> Element`:
   - `a_keyed_parent_anchors_its_unkeyed_children` — children and a grandchild of `div#box` read `box//span:0`,
     `box//p:0`, `box//p:0/b:0`;
   - `the_nearest_keyed_ancestor_anchors` — under `div#outer { div#inner { i {} } u {} }` the `i` reads
     `inner//i:0` and the `u` reads `outer//u:0`;
   - `an_unusable_id_anchors_nothing` — children of an element whose `id` is empty, holds a `/`, or repeats an
     earlier one read plain paths with no `//`;
   - `a_component_root_under_a_keyed_element_restarts_at_its_chain` — `div#slot { Item {} }` leaves Item's
     root at `Item/b:0`;
   - `a_key_spelled_like_a_component_stays_distinct` — a `div` with `id: "Item"` holding a `b`, beside an
     `Item {}` component whose root is a `b`, reads `Item//b:0` and `Item/b:0`, and the whole list is distinct;
   - `a_dioxus_keyed_row_under_a_keyed_list_reads_its_key_segment` — `ul#list` with keyed `li` rows reads
     `list//li[ada]`, `list//li[grace]`;
   - `an_edit_outside_the_anchor_keeps_the_anchored_id` — two apps, the second with an earlier same-tag sibling
     and a wrapper outside `#box`: the anchored ids are equal; a third with an earlier same-tag sibling inside
     `#box`: the anchored id differs.
   The six existing tests keep their pins: none has an unkeyed child under a keyed same-owner parent (sweep,
   research.md §Files inspected), and the skeleton's `main` anchors nothing because its children are another
   owner's roots.
4. **The library check** — new module `packages/dioxus-native-dom/src/actionable.rs`, compiled only under the
   crate's `accessibility` feature (it reads the accessibility tree's role), wired in
   `packages/dioxus-native-dom/src/lib.rs` the way `snapshot` is (`lib.rs:17-18`, `23-24`): a gated `mod` and a
   gated `pub use`. It adds:
   - `DioxusDocument::unkeyed_actionable(&self) -> Vec<UnkeyedActionable>` — every actionable element whose id
     holds a `/`, in document pre-order; empty when every actionable element reads its author key. It takes no
     argument, writes nothing, logs nothing and never panics: a node that does not resolve is skipped.
   - `UnkeyedActionable` — public, with rustdoc on every item: the element (its `NodeId`, the positional id it
     reads, its tag and its role), which of the three readers matched, and `remedy()`, text that names the fix —
     an HTML `id` that is non-empty, holds no `/` and is unique in the document. No field or text carries the
     element's text content, accessible name or an attribute value.
   - An element is actionable when any of three existing readers says so: `Node::is_focussable()`
     (`packages/blitz-dom/src/node/node.rs:546`); its accessibility node's role is in the closed list Button,
     Link, CheckBox, RadioButton, Slider, SpinButton, ScrollBar, ComboBox, ListBox, ListBoxOption, MenuItem,
     MenuItemCheckBox, MenuItemRadio, Tab, TreeItem, DisclosureTriangle, MultilineTextInput, plus every role
     `role_from_element_data`'s `input` arm returns (`packages/blitz-dom/src/accessibility.rs:260` onward); or it
     carries the `data-dioxus-id` attribute, which the bridge writes for every listener but `onmounted`
     (`packages/dioxus-native-dom/src/mutation_writer.rs:309-323`). Ids come from `element_ids()` and roles from
     `accessibility_tree()` — no second id or role computation. An element the accessibility tree leaves out
     (hidden) is still held by the other two readers.
5. **Library unit tests** — four tests in `actionable.rs`'s `mod tests`:
   - `an_unkeyed_actionable_element_is_reported_with_its_remedy` — a fixture with an unkeyed button, an unkeyed
     disabled button, an unkeyed `div` with a click handler, a button whose `id` repeats an earlier one, and a

## Constraints & rejected approaches
- A leading `#` on the anchor key — rejected by the founder: it starts a comment in bash and zsh, and intent
  §Findings 7 wants stand flows scriptable in shell alone (inputs#I2).
- A bare `key/segment` — rejected: a key spelled like a component name would read that component's path
  (`Item/b:0`, the pin at `element_id.rs:347`).
- Anchoring across component boundaries — rejected by the founder (inputs#I2): every lean task's root would
  read the same id under `task-body` on four screens, and component names would leave task ids.
- A test-local check with no library entry point — rejected by the founder (inputs#I3): the rule is for app
  authors, and the later CLI and driver reuse the function.
- A second id or role computation inside the library check — not done: ids come from `element_ids()` and roles
  from `accessibility_tree()` (a11y-plan §7; architecture §Standard Contracts → Dioxus DOM bridge).
- Adding `tabindex`, a `role` or a focusability change to the CRUD row to make it satisfy the check — not done:
  it changes the Tab order a11y-plan §5 pins; the row is keyed, nothing else.
- Deriving a key from text, a name or a list index — not done: security-plan §Input Validation bars a list
  index, pointer, hash, clock or process-local value from an id; a row's key is the person's model id and a
  card's key is a fixed slug.
- Keying the three non-lean tasks — not in this chunk: they are measured and carried (inputs#I3).
- Any print or log of an id in the id module, the library check or the stand checks — not done: the library
  returns data and the stand check's failure text travels as a test assertion message only (obs-plan §3; §6).

## Implementation notes

  holds no `/` (`element_id.rs:173`); a path that is not anchored either starts with `/` (document and app-root
  paths, `element_id.rs:163` with an empty base) or is a component chain of non-empty names followed by
  non-empty `{tag}:{n}` / `{tag}[{key}]` segments (`element_id.rs:103-114`, `210-215`), so it holds no `//`;
