## What this chunk builds
The driver's second surface: **the driver's commands as MCP tools**. intent §8 states the gap and the expectation — "OBSERVED: none." → "EXPECT: the same commands are exposed as MCP tools, and an agent session completes a stand flow through them." (`escher-0.1.0/intent.md:65-67`). The first surface is built: every driver command runs as one run of the `escher-session` binary (`escher_driver::command_line`, `packages/escher-driver/src/cli.rs:67`), over the one verb table (`VERBS`, nine verbs in two levels, `packages/escher-driver/src/schema.rs:388-390`).

- **Driver commands as MCP tools** — an MCP client lists the driver's tools and calls them; a tool is a verb of the one table, with the argument and result shapes the table states, and a refused call is a `Refusal` naming one of eight causes with its fixed remedy (CARRY 2). Which of the three session-level verbs (`start` · `status` · `stop`) become tools is decided here (CARRY 3; decision 3 below).
- **Local to the invoking user, no listener or auth surface** — the surface opens no port and no new socket and adds no credential path.
  - Verified at P3 against the fetched specification: the transport is the client's own child process speaking on its standard input and output — "The client launches the MCP server as a subprocess", messages "delimited by newlines", and "The server **MUST NOT** write anything to its `stdout` that is not a valid MCP message" (research.md §Scope, Platform issues consulted) — as the cold-agent pipe's stub already does (`scripts/cold_agent_stub.py:2`). MCP's other standard transport, Streamable HTTP, is "an independent process that can handle multiple client connections" — a listener — and is out by the entry's own words.
  - Verified at P3 as an open fork, both doors built: the MCP server process holds a `Session` itself and runs each call in process (`Session::run`, whose one production caller today is the host, `packages/escher-driver/src/host.rs:198`), or it is a client of a hosted session and sends each call over the registered socket (`escher_driver::call`, `packages/escher-driver/src/client.rs:82-90`, whose one production caller is the command line, `packages/escher-driver/src/cli.rs:315`). The second keeps one instance reachable by the command line and by MCP at once and is unix only; the first needs no host and no socket and works wherever a `Session` does. The operator's fork, with a founder-facing consequence on each side (decisions 3 and 5).
- **A tool call parents its trace** — every tool call leaves a span, and what the call does is recorded under it.
  - Verified at P3 by reading the code, not by a run: today a call leaves one span, `command` under the target `escher_driver`, made and entered inside `Session::run` with no `parent:` argument (`packages/escher-driver/src/execute.rs:74`, `:110-119`), eight fields of fixed words and counts (`execute.rs:79`). "Parents its trace" reads: the tool call's span is the parent of that `command` span. In one process a span made with no `parent:` takes the span entered on its thread as its parent, so a tool-call span entered around `Session::run` parents it with no change to the executor — the plan's first check runs this. The parent is not readable from the sink's lines: a closed span's line prints its own name and fields only (`packages/escher-telemetry/src/format.rs:162-173`), so the proof is a check's own subscriber, and a parent on the line itself would be a change to a ratified record class. Across the socket the nesting does not exist: the `command` span is made in the host process, and parenting it under a span of the MCP process needs a trace identity carried in the request — a new field on the wire, of an open value set, so a crossing question (decision 5).
  - Verified at P3 as a requirement (obs-plan §4, by the obs extract): the tool call's span follows the command span's rule — fixed schema words, bools and counts only; no id, name, value or call-supplied argument in a field, and of what MCP adds as client text (the tool name as the client spelt it, the request's `id`, the method string, the `arguments` object, a client's name or version) none is fielded. It sits under an `escher_` target, or the sink drops it whole.
- **An agent session completes a stand flow through them** — v010-13's acceptance: "Every command available on the command line is also offered as an MCP tool, and an agent session completes a stand flow using only those tools." (`matrix.py show --id v010-13`; method `dynamic-external`, unclaimed).
  - Verified at P3: what an "agent session" is, as a proof, is open. The pipe that runs one exists: `scripts/cold-agent.sh run counter` spawns a `claude` client with one stdio MCP server and no other tool (`.andromeda/test-plan.md:122`; `scripts/cold-agent.sh:256-257`), and its live run uses the operator's own login on the dev host only, reaching the model provider (`.claude/rules/security.md` §Secrets, §Surfaces). The pipe is bound to its stub: its `isolated` reading requires the client's tools to be exactly the stub's three and one connected server named `stub`, its task list is `(counter)` and its prompt is fixed (`scripts/cold-agent.sh:12`, `:15`, `:92-110`) — running the real server through it changes each, and each is pinned by `.github/scripts/test_cold_agent.py` (27 tests). What the founder ratified for the pipe (2026-10-06) is the toy stub's content reaching the provider, not the stand's screen. A scripted MCP client (a check that speaks the protocol with no model) is a second reading; it runs in CI and is no agent. Which one v010-13 means decides what its acceptance says — the founder's by `inputs#I1` (decision 4). The Cold-agent test itself is a later entry (`working-route.md:100`, v010-15).
- **The server reads JSON** `[premise-corrected: the take-up bullet named the requests of the handshake revisions only; the specification's current revision, 2026-07-28, has no `initialize` — research.md §Scope, Platform issues consulted]` — MCP is JSON-RPC 2.0 and every request arrives as JSON and must be parsed; which requests arrive depends on the protocol era. The revisions up to `2025-11-25` open with an `initialize` handshake, then `tools/list` and `tools/call` — what the pipe's stub speaks (`scripts/cold_agent_stub.py:120-132`). The current revision, `2026-07-28`, has no handshake: every request carries its protocol version, the client's identity and capabilities in a `_meta` object, a `server/discover` request is mandatory for a server to answer, and a result carries `resultType`. A server may speak either or both; a client of the current revision alone fails against a handshake-only server. Which era this server speaks is the operator's fork. Nothing in the driver reads JSON today: its `json` module is "Output only: nothing here reads JSON" (`packages/escher-driver/src/json.rs:1-2`), the socket's wire is a line grammar of its own (`packages/escher-driver/src/wire.rs:1-3`), and `escher-driver` names three crates, none a serialization crate (`packages/escher-driver/Cargo.toml:13-16`). The workspace names `serde` (`Cargo.toml:165`) and no `serde_json`; one member names it in its own manifest (`wpt/runner/Cargo.toml:52`) and the lock holds 1.0.151 (`Cargo.lock:7257`). Found at P3: `serde_json` is already compiled into `escher-driver` and into the stand's binary through the Dioxus crates (`cargo tree --locked -p escher-driver -e normal -i serde_json`), so naming it adds no package to either build. The MCP Rust SDK, `rmcp` 3.5.1, is not in the lock. A reader written by hand, `serde_json` named directly, or the SDK — decision 2, the founder's by `inputs#I1`; a named dependency is an arch §Stack registration (CARRY 4).
- **What the client sends is untrusted input** — verified at P3 as the rule every outside surface of the schema already follows (`.claude/rules/security.md` §Surfaces: "each through `validate` before anything is sent or run"): a request line comes from the agent's client, is read under a byte bound, a line outside JSON or outside the protocol is answered with a JSON-RPC error and runs nothing, and a tool call reaches `escher_driver::validate` before anything runs. No panic path on what a client supplies. The socket's own bounded reader cannot be reused as it stands: it builds a fresh buffer per call and fits one request per connection (`packages/escher-driver/src/wire.rs:287-289`).
- **`tools/list` serves the table** — verified at P3: the specification asks of a tool a `name`, a `description` and an `inputSchema`, and each is producible from the table's `'static` data — a verb's name and help, each argument's name, kind, bound and help (`packages/escher-driver/src/schema.rs:42-94`, `:155-165`). The verbs' names fit the specification's tool-name characters. This is the first place the table's help strings are served to anyone, which is the next entry's subject ("Self-description — verb list, help and schemas served by CLI and MCP from the one schema (v010-14)", `working-route.md:81`); where the line falls is under Boundaries.
- **A tool result's form** — verified at P3 against the fetched specification: a tool result is a list of content blocks with an `isError` flag; "Input validation errors" and business-logic errors are tool results with `isError: true`, which a client hands to the model, while an unknown tool and a request that is no well-formed call are JSON-RPC errors (`-32602`). The driver's answers already have one written form each, a line of JSON (`Outcome::to_json`, `Refusal::to_json`, `SessionError::to_json`, `json.rs:215`, `:255`, `:272`), and that writer leaves no raw line break in any text (`json.rs:16-32`), which a newline-delimited protocol line needs. Whether a tool result's text is that same line is the operator's fork; whether the writer is reused is CARRY 4.
