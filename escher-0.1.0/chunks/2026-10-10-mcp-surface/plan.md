## Goal
The driver gets its second surface: every driver command as an MCP tool. A client spawns `escher-session mcp` as its
own child and speaks MCP with it over the child's stdin and stdout, newline-delimited JSON-RPC 2.0, in the handshake
revisions (`initialize` · `tools/list` · `tools/call`). The surface has no listener, port, socket, file or
credential, so it is local to the invoking user. The server holds the app in its own process. All nine verbs of the
one table are tools: `start <app>` boots the app inside the server through the boot the binary hands over, and
`status` and `stop` act on that held session. Each `tools/call` leaves one `tool_call` span under `escher_driver`.
The driver's existing `command` span is its child by plain nesting, so the entry's "tool call parents its trace"
holds with no change to the executor.

A tool result is the driver's existing written form, except one case. A `snapshot` result's text block is
`Snapshot::to_text`'s output byte for byte. Every other result is the line of JSON the command line prints, and a
refusal and a session error carry `isError: true` (`inputs#I2`). Requests are read with `serde_json` as a reader only;
answers stay written by the crate's hand writer (`inputs#I3`, fork 2A). This crossing was ratified by the founder as
stated (`inputs#I3`, fork 1A): ids, accessible names, control values (a password's or a file input's as the mask),
the snapshot text and the diff out; an id and typed text in; the request's `id` echoed back within its bound.

v010-13 is claimed and proved three ways. A scripted MCP session completes a Counter flow by tool calls alone, both
in process in both layout modes and through the binary as a child process. One small live agent session on the dev
host, whose only tools are this server's, does the same in the operator pass (`inputs#I3`, fork 3A). Per
architecture §Standard Contracts (Driver session), security-plan §Input Validation, obs-plan §4 and test-plan §2 · §5
· §6 · §9.

5. **The MCP server — new module `packages/escher-driver/src/mcp.rs`.** It opens with a `//!` doc and exposes one
   public function, re-exported at the crate root:

   ```
   serve_mcp(input: impl BufRead, output: impl Write, apps: &[&str],
             boot: impl FnMut(&str) -> Result<Session, SessionError>, idle_expiry: Duration)
             -> Result<(), SessionError>
   ```

   It answers requests until the input ends (`Ok(())`); a failed read or write is `SessionError::Io`. It installs no
   subscriber, reads no environment variable and writes nothing but protocol lines to `output`.

   - **The line reader.** Reads one request line of at most `MAX_MCP_REQUEST_BYTES` = 65,536 bytes, terminator not
     counted, from the one `BufRead` it holds for its whole life, never a fresh buffer per line. Read-ahead bytes must
     survive; `wire::read_line` builds a fresh buffer per call and is not reused (`wire.rs:287-289`).
     - A longer line is read to its terminator and dropped, and answered `-32700`.
     - An empty line is skipped.
     - A line that is not UTF-8 or not JSON (`serde_json::from_str::<serde_json::Value>`) is answered `-32700`.
   - **The envelope.**
     - A JSON value that is not an object with `jsonrpc: "2.0"` and a string `method` is answered `-32600`.
     - A request with no `id` member is a notification and gets no reply, whatever its method.
     - An `id` that is not an integer (i64) and not a string of at most 128 bytes is answered `-32600` with `id: null`.
       Otherwise the reply echoes the `id`: an integer written back as an integer, a string through `json::string`.
       This echo is the one thing a client sent that is written back (`inputs#I3`, fork 1A).
   - **Methods.**
     - `initialize` answers `protocolVersion` with the client's requested version when it is one of `2025-06-18` ·
       `2025-03-26` · `2024-11-05`, and `2025-06-18` otherwise. It also answers `capabilities: {"tools": {}}` and
       `serverInfo: {"name": "escher", "version": <escher-driver's CARGO_PKG_VERSION>}`. Nothing the client sent in
       its `initialize` (its capabilities, its name or version) is read further, kept or written anywhere.
     - `ping` answers `{}`.
     - `tools/list` answers the nine tools (below), with no `nextCursor`.
     - `tools/call` (below).
     - Every other method is answered `-32601`. That includes `server/discover`, which tells a client of the current
       revision that this server speaks the handshake revisions.
     - Requests before `initialize` are served as after it; the handshake is not enforced.
   - **Protocol errors.** Each is a fixed `code` and a fixed `message` — `parse error` · `invalid request` ·
     `method not found` · `invalid params` · `unknown tool` — with no `data` and nothing of the request in it.
   - **The tool listing**, built from `VERBS` alone in the table's order. Each tool is `name` (the verb's name),
     `description` (the verb's `help`) and an `inputSchema`: `{"type":"object","properties":{…},"required":[…],
     "additionalProperties":false}`, with one property per `ArgSpec` in the table's order. Each property carries a
     `type` by kind, and a `description` written as the arg's `help`, then ` (`, then `ArgKind::bound()`, then `)`:
     - `id` · `text` · `name` → `"string"`; `key` → `"string"` with `"enum"` = `KEY_NAMES`; `flag` → `"boolean"`;
       `milliseconds` → `"integer"` with `"minimum": 1` and `"maximum": MAX_MILLISECONDS`;
     - `start`'s `app` gets `"enum"` = the `apps` the binary hands over;
     - `required` lists the args whose `required` is true.

     No string is written that the table or `apps` does not hold.
   - **A tool call.** `params` must be an object with a string `name`; `arguments` is optional (absent reads as `{}`)
     and, if present, must be an object. Otherwise the call is answered `-32602 invalid params`. A `name` that is not
     a verb of `VERBS` is answered `-32602 unknown tool`. Otherwise the call becomes a `Call { verb, args }`, one
     argument per member in the object's order:
     - a JSON string → `ArgValue::Text`, an integer in i64 → `ArgValue::Number`, a boolean → `ArgValue::Flag`;
     - any other value (null, a non-integer number, an array, an object) refuses the call `malformed` before anything
       else, with `Fault::WrongKind(<the table's name>)` when the verb's table names the argument and `Fault::Unnamed`
       when it does not.

     An instance-level verb then runs through `Session::run` on the held session. A session-level verb is checked by
     `validate_session` and answered by the server itself:
     - `start`: `boot(app)`, held; it is `AlreadyRunning` when one is held. Its answer is `json::started` of a `Hello`
       holding the app's name as label, `std::process::id()`, `served: 0` and `idle_expiry.as_secs()`.
     - `status`: `json::status` of the same, with `served` the count of tool calls answered on the held session
       before this one.
     - `stop`: drops the held session and answers `json::stopped()`.
     - An instance verb, `status` or `stop` with no held session is `SessionError::NoSession`.
   - **The tool result.** Every tool result is `{"content":[{"type":"text","text":…}],"isError":…}`:
     - an accepted `snapshot` → `text` is `Outcome::Screen`'s text itself, `isError: false`;
     - any other accepted call → the call's JSON line (`Outcome::to_json`, `json::started` · `status` · `stopped`),
       `isError: false`;
     - a refusal → `Refusal::to_json()`, `isError: true`;
     - a session error → `SessionError::to_json()`, `isError: true`.

     A result whose `text` is over 1,048,576 bytes (`MAX_ANSWER_BYTES`, as on the socket) is replaced by
     `SessionError::AnswerTooLarge`'s result: the call ran and is not rolled back. Every reply is one line: the whole
     JSON-RPC object written through `json.rs`'s `Object` and `string`, a `\n`, then a flush.
   - **Idle expiry.** When a request arrives and a session is held, the server compares the time since the last
     answered tool call (or since `start`) with `idle_expiry`. At or past it, the session is dropped before the
     request is handled. No timer and no thread; the read blocks as before.
   - **The `tool_call` span** — the founder's fork 4A (`inputs#I3`). Each `tools/call` request, and nothing else,
     opens `tracing::info_span!(target: "escher_driver", "tool_call", tool = Empty, ending = Empty)` and enters it
     before its `params` are read; it stays entered until the result is written.
     - `tool` is recorded as `row.name` from `schema::verb` when the call names a verb of the table, and is absent
       otherwise.
     - `ending` is recorded as `accepted` (an accepted call), `refused` (a `Refusal`) or `error` (a session error or
       a protocol error).
     - No other field. Nothing the client sent is recorded, nothing of a result, no length.
     - The `command` span that `Session::run` makes (`execute.rs:74`, no `parent:`) then has `tool_call` as its
       parent.
   - **No panic path on what a client sends:** no `unwrap`, `expect`, `panic!`, `unreachable!` or index outside the
     `#[cfg(test)]` module, and no print.

   **Unit tests, inline:**

     - the reader's verdicts: over-bound, empty, non-UTF-8, non-JSON, not an object, no `jsonrpc`, a notification;
     - each admitted and refused `id` form, with 128 and 129 bytes as the edges;
     - each method and the reply it gets;
     - each JSON value kind in `arguments` and the `ArgValue` or refusal it becomes;
   - the listing's nine tools against `VERBS`: name, description, property names in order, `required`, type per kind;

   - two requests sent in one `write` read as two;
   - assertions over a request carry a row index only.

## Implementation notes
- **The parent equality:** `Session::run` makes `command` with `tracing::info_span!` and no `parent:`
  (`execute.rs:74`, `:111`), so its parent is the span current on the thread when it is made. With `tool_call`
  entered around the call, that is `tool_call`. Read from the code and from `tracing`'s rule for a span macro without
  `parent:`, and not run; step 12's subscriber runs it. A reading of `command` with no parent there is a defect in
  step 5's enter, never in the executor.
- **Why the sink cannot show it:** a closed span's line prints the span's own name and stored fields
  (`packages/escher-telemetry/src/format.rs:162-173`), so `mcp_log` counts lines and the in-process check proves the
