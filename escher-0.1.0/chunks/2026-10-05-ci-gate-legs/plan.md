## Constraints & rejected approaches
- cargo-audit as the gate — rejected at the P4 fork (overseer): it fails on vulnerabilities only, so unmaintained
  and unsound findings would stay unowned.
- A rust-cache entry for the coverage job — rejected at the P4 fork (overseer): an instrumented target over a
  ≈ 9.73 / 10 GB cache evicts the other legs' entries.
- `-p blitz-tests` for the a11y leg — rejected: it resolves features differently from the `test` leg, so the
  restored shared cache would not match. Use `--workspace --test …`.
- A new job in `FAST_JOBS` — rejected: every slow job `needs` the fast set, so an advisory-DB red would block them
  all, and `test_c` pins the set.
- Renaming the browser bin `blitz` — rejected: §Occupied Resources → Names. `doc = false` resolves the collision.
- `--keep-going` in the doc leg — rejected: the gate must stop red. `--keep-going` is a diagnostic only.
- A blanket advisory allow, or `unmaintained`/`unsound` set to none — rejected: it empties the gate (security-plan
  §Dependency Security). Use per-ID ignores with reasons.
- Bumping one side of a coupled pin to clear an advisory — rejected (CLAUDE.md, arch §Established Decisions →
  [Dependency pinning]). Record such an advisory as a reasoned ignore.
- Pinning or adding `permissions` to publish-browser.yml / wpt.yml / wpt-post-results.yml — not this chunk. They never
  run on the fork, and a ref-only `if:` would re-arm them (UpstreamGuardTest keeps the guard).
- Per-job `permissions` blocks duplicating the workflow-level one — rejected: inherited, and the duplication adds no
  narrowing.
